01 · 用好 AI 编程：从会生成到能交付

发表于 2026-08-06 分类于 AI Agent 学习笔记 · 01 用好 · 个人交付

开篇 · 真实案例：B 端控制台登录，周五下午翻车

00 / 案例背景

一项看似简单的认证需求，如何在 AI 的快速生成下变成一次交付翻车？先从这个周五下午的 B 端控制台案例说起。

1. 项目背景与初始任务

团队在做一套内部 B 端控制台。迭代目标很具体：先打通邮箱注册 / 登录 / 登出，让运营同学能进系统配数据；OAuth、多租户、「记住我」都明确排到后面。后端已有 Express + TypeScript 骨架，会话打算沿用现有 session 方案，密码哈希与错误体规范写在仓库文档里。

负责这块的同学（下文称阿明）周五上午接到口头需求：「认证先做起来，下午最好能联调。」他打开 Cursor，把仓库根目录丢进上下文，输入一句：

帮我实现用户认证，要安全一点，最好用现在流行的写法。

2. 看似完成，实际失控

大约四十分钟，Agent 交出一大坨 Diff——注册、登录、JWT 中间件、若干工具函数，文件数后来统计超过 40 个。本地 npm test 当时大部分是绿的（很多是新写的、断言很松的测试）。阿明开了 PR，描述只有一行：「AI 生成认证模块，请 review。」

中午前他觉得自己赢了：需求含糊，输出却「看起来完整」。这是整场翻车最危险的一刻——把生成成功当成了交付成功。

3. 联调与 Review 的事实证据

14:30 前端联调。运营试用账号登录后点退出，再请求 GET /me，响应仍是 200，用户信息还在。紧接着错误弹窗里出现了服务器绝对路径。Code review 又揪出更刺眼的改动：密码哈希相关文件被「顺手优化」成另一套算法，与库里已有用户数据不兼容；顺带还起草了一截没人要的 OAuth 草稿。

时间线发生了什么表面结论
10:20一句 Prompt + 整仓上下文开工很快有代码
11:10大 Diff PR，测试「基本绿」好像做完了
14:30登出后 /me 仍 200会话没真正失效
14:45错误体泄路径；哈希被改；OAuth 多余禁区与范围都失控
15:00想「再生成一次整模块」差点在错误方法上加码

4. 停手，改用法

阿明没有换模型硬刚。他和 reviewer 达成共识：问题不在模型够不够强，而在输入、拆步、验收全没立住。后文整条线，就是他们把这次认证从「会生成」修到「能合并」的过程——先归层，再写契约、收证据、拆工序、失败写回，直到 PR 带上手动验收三步、CI 实打实转绿。

思考：生成结果为什么不能直接等于交付结果

这次翻车表面上发生在登出接口，实际上发生在更早的地方：任务没有被定义成可判断的目标，AI 也没有被限制在可靠的依据和可检查的步骤里。

因此，AI 编程真正需要解决的不是“怎样让模型一次写出更多代码”，而是三个问题：它应该改什么、依据是什么、怎样证明改对了。只要这三个问题没有答案，代码生成得越快，错误扩散得也可能越快。

带着这个问题继续：怎样把一个模糊的“做个登录”，变成 AI 和 reviewer 都能执行、检查并否决的工程任务？

Part 01 · 翻车归层：失败不是一个点

01 / 诊断

先别让 AI「再生成一次」。先问：这次到底死在哪一层？归错层，换再强的模型也是原地打转。

1. 当前现场：为什么不能直接「再生成」

阿明 15:00 的第一反应是：把整段认证模块删掉，换个更强模型，再生成一遍。这几乎是最常见的坏习惯。

危险点：「再生成」默认假设——上次失败只是模型不够好。但认证下午同时爆了四类问题：范围跑偏、依据没读、步骤不可检、失败没写回。它们不是同一类病，不能靠同一种药治。

正确动作是先归层：把现场现象映射到「说不清 / 依据错 / 步骤不可检 / 无闭环」四层之一（或叠加），再决定下一轮输入该改什么。

2. 核心问题：失败不是一个点

每一层看三样：现场长什么样 · 错误反应 · 正确处置

L1 · 说不清

目标与边界没钉死

现场：Prompt 只有「安全一点、流行写法」；Diff 里冒出本期没人要的 OAuth 草稿。

错反应：继续加功能，或让 AI「再完善一下登录」。

正确：先写清 Goal / Non-goals / Acceptance，再让 AI 动代码。

L2 · 依据错

没读对现行规范

现场：哈希被「顺手优化」；错误体把服务器路径打到前端；会话方案与仓库现有 session 不一致。

错反应：整仓 @ 进上下文，指望模型自己找对文件。

正确：只挂最小充分证据：会话实现、错误体规范、密码哈希禁区。

L3 · 步骤不可检

一次改太多，没法验收

现场：单次 PR 超过 40 个文件；本地测试「松绿」；联调才发现登出后 /me 仍 200。

错反应：一口气重生整模块，继续大 Diff。

正确：拆成可中断步骤，每步有命令/手动检查点，过了再往下。

L4 · 无闭环

失败没有写回输入

现场：联调红了，下一轮仍是「帮我修一下认证」；已知约束（登出必须失效、禁改哈希）没有进入 Prompt。

错反应：同一句话重试，或换模型硬刚同一输入。

正确：把失败现象写成下一轮硬约束，再小步回流。

3. 事实证据：现场现象如何归层

现场现象归属层根因一句话下一动作
做了 OAuth 草稿，本期没人要说不清目标与非目标没写死补契约，再动代码
哈希被「优化」、错误体泄路径依据错没指定必读规范与禁区收证据包，标禁区
一次 PR 改了 40+ 文件步骤不可检没有一步一验收拆 T01→Tn，设检查点
测松绿、联调才爆，仍想整模块重生无闭环失败没有写回下一轮输入失败写进回流 Prompt

4. 诊断结论：按顺序补缺

按顺序问，停在第一个「否」：

  1. 有没有可观测的验收句？（没有 → 说不清）
  2. AI 是否读对了现行代码 / 规范 / 禁区？（没有 → 依据错）
  3. 能否指出「做到哪一步、怎么证明过了」？（不能 → 步骤不可检）
  4. 失败后下一轮输入有没有新增约束？（没有 → 无闭环）
叠加很常见：阿明那次四层同时中招。处理顺序建议固定为：先说清楚 → 再给依据 → 再拆步骤 → 最后谈回流。后文 Part 02 起，就是按这个顺序把认证救回来。

常见误判：归错层会怎样

误判你实际在做的事典型结果
明明说不清，却猛加证据@ 更多文件，仍无验收句生成更完整，交付仍对不上
明明依据错，却换更强模型同一错误上下文，换引擎哈希/禁区问题复现
明明步骤不可检，却整模块重生更大 Diff、更难 review联调继续爆，PR 更难合
明明无闭环，却同一 Prompt 重试失败信息没进入下一轮同一坑踩第二遍

思考：诊断比重新生成更重要

同样是“登录失败”，可能是需求没有说清、现行规范没有读到、步骤无法验证，或是失败没有写回下一轮输入。症状相同，不代表根因相同；根因不同，修复动作也不该相同。

因此，归层不是给问题贴标签，而是为下一步选择正确的修复入口。先找到第一个缺口，再补齐它，才能避免把“换模型、加上下文、重生整模块”变成条件反射。

带着这个判断进入下一章：既然四层问题需要按顺序补缺，具体该如何把修复动作组织成一套可执行的计划？

这一幕带走：翻车先归层。四层可以叠加，但药不能混着开——先对症，再生成。

Part 02 · 修复计划：说清楚 · 给依据 · 跑可靠 · 变更好

02 / 总图

认证要救回来，不是换一个更强的模型，而是把四件事按顺序补齐——同一任务上的四层加固，不是四套互斥技巧。

1. 修复背景：归层之后，为什么先立计划

归层之后，阿明和 reviewer 没有立刻再开一轮生成。他们先把修复计划钉成四件事，并约定：缺哪一层，就不进入下一层。

说清楚要什么、不要什么、怎样算过
给依据最小充分的文件与规范
跑可靠一步一检、可中断可续
变更好失败变成下一轮约束
一句话：模型负责写 Diff；这四件事负责让 Diff 变得可合并。缺一层，就等于把「会生成」伪装成「能交付」。

2. 核心问题：四层缺口如何同时存在

每一格：翻车前怎么做 · 计划改成什么 · 后文哪章展开

① 说清楚

任务契约

翻车前：「做个登录，安全一点，流行写法。」

改成：Goal + Boundary + Acceptance + Non-goals；验收句可一票否决。

对应层：说不清 → Part 03

② 给依据

证据包

翻车前：整仓 @，指望模型自己找对文件。

改成：只挂 session / auth 路由 / 错误体规范 / 现有测试 + 契约全文。

对应层：依据错 → Part 04

③ 跑可靠

可检查工序

翻车前：一口气生成 40+ 文件，测试松绿就开 PR。

改成：T01→T06，每步有命令或手动检查点，过了再往下。

对应层：步骤不可检 → Part 05

④ 变更好

失败回流

翻车前：联调红了，同一句「修一下」重试或换模型。

改成：把红测 / 联调现象写成下一轮硬约束，小步回流。

对应层：无闭环 → Part 06

3. 计划证据：翻车前与修复动作的对照

翻车做法修复计划解决的问题
「做个登录」一句糊带验收的契约说不清：OAuth 乱跑、完成标准虚
整仓 @最小充分证据包依据错：哈希被改、错误体泄路径
一口气生成整模块T01→T06 一步一检步骤不可检：大 Diff、联调才爆
测红了再试 / 换模型失败写进下一轮 Prompt无闭环：同一坑反复踩

4. 执行结论：四件事必须按顺序补齐

  1. 先说清楚——没有可否决的验收句，后面三件事都会漂。
  2. 再给依据——契约有了，但禁区与现行实现没进视野，模型仍会「优化」哈希。
  3. 再跑可靠——证据齐了，仍一口气大 Diff，review 与联调救不回来。
  4. 最后变更好——前三层立住后，失败才有地方写回；否则回流只是换皮重试。

阿明案例的最短路径：

  1. 停手，不删模块重生
  2. 按 Part 01 归层（四层叠加）
  3. 按本计划补齐四件事
  4. 从 Part 03 起逐项落地，直到 PR 可合并
干货：四件事是串联加固，不是菜单点菜。常见误用是「只加强 Prompt」或「只多 @ 文件」——那是单点补丁，救不回认证这种复合翻车。

常见误解：这四件事不是什么

容易误解成实际是
四套互斥工具，选一个就行同一任务上的四层，通常要一起上
换更强模型的替代说法模型可换；用法结构不变
写完文档再开始写代码契约与证据可以短，但必须可检查
只适合大项目认证这种「半天联调」任务，缺一层一样会翻

思考：修复计划不是更长的 Prompt

“说清楚、给依据、跑可靠、变更好”看上去像四项准备工作，实质上是在把产品判断、仓库事实、执行检查和失败学习重新放回工程流程中。它们不是为 AI 增加仪式，而是为每一次变更建立可判断的边界。

如果只补其中一项，例如只把 Prompt 写得更长，或只追加更多文件，问题仍可能从另一个缺口进入。真正有效的修复，不是让模型一次做得更多，而是让每一步都知道为什么做、依据什么做，以及怎样证明做对了。

带着这个思考进入下一章：四件事中的第一件——“说清楚”，怎样被写成 AI 和 reviewer 都能否决的任务契约？

这一幕带走：修复计划 = 说清楚 → 给依据 → 跑可靠 → 变更好。下一章从「说清楚」开始，把「做个登录」写成可否决的契约。

Part 03 · 说清楚：把「做个登录」写成契约

03 / 契约

AI 不是读心术。你不写可否决的验收，它就用「看起来完整」当完成——阿明上午的「赢」，就是这么来的。

1. 契约背景：为什么必须先写契约

修复计划的第一件事是说清楚。说不清楚，证据包再精、工序再细，模型仍在猜「完成长什么样」。

阿明翻车根因之一：口头需求「认证先做起来」+ Prompt「安全一点、流行写法」——没有目标边界，没有可否决验收。OAuth 草稿、JWT 乱入、哈希「优化」，都是在填你没写死的空白。

契约不是长文档，是给 AI 和 reviewer 共用的短规格：写什么算过、写什么不许碰、写什么本轮不做。

2. 问题对照：从翻车版到可交付版

左边是阿明上午那句；右边是当场改成的契约骨架

翻车版：

帮我实现用户认证，要安全一点，最好用现在流行的写法。

可交付版（五块齐全）：

Goal: 注册 / 登录 / 登出；受保护接口在未登录或登出后返回 401。 Boundary: 只改 auth 相关模块（路由、session、中间件、对应测试）。 禁止修改密码哈希算法、禁止触碰生产密钥与 .env。 Acceptance:（任一失败 = 未完成） 1) auth 相关单测全绿 2) 手动：登录 → GET /me 200 → 登出 → GET /me 401 3) 错误响应不泄露堆栈与绝对路径 Non-goals: 本轮不做 OAuth、不做多租户、不做「记住我」长期会话。 Evidence:（下一章展开） session 实现、auth 路由、错误体规范、现有测试样例。

3. 证据与标准：契约五块各自做什么

Goal

要交付什么

用结果语言写，不写「实现认证模块」。阿明版：注册 / 登录 / 登出可用，受保护接口在未登录与登出后均为 401。

Boundary

改哪里 · 禁哪里

改动面 + 硬禁区。禁改哈希、禁碰 .env，就是为了挡住「顺手优化」和密钥泄漏。

Acceptance

怎样算过

每条必须可观测、可一票否决。测绿 + 手动路径 + 错误体不泄密，三条任一失败 = 未完成。

Non-goals

本轮明确不做

OAuth / 多租户 /「记住我」写进非目标，模型才不会用「流行写法」把范围撑爆。

Evidence 放哪：契约里可列证据清单作索引；具体挂哪些文件、怎么筛，是 Part 04。五块里前四块必须当场写清，Evidence 可以「先列名、后展开」。

4. 落地执行：验收句怎么写才算数

核心标准就一条：别人能不能根据这句话说「没过」而不吵架。

不合格（无法否决）合格（可一票否决）
尽量安全一点错误响应不出现堆栈与绝对路径
登录体验好一点正确账号登录后 GET /me 返回 200 与用户字段
会话处理好登出后再请求 GET /me 必须 401
测试差不多绿就行auth 相关单测全绿；任一红则本步未完成
别改太多无关代码Diff 仅限 auth 路由 / session / 中间件 / 对应测试

写 Acceptance 的三问：

  1. 失败时，我能指出哪一条命令或哪一次手动请求证明它挂了吗？
  2. 成功时，reviewer 能不能复现同一条路径？
  3. 这条验收是否依赖「感觉」「看起来」？有 → 重写。

补充清单：五分钟完成契约初稿

  1. Goal：用「用户能做什么 / 系统必须返回什么」写结果，不写实现口号。
  2. Boundary：列出可改路径；至少写一条硬禁区（哈希、密钥、无关模块）。
  3. Acceptance：≥2 条可观测句；标明「任一失败 = 未完成」。
  4. Non-goals：至少写出本期最容易被「流行写法」带偏的 1～3 项。
  5. 对齐：和 reviewer / 联调方对一遍验收句，无歧义再开生成。
案例节点：阿明补完这份契约后，OAuth 从「顺手做了」变成「明确不做」；登出后 /me 401 从「应该会吧」变成「不过就不能合」。后面证据包与工序，都挂在这份契约上。

思考：契约的价值是允许明确地说“不通过”

一份契约不是为了把 Prompt 写得更长，而是把“完成”从模糊判断变成共同判断。AI、开发者、reviewer 和联调方依据同一组目标、边界与验收句，就能在结果不符合预期时明确否决，而不是围绕“看起来差不多”争论。

当验收句能够指出具体接口、状态码、文件范围和安全约束时，后续的证据包才有筛选标准，工序才有检查点，失败回流也才知道应该增加哪条约束。

带着这个思考进入下一章：契约已经说明“要什么、不要什么、怎样算过”，还需要哪些仓库事实来约束 AI 的判断？

这一幕带走：契约 = Goal + Boundary + Acceptance + Non-goals（Evidence 索引可选）。少一项，就给翻车留门。下一章：把禁区与现行实现收成刚好够用的证据包。

Part 04 · 给依据：刚好够用的证据包

04 / 证据

哈希被「优化」、错误体泄路径，通常不是模型坏，是你没把禁区和现行实现放进视野——或者塞了太多噪音，关键信号被稀释。

1. 证据背景：契约写清了，为什么还要证据包

契约回答「要什么 / 不要什么 / 怎样算过」。证据包回答另一件事：仓库里现行事实是什么，哪些文件是硬约束。

阿明翻车：整仓 @ 进上下文。模型「看见」了很多无关模块，却没稳定 anchor 到 session 实现与错误体规范——于是用「流行写法」改哈希、用调试友好的错误体把路径打到前端。

证据包的目标不是「上下文越多越好」，而是最小充分：少到会猜错关键路径就补；多到开始稀释信号就减。

2. 核心问题：缺少关键依据时会发生什么

每项都对应现场某一类失败；没有「以防万一」的填充物

放入对应风险为什么必须有
src/auth/session.ts登出后 /me 仍 200会话创建 / 失效的现行实现
src/routes/auth/*.ts登录 / 登出入口漂移真实路由与中间件挂载点
docs/error-envelope.md错误体泄路径 / 堆栈对外错误形状的硬规范
tests/auth/*.spec.ts「松绿」掩盖回归已有断言，防止改坏仍宣称完成
契约全文（Part 03）范围与禁区口头化Goal / Boundary / Acceptance 进入同一视野
搭配一句禁区声明（写进 Prompt）：禁止修改密码哈希实现；禁止读取或改写 .env / 密钥文件；本轮不做 OAuth。

3. 证据边界：明确不放什么

整仓噪音

整个 src/

后果：相关文件被淹没；模型更容易「顺便重构」无关模块。

改成：只挂 auth 路径与直接依赖。

过期意见

旧分支 / 闲聊结论

后果：「上周有人说 JWT 过时了」变成实现依据，与仓库现行 session 方案冲突。

改成：只收现行主分支事实与已合并文档。

密钥风险

.env / 密钥文件

后果：泄漏进 Diff、日志或错误体；review 更难拦。

改成：禁区明文写出，文件根本不进上下文。

虚假完整

大段教程粘贴

后果：模型按教程「最佳实践」重写，偏离本仓库约定。

改成：用本仓 error-envelope.md 与现有测试当标准。

4. 执行结论：用三问筛选最小充分证据

每想多 @ 一个文件，先过三问；任一问答不上，就别加。

  1. 缺了它，AI 会猜错什么？说不出具体猜错点 → 多半是安慰剂，不加。
  2. 它是现行事实，还是过期意见？分支实验、聊天结论、外部博客 → 默认不进包。
  3. 它是否含密钥或无关噪音？有密钥 → 永不进；噪音大于信号 → 剪到相关片段或换摘要。

最小充分自检：

  1. 拿掉包里任意一项，是否会导致某一条 Acceptance 必然漂？会 → 该项必要。
  2. 包里是否存在「与验收无关、只是顺手 @」的文件？有 → 删。
  3. 禁区是否同时以文字出现在 Prompt 里？（只靠「没 @ 哈希文件」不够，模型仍可能新建一套。）

补充说明：证据包怎么挂进一轮对话

做法推荐度说明
契约全文 + 上表文件 + 禁区声明推荐阿明修复轮采用的组合
整仓 @ +「你看着办」禁止翻车上午的原样
只给契约、不给现行实现不足仍会发明第二套 session / 哈希
只给代码、不写禁区文字不足模型可能新建文件绕开禁区
干货：证据包是「给依据」，不是「塞上下文」。每多一份无关材料，真正决定登出是否失效的那几行，权重就再降一档。

思考：上下文不是越多越可靠

证据包的难点不在于“找到多少文件”，而在于判断哪些事实足以约束这一次变更。把整仓内容交给 AI，看起来减少了遗漏，实际上可能让会话实现、错误体规范和禁区声明淹没在无关信息里。

最小充分不是追求最少，而是让每一项材料都能回答一个明确问题：缺少它，AI 会在哪一条验收上判断错误？答不上来，就不应让它占据上下文。

带着这个思考进入下一章：当目标和依据都已明确，怎样把认证任务拆成可以逐步检查、失败也能定位的工序？

这一幕带走：证据包追求最小充分——必要文件 + 契约 + 明文禁区。多塞的每一份，都在稀释真正关键的信号。下一章：有了契约与依据，把认证拆成可检查步骤。

Part 05 · 跑可靠：认证拆成可检查步骤

05 / 工序

一次生成 40 个文件，等于没有检查点。中断后你只能重来；联调爆了，你也不知道该回滚到哪一步。

1. 工序背景：为什么契约和证据齐了，还要拆步

说清楚、给依据，解决的是「方向对不对」。跑可靠解决的是：进度可检、失败可定位、中断可续跑。

阿明翻车：一口气生成注册 + 登录 + JWT 草稿 + 中间件 + 测试，单次 PR 40+ 文件。本地「松绿」就开 PR；下午登出后 /me 仍 200 时，已经分不清该回哪一段 Diff。

工序不是把任务写细好玩，而是让每一小步都有输入 · 输出 · 检查点 · 失败停点——过了才准往下。

2. 核心问题：每一步怎样才算可检查

每一步开跑前，至少能回答这四句；写不清，就不要开生成。

要素要写清什么阿明 T04 示例
输入本步依赖的已确认产物T02/T03 已绿；session 现行实现在证据包内
输出本步要交出的可观察结果登出后会话失效；对应测试与手动路径
检查点用什么命令/手动动作一票否决auth.session 相关测绿 + 手动 /me→401
失败停点红了停在哪，禁止扩散到哪停在 T04；不准顺手改注册表单或哈希

3. 过程证据：认证交付的 T01 → T06

阿明修复轮实际采用的人侧工序；每步检查点不过，禁止进入下一步

  1. T01 契约确认：评审 Goal / Boundary / Acceptance / Non-goals；检查点 = 团队对验收句无歧义，再开写码。
  2. T02 登录可用：正确账号能拿到会话；检查点 = 登录相关单测绿。
  3. T03 受保护接口：无会话访问受保护路由 → 401；检查点 = 中间件 / 鉴权测试绿。
  4. T04 登出失效：登出后再请求 GET /me → 401；检查点 = 会话测试绿 + 手动探测同路径。（案例里在此红过，见 Part 06）
  5. T05 错误体：错误响应不泄堆栈 / 绝对路径；检查点 = 错误体快照或约定断言绿。
  6. T06 收束 PR：小 Diff、PR 写清验证步骤与禁区；检查点 = CI 绿 + Acceptance 清单全部勾完。
顺序为什么这样排：先钉契约 → 再登录 → 再鉴权 → 再登出失效（最容易漏）→ 再错误体安全 → 最后收 PR。登出失效单独成步，就是因为阿明把它埋在「大模块生成」里，联调才炸。

4. 执行结论：跑工序的三条铁律

铁律 1

只消费上一步产物

T04 没过，不准开始「顺便重构注册表单」。每步只改本步范围，输出交给下一步当输入。

铁律 2

检查点必须可复现

「我觉得登录行了」不算过。要有测试名或手动请求序列；reviewer 能按同一路径复核。

铁律 3

红了停步，不扩范围

失败时停在当前 T；把红证留给 Part 06 回流。禁止用「再生成整模块」跳过停点。

铁律补充

一步一 PR 亦可

不必六步六个 PR，但 Diff 与提交信息应能看出步界；至少本地按步验收后再叠下一段。

补充对照：一口气生成 vs 可检查工序

一口气生成（翻车）可检查工序（修复）
单次 40+ 文件 Diff每步小 Diff，范围写在 Boundary 里
测试松绿就开 PR每步专属检查点，过了才往下
联调爆了不知回哪红在 T04 → 只回流 T04
中断只能整段重来从最近绿的一步续跑
「顺便」改哈希 / OAuth失败停点禁止扩到禁区与非目标

开跑前 30 秒自检：

  1. 当前是 Tn，上一步检查点是否已绿？
  2. 本步输入 / 输出 / 检查点 / 失败停点是否写进 Prompt？
  3. 本步 Boundary 是否小于等于契约 Boundary？
  4. 若红，下一动作是「回流写约束」，还是「整模块重生」？（后者直接否决）
干货：工序是人侧 harness。模型可以在一步内多改几个文件，但跨步合并验收不行——那会把「哪一步坏了」重新变模糊。

思考：拆步不是减慢速度，而是减少返工

一次生成很多文件，表面上省去了等待时间，实际上把验证、定位和回退都推迟到了联调阶段。等问题暴露时，团队面对的是一整块难以判断的 Diff，而不是一个可以明确修复的步骤。

可检查工序的价值，在于把进度变成证据：每个“已完成”都对应一次可复现的检查，每个失败也都有明确的停点。这样 AI 才能持续向前推进，而不是每次出错都回到起点。

带着这个思考进入下一章：当 T04 的检查点真实失败时，怎样把这条红证写回下一轮输入，而不破坏已经通过的步骤？

这一幕带走：步骤契约 = 输入 · 输出 · 检查点 · 失败停点。写不清就不要开跑。下一章：T04 红了之后，如何把失败写回下一轮，而不是整模块重生。

Part 06 · 变更好：登出仍 200 之后发生了什么

06 / 闭环

T04 红了。正确动作不是「再生成整个认证」，而是把红结果写成下一轮输入里的硬约束——失败若没变成文字，就等于没发生过。

1. 回流背景：T04 检查点挂了

契约、证据包、工序都立住后，阿明按步推进。T01–T03 绿；跑到 T04 登出失效 时检查点不过：

检查项期望实际
auth.session.spec：登出后 GET /me401200（用户信息仍在）
手动同路径复现401200
第一反应陷阱：「把认证模块删了再生成」「换个更强模型」「顺便把注册也重构一下」。这三种都会毁掉已绿的 T01–T03，并把失败信息重新变糊。

2. 核心问题：失败若不写回会发生什么

「变更好」不是改态度，是改下一轮 Prompt 的结构：范围锁在当前步，证据钉死，约束新增，完成条件可否决。

错法

同一句话重试

「帮我修一下认证 / 登出有问题」。失败细节只在你脑子里，模型下一轮仍从模糊目标起步。

错法

整模块重生

丢掉已绿步骤，大 Diff 重来。登出 bug 可能修好，哈希禁区与错误体又可能被踩。

错法

只换模型

输入不变，引擎再强也在猜同一片空白。闭环缺的是约束文字，不是参数量。

正法

留证 → 归层 → 写回

把红测写进下一轮；锁在 T04；禁区再声明一遍；完成条件 = 原检查点转绿。

3. 事实证据：闭环三步如何定位问题

  1. 留证：测试名、期望 / 实际、手动复现路径；必要时贴相关日志片段（脱敏）。没有留证，归层只能靠感觉。
  2. 归层：再用 Part 01 口诀——这次是依据不足（没读清 session 清理）、步骤假设错，还是契约验收本来就含糊？阿明此轮判定：现行 session 清理路径未被遵守 → 偏「依据 / 实现约束」未写回。
  3. 写回：把「必须清理服务端 session（以仓库为准）」「禁止改哈希」「只改 session 清理与对应测试」写成下一轮硬约束，而不是口头叮嘱。

归层时多问一句：

  1. T01–T03 还成立吗？成立 → 禁止重做，只回流当前步。
  2. 失败是否证明契约 Acceptance 写错了？写错 → 先改契约再回流，不要用错误验收硬拧实现。
  3. 是否缺了一份证据文件？缺 → 补进证据包，再开回流轮。

4. 执行结论：把失败写成回流 Prompt

继续 T04，不重做已绿步骤；失败证据与新增约束同屏出现

继续 T04，不要重做 T01–T03。 失败证据： - 测试 auth.session.spec：登出后 GET /me 期望 401，实际 200 - 手动复现相同 约束（新增）： - 必须清理服务端 session / 令牌黑名单（以仓库现行实现为准） - 禁止改动密码哈希 - 只改 session 清理路径与对应测试 完成条件： - 上述测试转绿；手动复现 401
案例结果：一轮回流后 T04 转绿；随后 T05 错误体、T06 收束 PR。PR 描述写上手动三步验收与禁区，CI 实打实绿，reviewer 可按同一路径复核。

补充模板：回流 Prompt 可直接套用

区块写什么不要写成
范围锁继续 Tn，不要重做 T1…T(n-1)从头再做一遍认证
失败证据测试名 + 期望/实际 + 手动路径「登出好像有问题」
约束新增本轮必须遵守的实现约束与禁区「注意安全一点」
改动边界只改哪些路径 / 测试「相关的都可以动」
完成条件= 原检查点转绿（可否决）「修到差不多」
干货：闭环的质量 = 下一轮输入比上一轮多了哪些不可省略的约束。若两轮 Prompt 几乎一样，你只是在重试，不是在变更好。

思考：失败的价值取决于它是否改变下一轮输入

测试失败本身不会让系统变好；只有当期望、实际、范围和新增约束被写成下一轮可执行的输入，失败才从一次挫折变成一次学习。否则，模型每次面对的仍是同一片模糊的上下文。

回流的关键不是“再试一次”，而是保护已经验证通过的步骤，并让当前失败只影响必要的最小范围。这样，改动才具备累积性，而不是反复推倒重来。

这一幕带走：留证 → 归层 → 写回。失败变成下一轮文字，才算进过闭环。下一章：同一认证需求，三版 Spec 如何决定三种命运。

Part 07 · Spec 演进：v0.1 → v1.0

07 / 实战

同一认证需求，三版契约，决定了三种命运。Spec 每升一版，都是在减少「模型替你做产品决定」的空间。

1. 演进背景：同一需求为什么出现三种结局

版本写法特征缺什么案例结果
v0.1「做个登录，安全一点」目标 / 边界 / 验收全无功能看起来全，下午联调翻车
v0.5列了注册/登录/JWT，仍无否决句Acceptance 虚、Non-goals 弱、禁区口头登出失效、泄密、哈希被踩，修不完
v1.0Goal / Boundary / Acceptance / Non-goals / Evidence + Risk / Rollback—按 T01–T06 推进，回流后 PR 可合并
读法：不是「写得越长越好」，而是每一版是否关掉一类翻车通道。v0.5 比 v0.1 长，但关掉的通道不够，所以仍然翻车。

2. 核心问题：v0.1 为什么注定翻车

帮我实现用户认证，要安全一点，最好用现在流行的写法。
看起来像赢

生成很快、Diff 很全

注册 / 登录 / JWT 草稿 / 中间件都有；测试「松绿」；PR 一行描述。

实际输掉

验收与禁区为零

没人能一票否决「完成」；OAuth 可进、哈希可改、登出可假绿。

结论：v0.1 把产品决定权交给了模型的「流行写法」默认值。

3. 事实证据：v0.5 如何制造“已写清”的错觉

实现邮箱注册、登录、JWT 鉴权。 要支持受保护路由。尽量安全，参考业界最佳实践。 可以的话把登出也做了。
比 v0.1 多了什么仍然致命的缺口
点出了注册 / 登录 / 鉴权无可否决 Acceptance（「尽量」「可以的话」）
提到受保护路由未写登出后 /me 必须 401
提到「安全」未禁改哈希、未禁泄路径、未写 Non-goals
暗示 JWT与仓库现行 session 方案可能冲突（依据错）
干货：v0.5 最危险——它让人觉得「已经写清楚了」。功能清单 ≠ 契约；没有否决句，就仍是 v0.1 的精装版。

4. 执行结论：v1.0 如何成为可交付 Spec

阿明修复轮定稿；可直接复制改领域词

【认证 · Spec v1.0】 Goal: 注册/登录/登出；登出后受保护接口 401 Boundary: 只改 auth 模块；禁止动哈希与密钥 Acceptance: - auth 单测绿 - 手动：登录→/me 200→登出→/me 401 - 错误体不泄堆栈/绝对路径 Non-goals: OAuth / 多租户 / 长期「记住我」 Evidence: session.ts · auth 路由 · error-envelope · auth 测试 Risk: 会话清理遗漏；错误体回退 Rollback: 回退至 T03 通过的 commit
前五块

契约本体

Goal / Boundary / Acceptance / Non-goals / Evidence——对应 Part 03–04，关掉说不清与依据错。

Risk

已知高危点

显式写出「会话清理遗漏」「错误体回退」，提醒 T04 / T05 检查点不可省。

Rollback

可回退点

回退到 T03 已绿 commit，避免 T04 回流失败时整段认证不可救。

用法

挂进每一步

T01 评审本 Spec；后续每步 Prompt 引用同一版，回流只追加约束，不另起炉灶。

补充清单：你的 Spec 到了哪一版

  1. 有没有可否决的 Acceptance？没有 → 仍是 v0.1 / v0.5。
  2. 有没有硬 Boundary + 明文禁区？没有 → 哈希与密钥仍可能被「优化」。
  3. 有没有Non-goals挡住流行写法扩容？没有 → OAuth / JWT 草稿随时回来。
  4. 有没有Evidence 索引指向现行实现？没有 → 模型会发明第二套方案。
  5. 高风险任务有没有Risk + Rollback？没有 → 工序中断后难以安全回退。

演进原则：

  1. 每一版只为关掉上一版真实踩过的坑（阿明：登出 401、禁哈希、禁泄路径、禁 OAuth）。
  2. 不加无法检查的形容词（「安全」「优雅」「最佳实践」）。
  3. 定稿后改 Spec 要升小版本号，并同步改检查点——避免口头改、文档旧。

思考：Spec 的成熟度不由篇幅决定

Spec 从 v0.1 到 v1.0 的变化，不是增加更多形容词或实现细节，而是逐一关掉已经验证过的风险通道：目标漂移、禁区被踩、验收含糊、依据缺失和回退无门。

因此，最好的 Spec 不是一次写成的长文档，而是随着真实反馈持续升级的工程协议。每新增一条约束，都应该能指向一个风险、一条验收，或一个明确的回退动作。

带着这个思考进入下一章：当问题再次出现时，怎样根据症状先找到正确层级，而不是拿同一种修复方式到处试？

这一幕带走：功能清单不是契约。v1.0 = 可否决验收 + 禁区 + 非目标 + 证据 +（高风险时）Risk/Rollback。下一章：翻车后再修，按层分诊，别乱开枪。

Part 08 · 分诊台：按层修，别乱开枪

08 / 分诊

同样「登录失败」，修错层会越修越远。分诊顺序本身就是工序——乱序等于赌博。

1. 分诊背景：为什么不能“有红就再生成”

前面四件事（契约 / 证据 / 工序 / 闭环）在修复时是串联门禁。现场红了，若不问「死在哪一层」，默认动作往往是换模型、加上下文、整模块重生——枪开得很响，靶子却不对。

阿明走过的弯路：T04 红后先「换模型再生成」整段认证，耗掉约两小时，哈希禁区差点再被踩。按序分诊后，只回流 T04，一轮就过。

分诊台要做的事很具体：把症状映射到层 → 只修那一层（或按固定顺序补缺）→ 再开下一轮生成。

2. 核心问题：相同症状如何修错层

3. 事实证据：按什么顺序判断问题层

  1. 契约——验收与非目标若仍糊，修证据/工序只是在错误完成标准上加速。
  2. 证据——契约清了但现行实现与禁区没进视野，模型仍会发明第二套方案。
  3. 工序——依据齐了仍大 Diff，失败无法定位，回流也无从锁步。
  4. 闭环——前三层立住后，才把红证写进下一轮；否则写回也只是换皮重试。

60 秒分诊口令（与 Part 01 对齐）：

  1. Acceptance 能否一票否决？否 → 停在契约。
  2. 现行关键文件与禁区是否在上下文？否 → 停在证据。
  3. 能否指出当前 Tn 与检查点？否 → 停在工序。
  4. 下一轮是否新增了失败约束？否 → 停在闭环。

思考：分诊是在控制修复的范围

分诊的价值不只是更快找到原因，更重要的是防止一次局部失败扩大成整段系统的不确定性。明确“本轮只修哪一层”，才能保护已经验证通过的内容，让每一次修复都有边界。

面对叠加问题时，最容易犯的错误是希望一轮 Prompt 同时解决所有缺口。更可靠的方式是按固定顺序补齐：先统一完成标准，再补足依据，再恢复检查点，最后让失败进入回流。

Part 09 · 画清依赖：哪步能并行

09 / 执行图

人要先看清依赖，再让 AI 动手。否则「并行加速」只会制造冲突 Diff，把已绿检查点也冲掉。

1. 依赖背景：为什么工序拆完还要画依赖

Part 05 把认证拆成 T01–T06，解决的是「一步一检」。依赖图解决下一问：哪些步必须串行，哪些才能并行。

常见误用：看到六步就开两个 Agent——一个写登录，一个写登出与错误体。会话状态、中间件、错误形状同时被改，合并时冲突；更糟的是两边都「测绿」，合在一起登出后 /me 又 200。

规则很硬：能并行的，是无共享可变状态（或无共享同一验收路径）的步骤；会话链路默认串行。

2. 核心问题：哪些步骤能并行，哪些必须串行

T01 → T02无契约则登录「完成」无法否决功能写完仍对不齐验收

T03 → T04先分离「从未登录」与「登出后」200/401 原因混杂，回流难归层

3. 事实证据：串行与并行如何判断

必须串行

共享会话状态

登录 → 鉴权 → 登出失效，读写同一套 session。阿明主链 T02→T03→T04 不拆并行。

必须串行

验收互相定义

后一步的「过」以之前一步的绿为前提（如 T04 假设未登录 401 已成立）。

可并行

无共享可变点

T05 错误体规范主要动错误封装与快照；与会话主链文件重叠少时可并行。

可并行但仍要汇合

合并前统一

并行支路进 T06 前，做一次错误体 + 会话路径的联合冒烟，避免「各绿合红」。

并行三问（全是「是」才开第二路）：

  1. 两步是否会改同一批文件或同一数据结构？
  2. 一步的检查点是否依赖另一步的输出？
  3. 合并时是否需要人工解冲突才能保持两边验收？

任一问为「会 / 是」→ 串行。不要用「两个窗口更快」压过依赖。

4. 执行结论：五分钟画出依赖图

  1. 列出 Tn（沿用 Part 05），每步只写一个主检查点。
  2. 对每对步骤问：A 的输出是否是 B 的输入？是则画边 A→B。
  3. 标出共享可变状态（session、用户表、错误中间件）——相关步骤默认串进一条链。
  4. 无边且无共享状态的步骤，标为可并行候选；汇合点通常是 T06 或「联合冒烟」。
  5. 把图贴进 Spec / PR 描述，开 Agent 前先定「本轮只跑哪条边」。
案例用法：阿明修复时主链一人串行；错误体 T05 曾与 T03 短并行，合并前补了错误体快照 + 登出路径联合检查，再进 T06。

补充说明：盲并行会长什么样

做法典型结果改成
登录与登出两 Agent 同时改session API 冲突；假绿T02→T03→T04 串行
未画边就「全都交给 AI」回到 40+ 文件一锅端先图后跑，每轮只推进一条边

用并行「赶联调」冲突 Diff 更耗时串行主链通常更快收敛
干货：依赖图是给人看的执行合同，不是装饰。AI 不会自动尊重你没写进 Prompt 的边——开跑时写明「只做 Tn，依赖 T(n-1) 已绿，禁止改 T(n+1) 范围」。

思考：并行不是默认的加速方式

并行只在依赖已经被排除后才会带来速度；如果两个步骤共享会话状态、文件或验收路径，提前并行只是把等待时间换成合并冲突和更难定位的失败。

依赖图的意义，是先让人决定工作如何分叉与汇合，再让 AI 在清楚的边界内执行。主链保持串行、独立支路谨慎并行，通常比“同时开多个 Agent”更快得到可合并的结果。

这一幕带走：能并行的是无共享可变状态的步骤；会话链路通常必须串行。先画边，再动手。下一章：按风险档决定拆多细、查多严。

Part 10 · 按风险选拆法

10 / 选型

先定风险档，再定拆多细、查多严。认证默认按「高风险」打：强验收、小步 Diff、关键路径人工看一眼。档位定错，后面全错。

1. 风险背景：为什么拆法要跟风险走

契约、证据、工序、闭环是同一套能力；但用多深、拆多细不该一刀切。改一句文案却上完整 T01–T06，是浪费；认证却「短 Prompt 一次生成」，是阿明周五翻车的结构原因——不是运气差。

选型错误的典型想法：「都是让 AI 写代码，流程一样就行。」风险不同，失败代价不同：文案错了改一行；会话清不掉，可能是安全事故与联调全军覆没。

本层只回答一件事：开干前先定档，再选配套拆法。

2. 核心问题：不同风险为何不能用同一套流程

档位例子失败代价做法（拆法）
低改文案、加日志字段、调样式易回滚、影响面窄短契约 + 一次生成 + 冒烟
中新查询接口、内部工具脚本、非核心 CRUD功能错、局部回归分 2–4 步 + 每步测试 + 最小证据
高认证、支付、权限、数据迁移、密钥相关安全 / 数据 / 大面积不可用完整契约 + 细工序 + 人工门 + 可回滚点
阿明案例定档：B 端控制台登录 / 登出 / 会话 → 高。应用：Spec v1.0、证据包、T01–T06、T04 关键回流、PR 手写验收三步。若按「低」档一次生成，就是开篇翻车的复刻。

3. 事实证据：三档任务分别需要什么

低风险

轻量交付

契约：Goal + 1 条 Acceptance 即可。

证据：只挂被改文件。

工序：一步生成 + 本地冒烟。

闭环：红了改一句再生成，通常够用。

中风险

标准交付

契约：四块齐全，Acceptance ≥2。

证据：相关模块 + 现有测试。

工序：2–4 步，每步有测试检查点。

闭环：失败写回；可不必上 Risk/Rollback 长文。

高风险

加固交付

契约：v1.0 + Risk + Rollback。

证据：最小充分 + 明文禁区。

工序：细拆（如 T01–T06）+ 依赖图；关键路径人工看。

闭环：锁步回流；禁止整模块重生当默认。

人工门

高档必留

会话清理、权限判断、支付状态机、迁移脚本——至少一条路径人眼过一遍，不交给「测绿 = 可合」。

4. 执行结论：开工前三问如何定档

  1. 炸了会怎样？仅展示错 / 局部功能错 / 安全或数据错 → 大致对应低 / 中 / 高。
  2. 共享状态多吗？会话、权限、余额、迁移——共享可变状态越多，越往高档靠，并强制串行主链（Part 09）。
  3. 回滚容易吗？难回滚（已写库、已发令牌、已迁数据）→ 至少中档起，高档要写 Rollback 点。

拿不准时：

  1. 偏安全、鉴权、钱、数据 → 直接按高。
  2. 纯展示、文案、日志 → 按低，但 Acceptance 仍要可否决。
  3. 介于中间 → 按中起步；一旦出现禁区被踩或联调关键路径，立刻升档，而不是硬扛。

错法样子后果纠正

低当高改文案也上六步依赖图流程疲劳，下次反而跳过降到低：短契约 + 冒烟

思考：流程强度应该匹配失败代价

低风险任务不需要被复杂流程拖慢，高风险任务也不能因为赶时间就跳过门禁。真正需要判断的不是“AI 能不能做”，而是这次变更失败后，影响范围有多大、是否容易发现、是否容易回滚。

风险档的作用，是在开工前把这些判断转成具体约束：需要多完整的契约、多少证据、多少检查点，以及哪条路径必须由人复核。档位一旦确定，后续流程就不再依赖临场感觉。

Part 11 · 避坑：乘客心态清单

11 / 反模式

认证翻车里出现过的，全是可复现的坏习惯。根子往往不是模型弱，而是人坐在副驾——只负责「喊一句、等 Diff」。

1. 反模式背景：什么是“乘客心态”

乘客心态：把 AI 当成自动驾驶，自己只负责发车与抱怨路况。组织输入、钉验收、看禁区、做分诊——全甩给模型「看着办」。

阿明上午的乘客时刻：一句「安全一点、流行写法」→ 整仓 @ → 大 Diff PR 写「AI 生成，请 review」。人在流程里缺席，模型就用默认值填空；默认值不等于可交付。
司机心态：你负责契约、证据、工序、闭环与风险档；AI 负责在门禁内写 Diff。你不是乘客，你是组织输入与验收的人。

2. 核心问题：六种坏习惯如何让责任外置

大爆炸 Diff一次改 40+ 文件按风险档拆 Tn，一步一检
测红只重试「再生成一次」/ 换模型硬刚留证 → 归层 → 写回约束
禁区口头说聊天里提一句别改哈希写进 Boundary，每轮 Prompt 再声明
PR 无验证步骤「AI 写的请看」贴上手动验收三步 + 检查点结果

3. 事实证据：坏习惯为何会反复出现

短快感

生成成功 ≠ 交付成功

Diff 铺满屏幕的上午最容易自我奖励；联调才是真实考核。

把「检查点全绿 + 手动路径过」当奖励点。

责任外置

「AI 写的」当挡箭牌

PR 把 review 负担甩给同事，自己不写验证步骤。

作者先按 Acceptance 自测，再请人复核。

工具迷信

换模型当万能药

输入结构不变，只换引擎——闭环病治不好。

先分诊、先写回；模型可换，门禁不能少。

流程疲劳

高档任务偷用低档拆法

「赶联调，先生成再说」——风险档口头取消。

赶工时更要锁步；并行只开无依赖支路（Part 09–10）。

4. 执行结论：用司机动作替换乘客习惯

  1. 开干前：四产物齐（契约 / 证据 / 执行图 / 回流位）——详见 Part 12；缺一不开生成。
  2. 生成中：只推进当前 Tn；检查点不过不扩范围；禁区每轮写进 Prompt。
  3. 变红时：禁止「同一句重试」；走留证 → 归层 → 写回（Part 06 / 08）。
  4. 开 PR 时：描述里贴 Acceptance 勾选结果与手动三步；不写「AI 生成请看」。
  5. 复盘时：问「哪条坏习惯又冒头了」，升一版 Spec 或加一条门禁，而不是只骂模型。

一分钟自检（乘客警报）：

  1. 我是否说不清「哪一句能否决完成」？
  2. 我是否说不清「本轮禁止改什么」？
  3. 我是否说不清「当前卡在 Tn 的哪条检查点」？
  4. 红了之后，下一轮 Prompt 是否几乎没变？

任一「是」→ 你在坐客运；先补门禁，再呼叫 AI。

补充速查：反模式替换卡

你脱口而出背后坏习惯立刻改口
「先做出来再收」无验收开干「先写 Acceptance 再生成」
「全丢给它看吧」整仓塞上下文「只挂这几份现行文件」
「一口气搞定」大爆炸 Diff「本轮只做 Tn」
「再试一次 / 换个模型」测红只重试「先贴红证再写回」
「别改哈希啊」（仅口头）禁区口头说「Boundary：禁止改哈希」
「AI 写的，帮忙看下」PR 无验证步骤「已按下列三步自测通过：…」
干货：避坑清单不是道德说教，是可观察行为替换表。改口令、改 Prompt 结构、改 PR 模板，比「下次注意」有效。

思考：使用 AI 的责任不能外包

“AI 写的”只能说明代码的生成方式，不能说明需求已经正确、变更已经安全，或结果已经通过验收。真正承担交付责任的人，仍然要组织输入、维护边界、检查证据并决定是否合并。

司机心态也不是拒绝自动化，而是把自动化放进清楚的门禁里：让 AI 在当前步骤内提高执行速度，让人保留对目标、风险和最终结果的判断权。

这一幕带走：你不是乘客。你是组织输入与验收的人。下一章：把司机动作收成开干前打勾清单。

Part 12 · 开工清单：下次开干前打勾

12 / 清单

周一若再来一个「做个 XX」，先过这张表，再呼叫 AI。四产物不齐，不要开始；开始了就按图推进，按层分诊。

1. 清单背景：开工前需要拦住什么

清单不是文档仪式，是开干门禁：防止再滑回「一句 Prompt + 整仓 @ + 大 Diff」。阿明上午若勾完再生成，OAuth 乱跑与哈希被改，多半进不了第一轮。

用法：全部打勾才开第一轮生成。缺一项 = 仍在乘客座位上。高风险任务（认证 / 支付 / 权限）允许清单更长，不允许更短。

2. 核心问题：四产物缺一会怎样

① 契约Goal / Boundary / Acceptance / Non-goals
② 证据包必读文件 ≤ 必要集合
③ 执行图步骤、依赖、检查点
④ 回流位失败如何留证并写回
产物打勾标准（可否决）缺了会怎样
契约至少一条 Acceptance 能一票否决「做完了」；禁区与 Non-goals 已写模型用「流行写法」填空
证据包现行关键文件已列；密钥不进包；禁区有文字声明发明第二套实现 / 踩禁区
执行图Tn 列表 + 依赖边 + 每步检查点；风险档已定大爆炸 Diff，失败无法锁步
回流位预留「留证字段」与「只回流当前 Tn」的写法红了只会重试或整模块重生

3. 事实证据：开干前四问如何验收

  1. 完成标准：要完成什么？哪一句能一票否决「做完了」？
  2. 依据与禁区：依据是哪些现行文件？禁区写清了吗？
  3. 第一步：T01/T02 的检查点是什么？失败停在哪？
  4. 变红预案：若红了，下一轮 Prompt 将新增哪条约束？（现在就写草稿，不要等红了再想）

加问（高风险必答）：

  1. 风险档是低 / 中 / 高？写进 Spec 了吗？
  2. 主链哪些步必须串行？有没有误开并行？
  3. Rollback 点在哪（例如回退到 Tn 已绿 commit）？
  4. 哪条路径必须人工看一眼（人工门）？

4. 执行结论：按风险档裁剪清单

低

可裁短，不可删核

契约可短到 Goal + 1 条 Acceptance；证据只挂被改文件；工序一步 + 冒烟；回流可简化，但仍要「红了改哪句」。

中

四产物标准版

契约四块齐全；证据含测试；2–4 步带检查点；回流模板备用。

高

全量 + 人工门

v1.0 Spec（含 Risk/Rollback）；最小充分证据；细工序 + 依赖图；锁步回流；关键路径人眼过。

禁止

赶工删门禁

「先生成再补清单」= 乘客心态复辟。赶联调时更要先勾四问。

补充示例：认证任务勾完长这样

【开工勾选 · 认证 · 高风险】 ① 契约：Spec v1.0（注册/登录/登出；登出后 /me → 401；禁改哈希；非目标含 OAuth） ② 证据：session.ts · auth 路由 · error-envelope · auth 测试 · 契约全文 ③ 执行图：T01→T02→T03→T04→T06；T05 可短并行；检查点见 Part 05 ④ 回流位：红则锁当前 Tn；贴测试名+期望/实际；追加约束后重跑 四问答： - 否决句：登出后 GET /me 必须 401（另：单测绿、错误体不泄路径） - 禁区：哈希 / .env / 密钥；不进上下文 - 第一步检查点：T01 验收句无歧义；T02 登录测绿 - 变红预案：继续 Tn，不重做已绿步；写回 session 清理约束 人工门：T04 登出路径人眼过一遍 Rollback：回退至 T03 已绿 commit

干货：清单打勾的终点不是「表格填满」，而是第一轮 Prompt 已经写得出来——契约摘要、证据列表、本步 Tn、失败停点，同屏粘贴即可开跑。

思考：清单的价值在于阻止错误开始

开工清单不是把流程变得繁琐，而是把最容易被忽略的判断提前完成。只要目标、依据、步骤和失败预案中有一项空缺，第一轮生成就可能把不确定性放大成大 Diff。

清单也不要求所有任务使用同样的重量。低风险任务可以缩短表格，高风险任务则必须保留人工门、回滚点和关键路径验收；可以裁短，但不能删掉判断核心。

带着这个思考进入结语：当清单、工序和回流都成为习惯，AI 编程最终改变的究竟是模型能力，还是个人的交付方式？

这一幕带走：四产物齐 + 四问答清，才开干。开始了就按图推进，按层分诊。下一章收束：认证修完之后，带走可复用的用法。

结语 · 认证修完之后

收束

从「做个登录」到可合并 PR，靠的不是更长的 Prompt，而是可重复的用法。流程不变，换领域词就能迁到支付、权限、迁移。

1. 收束背景：阿明那天后来怎样

周五上午一句糊 Prompt，下午联调四连爆。停手之后，没有换模型硬刚，而是按本篇路径走完：归层 → 修复计划 → 契约 / 证据 / 工序 / 回流。Spec 升到 v1.0，T04 锁步回流转绿，PR 带上手动验收三步与禁区说明，CI 实打实绿，reviewer 按同一路径复核后合并。

翻车上午可合并时
输入「安全一点、流行写法」+ 整仓 @Spec v1.0 + 最小证据包 + 明文禁区
执行一口气 40+ 文件T01–T06，一步一检；T04 单独回流
失败时再生成 / 换模型留证 → 归层 → 写回约束
PR「AI 生成，请 review」验收勾选 + 手动三步 + 禁区说明
结果登出后 /me 仍 200；哈希被踩联调路径过；CI 绿；可合并
真正换掉的不是模型，是用法：人回到司机座——组织输入、钉验收、看禁区、按层分诊；AI 在门禁内写 Diff。

归层 · 分诊 · 定档

翻车先归层（Part 01）；再修按契约→证据→工序→闭环（Part 08）；开干前定低/中/高（Part 10）。

胜利标准

不是「生成成功」

别人能合并、联调过得去、上线不埋雷——才是个人交付的胜利。

一句话：用法先于模型。四件套齐了，再生成。

3. 事实证据：从翻车到可合并的完整路径

  1. 开篇–01：翻车现场 → 归层（说不清 / 依据错 / 步骤不可检 / 无闭环）
  2. 02–06：修复计划落地——契约 → 证据 → 工序 → 回流
  3. 07–08：Spec 升到 v1.0；按层分诊，别乱开枪
  4. 09–10：画依赖（何可并行）；按风险选拆法
  5. 11–12：丢掉乘客心态；开干前四产物打勾

4. 执行结论：下次换题只换领域词

骨架不动。把认证验收句换成新领域的可否决句即可——例如支付退款：

【迁移示例 · 支付退款 · 高风险】 Goal: 已支付订单可发起退款；退款成功后余额与订单状态一致 Boundary: 只改 refund 模块；禁止改账本写入旁路；禁止碰密钥 Acceptance: - 退款单测绿 - 手动：支付成功 → 退款 → 余额回滚正确 → 重复退款被拒 - 错误体不泄内部账本路径 Non-goals: 本期不做部分退款、不做跨境 Evidence: 账本服务现行实现 · refund 路由 · 错误体规范 · 退款测试 （其后：拆 Tn、定依赖、红了锁步写回——与认证同一套）
  1. 定档——支付 / 权限 / 迁移默认高；文案日志可低。
  2. 勾清单——四产物 + 四问（Part 12）；No-Go 不开干。
  3. 按序加固——说清楚 → 给依据 → 跑可靠 → 变更好。
  4. 红了分诊——契约 → 证据 → 工序 → 闭环；乱序不开枪。

本篇停在个人交付用法：把「会生成」修到「能交付」。不解释 Agent 内部为何能闭环，也不谈如何做成产品或平台——那是系列后面几层的事。

若你开始好奇机制：工具调用、记忆、规划如何被组织成「能自己跑完一轮认证」——读 02 · 吃透 AI Agent：从会说话到能闭环。

思考：可复用的不是答案，而是交付方式

这次认证案例的具体接口、文件路径和测试名称都属于当前项目，但它背后的交付方式可以迁移到支付、权限、迁移和其他高风险任务。变化的是领域词，不变的是契约、证据、工序、回流和验收。

当 AI 从“替我完成一项功能”变成“在明确边界内推进一组可验证步骤”，人的角色也从等待结果，转为设计约束、判断证据和承担最终决策。

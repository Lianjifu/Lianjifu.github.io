第 3 章：通道协议

消息通道与适配器协议

发表于2026-11-07 分类于OpenClaw 源码笔记

15+ 消息通道 = 1 个统一适配器协议——通道不是 OpenClaw 的"产品"，而是它的"输入端"。Gateway 看不到 WhatsApp 和 Slack 的差异，只看到统一的 Envelope。本模块展开所有内置通道的协议、凭据管理、消息路由与边界条件。

思考维度 内容
引导思考 展开
它为什么存在
  • WhatsApp、Telegram、Slack、Discord…… 十几个平台的接入协议各不相同
  • 如果 Gateway 里塞满平台分支，每加一个平台都要动核心代码
  • 通道不是产品，是输入端——它必须能整层替换而不影响别处
它解决什么问题
  • 把外部世界翻译成统一信封：每条消息进入 Gateway 前都被归一化为 Envelope
  • Gateway 看不到平台差异，只看到统一的消息结构
  • 给出连接模式、凭据管理与路由边界的完整约定
它在系统中的位置
  • 接入层的具体实现——定义消息怎么从外部世界进入 Gateway
  • L1 接入层，位于 Gateway 路由之前
  • 会话路由的输入侧：路由层与 Session Key 都在这一章
它如何工作
  • 五种连接模式：WebSocket、Native、Webhook、Long Polling 与它们的组合
  • 统一适配器协议：所有通道实现同一个接口，消息归一化为 Envelope
  • 八级路由匹配优先级从精确匹配逐级降级到兜底 Agent

3.2 通道设计的三个原则

原则 含义
通道是可信网关的边界通道插件代码运行在 Gateway 进程内，与 LLM / 工具执行隔离。所有凭据、连接状态都由 Gateway 统一管理。
通道适配器 = 不可信翻译层平台特异的协议细节（原始事件、流式卡片、附件 URL）都在适配器内归一化。Gateway 永远只看 Envelope。
通道策略 = 声明式配置DM 配对 / 群组白名单 / 限流 / 多账号 全部在 openclaw.json5 中声明，不在代码里硬编码。

3.5 5 种连接模式

每种连接模式对应一类外部平台的协议特性——选错模式，通道的延迟、稳定性、部署复杂度都会变。

连接模式通道优点限制
WebSocket 长连接WhatsApp · Discord · Web UI实时双向 · 低延迟（~50ms） · 服务端推送需心跳 · 重连逻辑 · 本地端口
Webhook 推送Slack · LINE · Google Chat无连接维护 · 简单 · 平台代管需公网 URL · 防火墙 · TLS 证书
Long PollingTelegram · 部分 IMAP防火墙友好 · 无需公网延迟 ~1-3s · 服务端开销
本地原生iMessage · CLI · IRC无外部依赖 · 协议直接平台绑定 · macOS only 等
Plugin 桥接WeChat · 自定义平台支持闭源平台依赖第三方稳定性

3.5.1 运维视角 · 怎么部署？

WebSocket / Native 通道只要 Gateway 能上网就行，无需公网入口。Webhook 通道需要把 https://your-domain.com/{channel}/events 暴露到公网——推荐用 Caddy + Let's Encrypt 自动签证书，或部署在 Cloudflare 后面。Long Polling 没有外部入口问题，适合内网部署。

3.5.2 网络视角 · 端口与连接数

WebSocket 类每个通道占 1 个出站连接；Webhook 类需要 1 个入站监听端口（默认 18789 的 sub-path，如 /slack/events）；Native 类通常使用系统级 API，不占网络端口。多个账号不会增加连接数，但会增加并发握手时的瞬时 CPU。

路由层定位

路由层是 Gateway 的决策中枢，负责将消息路由到正确的会话和处理逻辑。所有入站消息都必须经过路由解析。

路由发生的时机

路由匹配优先级

路由按最具体优先原则执行，从精确匹配逐级降级到兜底 Agent：

优先级详解

优先级匹配条件示例说明
① peerpeer.id 精确匹配特定用户的 DM最精确，一对一私聊
② parent回复链的 parent peer线程中的回复同一对话线程继承路由
③ guild+rolesguildId + memberRoleIdsAdmin 角色专属通道Discord 角色路由
④ guildguildId 匹配整个 Discord 服务器服务器级默认
⑤ teamteamId 匹配Slack 团队团队级路由
⑥ accountaccountId 匹配某个 WhatsApp 账号账号级路由
⑦ channel仅 channel 类型匹配所有 Telegram 消息通道级兜底
⑧ default无任何匹配回退到 default: true 的 Agent最终兜底

Session Key 设计

Session Key 是路由的核心输出，唯一标识一个会话。其格式为：

agent:{agentId}:{channel}:{accountId}:{scope}:{peerId}

会话键类型

类型格式说明
main 主键agent:{agentId}:{mainKey}单用户模式的主会话
per-peeragent:{agentId}:dm:{peerId}按发送者 ID 隔离，跨通道共享
per-channel-peeragent:{agentId}:{channel}:dm:{peerId}按通道 + 发送者隔离（推荐多用户）
per-account-channel-peeragent:{agentId}:{channel}:{accountId}:dm:{peerId}按账户 + 通道 + 发送者隔离
群聊agent:{agentId}:{channel}:{accountId}:group:{peerId}群组会话
频道agent:{agentId}:{channel}:{accountId}:channel:{peerId}频道会话
Telegram 论坛agent:{agentId}:{channel}:{accountId}:group:{peerId}:topic:{topicId}论坛主题隔离
Croncron:...定时任务
Webhookhook:...Webhook 触发
Nodenode-{id}节点调用

Session Key 的四层作用

作用说明实现
消息串联同一 Key 的消息归入同一历史窗口{sessionKey}.jsonl 记录文件
并发隔离每 Key 独立 Lane，保证串行resolveSessionLane()
存储定位按 Key 确定存储路径~/.openclaw/agents/{id}/sessions/
路由决策输入维度最终生成唯一 Keysession-key.ts

dmScope 隔离策略

dmScope 决定了哪些消息共享同一会话，是多租户安全的关键配置：

dmScopeKey 格式隔离粒度推荐场景
mainagent:{agentId}:所有 DM 共享一个主会话单用户个人使用
per-peeragent:{agentId}:dm:{peerId}按发送者隔离，跨通道共享多用户，同人不同端
per-channel-peer agent:{agentId}:{channel}:dm:{peerId}通道+发送者隔离多用户收件箱（推荐）
per-account-channel-peeragent:{agentId}:{channel}:{accountId}:dm:{peerId}最强隔离多账户多用户

安全警告：多用户 DM 场景下，必须启用 `per-channel-peer` 或更强隔离级别，否则用户 A 的私人信息可能泄露给用户 B。

Identity Links

如果同一人通过多个通道联系你，使用 `identityLinks` 合并会话：

{
  session: {
    identityLinks: {
      alice: ["telegram:123456789", "discord:987654321012345678"],
    },
  },
}

路由决策维度详解

维度来源作用示例值
channel消息元数据区分消息来源通道telegram / discord / whatsapp
accountId通道配置支持多账号隔离personal / work / bot1
peerId消息发送者标识发送者/群组123456（用户 ID）
guildIdDiscord/Slack服务器/工作空间Discord server ID
teamIdSlack团队标识Slack team ID

会话概述

会话（Session）是 OpenClaw 跟踪每段对话历史的方式。每当你通过聊天软件和 AI 说话，这段对话就保存在一个会话里。

生活类比

手机聊天 App 里的"单个聊天窗口"
         ↓
你在 Telegram 给 AI 发消息    → 一个会话
朋友通过同一个 Bot 发消息      → 另一个独立会话
AI 记得同一会话里说过的话      → 不同会话之间互不干扰

保存位置

~/.openclaw/agents/<agentId>/sessions/

每个会话是一个 `.jsonl` 文件，记录所有对话轮次（用户消息 + AI 回复）。

会话状态模型

存储结构

文件说明可删除？
sessions.json每智能体的会话映射（sessionKey → metadata）安全，会按需重建
{sessionKey}.jsonl实际对话记录丢失历史
.../-topic-{topicId}.jsonlTelegram 论坛主题隔离丢失主题历史

会话元数据（sessions.json）

{
  "agent:main:telegram:dm:123456": {
    sessionId: "uuid-xxx",
    updatedAt: 1736160000000,
    // 运行时也会读取 origin 元数据
    origin: {
      label: "Alice",                    // 人类可读标签
      provider: "telegram",              // 通道类型
      from: "123456",                    // 发送者 ID
      accountId: "personal",             // 所属账号
    },
  },
}

删除 sessions.json 条目是安全的，因为 Gateway 会按需重建。但删除 `.jsonl` 文件会丢失对话历史。

网关是事实来源

所有会话状态由网关拥有。UI 客户端必须查询网关获取会话列表和 Token 计数，而不是读取本地文件。

重置策略

OpenClaw 提供 5 种会话重置机制，决定何时创建一个新的会话 ID：

重置策略详解

策略触发条件行为默认值
每日重置 网关主机本地时间到达 atHour强制创建新会话凌晨 4：00
空闲重置超过 idleMinutes 无新消息滑动窗口到期后自动重置未设置
每类型覆盖direct / group / thread 分别配置覆盖该类型的所有会话无
每通道覆盖特定通道的所有会话覆盖该通道的所有会话无
手动触发用户输入 /new 或 /reset 命令立即创建新会话始终可用

当同时配置了每日和空闲重置时，先到期的那个强制创建新会话。

配置示例

{
  session: {
    dmScope: "main",
    identityLinks: {
      alice: ["telegram:123456789"],
    },
    reset: {
      mode: "daily",       // 每日重置
      atHour: 4,           // 凌晨 4:00
      idleMinutes: 120,    // 2 小时空闲也重置
    },
    // 按会话类型覆盖
    resetByType: {
      thread: { mode: "daily", atHour: 4 },
      direct: { mode: "idle", idleMinutes: 240 },
      group: { mode: "idle", idleMinutes: 120 },
    },
    // 按通道覆盖
    resetByChannel: {
      discord: { mode: "idle", idleMinutes: 10080 },  // 7 天
    },
    resetTriggers: ["/new", "/reset"],
  },
}

发送策略（Send Policy）

发送策略控制哪些消息可以投递到哪些通道。可以配置全局规则和会话级覆盖。

全局规则

{
  session: {
    sendPolicy: {
      rules: [
        // 禁止 Discord 群组消息
        { action: "deny", match: { channel: "discord", chatType: "group" } },
        // 禁止 Cron 通知
        { action: "deny", match: { keyPrefix: "cron:" } },
      ],
      default: "allow",     // 未匹配规则的消息默认允许
    },
  },
}

会话内覆盖

/send on        # 允许此会话投递
/send off       # 拒绝此会话投递
/send inherit   # 清除覆盖，使用全局规则

运行时处理流程

会话来源元数据（origin）

每个会话可以携带来源元数据，用于标识会话的发起上下文：

字段说明示例

from / to原始路由 ID"123456"
accountId多账户时的账号 ID"personal"

通道架构

通道是消息的"入口"与"出口"，连接用户与 Gateway 的桥梁。

通道适配器内部结构

通道消息流转

通道类型

类型通道接入方式
核心通道 Telegram, WhatsApp, Discord, Slack, Signal, iMessage, Google Chat, WebChatGateway 原生支持，统一管理
插件通道Matrix, Mattermost, Teams, LINE, Nostr, Twitch, Zalo, QQ, WeChat通过插件能力扩展

核心概念

概念说明作用
accountId通道账号标识，支持多账号同一通道可运行多个独立账号，故障隔离
peerId用户/群组标识区分不同发送者，路由到对应会话

账号是一级实体：同一 Channel 可运行多个 `accountId`，单个账号故障不影响其他账号。

3.7 ChannelAdapter 接口

所有通道必须实现这个接口（伪代码）：

interface ChannelAdapter { // 唯一标识（小写字母+数字） readonly id: string; // 'whatsapp' | 'telegram' | 'slack' | ... // 显示名（用于 UI） readonly displayName: string; // 支持的连接模式 readonly connectionMode: 'websocket' | 'webhook' | 'polling' | 'native'; // 生命周期钩子 init(config: ChannelConfig): Promise<void> connect(): Promise<void> disconnect(): Promise<void> // 入站：把外部消息归一化成 Envelope onMessage(handler: (envelope: Envelope) => void): void // 出站：把 ReplyEnvelope 翻译回原生格式 send(reply: ReplyEnvelope): Promise<void> // 健康检查（可选） healthCheck(): Promise<HealthStatus> }

接口稳定后，新增通道只需实现这 6 个方法——Gateway 不关心消息来自 WhatsApp 还是微信。

3.8 7 步生命周期

1
注册（Register）
在 openclaw.json5 中声明通道。无声明 = 不加载。
→ config/channels.{name}.enabled
2
初始化（Init）
Gateway 启动时调用 init(config)，完成 SDK 初始化、凭据加载、Schema 校验。
→ extensions/{name}/init.ts
3
连接（Connect）
建立到外部平台的长连接 / Webhook 注册 / Long Poll 启动。失败则按策略重试。
→ extensions/{name}/connection.ts
4
入站（Inbound）
接收外部消息 → 解析为原生结构 → 翻译成统一 Envelope → 转发 Gateway 的 onMessage handler。
→ extensions/{name}/inbound.ts
5
出站（Outbound）
Gateway 调用 send(replyEnvelope)，适配器把统一回复翻译回原生格式（文本 / 卡片 / 文件 / Interactive），发送到原平台。
→ extensions/{name}/outbound.ts
6
重连（Reconnect）
连接断开后，采用指数退避重连（1s → 2s → 4s → 8s → ... → 60s 上限）。连续失败 5 次触发告警。
→ extensions/{name}/reconnect.ts
7
关闭（Shutdown）
Gateway 关闭时调用 disconnect()，清理长连接、撤销 Webhook、释放资源。
→ extensions/{name}/shutdown.ts

3.12 Envelope · 统一消息信封

Envelope 是所有消息的「信封」——它定义了 Gateway 能看到的全部信息：

interface Envelope {
  // 唯一标识(UUID v4)
  id: string;

  // 通道 ID
  channel: string;          // 'whatsapp' | 'telegram' | 'slack' | ...

  // 账号 ID(同通道多账号时区分)
  account: string;         // 'personal' | 'work_bot' | ...

  // 发送者信息
  from: {
    id: string;           // 平台用户 ID
    displayName?: string;
    username?: string;     // @handle
    isVerified: boolean;   // 是否完成配对
  };

  // 会话上下文
  chat: {
    id: string;
    type: "dm" | "group" | "channel";
    title?: string;
  };

  // 消息内容
  body: {
    text?: string;            // 纯文本(已剥离 markup)
    html?: string;            // 富文本(可选,平台支持时)
    mentions?: string[];     // @到的用户 ID
    replyTo?: string;        // 引用的消息 ID
  };

  // 附件
  attachments?: Attachment[];

  // 元数据
  metadata: {
    timestamp: number;   // 毫秒
    isEdited?: boolean;
    threadId?: string;  // Slack thread, Telegram topic
    language?: string;
  };
}

提示

设计哲学

：Envelope 是最小共同子集。不是所有字段都有值——WhatsApp 没有 threadId，Slack 有。Gateway 知道哪些字段是平台特有的，通过 metadata.channel.* 访问。

3.14 出站 · ReplyEnvelope + 流式卡片

Gateway 返回的不是裸文本，而是 ReplyEnvelope:

interface ReplyEnvelope {
  target: {
    channel: string;
    account: string;
    chat: string;          // 原 chat ID
    replyTo?: string;
  };

  // 输出形式(平台可选择性支持)
  blocks: ReplyBlock[];

  // 流式更新支持
  stream?: {
    enabled: boolean;     // 是否可流式(平台支持时)
    updateInterval: number; // 毫秒,多久刷一次
  };
}

type ReplyBlock =
  | { type: "text", content: string }
  | { type: "code", content: string, lang?: string }
  | { type: "image", url: string | path: string }
  | { type: "buttons", actions: Button[] }
  | { type: "card", title: string, fields: CardField[] };

适配器把 blocks 翻译成平台原生格式：

ReplyBlockSlackTelegramWhatsApp
textBlock Kit section普通消息普通消息
code代码块 + 三反引号pre 标签三反引号
image附件上传sendPhotoimageMessage
buttonsBlock Kit actionsinline_keyboard不支持（降级为文本列表）
cardBlock Kit sectionInlineQueryResult不支持（降级为文本）

提示

降级策略

：如果 ReplyBlock 是平台不支持的类型，适配器自动降级为纯文本。例如 WhatsApp 不支持按钮 → 输出 [按钮 1] [按钮 2] [按钮 3] 文本列表。

3.14.1 流式输入指示 · 用户视觉反馈

LLM 在生成时，用户希望看到"对方正在输入"。OpenClaw 通过通道的 typing indicator 实现：Slack 发 typing event 每 3 秒重发、Telegram 调 sendChatAction("typing")、WhatsApp 设 presence 为 composing（部分版本支持）、Web UI 实时打字光标。Gateway 调用 channel.sendTypingIndicator(replyEnvelope)，适配器负责翻译。

3.15 重连策略与多账号

网络是不稳定的。OpenClaw 的通道适配器使用指数退避 + 抖动(Exponential Backoff with Jitter):

  • 第 1 次重试：1 秒后
  • 第 2 次重试：2 秒后（±100ms 抖动）
  • 第 3 次重试：4 秒后（±200ms 抖动）
  • 第 4 次重试：8 秒后（±400ms 抖动）
  • 第 5 次重试：16 秒后（±800ms 抖动）
  • 第 6+ 次重试：固定 60 秒（±2s 抖动）
  • 连续失败 5 次：触发告警，进入 Failed 状态

提示

为什么加抖动

：避免多个客户端同时重连导致雪崩——抖动让重连时刻随机分布，服务端压力更平缓。

一个通道可以接多个账号——每个账号是独立的配置块：

{
  channels: {
    telegram: {
      enabled: true,
      accounts: {
        work_bot: { botToken: "${TG_WORK}", workspace: "/home/me/work" },
        personal_bot: { botToken: "${TG_PERSONAL}", workspace: "/home/me/personal" },
        family_bot: { botToken: "${TG_FAMILY}", workspace: "/home/me/family" }
      }
    }
  }
}

3.15.1 隔离视角 · 一个 Gateway 怎么服务多身份？

每个账号绑定一个 workspace 目录，内部有独立的 memory/（长期记忆）、tasks/（任务状态）、skills/（个人技能库）。work_bot 看不到 personal_bot 的记忆与文件——即使两条会话同时活跃，LLM 上下文也不会交叉污染。

          OpenClaw 不保证。建议用官方 WhatsApp Business API（收费）或在 DM 配对码 + 限流下使用 Baileys，且务必使用非主账号测试。
        • iMessage 只能在 macOS 上用吗？
          对。Apple 协议限制。如果需要跨平台，推荐用 Telegram 或 Signal。
        • 通道消息能走 OAuth 鉴权吗？
          取决于平台。Slack/Teams/Discord 支持 OAuth 2.0，WhatsApp/微信需要扫码登录。详见 3.16 内置清单。
        • 附件超过 25 MB 怎么办？
          在 channels.{name}.maxAttachmentSize 调整（单位 bytes）。但要考虑 LLM 上下文窗口：25 MB 文本 ≈ 6M tokens，远超任何 LLM 的输入限制——实际上传大文件应该走"摘要/抽取"链路而不是直接喂给 LLM。
        • 通道插件需要 Node.js 24+ 吗？
          v2026.9.2 起：Node 24.16+ 或 26.1+ 推荐；Node 26 是 LTS 推荐版。早期 Node 22 LTS 仍可工作但有性能差异。

        3.18.3 一句话总结

        要点

        15+ 通道不是"开箱即用全可用"——它们是分级菜单。


        生产环境从 Telegram / Slack / Discord 起步，谨慎处理 WhatsApp / iMessage / WeChat。

        新增通道只需写一个 extensions/<name>/ 目录，实现 6 个方法的 ChannelAdapter 接口，无需改 Gateway 核心代码。

        新通道遇到问题先看 troubleshooting 指南。

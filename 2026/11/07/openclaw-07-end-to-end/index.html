7.1 一句话定位

本章要点

端到端 = 用一条具体消息，把前面 6 个模块串起来看——是"全局视角"的最佳入口。

本模块是 OpenClaw 文档的"汇聚点"，从一条 WhatsApp 消息出发，走完 9 个阶段、13 个参与者，把架构、通道、会话、模型、工具、钩子全串起来。
指标 规模 代表
个参与者13U·WA·Ch·GW·Q·AL…
个阶段9通道接入→善后
步时序图31完整消息流
典型总耗时3-8s从发送到回复
耗时占比~70%LLM 推理最大
个场景2WhatsApp·9 步概览

7.2 端到端流程的三个原则

原则 含义
具体场景 = 知识的具体化用一条真实消息走完全链路——比抽象架构图有效 10 倍。WhatsApp 日程查询是最经典的"含工具调用"场景。
阶段 5-6 是循环的模型推理 ↔ 工具执行 形成闭环，直到 LLM 输出最终答案——这就是 Agent 与单次 LLM 调用的根本区别。
单一可信网关 + 不可信执行所有消息过 Gateway 集中路由，所有外部动作走沙箱 + 钩子——这就是 OpenClaw 安全模型的物理落地点。

7.3 模块位置

7.4 场景设定 + 13 参与者

7.4.1 场景设定

  • 通道：WhatsApp DM（私聊）
  • 触发消息:Hey, what's on my calendar today?
  • 预期路径：触发 calendar.list_events 工具调用，返回自然语言答复
  • 用户：已配对的个人账号（work_bot）

7.4.2 13 个参与者

U 用户终端WhatsApp App

WA WhatsApp CloudMeta 服务器

Ch 通道插件extensions/whatsapp/

GW 网关src/gateway/

Q 命令队列网关内进程

AL Agent Runnersrc/agents/

PB Prompt 构建器packages/agent-core/

PR 模型 Providerextensions/anthropic

TX 工具执行器src/tools/ + 沙箱

SM 会话管理器session-manager.ts

CP 压缩compaction.ts

SP 持久化SQLite

WM 出站发送器WhatsApp 出站

7.5 9 个阶段概览

7.6 9 阶段详解

阶段 1 · 通道接入

7.6.1 1⃣ 通道接入——消息进 Gateway

参与:U → WA → Ch

动作:

  • 用户 WhatsApp App 发送消息到 Meta 服务器
  • Meta Webhook 推送到 extensions/whatsapp/
  • 规范化（去除 WhatsApp 特定字段）→ Envelope
  • WebSocket 帧发送到 Gateway 控制平面

耗时:50-200ms

阶段 2 · 网关路由

7.6.2 2⃣ 网关路由——Schema + 会话 + 入队

参与:GW → Q

动作:

  • JSON Schema 校验 Envelope
  • 解析 channel:account:peer → 定位 Session ID
  • 查 session.dmScope（决策 1）确定会话范围
  • 消息入队（queue.mode 决策 3）

耗时:5-20ms

阶段 3 · Agent 启动

7.6.3 3⃣ Agent 循环启动——加载 + 解析

参与:AL + SM

动作:

  • 从队列取出消息
  • 加载历史（SQLite + Markdown 记忆）
  • 解析 model/runtime/skills（决策 2）
  • 初始化运行栈

耗时:50-200ms

阶段 4 · Prompt 组装

7.6.4 4⃣ 提示词组装——8 层叠加

参与:PB

动作:

  • 加载 basePrompt + skills + bootstrap
  • 注入 memory（history summary）
  • 追加历史 messages
  • 附 user input + attachments

耗时:10-100ms

阶段 5 · 模型推理

7.6.5 5⃣ 模型推理——鉴权 + 流式

参与:PR

动作:

  • 鉴权（OAuth / API Key）
  • 发送请求到 LLM API
  • 流式接收 token → 触发阶段 7 事件
  • 检测 tool_use block → 进入阶段 6

耗时：1-5s（典型）

阶段 6 · 工具执行 · 核心

7.6.6 6⃣ 工具执行——钩子 + 沙箱

参与:TX

动作:

  • before_tool_call 钩子链（决策 4）→ 审计/阻断/改写
  • 沙箱创建（container 级别）
  • 执行 calendar.list_events
  • 返回结果 → after_tool_call 脱敏

耗时:500ms-30s

可循环：模型拿到结果后，可能继续推理（回到阶段 5）

阶段 7 · 流式 + 持久化

7.6.7 7⃣ 流式输出 + 持久化——事件推送

参与：SP + 通道

动作:

  • 流式 token 推到通道（streaming 决策 6）
  • 检查 compaction.threshold（决策 5）
  • 写入 SQLite（messages / tool_calls / events）

耗时：与阶段 5 并行

阶段 8 · 通道回复

7.6.8 8⃣ 通道回复——出站 + 送达回执

参与:WM → WA → U

动作:

  • 最终消息格式化为 WhatsApp 模板
  • 通过 Meta API 发送
  • 接收送达/已读回执

耗时:100-500ms

阶段 9 · 善后

7.6.9 9⃣ 善后——异步清理

参与:CP + Q

动作:

  • 压缩超期会话（用户无感知）
  • 更新统计 metrics
  • 推进队列里的下一条

耗时：0-数秒（后台）

7.7 用户体验时间线

0s用户在 WhatsApp 发送消息

0.05sOpenClaw 收到消息（经过阶段 1-3）

0.1sPrompt 组装完成（阶段 4）

1-3s开始看到首个 token（阶段 5 → 7）

2-5s看到工具调用 calendar.list_events（阶段 6）

3-8s完整回复结束（阶段 7-8）

8s+异步善后处理（阶段 9，用户无感知）

要点

教学价值

：这条场景展示了 OpenClaw 的 3 个核心特征——单一可信网关（阶段 2 集中路由）、不可信执行（阶段 6 沙箱 + 钩子）、声明式策略（所有决策在 config 里）。

7.10 性能瓶颈 + 错误恢复

7.10.1 性能瓶颈

从 9 步流程中识别出 4 个典型瓶颈：

瓶颈位置典型耗时占比
LLM 推理步骤 51-5s~70%
工具调用步骤 60.5-30s~25%
Prompt 组装步骤 410-100ms~2%
通道传输步骤 1， 8100-300ms~3%

要点

优化方向

：LLM 推理占大头——用更小的模型 / prompt caching / streaming / batch 处理。详见 模块 08 性能。

7.10.2 错误恢复路径

每个步骤都有对应的恢复策略——这就是"可恢复优于防御性"：

失败步骤恢复策略
1 通道接入Webhook 重试 / 丢弃（超 N 次）
2 网关路由Schema 错拒绝（不可恢复）
3 Agent 启动回退到默认 model
4 Prompt 组装截断历史 + 简化 memory
5 模型推理fallback chain（模型 1→2→3）
6 工具执行错误返回给 LLM，LLM 换工具
7 持久化WAL 模式 + retry queue
8 通道回复平台 API 重试 / 降级到邮件
9 善后后台任务，不阻塞主流程

要点

不可恢复的失败

：Schema 校验失败、配置错误、磁盘满——这些只能报错给用户。建议在生产环境配置监控告警（详见 09.3 监控）。

7.13 关键步骤拆解 + 4 个亮点

7.13.1 关键步骤拆解

7.13.2 步骤 1-6 · 消息进 Gateway（50-200ms）

用户消息从手机 → WhatsApp 服务器 → 通道插件 → Gateway 队列。

关键决策:session.dmScope（决策 1）、queue.mode（决策 3）

7.13.3 步骤 7-13 · Agent 准备（50-300ms）

从队列取出 → 加载历史 → 组装 8 层 Prompt → 准备调用 LLM。

关键决策:model 选择（决策 2）、systemPrompt 配置（决策 7）

7.13.4 步骤 14-23 · 模型 ↔ 工具循环（1-30s）

LLM 推理 → 流式推送 → 检测 tool_use → 钩子拦截 → 沙箱执行 → 回到 LLM。

关键决策：钩子（决策 4）、沙箱级别、compaction.threshold（决策 5）

7.13.5 步骤 24-28 · 回复与持久化（200-500ms）

写入 SQLite → 通道出站 → 用户看到消息。

关键决策:streaming（决策 6）

7.13.6 步骤 29-31 · 异步善后（后台）

压缩超期会话、更新 metrics、推进下一条消息——用户无感知。

7.13.7 4 个亮点

  1. 步骤 5 集中路由：所有消息都过 Gateway Schema 校验——这是 OpenClaw 单一可信入口的核心。
  2. 步骤 17/21 钩子拦截：工具调用的审计/阻断/脱敏都在这两个步骤——安全模型的物理落地点。
  3. 步骤 18 沙箱隔离：哪怕模型被注入，工具也只能在容器内乱搞——这是"不可信执行"的边界。
  4. 步骤 29 异步善后：压缩不阻塞用户响应，这是"流式先于善后"的体现。

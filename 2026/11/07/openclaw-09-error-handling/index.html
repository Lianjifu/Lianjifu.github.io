第 9 章：异常降级

错误与降级——失败分类与恢复策略

发表于2026-11-07 分类于OpenClaw 源码笔记

11 种异常场景 + 4 级重试策略——失败不是异常，是常态。OpenClaw 的容错设计让系统在部分组件挂掉时仍能降级运行。

思考维度 内容
引导思考 展开
它为什么存在

  • 单一可信网关意味着单点故障必须被显式处理，而不是假设它不会发生
  • 没有错误处理设计，降级就无从谈起

  • 给出可观测性四件套与关键 SLO，让失败能被看见
它在系统中的位置
  • 给模块 02 的单一可信网关加上错误处理维度
  • 覆盖通道层、网关层、模型层、工具层与配置层五处
  • 与模块 08 的性能章节互补：一个讲快，一个讲挂

本章全景

前八章讲的都是「顺利的时候怎么走」。这一章讲失败：错误发生了，系统怎么自救，以及怎么在用户投诉之前就知道。

核心判断是「可恢复优于防御性」：与其在每个可能出错的地方堆防御，不如把错误当正常流程设计——分类、判定可恢复性、选策略、必要时告警。

整章是三块拼起来的：5 类错误 × 4 类恢复策略 × 4 件套可观测性。前两块决定系统扛不扛得住，第三块决定你知不知道它扛不住。

9.1 定位与原则

第一段 · 定位与原则可恢复优于防御性：把错误当作正常流程的一部分来设计。

9.1.1 一句话定位

本章要点

"可恢复优于防御性"——把错误视为正常流程的一部分，设计 fallback 链路、监控告警、自动重试，而不是把所有错误都当作异常抛出。

本模块拆解：5 类错误、4 类恢复策略、可观测性 4 件套 + 关键 SLO。

思考笔记

「可恢复优于防御性」——把错误视为正常流程的一部分，设计 fallback 链路、监控告警、自动重试，而不是把所有错误都当异常抛出。

9.1.2 错误处理的三个原则

思考笔记

错误处理最容易走偏的地方是「一律重试」。三条原则划线：先分类再判定可恢复性，能恢复的自动恢复，不能恢复的立即告警。

原则 含义
可恢复优于防御性把错误处理设计为正常流程的一部分，而不是 try/catch 附加层。失败路径要像正常路径一样被主动规划。
可观测性 = 4 件套Metrics + Logs + Traces + Alerts 缺一不可——用户报障前你必须知道。OpenClaw 内置全部，你接 Prometheus + Grafana 就行。
4 类失败 → 4 类策略抖动（重试）、主备（Fallback）、雪崩（熔断）、末日（降级）——错误先分类，再决定走哪条恢复路径。

9.1.3 模块位置

思考笔记

读法三条：出错先定位类别，五类错误对应五套处理方式；想知道线上有没有出事看指标与告警；要给用户一个承诺看 SLO。

9.2 错误分类

第二段 · 错误分类五类错误对应五套处理方式，先分类，再判定能不能恢复。

9.2.1 5 大错误类别

思考笔记

按发生位置分类，是为了让处理方式也能按位置确定：通道层错误重试即可，配置层错误重试没有意义，必须人工改配置。

把错误按发生位置分类——不同位置有不同的恢复策略。先识别你的错误属于哪类。

9.2.2 5 大类详解

思考笔记

五类错误的共同点是「恢复动作不一样」：通道层重连，网关层排队，Agent 层降级，工具层换工具，配置层停机等人。

类别 1 · ChannelError

通道层错误

位置：通道接入与出站（模块 03)

示例:

  • WEBHOOK_429——Meta/Telegram/Slack 限流
  • WEBHOOK_TIMEOUT——Webhook 投递超时
  • AUTH_REVOKED——Bot token 失效
  • RATE_LIMIT_EXCEEDED——用户消息频率超限
  • CHANNEL_DOWN——通道平台宕机

可恢复性:高 大多数自动重试

默认处理：指数退避 + 平台重试 + 失败 N 次后丢弃并告警

类别 2 · GatewayError

网关层错误

位置：网关路由、Schema 校验、会话解析

示例:

  • SCHEMA_VALIDATION_FAILED——Envelope 字段缺失/类型错
  • SESSION_NOT_FOUND——会话 ID 不存在（罕见）
  • QUEUE_FULL——队列满（过载）
  • PERMISSION_DENIED——通道权限配置错误

可恢复性:中 部分自动恢复

默认处理：Schema 错直接拒绝（不可恢复）；队列满等几秒重试；权限错告警。

类别 3 · AgentError

Agent 层错误

位置：模型推理、Prompt 组装、Agent 循环

示例:

  • LLM_5XX——Anthropic/OpenAI 服务异常
  • LLM_TIMEOUT——模型响应超时（> 30s）
  • LLM_CONTEXT_OVERFLOW——Prompt 超上下文窗口
  • LLM_AUTH_FAILED——API Key 无效
  • MAX_TOOL_ROUNDS_EXCEEDED——工具循环超 20 轮
  • STREAM_INTERRUPTED——流式连接中断

可恢复性:高 fallback chain 重试

默认处理：Sonnet → Haiku fallback；5xx/timeout 重试；context overflow 截断历史；超 20 轮强制结束。

类别 4 · ToolError

工具层错误

位置：工具执行、沙箱、钩子

示例:

  • TOOL_TIMEOUT——工具执行超时（默认 30s）
  • SANDBOX_INIT_FAILED——container 沙箱启动失败
  • TOOL_NOT_FOUND——工具未注册
  • TOOL_ARG_INVALID——参数校验失败
  • HOOK_REJECTED——钩子拒绝（审计不通过）
  • POLICY_DENIED——策略引擎拒绝

可恢复性:高 错误返回给 LLM

默认处理：超时重试 3 次；沙箱失败 1 次重试；钩子拒绝告知 LLM，LLM 换工具；参数错直接返回 LLM 修正。

类别 5 · ConfigError

配置层错误

位置：配置加载、Schema 校验、模型/工具注册

示例:

  • CONFIG_INVALID——YAML/JSON 格式错
  • CONFIG_REQUIRED_MISSING——必填字段缺失
  • MODEL_NOT_FOUND——模型名错
  • TOOL_NOT_REGISTERED——工具未在 config 中声明
  • DISK_FULL——SQLite 磁盘满
  • PERMISSION_DENIED_FILE——文件权限错

可恢复性:低 需要人工修复

默认处理:启动失败，Gateway 拒绝启动。运行期发生的（磁盘满）立即告警 + 拒绝新请求。

9.2.3 可恢复性矩阵 + 错误处理配置

思考笔记

设计原则

：把可恢复错误处理为"正常流程"——用户看不到重试，直接得到结果。不可恢复错误要 立即告警，而不是悄悄重试无限次。

可恢复性矩阵

类别示例错误频率可恢复默认策略
1 通道429, timeout中高指数退避 + 平台重试
2 网关Schema 错低中拒绝 + 队列等
3 Agent5xx， 超时中高fallback chain
4 工具超时， 沙箱失败中高重试 + 告知 LLM
5 配置YAML 错， 磁盘满低低启动失败 + 告警

可恢复 vs 不可恢复

可恢复错误：临时性、相同输入重试可能成功、对最终结果影响小。

  • 网络超时、5xx、限流
  • 沙箱启动失败（资源临时不足）
  • LLM stream 中断（可重连）
  • 磁盘写失败（可重试到 WAL）

不可恢复错误：相同输入必然失败、需要人工介入。

  • Schema 校验失败（消息格式错）
  • API Key 无效
  • YAML 格式错
  • 磁盘满（除非扩容）
  • 钩子拒绝（审计不通过）

错误处理配置

# config/openclaw.yaml — 错误处理全局配置
errors:
  retry:
    maxAttempts: 3          # 默认重试次数
    initialDelay: "1s"       # 初始延迟
    maxDelay: "30s"          # 最大延迟
    backoffMultiplier: 2     # 指数退避倍数
  circuitBreaker:
    errorThreshold: 0.5     # 50% 错误率熔断
    window: "60s"           # 滑动窗口
    cooldown: "5m"          # 熔断持续
  fallbackChain:
    - claude-sonnet-4          # 首选
    - claude-haiku-4-5        # fallback
    - "static:I'm having trouble..."  # 静态 fallback

9.3 恢复策略

第三段 · 恢复策略退避重试、主备链、熔断、优雅降级——四个层次，逐层加码。

9.3.1 4 类恢复策略

思考笔记

四个策略不是四个选项，而是四个层次：退避重试解决临时抖动，主备链解决单点失效，熔断解决雪崩，优雅降级解决「不完美但可用」。

失败不可怕，可怕的是失败的方式不可控——4 个策略让失败变得可控、可预测、可恢复。

9.3.2 4 策略详解

思考笔记

防雪崩

：OpenClaw 可能在 1 分钟内涌入 1000 个消息，如果 LLM 限流 5xx，没有熔断会全部堆积。Circuit breaker 让失败请求 立即返回，不堆积在队列。
策略 1 · 临时抖动

指数退避重试（Exponential Backoff）

适用：网络抖动、5xx、超时——临时性问题，重试大概率成功。

原理：第 N 次重试等待 initialDelay × multiplier^N，加随机 jitter 防雪崩。

次数延迟累计
第 1 次1s1s
第 2 次2s3s
第 3 次4s7s
第 4 次8s15s
第 5 次16s31s

配置:

errors:
  retry:
    maxAttempts: 3          # 默认重试 3 次
    initialDelay: "1s"
    maxDelay: "30s"
    backoffMultiplier: 2
    jitter: "full"             # 0-100% 随机抖动

注意：不是所有错误都该重试。4xx（客户端错）直接拒绝，不重试。

策略 2 · 主备切换

Fallback Chain（主备链）

适用：主服务失败但备服务可用——比如 Sonnet 限流时切到 Haiku。

原理：按顺序尝试多个 provider，直到成功或全部失败。

providers:
  - name: claude-sonnet-4
    primary: true
  - name: claude-haiku-4-5
    fallback: true
  - name: ollama:llama-3.3
    fallback: true
    triggerOn: ["LLM_5XX", "LLM_TIMEOUT"]

触发切换的错误类型:

  • LLM_5XX——主服务 5xx
  • LLM_TIMEOUT——主服务超时
  • LLM_RATE_LIMITED——主服务限流
  • LLM_OVERLOADED——主服务过载
策略 3 · 防雪崩

Circuit Breaker（熔断器）

适用：下游服务持续失败时，防止请求堆积把上游拖垮。

三个状态:

  • Closed：正常，所有请求通过
  • Open：熔断，直接返回错误（5 分钟冷却）
  • Half-Open：放 1 个测试请求，成功 → Closed，失败 → Open

配置:

circuitBreaker:
  errorThreshold: 0.5      # 50% 错误率触发
  minRequests: 10         # 至少 10 个请求
  window: "60s"            # 滑动窗口
  cooldown: "5m"            # Open 持续
  halfOpenMax: 1          # 测试请求数
策略 4 · 不可恢复

优雅降级（Graceful Degradation）

适用：所有重试/fallback 都失败的"末日场景"——必须给用户一个体面的回复。

降级层级（从好到差）：

层级方案用户感受
1完整回复（Sonnet）
2简化回复（Haiku）
3缓存回复（历史相似问题）
4FAQ 静态回复
5告知稍后重试

配置:

degradation:
  tiers:
    - model: claude-haiku-4-5
      trigger: "primary_failed"
    - source: cache
      matchStrategy: semantic      # 语义相似
      minSimilarity: 0.85
    - source: faq
      file: faq.md
    - "我暂时无法处理请求,请稍后再试 "

9.3.3 决策流程 + 案例

思考笔记

决策流程把上面所有判断压成一棵可执行的树：先判断可恢复性，再选策略，最后才决定是否告警。照着走，就不会在半夜对着日志猜。

决策流程

案例

案例 1：LLM 限流

用户消息突然激增，Sonnet 4 触发 429。

  1. 第 1 次：Sonnet 429 → 等待 1s 重试
  2. 第 2 次：Sonnet 429 → 等待 2s 重试
  3. 第 3 次：Sonnet 429 → 切换 Haiku(fallback)
  4. Haiku 成功 → 用户无感
案例 2：LLM 持续失败

所有 provider 都返回 5xx。

  1. 请求 1-10：部分失败，错误率 < 50% → 继续重试
  2. 请求 11+：错误率 80% → 熔断器触发（Open 状态）
  3. 后续 5 分钟：直接返回降级回复，不调用 LLM
  4. 5 分钟后：测试 1 个请求 → 成功 → 恢复 Closed
案例 3：磁盘满

SQLite 写入失败（disk full）。

  1. 持久化失败 → 重试 3 次
  2. 仍失败 → 告警（磁盘满）
  3. 主流程继续——内存中暂存，等磁盘恢复后持久化
  4. 用户感知不到（响应正常返回）

9.4 可观测性与 SLO

第四段 · 可观测性与 SLO指标、日志、追踪、告警——在用户报障之前先知道。

9.4.1 可观测性 4 件套

思考笔记

出了问题怎么知道？用户报障前必须知道。四件套：指标、日志、追踪、告警——缺一件，故障发现就会从「告警」退化到「用户投诉」。

出了问题怎么知道？用户报障前必须知道——OpenClaw 内置的可观测性 4 件套 + 关键 SLO。

指标 Metrics
数值型时间序列——计数、延迟、直方图。Prometheus 格式输出。
日志 Logs
结构化 JSON 日志——每条事件都带 traceId， 可关联到追踪。
追踪 Traces
跨组件追踪——OpenTelemetry 标准，可视化请求链路。
告警 Alerts
基于指标触发——PagerDuty / Slack / 邮件，分级响应。

9.4.2 指标 + 日志

思考笔记

指标回答「有没有事」，日志回答「发生了什么」，追踪回答「在哪一步」。三者缺一，排查就会从「定位」退化到「翻日志猜」。

指标（Metrics）

OpenClaw 默认暴露 Prometheus 指标，端口 9090/metrics:

指标类型含义
openclaw_messages_totalCounter处理消息总数（channel 标签）
openclaw_response_time_secondsHistogram响应时间分布（分阶段）
openclaw_errors_totalCounter错误总数（error_type 标签）
openclaw_tool_calls_totalCounter工具调用总数（tool_name 标签）
openclaw_tokens_totalCounterLLM token 消耗（input/output 标签）
openclaw_queue_sizeGauge当前队列长度
openclaw_circuit_stateGauge熔断器状态（0=Closed，1=Open，2=HalfOpen）

Grafana 仪表盘模板（开箱即用）：

# grafana/dashboards/openclaw.json
# 5 个核心面板:
#   1. 请求量 + 错误率(双 Y 轴)
#   2. P50/P95/P99 延迟
#   3. Token 消耗趋势
#   4. 各通道消息量(stacked area)
#   5. 熔断器状态时间线

日志（Logs）

OpenClaw 输出 结构化 JSON 日志（默认 stdout，生产建议收 Loki / CloudWatch）：

// 单条日志示例
{
  "timestamp": "2026-09-05T10:23:45.123Z",
  "level": "info",
  "traceId": "5f3a...",
  "sessionId": "whatsapp:user1:bot123",
  "channel": "whatsapp",
  "event": "message_received",
  "toolCalls": 1,
  "durationMs": 2340,
  "tokens": {"input": 1250, "output": 340}
}

日志级别:

  • debug——调试信息（默认关闭）
  • info——关键事件（message_received / tool_called / response_sent）
  • warn——降级、fallback 触发
  • error——失败、超出重试
  • fatal——进程级错误（立即告警）

9.4.3 追踪 + 告警

思考笔记

追踪把散在多个服务里的调用串成一条链，告警决定什么时候叫人。两者配合，才有「用户还没投诉，我们已经知道」。

追踪（Traces）

OpenClaw 默认开启 OpenTelemetry，导出到 Jaeger / Tempo / Honeycomb：

Span 属性（标准 OpenTelemetry）：

  • openclaw.channel——通道类型
  • openclaw.session.id——会话 ID
  • openclaw.tool.name——工具名
  • openclaw.llm.model——模型名
  • openclaw.tokens.input——输入 token

告警（Alerts）

推荐配置——基于 PromQL 的告警规则：

groups:
  - name: openclaw_critical
    rules:
      # 告警 1:错误率 > 5%
      - alert: OpenClawHighErrorRate
        expr: |
          rate(openclaw_errors_total[5m]) /
          rate(openclaw_messages_total[5m]) > 0.05
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "错误率 5 分钟内 > 5%"

      # 告警 2:P99 延迟 > 30s
      - alert: OpenClawSlowResponse
        expr: |
          histogram_quantile(0.99,
            rate(openclaw_response_time_seconds_bucket[5m])
          ) > 30
        for: 10m
        labels: { severity: warning }

      # 告警 3:熔断器持续 Open
      - alert: OpenClawCircuitOpen
        expr: openclaw_circuit_state == 1
        for: 2m
        labels: { severity: critical }

      # 告警 4:Token 消耗异常
      - alert: OpenClawTokenSpike
        expr: |
          rate(openclaw_tokens_total[1h]) >
          rate(openclaw_tokens_total[24h] offset 1d) * 3
        for: 15m
        labels: { severity: warning }

9.4.4 关键 SLO + 模板 + 清单

思考笔记

错误预算

：99.5% 可用性 = 每月允许 ~3.6 小时停机。如果用完，新功能冻结——这是 SRE 用来平衡"速度 vs 稳定"的工具。

关键 SLO

SLO（Service Level Objective）是你对用户的承诺：

SLO目标测量方式
可用性99.5%成功响应 / 总请求（5min 滑动）
TTFT P95< 3s首 token 时间 P95
总延迟 P95< 10s完整响应 P95
工具成功率> 95%tool_calls.success / tool_calls.total
Fallback 触发率< 5%fallback_calls / total_calls

模板与工具

  • Grafana 仪表盘:openclaw/grafana/openclaw-overview.json（开箱即用）
  • Prometheus 告警规则:openclaw/prometheus/alerts.yml（上文示例）
  • OpenTelemetry Collector 配置:openclaw/otel-collector-config.yaml
  • 健康检查端点:GET /healthz（200 OK 表示健康）
  • 就绪检查端点:GET /readyz（检查依赖）

9.5 总结

收束 · 本章结论把失败视角的判断收成几条结论，并交代下一章的接口。

9.5.1 一句话总结

思考笔记

5 类错误 × 4 类策略 × 4 件套可观测性 = 完整的"失败视角"。



用户报障前必须知道——4 件套缺一不可。OpenClaw 内置全部，你只需要接 Prometheus + Grafana + Jaeger。

9.5.2 本章结论

  1. 可恢复优于防御性。把错误当正常流程设计，比堆防御代码更省事也更可靠。
  2. 先分类再判定。五类错误对应五套处理方式，重试不是万能药——配置错误重试一万次也没用。
  3. 四个策略是四个层次：退避重试、主备链、熔断、优雅降级，逐层加码，不必一步到位。
  4. 熔断不是可选项。没有熔断，一次限流就能把队列堆满，把局部故障放大成全局故障。
  5. 可观测性要在上线前配好。四件套齐全，故障发现才靠告警而不是靠用户。

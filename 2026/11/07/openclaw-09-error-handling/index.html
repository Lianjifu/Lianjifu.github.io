第 9 章：异常降级

错误处理与降级策略

发表于2026-11-07 分类于OpenClaw 源码笔记

11 种异常场景 + 4 级重试策略——失败不是异常，是常态。OpenClaw 的容错设计让系统在部分组件挂掉时仍能降级运行。

§ 1一句话定位

"可恢复优于防御性"——把错误视为正常流程的一部分，设计 fallback 链路、监控告警、自动重试，而不是把所有错误都当作异常抛出。本模块拆解：5 类错误、4 类恢复策略、可观测性 4 件套 + 关键 SLO。

§ 2错误处理的三个原则

可恢复优于防御性
把错误处理设计为正常流程的一部分，而不是 try/catch 附加层。失败路径要像正常路径一样被主动规划。
可观测性 = 4 件套
Metrics + Logs + Traces + Alerts 缺一不可——用户报障前你必须知道。OpenClaw 内置全部，你接 Prometheus + Grafana 就行。
4 类失败 → 4 类策略
抖动（重试）、主备（Fallback）、雪崩（熔断）、末日（降级）——错误先分类，再决定走哪条恢复路径。

§ 3模块位置

§ 45 大错误类别

把错误按发生位置分类——不同位置有不同的恢复策略。先识别你的错误属于哪类。

§ 55 大类详解

类别 1 · ChannelError

§ 5.1 通道层错误

位置：通道接入与出站（模块 03)

示例:

  • WEBHOOK_429——Meta/Telegram/Slack 限流
  • WEBHOOK_TIMEOUT——Webhook 投递超时
  • AUTH_REVOKED——Bot token 失效
  • RATE_LIMIT_EXCEEDED——用户消息频率超限
  • CHANNEL_DOWN——通道平台宕机

可恢复性:高 大多数自动重试

默认处理：指数退避 + 平台重试 + 失败 N 次后丢弃并告警

类别 2 · GatewayError

§ 5.2 网关层错误

位置：网关路由、Schema 校验、会话解析

示例:

  • SCHEMA_VALIDATION_FAILED——Envelope 字段缺失/类型错
  • SESSION_NOT_FOUND——会话 ID 不存在（罕见）
  • QUEUE_FULL——队列满（过载）
  • PERMISSION_DENIED——通道权限配置错误

可恢复性:中 部分自动恢复

默认处理：Schema 错直接拒绝（不可恢复）；队列满等几秒重试；权限错告警。

类别 3 · AgentError

§ 5.3 Agent 层错误

位置：模型推理、Prompt 组装、Agent 循环

示例:

  • LLM_5XX——Anthropic/OpenAI 服务异常
  • LLM_TIMEOUT——模型响应超时（> 30s）
  • LLM_CONTEXT_OVERFLOW——Prompt 超上下文窗口
  • LLM_AUTH_FAILED——API Key 无效
  • MAX_TOOL_ROUNDS_EXCEEDED——工具循环超 20 轮
  • STREAM_INTERRUPTED——流式连接中断

可恢复性:高 fallback chain 重试

默认处理：Sonnet → Haiku fallback；5xx/timeout 重试；context overflow 截断历史；超 20 轮强制结束。

类别 4 · ToolError

§ 5.4 工具层错误

位置：工具执行、沙箱、钩子

示例:

  • TOOL_TIMEOUT——工具执行超时（默认 30s）
  • SANDBOX_INIT_FAILED——container 沙箱启动失败
  • TOOL_NOT_FOUND——工具未注册
  • TOOL_ARG_INVALID——参数校验失败
  • HOOK_REJECTED——钩子拒绝（审计不通过）
  • POLICY_DENIED——策略引擎拒绝

可恢复性:高 错误返回给 LLM

默认处理：超时重试 3 次；沙箱失败 1 次重试；钩子拒绝告知 LLM，LLM 换工具；参数错直接返回 LLM 修正。

类别 5 · ConfigError

§ 5.5 配置层错误

位置：配置加载、Schema 校验、模型/工具注册

示例:

  • CONFIG_INVALID——YAML/JSON 格式错
  • CONFIG_REQUIRED_MISSING——必填字段缺失
  • MODEL_NOT_FOUND——模型名错
  • TOOL_NOT_REGISTERED——工具未在 config 中声明
  • DISK_FULL——SQLite 磁盘满
  • PERMISSION_DENIED_FILE——文件权限错

可恢复性:低 需要人工修复

默认处理:启动失败，Gateway 拒绝启动。运行期发生的（磁盘满）立即告警 + 拒绝新请求。

§ 6可恢复性矩阵 + 错误处理配置

§ 6.1可恢复性矩阵matrix

类别示例错误频率可恢复默认策略
1 通道429, timeout中高指数退避 + 平台重试
2 网关Schema 错低中拒绝 + 队列等

§ 6.2可恢复 vs 不可恢复recoverable

可恢复错误：临时性、相同输入重试可能成功、对最终结果影响小。

  • 网络超时、5xx、限流
  • 沙箱启动失败（资源临时不足）
  • LLM stream 中断（可重连）
  • 磁盘写失败（可重试到 WAL）

不可恢复错误：相同输入必然失败、需要人工介入。

  • Schema 校验失败（消息格式错）
  • API Key 无效
  • YAML 格式错
  • 磁盘满（除非扩容）
  • 钩子拒绝（审计不通过）
设计原则：把可恢复错误处理为"正常流程"——用户看不到重试，直接得到结果。不可恢复错误要 立即告警，而不是悄悄重试无限次。

§ 6.3错误处理配置config

# config/openclaw.yaml — 错误处理全局配置
errors:
  retry:
    maxAttempts: 3          # 默认重试次数
    initialDelay: "1s"       # 初始延迟
    maxDelay: "30s"          # 最大延迟
    backoffMultiplier: 2     # 指数退避倍数
  circuitBreaker:
    errorThreshold: 0.5     # 50% 错误率熔断
    window: "60s"           # 滑动窗口
    cooldown: "5m"          # 熔断持续
  fallbackChain:
    - claude-sonnet-4          # 首选
    - claude-haiku-4-5        # fallback
    - "static:I'm having trouble..."  # 静态 fallback

§ 74 类恢复策略

失败不可怕，可怕的是失败的方式不可控——4 个策略让失败变得可控、可预测、可恢复。

§ 84 策略详解

策略 1 · 临时抖动

§ 8.1 指数退避重试（Exponential Backoff）

适用：网络抖动、5xx、超时——临时性问题，重试大概率成功。

原理：第 N 次重试等待 initialDelay × multiplier^N，加随机 jitter 防雪崩。

次数延迟累计
第 1 次1s1s
第 2 次2s3s
第 3 次4s7s
第 4 次8s15s
第 5 次16s31s

配置:

errors:
  retry:
    maxAttempts: 3          # 默认重试 3 次
    initialDelay: "1s"
    maxDelay: "30s"
    backoffMultiplier: 2
    jitter: "full"             # 0-100% 随机抖动

注意：不是所有错误都该重试。4xx（客户端错）直接拒绝，不重试。

策略 2 · 主备切换

§ 8.2 Fallback Chain（主备链）

适用：主服务失败但备服务可用——比如 Sonnet 限流时切到 Haiku。

原理：按顺序尝试多个 provider，直到成功或全部失败。

providers:
  - name: claude-sonnet-4
    primary: true
  - name: claude-haiku-4-5
    fallback: true
  - name: ollama:llama-3.3
    fallback: true
    triggerOn: ["LLM_5XX", "LLM_TIMEOUT"]

触发切换的错误类型:

  • LLM_5XX——主服务 5xx
  • LLM_TIMEOUT——主服务超时
  • LLM_RATE_LIMITED——主服务限流
  • LLM_OVERLOADED——主服务过载
策略 3 · 防雪崩

§ 8.3 Circuit Breaker（熔断器）

适用：下游服务持续失败时，防止请求堆积把上游拖垮。

三个状态:

  • Closed：正常，所有请求通过
  • Open：熔断，直接返回错误（5 分钟冷却）
  • Half-Open：放 1 个测试请求，成功 → Closed，失败 → Open

配置:

circuitBreaker:
  errorThreshold: 0.5      # 50% 错误率触发
  minRequests: 10         # 至少 10 个请求
  window: "60s"            # 滑动窗口
  cooldown: "5m"            # Open 持续
  halfOpenMax: 1          # 测试请求数
防雪崩：OpenClaw 可能在 1 分钟内涌入 1000 个消息，如果 LLM 限流 5xx，没有熔断会全部堆积。Circuit breaker 让失败请求 立即返回，不堆积在队列。
策略 4 · 不可恢复

§ 8.4 优雅降级（Graceful Degradation）

适用：所有重试/fallback 都失败的"末日场景"——必须给用户一个体面的回复。

降级层级（从好到差）：

层级方案用户感受
1完整回复（Sonnet）
2简化回复（Haiku）
3缓存回复（历史相似问题）
4FAQ 静态回复
5告知稍后重试

配置:

degradation:
  tiers:
    - model: claude-haiku-4-5
      trigger: "primary_failed"
    - source: cache
      matchStrategy: semantic      # 语义相似
      minSimilarity: 0.85
    - source: faq
      file: faq.md
    - "我暂时无法处理请求,请稍后再试 "

§ 9.2案例case

§ 9.2.1 案例 1：LLM 限流

用户消息突然激增，Sonnet 4 触发 429。

  1. 第 1 次：Sonnet 429 → 等待 1s 重试
  2. 第 2 次：Sonnet 429 → 等待 2s 重试
  3. 第 3 次：Sonnet 429 → 切换 Haiku(fallback)
  4. Haiku 成功 → 用户无感

§ 9.2.2 案例 2：LLM 持续失败

所有 provider 都返回 5xx。

  1. 请求 1-10：部分失败，错误率 < 50% → 继续重试
  2. 请求 11+：错误率 80% → 熔断器触发（Open 状态）
  3. 后续 5 分钟：直接返回降级回复，不调用 LLM
  4. 5 分钟后：测试 1 个请求 → 成功 → 恢复 Closed

§ 9.2.3 案例 3：磁盘满

SQLite 写入失败（disk full）。

  1. 持久化失败 → 重试 3 次
  2. 仍失败 → 告警（磁盘满）
  3. 主流程继续——内存中暂存，等磁盘恢复后持久化
  4. 用户感知不到（响应正常返回）

§ 10可观测性 4 件套

出了问题怎么知道？用户报障前必须知道——OpenClaw 内置的可观测性 4 件套 + 关键 SLO。

指标 Metrics
数值型时间序列——计数、延迟、直方图。Prometheus 格式输出。
日志 Logs
结构化 JSON 日志——每条事件都带 traceId， 可关联到追踪。
追踪 Traces

§ 12.2告警（Alerts）alerts

推荐配置——基于 PromQL 的告警规则：

groups:
  - name: openclaw_critical
    rules:
      # 告警 1:错误率 > 5%
      - alert: OpenClawHighErrorRate
        expr: |
          rate(openclaw_errors_total[5m]) /
          rate(openclaw_messages_total[5m]) > 0.05
        for: 5m
        labels: { severity: warning }
        annotations:
          summary: "错误率 5 分钟内 > 5%"

      # 告警 2:P99 延迟 > 30s
      - alert: OpenClawSlowResponse
        expr: |
          histogram_quantile(0.99,
            rate(openclaw_response_time_seconds_bucket[5m])
          ) > 30
        for: 10m
        labels: { severity: warning }

      # 告警 3:熔断器持续 Open
      - alert: OpenClawCircuitOpen
        expr: openclaw_circuit_state == 1
        for: 2m
        labels: { severity: critical }

      # 告警 4:Token 消耗异常
      - alert: OpenClawTokenSpike
        expr: |
          rate(openclaw_tokens_total[1h]) >
          rate(openclaw_tokens_total[24h] offset 1d) * 3
        for: 15m
        labels: { severity: warning }

§ 13关键 SLO + 模板 + 清单

§ 13.1关键 SLOslo

SLO（Service Level Objective）是你对用户的承诺：

SLO目标测量方式
可用性99.5%成功响应 / 总请求（5min 滑动）
TTFT P95< 3s首 token 时间 P95
总延迟 P95< 10s完整响应 P95
工具成功率> 95%tool_calls.success / tool_calls.total
Fallback 触发率< 5%fallback_calls / total_calls
错误预算：99.5% 可用性 = 每月允许 ~3.6 小时停机。如果用完，新功能冻结——这是 SRE 用来平衡"速度 vs 稳定"的工具。

§ 14.2常见问题faq

  • 哪些错误会自动重试？
    网络超时、5xx 错误、临时资源不足——走指数退避。其他错误（如 4xx）直接返回 LLM。
  • 重试多少次合适？
    工具调用默认 3 次（指数退避 1s→2s→4s），LLM 调用默认 fallback chain 切换 1 次。
  • 怎么监控？
    OpenClaw 内置 metrics + structured logs，接入 Prometheus / Grafana / OpenTelemetry。详见 § 10-13。
  • 如何防止雪崩？
    Circuit breaker——当错误率 > 阈值时，自动熔断，降级到 fallback。详见 § 8 策略 3。
  • 熔断器阈值怎么设？
    推荐 50% 错误率，至少 10 个请求为窗口基础，5 分钟冷却。生产环境先观察一周再调优。
  • 不可恢复错误应该重试吗？
    不应该。Schema 错、API Key 无效等，重试无限次也不会成功——应该立即告警 + 拒绝请求。
  • 4 件套缺一不可吗？
    是的。Metrics（数值趋势） + Logs（具体事件） + Traces（调用链） + Alerts（主动通知）——任一缺失都难以快速定位问题。

§ 14.3一句话总结summary

5 类错误 × 4 类策略 × 4 件套可观测性 = 完整的"失败视角"。

性能基线与延迟分析

发表于2026-11-07 分类于OpenClaw 源码笔记

1，200 msg/s 与 0.8s TTFT——OpenClaw 的性能基线和瓶颈定位。把每条消息的耗时拆到毫秒级，识别"必须优化"vs"可以接受"。

§ 1一句话定位

性能优化的 80/20：大多数优化在 LLM 推理层——用 prompt caching、流式响应、合适的模型，把响应时间减半。本模块用数据告诉你 9 阶段耗时分布、3 种典型场景对比、5 大类 10+ 个具体优化方法。

§ 2性能优化的三个原则

80/20 法则
LLM 推理占 75% 耗时——把优化资源投在 P0（模型选择 + Prompt Caching + 流式），其他阶段边际效益递减。
流式优先
TTFT（首 token 时间）比总延迟更重要——用户看到第一个字符就认为"在响应"。流式 + 提前"思考中"消息可降低感知延迟 1s+。
配置 > 代码
所有优化都通过 openclaw.json5 配置——不改核心代码就能提效 50%。改配置 vs 改代码：总是先试配置。

§ 5.1占比分析percentage

80/20 法则：模型推理占 75% 耗时——你应该用 prompt caching、更小模型、流式优化去压缩这一段，而不是花时间优化 50ms 的本地路由。

流式增量20-100ms/token"在打字的感觉"

§ 7首 token 优化 （TTFT）

"首 token 到达时间"（TTFT） 是最影响用户感知的指标——优化优先级最高：

方法节省代价
更小模型（Haiku vs Sonnet）40-60%质量下降
Prompt caching30-50%首次写入开销
预热连接（keep-alive）100-300ms空闲连接
本地模型（Ollama）70-90%硬件成本
提前出"正在思考"感知延迟 -1000ms无
心理学技巧：用户对延迟的容忍度，与"是否有反馈"成正比——在 TTFT 前先发个"正在思考..."或"查日历中..."，用户感知延迟可降低 1s。

  • 截断工具结果：大响应截断，避免上下文爆炸

§ 10优化全景 + 5 大类

§ 10.1优化全景overview

§ 10.2类别 1 · 模型层（最优先）layer-1

类别 1 · 模型层

§ 10.3 模型层优化

LLM 推理占总耗时 75%——模型层优化收益最大。

  • ~50%
    1.1 · 模型分层（Sonnet vs Haiku）
    简单任务用 Haiku（40-60% 便宜、5 倍快），复杂任务才用 Sonnet。agents.defaults.model: claude-haiku-4-5。详见 模块 04 模型。
  • ~70%
    1.2 · 本地模型（Ollama）
    硬件允许时（> 16GB VRAM），Ollama 跑开源模型（llama-3.3-70b、qwen-2.5-72b），延迟 100-300ms，零成本，隐私安全。
  • ~25%
    1.3 · Batch 处理
    非交互式任务（总结、分类），用 Batch API（anthropic.messages.batches.create），5 分钟内返回，价格 -50%。
  • ~10%
    1.4 · Fallback 链
    首选 Sonnet，失败自动降级 Haiku。providers: [{ name: sonnet, primary: true }, { name: haiku, fallback: true }]。

§ 10.4类别 2 · Prompt 层（最优先）layer-2

类别 2 · Prompt 层

§ 10.5 Prompt 层优化

把不变的部分缓存，减少每次传输的 token 数。

  • ~50%
    2.1 · Prompt Caching（最关键）
    Anthropic 原生支持。cache_control: { type: ephemeral } 标记静态部分（System + Tools + Memory）。缓存命中时成本 -90%，延迟 -70%。
    // config/agents.yaml
agents:
  defaults:
    promptCaching:
      enabled: true
      breakpoints:
        - tools      # 工具列表缓存
        - system     # system prompt 缓存
        - memory     # memory 文件缓存
  • ~30%
    2.2 · Memory 摘要
    超 50 轮历史压缩为 memory.md 摘要（决策 5）。每次推理只传摘要，token 数从 50k 降到 2k。详见 模块 05 会话。
  • ~15%
    2.3 · 动态 Prompt 截断
    prompt.truncate.attachment: 5KB——大附件只传前 5KB，降低 input token。
  • ~10%
    2.4 · 共享 System Prompt
    多 Agent 共享同一个 base system prompt，避免每个 Agent 重复注入。agents.shared.basePrompt: prompts/base.md。

§ 10.6类别 3 · 流式层layer-3

类别 3 · 流式层

§ 10.7 流式层优化

用户感知延迟靠流式——TTFT 越短越好。

  • ~30%
    3.1 · Streaming 必开
    streaming.enabled: true（默认）。用户看到首个 token 后即认为 Bot 在响应——1-3s TTFT 即可。
  • ~20%
    3.2 · 提前"思考中"消息
    通过钩子在 LLM 推理前推送 正在思考... 状态消息，用户感知延迟可降低 1s。详见 模块 06 工具钩子。
  • ~5%
    3.3 · 连接预热
    providers[].keepAlive: true——保持 HTTP/2 长连接，省 TCP/TLS 握手 100-300ms。

§ 10.8类别 4 · 并发层layer-4

类别 4 · 并发层

§ 10.9 并发层优化

工具调用累计耗时 = 67%——并行是关键。

  • ~70%
    4.1 · 工具并行调用
    模型一次返回多个 tool_use 时，Gateway 默认并行执行。agents.defaults.parallelToolCalls: true,maxConcurrency: 5。5 个独立 API 调用从 15s 降到 3s。
  • ~50%
    4.2 · 工具结果缓存
    不变的工具结果（读日历、查天气）缓存 60s。tools.cache.ttl: 60。重复查询从 3s 降到 200ms。
  • ~30%
    4.3 · 工具超时设置
    tools.timeout: 30000（默认 5 分钟太长）。外部 API 30s 未响应立即失败，LLM 换工具。
  • ~15%
    4.4 · 结果截断
    tools.truncate.response: 20KB——工具响应过大时截断，避免上下文爆炸。详见 模块 06 工具钩子。

§ 10.10类别 5 · 架构层layer-5

类别 5 · 架构层

§ 10.11 架构层优化

需要更多投入——但适合特定场景。

  • ~80%
    5.1 · 边缘部署
    Gateway 部署到用户就近节点（Cloudflare、Vercel Edge），海外用户通道延迟从 500ms 降到 50ms。
  • ~60%
    5.2 · Plan-Execute 模式
    用 Parallel Runtime（详见 模块 04 模型），先做计划、再并行执行——复杂调研类任务从 30s 降到 8s。
  • ~40%
    5.3 · Speculative Decoding
    本地小模型先草拟 token，云端大模型批量确认——2-3 倍速度提升，适合代码补全等场景。
  • ~10%
    5.4 · WebSocket 复用
    不要每次新建 HTTP 连接——长连接 + keep-alive，降网络延迟 50-100ms。

§ 12.2常见问题faq

  • 首 token 延迟通常多少？
    云端 Sonnet 4 约 800ms-2s，本地 Ollama 约 100-500ms（模型大小而定）。
  • prompt caching 能省多少？
    典型场景 50-80% 成本下降，延迟减少 30-50%。详见 § 10 类别 2 Prompt Caching。
  • 什么时候用本地模型？
    隐私敏感、低延迟要求、成本敏感、批量任务。质量敏感仍用云端。
  • 流式对长回复有帮助吗？
    有。流式让用户在 1-3s 就看到首个 token，后面持续"打字中"——用户感知延迟大幅降低，即使总耗时相同。
  • 工具调用慢能怎么救？
    3 招：① 工具结果缓存（60s 内不重调）② 工具超时设短（30s 默认 5min）③ 多个独立工具并行（parallel： true）。
  • 优化优先级如何选？
    P0 立即做（1 小时内）：prompt caching、streaming、超时；P1 本周做（2 小时内）：模型分层、缓存、钩子；P2 必要时做（1-2 天）：本地模型、Plan-Execute。详见 § 11 清单。
  • 性能优化的 80/20 法则？
    80% 的延迟来自 LLM 推理层——把优化时间投在这里（模型选择 + Prompt Caching + 流式）收益最大；本地 50ms 的路由优化收益几乎为零。

§ 12.3一句话总结summary

优化优先级：P0 = prompt caching + streaming + 超时（立即做）。P1 = 模型分层 + 缓存 + 钩子（本周做）。P2 = 本地模型 + Plan-Execute（需要时做）。

80% 的性能问题，通过 P0 + P1 就能解决。LLM 推理占 75% 耗时——优化资源应该全部投在这里。

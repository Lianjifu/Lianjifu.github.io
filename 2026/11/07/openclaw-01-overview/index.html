发表于2026-11-07 分类于OpenClaw 源码笔记

1.1 一句话定位

本章要点

OpenClaw 不是"又一个 AI 助手"，而是个人 AI 时代的「操作系统底座」— 一个长期运行在你机器上、掌控全部状态的控制面。

它独占「本地 × 个人」象限：云端助手（Claude.ai / ChatGPT）的数据归平台，本地模型（Ollama）只做推理、不接管通道与记忆，Slack + Bot 则是企业云端、记忆互不相通。OpenClaw 把对话、决策、执行、跨设备四件事收进同一个进程——一个 Gateway（端口 18789）、一份记忆、一套策略，跨设备一致。

思考笔记

它的产品定位来自一句反问：如果 AI 助手的所有权不属于你，那它记住的每一件事都不算你的。

  • 三原则不是营销话术——它们是 技术约束，会直接出现在代码结构里（见 1.8 三原则详解）
  • "单一可信网关"看起来反直觉（单点故障？）— 实际上它换来的是 简化到极致的信任模型，而不是性能瓶颈（异步 I/O + 队列 + 副本扩展）

1.2 概览的三个原则

原则 含义
可信的网关单进程长期运行，掌控所有密钥 · 会话 · 通道连接 · 策略执行。所有数据流过同一个控制面——信任边界因此只有一个，不需要信任模型矩阵。
不可信的执行LLM 推理 · 工具执行 · 文件访问都运行在网关的隔离边界之外。网关可信但不担保执行——提示注入最多影响沙箱里的这一次运行。
确定性的策略策略以声明式配置集中管理，不散落在各个执行上下文里。改一条规则不需要读代码，配置文件 + 钩子就够。

1.4 生态定位

一句话定义：OpenClaw 是一个跨平台、个人优先的 AI 助手框架，通过单一可信网关连接模型、工具、消息通道和伴生应用。

理解一个产品最快的方式是看它不做什么。OpenClaw 把自己定位为 "Your assistant, on your devices, in your chats"——它填补的是一个具体象限:"个人使用 + 长期在线 + 本地优先 + 多通道连接"。下面用两个维度（谁使用、跑在哪）把它放进生态地图：

1.4.2 Hub-and-Spoke 架构

架构图分三层：外部触点（消息通道 + 伴生节点） → 单一 Gateway 控制面 → 本地优先存储。每个圆角矩形是一个进程，每条箭头是一次数据流。Gateway 是唯一可信方——外部不暴露任何内部状态，只通过反向连接（伴生节点）和受控协议（通道 Webhook）接入。

思考笔记

"本地 × 个人"象限的本质——把控制权从平台交还给用户。

  • 归一化：所有通道（Webhook / WebSocket / Polling）都被适配器翻译成同一种数据——Envelope 统一信封
  • 单点可信：Hub 是唯一可信方——API Key、OAuth Token、会话状态、策略规则全部内部化，外部只暴露 1 个 18789 端口
  • 无状态 Spoke：伴生节点不存数据，只是 UI 渲染层——挂掉就重连，数据零丢失

1.6 多通道架构

现代人的对话分散在 5-10 个 IM 应用中——微信、WhatsApp、邮件、Telegram、Discord... 但 AI 助手只能接其中一个，你被迫"绑定生态"。OpenClaw 的解法是通道适配器（Channel Adapter）：把不同平台的输入归一化为统一信封 Envelope。Gateway 不关心消息来自哪里，只看到「消息 + 发送者 + 会话」三要素——接入一个新通道只需写一个适配器，核心逻辑零侵入。

1.7.1 它不是什么

  • 不是云端 SaaS——OpenClaw 强调本地优先，数据归用户所有
  • 不是模型提供商——OpenClaw 是协调层，自己不训练/部署 LLM
  • 不是低代码平台——配置文件 + 插件代码，不是可视化拖拽
  • 不是团队协作工具——单一用户长期在线，不是 Slack 替代品

思考笔记

"不是什么"往往比"是什么"更能定义产品边界——因为差异化竞争永远在负面空间。

  • OpenClaw 不做云端——因为云端 AI 助手已经 被大厂垄断（Anthropic、OpenAI、Google），后入局者没有赢面
  • OpenClaw 不做模型训练——因为 LLM 训练是 千亿美金级的资本游戏，开源社区无法竞争
  • OpenClaw 不做团队协作——因为 Slack / Teams / 飞书 已经形成网络效应，后入局者没有迁移动力

这三条"不做什么"是产品定位的关键——把战场从红海拉到蓝海。

1.8 三原则详解

三原则不是营销话术——是经过实战权衡后选定的"约束条件"。任何一个看似"理所当然"的设计背后，都有无数被放弃的备选方案。本节用 3 段逐条拆解：每条原则"在解决什么问题"、"用何种方式解决"、"在代码哪个位置实现"。

1.8.1 原则一 · 可信的网关

核心：单进程长期运行，掌控所有密钥 · 会话 · 通道连接 · 策略执行。

为什么：把"信任边界"压缩到 1 个进程。所有需要保密的（API Key、OAuth Token、用户偏好、会话状态）都在 Gateway 内部，外部只暴露一个 18789 端口——即使被攻破，攻击者也只能从这一个入口进入。

代码位置:apps/gateway/src/index.ts（主入口） + apps/gateway/src/gateway/（子模块）。

1.8.2 原则二 · 不可信的执行

核心：LLM 推理 · 工具执行 · 文件访问都运行在网关隔离之外。

为什么：LLM 提示词注入（prompt injection）和工具参数污染是已知攻击面。把"执行"放到隔离沙箱，即使被攻击，影响范围限定在沙箱内——不会波及其他会话或本地文件。

代码位置:apps/gateway/src/tools/sandbox/（4 种沙箱：none/process/container/vm）。

1.8.3 原则三 · 确定性的策略

核心：策略以声明式配置管理，不分散在各个执行上下文里。

为什么：策略（谁能用什么工具、能否访问哪些路径、Token 限额）应该可审计、可回滚、可版本化——"1 行配置 = 1 条策略"的清晰性，胜过"代码里灵活散落"的便利。

代码位置:openclaw.config.yaml + apps/gateway/src/config/（加载/校验/热重载）。

1.8.4 三原则的相互制衡

三原则不是孤立的——它们之间有张力，需要平衡。下面的表格展示了"每个原则最可能被攻击的弱点"以及"OpenClaw 的应对方案"：

原则可能冲突OpenClaw 的取舍
可信网关性能——1 个进程 = 1 个瓶颈异步 I/O + 队列吸收峰值，横向扩展 Gateway 副本
不可信执行延迟——沙箱启动开销4 档沙箱（none→process→container→vm），按需选档
确定性策略灵活性——配置改动要重启配置热重载（watcher.ts），无需重启

1.8.5 三原则失守的反面案例

  • 失守"可信网关"：把多个 Gateway 进程共享 Token 存储——一旦某个进程被攻击，Token 全军覆没
  • 失守"不可信执行"：在 Gateway 进程内直接执行 shell 命令——提示词注入 = 服务器沦陷
  • 失守"确定性策略"：把权限检查散落在每个工具里——漏改一个 = 漏洞

思考笔记

三原则不是"理想"，是 "经过权衡后的最优"。每个原则都有代价，但 OpenClaw 选择"原则优先于性能"。

  • 把"信任"集中到 1 个进程看似反直觉——但换来的是 1 个攻击面而不是 N 个
  • 把"执行"放到沙箱看似延迟更高——但换来的是 "即使被攻破也不会失守"的承诺
  • 把"策略"集中到配置文件看似不够灵活——但换来的是 "1 行配置 = 1 条策略"的审计能力

用性能换安全，用灵活换可控——这是 OpenClaw 的核心价值主张。

技术栈选择 不是"最酷"，是"最适合"。

  • Node.js 20 而不是 Rust/Go——因为 OpenClaw 主要是 IO 密集型，Node 异步事件循环反而更合适

  • 不直接支持 MCP 协议——需通过 extensions/mcp-bridge 桥接（实验性）
  • 不内置语音通道——Twilio / WebRTC 需第三方扩展
  • 不内置图像生成——DALL-E / Midjourney 需单独配置
  • 不直接支持实时协作——多用户同时编辑同一会话尚未实现

思考笔记

性能基线 是承诺，不是天花板。

  • TTFT P50 0.8s 在 Sonnet 4 上是 OpenAI/Anthropic 直连速度——OpenClaw Gateway 自身开销 小于 100ms
  • 1，200 msg/s 的吞吐量是 单进程实测——横向扩展 Gateway 副本可线性提升
  • 内存占用 1.4GB @ 100 并发会话——平均 14MB / 会话，对现代机器是 无感开销

已知限制（不直接支持 MCP / 语音 / 图像生成）是 有意为之——让社区通过扩展实现，而不是把它们硬塞进核心。

        4. 1.11.2 常见问题

        • OpenClaw 适合我吗？
          如果你是个人 / 小团队，想要本地优先的 AI 助手 + 跨通道接管对话——OpenClaw 是为你设计的。如果是云端协作 / 企业级 / 团队内多人共用同一 AI 记忆，Slack+AI Bot 或 ChatGPT Team 更合适。
        • 一定要装 Docker 吗？
          不一定。沙箱有 4 档：none / process / container / vm。none 沙箱无需 Docker，适合信任的工具（如只读 HTTP 调用）。container 沙箱需要 Docker，适合执行任意命令的工具。
        • 怎么和 OpenAI / Anthropic 收费？
          你需要自己申请 API Key，在 openclaw.config.yaml 配置。OpenClaw 不做中转，直接用各家 SDK。
        • 商业化怎么算？
          Apache 2.0 协议——商用、修改、私有部署都允许，只需保留版权声明。
        • 性能比不上云端？
          OpenClaw 是协调层，不参与 LLM 推理。TTFT 由你的 LLM Provider 决定——用 Sonnet 4 是 Sonnet 4 的速度，本地 Ollama 是本地速度。Gateway 自身开销 <； 100ms。
        • 怎么贡献代码？
          看仓库 CONTRIBUTING.md。最简单：写一个新扩展（通道 / 模型 / 工具）→ PR。最快路径：加一个新通道，见 模块 10 源码导览 1.12-13。

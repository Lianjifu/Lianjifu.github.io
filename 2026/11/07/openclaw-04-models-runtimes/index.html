第 4 章：模型抽象

LLM Provider 与 Runtime 适配

发表于2026-11-07 分类于OpenClaw 源码笔记

30+ LLM + 5 种 Runtime = 单一 LLM 抽象层——OpenClaw 把"模型训练"留给 OpenAI/Anthropic，自己做"协调层"。Provider 是 LLM 适配，Runtime 是 Agent 调度。本模块拆解两层的抽象、选型、故障转移。

思考维度 内容
引导思考 展开
它为什么存在
  • 30+ 提供商、5 种 Runtime、几十个模型 ID，每家的协议和故障行为都不一样
  • 把「模型训练」留给 OpenAI 与 Anthropic，OpenClaw 只做协调层
  • 不把两件事拆开，配置就会变成一堆互相牵连的开关
它解决什么问题
  • Provider 与 Model 是身份，Runtime 与 Harness 是执行方式——两者独立配置、自由组合
  • 同一个模型可以换不同 Runtime，同一个 Runtime 也可以换不同模型
  • 所有组合都能在 openclaw.json5 里声明，不必改代码
它在系统中的位置
  • L3 推理层的具体实现——定义模型如何被调用
  • 上游接适配器与路由层，下游接执行层与工具沙箱
  • 与模块 03 一起构成消息进入模型之前的最后一段
它如何工作
  • 四层抽象栈：Provider → Model → Runtime → Harness，每层都是独立可配置项
  • Provider 负责协议与鉴权，Model 负责上下文与能力，Runtime 负责调度，Harness 负责装配
  • 故障转移在 Provider 层实现：配额、限流、区域不可用各有回退路径

4.1 一句话定位

本章要点

Provider/Model 是身份，Runtime/Harness 是执行方式。

OpenClaw 让你把这两件事独立配置、组合使用——同一模型可换不同 Runtime，同一 Runtime 可换不同模型，所有组合都能在 openclaw.json5 里声明。
指标 规模 代表
层抽象4Provider·Model·Runtime·Harness
种 Runtime5Single-shot·Loop·Streaming·Parallel·Hybrid
级模型选择4Agent→Channel→Workspace→Defaults
内置 Provider30+云·本地·企业·聚合
模型 ID200+Claude·GPT·Gemini·Qwen…
种 Harness5openclaw·codex·copilot·claude-cli·acp

4.2 推理层的三个原则

原则 含义
正交解耦——四层独立配置Provider / Model / Runtime / Harness 每一层都是独立配置项，任意组合都允许——不被任何单一厂商绑定。
5 种 Runtime——调用模式独立于模型同一模型可换不同 Runtime 调——Single-shot / Loop / Streaming / Parallel / Hybrid 适用不同场景。
4 级选择 + Fallback——声明式优先Agent → Channel → Workspace → Defaults 4 级查找，失败自动 fallback 到下一个候选，无需代码硬编码。

4.3 模块位置

4.4 四层抽象栈

4.5 四层详解

LAYER 1 · 提供者

4.5.1 Provider（提供者）

是什么：提供 LLM API 的厂商——Anthropic、OpenAI、Ollama、DeepSeek 等。

关心什么：API 协议、鉴权方式、配额限制、价格、地区限制。

不关心什么：具体哪个模型（那是 Model 层）。

代码位置:src/providers/[name]/（每个 Provider 一个目录，如 anthropic/、openai/、ollama/)

要点

类比

：Provider 像"快递公司"——UPS / FedEx / DHL。他们是送货的，但送什么包裹是另一回事。
LAYER 2 · 模型

4.5.2 Model（模型）

是什么：具体的模型 ID——claude-sonnet-4、gpt-4o、qwen2.5-72b。

关心什么：上下文窗口、最大输出、价格、能力评测、是否支持工具调用。

不关心什么：由谁提供（那是 Provider）。

代码位置:src/providers/[name]/models.ts（每个 Provider 目录下的模型清单）

要点

同 Provider 多 Model

：Anthropic Provider 提供 claude-opus-4 / claude-sonnet-4 / claude-haiku-4。OpenClaw 把它们都列在 Anthropic Provider 下，但每个都有独立的 context window、价格、benchmark 分数。
LAYER 3 · 运行时

4.5.3 Runtime（运行时）

是什么：调用 LLM 的执行模式——一次就够还是多轮循环？流式还是批量？

5 种 Runtime:

  • Single-shot——一次 LLM 调用就返回结果（翻译、摘要）
  • Loop——多轮 ReAct 循环（Agent 默认）
  • Streaming——边生成边返回（长文本）
  • Parallel——多任务并发（批量）
  • Hybrid——并行 + 流式组合（复杂任务，v2026.9.2 新增）

代码位置:src/runtimes/[type].ts

要点

Runtime 与 Model 正交

：同一个模型（比如 claude-sonnet-4）可以用 Single-shot 调一次，也可用 Loop 跑 Agent。Runtime 是调用模式，不是模型特性。
LAYER 4 · 执行后端

4.5.4 Harness（执行后端）

是什么：真正执行 Runtime 循环的进程——OpenClaw 自带一个，但也支持第三方 Harness。

5 种 Harness(v2026.9.2):

  • openclaw——自带，实现完整 Hooks / Policy / 工具白名单
  • codex——OpenAI 的官方 CLI（轻量，无完整 OpenClaw 治理）
  • copilot——GitHub Copilot CLI（IDE 集成友好）
  • claude-cli——Anthropic 官方 CLI（类似 codex）
  • acp——Agent Communication Protocol（标准化协议，可桥接其他系统）

代码位置:src/harness/[name].ts

要点

为什么需要 Harness 层

：有些场景你只想要一个简单的 LLM 调用器（比如 codex），不需要 OpenClaw 的全部治理能力。Harness 层让你按场景切换"执行后端"。

本章要点

学习要点

Provider 层概述

4.6 四层如何组合？

四层是正交的——任意组合都可以。

{
  agents: {
    research: {
      model: {
        provider: "anthropic",
        id: "claude-sonnet-4"
      },
      runtime: {
        type: "hybrid",       // 并行 + 流式
        parallelism: 4,
        stream: true
      },
      harness: "openclaw"     // 完整治理
    },
    quick_translate: {
      model: {
        provider: "ollama",
        id: "qwen2.5-7b"
      },
      runtime: {
        type: "single-shot"   // 一次性
      },
      harness: "codex"          // 轻量后端
    }
  }
}

要点

同一 Provider + Model 可用不同 Harness

:research 用 openclaw（完整治理）；quick_translate 用 codex（轻量）。模型一样（都 Anthropic），但执行后端不同。

4.7 四层对照

层回答的问题粒度变更频率
Provider谁提供 API？公司 / 产品线低（新增少）
Model哪个具体模型？模型 ID中（每月都有新）
Runtime怎么调？调用模式？5 种类型低（5 种已稳定）
Harness谁执行？后端进程低（5 种已稳定）

4.8 完整 4 层配置示例

{
  providers: {                                    // L1 · Provider
    anthropic: {
      apiKey: "${ANTHROPIC_API_KEY}",
      baseUrl: "https://api.anthropic.com"
    },
    ollama: {
      baseUrl: "http://localhost:11434"          // 本地模型
    }
  },

  runtimes: {                                       // L3 · Runtime
    default: { type: "loop", maxIterations: 10 },
    fast:    { type: "single-shot" }
  },

  harness: "openclaw",                            // L4 · Harness(全局默认)

  agents: {
    default: {
      model: "anthropic/claude-sonnet-4",          // L2 · Model
      runtime: "default",
      harness: "openclaw"
    },
    fast: {
      model: "ollama/qwen2.5-7b",                   // 用本地小模型
      runtime: "fast"
    }
  }
}

4.9 5 种 Runtime 一览

Single-shot一次调用就够
Loop多轮 ReAct
Streaming边生成边返回
Parallel多任务并发
Hybrid并行 + 流式
Runtime调用次数工具调用流式典型用例

4.10 5 种 Runtime 详解

RUNTIME 1 · 最简单

4.10.1 Single-shot（一次性）

一次 LLM 调用就返回结果——没有循环、没有工具调用。

适用场景

  • 翻译——输入一段文本，返回翻译
  • 摘要——输入长文，返回摘要
  • 分类——输入文本，返回分类标签
  • 简单问答——不需要外部信息

性能特征

延迟：~0.5-3s（单次 LLM 往返）
Token 开销：最小（无循环）
错误率：极低（简单调用）

配置示例

{
  agents: {
    translator: {
      runtime: {
        type: "single-shot",
        stream: false          // 一次性返回
      }
    }
  }
}
RUNTIME 2 · 默认

4.10.2 Loop（ReAct 循环）

多轮循环——LLM 思考 → 调用工具 → 观察结果 → 再思考 → 直到完成。这是 Agent 的默认模式。

适用场景

  • 工具调用密集的 Agent——文件操作、API 调用、数据库查询
  • 需要外部信息——RAG 检索、搜索
  • 多步推理——需要分步思考
  • 经典 ReAct — Thought → Action → Observation

性能特征

延迟：~5-60s（取决于轮数）
Token 开销：高（每轮都增加）
错误率：中（错误累积）

配置示例

{
  agents: {
    coder: {
      runtime: {
        type: "loop",
        maxIterations: 15,         // 最多 15 轮
        stream: true,                // 流式返回中间结果
        stopOnToolError: false       // 工具失败继续
      }
    }
  }
}
RUNTIME 3 · UX 优先

4.10.3 Streaming（流式生成）

单次调用，但边生成边返回——用户能看到文本逐字出现，无需等完整响应。

适用场景

  • 长文本生成——报告、文章、文档
  • UX 优先——用户希望快速看到响应
  • 聊天响应——让对话感觉更自然
  • 代码补全——逐字符出现的体验

性能特征

首 token 延迟（TTFT）：~200-800ms
总延迟：等同于非流式
UX 感受：极佳（立即看到内容）

配置示例

{
  agents: {
    writer: {
      runtime: {
        type: "streaming",
        chunkSize: 50,              // 每 50 字符推一次
        firstChunkTimeout: "5s"      // 首块超时
      }
    }
  }
}
RUNTIME 4 · 批量并发

4.10.4 Parallel（并行执行）

多个独立任务并发执行——每个任务是一个独立 LLM 调用，最终聚合成一个结果。

适用场景

  • 批量处理——100 封邮件分类、1000 条评论分析
  • 探索式任务——让 4 个不同视角同时回答
  • 投票/汇总——多次调用 + 共识
  • 独立子任务——没有依赖关系的并行

性能特征

吞吐量：极高（N 倍加速）
Token 开销：N × 单次
成本：高（并发 = 多计费）

配置示例

{
  agents: {
    classifier: {
      runtime: {
        type: "parallel",
        parallelism: 8,            // 8 个并发
        aggregation: "vote",        // 投票聚合
        consensusThreshold: 0.6   // 60% 共识
      }
    }
  }
}
RUNTIME 5 · v2026.9.2 新增

4.10.5 Hybrid（并行 + 流式）

Parallel + Streaming + Loop 的组合——并行多个子任务，每个子任务可流式返回，主任务协调它们。

适用场景

  • 代码评审——并行检查正确性、安全性、性能，边发现边报告
  • 文档对比——并行分析多个版本，流式输出差异
  • 多角度研究——并行探索多个角度，流式汇总
  • 复杂多步任务——既要并行又要协调

性能特征

复杂度：高（需协调）
适用性：复杂任务最佳
调试难度：较高（并发 + 流式）

配置示例

{
  agents: {
    code_reviewer: {
      runtime: {
        type: "hybrid",
        parallelism: 4,                // 4 个评审维度并行
        stream: true,                    // 流式报告发现
        maxIterations: 20,            // 主循环上限
        subTaskTimeout: "60s"
      }
    }
  }
}

4.11 Runtime 选择决策树

4.12 4 级选择流程

当用户问"用哪个模型"时，OpenClaw 有 4 层查找机制——越往后越通用，越靠前越精确。

4.13 4 级详解

LEVEL 1 · 最高优先级

4.13.1 Agent 级配置

适用：某个 Agent 必须用某个模型。

配置位置:openclaw.json5 → agents.[name].model

{
  agents: {
    research: {
      model: "anthropic/claude-sonnet-4"    // 固定 Sonnet
    },
    translator: {
      model: "ollama/qwen2.5-7b"          // 固定本地小模型
    }
  }
}

这是最高优先级——只要 Agent 级配了模型，后续的 Level 2/3/4 都被忽略。

要点

何时用

：Agent 性质决定了模型选择——比如 research 用 Sonnet（质量优先），translator 用本地 qwen2.5-7b（成本优先）。
LEVEL 2 · 通道覆盖

4.13.2 Channel（账号）级配置

适用：某个通道/账号的所有消息都用特定模型。

配置位置:channels.[name].accounts.[acc].model

{
  channels: {
    telegram: {
      accounts: {
        work: {
          model: "anthropic/claude-sonnet-4"   // 工作 bot 用 Sonnet
        },
        personal: {
          model: "ollama/qwen2.5-7b"          // 个人 bot 用本地小模型
        }
      }
    }
  }
}

回退触发：Agent 级未配置 → 使用 Channel 级。

要点

何时用

：不同身份用不同模型——工作 bot 必须高质量，个人 bot 优先成本。
LEVEL 3 · 工作区

4.13.3 Workspace 级配置

适用：某个工作目录的所有 Agent 都用同一模型。

配置位置：工作目录的 .openclaw/config.json5

{
  // /home/me/projects/secrets/.openclaw/config.json5
  model: "anthropic/claude-opus-4"      // 敏感项目强制用 Opus
}

Workspace 配置会覆盖用户根目录的默认，但被 Agent 级 / Channel 级覆盖。

要点

何时用

：项目级别的策略——比如金融项目强制用 Opus（质量优先），个人项目用 Sonnet（成本优先）。
LEVEL 4 · 兜底默认

4.13.4 全局默认

适用：其他所有级别都没配置。

配置位置:openclaw.json5 → defaults.model

{
  defaults: {
    model: "anthropic/claude-sonnet-4"     // 兜底
  }
}

如果没有配置 defaults.model，OpenClaw 会报错并拒绝启动（fail-closed）。

要点

必须配置 defaults

：OpenClaw 强制要求至少有一个 fallback——防止 Agent 误用随机模型。

4.14 auto 模式 · 让 OpenClaw 选

除了手动指定，你可以让 OpenClaw 自动选择最适合的模型：

{
  agents: {
    smart_router: {
      model: "auto"           // OpenClaw 自动选
    }
  },

  modelSelection: {
    mode: "auto",
    strategy: "cost-quality-balanced",
    candidates: [
      "anthropic/claude-sonnet-4",
      "openai/gpt-4o",
      "ollama/qwen2.5-72b"          // 本地兜底
    ],
    preferLocal: true           // 优先用本地模型
  }
}

auto 模式下，OpenClaw 根据任务复杂度、用户偏好、配额限制动态选择。

4.15 Fallback · 模型故障切换

如果首选模型调用失败（限流、断网、错误），OpenClaw 自动切换到下一个候选：

{
  agents: {
    resilient: {
      model: {
        primary: "anthropic/claude-sonnet-4",
        fallback: [
          "openai/gpt-4o",
          "ollama/qwen2.5-72b"          // 最后兜底:本地模型
        ],
        retryPolicy: {
          maxRetries: 2,
          retryDelay: "1s",
          retryOn: ["rate_limit", "timeout", "network_error"]
        }
      }
    }
  }
}

要点

本地模型作为最终兜底

：把 ollama/qwen2.5-72b 放在 fallback 链尾，确保云服务完全不可用时仍能工作。

4.15.1 模型故障转移

本章要点

学习要点

  • 模型故障转移的两阶段处理分别做什么？失败后如何逐级降级？
  • Profile 轮换的优先顺序是什么？冷却（Cooldown）的指数退避如何工作？
  • 账单禁用（Billing Disable）的退避策略和普通冷却有什么不同？
  • Fallback 模型切换的适用场景和不适用场景分别是什么？

两阶段故障处理

模型故障转移是 OpenClaw 的韧性保障，确保单模型失败不会导致整个系统不可用。

阶段处理内容失败处理
阶段一主模型内的 Profile 轮换（如多个 API Key）Profile 1 → Profile 2 → Profile 3
阶段二跨模型 Fallback 切换fallback 1 → fallback 2 → 所有失败

Profile 轮换顺序

当主模型配置了多个认证 Profile 时，按以下优先级轮换：

凭证类型

// API Key 类型
{ type: "api_key", provider: "anthropic", key: "sk-ant-..." }

// OAuth 类型
{ type: "oauth", provider: "google-antigravity", access: "...", refresh: "...", expires: 123, email: "user@gmail.com" }

Profile ID 格式

类型格式示例
默认provider:defaultanthropic:default
OAuthprovider:{email}google-antigravity:user@gmail.com

冷却机制（Cooldown）

当 Profile 由于认证/速率限制错误失败时，OpenClaw 将其标记为冷却并移到下一个 Profile：

冷却状态存储

{
  usageStats: {
    "anthropic:default": {
      lastUsed: 1736160000000,
      cooldownUntil: 1736160600000,  // 冷却到期时间
      errorCount: 2,                  // 连续错误次数
    },
  },
}

账单禁用（Billing Disable）

当遇到 "insufficient credits" 等账单/额度失败时，使用更长退避，不适用短冷却：

字段默认值
账单退避起点5 小时
翻倍每次账单失败翻倍
上限24 小时
计数器重置24 小时未失败

模型回退（Model Fallback）

如果提供商的所有 Profile 都失败，OpenClaw 移到 `agents.defaults.model.fallbacks` 中的下一个模型。

适用场景不适用场景
认证失败（所有 Profile 均失败）非认证类错误
速率限制（所有 Profile 均触发）
耗尽 Profile 轮换后的超时

当运行以模型覆盖（钩子或 CLI）启动时，回退在尝试所有 fallback 后，最终回退到 `agents.defaults.model.primary`。

配置

{
  agents: {
    defaults: {
      model: {
        primary: "anthropic/claude-sonnet-4-5",   // 主模型
        fallbacks: ["openai/gpt-5.2"],              // 回退列表
      },
    },
  },
}

完整配置示例

{
  auth: {
    profiles: { "...": "..." },
    order: { anthropic: ["anthropic:default"] },
    cooldowns: {
      billingBackoffHours: 5,
      billingMaxHours: 24,
      failureWindowHours: 24,
    },
  },
  agents: {
    defaults: {
      model: {
        primary: "anthropic/claude-sonnet-4-5",
        fallbacks: ["openai/gpt-5.2"],
      },
    },
  },
}

4.15.2 认证管理

本章要点

学习要点

  • OpenClaw 的认证凭证存在哪里？支持哪两种凭证类型？
  • Profile 轮换的优先级顺序是怎样的？
  • 如何通过环境变量注入 API Key？配置热重载如何影响认证变更？

认证体系

OpenClaw 的认证管理负责所有 Provider 的 API Key、OAuth Token 等凭证的存储、轮换和故障恢复。

凭证存储

存储路径

类型路径说明
主配置~/.openclaw/openclaw.jsonauth.profiles 和 auth.order 配置（不含密钥明文）
凭据文件~/.openclaw/agents/{agentId}/agent/auth-profiles.json实际凭证存储，含密钥
旧版兼容~/.openclaw/agent/auth-profiles.json旧版本使用的路径

凭证类型

// API Key 类型
{
  type: "api_key",
  provider: "anthropic",
  key: "sk-ant-...",
}

// OAuth 类型
{
  type: "oauth",
  provider: "google-antigravity",
  access: "ya29...",
  refresh: "1//...",
  expires: 1736160000000,
  email: "user@gmail.com",
}
类型适用 Provider自动刷新
api_keyAnthropic, OpenAI, Ollama, Gemini需手动更新
oauthGitHub Copilot, Google, Azure自动刷新 Token

Profile 轮换顺序

当 Provider 配置了多个认证 Profile 时，按以下优先级依次尝试：

Profile ID 格式

类型格式示例
默认{provider}:defaultanthropic:default
OAuth{provider}:{email}google-antigravity:user@gmail.com

环境变量注入

推荐将敏感凭证通过环境变量注入，避免明文存储在配置文件中：

{
  models: {
    providers: {
      anthropic: { apiKey: "${ANTHROPIC_API_KEY}" },
      openai: { apiKey: "${OPENAI_API_KEY}" },
    },
  },
}
# .env 文件（自动加载）
ANTHROPIC_API_KEY=sk-ant-...
OPENAI_API_KEY=sk-proj-...
GEMINI_API_KEY=AIza...

替换规则

语法行为
${VAR}替换为环境变量值，未设置时报错
${VAR:-default}未设置时使用默认值
$${VAR}转义为字面量 $VAR

认证与配置热重载

认证配置变更通过 Gateway 的热重载机制动态生效：

变更类型是否热生效说明
新增 API Key是新 Profile 立即可用
修改 auth.order是轮换顺序即时调整
OAuth Token 自动刷新是后台静默更新
新增 Provider需要重启Provider 适配器需重新加载

关键源码文件

文件作用
src/gateway/auth.ts连接认证 Token 验证
src/gateway/auth-rate-limit.ts认证速率限制
src/gateway/auth-mode-policy.ts鉴权策略决议
src/gateway/auth-surface-resolution.ts鉴权作用域解析
src/agents/model-fallback.ts认证失败后的回退逻辑

4.20 自定义 · 任何 OpenAI 兼容 API

几乎所有 LLM 都提供 OpenAI 兼容 API（改 baseUrl 即可）。OpenClaw 用 custom Provider 一键接入：

{
  providers: {
    my-llm: {                                    // 任意名字
      type: "custom",
      protocol: "openai-compatible",
      baseUrl: "https://api.example-llm.com/v1",
      apiKey: "${MY_LLM_API_KEY}",
      defaultModel: "my-llm-large"
    }
  }
}

要点

协议兼容列表

:openai-compatible（绝大多数）、anthropic-compatible（部分）、custom-http（完全自定义，需要写 JSON Schema 转换）。

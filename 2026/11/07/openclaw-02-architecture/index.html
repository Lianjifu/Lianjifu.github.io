2.1.2 核心架构的三个原则

思考笔记

原则 → 代码的映射不是一一对应：原则一是"设计约束"，体现在 Gateway 整个进程，而非某个文件。看到多个文件共同服务同一条原则，这是健康的架构。

第一段讲了"为什么"（三原则），第二段将讲"是什么"（四层架构）。这一节作为桥梁——把每条原则映射到具体代码位置，让抽象原则可见可寻。

三原则（见 模块 01 1.1.2 概览的三个原则）不是抽象口号——每条原则都对应到 apps/gateway/src/ 的具体子模块。

原则一 · 可信的网关 → gateway/ 子模块

核心：单进程长期运行，掌控所有密钥 · 会话 · 通道连接 · 策略执行。

代码位置:apps/gateway/src/gateway/

  • server.ts——WebSocket + HTTP 入口（端口 18789）
  • router.ts——JSON-RPC 路由（请求分发）
  • queue.ts——命令队列（顺序/并发/收集三种模式）
  • envelope.ts——Envelope 类型定义（标准化消息）
  • schema-validator.ts——JSON Schema 校验

原则二 · 不可信的执行 → tools/sandbox/ 子模块

核心：LLM 推理 · 工具执行 · 文件访问都运行在网关隔离之外。

代码位置:apps/gateway/src/tools/sandbox/

沙箱隔离强度性能适用场景
none无最快只读 HTTP / 内部工具
process进程级快可信子进程
container容器级中等需要文件系统隔离
vmVM 级最慢不可信代码（最大隔离）

原则三 · 确定性的策略 → config/ 子模块

核心：策略以声明式配置管理，不分散在各个执行上下文里。

代码位置:apps/gateway/src/config/

  • loader.ts——加载 openclaw.config.yaml
  • schema.ts——配置 Schema（Zod 校验）
  • watcher.ts——文件变更监听 → 热重载（无需重启）

三原则的相互约束

三原则不是孤立的——它们之间有张力，需要平衡：

  • 可信网关 vs 不可信执行——Gateway 掌握所有密钥，但又不能信任 LLM 推理——通过"Gateway 签名 / 执行隔离"分离
  • 不可信执行 vs 确定性策略——沙箱行为可能因环境差异而不同——通过"配置化沙箱选择"约束
  • 确定性策略 vs 可信网关——配置改动不能重启 Gateway（破坏可信性）——通过"热重载"解决

2.2 四层与运行

第二段 · 四层与运行OpenClaw 的骨架：L1–L4 四层如何切分职责，一条消息又如何在这四层之间流动。

2.2.1 四层架构

本章要点

学习要点

  • OpenClaw 的整体架构分几层？每层的核心组件和职责是什么？
  • 智能体 5 层状态机如何驱动消息从入站到回复的完整转化？
  • Gateway 为什么是"控制平面"和"单一事实来源"？
  • 新手最容易忽略哪三条规则？

思考笔记

四层架构不是微服务——都在同一个 Gateway 进程内，层间是函数调用（不是网络请求）。这意味着延迟低、调试简单、但单点容量受限——横向扩展是必要的。

四层架构是 OpenClaw 的"骨架"——每层职责单一，层间接口清晰。本节用 L1-L4 标注层次，让你能在脑中画出完整的运行时结构。

OpenClaw 把所有职责切成 4 层——从外到内，每层只与相邻层交互，层间接口稳定。

L1 · 接入层 （Access Layer）

职责：把外部消息平台的 webhook 归一化为内部 Envelope。

关键文件:

  • apps/gateway/src/gateway/server.ts——WebSocket + HTTP 服务器
  • apps/gateway/src/gateway/router.ts——JSON-RPC 路由
  • apps/gateway/src/gateway/envelope.ts——Envelope 类型定义
  • apps/gateway/src/channels/registry.ts——通道插件注册表

接口契约: Envelope = { id, channel, account, peer, content, timestamp, metadata? }

L2 · 编排层 （Orchestration Layer）

职责：Agent 循环 + Prompt 组装 + 会话管理。

关键文件:

  • apps/gateway/src/agents/runner.ts — Agent.run() 主入口
  • apps/gateway/src/agents/prompt-builder.ts——8 层 Prompt 组装
  • apps/gateway/src/agents/loop-controller.ts——最大工具轮次 + 提前结束
  • apps/gateway/src/session/manager.ts——会话管理

接口契约: AgentInput = { sessionId, userMessage, attachments? } → AgentOutput = { text, toolCalls?, stopReason }

L3 · 推理层 （Inference Layer）

职责：调用 LLM + 执行工具（在沙箱中）。

关键文件:

  • apps/gateway/src/agents/provider.ts——LLM Provider 接口
  • apps/gateway/src/tools/executor.ts——工具执行器
  • apps/gateway/src/tools/sandbox/——4 种沙箱实现
  • apps/gateway/src/hooks/chain.ts——钩子链

接口契约: ToolCall = { id, name, arguments } → ToolResult = { success, output, error? }

L4 · 持久层 （Persistence Layer）

职责：会话状态 + 长期记忆 + 配置存储。

关键文件:

  • apps/gateway/src/session/storage.ts——SQLite 存储
  • apps/gateway/src/session/compaction.ts——上下文压缩
  • apps/gateway/src/session/memory.ts——Markdown 记忆

接口契约: Session = { id, messages, metadata, lastActive }

为什么是 4 层而不是 3 层或 5 层？

4 层是经验总结——经过 3 年迭代才稳定。

  • 3 层不够：把 LLM 和工具合一层会让"沙箱边界"模糊
  • 5 层太多：加"中间件层 / 队列层"会增加跳跃成本
  • 4 层正好：每层职责单一、层间接口稳定、可独立测试

分层架构全景

从一句话定义开始，逐层展开 OpenClaw 的运行时骨架——从最外层用户交互，到 Gateway 控制平面，再到 AI Agent 执行引擎，最后到持久化层。看完这一节，你能在脑中画出完整的运行时架构图，并理解每层的边界和接口。

一句话版
OpenClaw = 一个自托管 Gateway 网关 + 一个 AI Agent + 很多通道、插件和节点
  • 自托管：运行在自己的电脑或服务器上，配置、会话、记忆默认都在本机
  • 核心设计问题：OpenClaw 的智能体为什么"能长期跑"，而不是只在 demo 里跑一次？

答案在于多层架构的韧性设计——会话持久化、队列并发控制、状态机容错、模型故障转移。每一层都有独立的容错和重试逻辑，单点故障不会导致整个 Agent 卡死。

Agent Loop 概述

智能体循环（Agent Loop）是将一条消息转化为操作和最终回复的权威路径。一次循环是每个会话的单次串行运行。

Agent Loop 的核心思想：不是一次 `model.generate（）` 就结束，而是多层状态机协同工作——队列控制（session lane → global lane）→ 执行（attempt）→ 事件稳定化（subscribe）→ 压缩等待（wait compaction）→ 收尾（finalize）→ 出错时自动恢复（profile 轮换 → compact → fallback）。

子模块之间怎么通信？

子模块之间通过函数调用（同步） + 事件总线（异步） 两种方式通信：

  • 函数调用——L2 调用 L3 的 agent.run(input)，L3 调用 L2 的 session.append(event)
  • 事件总线——钩子系统 （api.on(event, handler)） 用于跨模块的"广播"

不推荐：直接 import 另一个子模块的内部函数——通过它们暴露的接口。

2.4 信任与安全

第四段 · 信任与安全把「可信 / 不可信 / 隔离」从原则展开成三级可识别的边界，再对照真实威胁场景。

2.4.1 三级信任模型

思考笔记

三级信任模型的关键不是"信任"本身，而是"边界"——你在哪条边界上，决定你能调什么 API、读什么数据。开发者最常犯的错是"忘记自己处于哪条边界"。

思考笔记

三级信任模型的关键不是"信任"本身，而是"边界"——你在哪条边界上，决定你能调什么 API、读什么数据。开发者最常犯的错是"忘记自己处于哪条边界"。

三原则是"为什么这样设计"，三级信任是"具体落地为安全边界"。这一节把"可信 / 不可信 / 隔离"原则展开为 3 层可识别的边界。

OpenClaw 假设 没有任何输入是可信的——所有外部消息都需校验。信任分 3 级，影响不同行为。

Level 1 · 可信 （TRUSTED）

谁：Gateway 自身的代码 + 配置 + 密钥存储。

特征:

  • 掌握所有 API Key、OAuth Token、用户偏好
  • 执行配置中声明的策略（谁用什么工具、限额多少）
  • 不依赖任何外部输入做"关键决策"

代码位置:apps/gateway/src/ 全部子目录。

Level 2 · 半可信 （SEMI-TRUSTED）

谁:extensions/ 下的所有插件（通道、模型、工具）。

特征:

  • 通过 package.json + openclaw.config.yaml 显式启用
  • 运行在 extensions/ 子目录，不直接访问 Gateway 内部状态
  • 可以读配置 + 调用 L2 接口，但不能绕过沙箱

代码位置:extensions/<name>/ 下的所有 .ts 文件。

Level 3 · 不可信 （UNTRUSTED）

谁:

  • 外部消息——WhatsApp / Telegram / Slack 发来的所有内容
  • LLM 输出——所有 LLM 返回的文本、工具调用参数
  • 工具结果——第三方 API 返回的数据

特征:

  • 所有内容在 Gateway 处理前都要校验（Schema + Zod）
  • LLM 输出绝不直接执行，必须经过钩子链
  • 工具结果在用作下一轮 LLM 输入前，要做大小截断 + 内容过滤

4 层鉴权

ACPX Harness 权限

ACPX 会话通常是非交互式的（如 CI/CD 环境），不能点 TTY 权限弹窗，因此需要预先配置处理策略。

权限模式
参数值含义适用场景
permissionModeapprove-reads 只自动批准读取操作代码审查、静态分析
permissionModeapprove-all自动批准写入和 shell 命令完全信任的自动化环境
permissionModedeny-all拒绝所有权限请求高安全环境
nonInteractivePermissionsfail 遇到需要用户交互时直接失败及早发现问题
nonInteractivePermissionsdeny拒绝提示并尽量继续执行容忍部分失败
配置示例
openclaw config set plugins.entries.acpx.config.permissionMode approve-reads
openclaw config set plugins.entries.acpx.config.nonInteractivePermissions fail
openclaw gateway restart

重要：ACPX 权限不会放宽 host exec 审批；host exec 审批也不会放宽 ACPX Harness 提示。两者独立检查。

2.5 总结

收束 · 本章结论把三层结构收成几句可以带走的结论，并交代下一章的接口。

2.5.1 一句话总结

思考笔记

三原则（可信网关 · 不可信执行 · 确定性策略） → 四层（L1-L4） → Gateway 7 子模块 → 三级信任（TRUSTED / SEMI-TRUSTED / UNTRUSTED）。



看完本模块，你能把任意 OpenClaw 行为定位到具体的子目录 + 具体的接口契约。

2.5.2 本章结论

  1. 三原则是「为什么」，四层是「是什么」，子模块与契约是「在哪里」。三层缺一不可：只讲原则无法验证，只讲分层不知道边界在哪。
  2. 每层只与相邻层交互。层间接口稳定，意味着可以在任意一层上做替换或扩展，而不必推倒重来。
  3. Gateway 是唯一可信方。通道、模型、会话、工具、策略都从它进，也从它出——信任边界因此只有一个，不需要信任模型矩阵。
  4. 模块之间只需要对齐 5 条契约。Envelope、ToolCall、RpcRequest、Outbound、Provider：接一个新模块，先看它落在哪条契约上。
  5. 三级信任把原则落成可识别的边界。越往里权限越大，越往外越不可信；排查越权问题先定级别，再看这条数据流经过了哪几级。

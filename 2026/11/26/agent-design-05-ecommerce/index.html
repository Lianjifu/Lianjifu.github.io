第 5 章：电商 Agent

电商 Agent——导购、交易与售后的受控编排

发表于2026-11-26 分类于AI Agent 系统设计

电商 AI Agent 理解用户或商家意图，调用商品、交易、履约、售后、经营分析与增长五类领域的工具，执行受控动作并对结果负责。它和前面几章的差别在方向：客服与问答是响应式的，用户先来；营销是主动式的但只打扰不扣钱；电商是「既主动又要动钱」的——它推荐的每一件商品都要能被下单，它发起的每一笔退款都要扣真实的钱。难点不在生成推荐理由，而在「资金不能错、库存不能错、状态不能乱、承诺要兑现」。本章围绕智能导购、订单履约与售后、经营问数与增长，以及幂等与降级矩阵展开。

引导思考 展开
它为什么存在

  • 客服错了用户还能再问一次，电商错了是重复退款与超卖
  • 所以电商的第一性问题不是「怎么推荐得更准」，而是「哪些决定根本不能交给模型」

  • 电商 Agent 把一句自然语言变成一次有副作用的交易动作
  • 「耳机降了 80 能价保吗，那单面霜我要退」要变成查单、算钱、审批、扣款

它在系统中的位置
  • 它站在用户与交易系统之间，两头都要压住
  • 一头是「别推荐买不到的东西」，另一头是「别退错钱、别多退钱」

  • 下单的顺序比模型更决定成败
  • 只读并行、校验居中、写入串行，写超时先查单再决定重试

5.1 电商 Agent 是什么

第一段 · 电商 Agent 是什么这一段回答：电商 Agent 究竟是什么、给谁用、边界划在哪里，以及哪些指标是硬约束而不是目标值。

5.1.1 定义与四类核心场景

本章要点

电商 AI Agent 是在商品、交易、履约、售后、经营分析与增长场景中，理解用户或商家意图、调用领域工具、执行受控动作、对结果负责的智能体系统——它不只「会推荐」，还要「能查、能改、能退、能赔、能算」。四类核心场景各带一套风险与护栏：智能导购的风险是推荐无货与券后价算错，靠实时双校验加结构化槽位；订单售后是重复退款与超额赔付，靠状态机加幂等加审批；经营问数是口径错、越权与慢查询，靠 AST 白名单加行权限加 LIMIT；增长召回是打扰、超发与归因虚高，靠状态复核加 Lua 原子频控加 Holdout。

思考笔记

四类场景的护栏并排看就能看出电商的分工：导购错的是「承诺」，售后错的是「钱」，问数错的是「口径」，增长错的是「打扰」。但把四类串成一条系统的其实是「实时性」——导购、售后、增长都要求价格、库存、订单状态实时，只有问数允许缓存。所以电商架构的复杂度几乎全部集中在实时查询与写路径上，而不是模型能力上。

定义：电商 AI Agent 是在商品、交易、履约、售后、经营分析与增长场景中，理解用户或商家意图、调用领域工具、执行受控动作、对结果负责的智能体系统。它不仅「会推荐」，还要「能查、能改、能退、能赔、能算」。

四类核心场景：

5.1.2 典型用户与通用问答的差别

本章要点

四类用户是消费者、商家、客服与运营，诉求分别是找商品查订单退换货、经营分析与活动配置、处理售后与纠纷、增长召回与触达。与通用问答 Agent 的差别有六条：通用问答基本无副作用，电商涉及资金、库存与订单状态；通用问答的状态只在会话内，电商是强业务状态机；通用问答「答案合理即可」，电商的金额、库存与归属必须精确；通用问答通常没有多租户，电商要做商家、店铺、部门三级隔离；通用问答的结果可缓存，价格、库存、订单不可；通用问答的审计算「一般」，电商要全链路资金审计。

思考笔记

这张表里最容易被低估的是「多租户」那一行。多租户不是一个权限开关，而是一整套隔离：工具按租户授权、数据按租户过滤、审计按租户留痕、缓存键按租户分段。任何一环漏掉，隔壁店铺就能看到别人的订单。这类缺陷在功能测试里几乎不会出现，只在真实多租户环境里显形，所以它必须写进工具契约，而不是上线后再补。

5.1.3 系统边界、核心指标与 SLO

本章要点

范围内是意图理解与多轮对话、商品检索与实时校验、订单与售后工具编排、退款金额计算、经营问数与增长触达；范围外是商品主数据生产、搜索索引底层、支付渠道、财务结算、数仓建模与渠道网关。核心指标分任务、工具、性能、业务、安全五类。SLO 里有两条是硬约束而不是目标值：重复退款 0、错误写操作 0，另有审计覆盖率 100%；延迟目标分别是导购首响 P95 小于 2 秒、查单 P95 小于 500 毫秒、写操作 P99 小于 2 秒。

思考笔记

「重复退款 0」被写成硬约束而不是「低于 0.01%」是一个刻意的选择：这类错误的分母是订单数，一个几乎不发生的事件只要落在错的那几单上就是百分之百资损与客诉。把这类指标写成比率，等于给了一个可以「慢慢改善」的错觉——真正该盯的是绝对数。

5.2 核心矛盾与设计原则

第二段 · 核心矛盾这一段回答：概率性的推荐与确定性的交易之间冲突在哪里，以及四类正确性分别该怎么保。

5.2.1 本质与四大挑战

本章要点

本质矛盾是「推荐与生成的概率性」与「交易与资金的确定性」之间的冲突——模型可以猜用户想要什么，但不能猜退款金额。四大挑战按原文保留：高并发交易状态的一致性与幂等，重复点击、超时重试与消息重投都可能触发重复退款或重复下单；资金与库存操作的原子性与可回滚，退款、赔付、发券与改地址必须要么全成，要么可补偿；多轮工具调用下的上下文与依赖治理，读操作可以并行，写操作必须按依赖串行且不能丢约束；转化率与用户体验、合规底线的平衡，推荐要准、触达要克制、承诺要可兑现。

思考笔记

「模型可以猜用户想要什么，但不能猜退款金额」是全章最该记住的一句话，它同时给出了模型的权限边界：凡是能算准的事就交给规则引擎，凡是能有标准答案的事就不交给模型。反过来说，模型该负责的是「把模糊需求变成结构化槽位」与「把可行结果组织成有说服力的解释」，这两件事恰好没有唯一正确答案。

本质：电商 Agent 的核心矛盾，是「推荐/生成的概率性」与「交易/资金的确定性」之间的冲突。模型可以猜用户想要什么，但不能猜退款金额。

四大挑战（原文保留）：

  1. 高并发交易状态的一致性与幂等：重复点击、超时重试、消息重投都可能触发重复退款或重复下单。
  2. 资金与库存操作的原子性与可回滚：退款、赔付、发券、改地址必须要么全成，要么可补偿。
  3. 多轮工具调用下的上下文与依赖治理：读操作可以并行，写操作必须按依赖串行，且不能丢约束。
  4. 转化率与用户体验/合规底线的平衡：推荐要准、触达要克制、承诺要可兑现。

5.2.2 三个放大器与八组关键矛盾

本章要点

三个放大器决定了错误的代价形态：资金放大，一次错退或超赔乘以用户量，直接资损且对账困难；库存放大，推荐无货与超卖承诺，最终变成下单失败、投诉与赔付；口碑放大，错误推荐与承诺不兑现，表现为信任下降与留存流失。八组关键矛盾各自配了默认策略与反转条件，比如「推荐转化 vs 可信」默认相关性加可得性优先，只有广告位可以显式标注时才反转；「自动化 vs 资金安全」默认阈值加审批，低金额才可全自动；「并行效率 vs 依赖正确」默认用 DAG 或 Wave 串行，无依赖时才并行；「快速响应 vs 完整校验」默认关键状态必查，只读场景可缓存。

思考笔记

八组矛盾里最值得单挑的是「快速响应 vs 完整校验」：它把响应速度与正确性从对立变成了分层——先问这次调用要不要改状态，要改就必须查准，不要改就可以缓存。少了这层区分，团队要么为了快牺牲正确性，要么为了对牺牲体验，最后往往是用「体验」的名义把正确性让掉。

三个放大器：

放大器说明后果
资金放大一次错退/超赔乘以用户量直接资损、对账困难
库存放大推荐无货、超卖承诺下单失败、投诉、赔付
口碑放大错误推荐、承诺不兑现信任下降、留存流失

5.2.3 四类正确性与八类失败模式

本章要点

电商的四类正确性必须分开保证：商品事实靠实时接口加时间戳，交易状态靠状态机加先查后写，资金金额靠统一口径加规则引擎，权限归属靠身份校验加资源级鉴权。八类失败模式各有根因与防线：推荐无货因为只查索引不查实时，防线是实时双校验；券后价错因为券规则复杂，以营销引擎为准；重复退款因为重试或并发，靠幂等加状态机；超额赔付因为口径不统一，靠统一规则加审批；改地址越权因为缺身份校验，靠实名加归属校验；状态错乱因为无锁无版本，靠订单级锁加版本；提示注入因为备注含指令，靠隔离加白名单；问数口径错因为无语义层，靠指标卡。

思考笔记

失败模式这张表里，「重复退款」与「超额赔付」经常被混为一谈，其实是两种不同的病：前者是幂等问题——同一笔意图被执行了两次；后者是口径问题——同一次退款算出了两个金额。治法完全不同，前者要加唯一约束与状态机，后者要统一规则引擎。搞混就会出现「加了幂等键但金额还是算错」的假修复。

四类正确性：

层次要求保障手段
商品事实价格、库存、参数、促销准确实时接口 + 时间戳
交易状态订单、退款、履约状态正确状态机 + 先查后写
资金金额实付、运费、分摊、补贴一致统一口径 + 规则引擎
权限归属本人/商家/租户不越权身份校验 + 资源级鉴权

5.2.4 五层设计原则、威胁模型与成本结构

本章要点

五层设计原则是全章骨架：快慢分离，高频封闭判断走轻量模型或规则，复杂规划才进 Agent；读实时、写幂等，价格库存与订单状态必须实时查，所有写工具带幂等键；模型提议、规则裁决、工具执行，模型不能直接改资金或库存；可补偿、可审计，每个写操作都有状态机、幂等键、补偿路径与操作日志；先查后写，写超时属于「结果未知」，必须先查状态再决定是否重试。威胁模型覆盖冒充越权、恶意退款、薅羊毛、Prompt 注入与内部作弊。成本结构里 LLM 占比最大，其次是实时查询，工具调用居中，人工审批视风险而定。

思考笔记

五条原则里「先查后写」最容易被违反、后果也最直接：写超时在普通系统里是「重试一次」，在电商里是「结果未知」。同一个超时在支付场景可能已经扣款成功，盲目重试就是重复扣款。所以这条原则的本质不是「多查一次」，而是要求把「未知」当作一种独立的状态来处理，而不是默认它等于失败。

五层设计原则：

  • 快慢分离：高频封闭判断走轻量模型/规则，复杂规划才进 Agent。
  • 读实时、写幂等：价格、库存、订单状态必须实时查；所有写工具带幂等键。
  • 模型提议、规则裁决、工具执行：模型不能直接改资金或库存，只能调用受控工具。
  • 可补偿、可审计：每个写操作都有状态机、幂等键、补偿路径与操作日志。
  • 先查后写：写超时属于「结果未知」，必须先查状态再决定是否重试（护栏见写操作护栏）。

5.3.4 智能导购与商品推荐

本章要点

导购的核心挑战是理解模糊多维需求，比如「适合油痘肌、成分温和、预算 200 元以内的晚间洁面」，并结合实时库存、价格、券后价与促销规则给出可信推荐。三条架构要点：检索与实时状态双校验，商品知识与参数走向量加关键词的混合检索，价格、库存、促销资格与券可用性必须调用实时商品或营销引擎，禁止依赖静态索引或模型记忆；结构化事实槽位维护预算、肤质、必选条件与已排除商品，多轮追问不丢约束也不反复推荐被否决的款式；推荐解释说明为什么适合，并标注价格与库存的查询时点。四个工具分别负责混合检索、实时价格库存促销、券资格与券后价、无货时的替代品。

思考笔记

「禁止依赖静态索引或模型记忆」是导购与内容推荐的分野。内容推荐推荐错一个视频没有后果，导购推荐错一个商品会直接导致下单失败与客诉。所以导购不能沿用推荐的思路——检索层给的是「看起来匹配」，双校验给的是「现在买得到」，大促与库存剧烈波动的时段尤其如此。

5.3.5 订单、履约与售后

本章要点

订单售后涉及查单、改地址、催发货、退换货、价保补差与退款，动作落在强状态机与资金库存变更上，并发请求或超时重试极易导致重复退款、超额赔付或状态错乱。多工具依赖分三批执行：只读波次并行查订单、物流、价格历史与售后政策；校验波次查退款资格、算退款金额、查价保资格，不通过就跳过写操作并回填原因；写入波次把退款、价保与改地址按依赖串行执行，每步确认结果。写操作护栏逐项列了必查状态、审批限额与幂等键格式，改地址查未发货与次数限制，退款查已支付、未退款与售后窗口内。金额计算要考虑实付、运费、优惠分摊、补贴追回与部分退款，券后价与价保的比较口径必须固定。

思考笔记

三波次的价值在于把「想清楚」和「动真格」在时间上分开：校验波次不通过时写操作一次都不会发生，用户拿到的是一个有原因的拒绝而不是一次半途失败。金额那段「不能按原价退、按券后价赔」尤其值得记——它不是实现细节，而是口径必须唯一，否则客服无解、账务对不上。

  1. 只读波次：get_order、get_logistics、get_price_history、get_refund_policy 并行执行。

5.3.6 经营问数与增长召回

本章要点

经营问数的挑战是口径分歧、宽表复杂、慢查询与数据权限隔离。语义层固化支付 GMV、退款金额、净 GMV、券补贴、动销率与退货率的公式，并明确退款归属按原订单日期还是退款发生日期统计。执行安全三条：Schema 裁剪只召回相关表结构与样例值，SQL 走 AST 校验只放行只读查询并强制 LIMIT 与超时，执行层或视图层强制注入商家、店铺、部门权限过滤。增长召回的链路是决策模型判断时机与渠道、查实时订单与退订状态、Redis Lua 原子频控、带幂等键下发、快慢信号归因。电商特有的约束是触达前校验 SKU 仍有货、券仍可用、价格未变，且已支付、已退款、已退订用户必须排除。

思考笔记

问数这一节的价值在「净 GMV」这个口径上——它由三个有争议的分量拼成，任何一个分歧都会让环比结论失真。增长召回则和上一章的营销章互补：营销章讲通用触达护栏，电商这里补的是 SKU 有货、券可用、价格未变三条电商专属校验，缺一条就会把一个已失效的商品推到用户面前。

电商问数与经营分析 Agent

核心挑战：运营/商家问「华东区昨日净 GMV 环比变化及原因」「某类目退货率飙升」，面临指标口径分歧、宽表复杂、慢查询与数据权限隔离。

语义层固化口径：

  • 支付 GMV、退款金额、净 GMV、券补贴、动销率、退货率等公式与统计口径统一。
  • 明确退款归属：按原订单日期还是退款发生日期统计，必须写进指标卡。
  • 示例：净 GMV = 支付 GMV − 退款金额 − 券补贴（具体口径按业务定义）。

执行安全：

  • Schema 裁剪只召回相关表结构与样例值。
  • SQL 走 AST 校验，仅放行只读查询，强制 LIMIT 与超时。
  • 在执行层/视图层强制注入商家、店铺、部门权限过滤。
  • 结果结合维度特征渲染图表与归因拆解。

本章差异：多租户商家隔离、数据新鲜度与经营指标口径；通用能力（语义层、Schema Linking、SQL 自愈、权限）见第 1 章 · 问数 Agent。

增长与召回营销 Agent

核心场景：加购未支付召回、浏览未下单提醒、沉睡用户激活、会员到期触达。

链路：决策模型判断时机/渠道 → 查实时订单与退订状态 → Redis Lua 原子频控 → 带幂等键下发 → 快慢信号归因。

电商特有约束：

  • 触达前校验 SKU 是否仍有货、券是否仍可用、价格是否已变化。
  • 已支付、已退款、已退订用户必须排除。
  • 券预算与补贴成本纳入净 ROI，不只看点击率。

本章差异：频控、Holdout、Thompson Sampling 与降级矩阵详见第 4 章 · 营销 Agent。

5.3.7 多轮工具调用与上下文治理

本章要点

多轮工具调用裁剪上下文时，`assistant(tool_calls)` 与对应的 `role="tool"` 消息必须视为不可拆分的原子组，先瘦身超长 JSON 与日志，再整组淘汰，发往模型前做 `tool_call_id` 配对校验。结构化事实槽位锁定 order_id、sku_id、实付金额、已核实约束与已执行写操作，防止重复退款与重复查单；增量摘要承接早期排查脉络，近期 K 轮保留完整原始交互。上下文预算的顺序是系统提示与工具定义、事实槽位、最近 K 轮、滚动摘要、工具结果，工具结果优先保留结构化字段，长日志截断并保留错误码与关键行。并行与串行的分界是只读工具可并行、写工具按依赖串行，同一订单的写操作加订单级锁或版本号。

思考笔记

原子组这条是纯粹的协议债：工具调用与它的结果是一对，拆开就等于丢了结果或发了无主的调用。真正值得留意的是它与「上下文预算是有限的」这两件事的组合——裁剪时你不能挑着裁，只能整组留或整组丢，所以该优化的是「每组有多大」，也就是工具结果的结构化程度。

多轮工具调用与上下文治理

1. 原子工具组与配对安全

多轮工具调用裁剪上下文时，把 assistant(tool_calls) 与对应的 role="tool" 消息视为不可拆分的原子组：先瘦身超长 JSON/日志，再整组淘汰；发往模型前做 tool_call_id 配对校验，防止协议报错或状态断裂。

2. 结构化事实槽位 + 增量滚动摘要

  • 槽位锁定 order_id、sku_id、实付金额、已核实约束、已执行写操作，防止重复退款/重复查单。
  • 增量摘要承接早期排查脉络；近期 K 轮保留完整原始交互。

3. 上下文预算分配

系统提示与工具定义 → 事实槽位 → 最近 K 轮 → 滚动摘要 → 工具结果

工具结果优先保留结构化字段，长日志截断并保留错误码与关键行。

4. 并行与串行

  • 只读工具可并行；写工具按依赖串行。
  • 同一订单的写操作加订单级锁或版本号，避免并发改地址/退款互相覆盖。
  • 工具契约声明 side_effect、超时、重试语义、幂等要求与权限范围。

5. 写超时的正确处理

写调用超时属于「结果未知」，不能直接重试：先查订单/退款单状态，确认未成功后再用同一幂等键重试；已成功则复用结果。

5.3.8 幂等、降级与可观测性

本章要点

5.3.9 评测闭环与容量估算

本章要点

评测闭环五件套：黄金轨迹集是问题加期望工具序列加期望结果；工具沙箱模拟订单、退款、库存状态，覆盖成功、失败、超时与重复提交；对抗测试打 Prompt 注入、越权、诱导退款与伪造物流信息；在线 A/B 与 Holdout 验证真实解决率与增量；决策快照、工具轨迹、原因码与结果回流用于阈值校准、工具参数优化与策略精调。容量估算假设日会话 100 万、峰值 5 倍、平均 3 轮 5 次工具调用、写操作 5%、单次 4000 输入 500 输出 token：峰值会话 58 QPS，工具调用峰值 290 QPS，写操作峰值 15 QPS，LLM 调用峰值 174 QPS，日 token 约 135 亿，会话存储约 20GB 一天，工具调用日志约 10GB 一天。结论是 LLM 成本与工具下游压力是主要瓶颈，写操作量不大但必须强幂等。

思考笔记

「写操作峰值 15 QPS」这个数字看上去微不足道，却是整份容量表里唯一一处「慢一点就出事」的地方——读操作超时只是慢，写操作超时在支付场景可能已经扣款成功。所以给电商做容量评估时，15 这个数不该和 290 放在同一个量级上比较，它们是两种完全不同的负载。

评测闭环

  • 黄金轨迹集：问题 + 期望工具序列 + 期望结果。
  • 工具沙箱：模拟订单、退款、库存状态，覆盖成功、失败、超时、重复提交。
  • 对抗测试：Prompt 注入、越权、诱导退款、伪造物流信息。
  • 在线 A/B / Holdout：验证真实解决率与增量。
  • 回流：决策快照、工具轨迹、原因码与结果，用于阈值校准、工具参数优化与策略精调。

容量估算

假设：日会话 100 万，峰值 5 倍，平均 3 轮、5 次工具调用，写操作 5%，单次 4000 输入 + 500 输出 token。

指标计算结果
平均会话 QPS100 万 ÷ 86400≈ 11.6
峰值会话 QPS11.6 × 5≈ 58
工具调用峰值58 × 5≈ 290 QPS
写操作峰值290 × 5%≈ 15 QPS
LLM 调用峰值58 × 3≈ 174 QPS
Token/天100 万 × 3 × 4500≈ 135 亿
会话存储100 万 × 20KB≈ 20GB/天
工具调用日志500 万 × 2KB≈ 10GB/天

结论：LLM 成本与工具下游压力是主要瓶颈；写操作量不大但必须强幂等。扩容时的先坏顺序见扩容 10 倍，哪里先坏。

5.4 工程落地与规则护栏

第四段 · 工程落地与护栏这一段回答：方法论在电商链路上怎么一环一环接住——工具怎么约束、写操作怎么保护、上下文怎么裁、降级怎么分级。

5.4.1 端到端链路与门控路由护栏

本章要点

电商的端到端链路从用户消息经 Gateway 的鉴权、租户与限流，到 Intent Router 分流导购、售后、问数与增长，再进 Agent Orchestrator：加载槽位与摘要、规划只读与校验与写入的 DAG、经 Tool Gateway 走白名单、Schema 与幂等、高风险进 HITL 审批、留 Checkpoint，最后领域服务执行、结果校验与回复、事件审计与归因。门控与路由护栏五条：快慢分离，简单查询走规则或轻模型；意图置信度低就追问或转人工；高风险意图（退款、改地址）强制进入工作流，不允许自由发挥；租户与商家隔离，工具按租户授权。

思考笔记

链路里「高风险 → HITL 审批」与「Checkpoint」是两个常被省掉的节点。省掉审批意味着大额退款直接由模型拍板，省掉 Checkpoint 意味着一次失败要从头再来。而这两个节点恰好是电商里「不可逆动作」的兜底——它们本身不产生价值，只是把不可逆变成可逆。

端到端链路

用户消息
  → Gateway（鉴权、租户、限流）
  → Intent Router（导购/售后/问数/增长）
  → Agent Orchestrator
      ├→ 加载槽位与摘要
      ├→ 规划 DAG（只读/校验/写入）
      ├→ Tool Gateway（白名单、Schema、幂等）
      ├→ 高风险 → HITL 审批
      └→ Checkpoint
  → 领域服务执行
  → 结果校验与回复
  → 事件、审计、归因

门控与路由护栏

  • 快慢分离：简单查询走规则/轻模型，复杂多步进 Agent。
  • 意图置信度低 → 追问或转人工。
  • 高风险意图（退款、改地址）强制进入工作流，不允许自由发挥。
  • 租户/商家隔离，工具按租户授权。

5.4.2 工具契约与写操作护栏

本章要点

电商的工具契约七项要求逐条落到工程约束：描述写清用途、参数、限制与示例，Schema 约束类型、范围、枚举与必填，副作用声明 `side_effect` 是读、写还是资金，幂等要求写工具必须接受 `idempotency_key`，超时有独立超时与重试语义，权限做资源级鉴权与租户隔离，审计记录参数、结果、耗时与调用者。写操作护栏六条：先查后写，写前查状态、写超时先查结果；订单级锁与版本号防并发覆盖；金额由统一规则引擎计算，不由模型计算；超金额阈值转人工；不可逆动作执行前向用户二次确认；补偿走 Saga 逆序，失败进人工队列。

思考笔记

「金额由统一规则引擎计算，不由模型计算」和「模型不能直接改资金或库存」其实是同一条原则的两次出现：模型的价值在理解与表达，规则的价值在确定与可审计。把这两件事分开之后，很多事故的根因就自然消失了——因为模型从来就没有被允许碰钱。

项要求
描述用途、参数、限制、示例
Schema类型、范围、枚举、必填
副作用声明 side_effect（读/写/资金）
幂等写工具必须接受 idempotency_key
超时独立超时与重试语义

写操作护栏

  • 先查后写：写前查状态，写超时先查结果。
  • 订单级锁/版本号：防并发覆盖。
  • 金额规则引擎：统一口径，不由模型计算。
  • 阈值审批：超金额转人工。
  • 二次确认：不可逆动作向用户确认。
  • 补偿：Saga 逆序补偿，失败进人工队列。

5.4.3 上下文治理与降级熔断

本章要点

上下文治理护栏五步成序：先估算 token 并预留输出，再裁剪超长工具结果，然后整组淘汰早期 tool 交互，接着更新事实槽位与摘要，最后做 `tool_call_id` 配对校验。降级与熔断四条：资金、状态与频控一律 Fail-Closed；导购与生成走缓存或模板兜底；高频抖动的依赖配熔断器；每次降级都要打标，避免兜底效果被算成策略效果。

思考笔记

五步治理里「先估算 token 并预留输出」是唯一步骤顺序敏感的一步：很多裁剪策略写着写着就不裁了，就是因为把预算全花在了输入上，留给输出的余量被挤成了零，模型被迫把答案截断。预留输出应该发生在裁剪之前，而不是事后补救。

上下文治理护栏

步骤动作
1估算 token，预留输出
2裁剪超长工具结果
3整组淘汰早期 tool 交互
4更新事实槽位与摘要
5配对校验 tool_call_id

降级与熔断

  • 降级矩阵以降级矩阵为准，本节只列执行动作。
  • 资金/状态/频控：Fail-Closed。
  • 导购/生成：缓存/模板兜底。
  • 高频抖动依赖：熔断器。
  • 降级打标，避免效果误算。

5.4.4 观测压测与上线检查

本章要点

观测分五类：会话看轮次、意图分布与解决率，工具看成功率、P99 与超时率，写操作看成功率、重复率与审批率，业务看转化率、退款时长与 ROI，安全看越权、注入与资损。压测六项覆盖峰值 5 倍会话、单订单并发写、支付与退款超时、库存与价格服务故障、LLM 限流、重复消息与重复点击。上线检查十问逐条对应前面所有原则：写工具是否全部支持幂等键、写超时是否先查后重试、状态机是否覆盖所有跃迁、金额规则是否统一可审计、高风险操作是否强制审批、工具是否白名单加 Schema 校验、上下文是否原子组裁剪、降级是否分级、审计是否覆盖决策与动作、黄金轨迹与对抗测试是否通过。

思考笔记

5.5 端到端案例

第五段 · 端到端案例这一段回答：一个真实的售后组合请求怎么走完整条链路，以及四个变体分别暴露什么。

5.5.1 案例：价保与退款的组合请求

本章要点

案例是用户同时要价保和退货退款：上周买的耳机降了 80 元能不能价保，昨天那单面霜想退。八步走完：意图拆成价保与退货退款并分别绑定订单与 SKU；槽位锁定两个 order_id、sku_id、实付金额、收货时间与是否拆封；只读波次并行查订单、物流、价格历史与售后政策；校验波次确认耳机签收 5 天在 7 天价保窗口内、面霜未拆封在 7 天无理由窗口内；风险判断是合计退款 379 元低于自动阈值，但该用户近 30 天已有 3 次退款触发风控，挂起人工复核；审批通过后以价保与退款各自的幂等键串行提交；退款成功但优惠券追回失败时进入 Saga 补偿与人工队列，绝不对同一订单再次发起退款。

思考笔记

这个案例里最关键的不是流程，而是「风险判断」那一步：合计 379 元低于阈值本该自动通过，是「近 30 天已有 3 次退款」这条与金额无关的信号把它拦了下来。这说明阈值不能只看单笔金额，用户维度的历史行为同样是资损的前兆。

案例：价保 + 退款组合请求

用户：「上周买的耳机现在降了 80，能价保吗？另外昨天那单面霜我想退。」

  1. 意图拆分：价保 + 退货退款，分别绑定订单与 SKU。
  2. 槽位：两个 order_id、sku_id、实付金额、收货时间、是否拆封。
  3. 只读波次：并行查订单、物流、价格历史、售后政策。
  4. 校验波次：
    • 耳机已签收 5 天，在 7 天价保窗口内，价差 80 元，无「特殊商品不参与价保」限制。
    • 面霜昨日签收、未拆封，在 7 天无理由退货窗口内。
  5. 风险判断：合计退款 379 元，低于自动处理阈值；但该用户近 30 天已有 3 次退款，触发风控标记 → WAITING_FOR_HUMAN 人工复核。
  6. 写入波次：审批通过后，分别以 pp:{order_id}:{sku_id}:{price_version} 与 refund:{order_id}:{request_id} 为幂等键提交价保和退款，串行确认。
  7. 补偿：退款成功但优惠券追回失败时，进入 Saga 补偿/人工队列，绝不对同一订单再次发起退款。
  8. 回复：告知价保金额、退款到账时间、退货方式与所需材料。

常见失败：重复点击 → 幂等键去重；写超时 → 先查单再重试；已退款 → BIZ_ALREADY_REFUNDED；超窗口 → BIZ_OUT_OF_WINDOW 并解释规则。

5.5.2 变体：智能导购、无货替代与经营问数

本章要点

三个变体各练一条链路。智能导购六步：查询改写成控油、温和、氨基酸洁面；混合检索向量加属性过滤取 Top-20；批量实时查价格、库存与券后价；排序综合相关性、可得性、价格匹配与评价；无货时先给同款不同规格再给相似款并说明差异；最后解释成分、适用肤质、券后价与查询时点。无货与替代的纪律是四条：先查同款其他规格与颜色，再查相似款并保持品类与价格带，明确告知「原商品无货，以下为替代」，不静默换品、不虚标库存。经营问数五步：语义层确认净 GMV 口径与退款归属，Schema 裁剪订单、退款、券、门店与地区，权限重写为仅华东仅本商家，按渠道、品类与门店做贡献度归因，最后输出结论加 SQL 加口径加注意事项。

思考笔记

三个变体放在一起看有个共同点：每一步的输出都是「可核验的」——导购给券后价与查询时点，问数给 SQL 与口径，替代给差异说明。电商 Agent 的输出契约不是一段流畅的建议，而是「结论加依据加依据的时点」三件套，缺了第三件用户就没法判断该不该信。

变体 A：智能导购

用户：「适合油痘肌、成分温和、预算 200 元以内的晚间洁面。」

  1. 查询改写：控油、温和、氨基酸洁面。
  2. 混合检索：向量 + 属性过滤，Top-20。
  3. 实时校验：批量查价格、库存、券后价。
  4. 排序：相关性 + 可得性 + 价格匹配 + 评价。
  5. 无货替代：同款不同规格 → 相似款，明确差异。
  6. 解释：说明成分、适用肤质、券后价与查询时点。

护栏：不编造参数；推广位标注；价格库存带时间戳。

变体 B：无货与替代

  • 先查同款其他规格/颜色。
  • 再查相似款，保持品类与价格带。
  • 明确告知「原商品无货，以下为替代」。
  • 不静默换品，不虚标库存。

变体 C：经营问数

问题：「华东区昨日净 GMV 环比下降的原因？」

  • 语义层确认净 GMV 口径与退款归属。
  • Schema 裁剪：订单、退款、券、门店、地区。
  • 权限重写：仅华东、仅本商家。
  • 归因：按渠道、品类、门店拆贡献度。
  • 输出：结论 + SQL + 口径 + 注意事项。

5.5.3 故障兜底、扩容与取舍复盘

本章要点

故障与兜底六条：重复退款靠幂等键、唯一索引与状态机；写超时结果未知就先查单再决定重试；库存服务超时则展示缓存并标注、结算拦截；支付接口超时状态未知就查单确认；LLM 限流切备用模型或转人工；审批系统故障时暂停写入但保留只读。扩容 10 倍的先坏顺序是六级：LLM 配额先坏（429 与排队）、然后实时商品查询（读写分离）、然后订单库（连接数与锁竞争）、然后工具下游（并发控制与熔断）、然后审批人力（阈值优化）、最后事件链路（扩分区与采样）。取舍复盘六条把每个决策的代价、收益与重新评估条件都写明了：快慢分离代价架构复杂、收益低延迟与可控，场景简单可合并；写操作审批代价人工成本、收益防资损，风控成熟可放宽；实时双校验代价延迟与成本、收益不推荐无货，库存稳定可缓存；DAG 与 Wave 代价编排复杂、收益依赖正确，单工具场景可简化；原子组裁剪代价实现复杂、收益协议安全，上下文充足可简化；Fail-Closed 代价少成交、收益不资损，依赖稳定可放宽。

思考笔记

扩容顺序里「审批人力」排在第五位很反直觉——它不是技术瓶颈，却是唯一一个扩容解决不了的瓶颈。加机器、读写分离、熔断都能在几天内做完，而培养一批能判断大额退款与价保政策歧义的审批人需要几个月。所以审批队列的长度是业务扩张速度的天花板，不是工程排期能绕过去的。

5.6 演进、指标与误区

第六段 · 演进与误区这一段回答：电商这套系统怎么一步步长大，成熟后看哪几个数，以及哪些坑最贵。

5.6.1 演进路线与指标体系

本章要点

电商的演进六级：L0 规则客服机器人起步做 FAQ 与关键词，L1 导购加查询在商品咨询量大时上检索与实时价格，L2 售后工具化在售后量大时补状态机与幂等，L3 多工具 Agent 在复杂请求场景上 DAG、槽位与 HITL，L4 问数加增长在经营需求出现时上语义层与 CDP，L5 全场景智能体在成熟后统一编排并自动调优。指标体系五层：任务层的解决率、转人工率与满意度判断价值，工具层的成功率、写成功率与重复率判断可靠性，业务层的转化率、退款时长与 ROI 判断效果，安全层的越权、注入与资损判断风险，成本层的单会话成本与降级比例判断可持续。

思考笔记

L2「售后工具化」是电商绕不开的一级，因为退款这类动作在没有状态机与幂等的前提下根本不该上线。很多团队直接从 L1 跳到 L3，用大模型包住整个售后链路，结果是模型越强、错得越贵——工具化的意义恰恰是先把能确定的部分确定下来，再把模型放到它该在的位置上。

5.6.2 评测回归与成本优化

本章要点

评测与回归六条：黄金轨迹集覆盖导购、售后、问数与增长；工具沙箱模拟成功、失败、超时与重复提交；对抗测试打注入、越权与诱导退款；在线 A/B 与 Holdout 验证真实解决率；每周复盘 Top 错误并沉淀到工具描述与槽位规则。成本优化五条按收益排序：模型分级把意图识别与抽取交给小模型；缓存商品详情、价格快照与工具结果；上下文用原子组加槽位加摘要；批量做商品与价格查询；早停在置信度高时不跑满步数。

思考笔记

「每周复盘 Top 错误，沉淀到工具描述与槽位规则」是把评测闭环真正闭上的一步：复盘的产出不是一份报告，而是工具描述里的几句话与槽位里的几条规则。工具描述写清楚了「这个工具什么时候该用、什么时候不该用」，模型少调错一次工具，收益比换一个更大的模型大得多。

评测与回归

  • 黄金轨迹集覆盖导购、售后、问数、增长。
  • 工具沙箱模拟成功、失败、超时、重复提交。
  • 对抗测试：注入、越权、诱导退款。
  • 在线 A/B 与 Holdout 验证真实解决率。
  • 每周复盘 Top 错误，沉淀到工具描述与槽位规则。

成本优化

  • 模型分级：意图/抽取用小模型。
  • 缓存：商品详情、价格快照、工具结果。
  • 上下文：原子组 + 槽位 + 摘要。
  • 批量：商品/价格批量查询。
  • 早停：置信度高不跑满步数。

本章要点

5.6.4 高频追问、答题提纲与一页纸作战手册

本章要点

电商的高频追问十二条覆盖防止重复退款、避免推荐无货商品、多 Tool Call 排序、防备注里的 Prompt 注入、评测方式、退款金额算法、写超时处理、并发写同一订单、上下文裁剪、多租户隔离、金额口径不一致与防越权改地址。答题提纲给 25 分钟版：0–3 分钟澄清场景、会话量、交易风险与实时性，3–6 分钟算会话、工具、写操作 QPS 与 token，6–11 分钟讲五层架构，11–16 分钟讲导购双校验、售后状态机与 DAG 与 Wave，16–21 分钟讲幂等、金额规则、上下文治理与降级，21–25 分钟讲评测、成本与取舍，后面还配五道练习。一页纸作战手册把全章收成三块：主线与放大器、工具与写路径、金额与验证。

思考笔记

十二条追问里「退款金额怎么算」这一条最好用来自测——它看起来简单，实际要同时说清实付、运费、优惠分摊、补贴追回与部分退款五项，而且要给出统一口径的落点。能答出这一条的人，通常也答得出后面所有关于幂等与降级的问题，因为三者共用同一套「口径唯一」的思路。

高频追问

  • 如何防止重复退款？ → 幂等键 + 唯一约束 + 状态机条件更新，超时先查单。
  • 如何避免推荐已下架/无货商品？ → 检索后调用实时价格库存接口二次校验。
  • 多个 Tool Call 怎么排？ → 只读并行、校验居中、写入串行，按 DAG/Wave 执行。
  • 如何防止用户备注里的 Prompt 注入？ → 不可信文本隔离，工具白名单与参数校验，写操作确认。
  • 如何评测电商 Agent？ → 黄金轨迹 + 工具沙箱 + 对抗测试 + 在线 A/B 与人工转接率。
  • 退款金额怎么算？ → 实付、运费、优惠分摊、补贴追回与部分退款统一口径。
  • 写超时怎么办？ → 先查订单/退款单状态，确认未成功再用同一幂等键重试。
  • 并发写同一订单怎么办？ → 订单级锁 + 版本号 + 条件更新。
  • 上下文怎么裁？ → assistant(tool_calls) 与 tool 消息整组保留/淘汰。
  • 如何做多租户隔离？ → 工具、数据、权限、审计全隔离。
  • 金额口径不一致怎么办？ → 规则引擎统一，指标卡固化。
  • 如何防止越权改地址？ → 实名 + 订单归属校验 + 二次确认。

答题提纲与练习

25 分钟答题提纲：

时间内容
0–3 min澄清：场景、会话量、交易风险、实时性
3–6 min容量：会话/工具/写操作 QPS、token
6–11 min五层架构：门控 → 编排 → 工作流 → 工具 → 归因
11–16 min导购双校验、售后状态机、DAG/Wave
16–21 min幂等、金额规则、上下文治理、降级
21–25 min评测、成本、取舍

练习：

  1. 设计日 100 万会话的电商 Agent，给出五层架构。
  2. 设计退款链路的幂等与状态机，要求不重复扣款。
  3. 设计多工具 DAG，覆盖只读、校验、写入三波次。
  4. 设计上下文原子组裁剪与槽位方案。
  5. 设计导购的实时双校验与无货替代策略。

一页纸速记

主线与放大器

  • 电商 Agent = 导购 + 交易 + 售后 + 问数 + 增长。
  • 三个放大器：资金、库存、口碑。

工具与写路径

  • 读实时、写幂等、钱必审。
  • 工具分批：只读并行、校验居中、写入串行。
  • 上下文原子组：assistant(tool_calls) + tool 不可拆。
  • 写超时先查后重试，绝不盲目重试。

金额与验证

  • 模型提议、规则裁决、工具执行。
  • 金额由规则引擎算，不由模型算。
  • 降级：资金/状态/频控 Fail-Closed。
  • 没有黄金轨迹与对抗测试，就无法证明 Agent 可靠。

5.7 总结

总结把这一章收成一页纸：结论、边界，以及下一章要解决什么。

5.7.1 一句话总结

思考笔记

电商 Agent 的第一性问题不是「模型够不够准」，而是「哪些决定绝不能交给模型」：模型负责理解与表达，规则负责金额与状态，工具负责执行——凡是能算准的就交给规则引擎，凡是能改状态的就必须有幂等键、状态机与二次确认。

5.7.2 本章结论

  1. 模型提议、规则裁决、工具执行。模型不能直接改资金或库存，金额由规则引擎算，不由模型算。退款金额要同时考虑实付、运费、优惠分摊、补贴追回与部分退款，口径不唯一客服就无解。
  2. 写路径的三条铁律：先查后写、写超时先查单、写操作带幂等键。先查后写是因为状态复核只读免费而盲目重试在支付场景就是重复扣款；写超时是一种「结果未知」的独立状态，不能默认等于失败。
  3. 重复退款 0、错误写操作 0 是硬约束，不是比率。这类错误的分母是订单数，落在错的那几单上就是百分之百资损。幂等键配唯一索引与状态机条件更新，是让它在架构上不可能发生，而不是概率很低所以还行。
  4. 读实时、写幂等、钱必审。价格、库存、券后价与订单状态必须实时查，缓存与模型记忆都不构成承诺；不可逆动作执行前必须向用户二次确认，超金额阈值转人工。
  5. 先算放大，再定链路。资金放大、库存放大、口碑放大三种代价形态不同，护栏也不同。工具链路的规模在写操作只有 15 QPS，但一次写错的代价是读操作的一万倍。

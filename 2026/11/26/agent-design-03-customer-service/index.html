客服 Agent——从答疑到受控代办

发表于2026-11-26 分类于AI Agent 系统设计

客服 AI Agent 不只是「会聊天的机器人」，而是能执行业务动作、可审计、可回滚、可人工接管的服务系统：它接收多渠道工单，完成意图识别、知识检索、工具调用与回复生成，在不确定或高风险时转人工。核心工程挑战是「同一个意图不能执行两次、执行到一半崩了要能恢复」。本章围绕 Agent 架构与队列 Worker、状态机与 Checkpoint、幂等与 HITL、三层记忆与上下文放大、工具防注入展开。

  • 一旦能调退款、改地址、发邮件，它就从聊天机器人变成了一个要背账的系统

  • 它解决的是「把请求变成一次可撤销、可审计的执行」
  • 不只是回答问题，而是把问题变成订单查询、审批通过、状态回写这些有副作用的动作
  • 难点不在生成，在于同一个意图不能执行两次，执行到一半崩了要能恢复

  • 它站在业务系统之上、工单与审批之下

  • 客服意图高度集中，用流程覆盖高频动作、用 Agent 处理长尾，比「全部走 Agent」便宜一个数量级

3.1 客服 Agent 是什么

第一段 · 客服 Agent 是什么这一段回答：客服 Agent 究竟是什么、给谁用、边界划在哪里，以及哪些决策一旦做错就要停机迁移。

3.1.1 定义与三类能力

本章要点

客服 AI Agent 是面向客户服务场景的智能体系统：接收多渠道工单，完成意图识别、知识检索、工具调用与回复生成，并在不确定或高风险时转人工。它不只是「会聊天的机器人」，而是能执行业务动作、可审计、可回滚、可人工接管的服务系统。能力分三层——问答靠知识库、事务靠业务工具、协同靠人与审批，风险依次递增：幻觉与过期知识、误操作与越权、上下文丢失与重复劳动。

思考笔记

「三类能力」这张表真正的分界线是「有没有副作用」：问答错了是一句错话，事务错了是真金白银。后面的所有架构选择——幂等、审批、审计、恢复——都只是在为「事务」这一层买单。如果一个团队说自己在做客服 Agent 却说不清哪些动作属于事务，那它做的其实只是 FAQ 机器人。

定义：客服 AI Agent 是面向客户服务场景的智能体系统。它接收多渠道工单，完成意图识别、知识检索、工具调用、回复生成，并在不确定或高风险时转人工。它不只是「会聊天的机器人」，而是能执行业务动作、可审计、可回滚、可人工接管的服务系统。

三类能力：

3.1.2 与相近系统的区别与业务价值

本章要点

规则机器人覆盖窄、维护贵，但确定性强；RPA 跑固定流程，没有自然语言理解且异常处理弱；通用聊天助手能生成回答，却无业务工具、无工单状态、无审计；人工客服判断力强，但成本高、时效不稳定。业务价值有四层：拦截常见问题降本，7×24 小时秒级首响提效，政策口径统一，全量结构化对话反哺产品与知识库。

思考笔记

与人工客服的差别值得多想一层：模型强在量大、判断确定，人强在罕见、模糊、需要担责。所以分工不该是「简单的给模型、难的给人」，而应是「模型先接住所有能靠规则闭环的，剩下的带着完整上下文交给人」——交接质量才是关键指标，转人工率本身不是。

与相近系统的区别：

系统核心与客服 Agent 的差异
规则机器人决策树/关键词覆盖窄、维护贵，但确定性强
RPA固定流程自动化无自然语言理解，异常处理弱
通用聊天助手生成回答无业务工具、无工单状态、无审计
客服 Agent理解 + 检索 + 工具 + 人机协同有副作用、强一致、强审计
人工客服人处理成本高、时效不稳定，但判断力强

业务价值：

  • 降本：拦截常见问题，减少人工坐席。
  • 提效：7×24 小时、秒级首响、并行处理。
  • 一致性：政策口径统一，减少人为差异。
  • 可分析：全量对话结构化，反哺产品与知识库。

3.1.3 系统边界、核心指标与不可逆决策

本章要点

范围内是工单接入与渠道归一、意图识别与路由、知识检索、工具编排与执行、人工转接与审批、会话状态与审计；范围外是呼叫中心话务、订单主数据、支付渠道本身、知识库内容生产与坐席排班。核心指标分效果、正确、效率、成本、安全五类，SLO 里有两条是硬约束：错误退款为 0、审计覆盖率 100%。本章七项不可逆决策——状态机语义、幂等键构造、Checkpoint schema、工具契约、上下文治理策略、RAG 分块与索引 schema、自动化分级阈值——做错了要停机迁移加数据回填。

思考笔记

判断一个决策是不是单向门，看它改动之后「历史数据还能不能解释」。幂等键规则一改，历史上已经发生的重复退款就再也认不出来，只能人工对账；工具契约一改，存量 Checkpoint 里的旧调用无法重放。相比之下模型选择、批大小、top-k、K 值都可以快速试错——但 K 值属于「可逆但很贵」，改了必须跑全量回归。

3.2 核心矛盾与设计原则

第二段 · 核心矛盾这一段回答：概率输出与确定性动作之间到底隔着什么，为什么这六条原则在冲突时说了算。

3.2.1 本质与六条章级原则

本章要点

本质矛盾是 LLM 的概率性输出与业务动作的确定性要求之间的冲突——模型可以猜，退款不能猜。六条章级原则规定冲突时以谁为准：概率负责决策、确定性负责执行；有副作用的动作必须可幂等、可审计、可补偿；规则在代码层，不在 Prompt 里；上下文是预算不是容器；不确定就交出去；每一步都要能重放。

思考笔记

第一条原则的落地方式是那句硬话：未经校验的模型输出永远不是「已完成」。它把「模型说它做完了」和「系统确认它做完了」分成两件事——后者需要状态机、幂等表和快照来支撑。也正因如此，客服 Agent 的失败往往不表现为报错，而表现为「看起来完成了，其实是半成品」。

本质：客服 Agent 的核心矛盾，是「LLM 的概率性输出」与「业务动作的确定性要求」之间的冲突。模型可以猜，退款不能猜。

六条章级原则（贯穿全章，冲突时以这六条为准）：

  1. 概率负责决策，确定性负责执行——模型的输出必须经过确定性校验（Schema、阈值、状态机）才能变成动作。未经校验的模型输出永远不是「已完成」。
  2. 有副作用的动作必须可幂等、可审计、可补偿——退款、发邮件、改地址，缺一个都不能上线。
  3. 规则在代码层，不在 Prompt 里——Prompt 可以被注入内容覆盖或诱导；安全规则、金额阈值、审批权限必须落在代码/策略层。
  4. 上下文是预算，不是容器——每次注入都要算钱。上下文成本随轮数二次增长，裁剪把它压回线性（上下文治理与上下文放大）。
  5. 不确定就交出去——置信度不足、连续失败、政策未命中，宁可转人工也不要编。「不知道」必须能被识别，不能被润色掉。
  6. 每一步都要能重放——事件、Checkpoint、审计三者齐全，任何动作都能回答「当时基于什么、谁批准、为什么」。

3.2.2 三个不等式与三个放大器

本章要点

三个不等式划定了边界：LLM 自由度远大于业务动作容错度，工单轮数远大于上下文窗口能装的轮数，用户能接受的等待远小于 Agent 深度推理耗时——首响必须快，长任务必须异步。三个放大器量化了代价：上下文放大让 token 成本随轮数二次增长，副作用放大让一次误判等于真金白银，信任放大让工具结果里藏的指令变成一次越权。

思考笔记

三个放大器里只有上下文放大是本章独有的，也最容易被当成「优化项」而不是「架构约束」。客服是唯一一个「用户多聊两句，成本就翻倍」的架构——别的系统放大的是数据量，客服放大的是对话本身。所以上下文预算必须和幂等、审批写在同一份方案里，而不是留给性能优化阶段。

三个不等式：

LLM 的自由度  >>  业务动作的容错度     → 模型可以猜，退款不能猜
工单轮数      >>  上下文窗口能装的轮数   → 不裁剪则成本按 O(n²) 爆炸
用户能接受的等待  <<  Agent 深度推理耗时  → 首响必须快，长任务必须异步

三个放大器（本章最贵的量都藏在这里）：

放大器说明后果量化
上下文放大每轮把历史与工具结果重新注入token 成本随轮数二次增长无裁剪 O(n²)、裁剪后 O(n)；20 轮工单比 4 轮贵 17 倍（上下文治理与上下文放大）
副作用放大一句话可能触发退款、改址、开票一次误判 = 真金白银幂等键 + 审批 + 快照三层兜
信任放大模型把工具结果当指令执行一次注入 = 一次越权外部数据不可信 + 规则在代码层

本章的放大器方向值得单独记：别的系统放大的是数据量，客服章的放大器是上下文——它是唯一一个「用户多聊两句，成本就翻倍」的架构。

3.2.3 三层正确性与八组关键矛盾

本章要点

三层正确性必须分开保证：答案正确靠 RAG、引用、自省与人工兜底；动作正确靠 JSON Schema、幂等键与状态机；权限正确靠代码层策略、审批与租户隔离。八组关键矛盾各配了默认策略与反转条件，比如「自动化 vs 正确性」默认风险分级、高风险走人工确认，低风险场景才可全自动。

思考笔记

把正确性拆成三层，最直接的好处是能定位问题究竟出在哪一层。「答错了」是答案层，「退款金额错了」是动作层，「退到了别人的款」是权限层——三者的排查路径、修复位置和上线阻塞程度完全不同。混在一起谈「准确率」，最后往往会得到「再加一道审批吧」这种既贵又没打到点上的方案。

三层正确性（必须分开保证）：

层次要求保障手段
答案正确事实、政策、引用准确RAG + 引用 + 自省 + 人工兜底
动作正确工具选对、参数对、只执行一次JSON Schema + 幂等键 + 状态机
权限正确不越权、不绕过审批代码层策略 + 审批 + 租户隔离

矛盾典型表现默认策略何时反转

3.2.4 失败模式、自动化分级与成本结构

本章要点

七类失败模式各有防线：幻觉靠强制引用与低置信转人工，工具误选靠工具白名单与评测，参数错误靠 Schema 与二次确认，越权靠代码层策略，提示注入靠数据包裹与来源标注，死循环靠最大步数与超时，上下文污染靠版本号与恢复前校验。自动化分 L0 到 L4 五级，L2 半自动是主流生产形态。成本结构里 LLM token 排第一，向量检索与工具调用次之，存储最小，人工兜底视转人工率而定。

思考笔记

七类失败里最值得单独记住的是「上下文污染：用旧参数执行新动作」。它不会像越权那样报错，因为参数格式完全合法——只是取的是第 3 轮之前那个已经过期的订单号。这类错误只有靠版本号和恢复前重校验才能拦住，靠模型自觉基本无望。

为什么「把规则写进 Prompt」不够（章级原则 3 的完整论证）：

  • Prompt 可以被注入内容覆盖或诱导。
  • 模型输出不稳定，同一输入可能不同结果。
  • 审计需要确定性证据，不能依赖「模型说它遵守了」。
  • 结论：安全规则、金额阈值、审批权限必须落在代码/策略层，Prompt 只做提示。

3.3.3 架构模式、工单接入与队列 Worker

本章要点

五种架构模式里 ReAct 最灵活但步数多成本高，Workflow 最可控可审计却灵活性低，Router 先分类再分派最简单最快。生产建议是 Router 优先：FAQ 走 RAG 直答、订单查询走固定只读流程、退款改址走固定流程加人工审批、投诉与低置信转人工。接入层只做校验、落库、返回工单号，不在请求线程里跑 Agent；去重用来源加外部编号的幂等键。Worker 无状态可水平扩容，靠可见性超时、启动扫描与 Checkpoint 三重兜底防崩溃。

思考笔记

「越少用 Agent 循环越好」是这一节最值钱的一句。客服意图分布高度集中，咨询占六成，用固定流程覆盖高频标准动作、用 Agent 只处理长尾，比「全部走 Agent」便宜一个数量级且更可控。判断标准也很简单：这个动作的标准流程能不能写成确定步骤？能就别交给模型循环。

  • 接入方式：Webhook 推送（实时）、API 轮询（兼容老系统）、消息队列订阅。
  • 同步 vs 异步：接入层只做校验、落库、返回 ticket_id，不在请求线程里跑 Agent；耗时任务全部异步化。
  • 去重：source + external_id 幂等键，重复消息直接返回已有工单。
  • 优先级：VIP、投诉、超时工单优先；按租户隔离队列。
  • 接入不做业务判断：渠道适配器只负责把五种渠道归一成统一消息模型（channel、user_id、content、attachments、locale、priority），不解析意图、不查订单。

Worker 设计：

  • 无状态，水平扩容；按租户/优先级分队列。
  • 心跳 + 可见性超时，防止消息被重复消费。
  • 长任务拆 Step，每步落 Checkpoint。
  • 消费成功后 ack；失败重试；超次数进死信。

Worker 崩溃的三重兜底：

兜底机制兜住什么
可见性超时消息超时未 ack 自动重投进程被 kill -9
启动扫描启动时扫 RUNNING 超时任务宕机后卡住的任务
Checkpoint从最后一步恢复重跑代价（不重复副作用）

三层缺一不可：只有可见性超时，重投的消息可能从第 1 步重跑；只有启动扫描，进程内的消息会永久卡住；只有 Checkpoint，重投时无法知道做到哪一步。Checkpoint 是唯一保证「不重复副作用」的那一层。

3.3.4 状态机、Checkpoint 与恢复

本章要点

状态机从待处理到已解决，中间挂起等待人工，失败进死信；每次状态变更写库带版本号，重试用指数退避加随机抖动，并区分可重试与不可重试。Checkpoint 每步落一次，含步骤号、状态版本、工具调用计划、已完成结果、待审批项、消息、事实槽位与 token 累计。恢复时三条硬规则：先重新校验外部状态、一律先查幂等表、版本不匹配就停并转人工。

思考笔记

「版本不匹配就停，绝不以最新的为准强行继续」是最反直觉也最正确的一条。听起来「以最新状态为准继续执行」更聪明，但那等于让一个旧快照授权一个新动作——用户上周同意的退款，不代表他今天还同意。这条规则的代价是一次人工介入，收益是不会把一次不确定执行变成一次不可撤销的资金动作。

状态机、Checkpoint 与恢复

状态机：

PENDING → RUNNING → WAITING_TOOL → RUNNING → RESOLVED
              ↓            ↓
           RETRYING     WAITING_HUMAN → RESOLVED / CLOSED
              ↓
           FAILED → DEAD_LETTER
  • 每次状态变更写库（带 version），支持断点续跑。
  • 重试：指数退避 + 随机抖动，区分可重试（超时/限流）与不可重试（参数/权限）。
  • 超过最大次数进 DLQ，人工介入或补偿。
  • Worker 崩溃靠可见性超时重新投递；启动时扫描 RUNNING 超时任务。

重试公式：

delay = min(cap, base × 2^attempt) + random_jitter

恢复时的三条硬规则：

  1. 恢复前重新校验状态：从 Checkpoint 恢复时，先校验外部世界有没有变（订单是否已退款、政策是否已改、库存是否还在），而不是直接信任快照。
  2. 副作用动作一律先查幂等表：恢复时如果 executed_actions 里已有该 tool_call_id，直接复用结果，不重发。
  3. 版本不匹配就停：Checkpoint 的 state_version 与库里的当前版本不一致时，停止执行并转人工，绝不「以最新的为准」强行继续。

3.3.5 幂等、并发与部分挂起

本章要点

幂等三件套是幂等键、唯一索引或去重表、状态机条件更新。幂等键的正确粒度是工单号加步骤号加调用号——同一工单、同一步骤、同一个调用意图三者齐一才算重复。并发上同一工单串行、不同工单并行，用乐观锁版本号、分区消费和工单粒度的分布式锁。高风险动作进待审批列表，绑定调用号、幂等键与审批快照，任务挂起并释放 Worker，依赖它的下游动作延后。

思考笔记

幂等键粒度是本章最容易做错的一处，两个方向都会翻车：键只到工单号，同一工单的两次合法退款（先退部分、后退剩余）会被误判成重复而丢掉；键只到调用号而它每次重试都新生成，幂等等于完全没做。正确粒度是把「意图」也放进键里，而不是把「调用次数」当唯一标识。

幂等与并发

幂等三件套：

  1. 幂等键（ticket_id + action + step，工具级用 ticket_id + step_id + tool_call_id）。
  2. 唯一索引 / 去重表。
  3. 状态机条件更新（UPDATE ... WHERE status = 'PENDING'）。

并发控制：

  • 同一工单串行、不同工单并行。
  • 乐观锁 version，冲突重试。
  • 分布式锁按 ticket_id 粒度，注意锁超时与归属校验。
  • 分区消费保证同一工单落到同一分区。

幂等键的粒度是本章最容易做错的一处。若键只到 ticket_id，同一工单里的两次合法退款（先退部分、后退剩余）会被误判为重复；若键只到 tool_call_id 而 tool_call_id 每次重试都新生成，则幂等完全失效。正确粒度是 ticket_id + step_id + tool_call_id——同一工单、同一步骤、同一个调用意图，三者齐一才判定为重复。

HITL、部分挂起与 DAG

工具分类：

类别示例策略
SAFE_AUTO查询订单、查物流、查政策直接执行
HIGH_RISK_APPROVAL退款、改地址、发邮件、改权限挂起审批

部分挂起流程：

  1. 安全动作先行：只读/低风险工具执行，结果写入 completed_results。
  2. 高风险动作进 pending_approvals，绑定 tool_call_id、idempotency_key、approval_id。
  3. 任务置 WAITING_FOR_HUMAN，释放 Worker。
  4. 依赖高风险结果的下游动作延后。
  5. 审批完成后回填结果，唤醒 Agent 继续。

依赖顺序：

  • 阶段门禁：Stage 1 只读探测 → Stage 2 风险评估/审批挂起 → Stage 3 副作用执行与通知。
  • DAG/拓扑顺序：depends_on 或参数占位；前置未完成/未获批时，下游保持 BLOCKED/PENDING，绝不越级执行。
  • 审批快照：涉及资金/权限的参数以审批时快照为准，防「审批看 A 参数、执行变 B 参数」。

失败补偿（Saga）：

  • 高风险工具失败：带原 idempotency_key 退避重试；仍失败则回填错误、状态 FAILED 或转人工，不静默当作成功。
  • 前半成功、后半失败：为可逆写操作定义补偿工具（cancel_freeze/reverse_action），按逆序补偿并记录审计。
  • 不可逆动作（已发邮件、已打款）记录异常交人工/对账，不能假装回滚完成。
  • 部分审批通过/驳回：逐条记录 tool_call_id 的审批状态与批注，写回 Checkpoint。

挂起不是阻塞：任务挂起时必须释放 Worker，否则一个待审批工单会长期占住一个执行槽位，在审批高峰期直接打满 Worker 池。挂起 = 状态落库 + 队列消息移除，恢复 = 审批回调重新入队。

3.3.6 工具契约与上下文治理

本章要点

工具契约七项要求：描述清晰、Schema 严格、权限白名单、写操作接受幂等键、独立超时、返回精简且含错误码、全量审计；敏感工具如退款、改地址、外发邮件、改权限必须二次确认，而工具改名等于换模型，变更要走与 Prompt 同级的回归流程。上下文治理用三层记忆：结构化事实槽位锁死硬状态、增量滚动摘要保留推理脉络、近期 K 轮完整交互保住工具链细节。

思考笔记

两处最容易踩的坑互为镜像。工具侧：描述写清楚了不等于约束生效，模型仍可能选错工具，所以 Schema 校验与二次确认才是硬约束。上下文侧：三层记忆里最值钱的是结构化事实槽位，尤其是已执行动作那一栏——它直接决定「同一个动作会不会被执行两次」，这是防重复退款的最后一道上下文级防线。

3.3.7 防注入与 RAG 检索链路

本章要点

每个调用号都必须有对应的工具消息回填，失败与跳过也要回填错误码，否则模型会报错或死循环。防注入分三层纵深：输入层把外部数据标注为不可信并与指令分区，判定层把危险动作的判定放在代码层，处置层检测到注入特征就丢弃结果并转人工。检索侧给出混合分块（语义分块加父子索引，基线 300–800 token 带 10%–20% 重叠）、混合召回（稠密向量、稀疏 BM25 与知识图谱，RRF 融合）、交叉编码器重排（Top-50 精排为 Top-5 至 Top-8）与强制引用。

思考笔记

三层纵深里真正的安全底线是判定层，因为它与模型无关：输入层的标注可能被模型忽略，处置层只是事后补救，判定层挡住的却是「模型被说服去调用一个合法但不该调的工具」。检索侧同理，先 ACL 过滤再召回重排的顺序不能反——反了就是先召回再过滤，白费算力还留下泄漏窗口。

工具结果回填与防注入

回填规则：

  • 每个 tool_call_id 必须有对应的 tool 消息，即使失败/超时/被跳过，也要回填错误码与原因，否则部分模型 API 会报错或死循环。
  • 回填内容含 tool_call_id、tool_name、执行状态（success/error/skipped）与精简结构化数据。
  • 区分「查到空结果」与「接口报错」。

防注入：

  • 外部数据不可信：工单内容、网页抓取、第三方接口、用户备注可能含对抗指令。
  • 工具结果作为数据载荷包裹或标注来源。
  • 核心规则与审批权限判定放在代码/策略层，不能依赖 Prompt 劝导模型。
  • 敏感信息脱敏：手机号、身份证、完整卡号、内部 Token。

防注入的三层纵深：

层手段挡住什么
输入层用户内容与工具结果一律标为「不可信数据」，与指令分区直接注入
判定层危险动作的判定在代码层做（金额、账号、资源归属）绕过模型的越权
处置层检测到注入特征 → 丢弃该结果 + 转人工 + 告警未知形态的注入

任何一层单独都不够：输入层的标注可能被模型忽略，判定层挡不住「模型被说服去调用一个合法但不该调的工具」，处置层只是事后补救。真正的安全底线是判定层——它与模型无关。

RAG 数据管道

版面分析与多模态：

  • 复杂 PDF/PPT/扫描件需要版面检测、表格结构还原（行列合并、表头继承）与公式识别，输出带 H1–H3 层级和页码/章节锚点的结构化文本。
  • 内嵌图表可生成「结构化摘要 + 原图链接」，支持图文联合检索。
  • 增量更新：基于内容哈希增量重切分，避免全量重建。
  • 权限继承：同步文档级 ACL 到索引元数据，检索阶段按用户权限过滤。

混合分块：

  • 语义分块：按主题/语义断点切分，避免硬截断。
  • 父子索引：子块 150–300 token 用于精确召回；命中后回溯父块 800–1500 token 送入 LLM。
  • 基线：固定窗口 300–800 token + 10%–20% overlap、按标题层级切分、表格/代码单独处理。

摄入流水线：

数据源 → 连接器（增量/ACL）→ 解析（版面/OCR/表格/公式）
      → 清洗/脱敏 → 分块（父子）→ 向量化/索引
      → 元数据（来源、版本、ACL、页码/锚点）

常见坑：OCR 错误、表格跨页、标题层级丢失、权限不同步、重复文档、版本冲突。

混合检索与重排

召回擅长短板
稠密向量同义、语义相似精确型号/错误码易漂移
稀疏 BM25专有名词、编号、短语语义泛化弱
知识图谱多跳关系、全局主题构建成本高

融合：RRF（Reciprocal Rank Fusion）。

score(d) = Σ 1 / (k + rank_i(d)),  k 常取 60

重排：

  • Bi-Encoder 大规模粗筛。
  • Cross-Encoder 对 (Query, Candidate) 细粒度打分，Top-50 精排为 Top-5~8。
  • 计算量大，只对候选集使用；高频 Query 可缓存。

指标与权限：Recall@K、MRR、NDCG、引用准确率；先 ACL 过滤再检索/重排（顺序反了会先召回再过滤，白费算力且有泄漏风险）。

Agentic RAG 闭环

查询改写与路由：

  • 模糊/多意图问题做查询扩展或子问题拆解。
  • 路由到对应知识域（财务制度、SRE 手册、产品文档），避免跨库噪声。
  • 多轮对话结合历史改写指代。

自省与纠错（Self-Reflection / CRAG）：

  • 检索后评估证据充分性与相关性。
  • 命中为空或不足时，触发改写重检、补充检索，或明确告知「知识库无足够依据」，严禁编造。
  • 评分维度：相关性、覆盖度、矛盾检测。
  • 设置最大改写次数，仍失败转人工。

强制引用：

  • 核心断言绑定文档 ID + 片段 ID + 页码/锚点。
  • 前端支持点击跳转原文。
  • 用引用覆盖率、引用准确率评测。
  • 无引用/低置信度回答降级为「建议转人工」。

3.3.8 评估方法与容量成本模型

本章要点

离线评测用 500 条黄金集，指标有意图、工具选择、参数、任务完成、幻觉与政策违规率；黄金集必须按意图、风险等级、渠道、轮数分桶，否则六成咨询类会把退款类的失败淹没。容量口径给出：峰值 LLM 调用 232 QPS、并发任务约 3480、Worker 约 348、平均输入约 4 万 token 每工单，输入 400 亿 token 每天、输出 24 亿、合计 424 亿，模型成本约 9.9 万元每天，模型分级可再省 45%。

思考笔记

这一段推翻了原版最关键的一个估算：按「100 万乘 4 次乘 3600 token」算出 144 亿每天，等于假设每次调用的输入恒定在 3000，而第二次调用的输入已经包含了第一轮的全部对话与工具结果——输入是随轮次增长的。正确的量是 424 亿每天，接近原文的三倍，账单从「几万元每天」变成「近 10 万元每天」。

评估方法

离线评测：

  • 黄金集：500 条历史工单，标注意图、应调工具、关键参数、期望答案/政策。
  • 指标：意图准确率、工具选择准确率、参数准确率、任务完成率、幻觉率、政策违规率。
  • 回归：每次 Prompt/模型/工具变更跑一遍。

在线评测：

  • 一次解决率、转人工率、CSAT、平均处理时长、关键动作成功率、单工单成本。
  • A/B：按租户/流量分桶；护栏指标（投诉率、违规率）。

安全评测：提示词注入、越权退款、PII 泄露、恶意链接；红队测试。

黄金集怎么建：不是人工标 500 条就完事——要先按意图、风险等级、渠道、轮数分桶，否则 60% 的咨询类工单会把退款类的失败完全淹没。分层指标（每桶单独看）比总体准确率有用得多。

3.3.9 不确定性与安全合规

本章要点

不确定性的四个来源各有阈值：意图置信度低于 0.7、检索覆盖度低于 0.6、工具选择前两名分差小于 0.15、参数校验失败或跨字段矛盾。模型自报的置信度不可靠，更稳的是用分类器头输出置信度，或同一输入采样三次看一致性。转人工有七个触发条件，触发时必须带上完整对话上下文、事实槽位与已执行动作、已尝试的路径、触发原因与置信度、以及 Agent 的建议。安全侧覆盖提示注入、越权、PII 泄露、恶意参数、知识库投毒与模型窃取，越权要三道闸同时成立，多租户隔离有五个面。

思考笔记

转人工率是双面指标，单看它会得出相反的结论：太低说明 Agent 在硬答，是幻觉与错误投诉的先行指标；太高说明自动化没做起来。它必须与一次解决率、CSAT、投诉率放在一起看。更有价值的是「转人工时带上了什么」——不带上下文和已执行动作，用户就得重新描述一遍，CSAT 会直接崩，而这恰恰是最容易被忽略的转人工质量问题。

3.4.4 人工协同、降级矩阵与延迟预算

本章要点

人工协同要求审批队列按风险、金额、等待时长排序，审批视图给出订单、政策、金额快照与 Agent 建议，审批超时后回到 Agent 或转人工。降级矩阵覆盖九类故障，每类都写清影响、降级动作与用户看到什么，其中工具下游故障必须「只读加转人工，不假装成功」。延迟预算表是唯一口径：接入 50ms、鉴权与路由 80ms、首响生成目标 800ms 硬限 3 秒、单工单总时长 2 分钟、审批等待 24 小时。

思考笔记

「不假装成功」是降级的第一原则。工具超时后回答「已经为您退款」，是最恶劣的失败模式——用户拿到一句假话，财务拿到一次对不上的账。所以降级路径必须明确区分成功、失败、进行中三种状态，而不是笼统地回一句「处理中」。另外预算与超时是两个数，必须满足超时大于等于预算。

人工协同

  • 审批队列：按风险、金额、等待时长排序。
  • 审批视图：订单、政策、金额快照、Agent 建议。
  • 审批超时：过期后回到 Agent 或转人工。
  • 转人工：携带完整上下文与已执行动作，避免用户重复描述（清单见 不确定性管理与转人工决策）。

3.5 端到端案例

第五段 · 端到端案例这一段回答：一个真实的退款工单怎么走完整条链路，以及四个变体分别暴露什么。

3.5.1 案例：电商退款工单

本章要点

一笔实付 500 元、已签收、理由为商品破损的订单走完整条链路：接入靠来源加外部编号幂等，编排识别为高风险退款，只读动作先行（查订单、查政策），500 元超过 300 元阈值，退款调用进待审批并绑定幂等键与金额快照，任务挂起并释放 Worker；审批通过后从 Checkpoint 恢复，先重校验订单是否已被其它渠道退款，再带幂等键执行，返回退款单号，最后才通知。

思考笔记

这个案例里最值得学的是「恢复时先重校验」这一步：审批到执行之间可能隔了几分钟，这期间用户可能在另一个渠道已经退过款。如果直接信任快照，就会退两次。整条链路的安全性不来自模型，而来自三件工程事——幂等键、审批快照、恢复前重校验，三者缺一都可能出现重复退款。

3.5.2 多渠道客服与单轮多工具案例

本章要点

多渠道案例给的是归一与路由：邮件、网页表单、IM 与电话转写统一成同一套消息模型，FAQ 走检索、订单退款走业务工具、投诉法律直接转人工，知识闭环是已解决工单提炼 FAQ、审核入库、重新索引。单轮多工具案例给的是编排：只读先行并写入已完成结果，高风险挂起并释放 Worker，依赖项延后，审批后按 DAG 继续，部分通过则逐条记录状态与批注。

思考笔记

多渠道案例里那句「重排后只注入前五条」是零风险的纯收益优化：前二十条候选全进上下文约 6000 token，其中只有五份会进答案，其余全是噪音。知识闭环那一段则提醒了一件事——客服 Agent 的知识库不是一次性工程，它的质量会随工单积累持续变化，这条链没打通，前面所有检索优化都会被陈旧的 FAQ 拖住。

案例：多渠道客服与知识库 RAG

渠道归一：邮件、网页表单、在线 IM、电话转写 → 统一内部消息模型（channel、user_id、content、attachments、locale、priority）。

意图路由：

  • FAQ/产品咨询 → RAG 回答。
  • 订单/退款/物流 → 业务 Agent + 工具。
  • 投诉/法律/高危 → 直接转人工。
  • 低置信度/连续失败 → 转人工。

RAG 链路：切分 300–800 token、重叠 10%–20% → embedding → top-k（5–20）→ rerank → 生成带引用回答；知识库版本化、增量索引。

top-k 的注入量要收敛：top-20 候选全进上下文约 6000 token，其中只有 5 份会进答案。应当 rerank 后只注入 top-5，这是零风险的纯收益优化（上下文治理与上下文放大）。

权限与安全：按租户/角色过滤知识库；PII 脱敏；外部文档不可信，防注入。

转人工策略：VIP、负面情绪、敏感词、金额阈值、用户主动要求。

知识闭环：已解决工单 → 提炼 FAQ → 审核入库 → 重新索引；差评/纠错反馈。

指标：检索命中率、回答准确率、引用率、自助解决率、转人工率。

案例：单轮多工具与审批

问题：一轮里同时有只读查询、写操作、人工审批，怎么编排？

方案：

  1. 分类：SAFE_AUTO vs HIGH_RISK_APPROVAL。
  2. 只读先行，结果落 completed_results。
  3. 高风险进 pending_approvals，任务挂起并释放 Worker。

  • 审批快照锁定参数，防执行时被改。
  • 部分审批通过时，逐条记录状态。

3.5.3 上下文超限、故障兜底与扩容取舍

本章要点

上下文超限的排查有固定顺序：先看轮数分布是否右移，再看工具结果是否变长、检索候选是否放大、K 值是否过小、模型是否被换成更贵的；处置上先治理工具结果冗余与检索候选冗余这两项零质量损失项，再调 K 并配回归。故障兜底补两条：Checkpoint 版本不兼容就停止转人工，不得强行按新版本解析旧快照；工具契约变更后老工单未完成，按旧版本处理或直接转人工。扩容 10 倍的先坏顺序是模型配额、队列、工具下游、向量检索、审批人力、存储，最后是成本——而成本这一位是非线性的。取舍复盘用八条决策记录了各自的代价、收益与重新评估条件。

思考笔记

扩容那一段有本章特有的非线性：大促期间复杂退款与投诉占比上升，20 轮工单占比若从 10% 涨到 15%，平均输入 token 从 4 万涨到 4.44 万，总 token 就涨 11 倍而不是 10 倍。所以容量评审必须按「轮数分布右移」后的口径算，只乘 10 的评审会在第一个大促把模型配额和账单一起打爆。

变体：上下文超限与成本失控

症状：某天模型账单翻倍；部分长工单的回答开始丢事实（订单号说错、金额说错）。

定位顺序：

#检查说明
1轮数分布是否右移平均轮数上升 = 用户行为或政策变化，不是代码问题
2工具结果是否变长某个工具改了返回结构，多带了字段
3检索候选是否放大top-k 被调大了
4K 值是否过小裁剪过早 → 质量下降
5模型是否被换成了更贵的路由改动导致大模型占比上升

处置：

  • 先治理工具结果冗余与检索候选冗余——这两项零质量损失。
  • 再调整 K，但必须配回归：K 变小会丢事实，K 变大要钱。
  • 模型分级：按意图路由，咨询类走低成本的分类 + 小模型。
  • 兜底：单工单 token 预算，超预算即降级（转人工或简化回答），而不是静默截断。

护栏：单工单 token 预算 + 裁剪触发记录 + 按意图分层的成本看板。

「成本涨了」与「质量掉了」经常是同一个原因：为了省成本把 K 调小，结果长工单丢事实、错误率上升，转人工率反而涨。所以 K 不是一个可以单独调的旋钮——它必须与「每工单平均轮数」「裁剪触发率」「转人工率」放在同一张看板上。

3.6.1 演进路线与指标体系

本章要点

演进路线 L0 到 L5：纯人工加 FAQ、推荐回复、半自动、自动加抽检、全自动、多 Agent 跨域，每一级都有量化的触发条件。指标体系六层：业务、正确、效率、成本、安全，加上三组信号层——转人工率与投诉率的相关性、低置信工单占比的周环比、回归通过率。

思考笔记

信号层里最有用的一条是「转人工率与投诉率的相关性」：两者同步上升，说明 Agent 在硬答，这比单看任一指标都更早暴露问题。它揭示了一个容易被掩盖的机制——自助解决率从 40% 升到 60% 但 CSAT 下降，意味着转人工率被压下去了，但错误没减少，只是从「被坐席发现」变成了「被用户发现」。

3.6.2 评测回归与成本优化

本章要点

离线评测用分桶黄金集，每次 Prompt、模型、工具变更都要跑回归并比较分桶指标。发布流程是离线回归、影子流量、1% 灰度、10%、50%、全量，每一步都有回滚开关；回滚能力按变更类型区分，Prompt 可配置热切、模型可路由热切，但工具契约只能双版本共存。成本优化按收益排序：上下文裁剪省 59% 居首，模型分级 45% 次之，工具结果瘦身 13%、检索候选收敛 11%，缓存排第五。

思考笔记

这张成本表的顺序与直觉相反，最容易被想到的「缓存」排在第五位，因为客服 Agent 的成本大头不是重复调用，而是上下文长度——先治长度，再治重复。还有一个反直觉但重要的前提：裁剪省下的 59% 是以「必须配回归」为代价的，K 值调小会丢事实，而丢事实造成的质量下降不会出现在成本表上，只会在投诉率上。

评测、回归与发布

离线评测：

  • 黄金集 500 条，按意图、风险等级、渠道、轮数分桶（评估方法）。
  • 每次 Prompt/模型/工具变更跑回归，比较分桶指标而非总体准确率。

发布流程：

Prompt/模型/工具变更
  → 离线回归（黄金集分桶指标全部不退化才进下一步）
  → 影子流量（新版本并行跑，不执行动作，只比对）
  → 1% 灰度（看护栏指标：错误退款、投诉率、转人工率、单工单 token）
  → 10% → 50% → 全量
  → 每一步都有回滚开关

回滚能力：

变更类型回滚方式注意
Prompt配置热切，秒级需保留旧版本配置
模型路由配置热切需确认降级模型可用
工具契约双版本共存，不能瞬时回滚因此工具变更必须预留一个版本周期
知识库索引版本切换需保留旧索引直到新索引验证通过

在线 A/B：按租户/流量分桶；护栏指标优先（错误退款 > 投诉率 > 转人工率 > 自助解决率）。

复盘模板：

目标 → 实际量级（工单数 / 轮数分布 / token）

模板末尾必须有「行动项 → 负责人 → 验证结果」。对 Agent 尤其如此——「优化 Prompt」不是行动项，「意图分类的 Prompt 加上版本字段，3 月 5 日回归验证咨询类准确率从 88% 提升到 93% 且退款类不退化」才是。

3.6.3 产品对比与常见误区

本章要点

思考笔记

3.6.4 高频追问、答题提纲与一页纸手册

本章要点

高频追问 17 条覆盖防重复退款、崩溃恢复、单轮多工具、注入防护、token 成本、上下文裁剪、评测方法、检索排查、上下文超限、多租户隔离、审批超时、下游故障、越权防护、置信度可信度、转人工率合理值、Prompt 变更与十万并发设计。答题提纲给 10 分钟版与 35 分钟版，一页纸作战手册按 S0 到 S5 六阶段组织，每阶段都配动作、自检问题与合格线。

思考笔记

答题提纲的设计值得注意：10 分钟版强调先给框架，35 分钟版把「上下文成本推导」「幂等与恢复」「不确定性与转人工」放在深挖环节，因为这三处最能区分「背过」与「算过」。手册里每一步都带合格线，比如「落七锚点」的合格线是写出 7 项并指明事实源是工单加工具调用加审批记录——这种可自检的表述比原则更好用。

高频追问

  • 如何防止重复退款？ → 幂等键（ticket_id + step_id + tool_call_id）+ 唯一索引 + 状态机条件更新 + 审批快照 + 全链路审计。
  • Agent 卡住/崩溃怎么办？ → Checkpoint + 可见性超时 + 启动扫描 + 幂等重试；恢复前重校验外部状态。
  • 单轮既有只读又有人工审批怎么执行？ → 分类，只读先行，高风险挂起（释放 Worker），依赖项延后，审批后按 DAG 继续。
  • 如何防止工具结果注入？ → 结果作为不可信数据包裹，规则与审批在代码层，脱敏与检测；命中注入即丢弃并转人工。
  • 如何控制 token 成本？ → 先治上下文长度（裁剪 O(n²)→O(n)），再模型分级（45%），再工具/检索冗余，最后才是缓存。
  • 上下文怎么裁？成本怎么算？ → 三层记忆；不裁剪输入 token 按 O(n²) 增长，20 轮工单比 4 轮贵 17 倍；裁剪后只贵 7 倍，省 59%。
  • 如何评估 Agent 是否变好？ → 分层黄金集回归 + 影子流量 + 灰度 + 护栏指标 + 红队。
  • RAG 答不准怎么排查？ → 召回 → 切片 → 重排 → 生成逐段定位；引用为空是检索问题，有引用但答案是错的是生成问题。
  • 上下文超限丢什么？ → 先裁工具输出，再折叠早期轮次，保留事实槽位与最近 K 轮；并记录裁剪原因。
  • 如何做多租户隔离？ → 知识库、工具、队列、配额、审计五面隔离。
  • 审批超时怎么办？ → 过期回到 Agent 或转人工，不自动放行高风险动作。
  • 工具下游挂了怎么办？ → 重试 + 熔断 + 转人工，绝不回报成功。
  • 如何防止越权？ → 身份 + 资源归属 + 金额阈值三道闸在代码层 + 审批 + 审计。
  • 模型返回的置信度可信吗？ → 不可信；用分类器头或多次采样一致性判断。
  • 转人工率多少算合理？ → 没有绝对值，必须与投诉率、一次解决率、CSAT 合看。
  • Prompt 改了怎么保证不退化？ → 分层黄金集回归 → 影子流量 → 1% 灰度 → 逐步放量，每步都有回滚开关。
  • 10 万并发怎么设计？ → 接入无状态 + 队列削峰 + Worker 无状态可扩 + Step 级幂等 + 挂起释放 Worker + 多级降级。

3.7 总结

总结把这一章收成一页纸：结论、边界，以及下一章要解决什么。

3.7.1 一句话总结

思考笔记

客服 Agent 的可信度不来自更强的模型，而来自三件工程事：幂等键保证同一个意图只执行一次，Checkpoint 与审批挂起保证执行到一半能恢复，代码层规则保证它不能越权。

3.7.2 本章结论

  1. 概率负责决策，确定性负责执行。未经校验的模型输出永远不是「已完成」。答案正确、动作正确、权限正确是三层叠加，混在一起谈准确率只会得到「再加一道审批」这种没打到点上的方案。
  2. 幂等键的粒度决定这套系统会不会重复退款。正确粒度是工单号加步骤号加调用号：同一工单、同一步骤、同一个调用意图三者齐一才算重复。只到工单号会丢掉合法的部分退款，只到调用号则幂等完全失效。
  3. 上下文是本章最贵的量。不裁剪时输入 token 按轮数二次增长，20 轮工单比 4 轮贵 17 倍；裁剪后只贵 7 倍并省 59%。正确的量是 424 亿 token 每天、约 9.9 万元每天，而不是按平均值估出来的 144 亿。
  4. 挂起要释放 Worker，恢复前要重新校验。挂起时释放执行槽位，否则审批高峰会打满 Worker 池；恢复前先重校验外部状态、版本不匹配就停并转人工，否则一次不确定执行就会变成一次不可撤销的资金动作。
  5. 降级的第一原则是不假装成功。工具超时后回答「已经为您退款」，用户拿到一句假话，财务拿到一次对不上的账。降级路径必须区分成功、失败与进行中三种状态，转人工则必须带上完整上下文与已执行动作。

文旅 Agent——行程、资源与动态重排

发表于2026-11-26 分类于AI Agent 系统设计

文旅 AI Agent 覆盖旅行前、中、后全周期：理解用户偏好与实时环境，完成行程规划、资源检索、预订交易、旅中伴游、突发重排与经营分析。它和前面几章的根本差别有两个：约束来自物理世界——营业时间、余票、天气、交通、人力，不是模型能商量的；资源是共享且强实时的——房间、座位、机票有限且会被别人买走。所以硬约束校验层不可省且必须在生成之前跑，资源必须预占加 TTL 加对账，缓存不能承诺有位。难点不在「排得顺」，而在组合空间会指数爆炸、资源会被抢走、行程会在旅中被现实打断。本章围绕需求解析与槽位、时空搜索与剪枝、预占支付与对账、影响图与旅中重排展开。

6.1 文旅 Agent 是什么

第一段 · 文旅 Agent 是什么这一段回答：文旅 Agent 究竟是什么、给谁用、边界划在哪里，以及哪些决策一旦做错就要停机迁移。

6.1.1 定义与两个根本差别

本章要点

文旅 AI Agent 是在旅行前、中、后全周期内，理解用户偏好与实时环境，完成行程规划、资源检索、预订交易、旅中伴游、突发重排与经营分析的智能体系统——它不只「会推荐景点」，还要「排得顺、订得到、改得动、算得清」。它与前面各章的 Agent 有两个根本差别：约束来自物理世界，营业时间、余票、天气、交通、人力不是模型能商量的，所以硬约束校验层不可省且必须在生成之前跑；资源是共享且强实时的，房间、座位、机票有限且会被别人买走，所以必须预占加 TTL 加对账，缓存不能承诺有位。

思考笔记

第二个差别是文旅与营销的分水岭：营销发错了可以撤回一部分，文旅发错了是超售——用户到了现场才知道。营销的触达是「打扰用户」，文旅的超售是「让用户白跑一趟」，后者在社交平台上的传播成本高一个量级。所以这一章的 P0 护栏几乎全部集中在「承诺之前」。

6.1.2 三类能力层次与典型用户

本章要点

三类能力层次对应三种决策周期：L1 规划回答「去哪、怎么排」，输出行程时间轴与候选清单，决策周期分钟级，难度中；L2 预订回答「订得到吗、花多少」，输出预占、订单与支付，决策周期在资源侧是秒级，难度较高；L3 旅中回答「现在怎么办」，输出伴游回答与突发重排方案，决策周期秒级，难度高。四类典型用户是自由行游客、家庭亲子、景区运营与文旅集团，诉求分别是规划比价预订、节奏无障碍安全、客流核销收益、多景区经营分析，主要风险则是闭园扑空与超售、强度不匹配与安全风险、口径错与越权、口径不一与归因虚高。

思考笔记

三层能力分开的意义在于它们的时间预算差了一个数量级：规划给 15 秒、伴游只给 1.5 秒、预订的资源侧只给 1 秒。把这三层塞进同一条链路，结果必然是拿规划的钱做伴游的事——最后谁都做不好。所以「这是哪一层」应该是第一道路由判断，而不是默认都走 Agent。

6.1.3 与相近系统的区别与系统边界

本章要点

与传统 OTA 的差异是：OTA 卖「机票酒店」这一个个单品，不组合也不排程。旅游攻略与内容社区说得好，但不管今天能不能去、还有没有房。地图导航只管两点之间的路径，不管多点组合与时间窗。通用旅行 LLM 会生成建议，但不接实时资源，会推荐已闭园的地方。文旅 Agent 的差异是把「建议」变成「订得到、改得动」。系统边界上，范围内是需求理解与行程规划、资源检索与实时校验、预占下单支付编排、旅中伴游与重排、经营问数与营销触达；范围外是 POI 与酒店航班主数据、航司与酒店内部系统、支付渠道、景区现场调度、数仓建模与渠道网关。

思考笔记

「通用旅行 LLM 会推荐已闭园的地方」这句看着像吐槽，其实是整个行业的能力分界线：内容生成的边际成本几乎为零，实时资源的边际成本很高。所以文旅产品的价值不在「能不能写出一段漂亮的攻略」，而在「能不能让用户按它出门并且真的走得通」——这也是为什么这一章的工程量全在约束与锁定上。

6.1.4 核心指标、SLO 与不可逆决策清单

本章要点

核心指标分行程、搜索、交易、体验、经营与安全六类，其中两个是本章特有：可行解产出率衡量有多少比例的规划请求真的产出了可行行程，评估次数与预算则是剪枝效率的直接读数。SLO 里三条是硬约束：超售 0、重复扣款 0、约束违反的行程 0；延迟目标分别是行程规划 P95 小于 15 秒、伴游回答 P95 小于 1.5 秒、库存查询 P95 小于 300 毫秒、预占 P99 小于 1 秒、重排方案生成 P95 小于 30 秒，审计覆盖率 100%。七项不可逆决策覆盖行程对象模型与版本语义、硬约束的定义与数据来源、预占语义与 TTL 策略、写操作的幂等键构造规则、与资源服务的对接契约、支付与退款的账务口径、归因窗口与 Holdout 分流规则。

思考笔记

没有可行解产出率与评估次数这两个指标，团队只会盯着「采纳率」，而采纳率低的时候根本分不清是模型不行还是搜索预算被吃光了。采纳率是结果指标，它是两个原因相乘的结果——只看它，等于把两个独立的工程问题混成一个，然后去优化那个看起来更好看的那个。

6.2 核心矛盾与设计原则

第二段 · 核心矛盾这一段回答：自由度与硬约束的冲突到底有多大，三个放大器与四层正确性分别怎么守。

6.2.1 本质与六条章级原则

本章要点

本质矛盾是「用户想要的自由度」与「现实世界的硬约束」之间的冲突——模型可以生成任意行程，但景区会闭园、航班会延误、房间会售罄。自由度的上限由约束决定，而约束由实时接口决定，这就是全章工程量的来源。六条章级原则在冲突时说了算：先可行后好看，硬约束全部过闸之后才谈推荐理由与文案；资源服务是唯一事实源，索引、缓存与模型记忆都不构成「有位」的承诺；先预占后支付，写超时先查单；行程是版本化对象，局部变更只重排受影响的天与项，已确认项不可被静默改写；变更必确认、触达必克制；搜索空间靠剪枝不靠召回，候选数上限由评估预算倒推。

思考笔记

第一条原则里那句「先给理由再校验，等于给用户希望再撤回」，是文旅与电商最本质的差别。电商里先说后撤是体验问题，文旅里先说后撤是白跑一趟。所以顺序在这里不是风格问题，而是产品承诺问题：只要先校验，用户看到的每一句话就已经成立。

本质：文旅 Agent 的核心矛盾，是「用户想要的自由度」与「现实世界的硬约束」之间的冲突。模型可以生成任意行程，但景区会闭园、航班会延误、房间会售罄。自由度的上限由约束决定，而约束由实时接口决定——所以这是本章所有工程量的来源。

六条章级原则（贯穿全章，冲突时以这六条为准）：

  1. 先可行、后好看——硬约束（营业时间、余票、交通耗时、天气、人力）全部过闸之后，才谈推荐理由与文案。顺序不能反：先给理由再校验，等于给用户希望再撤回。
  2. 资源服务是唯一事实源——价格、库存、余票、退改规则必须实时查询。索引、缓存、模型记忆都不构成「有位」的承诺。
  3. 先预占、后支付；写超时先查单——没有成功预占就不承诺有位；支付超时先查单确认，绝不盲目重试。
  4. 行程是版本化对象——局部变更只重排受影响的天 / 项，已确认项不可被静默改写。
  5. 变更必确认、触达必克制——涉及资金或行程大改时让用户确认；旅中通知严格频控，紧急安全事件才可突破。
  6. 搜索空间靠剪枝，不靠召回——候选数的上限由评估预算倒推，不由召回率正推。召回更多候选，大部分会死在第一道硬约束上，白白吃掉上下文与时间预算。

6.2.2 三个不等式、三个放大器与四层正确性

本章要点

三个不等式划出本章的工程量来源：候选组合数 C(N,k) 的 D 次方远大于评估预算能覆盖的分支数，所以靠剪枝不靠穷举；行程项数远大于单次事件的受影响项数，所以靠影响图不靠全量重排；行程客单价远大于单次错误的容忍度，所以资金类错误必须 fail-closed。三个放大器给出量化：时空搜索放大，3 天每天 3 点是 2.26×10¹⁸ 种组合、可行解只剩万分之一、必须剪枝 15 个数量级；行程变更放大，全行程 20 项重排是 3.5×10⁹ 种、只重排受影响 8 项是 6,561 种、降 5 个数量级；资金与安全放大，5 天 4 晚行程客单价 ¥6,700、重复扣款一次实际损失约 ¥10,000。四层正确性是时空可行、资源真实、资金正确、变更可控。

思考笔记

三个放大器里最容易被忽略的是第三个：客单价高意味着单次错误的绝对损失巨大，也就意味着它不能用概率来安慰自己。重复扣款率 1e-5 在别的系统里是完全可接受的数字，在日 2.5 万单的文旅里是每天 0.25 单、约 ¥2,500 直接损失——绝对值太小，小到在报表上看不见，于是就永远不会被修。

6.2.4 信任分级、威胁模型与成本结构

本章要点

信任分级是行程建议的输出契约，分四档：高信任要求全部硬约束已校验、资源已实时确认、时间矩阵完整，输出行程加每个点的校验依据加总预算；中信任是行程可行但部分点位信息较旧或余票未锁，输出行程但要标注哪些点需要出发前复核；低信任是约束校验未跑完、资源接口超时或未查余票，此时只给候选清单与「请自行确认」的提示，不给行程；拒绝态则是越权、资源被占或超出安全策略，明确拒绝并给替代路径。威胁模型覆盖黄牛抢票、虚假预订、冒充越权、Prompt 注入、恶意退改与景区侧提示注入。成本结构里最大的是 LLM，尤其候选 POI 描述；其次是实时资源查询；地图与天气居中；人工审批视风险而定。

思考笔记

「低」这一档是本章新增的，也是很多系统最缺的一档：把「查不到余票」当成「有位」，就会给出一条看起来完整、但有一个点根本订不到的行程。旅行行程的可用性是「与」的关系——一行里只要一个点订不到，整条行程就是废的。所以低信任态不是保守，而是唯一正确的输出：给候选清单，不给行程。

思考笔记

6.3.4 时空搜索放大、剪枝与组合优化

本章要点

组合空间是每天的无序组合数 C(N,k) 的 D 次方。代入基准召回 Top-200、每天 3 点、3 天：每天组合数 1,313,400，三天组合空间约 2.26×10¹⁸；每天可行比例约 4.5%，三天可行比例约 0.009%。评估预算才是真正的稀缺资源：规划 P95 15 秒里留 10 秒给评估，单点约束评估 2ms 给出 5,000 次预算，单组合评估 50ms 给出 200 次预算——两者差 2.26×10¹⁸，必须剪枝 15 个数量级。五层剪枝漏斗是召回裁剪（200 候选到 80）、单点硬约束预筛（80 到 34）、时空分块剪枝、回溯剪枝、局部搜索收敛，每层省 2 到 3.6 个量级。结论是 K 值要按预算倒推而不是按召回率正推：K 从 200 降到 84，进 Prompt 的描述从 16,000 token 降到 6,720、预筛时间同样降 58%，而可行解一个不少。

思考笔记

「可行解数量是 2.0×10¹⁴，所以可行解多不多根本不是瓶颈——能不能找到才是」是这一节最重要的一句翻转。组合空间大到没有意义，真正的问题是「你只有几万次评估机会，而可行解分散在 10¹⁸ 的空间里」。所以整套工程的重点不是生成更聪明的行程，而是把搜索效率提上去——剪枝不是优化，是这个系统能不能存在的前提。

时空搜索放大：候选、可行解与剪枝

本节是搜索与剪枝的权威版，组合优化与路线排序、行程规划护栏、变体 D：时空搜索预算与 K 值取舍只引用。

问题定义：给定候选集 N 个 POI、行程 D 天、每天 k 个点，求一个满足全部硬约束的时间轴。

每天的无序组合数 = C(N, k)
D 天的组合数     = C(N, k)^D

五层剪枝漏斗（把 10¹⁸ 降到能算的量级）：

  → 召回裁剪（域 / 主题聚类）           2.26e18 → 6.3e16

「召回 Top-K 越大越好」在文旅是错的（这是本章的核心结论）：

所以 K 的正确取法是倒推，不是正推：

K 上限 = 单点评估预算 ÷ (每天点数 × 剪枝保留率)

而不是「召回率能到多少就取多少」。文旅的系统不是缺候选，是缺剪枝。

剪枝之外的两个工程约束：

约束说明
时间矩阵必须降维全量两两时间矩阵 = C(10万, 2) = 5 × 10⁹ 项，不可行。必须按区域聚类：2,000 个区域 × 每区 50 个 POI → 区域对 200 万项，缓存 ≈ 32MB。代价是同区域内耗时用平均值 + 距离修正，精度下降

组合优化与路线排序

目标：在时间窗内最小化通勤、平衡每日强度、满足全部硬约束。

方法：

  • 时间矩阵：POI 两两之间的通勤时间（必须区域级降维，见时空搜索放大：候选、可行解与剪枝）。
  • 时间窗约束：营业时间、预约时段。
  • 启发式：最近邻构造 + 2-opt 局部优化。
  • 每日缓冲：用餐、休息、机动时间。

输出：每天时间轴、交通方式、预约提醒、室内备选方案。

评分函数（在可行解里挑「最好的」）：

总分 = w1·(行程紧凑度) + w2·(用户偏好命中) + w3·(体力均衡)
     − w4·(预算超支) − w5·(绕路惩罚) − w6·(天气风险)

权重不是玄学，必须能被解释与回放。用户问「为什么排成这样」，系统要能说出「因为你说不赶路，所以每天只排 2 个点并留了 1.5 小时缓冲」——权重表 + 槽位 + 约束余量，三样加起来就是行程的解释。解释不了的评分函数，用户不会信任，也不会采纳。

「不赶路」的工程含义：不是「少排一个点」，而是把缓冲时间显式建模。带老人小孩的行程若不留缓冲，路上 20 分钟的延误就会顶掉下一个预约——缓冲不是浪费，它是可行性的一部分。

6.3.5 资源锁定：预占、支付与对账

本章要点

资源锁定分五个波次：只读波次并发查酒店、航班状态、票务余量与接送路线；校验波次查价格、余票、退改规则、实名信息与入住规则；预占波次锁房、占座、锁票，带 TTL 与幂等键；支付与确认波次成功后确认订单、失败则释放预占；补偿波次处理多段订单部分失败。预订状态机从 QUOTED 到 HELD 到 PAYING 到 CONFIRMED，异常路径是 EXPIRED（TTL 到期回收）、NEED_RECONFIRM（价格或库存变化）、FAILED 与 CANCELLED、REFUNDED。资金放大算得很具体：5 天 4 晚行程客单价 ¥6,700，重复扣款一次的实际损失约 ¥10,000，超售一次约 ¥1,200 每间；日预订量 2.5 万单，重复扣款率 1e-5 意味着每天约 ¥2,500，超售率 1e-4 意味着每天约 ¥3,000。

思考笔记

这些数字说明一件事：在日 2.5 万单的量级上，「重复扣款 0」和「超售 0」不能靠事后对账兜底——概率乘上单量就是每天几千元的直接损失，再加上不可控的口碑损失。它们必须是 P0 护栏，必须在架构上不可能发生，而不是「概率很低所以还行」。这句话可以直接搬到任何高客单价的交易系统里。

  竞态率 ≈ 2.7 / 3,000 ≈ 0.09%

  • 价格变化：报价到支付之间重新校验；涨幅超过阈值必须让用户确认，不能静默扣款。
  • 幂等：下单、支付、退改都带 idempotency_key；同一订单的写操作加版本号或订单级锁。

  • 对账：预占、支付、确认、退款定时对账，处理超时未决与单边账。

6.3.6 旅中事件驱动重排与伴游导览

本章要点

行程变更放大是本章第二个签名量：全行程 20 项、每项 3 个备选是 3²⁰ 约 3.49×10⁹ 种重排组合，只重排受影响 8 项是 3⁸ 即 6,561 种，降 5 个数量级——全量重排不是慢，是根本算不出来。影响图的传播规则决定边界：硬时间依赖、资源依赖与预算耦合传播，软时间依赖与偏好耦合不传播。重排四条纪律是只改受影响项、至少两个方案、涉及费用变化必须确认、失败要回滚并给备选。伴游依赖实时定位、当前时段与步行或打车距离，要求低延迟、短回答、强可核验性；五个工具覆盖附近召回、营业状态、排队预约余量、路线耗时与天气预警。因为伴游只有 1.5 秒，它只注入当前位置、同行人约束与附近候选 Top-8，不注入完整行程。

6.3.7 经营问数、营销归因与上下文治理

本章要点

文旅经营问数的挑战是口径分歧、宽表复杂与跨部门跨景区权限隔离。指标口径要明确统计粒度（小时、日或节假日）、分母（预约量、入园量或可售库存）与退款归属，示例是核销率等于实际核销数除以有效预约数、净营收等于门票加园内消费减退款减渠道佣金；执行安全是语义层固化指标、Schema 裁剪、SQL 走 AST 校验只读并强制 LIMIT 与超时、执行层或视图层强制注入景区门店部门权限过滤。营销与长周期归因的链路是决策模型判断时机与渠道、查实时订单退订免打扰、Redis Lua 原子频控、带幂等键下发、快慢信号归因；文旅特点是决策周期长要覆盖 7 到 30 天、价格敏感度高所以券补贴计入净贡献、促销轰炸反感强所以行前与旅中都要控制频次与静默时段。上下文治理里候选 POI 描述占输入 token 的 32%，是最大的一块。

思考笔记

文旅问数与上一章电商问数的方法论完全一致，但文旅特有的难点是混杂因素：天气、节假日、促销三个因素不显式控制，「客流下降 5%」的归因结论会全是错的。这提醒一件事：同样一套技术栈，落到不同行业，真正的工作量往往在口径与混杂因素上，而不在查询引擎。

文旅经营问数

核心挑战：景区 / 航司 / 酒店运营分析「分时入园人数、核销率、连带消费、客诉率、淡旺季净收益」，面临口径分歧、宽表复杂与跨部门 / 跨景区权限隔离。

指标口径：

  • 分时入园人数、预约核销率、客单价、连带消费、客诉率、退款率、净营收。
  • 明确统计粒度（小时 / 日 / 节假日）、分母（预约量 / 入园量 / 可售库存）与退款归属。

  • 语义层固化指标；Schema 裁剪只召回相关表。

6.3.8 幂等、降级矩阵与可观测性

本章要点

幂等分七层：预占用 hold 前缀加类型、资源、用户与请求号，下单用 booking 前缀加用户与请求号，支付用 booking_id 与支付请求号做状态机条件更新，退改同理，状态用条件更新，消息用去重表加 msg_id 唯一，最后一层是资源查询必须带查询时点——写操作必须复核，不复用查询结果。降级矩阵按「依赖失效时，失效的后果是少卖一单，还是让用户白跑一趟、白扣一次钱」判断：支付退款退改、库存票务余量、退订黑名单、Redis 频控、营业状态闭园都是 Fail-Closed，天气保守降级，地图路线降级并标注不确定性，硬约束评估超时则降级为候选清单、不给行程。事件 Envelope 里除了通用字段还多了 itinerary_id、booking_id 与 poi_id，原因码新增了搜索相关的三个：搜索预算耗尽、无可行解、被剪枝到上限。

本章要点

评测闭环包含黄金行程集、资源沙箱、故障注入与在线 A/B 四层常规手段，外加本章新增的搜索专项评测：给定候选集与约束，统计剪枝后候选数、评估次数、可行解产出率与是否触发预算耗尽。容量估算假设日会话 50 万、峰值系数 5、平均 4 轮 8 次工具调用、预订转化 5%、单次输入 5,000 token 单次输出 800 token：峰值会话 29 QPS、峰值 LLM 调用 116 QPS、峰值工具调用 232 QPS、其中资源查询约 139 QPS、峰值预订写约 12 QPS；日合计 token 116 亿，日 LLM 成本约 ¥32,800，约合 98 万元一个月。存储合计约 23.5GB 一天、约 8.6TB 一年，时间矩阵缓存约 32MB。结论是瓶颈在 LLM 成本与资源查询，而预订写只有 12 QPS，但写操作虽少，一次错误的代价是查询的一万倍。

思考笔记

「搜索专项评测」是本章特有的评测维度：规划质量不只由「最终行程好不好」衡量，还由「花了多少评估找到它」衡量。同样一个好行程，用 5,000 次评估找到的和用 500 次找到的，是两个系统——后者才能扛住峰值流量。所以这四个数必须进回归门禁，而不是只在压测时看一眼。

评测闭环

  • 黄金行程集：需求 + 期望约束 + 可行路线。
  • 资源沙箱：模拟航班、酒店、票务、天气、闭园，覆盖售罄、超时、价格变动、重复提交。
  • 故障注入：航班延误、台风闭园、预约余票归零、支付超时。
  • 搜索专项评测（本章新增）：给定候选集与约束，统计剪枝后候选数、评估次数、可行解产出率、是否触发预算耗尽。
  • 在线 A/B / Holdout：验证采纳率、转化率与客诉率；决策快照、工具轨迹、原因码与结果回流，用于约束权重、阈值与策略优化。

6.4 工程落地与规则护栏

第四段 · 工程落地与护栏这一段回答：方法论在文旅链路上怎么一环一环接住——规划、预订、重排各自的护栏，以及四条轨道的时间预算。

6.4.1 端到端链路与门控路由护栏

本章要点

文旅的端到端链路从用户请求或旅中事件经 Gateway 的鉴权、租户与限流，到 Intent Router 分流规划、预订、伴游、问数与营销，再进 Planner 与 Agent Orchestrator：加载槽位与行程版本、按预算定 K 做候选召回、单点硬约束预筛、组合优化或影响图重排并带评估预算、经 Tool Gateway 走白名单与 Schema 与幂等、高风险变更走用户确认或审批，最后资源服务执行、结果校验与回复、事件审计与归因。门控护栏五条：快慢分离，意图置信度低就追问，高风险意图强制进入工作流，租户隔离，以及规划类请求必须带「行程长度 × 每天点数」的槽位，否则无法估搜索预算。

文旅链路图上最该盯的三行是「按预算定 K」「硬约束预筛」「带评估预算」：前两行决定搜不搜得到，第三行决定来不来得及。三行都在 Planner 内部——所以 Planner 不是「一次 LLM 调用」，而是一套有明确时间预算的搜索系统。这一点如果搞错，整个架构的预算表就全是错的。

6.4.2 行程规划与预订写操作护栏

本章要点

行程规划护栏九条：硬约束优先，营业、余票、交通、天气、体力、预算全过；K 按预算倒推不按召回率正推；评估预算设硬限，超出即早停返回当前最优可行解；时间矩阵区域级降维且精度下降要在答案里标注；每日缓冲要留用餐休息与机动；已确认项重排不可静默修改；无解时让用户选择而不硬凑，「明确告知无解」是合法输出；预算给区间不给单点假精确；校验依据随行程输出，每个点附校验结果与查询时点。预订与写操作护栏八条：先预占后支付且预占带 TTL、支付前续期加「支付中」状态加回收跳过来消除 TTL 竞态、支付前复检价格与库存、所有写操作用幂等键与状态机条件更新、写超时先查单不盲目重试、高金额与非标退改转人工、多段订单失败按 Saga 逆序补偿、定时对账预占支付确认与退款。

思考笔记

「明确告知无解」这条排在护栏清单里而不是被排除掉，是这一节最重要的判断。硬凑出来的行程——闭园的景点、过期的余票、超出预算的门票——每一个都会在旅途中变成一次客诉。所以搜索系统的降级顺序应该是先降质量、最后降可行性，因为可行性是这个产品唯一不可妥协的东西。

  • 支付前续期 + 「支付中」状态 + 回收跳过（消除 TTL 竞态）。
  • 支付前复检价格 / 库存。
  • 所有写操作用幂等键 + 状态机条件更新。
  • 写超时先查单，不盲目重试。
  • 高金额 / 非标退改转人工。
  • 多段订单失败按 Saga 逆序补偿。
  • 定时对账：预占、支付、确认、退款。

6.4.3 重排护栏与上下文工具护栏

本章要点

重排护栏七条：事件驱动不做全量轮询；用影响图定位受影响项且必须有「不传播」规则；局部重排不重算未受影响项；生成至少两个方案并比较成本与可行性；涉及费用变化必须由用户确认；合并通知避免轰炸；执行失败回滚并给备选。上下文与工具护栏六条：原子组裁剪并配对校验；候选 POI 列表按通过率裁剪而不是按 top-k 截断；槽位锁定行程、预订、偏好与已执行动作；工具声明副作用、超时、重试、幂等与权限；查询结果不得直接作为写操作依据；敏感信息脱敏。

思考笔记

「候选 POI 列表按通过率裁剪，而不是按 top-k 截断」这一条是本章的特色护栏：别的系统裁上下文是按 token 从后往前截，而文旅必须按硬约束通过率裁——被截掉的那部分大概率本来就过不了闸。这个差别同样一条工程动作，在两个系统里的收益差了十几倍。

重排护栏

  • 事件驱动，不做全量轮询。
  • 影响图定位受影响项，且必须有「不传播」规则（旅中事件驱动重排）。
  • 局部重排，不重算未受影响项。
  • 生成至少两个方案，比较成本与可行性。
  • 涉及费用变化必须用户确认。
  • 合并通知，避免轰炸。
  • 执行失败回滚并给备选。

上下文与工具护栏

  • 原子组裁剪，配对校验。
  • 候选 POI 列表按通过率裁剪（不是按 top-k 截断）。
  • 槽位锁定行程、预订、偏好、已执行动作。
  • 工具声明副作用、超时、重试、幂等、权限。
  • 查询结果不得直接作为写操作依据。
  • 敏感信息脱敏。

6.4.4 降级熔断与延迟预算

本章要点

降级与熔断的执行动作是：资金、库存与营业状态 Fail-Closed；地图与天气保守降级并提示不确定性；生成与推荐用模板或基础列表兜底；硬约束评估超时降级为候选清单，不给行程；高频抖动依赖配熔断器；降级打标 `degraded` 加 `fallback_mode` 加 `reason_code`。延迟预算是本章唯一的时间口径来源，分四条轨道：规划轨道 P95 小于 15 秒，七段里单点硬约束预筛 400ms、组合评估 8 秒、LLM 生成说明 2 秒；伴游轨道 P95 小于 1.5 秒，五段里营业与排队预约状态 300ms、LLM 生成短答 500ms；预订写轨道预占创建 200ms、支付 500ms、退改 500ms，全部写超时先查单；重排轨道 P95 小于 30 秒，受影响项重新评估 5 秒、多方案生成 10 秒、用户确认异步最长 24 小时后转保守执行。

思考笔记

四条轨道的时间预算是同一个方法论：每一步都要有「超时后用户看到什么」的答案，而不是「超时了报错」。最反直觉的是伴游轨道——结构化列表（距离、耗时、是否开放）比一段生成的散文更快也更有用，在 1.5 秒的预算里，生成散文是最不该花的钱。

6.5 端到端案例

第五段 · 端到端案例这一段回答：一次真实的航班延误怎么触发重排，以及搜索预算不足时三条路径该怎么排序。

6.5.1 案例：航班延误 4 小时后的行程重排

本章要点

背景是用户原定 14:00 航班、18:00 入住酒店、次日 09:00 景区预约入园，航班延误到 18:00 起飞。七步走完：事件接入由 flight.status.changed 触发并关联 itinerary_id 与后续预订；影响分析按传播规则判定——机场接送、酒店入住、晚餐、次日预约传播，次日早餐与美食推荐不传播，受影响 4 项而不是全行程 20 项；只读查询航班新时刻、酒店最晚入住政策、接送运力与景区次日余票；生成方案，组合数 3⁴ 即 81 种秒级算完，方案 A 改约 22:30 接送并保留房间、景区改约次日 11:00，方案 B 取消当晚酒店改住机场附近；成本与确认是 A 接送加 60 元、景区改约免费，B 产生酒店取消损失，涉及费用变化所以只推送一次并等待用户确认；确认后以幂等键锁定接送与景区新时段并更新酒店入住备注，失败则回滚并给备选；触达合并成一条通知，只在有新变更时再提醒。

思考笔记

「受影响 4 项 vs 20 项」是本章最重要的一个数：它把重排的组合数从 3²⁰ 降到 3⁴，从 35 亿种变成 81 种。如果影响图没有「不传播」规则，这一步就退化成 20 项全排——算法再强也算不出来，而且用户已确认的酒店入住时间会被改掉。数字上省了五个数量级，性质上是从「不可行」变成「可行」。

案例：航班延误 4 小时后的行程重排

背景：用户原定 14:00 航班，18:00 入住酒店，次日 09:00 景区预约入园。航班状态变更为延误至 18:00 起飞。

  1. 事件接入：flight.status.changed 触发重排，关联 itinerary_id 与后续预订。
  2. 影响分析：机场接送需后移；酒店入住变为 22:00 后；次日 09:00 预约可能受疲劳影响；晚餐时间被压缩。按传播规则判定：接送 → 酒店入住 → 晚餐 → 次日预约 传播；次日早餐、次日的美食推荐 不传播（软依赖与偏好耦合）→ 受影响 4 项，不是全行程 20 项。
  3. 只读查询：航班新时刻、酒店最晚入住政策、接送运力、景区次日各时段余票。
  4. 生成方案（组合数 3⁴ = 81 种，秒级算完）：
    • 方案 A：改约 22:30 接送，酒店确认保留房间，景区改约次日 11:00。
    • 方案 B：取消当晚酒店，改住机场附近，次日直接前往景区。
  5. 成本与确认：方案 A 接送 +60 元、景区改约免费；方案 B 产生酒店取消损失。涉及费用变化，推送一次并等待用户确认。
  6. 执行：确认后以幂等键锁定接送与景区新时段，更新酒店入住备注；失败则回滚并给备选。
  7. 触达：合并为一条通知，避免重复轰炸；后续仅在有新变更时提醒。

常见失败：未先查余票就承诺改约 → BIZ_SOLD_OUT；支付超时直接重试 → 可能重复扣款；酒店房间未预占 → 到店无房。

第 2 步的「受影响 4 项 vs 20 项」是本章最重要的一个数：它把重排的组合数从 3²⁰ 降到 3⁴，从 35 亿种变成 81 种。如果影响图没有「不传播」规则，这一步就会退化成 20 项全排——算法再强也算不出来，而且用户已确认的酒店入住时间会被改掉。

6.5.2 变体：多日规划、旅中伴游与长周期归因

本章要点

多日行程规划的需求是「带老人小孩，5 天 4 晚，预算 6000，不赶路，避开雨天户外」，六步走：槽位锁定人数结构、日期、预算、节奏与偏好，并把「带老人小孩」标记为硬约束而非偏好；候选召回按亲子、人文、自然并按体力分级，K 按 5 天乘 3 点倒推；六项硬约束全过；组合优化每天 2 到 3 个点并预留午休与机动；每天至少一个室内备选；输出时间轴、交通、预约提醒、预算分项与每个点的校验依据。旅中伴游的需求是「现在在西湖边，带孩子，附近有什么能去的」，五步：LBS 召回 Top-8 而不是 Top-20、实时营业与排队与预约校验、路线耗时与天气提醒、输出 3 个结构化选项加距离耗时注意事项与查询时点、不推荐闭园封路与极端天气路线。长周期营销归因的场景是用户 20 天前看过三亚行程今天下单，用 30 天窗口并区分直接与辅助转化，用 Holdout 算真实增量，扣除券补贴与渠道佣金算净贡献。

思考笔记

三个变体共同暴露的一件事是「同一个参数不能驱动两条轨道」：规划 15 秒、Top-20、可生成解释；伴游 1.5 秒、Top-8、只能给结构化列表。用同一个「召回 Top-K」去驱动两条轨道，是伴游做不快的最常见原因。伴游那条推论尤其值得记：归因窗口按决策周期分布来定，30 天对提前很久订的用户仍然不够。

变体 A：多日行程规划

需求：「带老人小孩，5 天 4 晚，预算 6000，不赶路，避开雨天户外。」

  1. 槽位：人数结构、日期、预算、节奏、偏好；「带老人小孩」被标记为硬约束而非偏好。
  2. 候选召回：亲子 / 人文 / 自然，按体力分级；K 按 5 天 × 3 点倒推。
  3. 硬约束：营业、预约、交通、天气、体力、预算，六项全过。
  4. 组合优化：每天 2–3 个点，预留午休与机动。
  5. 天气备选：每天至少一个室内方案。
  6. 输出：时间轴 + 交通 + 预约提醒 + 预算分项 + 每个点的校验依据。

这个需求最狠的地方：5 天 × 3 点的组合空间是 C(200,3)⁵ = 3.9 × 10²⁴——比时空搜索放大：候选、可行解与剪枝的 3 天例子还大 6 个数量级。所以「5 天行程」必须靠分天求解（每天独立求最优 + 天间衔接约束），而不是全局穷举。

变体 B：旅中伴游

需求：「现在在西湖边，带孩子，附近有什么能去的？」

  1. LBS 召回附近 POI（Top-8，不是 Top-20——伴游只有 1.5 秒预算）。
  2. 实时营业 / 排队 / 预约校验；无法确认的点不推荐。
  3. 路线耗时与天气提醒。
  4. 输出：3 个结构化选项 + 距离 + 耗时 + 注意事项 + 查询时点（不生成散文）。
  5. 安全：不推荐闭园 / 封路 / 极端天气路线；带小孩时优先有洗手间与休息点的选项。

伴游与规划用同一套候选召回逻辑，但预算差 10 倍：规划 15 秒、Top-20、可生成解释；伴游 1.5 秒、Top-8、只能给结构化列表。用同一个「召回 Top-K」的参数去驱动两条轨道，是伴游做不快的最常见原因。

变体 C：长周期营销归因

场景：用户 20 天前看过三亚行程，今天下单。

  • 归因窗口 30 天，区分直接与辅助转化。
  • Holdout 计算真实增量。
  • 扣除券补贴与渠道佣金，算净贡献。
  • 快信号熔断高退订变体。

文旅营销的归因有一个别的章没有的陷阱：用户今天下单的可能是上个月的行程（提前很久订好），也可能是今天的最后一刻。30 天窗口对前者仍然不够。 所以文旅的归因窗口必须按决策周期分布来定，而不是拍一个 30 天。

6.5.3 搜索预算取舍、故障兜底、扩容与复盘

本章要点

变体 D 是一次真实的容量危机：规划请求量涨 3 倍（20 万到 60 万一天），规划 P95 从 12 秒涨到 19 秒。三条路的账算清楚：加机器每天多 ¥26,240、可行解产出率 95% 保持不变；下调 K 从 20 到 8 每天省 ¥4,608 但产出率从 95% 掉到 60%；热门行程结果缓存命中 40% 的请求、每天省 24 万乘 4 次乘 5,000 token 即 48 亿 token 约 ¥9,600、可行解一个不少。决策顺序是先做无损的结果缓存，再加机器，最后才考虑降 K。故障与兜底补三条：预占 TTL 与支付竞态用支付前续期加回收跳过支付中，硬约束评估超时降级为候选清单，重排时备选资源也售罄就给出取消该点加退款的方案而不是重试到成功。扩容 10 倍的先坏顺序是搜索预算（最先坏，且是非线性）、资源查询、LLM 配额、预占、重排事件、地图天气、归因存储、成本。

思考笔记

「降 K 是最后手段，不是第一手段」，因为它的代价不是「行程差一点」而是「35% 的请求给不出行程」——而给不出行程的用户不会投诉，只会走掉。所以搜索系统的降级顺序应该是先降质量、最后降可行性，因为可行性是这个产品唯一不可妥协的东西。而扩容那一位的非线性也不是 QPS，是可行解产出率。

变体 D：时空搜索预算与 K 值取舍

场景：规划请求量涨了 3 倍（20 万 → 60 万 / 天），规划 P95 从 12s 涨到 19s。怎么办？

先算清楚三条路的账（规划部分日成本基线 ¥13,120）：

方案增量成本 / 天可行解产出率性质
A 加机器+¥26,24095% → 95%（不变）贵但无损
B 下调 K（20 → 8）−¥4,608（规划输入 −19.2%）95% → 60%省得少，损得多
C 热门行程结果缓存−¥9,60095% → 95%（不变）省且无损

C 的算法：命中 40% 的规划请求（60 万 × 40% = 24 万 / 天）直接返回预计算结果，省 24 万 × 4 次 × 5,000 token = 48 亿 token = ¥9,600 / 天，且一个可行解都没损失。

决策顺序：

1. 先做结果缓存（C）——无损且更便宜
2. 再加机器（A）——贵但无损
3. 最后才考虑降 K（B）——有损，且损的是可行性

降 K 是最后手段，不是第一手段，因为它的代价不是「行程差一点」而是「35% 的请求给不出行程」——而给不出行程的用户不会投诉，只会走掉。这是本章的一条反直觉但极其重要的结论：搜索系统的降级顺序应该是「先降质量、最后降可行性」，因为可行性是这个产品唯一不可妥协的东西。

思考笔记

作战手册里最该抄进自己项目文档的是 S0 的第三条自检：「行程多长？每天几个点？」——各给一个带来源的数值，因为它决定搜索空间。大多数文旅项目的评审都卡在「功能上不上线」，而这条自检的作用是在写第一行代码之前就暴露搜索空间的量级，避免三个月后才发现 P95 根本守不住。

高频追问

  • 如何防止机酒票超售？ → 资源服务原子扣减 + 预占 TTL + 回收跳过「支付中」 + 幂等键 + 定时对账。
  • 如何在航班延误后快速重排？ → 事件驱动影响图（带不传播规则）+ 实时余票 / 政策查询 + 备选方案 + 用户确认。
  • 行程规划如何避免绕路？ → 时间矩阵（区域级降维）+ 时间窗约束 + 路线排序 + 每日缓冲。
  • **规划为什么会超时？ → 候选组合爆炸。要查三件事：K 值是不是按预算定的、剪枝漏斗有没有生效、评估预算有没有硬限与早停。
  • 召回多少候选合适？ → 按评估预算倒推：K ≤ 单点评估预算 ÷ (每天点数 × 剪枝保留率)，而不是按召回率正推。
  • 长决策周期如何归因？ → 长窗口（按决策周期分布定）+ Holdout + 辅助转化 + 扣除补贴与渠道成本。
  • 伴游如何做到低延迟？ → 实时工具 + Top-8 而非 Top-20 + 精简上下文 + 结构化列表 + 缓存热点状态。
  • 依赖超时怎么降级？ → 资金 / 库存 / 营业状态 Fail-Closed；地图 / 天气保守降级并提示不确定性；硬约束评估超时 → 给候选清单，不给行程。
  • 价格变了怎么办？ → 支付前复检，超阈值让用户确认。
  • 预占过期怎么办？ → TTL 回收，重新预占或给备选；回收必须跳过「支付中」的持有。
  • 重排会不会改掉已确认项？ → 局部重排 + 版本 + 确认。
  • 如何评估文旅 Agent？ → 黄金行程 + 资源沙箱 + 故障注入 + 搜索专项评测 + 在线 A/B。
  • 紧急安全事件如何触达？ → 可突破普通频控，但必须去重与分级。

总结把这一章收成一页纸：结论、边界，以及下一章要解决什么。

6.7.1 一句话总结

思考笔记

文旅 Agent 的第一性问题不是「推荐得准不准」，而是「评估预算能覆盖多少分支」：先量行程长度与每天点数，再按预算倒推 K 值，把硬约束前置、把资源锁进预占、把影响图的「不传播」规则写死——剩下的才轮到模型去做表达。

6.7.2 本章结论

  1. 搜索空间靠剪枝，不靠召回。3 天每天 3 点是 2.26×10¹⁸ 种组合，评估预算只有 5,000 次单点与 200 次组合，必须剪掉 15 个数量级。K 从 200 降到 84，省 58% 的上下文与预筛时间，可行解一个不少。
  2. 硬约束前置，超时就不给行程。先可行后好看：闭园的景点、过期的余票、超预算的门票，每一个都会在旅途中变成一次客诉。硬约束评估超时正确的产品形态是候选清单加提示，不是一份宽松的行程。
  3. 资源服务是唯一事实源，写操作不复用查询结果。缓存里的「有房」可能已过期 40 秒，查询必须带查询时点；「30 秒前查到有房」不能作为 30 秒后扣款的理由。缓存与索引全是投影，投影不能当承诺。
  4. 预占与支付之间有一道竞态，三道防护都要上。TTL 900 秒、支付 P99 800 毫秒、峰值预占 3,000 QPS，竞态率约 0.09%，日订单 2.5 万单就是每天 22 单可能超售、约 ¥26,400 损失。支付前续期、「支付中」状态跳过回收、超时先查单。
  5. 影响图的价值在于切出不相关的项。全行程 20 项重排是 3.5×10⁹ 种，只重排受影响的 8 项是 6,561 种，降 5 个数量级。软时间依赖与偏好耦合不传播——航班晚 4 小时不该把用户的美食偏好也重排一遍。

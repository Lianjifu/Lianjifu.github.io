问数 Agent——从模糊提问到可信结论

发表于2026-11-26 分类于AI Agent 系统设计

问数 Agent（ChatBI / Text-to-SQL）把自然语言问题转成可信 SQL，再转成可解释的数据结论。难点不在「生成 SQL」，而在语义歧义、Schema 过大、结果集过大、权限越界与结论解读。本章围绕语义层与指标治理、Schema 裁剪、SQL 校验与权限重写、结果集下推、沙箱与资源护栏、归因与可信表达展开。

思考维度 内容
引导思考 展开
它为什么存在
  • AI 会写 SQL，但「写出来」和「敢拿去用」之间隔着一整套信任机制
  • 自然语言到 SQL 的转换只解决了问题的一小半——剩下的全是「这个答案能不能信」
  • 口径不一致、越权读取、结果集被截断，这三类错误都不会报错，却会变成一个看起来合理的数字
它解决什么问题
  • 把「自然语言」翻译成「数据库语义」
  • 歧义、Schema 规模、结果集规模、权限边界，四道坎依次挡在可信答案之前
  • 每一道坎的解法都不是「让模型更聪明」，而是把约束固化到模型之外

  • 语义层与指标治理是整个系统的坐标系
  • 指标的标准表达式、版本与作用域，决定了所有答案能否互认
  • 下游的 Schema 裁剪、SQL 校验、缓存指纹、审计记录全部挂在它上面
它如何工作
  • 结果集是本章最贵的量
  • 一次查询可能回传几十万行，明细直返可达 21.6 亿 token
  • 统计下推与样本分离既是成本优化，也是结论完整性的保证

1.1 问数 Agent 是什么

第一段 · 问数 Agent 是什么这一段回答：问数 Agent 究竟是什么、给谁用、边界划在哪里，以及哪些决策一旦做错就要停机迁移。

1.1.1 定义与能力层次

本章要点

问数 Agent 不是「一个更聪明的 SQL 生成器」，而是一条从提问到可信答案的受控流水线。它接收自然语言问题，完成意图澄清、指标映射、Schema 裁剪、SQL 生成与校验、沙箱执行、结果校验、图表路由与结论表达。三个能力层次从取数到归因，难度与链路长度同步上升。

思考笔记

定义句里最关键的四个字是「受控流水线」——它意味着系统的价值不在生成能力，而在拦截能力。如果读完只记住了「NL2SQL」，理解还差一层：真正难的不是把话变成 SQL，而是把每种错误拦在答案之前。

定义：问数 AI Agent 是面向数据分析场景的智能体系统。它接收自然语言问题，完成意图澄清、指标映射、Schema 裁剪、SQL 生成与校验、沙箱执行、结果校验、图表路由与结论表达，最终给出可追溯、可核验、可解释的数据答案。

它不是「一个更聪明的 SQL 生成器」，而是一条从提问到可信答案的受控流水线：每一步都可能出错，系统的价值在于把每种错误拦在答案之前，而不是指望模型一次就对。

三个能力层次：

层次回答的问题典型输出难度本章覆盖
L1 取数是多少明细 / 聚合结果、图表中全链路
L2 分析怎么变同比环比、趋势、分组对比较高归因分析
L3 归因 / 建议为什么、怎么办贡献度拆解、原因假设、下一步高归因分析、净营收环比下降归因

1.1.2 用户、场景与与传统 BI 的关系

本章要点

业务分析师、运营、管理层、数据团队是四类主要用户，风险各不相同。与传统 BI 不是替代关系而是分工关系：固定报表负责高频、已知、口径已定的需求，问数 Agent 负责长尾、探索、口径待定的部分。

思考笔记

这一节最该带走的是那句分工：凡是能固化成报表的需求，就不该留在问数链路里——报表是零成本、零幻觉、零越权的。很多团队把本该做报表的问题都丢给 Agent，等于把一个本可零风险解决的问题做成了高风险问题。

典型用户与场景：

1.1.3 边界、指标与不可逆决策

本章要点

问数 Agent 负责问题理解、口径、Schema、SQL、权限、图表六件事，不负责埋点、数仓建模、身份认证等基础能力。核心指标分正确、体验、安全、成本、质量五类。另有七项不可逆决策，做错了要停机迁移，而不是发个版本。

思考笔记

不可逆清单是这一段的分量所在。指标的标准表达式、语义层的命名模型、权限的强制技术形态、缓存指纹的维度——这四项任何一项改动都会让历史答案失效。真正值得记住的是那句对照：它们是单向门，决策时要多评审、做原型、留迁移方案；其余是双向门，可以快速试错。

1.2 核心矛盾与设计原则

第二段 · 核心矛盾这一段回答：自然语言与数据库语义之间到底隔着什么，为什么这六条原则在冲突时说了算。

1.2.1 本质与六条章级原则

本章要点

本质矛盾是自然语言的模糊性与数据库语义的精确性之间那道鸿沟，再叠加 LLM 的概率生成与 SQL 的确定性执行。六条章级原则规定了冲突时以谁为准：口径在语义层、权限在执行层、先下推再回传、结论可回溯、不确定就降级、读操作没有回滚所以防线前置。

思考笔记

六条原则里最容易被违反的是第一条和第二条，因为它们都要求「把约束放在模型外面」。写 Prompt 让模型「只查本部门」是软的，注入内容可以覆盖它；查询重写、策略层、视图是硬的。一个很实用的自检：如果某条护栏需要靠模型自觉执行，它就不是护栏。

本质：问数 Agent 的核心矛盾，是「自然语言的模糊性」与「数据库语义的精确性」之间的鸿沟，再叠加「LLM 的概率生成」与「SQL 的确定性执行」。模型可以猜，账不能猜——而问数 Agent 恰好是在「猜出来的 SQL」上直接驱动生产数仓。

六条章级原则（贯穿全章，冲突时以这六条为准）：

  1. 口径在语义层，不在 Prompt 里——模型只能引用标准指标，不能自创公式。「模型算出来的」不是口径，「指标卡里写着的」才是口径。
  2. 权限在执行层强制，不靠模型自觉——查询重写、视图、策略层是硬约束，Prompt 里的「请只查本部门」是软建议。Prompt 会被注入内容覆盖，策略层不会。
  3. 先下推再回传，绝不靠截断控制上下文——统计在 SQL 里算完，明细只回传样本。截断省的是 token，丢的是分布。
  4. 结论必须可回溯到 SQL 与口径——没有可回溯 SQL 的答案不可信；没有口径的答案不可用。
  5. 不确定就降级为「给 SQL 不给结论」——检索不足、结果异常、口径冲突时，宁可只交 SQL 和原始结果，也不要编一个结论。「不知道」必须能被识别，不能被润色掉。
  6. 读操作没有回滚，所以防线必须前置——问数不写业务库，但会泄露数据、打爆数仓、给出错误结论。这三件事都没有「撤销」按钮，因此校验必须发生在执行之前，而不是之后。

1.2.2 三个不等式与三个放大器

本章要点

问数这条链上有三组不等式划定边界：结果集行数远超上下文能装的行数、Schema 规模远超 Prompt 能承载的规模、自然语言歧义远超 SQL 的确定性。三个放大器量化了代价：结果集放大可达 10 万倍，Schema 放大 1333 倍，口径放大最难察觉。

思考笔记

放大器这一段要看的是量级差：结果集放大 10 万倍、Schema 放大 1333 倍，两者差两个数量级。这直接决定了优化优先级——先削结果集，再削 Schema。如果反过来做，你会花大量力气在 Schema 提示词上，而真正会爆的那一头原封不动。

三个不等式：

结果集行数    >>  上下文能装的行数     → 靠下推聚合，不靠截断
Schema 规模   >>  Prompt 能承载的规模  → 靠裁剪 + 分层索引
自然语言歧义  >>  SQL 的确定性         → 靠语义层 + 澄清 + 校验

三个放大器（本章最贵的量都藏在这里）：

放大器说明后果量化
结果集放大一次查询可能回传几十万行；行放大 × 列放大上下文撑爆 / 结论失真明细直返 21.6 亿 token/题；下推后 2.16 万，10 万倍（结果集治理与下推）
Schema 放大5000 张表的元数据全进 Prompt选错表 + 根本放不下全量 200 万 token；裁剪后 1500，1333 倍（Schema 裁剪）
口径放大同一个「营收」在多个部门有多种口径答案无法互认、结论对不上会口径版本 × 作用域组合，冲突必须显式裁决（口径冲突与作用域）

本章的放大器方向值得单独记：别的系统放大的是数据量，问数章的放大器是结果集——它是唯一一个「答案本身太大，把模型挤爆」的架构：进上下文的是 Schema，中间是 SQL，出上下文的是结果集，三头都在挤压同一个窗口。

1.2.3 四层正确性与八组关键矛盾

本章要点

正确性分口径、SQL、权限、解读四层，必须分开保证。八组矛盾给每一条标注了默认策略与反转条件，比如「自动化 vs 资金安全」默认阈值加审批，低金额可全自动。

思考笔记

原文只列了四层，漏掉了「结果完整」这一层——它恰恰是结果集放大最直接的后果，也是最容易被忽略的一类错误。补进去之后，问数的正确性就是「口径 + SQL + 权限 + 结果完整 + 解读」五层叠加。这个补充值得记住，因为它把最隐蔽的错误从视野里捞了出来。

四层正确性（必须分开保证，缺一层就有一类错答案）：

层次要求保障手段典型漏法
口径正确指标、时间、过滤与业务定义一致语义层固化 + 版本 + 作用域SQL 语法全对，指标算错了
SQL 正确语法、Join、聚合、方言AST 校验 + 白名单 + 自愈笛卡尔积、少 Join、枚举写错
权限正确行 / 列 / 租户 / 密级查询重写 + 视图 + 策略层只靠 Prompt 提醒模型
解读正确不过度推断、不混淆相关与因果归因规范 + 引用 + 人工复核把相关性写成因果

为什么「生成对了 SQL」还不够：

  • 口径可能错：SQL 语法正确，但指标定义不是业务要的。
  • 权限可能错：查到了不该看的数据。
  • 性能可能错：结果对，但打爆数仓。
  • 结果可能残：SQL 对，但只回传了前 100 行，用户以为这就是全量（结果集治理与下推）。
  • 解读可能错：数据对，结论错。

结论：问数 Agent 的正确性是「口径 + SQL + 权限 + 结果完整 + 解读」五层叠加。原版只列了四层，漏掉了「结果完整」这一层——它恰恰是本章放大器最直接的后果，也是最容易被忽略的一类错误。

1.2.4 失败模式、信任分级与威胁模型

本章要点

1.3.3 语义层与口径冲突裁决

本章要点

1.3.4 Schema 裁剪、问题澄清与澄清成本判据

本章要点

Schema 裁剪用三层漏斗把 5000 张表收到 5 张，全量 200 万 token 裁到 1500，放大 1333 倍——不裁剪不是「贵一点」，而是根本不可行。问题分六类，其中口径咨询与明细导出必须从主链路分流。澄清成本约 ¥0.004 加 1.5 秒，错误成本至少 1 人天，所以口径不确定时追问永远划算。

思考笔记

澄清成本对比是本章最实用的一段推导，但结论有两个而不是一个：追问几乎零成本所以该追；但追问有次数上限，超过两次用户会转人工，所以必须一次问全所有必要槽位，而不是挤牙膏。

Schema 裁剪（Schema Linking）

本节是 Schema 裁剪的权威版，语义层护栏只引用。

元数据维度：

维度用途
表 / 列注释语义匹配
主外键Join 路径
枚举值抽样过滤条件
基数判断聚合粒度
新鲜度避免用过期表
PII 标签权限与脱敏
血缘选上游 / 下游表
业务域标签域路由

检索策略（五路并行，合并去重）：

  1. 语义检索：问题 → 表 / 列描述向量召回。
  2. 关键词检索：专有名词、编号、字段名精确匹配。
  3. 历史 Join 路径：相似问题用过的关系（命中率最高的一路）。
  4. 相似问题缓存：命中直接复用表集合。
  5. 业务域路由：先定位域，再在域内检索。

裁剪原则：

  • 只暴露 Top-K 表与关键列，降低噪音。
  • 大表只给常用列与分区键。
  • 枚举值给抽样，不给全量。
  • 敏感列默认不暴露给模型（不是「暴露了再要求模型别用」）。

Schema 放大有多严重（量化）：

全量 Schema = 5000 张表 × (表级描述 100 token + 15 列 × 20 token)
            = 5000 × 400 = 200 万 token
上下文窗口 ≈ 200K token → 放不下，且噪声会让召回精度崩塌

裁剪后 = Top-5 表 × (100 + 10 列 × 20) = 5 × 300 = 1500 token
放大倍数 = 200 万 / 1500 = 1333 倍

1333 倍这个数字要说明两件事：第一，不裁剪不是「贵一点」，而是「根本不可行」——200 万 token 远超任何模型的上下文窗口；第二，裁剪不只是省 token，它同时是召回精度的手段：5000 张表进 Prompt，Top-1 命中率会低到无法使用。Schema 裁剪是可行性需求，不是成本优化项。

裁剪的三层漏斗：

层手段典型收敛比
域路由先定业务域5000 → 200
表召回向量 + 关键词 + 历史路径200 → 20
列裁剪关键列 + 分区键 + 抽样枚举20 表 × 40 列 → 5 表 × 10 列

问题分类与澄清

类型示例路由
简单取数「昨天华东订单量」快路径，直接生成
多维分析「各渠道转化率对比」标准 SQL + 图表
归因「为什么下降」慢路径，多步分析
口径咨询「净营收怎么算」查指标卡，不查库
明细导出「导出上周全部订单」走独立导出审批链路
闲聊 / 越界「帮我写周报」拒绝或转人工

两类问题必须被识别出来并从主链路分流：口径咨询根本不该生成 SQL（查指标卡即可，省掉整个数仓链路）；明细导出根本不该留在问数链路里（结果集不可控、权限与合规要求不同）。把它们混在同一条流水线里，是很多问数系统后期失控的根因。

何时追问：

  • 指标不明确（营收 vs 净营收）。
  • 时间范围缺失或模糊（「最近」）。
  • 实体不明确（「华东」是否含某省）。
  • 口径冲突（多版本 / 多作用域）。
  • 权限范围影响结果。

何时用默认值：

  • 低风险、可撤销、有明确惯例。
  • 默认值必须在答案中显著注明。

多轮澄清：保留 confirmed_slots（指标、时间、实体、过滤、粒度），后续轮次复用，避免重复问。

澄清成本 vs 错误成本

追问一次的成本是可量化的，而错误答案的成本往往不可量化——这正是必须写进方案的判据。

澄清成本：

项数值说明
额外 LLM 调用1 次输入 ~1000 token（已确认槽位 + 问题）
token 成本≈ 2,000 token按输入 ¥2 / 百万计，约 ¥0.004
额外延迟+1.5s一次生成调用
用户耐心消耗1 次追问 2 次以上，转人工率显著上升
口径风险0槽位确认后写入，后续复用

错误答案的成本：

项量级说明
直接成本视决策金额而定错误的投放 / 库存 / 人力决策
信任成本高且不可逆一次错答被识破，采纳率长期下降
复核成本每次 +1 人天分析师复核 + 沟通 + 纠正
权限成本不可估越权口径泄露属于合规事故

判据：

追问成本（¥0.004 + 1.5s）  <<  错误成本（≥ 1 人天复核 + 决策损失 + 信任损失）
                                    → 追问

口径可由作用域唯一确定                →  不追问，直接答 + 注明版本

澄清决策链路：

追问一次的成本（实测）
  → 2,000 token + 1.5s + 一次用户耐心（≈ ¥0.004）
  → 对照：错误答案 ≥ 1 人天复核 + 决策损失 + 信任损失（不可逆）
  → 结论：口径不确定时，追问永远划算
  → 但上限 1 次（同一问题）—— 追问 2 次以上，用户会直接转人工
  → 一次问全所有必要槽位，不挤牙膏

三个必须记住的推论：

  1. 追问几乎是零成本的：一次追问不到半分钱，而一次错误答案至少一个人天。口径不确定时，追问永远是划算的。
  2. 但追问有次数上限：连续追问 2 次以上，用户会放弃并转人工。所以应当一次问全所有必要槽位，而不是挤牙膏。
  3. 可以用默认值替代追问的只有一种情况：默认值既符合惯例、又被显式注明、且用户能一眼看出并纠正。其余情况都要追问。

1.3.5 SQL 生成、校验与自愈

本章要点

生成阶段用结构化输出约束格式，并强制声明 metrics_used，让下游能在生成阶段就核对口径。校验分拦截与改写两类：语法、语句类型、危险操作、表列白名单是拦截；权限重写、资源改写是改写。自愈只能改「怎么查」，不能改「查什么」。

思考笔记

「自愈只改怎么查、不改查什么」是这一段的红线。重试时可以调时间范围、分区裁剪、Join 顺序，但不得放宽行级权限、不得去掉用户确认过的过滤条件、不得把聚合改回明细全量——放宽语义的自愈会变成权限绕过，这是把可用性问题变成了安全问题。

SQL 生成

Prompt 结构：

System：角色、约束、输出格式、安全规则
Context：指标定义（含版本）、裁剪后 Schema、枚举样本、方言、业务规则
Examples：按问题类型检索的 Few-shot
Question：用户问题 + 已确认槽位
Output：JSON { sql, explanation, assumptions, confidence, metrics_used }

生成约束：

  • 只输出 SELECT / WITH。
  • 禁止 SELECT *，必须显式列。
  • 必须带时间过滤（除非用户明确全量）。
  • 默认带聚合：除非问题明确要明细，否则强制 GROUP BY 或聚合函数（结果集治理与下推）。
  • 自动加 LIMIT。
  • 使用标准 Join，禁止隐式笛卡尔积。
  • 方言适配（MySQL / PostgreSQL / Hive / Spark / ClickHouse）。
  • 必须声明所用指标（metrics_used），供下游做口径核对。

Few-shot 选择：按问题类型（单表、多表、聚合、窗口、同比、贡献度）检索相似样例；样例必须是本方言、本指标版本下验证过的。

metrics_used 是一个成本极低、价值极高的字段：它让下游可以在生成阶段就核对「这个 SQL 用的是不是标准指标口径」，而不是等到结果出来再靠人肉看 SQL。它在错误还没变成一个数字之前就把错误拦下了。

SQL 校验与权限重写

本节是 SQL 校验与权限重写的权威版，生成与校验护栏只引用。

校验内容拦截还是改写

权限重写示例：

-- 原始
SELECT region, SUM(amount) FROM orders GROUP BY region;

-- 重写后（用户仅华东）
SELECT region, SUM(amount) FROM orders
WHERE tenant_id = 42 AND region = 'east'
GROUP BY region;

权限强制链路：

原始 SQL（模型生成）
  → AST 解析（失败即拦截，不给模型解释机会）
  → 语义校验（表列白名单、Join 条件、聚合合法性）
  → 权限重写（行级 WHERE 注入 + 列级白名单裁剪 + 密级掩码）
  → 资源改写（LIMIT 注入、扫描量预估、超阈值改写或拒绝）
  → 方言编译（转为目标引擎可执行计划）
  → 送入只读沙箱执行

为什么必须在执行层：Prompt 里的「请只查本部门」可以被注入或忽略；只有重写 / 视图 / 策略层才是强制约束。而且模型是概率性的——即使 Prompt 写对了，同一输入也可能生成一条漏掉租户条件的 SQL。依赖模型守规矩的系统，迟早会漏一次。

沙箱执行与资源护栏

措施说明参考阈值

独立资源组限制 CPU / 内存 / 并发问数专用队列

最大返回行数与最大扫描量是两个不同的闸：扫描量拦的是「代价高但结果小」的查询（一次全表聚合），返回行数拦的是「代价中等但结果巨大」的查询（明细导出）。只设其中一个，另一个方向就会被打爆。

报错自愈

执行失败
  → 分类错误：语法 / 语义 / 权限 / 资源 / 超时
  → 语法 / 语义：把报错 + 相关 Schema 回填，重新生成
  → 权限：不重试，直接拒绝并提示
  → 资源 / 超时：缩小范围或改写，最多 1 次
  → 超过最大重试（2–3 次）：返回可解释错误或转人工

自愈的安全边界：自愈只能改写「怎么查」，不能改写「查什么」——重试时可以调整时间范围、分区裁剪、Join 顺序、聚合粒度，但不得放宽行级权限、不得去掉用户确认过的过滤条件、不得把聚合改回明细全量。放宽语义的自愈会变成权限绕过。

失败样本沉淀：记录错误 SQL、报错、修正结果，用于优化 Schema 描述与 Few-shot；同时按错误类型统计 Top-N——「枚举写错」占比高说明枚举样本要给全；「表选错」占比高说明域路由有问题。

1.3.6 结果校验与结果集治理

本章要点

结果校验要能区分「无数据」与「过滤错」，空结果绝不能当成答案是 0。结果集治理给出四段漏斗：明细直返 21.6 亿 token、显式列 2.16 亿、截断 1.8 万、统计下推 2.16 万——最后一行是唯一同时可行且结论完整的方案。

思考笔记

这一段有两句话值得单独抄下来：第一，截断与下推的 token 几乎一样（1.8 万 vs 2.16 万，只差 20%），但结论完整性完全不同——截断把订单金额的 P99 从全量分布变成前 100 行的分布；第二，行放大 10,000 倍比列放大 10 倍严重三个数量级，所以治理重心是「别把那么多行带回来」，而不是「少查几列」。

结果校验

校验说明不通过时
行数空结果是否合理区分「无数据」与「过滤错」
列类型数值 / 时间 / 字符串是否符合预期拒绝或降级
空值 / NaN比例是否异常标注
口径一致性分项之和是否等于总计拒绝
异常值同比 / 环比是否超阈值标注 + 提示复核
二次核对关键结论用另一条 SQL 验证降级为只给 SQL
截断检测本次结果是否被截断 / 是否为部分结果标注 + 降低信任级别

空结果处理：区分「确实没有数据」与「过滤条件写错」；后者应触发澄清或自愈。空结果绝不能当成「答案是 0」。

1.3.7 权限、可视化与归因

本章要点

权限分租户、行级、列级、密级、导出、审计六层，强制优先级是策略层 > 查询重写 > 应用层，Prompt 只能辅助。列级权限与 Schema 裁剪联动——敏感列默认不进入给模型的 Schema。归因要区分加法、乘法与结构三种分解，并先做辛普森结构校验。

思考笔记

「敏感列默认不暴露给模型」常被当成优化项，其实它是安全边界：模型看不到的列，就不可能被写进 SQL，等执行层再拦就等于依赖模型不犯错。另一个容易忽略的是辛普森检查——整体退款率上升但每个渠道都在下降，原因是高退款率渠道的占比变了，这时候去「优化」那个渠道，就是让运营去优化一个什么都没做错的渠道。

1.3.8 评测、缓存、成本与容量

本章要点

评测主指标必须是执行准确率，口径正确率单独看，完全匹配率只作回归辅助。缓存指纹必须是四元组：问题、权限、数据版本、语义层版本，缺一维就可能给出过期或越权答案。容量估算给出日 85 亿 token、约 ¥1.93 万，其中结果集占输入 63%。

思考笔记

四元缓存指纹里最容易漏的是数据版本：缓存命中后返回了昨天的分区数据，答案看起来完全正常，只是过时了。而问数的使用者往往不会去核对时间戳，所以过期必须被显式标注，而不是被隐藏。另外「只评 EM 是最常见的评测错误」——同一份结果可以由十几条等价 SQL 得到，EM 会把这些全判错。

1.4.3 结果集、解读与审计

本章要点

结果集护栏有六个执行动作，第 5 步「截断即标注并下调信任级别」最容易被省略也最不能省。结果与解读护栏禁止把相关系数表述为因果。审计要同时留改写前 SQL 与改写后 SQL。

思考笔记

「改写前 SQL」必须留档，因为它是证明「这条 SQL 本来会越权、是我们拦下来的」的唯一证据。只留改写后的 SQL 等于没留审计——事后没人能证明防线生效过。同理，「截断标记缺失一次，就可能产生一个基于前 100 行的业务决策」。

结果集与回传护栏

1.5 端到端案例

第五段 · 端到端案例这一段回答：一个真实的归因问题怎么走完整条链路，以及四个变体分别暴露什么。

1.5.1 案例：净营收环比下降归因

本章要点

一个「为什么本周净营收环比下降 12%」的问题走完整条链路：澄清三个槽位一次问全、语义层解析版本、域路由裁剪到 18 列、权限重写注入租户与区域、贡献度在 SQL 里算完只回传 Top-20。首轮 SQL 因枚举写错结果为空，修正后成功。

思考笔记

这一段最值得记的是贡献度下推那段 SQL 的意义：它把「哪几行贡献最大」变成数据库的一次排序。模型在 960 行上排序会出错，在全量上排序根本做不到；下推之后不仅省 48 倍 token，排序还是精确的。这就是「下推」的通用范式——凡是对结果集全体做一次计算的步骤，都应该下推到 SQL，而不是把结果集交给模型。

案例：净营收环比下降归因

问题：「为什么本周净营收环比下降 12%？」

链路：

  1. 澄清：净营收口径（net_revenue@v2.3，财务口径，含税减退货冲减减折扣补贴）、本周 / 上周口径（自然周 W46 / W45，Asia/Shanghai）、范围（全公司还是某区域）。三个槽位一次问全，不挤牙膏。
  2. 语义层：net_revenue@v2.3 表达式解析；排除测试单、未结算单、内部单；时间口径到「数据截止 2026-11-24 06:00」。
  3. Schema 裁剪：域路由到「交易域」→ 表召回命中 orders / refunds / discounts / channel_dim / region_dim → 列裁剪到 18 列。
  4. 权限：用户只看华东区 → 查询重写注入 tenant_id = 42 AND region = 'east'。
  5. SQL：CTE 计算本期与上期净营收，贡献度在 SQL 里算完，只回传 Top-20 贡献行。
  6. 执行：发现华东区下降 18%，其中渠道 A 下降 30%，品类 X 退款率上升。
  7. 自愈：首次 SQL 用了错误的退款状态枚举，结果为空；用枚举样本修正为 refund_status IN ('APPROVED','COMPLETED') 后成功。
  8. 输出：折线趋势 + 贡献度柱状图 + 结论「主要来自华东区渠道 A 的品类 X 退货上升」。

贡献度下推的 SQL（这是本章方法论最关键的一段代码）：

WITH base AS (
  SELECT o.region, o.channel, o.category,
         SUM(o.paid_amount) - SUM(r.refund_amount) - SUM(d.discount_amount) AS net_revenue
  FROM orders o
  LEFT JOIN refunds r
         ON r.order_id = o.order_id
        AND r.refund_status IN ('APPROVED','COMPLETED')
  LEFT JOIN discounts d ON d.order_id = o.order_id
  WHERE o.tenant_id = 42
    AND o.region = 'east'
    AND o.stat_date BETWEEN '2026-11-10' AND '2026-11-23'
  GROUP BY o.region, o.channel, o.category
),
cur  AS (SELECT * FROM base WHERE stat_week = 'W46'),
prev AS (SELECT * FROM base WHERE stat_week = 'W45'),
contrib AS (
  SELECT c.region, c.channel, c.category,
         c.net_revenue - p.net_revenue AS delta,
         SUM(c.net_revenue - p.net_revenue) OVER () AS total_delta
  FROM cur c JOIN prev p
    ON c.region = p.region AND c.channel = p.channel AND c.category = p.category
)
SELECT region, channel, category, delta,
       delta / NULLIF(total_delta, 0) AS contrib_pct
FROM contrib
ORDER BY ABS(delta) DESC
LIMIT 20;

这段 SQL 的价值不在语法，在它把「哪几行贡献最大」变成了数据库的一次排序。如果让模型把 960 行（8 地区 × 6 渠道 × 20 品类）全拿回来自己算贡献度，回传 17.3 万 token；用这个写法，数据库算完只回传 20 行 = 3,600 token，省 48 倍，而且排序是精确的——模型在小样本上排序会出错，在全量上排序则根本做不到。

这就是「下推」的通用范式：凡是「对结果集的全体做一次计算」的步骤，都应该下推到 SQL，而不是把结果集交给模型。

结论表达：

本周净营收环比 -12%（口径：net_revenue@v2.3 财务口径，排除测试单/未结算）
数据截止 2026-11-24 06:00 · 已按租户与区域权限过滤 · 结果未截断

渠道 A 下品类 X 退款率由 3.1% 升至 6.8%

1.5.2 四个变体：自助取数、澄清、权限与明细

本章要点

四个变体覆盖快路径（自助取数，8 行结果、无放大）、多轮澄清（候选指标加 confirmed_slots）、权限受限（过滤后必须说出来）与明细查询（改写问题为直方图加分位数）。四个变体合起来说明：主路径决定能不能上线，变体决定会不会失控。

思考笔记

变体 D 里那三段 SQL 的对比是整章方法论的一次实地验证：明细直返 21.6 亿 token、LIMIT 100 截断 1.8 万但 P99 算错、统计加直方图加样本 2.16 万且分布完整。任何用截断换 token 的方案，都是在用一个 16% 的成本节省，去换一个「P99 算错」的隐性损失。

变体 A：自助取数

问题：「昨天各渠道订单量」

  • 无需澄清，命中标准指标 order_count，无多口径。
  • Schema 只需 orders + channel_dim。
  • 生成单表聚合 SQL（带 GROUP BY channel）。
  • 结果形状：分类对比 → 柱状图。
  • 结果集 8 行，无放大问题，直接给结果 + SQL + 口径。

快路径是这个系统的主路径：像这样的问题应当走「意图分类 → 直接生成 → 校验 → 执行」，全程不超过 5s，不做任何 Schema 深度检索与多步分析。问数系统能不能上线，取决于这条路径的延迟与准确率，而不是归因能力。

变体 B：多轮澄清

问题：「最近销售额怎么样？」

  • 「最近」不明确 → 追问时间范围。
  • 「销售额」有歧义 → 提供 gmv / net_revenue 两个候选（两个都是标准指标，不自创）。
  • 用户确认后写入 confirmed_slots。
  • 后续追问复用已确认口径，不再重复问。

澄清决策：

澄清一次的成本（实测）
  2,000 token（≈ ¥0.004） + 1.5s + 一次用户耐心
  vs
错误答案的成本
  ≥ 1 人天复核 + 决策损失 + 信任损失（不可逆）
→ 追问

但：追问上限 1 次（同一问题），追问 2 次以上 → 直接给候选列表或转人工

原则：澄清成本低于错误成本时追问；否则用默认值并显著注明。口径类问题几乎总是「追问」——因为默认值错误的代价太高。

变体 C：权限受限

问题：「全公司各区域营收」

  • 用户仅有华东权限。
  • 查询重写注入 tenant_id = 42 AND region = 'east'。
  • 答案明确说明「仅展示您有权限的华东区域」——不能默默只给一个区域，让用户误以为是全公司。
  • 审计记录改写前 SQL 与改写后 SQL。

权限过滤后必须在答案里说出来，否则用户会把「华东」当成「全公司」，得出「其他地区营收为 0」的错误结论。被过滤掉的维度，必须以「不可见」的形式出现在答案里。

变体 D：明细查询与结果集放大

问题：「上周华东区所有订单明细，看一下金额分布」

症状：系统按字面理解，生成一条明细 SQL，回传 120 万行。

1.5.3 故障兜底、扩容与取舍

本章要点

1.6.1 演进路线与指标体系

本章要点

思考笔记

L2 到 L3 的跨越是被两类问题逼回来的：口径问题（同一个营收两个部门算出两个数）和安全问题（模型把租户条件漏掉）。这两类问题都不会自己消失，只会在规模变大后变得更频繁——所以「暂时不做语义层」不是拖延，是把账单推到以后。

1.6.2 评测回归与成本优化

本章要点

问数的评测回归黄金集要覆盖明细类与口径冲突，并且每次模型、Prompt、语义层、引擎变更都要跑回归，在线 A/B 护栏指标优先。成本优化分两条轨道：上下文 token 侧第一刀是结果集下推，数仓计算侧第一刀是物化视图。

思考笔记

  • 在线 A/B，护栏指标优先（越权、错误结论、截断未标注）。
  • 每周复盘 Top 错误，沉淀到 Few-shot 与 Schema 描述。

1.6.4 高频追问、答题提纲与一页纸作战手册

本章要点

问数的高频追问 12 条覆盖模型编造指标、危险 SQL、权限保证、自愈边界、Schema 过大、结果集过大、评测、归因、成本、口径冲突、多轮槽位、提示注入与结果可信。答题提纲给 10 分钟版与 35 分钟版，一页纸作战手册按 S0 到 S5 六阶段组织。

思考笔记

答题提纲与练习的设计值得注意：10 分钟版强调「先给框架」，35 分钟版把「结果集 63% 占比的推导」和「扫描量的非线性」放在前 14 分钟——因为这两处最能区分「背过」与「算过」。练习里第 6、7 题是必做的计算题，不算一遍就不知道自己有没有真的理解成本结构。

高频追问

  • 如何防止模型编造指标？ → 语义层固化指标，Agent 只能引用标准定义；生成阶段声明 metrics_used，执行前核对版本；SQL 与结果可追溯。
  • 如何防止危险 SQL？ → AST 白名单 + 只读资源组 + 超时 / 行数 / 扫描量限制 + EXPLAIN 代价预估。
  • 如何保证行 / 列权限？ → 查询重写 / 视图 / 策略层强制，不靠 Prompt；敏感列不进入模型 Schema。
  • SQL 生成错了怎么办？ → 报错回填 + 最大重试 2–3 次 + 失败样本沉淀；自愈只改「怎么查」，不改「查什么」。
  • Schema 太大怎么办？ → 域路由 + 语义检索 + 关键词 + Join 历史 + 列裁剪，只暴露 Top-K。
  • 结果集太大怎么办？ → 统计下推到 SQL + 样本替代全量 + 列裁剪；不要靠截断。
  • 如何评估问数 Agent？ → 执行准确率为主 + 口径正确率 + 在线采纳率与分歧率 + 安全测试。
  • 如何做归因？ → 同比环比 + 维度下钻 + 贡献度拆解（贡献度在 SQL 里算）；结论标注假设并做结构校验。
  • 如何控制成本？ → 先下推结果集，再物化视图，再模型分级，再缓存；先削大头。
  • 口径冲突怎么办？ → 指标版本 + 作用域 + 固定裁决顺序 + 答案注明；判不了就列候选。
  • 多轮如何不重复问？ → confirmed_slots 保存已确认口径。
  • 如何防止提示注入？ → 问题文本作为数据、结构化输出、规则与判定在代码层。
  • 如何保证结果可信？ → 结果校验 + 二次核对 + 截断标注 + 低置信不下结论。

1.7.1 一句话总结

思考笔记

问数 Agent 的可信度不来自更强的模型，而来自四道落在模型之外的防线：口径在语义层、权限在执行层、结果靠下推而不是截断、答案必须带口径与 SQL。

1.7.2 本章结论

  1. 问数是一条受控流水线，不是一次生成。每一步都可能出错，系统的价值是把每种错误拦在答案之前。正确性是口径、SQL、权限、结果完整、解读五层叠加，缺一层就有一类错答案。
  2. 成本的大头是结果集，不是 Schema。结果集回传占输入 token 的 63%，Schema 只占 9%。把 Schema 裁剪当成本优化是打错靶子；真正的杠杆是统计下推与样本分离。
  3. 截断换来的省 token 是负收益。截断与下推的 token 只差 20%，但截断会把 P99 从全量分布变成前 100 行的分布。结论完整性不是能用 token 衡量的量。
  4. 越权与口径漂移必须落在执行层。Prompt 里的「只查本部门」是软建议，注入内容可以覆盖它；查询重写、策略层、视图才是硬约束。依赖模型守规矩的系统，迟早会漏一次。
  5. 不完整的结果比失败更危险。失败会被人发现，错误的数字会被拿去做决策。所以截断必须标注、冲突必须摊开、语义层不可用就停止问数。

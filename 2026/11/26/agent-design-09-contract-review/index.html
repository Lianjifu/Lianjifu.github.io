合同审查 Agent——逐条可判定的审查结论

发表于2026-11-26 分类于AI Agent 系统设计

合同审查 AI Agent 接收合同文件（PDF / 扫描件 / Word / 在线签署件），完成文档解析与条款层级还原、确定性规则分诊、逐条全覆盖扫描、要素抽取与模板差异比对、多版本冲突检测、风险分级与敞口计价、引用定位与人工复核派发，最终给出逐条可定位、可核验、可追责的审查结论与修改建议。它与问答 Agent 是同构且互为镜像的一对：两者都是「检索 → 判定 → 出结论」，差别在判定对象——问答读的是知识块，合同审查读的是合同条款；差别在召回策略——问答是「召回宽、注入窄」，合同审查是「窄召回、逐条全覆盖」；差别在评估口径——问答按准确率评估，合同审查按漏检率评估。本章围绕文档解析与条款层级还原、规则前置与分层审查、漏检率与误报率的代价不对称、引用定位与人工复核、案件隔离与保密边界展开。

引导思考 展开
它为什么存在
  • 合同审查是判侧系统：输出不是一段话，而是一组逐条结论
  • 它和问答一样是「检索 → 判定 → 出结论」，但结论要进评审记录，要能被对方律师复核
  • 所以每条结论都必须带三元组定位：条款号、页码、字符区间，缺一不可
它解决什么问题
  • 它解决的是「一条都不能漏」，而不是「把合同读懂」
  • 漏掉一条免责条款，风险敞口就全额转移给我方，而且不会有人来投诉
  • 这类错误没有举报机制，所以全部防线都要前移到「让每一条都过一遍」
它在系统中的位置
  • 它站在原文与结论之间，两头都要压住
  • 一头是保密边界：案件隔离与外传白名单；一头是判定边界：规则判命中，模型判越线
  • 事实源是原文文件、条款编号表、审查结论、复核记录与审计日志，其余全是可重建的投影
它如何工作
  • 两条通道必须并跑：存在性与内容性
  • 「合同里没写某必备条款」和「合同里写了但越线了」是两种完全不同的漏检
  • 前者无论读得多仔细都查不出来，只能拿必备条款清单去比——缺了这条通道，全覆盖也漏三分之一

9.1 合同审查 Agent 是什么

第一段 · 合同审查 Agent 是什么这一段回答：合同审查 Agent 究竟是什么、给谁用、边界划在哪里，以及哪些决策一旦做错就要停机迁移。

9.1.1 定义与三类能力层次

本章要点

合同审查 AI Agent 是面向法律文本审查场景的智能体系统：接收合同文件，完成文档解析与条款层级还原、确定性规则分诊、逐条全覆盖扫描、要素抽取与模板差异比对、多版本冲突检测、风险分级与敞口计价、引用定位与人工复核派发，最终给出逐条可定位、可核验、可追责的审查结论。它与问答 Agent 同构而互为镜像：判定对象从知识块换成合同条款，召回策略从「召回宽、注入窄」换成「窄召回、逐条全覆盖」，评估口径从准确率换成漏检率。能力分三层：L1 单文档要素提取、L2 单文档风险审查、L3 文件组审查与谈判建议，难度逐层递增。

思考笔记

「每一条都过，且每条结论都能点开原文」是这一章唯一不可妥协的产品定义，少了前半句它会漏，少了后半句它不可用——律师无法对着一句「该条款存在一定风险」去和对方谈判，他需要的是「第 12.3 条第 2 款，原文『卖方不承担任何间接损失』」。这句话也划清了本章与通用大模型读合同的区别：后者给的是摘要，而摘要会漏条款，且漏了不会报错。

定义：合同审查 AI Agent 是面向法律文本审查场景的智能体系统。它接收合同文件（PDF / 扫描件 / Word / 在线签署件），完成文档解析与条款层级还原、确定性规则分诊、逐条全覆盖扫描、要素抽取与模板差异比对、多版本冲突检测、风险分级与敞口计价、引用定位与人工复核派发，最终给出逐条可定位、可核验、可追责的审查结论与修改建议。

它与问答 Agent 是同构且互为镜像的一对：两者都是「检索 → 判定 → 出结论」，差别在判定对象——问答读的是知识块，合同审查读的是合同条款；差别在召回策略——问答是「召回宽、注入窄」，合同审查是「窄召回、逐条全覆盖」；差别在评估口径——问答按准确率评估，合同审查按漏检率评估。

两章的核心方法论也是镜像的：问答章说「召回宽、注入窄，绝不靠加宽召回换命中率」，本章说「窄召回、逐条全覆盖，绝不靠抽检换成本」。同一个底层道理的两面：送进模型的东西，要么是算好的，要么是筛过的；不能是原样倒进去的，也不能是抽样挑出来的。

但两章的失败代价完全不对称：问答章漏一条，用户大概率会点「这个不对」；本章漏一条，没有任何人会告诉你——因为合同上不会标注「此处本应有免责条款而现在没有」。这个不对称决定了整章的工程重心：全部防线都要前移到「让每一条都过一遍」。

9.1.2 与相近系统的区别、用户与场景

本章要点

四类用户的关注点各不相同：企业法务要风险不漏、条款齐、说得清，主要风险是漏掉必备条款事后无法追回；律所律师要风险定位准、结论可引用，主要风险是漏检免责条款导致敞口全额转移；业务方要快、改得动，风险是套模板时被静默改掉关键条款；合规风控要漏检率可举证，风险是结论不可核验。与相近系统的区别也很清楚：文档管理系统只存不判，条款库提供「应该有什么」却不判断「实际有什么」，文本比对工具只看差异不看差异是否越线，通用大模型读合同生成摘要且漏了不报错。

思考笔记

这张表真正的分界线是「有没有做判定」以及「判定能不能被核验」。条款库与合同审查 Agent 表面都在处理条款，但一个给的是标准文本，另一个给的是「这份合同缺了什么、越了什么」的判定——前者无法回答「这份合同有没有问题」，后者才能。落到团队分工上，这意味着文档管理、条款库、审查系统可以是三套东西，不必合并，也不该互相替代。

9.1.3 系统边界、核心指标与不可逆决策

本章要点

范围内是文档解析与编号生成、规则集执行与清单比对、要素抽取与差异比对、风险分级与敞口计价、复核派发与审计留痕；范围外是合同起草与条款库维护、实体尽调、律师的执业判断与谈判决策、法院或仲裁的最终认定。核心指标六类，其中两个是本章特有：P0 条款漏检率（条数与敞口加权两种口径）与存在性漏检率，后者专指合同里根本没写的必备条款漏掉了多少。SLO 里有两条硬约束：条款覆盖率与定位三元组完整率都是 100%，跨案访问与外传字段越界都是 0。本章七项不可逆决策覆盖条款切分与编号模型、必备条款清单与禁限规则集口径、风险敞口计价口径、定位与引用契约、案件级隔离模型、外部模型调用边界与文件组基线口径。

思考笔记

判断一个决策是不是单向门，看它改动之后「历史数据还能不能解释」。编号模型一改，历史上所有结论的定位同时失效，复核队列要整批重跑；规则集口径一改，「什么算漏检」这个基准就变了，漏检率的历史曲线全部作废。相比之下模型选择、τ 阈值、w 窗口都可以快速试错——但 τ 与 w 属于「可逆但很贵」，它们直接改写漏检率这个主指标，动它们必须配黄金集回归。

9.2 核心矛盾与设计原则

第二段 · 核心矛盾这一段回答：全覆盖的成本与漏检必须为零之间到底隔着什么，为什么这六条原则在冲突时说了算。

9.2.1 本质与六条章级原则

本章要点

本质矛盾是「逐条全覆盖的成本」与「漏检必须为零的诉求」之间的冲突：一份合同 180 条一条都不能少看，但每条都调用最强模型与最宽上下文，成本会超过人工全审，这意味着「抽检」和「只看重点条款」在这个领域是原罪级错误。六条章级原则规定冲突时以谁为准：漏检率优先于效率，规则前置、模型不判确定性的事，存在性与内容性两条通道都要过，每条结论必须可点开定位，高风险强制人工复核但复核不是漏检的防线，保密边界先于能力边界。

思考笔记

第二条原则的理由不是成本，是可复现与可对账：同一条款判两次必须得出同一个结论，否则结论进不了合同评审记录。第五条原则最容易被误解成「有人工把关就安全」，其实恰恰相反——人工只能纠正误报与等级判定，漏检的条款根本没进复核队列，所以漏检的防线在覆盖率，不在人力。第六条则解释了为什么保密边界要在定题阶段落定：一次串案无法追回，一次静默外传无法解释。

本质：合同审查 Agent 的核心矛盾，是「逐条全覆盖的成本」与「漏检必须为零的诉求」之间的冲突。一份合同 180 条，一份都不能少看；但每条都调用最强的模型与最宽的上下文，成本会超过人工全审。这意味着「抽检」和「只看重点条款」在这个领域是原罪级别的错误，而不是优化手段。

六条章级原则（贯穿全章，冲突时以这六条为准）：

  1. 漏检率优先于效率——漏检率是唯一的主指标，效率是约束不是目标。一条被漏掉的免责条款，其期望损失等于 2,308 条误报的复核成本；抽检省下的钱，买不起这个风险。
  2. 规则前置，模型不判确定性的事——禁限条款、金额阈值、必备条款清单必须走确定性规则 / 正则 / DSL。理由不是成本，是可复现与可对账：同一条款判两次必须得出同一个结论，否则结论无法进合同评审记录。
  3. 两条通道都要过：存在性与内容性——「合同里没写某必备条款」与「合同里写了但越线了」是两种漏检，前者无论你读得多仔细都查不出来，只能靠拿清单去比。
  4. 每条结论必须可点开定位——clause_id + 页码 + 字符区间三元组是结论的一部分，不是附件。定位缺失的结论等于没有结论。
  5. 高风险强制人工复核，但复核不是漏检的防线——人工只能纠正误报与等级判定；漏检的条款根本没进复核队列。所以漏检的防线在覆盖率，不在人力。
  6. 保密边界先于能力边界——案件隔离与外传白名单在 S0 就落定，不在上线前打补丁。一次串案无法追回，一次静默外传无法解释。

9.2.2 三个不等式与三个放大器

本章要点

三个不等式划定了边界：漏检代价远大于误报代价，漏一条 P0 免责条款等于 2,308 条误报的复核成本；条款数量远大于人工速率，日 21.6 万条条款对 50 名律师，覆盖率只能是硬约束；生成能力远大于判别能力，模型会「合理地」认定一个越线条款没问题。三个放大器量化代价：条款漏检放大让漏掉一条 P0 的敞口全额转移、损失不可逆且无人举报，漏检率停在 0.84% 一年就放过去 2,268 条带病条款、约 ¥10.9 亿期望损失；覆盖放大让成本随条款数线性增长；文件组放大让组内冲突有三分之二是单文档看不见的。

思考笔记

这一章最贵的一笔账在「失败不可见性」上。前面所有 Agent 章的错误最终都会被人看见——用户点踩、业务方投诉、告警爆炸、账对不上；合同审查的错误只有一种人看得见：几年后打官司时的对方律师。所以这一章的架构重心与别章不同，别章可以用后验指标做兜底，这一章必须把防线全部前移到「让每一条都过一遍」，因为漏掉的条款连投诉都不会有。

三个不等式：

漏检代价  >>  误报代价   →  漏一条 P0 免责条款 ＝ 2,308 条误报的复核成本
条款数量  >>  人工速率   →  日 21.6 万条条款 vs 50 名律师，覆盖率是硬约束
生成能力  >>  判别能力   →  模型会「合理地」认定一个越线条款没问题

三个放大器（本章最贵的量都藏在这里）：

放大器说明后果量化
条款漏检放大（本章核心）漏掉一条 P0 条款 = 该项风险敞口全额转移给我方损失不可逆，且无人举报漏检 1 条 P0 = ¥48 万期望损失 ＝ 2,308 条误报复核；漏检率停在 0.84%，一年放过去 2,268 条带病条款 ＝ ¥10.9 亿期望损失（风险分级与敞口计价）

更关键的是它的失败不可见性：前面所有章的错误最终都会被人看见——用户点踩、业务方投诉、告警爆炸、账对不上。本章的错误只有一种人看得见：几年后打官司时的对方律师。

9.3 理论与方法论

第三段 · 理论与方法论这一段回答：从七项前置锚点出发，一步步推到方法论与容量成本；解析、通道、窗口、规则、定位各怎么治。

思考笔记

9.3.3 文档解析与两条审查通道

本章要点

解析五步是版式还原、OCR、层级还原、表格与附件归位、修订痕迹还原，每一步都有典型失败与防线，其中 OCR 的数字错误最凶险——`¥5,000,000` 被识别成 `¥S,000,000`，整份合同的敞口就错了而且不报错，因此金额、期限、比例字段必须走数字字段双通道校验。切分粒度不等于审查粒度：切分与编号用单条条款（平均 120 token），模型判定用条款加 w = 3 邻接窗口。两条审查通道必须并跑：存在性通道靠必备条款清单比对查缺失，内容性通道靠规则前置加全量扫描加精审查越线。

思考笔记

三种方案的实测对照把这一节讲透了：全文一次调用的漏检率 42.6%，逐条全覆盖加全量精审是 32.9%，分层方案是 0.84%。注意中间那一档——它覆盖了每一条条款，却仍然漏掉三分之一的 P0 问题，因为缺失的条款不存在，再仔细也读不出来。所以「全覆盖」不等于「无漏检」，全覆盖只是内容性通道的充分条件，存在性通道需要另一套机制，这是清单比对这类机制在分层架构里才有位置的原因。

文档解析与条款层级还原

五步解析：

原始文件
  → ① 版式还原（页 / 栏 / 页眉页脚 / 表格边界）
  → ② OCR（仅扫描件；文本层 PDF 直接抽文字层）
  → ③ 层级还原（章 / 条 / 款 / 项 的编号模式识别）
  → ④ 表格与附件归位（表头绑定 + 附件挂到主协议条款）
  → ⑤ 修订痕迹还原（基线文本 + 修订序列）
  → 条款编号表（clause_id + 层级路径 + 页码 + 字符区间）

每一步的失败模式与防线：

步骤典型失败后果防线
① 版式还原双栏合同串行条款内容拼接错乱版式检测 + 串行还原校验
② OCR数字识别错（0 / O、1 / l）金额与期限全错数字字段双通道校验（见下）
③ 层级还原附件里的编号被当成正文编号clause_id 冲突附件独立命名空间 + 编号前缀
④ 表格归位表格行被当纯文本违约金表读不出来表格行必须携带表头与所属条款号
⑤ 修订痕迹只取到最终文本，修订丢失跨版本差异无处可查必须还原成「基线 + 修订序列」

OCR 的数字错误是本章最凶险的失败：合同里的金额、期限、比例集中在一两个字符上，¥5,000,000 被识别成 ¥S,000,000，整份合同的敞口计算就错了，而且不报错。因此必须有数字字段双通道校验：OCR 置信度 < 0.9 的段落、以及所有金额 / 期限 / 比例字段，一律经过独立的数值抽取 + 人工确认，不允许直接进入判定。

切分粒度 ≠ 审查粒度（本章的关键工程点）：

阶段粒度理由
切分与编号单条条款（平均 120 token）稳定单元，编号可跨版本对齐，定位可精确到区间
规则匹配单条条款禁限条款与金额阈值必须在单条上判定，不能跨条拼接
模型判定条款 + w = 3 邻接条款窗口（480 token）判定需要定义与相邻义务（审查上下文窗口的倒 U 型）
要素抽取单条条款要素是条款级属性，跨条会串味

这是本章与第 2 章 · 问答 Agent最像的地方、也是最容易照抄错的地方：第 2 章 · 问答 Agent的教训是「检索粒度 ≠ 注入粒度」，本章的教训是「切分粒度 ≠ 审查粒度」。切分要小而稳（便于编号与定位），审查要够而不多（w = 3，够则准、多则污染）。

附件处理：附件是独立文档，但受主协议条款约束（如「附件二为本协议不可分割的组成部分」）。必须建立附件 ↔ 主协议条款的引用图，否则会出现「主协议说赔偿上限见附件二，而附件二里没有这一条」这种双文档才能发现的缺口。

两条审查通道：存在性与内容性

这是本章的结构性分叉，也是与第 2 章 · 问答 Agent最本质的差别——问答只有一条通道（检索出证据），合同审查有两条。

通道审什么靠什么发现漏检能靠「读得更仔细」改善吗
存在性通道合同里根本没有的必备条款必备条款清单比对不能——不存在的东西读不出来
内容性通道合同里写了但越线了的条款规则前置 + T1 全量扫描 + T2 精审能，但要付出覆盖成本

为什么必须分开报指标：黄金集（1,080 条 P0 问题 / 批）中，内容性 P0 问题占 70%（756 条）、存在性 P0 问题占 30%（324 条）。混在一起报一个「漏检率」，会得到一个看起来还行、实际上一半来源没被治理的数。

9.3.4 上下文窗口与风险敞口计价

本章要点

w 是参与判定一条条款的邻接条款数，判定一条条款的正文 token 约为 (w + 1) × 120。黄金集 6.4 万条款对的实测给出倒 U 型曲线：w = 0 漏检 13.1%、w = 1 是 7.4%、w = 3 降到 4.1%、w = 6 回升到 4.3%、w = 12 是 6.2%、w = 30 回升到 10.4%，每条款 token 从 120 涨到 3,720。风险分三级：P0 的敞口按合同金额全额计价，P1 按固定重谈成本，P2 几乎无直接损失。平均合同金额 800 万、事件概率 6%，漏检 1 条 P0 的期望损失 48 万，而误报 1 条的复核代价是 208 元。

思考笔记

倒 U 型的两个拐点各有原因，第二个更反直觉：w = 0 会漏是因为定义与例外常写在别处，只看本条款模型会判成无风险；w = 30 漏检回升不是没看见风险，而是看见了并归错了地方——窗口一旦跨过章节边界，模型会认定「别处已经约定了」而放过当前条款。所以邻接要按语义取，优先取父级标题路径与紧邻前后条款，而不是按 token 距离取。实践上窗口还应按章节类型分档，定义密集章节放到 6，一般义务保持 3，分类目设的综合漏检率是 3.6% 且 token 少 12%。

实践含义有两条：

  1. 窗口要按章节类型设，而不是全局一个值。定义密集的章节（定义、赔偿、保证）用 w = 6；一般义务条款用 w = 3。实测混用 w = 6 的总漏检率是 4.3%，分类目设的综合漏检率是 3.6%，token 还少 12%。
  2. 邻接要按语义取，不能按 token 距离取：优先取父级标题路径与紧邻的前后条款，而不是「附近 480 token 的内容」。

9.3.5 规则前置与要素抽取比对

本章要点

三类确定性规则不能交给模型：禁限条款（正则加词典加否定式检测）、金额阈值（数值抽取加阈值比较）、必备条款清单（结构匹配加语义等价判断），理由是不可复现、不可对账、阈值改一次要立刻生效、成本反比。分工口径很清楚：是否命中禁限清单、金额是否超阈值、是否缺必备条款归规则，是否越线、越了什么线、风险等级与修改建议归模型。要素抽取分主体、金额、期限、违约责任、生效条件五类，差异判定分一致、偏离、缺失三态，其中金额容忍带 ±5%、期限 ±30 天、比例 ±1 个百分点，容忍带必须写进规则层。

思考笔记

「阈值改一次要当天对全量在审合同生效」这一条最能说明规则与模型的分界。金额阈值是业务政策，改完要立刻生效；模型做不到这一点，它的阈值只能靠重训或重跑生效。同样地，容忍带不是一个「宽松度」旋钮，而是一个必须被写死的业务口径——不同到什么程度才需要谈判，这件事没法让模型自己拿捏，否则同一个 3% 的差异两次评审可能给出不同结论，而那份结论要进合同评审记录。

规则前置：禁限条款、金额阈值、必备条款清单

本章要点

文件组平均 5 份、条款总量 630 条，是单份的 3.5 倍。五类冲突分别是金额不一致、期限不一致、定义不一致、优先顺序冲突与附件引用失效，裁决依据是「优先顺序条款」——很多合同会写本协议优先于其全部附件，必须先把这个条款解析出来，它决定后面所有冲突往哪边倒。三元组定位是结论不可分割的一部分：clause_id 加页码加字符区间，粒度到条款加块内区间，必须可点开原文，页码要分物理页与条款序号页两套，系统自动抽取 2% 的结论校验高亮片段是否真的支持该结论，实测抽检定位准确率 99.6%。

思考笔记

组内审查的增量价值很能说明问题：单文档审查发现 2 个冲突，文件组审查发现 6 个，其中 4 个是单文档看不见的。这与多跳问答里「每一步都对、合起来错」是同构的问题，但后果更重——合同审查错了没人会发现，因为组内冲突只有把 5 份文件摊在一起时才看得见。裁决上还有一个必须分开的第三类：优先顺序条款能裁的自动裁，时间序能裁的（修订稿优先）自动裁，两者都不能裁的必须升级人工，因为「后签文件优先」是一条法理规则，不是系统能定的口径。

必须说清一件事：人工复核不是漏检的防线。

复核队列里只有「模型认为有问题」的条款。模型判为无风险而实际有风险的条款，根本不会进队列。 抽样复核率 2%，且人工对被抽样的漏检捕获率约 40%——对 P0 漏检的总捕获率只有 0.8%。

所以：漏检的防线在「让每一条都过一遍」与「把确定性的事交给规则」，不在人力。 人力能解决的是误报与等级判定——把「误报太多」归因成「要加规则」，是把问题归错了地方。

「未审查」必须显式存在。 把「未审查」默认显示成「未发现问题」，是本章最贵的一种失败：它把漏检从「一个错误」变成「一个看不见的错误」，而且系统还声称自己审过了。

9.3.7 权限保密、阈值决策与评测

本章要点

案件级命名空间把分片键与缓存键都绑上 case_id，理由是实测相似条款命中率 63%，隔离做在过滤层几乎必然串案。脱敏在进模型前做，但阈值判定必须在脱敏前用规则做——规则在受信域内拿到原值算出「超阈值 / 未超阈值」，模型只看到脱敏文本加已算好的结论。τ 是判定有风险的置信度阈值，扫描显示工作点取 0.40：复核队列 1,400 条 / 天约 117 小时，漏检率 1.0%，在盈亏平衡点 2.23% 之内；而每收紧一档代价收益比从 1:5.5 涨到 1:388。评测的黄金集分三个分区：正常合同、刻意构造的缺失条款、刻意埋入的禁限条款。

思考笔记

把脱敏后的金额交给模型去判阈值，判断必然错误——脱敏的目的是不外传，不是让判断变瞎，这是很多安全合规改造把系统改傻的典型方式。阈值那一节则说明了一件事：任何只统计显性痛点的指标体系，都会自动把系统推向更严的 τ，而更严的 τ 恰恰在放大那个没人看的损失；所以阈值必须用期望损失而不是投诉数来定，一旦定错，后果不是效果差一点，而是每年悄悄放过去两千多条带病条款。

常见做法后果

这是本章的一个关键工程点：脱敏在「进模型前」做，但阈值判定必须在「脱敏前」用规则做——规则在受信域内拿到原值、算出「超阈值 / 未超阈值」，模型只看到脱敏文本 + 已算好的结论。

如果把脱敏后的金额交给模型去判阈值，它的判断必然错误——脱敏的目的是不外传，不是让判断变瞎。把这两件事混在一起，是很多「安全合规改造」把系统改傻的典型方式。

三条结论：

  1. 收紧阈值是超线性变贵的：代价收益比从 1 : 5.5 涨到 1 : 388，跨度 70 倍。原因是漏检损失随 τ 上升是凸的（漏掉的多是高敞口条款），而复核成本随 τ 上升是凹的（长尾队列本来就很短）。
  2. 工作点选 τ = 0.40：复核队列 1,400 条 / 天 ≈ 117 小时 / 天 ≈ 15 人日，50 人的团队扛得住；而漏检率 1.0% 在盈亏平衡点 2.23% 之内（容量与成本估算）。
  3. 队列长度必须有上限，且上限不是靠抬 τ 解决的：超限时升级人工、延后非关键合同、或把非 P0 项降级到抽检。「提高 τ 来压队列」是本章最典型的错动作。

为什么这一节必须存在：因为「误报太多」是显性的、可追责的痛——律师会抱怨、领导会看到、投诉会被记下来；而「漏检」是隐性的、几年后才出现的痛。任何只统计显性痛点的指标体系，都会自动把系统推向更严的 τ，而更严的 τ 恰恰放大那个没人看的损失。

所以阈值必须用「期望损失」而不是「投诉数」来定。 一旦定错，后果不是「效果差一点」，而是每年悄悄放过去 2,000 多条带病条款。

「漏检反查率」是滞后但最真：它统计的是事后争议中发现的漏检。它几乎不可能实时采集，但它是对前面所有指标的最终裁决——一个漏检率 0.84% 但漏检反查率高的系统，说明漏检被算到了「不重要」的问题上。

条数口径与加权口径为什么会差这么多：实测条数漏检率 0.84%，敞口加权漏检率 1.15%——因为漏掉的多是高敞口条款（小额的、措辞类的问题模型恰好判对了）。这 37% 的差距，就是「用条数汇报漏检率」的代价。

9.3.8 容量与成本模型

本章要点

容量单位是条款 / 秒：峰值合同 0.042 QPS、峰值模型调用约 1 次 / 秒、峰值条款吞吐 7.5 条 / 秒。token 拆解给出模型段合计 12.9 万元 / 天，其中 T1 全量扫描占模型输入 80.6%、必备条款清单比对占 13.8%、T2 精审占 5.6%。三段成本拆分：模型调用 85.4%、存储 8.0%、OCR 3.6%、规则引擎 2.9%，合计 15.08 万元 / 天。与人工全审对比，AI 方案含复核 44.2 万元 / 天，净省 1,155 万元 / 天，由此算出盈亏平衡漏检率 2.23%，当前实测条数口径 0.84%（余量 2.65 倍）、敞口加权口径 1.15%（余量仅 1.94 倍）。

9.3.9 重跑、幂等与版本基线

本章要点

幂等键由文档哈希加规则版本加清单版本加模板版本加模型版本构成，换模型版本要重跑全部条款，换规则集版本只重跑受影响条款，同一份合同重复提交直接命中幂等键。规则集升级后的历史影响面必须回溯重算：改一条禁限规则，当年判定为无风险但按新规则应判风险的条款要回溯并通知，否则漏检率的历史曲线就断了。基线口径必须固定三件事：哪一版文件、哪一组文件、哪一版规则与清单，三者构成 review_baseline 并写进每一条结论。

思考笔记

「哪一版」是最容易被忽略的那一件：对方发来第 3 稿，律师在第 3 稿上签字，但审查结论是按第 1 稿的规则做的——这份结论引用的是一份已经不存在的文本。这条纪律与幂等键是一对，幂等键保证同一份输入不重复产出结论，基线口径保证这份结论能说清它是在什么规则、什么文本、什么文件组上得出的；缺了基线，回溯重算与审计都无从下手。

9.4.4 降级矩阵与延迟预算

本章要点

降级矩阵的判据只有一条：依赖失效的后果是「漏检」还是「少给信息」，凡有可能造成静默漏检的依赖一律 fail-closed。全章有三个 Fail-Closed：案件权限服务、规则引擎、必备条款清单库；审计写入对高敏案件也是 Fail-Closed；T2 精审模型超时则只给条款定位与原文不给结论，T1 扫描模型超时则标「覆盖不完整」且不进签署关键路径。延迟预算是唯一口径：接入鉴权 80ms、解析 1.2s、T0 规则 60ms、清单比对 2.5s、T1 扫描 6s / 批、T2 精审 12s / 批，单份合同墙钟目标 40 秒、硬限 120 秒。

思考笔记

本章比问答章多出两个 Fail-Closed，原因是一条存在性通道：清单库一旦缺失，漏检会静悄悄地涨上去而没有任何报错，所以它必须和权限、规则一样是硬闸门。延迟预算里最容易做错的是把 T1 扫描与清单比对当成「质量增强」去挤掉——它们不是增强项，它们就是覆盖率本身的实现；预算被挤掉时正确做法是排队把单份墙钟拉长，而不是砍掉扫描，因为砍扫描就是直接提高漏检率。

9.5 端到端案例

9.5.1 案例：并购框架协议审查

本章要点

《MSA-2026-014 并购框架协议》32 页 180 条、含附件二与补充协议一、合同金额 8,000 万、我方为卖方。链路十步：接入时定为严格密级并替换主体名；解析出 9 章 180 条并把附件二表格归位；T0 规则命中免责、境外管辖、自动续约三项 P0 与违约金、预付款两项 P1；T1 全量扫描 174 条抓到一条不含禁限关键词的第 7.6 条单方调整分成比例；T2 精审确认 5 条 P0 并补出与附件二冲突；清单比对发现数据安全责任分配整条缺失；要素与文件组冲突按优先顺序条款裁决。结论 6 条 P0 加 3 条 P1 加 1 条缺失，最重的一条敞口 800 万、期望损失 480 万。

思考笔记

这个案例最值得讲的是第 4 步与第 6 步：第 7.6 条不含任何禁限词库里的词，只跑规则一定会漏，而它恰恰是本份合同最贵的一条；清单比对抓到的是一条根本不存在的条款，无论多仔细地逐条读都读不出来。两条加起来 780 万，占本份合同全部期望损失的一半，而它们来自两条独立通道——任何一条都替代不了另一条，这正是必须并跑的原因。

9.5.2 多版本冲突、权限隔离与双语术语

本章要点

三个变体各暴露一类问题。多版本冲突案例中，5 份文件查出 5 个冲突、4 个单文档看不见，其中补充协议与主协议期限不一致的那一条因为优先顺序条款没有提及补充协议而必须升级人工。跨客户与跨律所权限隔离案例用两份共享同一标准模板 14 条条款的合同（相似条款命中率 63%）做对照：全局索引加检索后过滤不越权但有效命中率从 97% 掉到 41%，全局缓存实测串案 17 次，案件级命名空间串案 0 次而有效命中率 97%。双语案例中术语表锁定加管辖语言裁决把漏检率从 3.8% 拉回 1.9%，几乎回到单语水平。

思考笔记

权限隔离那组对照说明「不越权」和「可用」是两件事：检索后过滤同样不越权，却把有效命中率打到 41%，而团队通常会去调 top-k 或换模型，治错了地方；全局缓存那 17 次则是把别人的条款直接返回给当前用户，每一次都是一次保密事故，且都不会报错。所以隔离必须做在分片键上——过滤层的实现在赶工期时很容易被简化掉，分片键不会。

第 2 条是本章特有的一个「无法自动裁决」的情形：优先顺序条款通常只写「本协议优先于附件」，没有提补充协议。这时系统不能自己选一个——必须升级人工，因为「后签文件优先」是一条法理规则，不是本系统能定的口径。

本章要点

误报投诉案例给出正确的解法：业务方要求提高阈值，但把 τ 从 0.40 提到 0.60，复核成本省 20.6 万 / 天而漏检期望损失多付 1,245 万 / 天，代价是收益的 60 倍；正确的做法是队列分级、规则误报治理与要素偏离分流，把队列从 1,400 降到约 1,030 条而漏检率保持 1.0% 不变。模型不可用案例给出最终界面的三态形态：已审查发现问题 4 条、已审查未发现问题 171 条、未审查 5 条并给出条款定位与原文，另加一条「存在性通道为结构匹配，语义等价未校验」。扩容十倍的先坏顺序是人工复核产能、模型预算、OCR 产能、规则引擎 CPU、审计存储、定位抽检，并发排在最后。

9.6.2 评测回归与成本优化

本章要点

黄金集三个分区缺一不可，刻意构造的样本占 15%，低于这个比例存在性通道的漏检会被正常样本稀释成看不见的小数；主指标是 P0 漏检率，条数口径与敞口加权口径并列，只报条数口径会掩盖 37% 的差距。八类变更全都要重跑黄金集，回归要同时看漏检率与误报率。成本优化有七项，前六项是纯收益：规则集扩容让 T1 扫描降 38%、w 值校准让 T2 降 43%、批处理摊薄指令降 72%、模型分级降 35%、复核队列分级降 30%、正则合并预编译降 40%；只有第七项「缩小 T1 扫描范围」带代价，它直接抬高漏检率且必须重算 2.23% 的盈亏平衡点。

思考笔记

成本表的排序本身就是结论：合同审查的成本优化有一个强约束，你唯一能省的那一笔恰好是漏检率的担保。前六项之所以是纯收益，是因为它们没有减少「必须过一遍」的条款数，只是让过一遍更便宜；第七项则直接减少了过一遍的范围。与此对应，「只看误报率做回归」会把系统调成「什么都不敢报」，只看漏检率则会调成「什么都要复核」。

评测与回归

  • 黄金集三个分区：正常合同 / 刻意缺失条款 / 刻意埋入禁限条款，缺一不可。刻意构造的样本占黄金集的 15%——低于这个比例，存在性通道的漏检会被正常样本稀释成看不见的小数。
  • 主指标是 P0 漏检率，条数口径与敞口加权口径并列；只报条数口径会掩盖 37% 的差距。
  • 每周重跑黄金集：换规则集、换清单、换模板、换抽取器、改 w 值、改 τ、改 OCR 引擎、换模型版本——八类变更全都要重跑，因为它们都直接改变漏检率。
  • 变更回归要看两个数：漏检率与误报率同时看；只看误报率会把系统调成「什么都不敢报」，反之只看漏检率会调成「什么都要复核」。
  • 线上以「复核推翻率」与「漏检反查率」做代理；复核推翻率上升即回滚。
  • 回滚能力分层：规则集、清单版本、τ、w 都是配置项，秒级回滚；模型版本回滚需重跑；w 值改动最贵（需重跑黄金集全量）。
  • 被推翻的样本必须回流黄金集——每一次人工推翻，都是一个免费的黄金集样本。

前六项全是纯收益，只有第七项带代价。 这个排序本身就是结论：合同审查的成本优化有一个强约束——你唯一能省的那一笔，恰好是漏检率的担保。

第 1 项（规则集扩容）是唯一同时降本又降漏检的手段，所以它排第一：每多覆盖一个禁限条款，规则就替模型挡掉一批，而模型扫过的面积不变——省下的模型调用是被省下的，不是不该花的。

第 7 项必须永远排在最后，且每次都要重算平衡点。 平衡点不是常数——它随合同金额、人工成本、复核队列变化而变。拿去年的平衡点决定今年的扫描范围，是本章最典型的一次事故。

9.6.4 高频追问、答题提纲与一页纸手册

本章要点

高频追问 13 条覆盖怎么保证不漏条款、漏检率与效率冲突怎么办、误报太多怎么降、怎么判断结论可信、人工复核能否解决漏检、两份合同一起审有什么坑、冲突怎么裁决、多语言合同怎么做、客户之间会不会串、合同能否给外部模型看、怎么评估、模型不可用怎么办、扩容十倍先坏哪里。答题提纲给 10 分钟版与 35 分钟版，一页纸作战手册按 S0 到 S5 六阶段组织，每阶段配动作、自检问题与合格线，S0 里专门有一条要量单份条款数，S3 里专门有一条要算覆盖与平衡点。

思考笔记

答题提纲的设计值得注意：35 分钟版把「漏检放大推导加盈亏平衡点」「存在性通道为什么不可省」「阈值收紧的边际代价」「窗口倒 U 型与上下文污染」放进深挖环节，因为这四处最能区分「背过」与「算过」。手册里每一步都带合格线，比如「量条款数」的合格线是给出带来源的条款数并指出它是页数的 5.6 倍，这种可自检的表述比原则更好用。

高频追问

  • 怎么保证不漏条款？ → 三条防线：① T0 规则 + T1 全量扫描保证每条都过（覆盖率 100%，可对账）；② 存在性通道用必备条款清单比对（查「缺失」）；③ 拒答式输出：「未审查」显式三态，不假装通过。
  • 漏检率和效率冲突怎么办？ → 漏检率优先，且要算盈亏平衡漏检率（本例 2.23%）：低于它 AI 才划算。成本优化单里唯一能省的那笔就是覆盖率担保，所以它排最后。
  • 误报太多怎么降？ → 不要抬 τ（代价是漏检率 3.4 倍）。用队列分级 + 规则误报治理 + 要素偏离分流，实测队列降 26% 而漏检率不变。
  • 怎么判断结论可信？ → 三元组定位完整率 100% + 抽检定位准确率 ≥ 99.5% + 人工复核推翻率 + 事后漏检反查率。可信度不靠措辞，靠可核验。
  • 人工复核能解决漏检吗？ → 基本不能。模型判为无风险的条款不进队列，抽样捕获率只有 0.8%。人力解决的是误报与等级判定。
  • 两份合同一起审有什么坑？ → 组内冲突：主协议与附件的金额、期限、定义、优先顺序、附件引用。单份审对 ≠ 组内审对，实测 5 个冲突里有 4 个单文档看不见。
  • 冲突怎么裁决？ → 三种结果分开：优先顺序条款能裁的自动裁；时间序能裁的（修订稿优先）自动裁；两者都不能裁的升级人工（如优先顺序条款未提及补充协议）。
  • 多语言合同怎么做？ → 术语表锁定 + 管辖语言条款裁决。双语使漏检率涨 3.8 倍，术语表能拉回 1.9%。术语表必须按客户分组版本化。
  • 客户之间会不会串？ → 会，如果隔离做在过滤层。实测相似条款命中率 63%，全局缓存串案 17 次。隔离必须做在分片键与缓存键上。
  • 合同能给外部模型看吗？ → 默认拒。字段级白名单 + 单合同字符上限 + 脱敏先于出域 + 阈值判定在受信域做（脱敏后模型判不出阈值）+ 外传留痕与客户同意。
  • 怎么评估合同审查 Agent？ → 黄金集含「正常 / 刻意缺失 / 刻意埋入」三类；主指标 P0 漏检率（条数 + 敞口加权）；线上以复核推翻率与漏检反查率做代理。
  • 模型不可用怎么办？ → 只给条款定位与原文，不给结论；把系统从「给判断」拉回「摆原文」；「未审查」必须显式。
  • 扩容 10 倍先坏哪里？ → 人工复核产能与模型预算，不是并发（峰值模型调用才 10 次 / 秒）。这是本章与其它 Agent 章最大的结构差异。

9.7.1 一句话总结

思考笔记

合同审查 Agent 的可信度不来自更强的模型，而来自三件工程事：规则前置保证同一条款两次判定一致，逐条全覆盖保证缺失条款之外的问题不漏，三元组定位保证每条结论都能被对方律师点开核对。

9.7.2 本章结论

  1. 漏检率是唯一的主指标，效率只是约束。漏掉一条 P0 免责条款的期望损失是 48 万，等于 2,308 条误报的复核成本；漏检率停在 0.84% 一年就是 2,268 条带病条款、约 10.9 亿期望损失，而且没有人会来投诉。
  2. 全覆盖不等于无漏检，存在性通道必须独立存在。逐条全覆盖加全量精审的实测漏检率是 32.9%，分层方案是 0.84%，差别就在必备条款清单比对这条独立通道——不存在的东西，读得再仔细也读不出来。
  3. 规则前置的理由是可复现与可对账，不是省钱。禁限条款、金额阈值、必备条款清单必须走确定性规则，因为同一条款判两次必须得出同一个结论，结论才进得了合同评审记录；容忍带同理，它是写死的业务口径而不是模型可以拿捏的判断。
  4. 「未审查」必须显式显示为第三态。把没审过显示成未发现问题，是本章最贵的一种失败：它把漏检从一个错误变成一个看不见的错误，而且系统还声称自己审过了。模型不可用时只给条款定位与原文，不给结论。
  5. 扩容先坏的是人和钱，不是机器。峰值模型调用才 1 次 / 秒，扩到十倍也才 10 次 / 秒；先坏的是复核队列从 1,400 条涨到 14,000 条、50 人变 250 人，以及日模型成本从 12.9 万涨到 128.98 万。

## 第二十二章 客服 AI Agent 系统

> **本章导读**：客服 Agent 是「概率模型 + 确定性业务」的结合体——它要回答用户问题，更要安全地执行退款、改地址、查物流等有副作用的动作，核心工程挑战是「同一个意图不能执行两次、执行到一半崩了要能恢复」。本章围绕 Agent 架构与队列 Worker、状态机与 Checkpoint、幂等与 HITL、三层记忆与上下文放大、工具防注入展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 22.1 核心定义与定位

**定义**：客服 AI Agent 是面向客户服务场景的智能体系统。它接收多渠道工单，完成意图识别、知识检索、工具调用、回复生成，并在不确定或高风险时转人工。它不只是「会聊天的机器人」，而是**能执行业务动作、可审计、可回滚、可人工接管**的服务系统。

**三类能力**：

| 能力 | 说明 | 典型动作 | 风险 |
|---|---|---|---|
| 问答 | 基于知识库回答 | FAQ、政策解释、产品咨询 | 幻觉、过期知识 |
| 事务 | 调用业务工具 | 查订单、改地址、退款、开票 | 误操作、越权 |
| 协同 | 与人协作 | 转人工、审批、补充信息 | 上下文丢失、重复劳动 |

**与相近系统的区别**：

| 系统 | 核心 | 与客服 Agent 的差异 |
|---|---|---|
| 规则机器人 | 决策树/关键词 | 覆盖窄、维护贵，但确定性强 |
| RPA | 固定流程自动化 | 无自然语言理解，异常处理弱 |
| 通用聊天助手 | 生成回答 | 无业务工具、无工单状态、无审计 |
| 客服 Agent | 理解 + 检索 + 工具 + 人机协同 | 有副作用、强一致、强审计 |
| 人工客服 | 人处理 | 成本高、时效不稳定，但判断力强 |

**业务价值**：

- 降本：拦截常见问题，减少人工坐席。
- 提效：7×24 小时、秒级首响、并行处理。
- 一致性：政策口径统一，减少人为差异。
- 可分析：全量对话结构化，反哺产品与知识库。

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 工单接入与渠道归一 | 呼叫中心底层话务 |
| 意图识别与路由 | 业务订单主数据 |
| 知识检索（RAG） | 知识库内容生产 |
| 工具编排与执行 | 支付渠道本身 |
| 人工转接与审批 | 坐席排班与绩效 |
| 会话状态与审计 | 全站风控 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 效果 | 一次解决率、自助解决率、转人工率、CSAT |
| 正确 | 意图准确率、工具选择准确率、参数准确率、政策违规率 |
| 效率 | 首响时延、平均处理时长、并发工单数 |
| 成本 | 单工单 token 成本、单工单人工成本 |
| 安全 | 越权拦截率、注入拦截率、PII 泄露数 |

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 工单接入 P99 | < 200ms |
| 首响 P95 | < 3s |
| 异步任务完成 P95 | < 2min |
| 转人工时延 | < 30s |
| 可用性 | 99.9% |
| 错误退款 | **0**（硬约束，不用百分比衡量） |
| 审计覆盖率 | **100%** |

**本章专属不可逆决策清单**（做错了要停机迁移 + 数据回填 + 全量对账，不是发个版本就能改）：

| 决策 | 为什么不可逆 | 改动代价 |
|---|---|---|
| **工单状态机的状态与跃迁语义** | 状态机、Checkpoint、审批、恢复、超时全部依赖同一套语义 | 全部恢复逻辑重写 + 存量工单状态迁移 + 在途任务全部人工接管 |
| **幂等键的构造规则**（`ticket_id + action + step`） | 所有写工具、去重表、回调校验共用它 | 存量幂等记录失效 → **已发生的重复退款无法自动识别**，需人工对账 |
| **Checkpoint 的 schema 与存储选型** | 恢复逻辑、版本兼容、跨版本迁移全建立在它上面 | 全量 schema 迁移 + 存量任务无法恢复 + 回滚窗口关闭 |
| **工具契约**（工具名 + JSON Schema + 权限模型） | Agent 的行为由工具描述决定；改了描述等于改了行为 | 模型行为不可复现 + 存量 Checkpoint 里的旧调用无法重放 + 全量回归 |
| **上下文治理策略**（三层记忆的字段与裁剪规则） | 决定 token 成本与事实保真度 | 同一问题在不同版本得到不同答案 + 成本模型全部作废 + 全量重跑评测 |
| **RAG 的分块策略与索引 schema（含 ACL 字段）** | 召回质量与权限过滤都建立在它上面 | 全量重建索引 + 召回结果突变 + 权限过滤出现历史越权窗口 |
| **自动化分级与审批阈值**（金额/风险的 HITL 边界） | 决定人工成本与错误率的平衡点 | 一旦对外承诺过 SLA 很难改；调整等于悄悄改变风险偏好 |

> **对照第一章 §1.4.4**：这七项属单向门，决策时要多评审、做原型、留迁移方案。其余（模型选择、批大小、top-k、K 值、工具超时、Worker 并发）都是双向门，可以快速试错——但 **K 值（保留轮数）与 top-k 属于「可逆但很贵」**：调它们会改变全部历史工单的回答质量，必须伴随评测回归。

### 22.2 核心解读与关键矛盾

**本质**：客服 Agent 的核心矛盾，是「LLM 的概率性输出」与「业务动作的确定性要求」之间的冲突。模型可以猜，退款不能猜。

**六条章级原则**（贯穿全章，冲突时以这六条为准）：

1. **概率负责决策，确定性负责执行**——模型的输出必须经过确定性校验（Schema、阈值、状态机）才能变成动作。**未经校验的模型输出永远不是「已完成」**。
2. **有副作用的动作必须可幂等、可审计、可补偿**——退款、发邮件、改地址，缺一个都不能上线。
3. **规则在代码层，不在 Prompt 里**——Prompt 可以被注入内容覆盖或诱导；安全规则、金额阈值、审批权限必须落在代码/策略层。
4. **上下文是预算，不是容器**——每次注入都要算钱。上下文成本随轮数二次增长，裁剪把它压回线性（§22.3.14）。
5. **不确定就交出去**——置信度不足、连续失败、政策未命中，宁可转人工也不要编。**「不知道」必须能被识别，不能被润色掉。**
6. **每一步都要能重放**——事件、Checkpoint、审计三者齐全，任何动作都能回答「当时基于什么、谁批准、为什么」。

**三个不等式**：

```
LLM 的自由度  >>  业务动作的容错度     → 模型可以猜，退款不能猜
工单轮数      >>  上下文窗口能装的轮数   → 不裁剪则成本按 O(n²) 爆炸
用户能接受的等待  <<  Agent 深度推理耗时  → 首响必须快，长任务必须异步
```

**三个放大器**（本章最贵的量都藏在这里）：

| 放大器 | 说明 | 后果 | 量化 |
|---|---|---|---|
| **上下文放大** | 每轮把历史与工具结果重新注入 | token 成本随轮数二次增长 | 无裁剪 O(n²)、裁剪后 O(n)；20 轮工单比 4 轮贵 17 倍（§22.3.14） |
| **副作用放大** | 一句话可能触发退款、改址、开票 | 一次误判 = 真金白银 | 幂等键 + 审批 + 快照三层兜 |
| **信任放大** | 模型把工具结果当指令执行 | 一次注入 = 一次越权 | 外部数据不可信 + 规则在代码层 |

> **本章与第 02、04、05 章的放大器方向不同**：Feed 是读放大，秒杀是写放大，广告是请求/写/查询三层放大。**Agent 章的放大器是上下文放大**——它是唯一一个「用户多聊两句，成本就翻倍」的架构。

**三层正确性**（必须分开保证）：

| 层次 | 要求 | 保障手段 |
|---|---|---|
| 答案正确 | 事实、政策、引用准确 | RAG + 引用 + 自省 + 人工兜底 |
| 动作正确 | 工具选对、参数对、只执行一次 | JSON Schema + 幂等键 + 状态机 |
| 权限正确 | 不越权、不绕过审批 | 代码层策略 + 审批 + 租户隔离 |

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 自动化 vs 正确性 | 全自动省人但风险高 | 风险分级，高风险 HITL | 低风险场景可全自动 |
| 延迟 vs 推理深度 | 多步推理慢 | 首响快、长任务异步 | 复杂工单可接受分钟级 |
| 上下文完整 vs 成本 | 全量历史贵 | 三层记忆 + 裁剪 | 短会话可全量 |
| 自治 vs 可控 | Agent 自主但可能越权 | 工具白名单 + 审批 | 只读工具可放宽 |
| 一致 vs 并发 | 多 Worker 同时推进 | 按 ticket 串行 + 版本号 | 不同工单可并行 |
| 知识时效 vs 索引成本 | 频繁重建贵 | 增量索引 + 版本化 | 小知识库可全量 |
| 安全 vs 体验 | 验证多则摩擦 | 风险分级 | 高价值操作强制 |
| 通用 vs 领域 | 通用模型泛化好但不准 | 领域 Prompt + 工具 + RAG | 通用问答可放宽 |

**七类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| 幻觉 | 编造政策/订单状态 | 无依据生成 | 强制引用、低置信转人工 |
| 工具误选 | 该查订单却调退款 | 意图/工具描述不清 | 工具白名单、少样本、评测 |
| 参数错误 | 退款金额/订单号错 | 抽取错误、未校验 | JSON Schema、二次确认 |
| 越权 | 绕过审批直接退款 | Prompt 被绕过 | 代码层策略，不靠 Prompt |
| 提示注入 | 工具结果里藏指令 | 外部数据不可信 | 数据包裹、来源标注 |
| 死循环 | 反复调用同一工具 | 无终止条件 | 最大步数、token 预算、超时 |
| 上下文污染 | 用旧参数执行新动作 | 状态过期 | 版本号、恢复前校验 |

**自动化分级**：

| 级别 | 说明 | 人工参与 | 适用 |
|---|---|---|---|
| L0 | 纯人工 | 全部 | 法律、投诉、高危 |
| L1 | 辅助推荐 | 人工确认后发送 | 新人坐席、复杂问题 |
| L2 | 半自动 | 低风险自动，高风险确认 | 主流生产形态 |
| L3 | 自动 + 抽检 | 仅异常介入 | 成熟场景 |
| L4 | 全自动 | 事后审计 | 极低风险、标准化 |

**为什么「把规则写进 Prompt」不够**（章级原则 3 的完整论证）：

- Prompt 可以被注入内容覆盖或诱导。
- 模型输出不稳定，同一输入可能不同结果。
- 审计需要确定性证据，不能依赖「模型说它遵守了」。
- 结论：**安全规则、金额阈值、审批权限必须落在代码/策略层，Prompt 只做提示**。

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| LLM token | 最大 | 模型分级、缓存、上下文裁剪 |
| 向量检索/重排 | 中 | 候选集控制、缓存 |
| 工具调用 | 中 | 并发、结果缓存 |
| 存储与日志 | 小 | 分层、TTL |
| 人工兜底 | 视转人工率 | 提升自助率、知识质量 |

### 22.3 理论与方法论

#### 22.3.1 S0：七项前置锚点

先落定七件事，它们共同决定**可行域**——不在可行域内的方案不参与讨论。

| # | 锚点 | 本章答案 | 影响 |
|---|---|---|---|
| 1 | **业务目标与成功标准** | 自助解决率 60%、转人工率 < 25%、错误退款 0 | 决定自动化分级与 HITL 边界 |
| 2 | **规模量级** | 日工单 100 万、峰值 58 QPS、平均 6 轮对话、每工单 4 次 LLM 调用 | 决定队列、Worker 数、模型配额与 token 预算 |
| 3 | **质量属性优先级** | 不越权 > 不重复执行 > 不超支 > 体验 > 成本 | 决定降级顺序与 fail-closed 边界 |
| 4 | **硬约束** | 退款等有副作用动作须可审计可回滚；PII 最小化与留存期；多租户隔离；录音与对话留存 | 定义可行域；合规要求不可用技术折抵 |
| 5 | **不可逆决策清单** | 见 §22.1 的本章七项 | 决策流程：多评审 + 原型 + 迁移方案 |
| 6 | **核心路径与事实源** | 核心路径 = 接入 → 编排 → 执行 → 审批 → 执行 → 通知；事实源 = **工单表 + 工具调用记录 + 审批记录** | 决定缓存与对账对象；Checkpoint 与知识索引全是投影 |
| 7 | **竞争与协作边界** | 支付渠道、订单主数据、知识内容生产在外部；接入、编排、执行、工具、审批、审计自建 | 决定服务边界与团队成本 |

> **第 2 项为什么改变答案**：1 万工单/天时，「全量上下文塞进 Prompt」毫无成本；100 万工单/天、平均 6 轮对话时，同一个做法每天烧掉 400 亿输入 token。**Agent 的规模参数不只是并发，还有「会话长度」——后者决定成本曲线是线性还是二次。**

#### 22.3.2 4S 收敛顺序

```
S0 定题（锚点 + 不可逆清单）
   → Scenario 定工单量、轮数分布、风险等级、自动化目标
      → Service 定接入、编排、执行、人工协同的边界
         → Storage 定工单、Checkpoint、审批、知识索引的唯一事实源
            → Scale 定队列、并发、模型配额、上下文预算、降级
```

#### 22.3.3 Scenario：场景与规模

| 维度 | 数值 | 推导与来源 |
|---|---|---|
| 日工单量 | 100 万 | — |
| 平均工单 QPS | 100 万 ÷ 86400 | ≈ **11.6** |
| **峰值工单 QPS** | 11.6 × 5 | **58**（峰值系数 5：晚高峰 3 小时承载当日 45%，叠加营销活动脉冲） |
| 渠道 | 网页、App、IM、邮件、电话转写 | 渠道数决定适配器与归一成本 |
| 意图分布 | 咨询 60%、订单 25%、退款 10%、投诉 5% | **风险不均：15% 的工单要 HITL** |
| 会话长度分布 | 4 轮 60% / 8 轮 30% / 20 轮 10% | **直接决定 token 成本曲线（§22.3.14）** |
| 每工单 LLM 调用 | 平均 4 次 | 分类 + 规划 + 生成 + 反思 |
| 自动化目标 | 自助解决率 60%，转人工率 < 25% | 决定 L2 半自动为主流形态 |
| 风险等级 | 退款/改址为高风险，需审批 | 决定 HITL 阈值 |
| 语言 | 中英，后续多语言 | 每加一门语言，工具与知识库各翻一倍 |
| 合规 | 录音/对话留存、PII 保护、多租户隔离 | — |

> **「会话长度分布」是本章独有的关键参数**。传统系统的容量参数是 QPS，Agent 系统还必须给出**轮数分布**——否则 token 成本只能算平均值，而平均值会系统性低估长尾工单的代价。

#### 22.3.4 Service：服务与接口

| 服务 | 职责 | 同步/异步 | 关键点 |
|---|---|---|---|
| Channel Adapter | 渠道归一、协议适配 | 同步 | 幂等接入 |
| Ticket Service | 工单创建、状态、分配 | 同步 | `ticket_id`、唯一索引 |
| Orchestrator | 鉴权、限流、意图路由 | 同步 | 快速返回，不跑 Agent |
| Task Queue | 任务排队、优先级 | 异步 | 分区、可见性超时 |
| Agent Worker | 执行 Agent 循环 | 异步 | 无状态、Checkpoint |
| Tool Gateway | 工具注册、鉴权、限流 | 同步 | 白名单、Schema、幂等 |
| RAG Service | 检索、重排、引用 | 同步 | ACL、混合召回 |
| HITL Service | 审批、转人工 | 异步 | 挂起/恢复、快照 |
| Audit Service | 全链路审计 | 异步 | 不可篡改 |
| Budget Service | token / 步数 / 时长预算 | 同步 | 超预算即降级 |

**同步/异步边界**：

- 同步：接入、鉴权、意图路由、只读工具、审批提交。
- 异步：Agent 循环、生成回复、通知、审计、报表。
- 判断标准：用户在等吗？失败能补偿吗？会不会产生副作用？

**核心 API**：

| 方法 | 路径 | 说明 | 幂等 |
|---|---|---|---|
| POST | `/api/v1/tickets` | 接入工单，返回 `ticket_id` | 是（`source + external_id`） |
| GET | `/api/v1/tickets/{id}` | 查询状态 | 只读 |
| POST | `/api/v1/tickets/{id}/messages` | 追加用户消息 | 是（`message_id`） |
| POST | `/api/v1/approvals/{id}/approve` | 审批通过 | 是（幂等键 + 快照） |
| POST | `/api/v1/approvals/{id}/reject` | 审批驳回 | 是 |
| POST | `/api/v1/tickets/{id}/handoff` | 转人工 | 是 |
| POST | `/api/v1/tickets/{id}/resume` | 审批后恢复执行 | 是（校验 `state_version`） |

#### 22.3.5 Storage：数据模型

| 数据 | 存储 | 事实源 / 投影 | 关键设计 |
|---|---|---|---|
| 工单 | MySQL | **事实源** | `ticket_id` 主键，`(source, external_id)` 唯一 |
| 消息 | MySQL / 文档库 | **事实源** | 按 `ticket_id` 分区，时间序 |
| 工具调用记录 | MySQL | **事实源** | `tool_call_id` 唯一，含参数与结果 |
| 审批记录 | MySQL | **事实源** | `approval_id`、参数快照、状态、批注 |
| 审计日志 | 日志 / 数仓 | **事实源** | 不可篡改，保留 180 天+ |
| 任务 | MySQL / Redis | 投影 | `task_id`、状态、优先级 |
| Checkpoint | PostgreSQL / Redis / 对象存储 | 投影（可重建但代价高） | 每步快照，带 `state_version` |
| Refresh 后的会话上下文 | Redis | 投影 | 短期缓存，丢则重算 |
| 知识索引 | 向量库 + 倒排 | 投影 | 文档块 + ACL 元数据 |
| 队列消息 | Kafka / RabbitMQ | 投影 | 可重放 |

> **Checkpoint 是投影但不是「随便丢」的那种投影**——它丢了任务就恢复不了，只能人工接管。所以它有独立保留期、独立容量规划与独立监控，不能当缓存对待。

**任务三级模型**：

```
Ticket（工单：一个用户诉求的完整生命周期）
  └→ Task（一次处理请求：一次「读懂 + 规划 + 执行」）
       └→ Step（最小可重试单元：一次 LLM 决策 或 一次工具调用）
```

> **三级模型是幂等与恢复的基石**：幂等键要落在 Step 级（`ticket_id + step_id + tool_call_id`），Checkpoint 落在 Task 级，审计落在 Step 级。粒度错了，重复执行与恢复就都做不对。

**工单表**：

```sql
CREATE TABLE tickets (
  ticket_id    BIGINT PRIMARY KEY,
  source       VARCHAR(16) NOT NULL,
  external_id  VARCHAR(128) NOT NULL,
  user_id      BIGINT NOT NULL,
  channel      VARCHAR(16) NOT NULL,
  status       TINYINT NOT NULL DEFAULT 0,
  priority     TINYINT NOT NULL DEFAULT 0,
  risk_level   TINYINT NOT NULL DEFAULT 0,   -- 0 低 1 中 2 高（高风险必审批）
  tenant_id    BIGINT NOT NULL,
  created_at   BIGINT NOT NULL,
  UNIQUE KEY uk_source_external (source, external_id),
  KEY idx_tenant_status (tenant_id, status)
);
```

#### 22.3.6 Scale：扩展与兜底

| 维度 | 手段 | 触发条件（量化） |
|---|---|---|
| 接入 | 无状态网关、水平扩容 | 入口 P99 > 200ms 或 CPU > 60% |
| 执行 | Worker 池、分区消费 | 队列等待 > 30s |
| 隔离 | 按租户/优先级分队列 | 单租户占比 > 20% 或其等待 > 其他租户 3 倍 |
| 限流 | 令牌桶、并发上限 | 队列深度 > 10000 或 LLM 调用超配额 |
| 成本 | 模型分级、缓存、上下文裁剪 | 单工单 token > 预算 120% |
| 预算 | 每工单最大步数/token/时长 | 超预算即降级 |
| 降级 | 模板回复、转人工、只读 | 模型/工具/队列故障 |

#### 22.3.7 Agent 架构模式

| 模式 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| ReAct | 思考 → 行动 → 观察循环 | 灵活、可解释 | 步数多、成本高 | 工具型任务 |
| Plan-Execute | 先规划再执行 | 全局视角 | 计划可能过期 | 多步复杂任务 |
| Router | 先分类再分派 | 简单、快 | 覆盖有限 | 意图清晰场景 |
| Workflow | 预定义流程 + LLM 填参 | 可控、可审计 | 灵活性低 | **高风险标准流程** |
| Multi-Agent | 多角色协作 | 分工专业 | 协调复杂、成本翻倍 | 大型复杂场景 |

**生产建议**（本章的默认形态）：

```
Router（意图分流）
  ├─ FAQ/咨询      → RAG 直答（不进入 Agent 循环）
  ├─ 订单/物流查询 → Workflow（固定只读工具，最稳最省）
  ├─ 退款/改址    → Workflow + HITL（高风险，动作固定）
  └─ 投诉/复杂/低置信 → 转人工
```

> **越少用 Agent 循环越好**。ReAct 的灵活性和成本都是线性甚至二次的增长，而客服场景的意图分布高度集中（咨询 60%），用 Workflow 覆盖高频标准动作、用 Agent 处理长尾，比「全部走 Agent」便宜一个数量级且更可控。

#### 22.3.8 工单接入与异步任务

- **接入方式**：Webhook 推送（实时）、API 轮询（兼容老系统）、消息队列订阅。
- **同步 vs 异步**：接入层只做校验、落库、返回 `ticket_id`，**不在请求线程里跑 Agent**；耗时任务全部异步化。
- **去重**：`source + external_id` 幂等键，重复消息直接返回已有工单。
- **优先级**：VIP、投诉、超时工单优先；按租户隔离队列。
- **接入不做业务判断**：渠道适配器只负责把五种渠道归一成统一消息模型（channel、user_id、content、attachments、locale、priority），不解析意图、不查订单。

#### 22.3.9 队列与 Worker

| 队列 | 特点 | 适用 |
|---|---|---|
| Kafka | 高吞吐、可回放 | 事件流、审计 |
| RabbitMQ | 路由灵活、延迟低 | 任务分发 |
| Redis Stream | 轻量、易部署 | 中小规模 |
| SQS | 云托管 | 云上 |

**Worker 设计**：

- 无状态，水平扩容；按租户/优先级分队列。
- 心跳 + 可见性超时，防止消息被重复消费。
- 长任务拆 Step，每步落 Checkpoint。
- 消费成功后 ack；失败重试；超次数进死信。

**Worker 崩溃的三重兜底**：

| 兜底 | 机制 | 兜住什么 |
|---|---|---|
| 可见性超时 | 消息超时未 ack 自动重投 | 进程被 kill -9 |
| 启动扫描 | 启动时扫 `RUNNING` 超时任务 | 宕机后卡住的任务 |
| Checkpoint | 从最后一步恢复 | 重跑代价（不重复副作用） |

> 三层缺一不可：只有可见性超时，重投的消息可能从第 1 步重跑；只有启动扫描，进程内的消息会永久卡住；只有 Checkpoint，重投时无法知道做到哪一步。**Checkpoint 是唯一保证「不重复副作用」的那一层。**

#### 22.3.10 状态机、Checkpoint 与恢复

**状态机**：

```
PENDING → RUNNING → WAITING_TOOL → RUNNING → RESOLVED
              ↓            ↓
           RETRYING     WAITING_HUMAN → RESOLVED / CLOSED
              ↓
           FAILED → DEAD_LETTER
```

- 每次状态变更写库（带 `version`），支持断点续跑。
- 重试：指数退避 + 随机抖动，区分可重试（超时/限流）与不可重试（参数/权限）。
- 超过最大次数进 DLQ，人工介入或补偿。
- Worker 崩溃靠可见性超时重新投递；启动时扫描 `RUNNING` 超时任务。

**重试公式**：

```
delay = min(cap, base × 2^attempt) + random_jitter
```

**Checkpoint 结构**：

| 字段 | 作用 |
|---|---|
| `step_id` | 当前步骤 |
| `state_version` | 全局单调递增，防并发覆盖 |
| `tool_calls_plan` | 每个工具的状态 |
| `completed_results` | 按 `tool_call_id` 索引的结果快照 |
| `pending_approvals` | 待人工处理项 |
| `messages` | 上下文消息 |
| `fact_slots` | 结构化事实槽位 |
| `token_usage` | 成本累计 |

**工具状态**：PENDING / WAITING_APPROVAL / APPROVED / REJECTED / RUNNING / SUCCEEDED / FAILED / COMPENSATED。

任何审批回调、工具完成回调或超时事件更新 Checkpoint 时，都必须校验 `state_version` 或按 `ticket_id` 串行；只有 `pending_approvals` 全部清空，任务才回到完整的 `RUNNING` 循环。

**恢复时的三条硬规则**：

1. **恢复前重新校验状态**：从 Checkpoint 恢复时，先校验外部世界有没有变（订单是否已退款、政策是否已改、库存是否还在），而不是直接信任快照。
2. **副作用动作一律先查幂等表**：恢复时如果 `executed_actions` 里已有该 `tool_call_id`，直接复用结果，不重发。
3. **版本不匹配就停**：Checkpoint 的 `state_version` 与库里的当前版本不一致时，**停止执行并转人工**，绝不「以最新的为准」强行继续。

#### 22.3.11 幂等与并发

**幂等三件套**：

1. 幂等键（`ticket_id + action + step`，工具级用 `ticket_id + step_id + tool_call_id`）。
2. 唯一索引 / 去重表。
3. 状态机条件更新（`UPDATE ... WHERE status = 'PENDING'`）。

**并发控制**：

- 同一工单串行、不同工单并行。
- 乐观锁 `version`，冲突重试。
- 分布式锁按 `ticket_id` 粒度，注意锁超时与归属校验。
- 分区消费保证同一工单落到同一分区。

> **幂等键的粒度是本章最容易做错的一处**。若键只到 `ticket_id`，同一工单里的两次合法退款（先退部分、后退剩余）会被误判为重复；若键只到 `tool_call_id` 而 `tool_call_id` 每次重试都新生成，则幂等完全失效。**正确粒度是 `ticket_id + step_id + tool_call_id`——同一工单、同一步骤、同一个调用意图，三者齐一才判定为重复。**

#### 22.3.12 HITL、部分挂起与 DAG

**工具分类**：

| 类别 | 示例 | 策略 |
|---|---|---|
| `SAFE_AUTO` | 查询订单、查物流、查政策 | 直接执行 |
| `HIGH_RISK_APPROVAL` | 退款、改地址、发邮件、改权限 | 挂起审批 |

**部分挂起流程**：

1. 安全动作先行：只读/低风险工具执行，结果写入 `completed_results`。
2. 高风险动作进 `pending_approvals`，绑定 `tool_call_id`、`idempotency_key`、`approval_id`。
3. 任务置 `WAITING_FOR_HUMAN`，释放 Worker。
4. 依赖高风险结果的下游动作延后。
5. 审批完成后回填结果，唤醒 Agent 继续。

**依赖顺序**：

- **阶段门禁**：Stage 1 只读探测 → Stage 2 风险评估/审批挂起 → Stage 3 副作用执行与通知。
- **DAG/拓扑顺序**：`depends_on` 或参数占位；前置未完成/未获批时，下游保持 `BLOCKED/PENDING`，绝不越级执行。
- **审批快照**：涉及资金/权限的参数以审批时快照为准，防「审批看 A 参数、执行变 B 参数」。

**失败补偿（Saga）**：

- 高风险工具失败：带原 `idempotency_key` 退避重试；仍失败则回填错误、状态 `FAILED` 或转人工，不静默当作成功。
- 前半成功、后半失败：为可逆写操作定义补偿工具（`cancel_freeze`/`reverse_action`），按逆序补偿并记录审计。
- 不可逆动作（已发邮件、已打款）记录异常交人工/对账，不能假装回滚完成。
- 部分审批通过/驳回：逐条记录 `tool_call_id` 的审批状态与批注，写回 Checkpoint。

**挂起不是阻塞**：任务挂起时必须**释放 Worker**，否则一个待审批工单会长期占住一个执行槽位，在审批高峰期直接打满 Worker 池。挂起 = 状态落库 + 队列消息移除，恢复 = 审批回调重新入队。

#### 22.3.13 工具契约与设计

| 项 | 要求 |
|---|---|
| 描述 | 清晰说明用途、参数、限制、示例（描述本身就是模型的说明书） |
| Schema | JSON Schema 严格校验，枚举/范围/格式 |
| 权限 | 工具白名单、按角色/租户授权、按金额阈值 |
| 幂等 | 写操作必须接受 `idempotency_key` |
| 超时 | 每个工具独立超时，避免拖垮链路 |
| 返回 | 结构化、精简、含错误码 |
| 审计 | 参数、结果、耗时、调用者全记录 |

**敏感工具二次确认**：退款、改地址、发送外部邮件、修改权限。

**工具契约的版本演进**（不可逆决策，见 §22.1）：

| 变更类型 | 是否兼容 | 处理 |
|---|---|---|
| 新增可选字段 | 兼容 | 直接上线 |
| 新增必填字段 | **不兼容** | 双版本共存，老调用补默认值 |
| 改字段语义 | **不兼容** | 视为新工具名，旧工具保留一个版本周期 |
| 删字段 | **不兼容** | 先停止写入、观察、再删 |

> **工具改名等于换模型**。工具名与描述是模型选择工具的主要依据，改名或改描述会让模型的行为发生难以预测的变化。**因此工具契约变更必须走与 Prompt 变更同级的回归流程**（§22.3.19、§22.6.3），而不是当作普通发版。

#### 22.3.14 上下文治理：三层记忆与上下文放大

**本节是上下文治理的权威版**，§22.4.7 与 §22.5.4 只引用。

**三层记忆**：

| 层 | 内容 | 作用 |
|---|---|---|
| 结构化事实槽位 | 已确认订单号、金额、政策、已执行动作、待办 | 锁定硬状态，防旧值污染 |
| 增量滚动摘要 | 滑出窗口的早期轮次压缩 | 保留推理脉络与诉求演进 |
| 近期完整交互 | 最近 K 轮完整 user/assistant/tool | 保证当前工具链细节完整 |

**事实槽位字段**：

- `entities`：订单号、用户 ID、工单号、金额、商品/账户标识。
- `confirmed_constraints`：已核实规则（「7 天无理由已过」「余额 120 元」）。
- `executed_actions`：已生效副作用（「已提交退款单号 RF-882」），防止重复调用。
- `open_issues / pending_items`：未闭环问题。

**触发与更新**：

- 触发：窗口溢出（超过 K 轮）或 Token 达到预算 75%–80%。
- 顺序：先裁剪超长 tool 结果 → 仍超限再压缩早期轮次。
- 增量：只把新滑出的 `delta_turns` 与当前 `fact_slots + rolling_summary` 做增量合并。
- 槽位：新事实写入；可信新值覆盖并记录变更；`executed_actions` 高保护；失效假设及时清理。
- 摘要：200–400 token，记录「做了什么尝试、遇到什么阻碍、推进到哪一步」。

**三种方案对比**：

| 维度 | 滑动窗口 | 纯滚动摘要 | 事实槽位 + 增量摘要 |
|---|---|---|---|
| 精确 ID/金额/状态 | 滑出即丢 | 易被改写 | 高（结构化锁定） |
| 多步排查脉络 | 较弱 | 较好 | 好 |
| 防重复调用 | 较差 | 一般 | 强 |
| Token 成本 | 最低 | 中 | 中低 |

**注入方式**：放在 System Prompt 之后、近期对话之前，用 JSON/分隔区块标记，并声明「以下为历史状态，仅作参考；高风险操作仍须遵循系统规则与当前最新输入」。

---

**上下文放大：Agent 系统最贵的那个量**

设每次 LLM 调用的输入 = 固定部分 C（system prompt 800 + 事实槽位 300 = 1100）+ 已发生轮次 × 每轮新增 L（user 80 + assistant 200 + tool 结果 1200 = **1480**）。

| 策略 | 第 i 次调用的输入 | 一个 n 轮工单的总输入 |
|---|---|---|
| **不裁剪** | C + i·L | `n·C + L·n(n+1)/2` → **O(n²)** |
| **裁剪（保留 K=4 轮）** | C + min(i, K)·L（+ 滚动摘要 400） | **O(n)**，常数被 K 锁住 |

代入实际数字：

```
无裁剪：第 i 次输入 = C + i·L          →  n 轮总输入 = O(n²)
  n=4    19,200
  n=12  128,640
  n=20  332,800

裁剪（保留 K=4）：第 i 次输入 = C + min(i,K)·L   →  n 轮总输入 = O(n)
  n=4    19,200   ← 没超过 K，裁剪白做
  n=12   78,560   ← 省 39%
  n=20  137,920   ← 省 59%
```

| 工单轮数 n | 不裁剪输入 token | 裁剪后（K=4） | 节省 |
|---|---|---|---|
| 4 | 19,200 | 19,200 | 0%（没超过 K，裁剪白做） |
| 8 | 62,080 | 48,880 | **21%** |
| 12 | 128,640 | 78,560 | **39%** |
| 20 | 332,800 | 137,920 | **59%** |

> **两个必须写进方案的结论**：
> 1. **不裁剪时，第 20 轮的工单比第 4 轮的贵 17.3 倍；裁剪后只贵 7.2 倍。** 裁剪的价值不是「更便宜」，而是**让成本与轮数解耦**——它把一条会失控的二次曲线压成直线。
> 2. **K 值是有代价的**：K=4 在 n=4 的短工单上完全没收益（19,200 = 19,200），只在 n > K 后才开始生效。所以 K 的取值应当按**实际轮数分布**定，而不是拍脑袋。**先量分布，再定 K。**

**上下文的另外两处冗余**（与轮次无关，但同样在烧钱）：

| 冗余来源 | 现状 | 优化 | 收益 |
|---|---|---|---|
| 工具结果冗余 | 一次工具返回 10KB（≈2500 token），模型实际只用 3 个字段 | 按字段裁剪 + 摘要 | 每工单省 ≈5200 token（占输入 13%） |
| 检索候选冗余 | top-20 候选 × 300 token = 6000 token 全进上下文，实际只有 5 份进答案 | 收敛到 top-5 后再注入 | 每工单省 ≈4500 token |

> **三条冗余的共同判据**：**进入上下文的 token 必须能被最终答案用到**。凡是「模型看不到也照样能答对」的内容，就不该进上下文——这是比任何调参都有效的一刀。

#### 22.3.15 工具结果回填与防注入

**回填规则**：

- 每个 `tool_call_id` 必须有对应的 `tool` 消息，即使失败/超时/被跳过，也要回填错误码与原因，否则部分模型 API 会报错或死循环。
- 回填内容含 `tool_call_id`、`tool_name`、执行状态（success/error/skipped）与精简结构化数据。
- 区分「查到空结果」与「接口报错」。

**防注入**：

- 外部数据不可信：工单内容、网页抓取、第三方接口、用户备注可能含对抗指令。
- 工具结果作为数据载荷包裹或标注来源。
- 核心规则与审批权限判定放在代码/策略层，不能依赖 Prompt 劝导模型。
- 敏感信息脱敏：手机号、身份证、完整卡号、内部 Token。

**防注入的三层纵深**：

| 层 | 手段 | 挡住什么 |
|---|---|---|
| 输入层 | 用户内容与工具结果一律标为「不可信数据」，与指令分区 | 直接注入 |
| 判定层 | 危险动作的判定在代码层做（金额、账号、资源归属） | 绕过模型的越权 |
| 处置层 | 检测到注入特征 → 丢弃该结果 + 转人工 + 告警 | 未知形态的注入 |

> **任何一层单独都不够**：输入层的标注可能被模型忽略，判定层挡不住「模型被说服去调用一个合法但不该调的工具」，处置层只是事后补救。**真正的安全底线是判定层——它与模型无关。**

#### 22.3.16 RAG 数据管道

**版面分析与多模态**：

- 复杂 PDF/PPT/扫描件需要版面检测、表格结构还原（行列合并、表头继承）与公式识别，输出带 H1–H3 层级和页码/章节锚点的结构化文本。
- 内嵌图表可生成「结构化摘要 + 原图链接」，支持图文联合检索。
- 增量更新：基于内容哈希增量重切分，避免全量重建。
- 权限继承：同步文档级 ACL 到索引元数据，检索阶段按用户权限过滤。

**混合分块**：

- 语义分块：按主题/语义断点切分，避免硬截断。
- 父子索引：子块 150–300 token 用于精确召回；命中后回溯父块 800–1500 token 送入 LLM。
- 基线：固定窗口 300–800 token + 10%–20% overlap、按标题层级切分、表格/代码单独处理。

**摄入流水线**：

```
数据源 → 连接器（增量/ACL）→ 解析（版面/OCR/表格/公式）
      → 清洗/脱敏 → 分块（父子）→ 向量化/索引
      → 元数据（来源、版本、ACL、页码/锚点）
```

**常见坑**：OCR 错误、表格跨页、标题层级丢失、权限不同步、重复文档、版本冲突。

#### 22.3.17 混合检索与重排

| 召回 | 擅长 | 短板 |
|---|---|---|
| 稠密向量 | 同义、语义相似 | 精确型号/错误码易漂移 |
| 稀疏 BM25 | 专有名词、编号、短语 | 语义泛化弱 |
| 知识图谱 | 多跳关系、全局主题 | 构建成本高 |

**融合**：RRF（Reciprocal Rank Fusion）。

```
score(d) = Σ 1 / (k + rank_i(d)),  k 常取 60
```

**重排**：

- Bi-Encoder 大规模粗筛。
- Cross-Encoder 对 `(Query, Candidate)` 细粒度打分，Top-50 精排为 Top-5~8。
- 计算量大，只对候选集使用；高频 Query 可缓存。

**指标与权限**：Recall@K、MRR、NDCG、引用准确率；**先 ACL 过滤再检索/重排**（顺序反了会先召回再过滤，白费算力且有泄漏风险）。

#### 22.3.18 Agentic RAG 闭环

**查询改写与路由**：

- 模糊/多意图问题做查询扩展或子问题拆解。
- 路由到对应知识域（财务制度、SRE 手册、产品文档），避免跨库噪声。
- 多轮对话结合历史改写指代。

**自省与纠错（Self-Reflection / CRAG）**：

- 检索后评估证据充分性与相关性。
- 命中为空或不足时，触发改写重检、补充检索，或明确告知「知识库无足够依据」，严禁编造。
- 评分维度：相关性、覆盖度、矛盾检测。
- 设置最大改写次数，仍失败转人工。

**强制引用**：

- 核心断言绑定文档 ID + 片段 ID + 页码/锚点。
- 前端支持点击跳转原文。
- 用引用覆盖率、引用准确率评测。
- 无引用/低置信度回答降级为「建议转人工」。

```
Query → 改写/路由 → 混合召回 → Rerank → 证据评估
   ↑                                         │ 不足
   └──────────── 改写/补检 ←─────────────────┘
                                             │ 充分
                                生成 + 引用 → 用户反馈 → 知识库更新
```

#### 22.3.19 评估方法

**离线评测**：

- 黄金集：500 条历史工单，标注意图、应调工具、关键参数、期望答案/政策。
- 指标：意图准确率、工具选择准确率、参数准确率、任务完成率、幻觉率、政策违规率。
- 回归：每次 Prompt/模型/工具变更跑一遍。

**在线评测**：

- 一次解决率、转人工率、CSAT、平均处理时长、关键动作成功率、单工单成本。
- A/B：按租户/流量分桶；护栏指标（投诉率、违规率）。

**安全评测**：提示词注入、越权退款、PII 泄露、恶意链接；红队测试。

**黄金集怎么建**：不是人工标 500 条就完事——**要先按意图、风险等级、渠道、轮数分桶**，否则 60% 的咨询类工单会把退款类的失败完全淹没。**分层指标（每桶单独看）比总体准确率有用得多。**

#### 22.3.20 容量与成本模型

**本节是容量口径的权威版**，§22.5 与 §22.6 只引用。

**假设**：日工单 100 万，峰值系数 5，平均每工单 4 次 LLM 调用；system prompt 800 token、事实槽位 300 token、滚动摘要 400 token；每轮新增 1480 token（user 80 + assistant 200 + tool 结果 1200）；单次输出 600 token；保留 K=4 轮；模型价格输入 ¥2/百万 token、输出 ¥8/百万 token（示例价，需按实际模型替换）；轮数分布 4 轮 60% / 8 轮 30% / 20 轮 10%。

**一、流量与并发**

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均工单 QPS | 100 万 ÷ 86400 | ≈ 11.6 |
| **峰值工单 QPS** | 11.6 × 5 | **58** |
| **峰值 LLM 调用 QPS** | 58 × 4 | **232** |
| 并发任务数 | 58 QPS × 平均处理 60s | ≈ 3480 |
| Worker 数（每 Worker 10 并发） | 3480 ÷ 10 | ≈ **348** |

**二、上下文与 token**

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均输入 token/工单 | 0.6×19,200 + 0.3×48,880 + 0.1×137,920 | ≈ **4 万** |
| **输入 token/天** | 4 万 × 100 万 | **400 亿** |
| 输出 token/天 | 2,400 × 100 万 | **24 亿** |
| **合计 token/天** | — | **424 亿** |
| **LLM 成本/天** | 400亿/1e6×2 + 24亿/1e6×8 | **≈ 9.9 万元**（约 90 万元/月） |
| 模型分级后成本/天 | 60% 走小模型（¥0.5/¥2） | ≈ 5.5 万元，**省 45%** |

> **原文的 token 估算是错的**：按「100 万 × 4 次 × 3600 token」算出 144 亿/天，等于假设每次调用的输入恒定在 3000。**但第 2 次调用的输入已经包含第 1 轮的全部对话与工具结果**——输入是随轮次增长的。正确的量是 **424 亿/天，接近原文的 3 倍**，且成本从「几万元」变成「近 10 万元/天」。**这是本章最重要的一个估算修正。**

**三、存储**

| 指标 | 计算 | 结果 |
|---|---|---|
| 消息存储 | 100 万 × 10KB | ≈ 10GB/天 |
| Checkpoint 热数据 | 100 万 × 20KB × 7 天 | ≈ 140GB |
| 向量索引 | 500 万块 × 1.5KB | ≈ 7.5GB |

**四、结论**

1. **瓶颈在 LLM 配额与 token 成本，不在存储**——10GB/天的消息相比 9.9 万元/天的模型成本可以忽略。
2. **成本的第一杠杆是上下文裁剪**（O(n²) → O(n)，59%），第二是模型分级（45%），第三才是缓存。
3. **232 QPS 的 LLM 调用峰值决定了采购量**：按每模型实例 10 QPS 计，需 24 个实例并留 50% 余量 → 36 个。
4. **348 个 Worker 的并发是排队决定的，不是算力决定的**：算力瓶颈在模型侧，Worker 主要耗在等待上，因此 Worker 可以远少于「58 QPS × 60s」这个直觉数字所暗示的规模（348 已含 10 并发/Worker）。
5. **必须先量轮数分布**——它决定成本曲线的形状，也决定 K 值怎么取。

#### 22.3.21 不确定性管理与转人工决策

**不确定性的四个来源**：

| 来源 | 信号 | 阈值参考 |
|---|---|---|
| 意图识别 | 分类器置信度 | < 0.7 → 不路由，走澄清或转人工 |
| 检索充分性 | 证据覆盖度、自省评分 | < 0.6 或无命中 → 补检或转人工 |
| 工具选择 | 多次采样一致性 | Top-1 与 Top-2 分差 < 0.15 → 降级 |
| 参数抽取 | Schema 校验 + 交叉校验 | 校验失败或跨字段矛盾 → 二次确认 |

> **模型自报的置信度不可靠**。更稳的做法：用**分类器头**输出置信度，或**多次采样看一致性**（同一输入采样 3 次，工具选择不一致就降级）。把「模型说它有 95% 把握」当成置信度，是评测与线上表现脱节的主要来源。

**转人工的七个触发条件**：

```
意图置信度 < 0.7 ─┐
检索无依据       ──┤
参数校验失败     ──┤→ 澄清一次 ──仍不确定──→ 转人工（带完整上下文）
同工具同参 ×3    ──┤
用户明确要求     ──┤
情绪/合规命中    ──┘
```

| 触发 | 判定 | 动作 |
|---|---|---|
| 意图不明 | 置信度 < 0.7 | 先问一句澄清，仍不明则转人工 |
| 知识无依据 | 检索无命中或覆盖度低 | 明确告知无依据 → 转人工 |
| 参数校验失败 | Schema 失败或跨字段矛盾 | 二次确认 → 仍失败转人工 |
| 循环迹象 | 同工具同参重复 ≥ 3 次 | 立即中断并转人工 |
| 用户要求 | 关键词或显式按钮 | 立即转人工 |
| 高风险动作 | 金额/资源命中高风险 | 挂起审批（非转人工） |
| 情绪与合规 | 投诉、监管、法律词 | 直接转人工，不尝试自动处理 |

**转人工时必须带上什么**（否则用户要重复描述，CSAT 直接崩）：

| 必带 | 作用 |
|---|---|
| 完整对话上下文 | 坐席知道已经说过什么 |
| `fact_slots` 与 `executed_actions` | 坐席知道已经做了什么、哪些别重复 |
| 已尝试的工具与路径 | 坐席知道哪条路走不通 |
| 触发转人工的具体原因与置信度 | 坐席知道该看哪里 |
| Agent 的建议与下一步 | 缩短处理时间 |

> **转人工率是双面指标**。转人工率过低，往往意味着 Agent 在硬答（幻觉与错误投诉的先行指标）；转人工率过高，说明自动化没做起来。**必须与一次解决率、CSAT、投诉率一起看**，单看转人工率会得出相反的结论。

#### 22.3.22 安全与合规

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| 提示注入 | 工单内容/工具结果 | 数据包裹、规则在代码层 |
| 越权操作 | 冒充他人/绕过审批 | 身份校验、资源级鉴权 |
| PII 泄露 | 上下文/日志/回复 | 脱敏、最小化、审计 |
| 恶意工具参数 | 构造订单号/金额 | Schema、范围校验、二次确认 |
| 知识库投毒 | 写入错误文档 | 入库审核、来源可信度 |
| 模型窃取 | 大量试探 | 限流、异常检测 |

**越权的三道闸**（必须同时成立）：

| 闸 | 检查 | 失败动作 |
|---|---|---|
| 身份 | 调用者是不是该工单的用户 / 该租户 | 拒绝 |
| 资源归属 | 该订单/该资源是不是这个用户的 | 拒绝 |
| 金额与风险阈值 | 金额、动作类型、累计次数是否越线 | 挂起审批或拒绝 |

**PII 处理的五点**：

| 点 | 做法 |
|---|---|
| 采集即最小化 | 不收集就不用；位置、通讯录、设备指纹不进业务库 |
| 脱敏优先 | 入上下文与日志前脱敏（手机号、证件、卡号、地址） |
| 留存有期限 | 对话与录音 180 天，衍生画像更短，到期物理删除 |
| 导出与删除 | 用户可导出、可删除；删除要穿透到向量索引、缓存与归档（§22.3.16 的 ACL 元数据也要清） |
| 访问留痕 | 谁在什么时候看了哪个用户的对话 |

**多租户隔离的五个面**：

| 面 | 隔离方式 | 漏掉的后果 |
|---|---|---|
| 知识库 | 索引元数据带 `tenant_id`，检索前过滤 | 跨租户召回他人文档 |
| 工具 | 按租户授权 + 资源归属校验 | 跨租户调用业务接口 |
| 队列 | 分队列或分区键含租户 | 大租户挤占其他租户 |
| 配额 | 按租户的 token/并发配额 | 一个租户烧光全量额度 |
| 审计 | 日志带租户，审计查询按租户过滤 | 审计本身越权 |

**合规底线**：对话与录音留存期、跨境传输评估、审计不可篡改、错误退款为零、审批快照可举证。这五条不满足，Agent 就不该上线。

#### 22.4 工程落地与规则护栏

### 22.4 工程落地与规则护栏

#### 22.4.1 端到端链路

```
用户（网页/App/IM/邮件/电话）
  → 渠道适配器（归一化）
  → 工单接入（幂等、落库、返回 ticket_id）
  → Orchestrator（鉴权、限流、意图路由）
  → 任务队列（优先级、分区、租户隔离）
  → Agent Worker
      ├→ 上下文组装（三层记忆 + 预算检查）
      ├→ RAG（召回 → 重排 → 引用）
      ├→ LLM 规划（回复 / 工具 / 转人工）
      ├→ Tool Gateway（白名单、Schema、幂等、归属校验）
      ├→ HITL（挂起 / 审批 / 恢复）
      └→ Checkpoint（每步持久化）
  → 工单状态更新 / 回复 / 通知
  → 审计与指标
```

> **图里最重要的一行是「预算检查」**。它必须在上下文组装之前跑，而不是组装之后才发现超限——否则超限那一刻的 token 已经付掉了。

#### 22.4.2 接入层护栏

| 护栏 | 说明 |
|---|---|
| 幂等键 | `source + external_id` 唯一索引 |
| 鉴权 | 渠道签名、租户校验 |
| 限流 | 按渠道/租户/用户三维 |
| 内容安全 | 敏感词、附件病毒扫描 |
| 快速返回 | 只落库，不同步跑 Agent |

#### 22.4.3 编排层护栏

- 意图路由：FAQ → RAG；订单/退款 → 业务 Agent；投诉/法律 → 人工。
- 低置信度、连续失败、用户主动要求 → 转人工（触发条件见 §22.3.21）。
- 租户隔离：知识库、工具、配额按租户隔离。
- 预算：单工单最大步数、token、时长（§22.4.10）。

#### 22.4.4 执行循环护栏

| 限制 | 建议值 | 作用 |
|---|---|---|
| 最大步数 | 8–12 | 防死循环 |
| 单步 LLM 超时 | 10s | 防卡死 |
| 单次工具超时 | 3s | 防拖垮链路 |
| **单工单总时长** | **2min（不含审批等待）** | 与 SLO「异步任务完成 P95 < 2min」对齐 |
| Token 预算 | 按模型定（超 120% 告警） | 控成本 |
| 工具并发 | 3–5 | 防下游压力 |
| 重复调用检测 | 同工具同参 | 防循环 |
| **挂起即释放 Worker** | — | 防审批高峰打满 Worker 池 |

#### 22.4.5 工具层护栏

- 白名单：只暴露必要工具。
- Schema：严格校验类型、范围、格式。
- 权限：按角色/租户/金额阈值；**归属校验在代码层**。
- 幂等：写操作必须带 `idempotency_key`。
- 二次确认：敏感工具必须 HITL。
- 审计：参数、结果、耗时、调用者。
- 超时与熔断：下游故障快速失败。

#### 22.4.6 回填与注入防护

- 每个 `tool_call_id` 都有回填，失败也要回填错误码。
- 工具结果包裹为不可信数据，标注来源。
- 规则与审批在代码层强制执行。
- 脱敏后再进上下文。
- 检测到注入特征时，丢弃该结果并转人工。

#### 22.4.7 上下文裁剪落地

方案见 §22.3.14，本节只列执行步骤：

| 步骤 | 动作 |
|---|---|
| 1 | 估算 token，预留输出与余量 |
| 2 | 裁剪工具输出（字段/摘要/截断） |
| 3 | 折叠早期轮次进增量摘要 |
| 4 | 仍超限 → 重置上下文或转人工 |
| 5 | **记录裁剪原因与影响**（哪次调用被裁了、丢了什么） |

> 第 5 步常被省略，但它是**唯一能解释「为什么同一个问题两次答案不同」的线索**。没有裁剪记录，线上问题只能靠猜。

#### 22.4.8 人工协同

- 审批队列：按风险、金额、等待时长排序。
- 审批视图：订单、政策、金额快照、Agent 建议。
- 审批超时：过期后回到 Agent 或转人工。
- 转人工：携带完整上下文与已执行动作，避免用户重复描述（清单见 §22.3.21）。

#### 22.4.9 降级矩阵

**本节是降级的权威版**，§22.5.5 只引用。

| 故障 | 影响 | 降级 | 用户看到什么 |
|---|---|---|---|
| LLM 不可用 | 无法生成 | 模板回复 + 转人工 | 收到固定话术或被转人工 |
| LLM 限流 | 排队变长 | 降级到小模型 + 排队上限 | 首响变慢，但不至于无响应 |
| 向量库不可用 | 无法检索 | 关键词检索 / FAQ 兜底 | 回答变泛或明确说「暂时查不到」 |
| 工具下游故障 | 无法执行 | 只读 + 转人工，**不假装成功** | 明确告知处理中或转人工 |
| 队列积压 | 处理延迟 | 扩容消费者、优先级调度 | 首响变慢 |
| 审批系统故障 | 高风险阻塞 | 暂停高风险动作，保留只读 | 高风险请求排队等待 |
| Checkpoint 存储故障 | 无法恢复 | 停止长任务，短任务内存执行 | 短任务照常，长任务转人工 |
| 上下文超限 | 任务失败 | 裁剪 → 摘要 → 重置 → 转人工 | 可能收到较简略的回答 |
| 预算耗尽 | 成本失控 | 停止本工单并转人工 | 转人工，不静默截断 |

> **「不假装成功」是本章降级的第一原则**。工具超时后回答「已经为您退款」是本章最恶劣的失败模式——用户拿到一句假话，财务拿到一次对不上的账。**降级路径必须明确区分「成功」「失败」「进行中」三种状态。**

#### 22.4.10 延迟预算与超时降级

**本表是唯一的延迟口径来源**，其他小节只引用。

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 接入与渠道归一 | 50ms | 200ms | 429 / 落库失败提示 |
| 鉴权与意图路由 | 80ms | 300ms | 低置信 → 转人工 |
| 队列等待 | — | 30s | 超过上限 → 直接转人工，不无限排队 |
| **首响生成（首轮回复）** | **800ms** | **3s** | 模板回复兜底 |
| 单步 LLM 调用 | 1.5s | 10s | 中止本步 |
| 单次工具调用 | 500ms | 3s | 返回错误码，走补偿路径 |
| 单工单总时长（不含审批） | — | 2min | 转人工 |
| 审批等待 | — | 24h | 过期 → 回到 Agent 或转人工 |
| 含审批的总墙钟 | — | 10min | 转人工 |

> **预算与超时是两个数**：预算是正常情况下希望花多少，超时是超过就触发降级的硬限。两者必须满足「超时 ≥ 预算」。**「首响 3s」是用户可感知的承诺，「单工单 2min」是后台完成时间，两者不是同一个数**——原文把它们混在一起，是本章要修正的一处口径。

#### 22.4.11 观测与压测

**指标**：

| 类别 | 指标 |
|---|---|
| 接入 | QPS、去重率、失败率 |
| 队列 | 积压、等待时长、死信数 |
| 执行 | 步数分布、工具成功率、超时率、恢复次数 |
| 上下文 | 输入 token 分布、裁剪触发率、**每工单平均轮数** |
| RAG | 召回率、重排耗时、引用率 |
| 人工 | 转人工率、审批时长、驳回率 |
| 成本 | 单工单 token、单工单耗时、模型费 |
| 安全 | 注入拦截、越权拦截、PII 泄露 |

> **「每工单平均轮数」与「裁剪触发率」是 Agent 章特有的两个必看指标**：轮数分布右移意味着成本要涨，裁剪触发率上升意味着质量要掉。**它们比「token 总量」更能提前发现问题**——token 总量是结果，平均轮数是原因。

**压测**：

- 峰值 5 倍工单。
- LLM 限流与超时。
- 工具下游故障。
- 队列积压恢复。
- Worker 崩溃与恢复（验证 Checkpoint 与幂等）。
- 重复消息与重复审批。
- **长工单压测**（20 轮 + 大工具结果，验证上下文预算与裁剪）。
- **注入与越权红队**。

#### 22.4.12 规则护栏清单

| 领域 | 护栏 | 优先级 |
|---|---|---|
| **副作用安全** | 写操作必须幂等键 + 唯一索引 + 可补偿；**错误退款必须为 0**；工具失败不得回报成功 | **P0** |
| **审批与额度** | 高风险动作强制 HITL；金额阈值与审批快照；阈值变更需审批 | **P0** |
| **越权防护** | 身份 + 资源归属 + 金额阈值三道闸在代码层，模型无权绕过 | **P0** |
| **注入防护** | 外部数据标注为不可信；危险判定在代码层；命中注入特征即丢弃并转人工 | **P0** |
| **PII 与隐私** | 最小化采集、入上下文与日志前脱敏、留存期与到期删除、访问留痕 | **P0** |
| **多租户隔离** | 知识库 / 工具 / 队列 / 配额 / 审计五面隔离 | **P0** |
| **审计** | 决策与动作全量留痕、不可篡改、含参数快照与调用者 | **P0** |
| **幂等与恢复** | Step 级幂等键；每步落 Checkpoint；恢复前重校验外部状态；版本不匹配即停 | P1 |
| **上下文预算** | 每工单步数 / token / 时长三重预算；超预算即降级，不硬扛 | P1 |
| **工具契约** | 不兼容变更双版本共存；改名与改描述走回归流程 | P1 |
| **不确定性处置** | 置信度阈值与七类转人工触发；转人工携带完整上下文 | P1 |
| **评测** | 分层黄金集 + 每次变更回归 + 红队 | P1 |
| 成本 | 单工单 token 超预算 120% 触发容量评审 | P2 |

> **客服 Agent 的护栏几乎全是 P0**，因为它的失败模式直接落在「钱」和「隐私」上：一条越权退款是真金白银，一次 PII 泄露是合规事故。**这类护栏不存在「先上后补」的空间。**

#### 22.4.13 上线检查（10 问）

1. `source + external_id` 唯一索引是否生效？写工具是否全部带 Step 级幂等键？
2. 状态机与 Checkpoint 是否覆盖所有跃迁？**恢复前是否重新校验外部状态**？
3. 高风险工具是否强制 HITL？审批是否锁定参数快照？
4. 工具结果是否全部回填（含失败与跳过）？
5. 上下文是否设了三重预算？**裁剪触发是否留痕**？K 值是否按实测轮数分布定的？
6. 注入防护是否在代码层？归属校验与金额阈值是否绕过不了模型？
7. 转人工是否携带完整上下文、已执行动作与触发原因？
8. 审计是否覆盖决策与动作，且不可篡改？PII 是否在入库与入上下文前脱敏？
9. 降级路径是否演练过？**工具超时后是否确实回报失败而不是成功**？
10. 变更流程是否包含回归、影子与灰度？工具改名是否走了与 Prompt 同级的评审？

### 22.5 典型案例与端到端解决

#### 22.5.1 案例：电商退款工单

**场景**：用户对订单 #12345（实付 500 元、已签收、理由「商品破损」）发起退款。

```
用户 → 网页/IM/邮件 → 渠道适配器 → 工单接入
                                      │ 幂等键 source + external_id
                                      ▼
                                  工单库 ticket_id
                                      │
                                      ▼
                         Orchestrator（鉴权/限流/意图路由）
                                      │
                                      ▼
                              任务队列 → Agent Worker
                                      │
                     Observe → Think → Act 循环
                     ├─ get_order_detail（只读）
                     ├─ check_refund_policy（只读）
                     ├─ issue_refund（高风险，挂起审批）
                     └─ send_notification（依赖退款结果）
                                      │
                                      ▼
                          人工审批 → 恢复 → 执行退款 → 通知
```

**时序**：

1. **接入**：webhook 带 `source=web`、`external_id`；唯一索引防重复，重复请求返回已有 `ticket_id`。
2. **编排**：意图 `refund_request`，置信度 0.92；按租户/优先级入队；风险等级判定为「高」（涉及资金）。
3. **执行**：Worker 加载 Checkpoint；`get_order_detail` 返回已签收、实付 500、可退；`check_refund_policy` 返回符合条件，但金额 > 300 需人工审批。
4. **部分挂起**：只读结果写 `completed_results`；`issue_refund` 进 `pending_approvals`，绑定 `tool_call_id`、`idempotency_key`、金额快照 500；任务置 `WAITING_FOR_HUMAN`，**释放 Worker**。
5. **审批**：客服看到订单、政策、金额快照；通过后触发恢复事件。
6. **执行**：Worker 从 Checkpoint 恢复，**先重校验订单状态**（是否已被其他渠道退款），再带幂等键调用退款，返回 `refund_id=RF-882`；写回结果与 `executed_actions`。
7. **通知**：仅在退款成功后执行 `send_notification`；失败重试，不阻塞主状态。
8. **完成**：工单 `RESOLVED`，记录审计与耗时。

**异常路径**：

| 异常 | 处理 |
|---|---|
| 重复 webhook | `(source, external_id)` 唯一索引，返回已有工单 |
| Worker 崩溃 | Checkpoint 恢复；退款幂等，不重复扣款 |
| 退款接口超时 | 带原幂等键退避重试；仍失败转人工/对账，**绝不回报成功** |
| 审批超时 | 审批项过期，任务回到 Agent 或转人工 |
| 审批后政策变化 | 资金参数以审批快照为准；重大变化需重新审批 |
| 通知失败 | 重试/降级站内信，不影响退款结果 |
| 恢复时订单已被人工退款 | 重校验发现状态已变 → 停止并转人工，不重复退款 |

#### 22.5.2 案例：多渠道客服与知识库 RAG

**渠道归一**：邮件、网页表单、在线 IM、电话转写 → 统一内部消息模型（channel、user_id、content、attachments、locale、priority）。

**意图路由**：

- FAQ/产品咨询 → RAG 回答。
- 订单/退款/物流 → 业务 Agent + 工具。
- 投诉/法律/高危 → 直接转人工。
- 低置信度/连续失败 → 转人工。

**RAG 链路**：切分 300–800 token、重叠 10%–20% → embedding → top-k（5–20）→ rerank → 生成带引用回答；知识库版本化、增量索引。

> **top-k 的注入量要收敛**：top-20 候选全进上下文约 6000 token，其中只有 5 份会进答案。**应当 rerank 后只注入 top-5**，这是零风险的纯收益优化（§22.3.14）。

**权限与安全**：按租户/角色过滤知识库；PII 脱敏；外部文档不可信，防注入。

**转人工策略**：VIP、负面情绪、敏感词、金额阈值、用户主动要求。

**知识闭环**：已解决工单 → 提炼 FAQ → 审核入库 → 重新索引；差评/纠错反馈。

**指标**：检索命中率、回答准确率、引用率、自助解决率、转人工率。

#### 22.5.3 案例：单轮多工具与审批

**问题**：一轮里同时有只读查询、写操作、人工审批，怎么编排？

**方案**：

1. 分类：`SAFE_AUTO` vs `HIGH_RISK_APPROVAL`。
2. 只读先行，结果落 `completed_results`。
3. 高风险进 `pending_approvals`，任务挂起并释放 Worker。
4. 依赖高风险结果的下游动作延后。
5. 审批后按 DAG 继续；失败走补偿。

**关键点**：

- 审批快照锁定参数，防执行时被改。
- 部分审批通过时，逐条记录状态。
- `executed_actions` 防重复调用。

#### 22.5.4 变体：上下文超限与成本失控

**症状**：某天模型账单翻倍；部分长工单的回答开始丢事实（订单号说错、金额说错）。

**定位顺序**：

| # | 检查 | 说明 |
|---|---|---|
| 1 | **轮数分布是否右移** | 平均轮数上升 = 用户行为或政策变化，不是代码问题 |
| 2 | 工具结果是否变长 | 某个工具改了返回结构，多带了字段 |
| 3 | 检索候选是否放大 | top-k 被调大了 |
| 4 | K 值是否过小 | 裁剪过早 → 质量下降 |
| 5 | 模型是否被换成了更贵的 | 路由改动导致大模型占比上升 |

**处置**：

- 先治理**工具结果冗余**与**检索候选冗余**——这两项零质量损失。
- 再调整 K，但**必须配回归**：K 变小会丢事实，K 变大要钱。
- 模型分级：按意图路由，咨询类走低成本的分类 + 小模型。
- 兜底：单工单 token 预算，超预算即降级（转人工或简化回答），**而不是静默截断**。

**护栏**：单工单 token 预算 + 裁剪触发记录 + 按意图分层的成本看板。

> **「成本涨了」与「质量掉了」经常是同一个原因**：为了省成本把 K 调小，结果长工单丢事实、错误率上升，转人工率反而涨。**所以 K 不是一个可以单独调的旋钮**——它必须与「每工单平均轮数」「裁剪触发率」「转人工率」放在同一张看板上。

#### 22.5.5 故障与兜底

降级矩阵以 §22.4.9 为准，本例补充两条：

| 故障 | 影响 | 兜底 |
|---|---|---|
| Checkpoint 版本不兼容 | 无法恢复 | 停止该工单并转人工；**不得强行按新版本解析旧快照** |
| 工具契约变更后老工单未完成 | 老 `tool_call_id` 找不到 | 双版本共存期内按旧版本处理，或直接转人工 |

#### 22.5.6 扩容 10 倍，哪里先坏？

以 §22.3.20 的基准放大 10 倍（日 1000 万工单、峰值 580 QPS、LLM 调用 2320 QPS）：

| 顺序 | 先坏的点 | 现象 | 触发指标 | 对策 |
|---|---|---|---|---|
| 1 | **LLM 配额** | 429、排队、延迟飙升 | 调用 QPS > 配额 80% | 模型分级、缓存、跨供应商、限流 |
| 2 | **队列** | 积压、首响变慢 | 等待 > 30s | 扩分区、扩 Worker、优先级调度 |
| 3 | **工具下游** | 超时、限流 | 工具 P99 > 3s | 并发控制、结果缓存、熔断 |
| 4 | **向量检索** | P99 上升 | 检索 P99 > 500ms | 索引分片、候选集收敛、缓存高频 Query |
| 5 | **审批人力** | 审批排队 | 审批等待 > 4h | 提高自动化率、优化金额阈值 |
| 6 | **存储** | 日志 / Checkpoint 增长 | 磁盘水位 > 70% | TTL、分层、归档 |
| 7 | **成本（非线性）** | 账单涨幅 > 流量涨幅 | 单工单 token > 预算 120% | 治理轮数分布、K 值、模型分级 |

> **第 7 位是本章特有的非线性**：流量涨 10 倍，token **不是**涨 10 倍。大促期间复杂退款与投诉占比上升，长工单（20 轮）占比若从 10% 涨到 15%，平均输入 token 从 4 万涨到 4.44 万（+11%），于是总 token 涨 **11 倍而非 10 倍**。**容量评审必须按「轮数分布右移」后的口径算，而不是简单乘 10。**

#### 22.5.7 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| 异步执行 | 结果非实时 | 不占连接、可重试 | 极简问答可同步 |
| 高风险 HITL | 人工成本 | 防止错误退款 | 风控成熟后可放宽 |
| 三层记忆 | 实现复杂 | 控 token、防污染 | 短会话可简化 |
| 混合检索 | 复杂度 | 召回更准 | 单一召回足够时可简化 |
| 强制引用 | 生成受限 | 可追溯、降幻觉 | 闲聊场景可放宽 |
| 模型分级 | 路由复杂 | 成本大幅下降 | 模型价格变化 |
| **Router 优先于 Agent** | 覆盖度受限 | 高频场景更稳更省 | 长尾意图占比显著上升时扩大 Agent 覆盖 |
| **裁剪（K 值）** | 短工单无收益、长工单可能丢事实 | 把成本从 O(n²) 压回 O(n) | 轮数分布变化时重估 K |

### 22.6 闭环演进与常见误区

#### 22.6.1 演进路线

| 阶段 | 形态 | 触发条件（量化） | 关键改造 |
|---|---|---|---|
| L0 | 纯人工 + FAQ | 起步：工单 < 1 万/天 | 知识库、工单系统 |
| L1 | 推荐回复 | 坐席效率瓶颈：人均处理 > 8 单/天 | RAG、话术推荐 |
| L2 | 半自动 | 常见问题量大：咨询类占比 > 50% | 意图路由、工具、HITL |
| L3 | 自动 + 抽检 | 自助解决率 > 50% 且违规率 < 0.1% | 评测、护栏、成本优化 |
| L4 | 全自动 | 极低风险场景且转人工率 < 10% | 审计、异常检测 |
| L5 | 多 Agent / 跨域 | 单域意图覆盖 > 80% 且编排复杂度可控 | 工具复用、跨域路由 |

#### 22.6.2 指标体系

| 层级 | 指标 | 用途 |
|---|---|---|
| 业务 | 自助解决率、转人工率、一次解决率、CSAT | 判断价值 |
| 正确 | 意图/工具/参数准确率（**按意图与风险分层看**）、幻觉率、政策违规率 | 判断质量 |
| 效率 | 首响 P95、处理时长、并发工单、队列等待 | 判断体验 |
| 成本 | 单工单 token、单工单模型费、单工单人工成本 | 判断可持续 |
| 安全 | 注入拦截、越权拦截、PII 泄露、**错误退款数** | 判断风险 |
| **信号** | **转人工率与投诉率的相关性** | 两者同步上升 = Agent 在硬答，比单看任一指标更早暴露 |
| **信号** | **低置信工单占比的周环比** | 模型/知识/输入分布变化的先行指标 |
| **信号** | **回归通过率（每次 Prompt/模型/工具变更）** | 判断变更能否安全上线的唯一硬指标 |

> **技术达标但业务未改善 = 没解决**。自助解决率从 40% 升到 60% 但 CSAT 下降，说明 Agent 答得更快却没答对——**转人工率被压下去了，错误没减少，只是从「被坐席发现」变成了「被用户发现」**。这类问题只看自助解决率会得出完全相反的结论。
>
> **「转人工率」必须与投诉率、一次解决率一起看**：转人工率低不等于好，可能是硬答。

#### 22.6.3 评测、回归与发布

**离线评测**：

- 黄金集 500 条，**按意图、风险等级、渠道、轮数分桶**（§22.3.19）。
- 每次 Prompt/模型/工具变更跑回归，比较**分桶指标**而非总体准确率。

**发布流程**：

```
Prompt/模型/工具变更
  → 离线回归（黄金集分桶指标全部不退化才进下一步）
  → 影子流量（新版本并行跑，不执行动作，只比对）
  → 1% 灰度（看护栏指标：错误退款、投诉率、转人工率、单工单 token）
  → 10% → 50% → 全量
  → 每一步都有回滚开关
```

**回滚能力**：

| 变更类型 | 回滚方式 | 注意 |
|---|---|---|
| Prompt | 配置热切，秒级 | 需保留旧版本配置 |
| 模型 | 路由配置热切 | 需确认降级模型可用 |
| 工具契约 | **双版本共存**，不能瞬时回滚 | 因此工具变更必须预留一个版本周期 |
| 知识库 | 索引版本切换 | 需保留旧索引直到新索引验证通过 |

**在线 A/B**：按租户/流量分桶；护栏指标优先（错误退款 > 投诉率 > 转人工率 > 自助解决率）。

**复盘模板**：

```
目标 → 实际量级（工单数 / 轮数分布 / token）
     → 瓶颈点（哪一层）→ 故障与止损 → 数据偏差
     → 根因 → 改进项 → 负责人 → 验证结果 → 下次演练验证
```

> 模板末尾必须有「行动项 → 负责人 → 验证结果」。对 Agent 尤其如此——**「优化 Prompt」不是行动项，「意图分类的 Prompt 加上版本字段，3 月 5 日回归验证咨询类准确率从 88% 提升到 93% 且退款类不退化」才是**。

#### 22.6.4 成本优化

优先级（按收益排序，详见 §22.3.14 与 §22.3.20）：

| 手段 | 收益 | 代价 |
|---|---|---|
| **上下文裁剪（K 值）** | 20 轮工单省 59% | 需回归验证不掉事实 |
| **模型分级** | 约 45% | 路由复杂，分类错误要能降级 |
| 工具结果瘦身 | 每工单约 13% | 需按字段裁剪，可能丢信息 |
| 检索候选收敛（top-20→top-5） | 每工单约 11% | 召回率可能下降，需看 Recall@5 |
| 缓存（FAQ、前缀、工具结果） | 视重复率 | 缓存失效策略 |
| 早停 | 高置信度不跑满步数 | 早停过早会漏动作 |
| 批处理 | 离线评测/摘要 | 不适用在线链路 |

> **注意这张表的顺序与直觉相反**：最容易被想到的「缓存」排在第五位。**因为 Agent 的成本主要不是重复调用，而是上下文长度**——先治长度，再治重复。

#### 22.6.5 产品对比

| 产品/场景 | 形态 | 关键能力 | 主要挑战 |
|---|---|---|---|
| 电商客服 | 退款/物流/售后 | 工单 + 工具 + 审批 | 资金安全、重复退款 |
| SaaS 支持 | 工单 + 知识库 | RAG + 多租户 | 权限隔离、知识时效 |
| 银行客服 | 高合规 | MFA + 人工 | 合规、审计 |
| 电信客服 | 套餐/账单 | 业务工具 | 系统集成复杂 |
| 内部 IT 支持 | 工单 + 自助 | 知识库 + 自动化 | 长尾问题 |
| 出海客服 | 多语言 | 翻译 + 本地知识 | 语言质量、合规 |

#### 22.6.6 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 只画 LLM 不讲队列 | 无法落地 | 接入/队列/状态机完整 |
| 同步跑 Agent | 请求超时、无法重试 | 异步 + `ticket_id` |
| 没有幂等 | 重复退款/重复通知 | 幂等键 + 唯一索引 + 状态机 |
| 把规则写进 Prompt | 可被注入绕过 | 规则在代码/策略层 |
| 不做人工兜底 | 低置信度硬答 | 阈值 + 转人工 |
| 工具结果不回填 | 模型报错/死循环 | 每个 `tool_call_id` 都回填 |
| 上下文全量塞 | 成本高、污染 | 三层记忆 + 裁剪 |
| 不记录已执行动作 | 重复调用 | `executed_actions` |
| 审批不看快照 | 执行参数被改 | 审批快照 |
| 失败当成功 | 数据不一致 | 明确错误 + 补偿 |
| 不做评测 | 无法判断变好 | 黄金集 + 在线指标 + 红队 |
| 忽略知识库 ACL | 越权召回 | 检索前过滤 |
| **按平均值估 token** | 漏掉 O(n²) 的上下文增长，长工单成本被严重低估 | 按轮数分布算（§22.3.20） |
| **只按工单数估 LLM 调用** | 每工单平均 4 次调用，实际是工单数的 4 倍 | 调用峰值 = 峰值工单 × 每工单调用数 |
| **把模型自报置信度当真** | 模型说 95% 把握不代表准 | 分类器头或多次采样一致性（§22.3.21） |
| **转人工率越低越好** | 硬答会压低转人工率却推高投诉率 | 与投诉率、一次解决率合看 |
| **工具改名当普通发版** | 工具名与描述就是模型的说明书，改了等于换模型 | 走回归 + 双版本共存（§22.3.13） |
| **只做端到端准确率** | 60% 咨询类会把 10% 退款类的失败淹没 | 分层指标（§22.3.19） |
| **裁剪后不回归** | K 值调小丢事实，质量下降被当成成本优化 | 裁剪变更必须配回归（§22.6.3） |

#### 22.6.7 高频追问

- **如何防止重复退款？** → 幂等键（`ticket_id + step_id + tool_call_id`）+ 唯一索引 + 状态机条件更新 + 审批快照 + 全链路审计。
- **Agent 卡住/崩溃怎么办？** → Checkpoint + 可见性超时 + 启动扫描 + 幂等重试；恢复前重校验外部状态。
- **单轮既有只读又有人工审批怎么执行？** → 分类，只读先行，高风险挂起（**释放 Worker**），依赖项延后，审批后按 DAG 继续。
- **如何防止工具结果注入？** → 结果作为不可信数据包裹，规则与审批在代码层，脱敏与检测；命中注入即丢弃并转人工。
- **如何控制 token 成本？** → 先治上下文长度（裁剪 O(n²)→O(n)），再模型分级（45%），再工具/检索冗余，最后才是缓存。
- **上下文怎么裁？成本怎么算？** → 三层记忆；不裁剪输入 token 按 O(n²) 增长，20 轮工单比 4 轮贵 17 倍；裁剪后只贵 7 倍，省 59%。
- **如何评估 Agent 是否变好？** → 分层黄金集回归 + 影子流量 + 灰度 + 护栏指标 + 红队。
- **RAG 答不准怎么排查？** → 召回 → 切片 → 重排 → 生成逐段定位；引用为空是检索问题，有引用但答案是错的是生成问题。
- **上下文超限丢什么？** → 先裁工具输出，再折叠早期轮次，保留事实槽位与最近 K 轮；并记录裁剪原因。
- **如何做多租户隔离？** → 知识库、工具、队列、配额、审计五面隔离。
- **审批超时怎么办？** → 过期回到 Agent 或转人工，不自动放行高风险动作。
- **工具下游挂了怎么办？** → 重试 + 熔断 + 转人工，**绝不回报成功**。
- **如何防止越权？** → 身份 + 资源归属 + 金额阈值三道闸在代码层 + 审批 + 审计。
- **模型返回的置信度可信吗？** → 不可信；用分类器头或多次采样一致性判断。
- **转人工率多少算合理？** → 没有绝对值，必须与投诉率、一次解决率、CSAT 合看。
- **Prompt 改了怎么保证不退化？** → 分层黄金集回归 → 影子流量 → 1% 灰度 → 逐步放量，每步都有回滚开关。
- **10 万并发怎么设计？** → 接入无状态 + 队列削峰 + Worker 无状态可扩 + Step 级幂等 + 挂起释放 Worker + 多级降级。

#### 22.6.8 答题提纲与练习

**10 分钟版（自述型）**：

| 时间 | 内容 |
|---|---|
| 0–1 min | 澄清：工单量、渠道、意图分布、风险等级、自动化目标、**轮数分布** |
| 1–3 min | 容量：QPS、并发 Worker、LLM 调用峰值、**上下文 token 与成本** |
| 3–5 min | 架构：接入 → 编排 → 队列 → Worker → 工具/人工 |
| 5–7 min | 状态机、Checkpoint、幂等、HITL |
| 7–9 min | 深挖一个点（推荐：上下文成本 / 重复退款防护） |
| 9–10 min | 安全护栏、降级、评测 |

**35 分钟版（深聊型）**：

| 时间 | 内容 |
|---|---|
| 0–5 min | 澄清与七锚点：规模、轮数分布、风险、不可逆清单 |
| 5–14 min | 容量与成本（含 O(n²) vs O(n) 的推导与模型分级收益） |
| 14–22 min | 架构与数据流：接入/编排/队列/Worker/工具/人工，分层与预算 |
| 22–26 min | 数据模型与 API：工单、Checkpoint、幂等键、审批快照 |
| 26–34 min | 深挖三个点（各约 3 min）：① 幂等与恢复 ② 上下文治理与成本 ③ 不确定性与转人工 |
| 34–35 min | 演进阈值、安全护栏、评测闭环 |

**练习**：

1. 设计日 100 万工单的客服 Agent，给出异步链路、状态机与容量（**含 token 与成本**）。
2. 设计退款场景的幂等与审批方案，要求不重复扣款。
3. 设计单轮多工具的 DAG 与部分挂起流程，说明挂起时为什么要释放 Worker。
4. 设计三层记忆的触发与更新规则，并估算 20 轮工单相对 4 轮工单的成本倍数。
5. 设计 RAG 评估方案，覆盖召回、重排、引用与分层准确率。
6. 计算：日 100 万工单、平均 6 轮、每轮 1 次调用、每次输出 600 token，输入 ¥2/百万、输出 ¥8/百万——每天多少 token、多少钱？若不做上下文裁剪呢？
7. 设计「转人工率下降但投诉率上升」的排查路径。

#### 22.6.9 一页纸作战手册

**S0 定题**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 落七锚点 | 唯一事实源是什么？哪几个决策不可逆？ | 7 项写下来，事实源 = 工单 + 工具调用 + 审批记录 |
| 定优先级 | 越权、超卖（超支）、体验冲突时保谁？ | 不越权 > 不重复执行 > 不超支 > 体验 > 成本 |

**S1 建模**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 分层 | 每层只做什么、明确不做什么？ | 接入/编排/队列/Worker/工具/人工六层职责表 |
| 定粒度 | 幂等键落在哪一层？ | Step 级（`ticket_id + step_id + tool_call_id`） |
| 定状态 | 崩溃后从哪恢复？ | 状态机 + 每步 Checkpoint + 恢复前重校验 |

**S2 决策**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 选架构模式 | 哪些走 Workflow、哪些走 Agent？ | Router 优先；高风险走 Workflow + HITL |
| 选上下文 | K 值怎么定？ | 先量轮数分布，再定 K（§22.3.14） |
| 选自动化级别 | 哪些动作免审批？ | 金额阈值 + 风险分级，阈值变更需审批 |

**S3 论证**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 算并发 | Worker 要多少？ | 峰值工单 58 QPS → 348 Worker |
| 算 token | 上下文怎么算？ | 按轮数分布；424 亿 token/天、约 9.9 万元/天 |
| 算质量 | 怎么知道变好了？ | 分层黄金集 + 回归通过率 |

**S4 兜底**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 写延迟预算 | 首响与总时长各是多少？ | 首响 3s、总时长 2min、审批 24h（§22.4.10） |
| 写降级矩阵 | 每个依赖挂了用户看到什么？ | 8 类故障各有行为；工具失败不得回报成功 |
| 定护栏 | 安全排第几？ | 副作用、审批、越权、注入、隐私、多租户、审计 **七项 P0** |

**S5 闭环**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 定演进阈值 | 涨 10 倍哪里先坏？ | LLM 配额 → 队列 → 工具下游（§22.5.6） |
| 定指标 | 技术好了业务就好了吗？ | 转人工率必须与投诉率合看 |
| 建复盘闭环 | 行动项有负责人吗？ | 行动项 → 负责人 → 验证结果 |

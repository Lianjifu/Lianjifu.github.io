## 第二十六章 电商 AI Agent 系统

> **本章导读**：电商 Agent 横跨导购与商品检索、下单与履约工具调用、售后退款与纠纷处理、经营问数与增长自动化，核心工程挑战是「资金不能错、库存不能错、状态不能乱、承诺要兑现」。本章围绕导购推荐、订单履约与售后、经营问数与增长、幂等与降级矩阵展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 26.1 核心定义与定位

**定义**：电商 AI Agent 是在商品、交易、履约、售后、经营分析与增长场景中，理解用户或商家意图、调用领域工具、执行受控动作、对结果负责的智能体系统。它不仅「会推荐」，还要「能查、能改、能退、能赔、能算」。

**四类核心场景**：

| 场景 | 核心工具 | 主要风险 | 关键护栏 |
|---|---|---|---|
| 智能导购 | 商品检索、实时价格/库存、券资格 | 推荐无货、券后价算错 | 实时双校验 + 结构化槽位 |
| 订单售后 | 查单、改地址、退款、价保 | 重复退款、超额赔付 | 状态机 + 幂等 + 审批 |
| 经营问数 | SQL 沙箱、语义层 | 口径错、越权、慢查询 | AST 白名单 + 行权限 + LIMIT |
| 增长召回 | CDP、触达、频控 | 打扰、超发、归因虚高 | 状态复核 + Lua + Holdout |

**典型用户**：

| 用户 | 诉求 | 关注点 |
|---|---|---|
| 消费者 | 找商品、查订单、退换货 | 准确、快、别骗我 |
| 商家 | 经营分析、活动配置 | 口径、权限、成本 |
| 客服 | 处理售后、纠纷 | 可接管、可追溯 |
| 运营 | 增长召回、触达 | 增量、打扰、合规 |

**与通用问答 Agent 的区别**：

| 维度 | 通用问答 Agent | 电商 Agent |
|---|---|---|
| 副作用 | 基本无 | 资金、库存、订单状态 |
| 状态 | 会话内 | 强业务状态机 |
| 正确性 | 答案合理即可 | 金额/库存/归属必须精确 |
| 多租户 | 通常无 | 商家/店铺/部门隔离 |
| 实时性 | 可缓存 | 价格/库存/订单必须实时 |
| 审计 | 一般 | 全链路资金审计 |

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 意图理解与多轮对话 | 商品主数据生产 |
| 商品检索与实时校验 | 搜索索引底层 |
| 订单/售后工具编排 | 支付渠道 |
| 退款金额计算 | 财务结算 |
| 经营问数 | 数仓建模 |
| 增长触达 | 渠道网关 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 任务 | 任务成功率、一次解决率、人工转接率、满意度 |
| 工具 | 工具成功率、写操作成功率、重复退款率、错误写操作率 |
| 性能 | 决策/工具延迟 P99、单会话成本、降级比例 |
| 业务 | 导购转化率、售后处理时长、营销增量 ROI |
| 安全 | 越权拦截率、注入拦截率、资损事件数 |

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 导购首响 P95 | < 2s |
| 查单 P95 | < 500ms |
| 写操作 P99 | < 2s |
| 重复退款 | 0（硬约束） |
| 错误写操作 | 0（硬约束） |
| 审计覆盖率 | 100% |

### 26.2 核心解读与关键矛盾

**本质**：电商 Agent 的核心矛盾，是「推荐/生成的概率性」与「交易/资金的确定性」之间的冲突。模型可以猜用户想要什么，但不能猜退款金额。

**四大挑战**（原文保留）：

1. **高并发交易状态的一致性与幂等**：重复点击、超时重试、消息重投都可能触发重复退款或重复下单。
2. **资金与库存操作的原子性与可回滚**：退款、赔付、发券、改地址必须要么全成，要么可补偿。
3. **多轮工具调用下的上下文与依赖治理**：读操作可以并行，写操作必须按依赖串行，且不能丢约束。
4. **转化率与用户体验/合规底线的平衡**：推荐要准、触达要克制、承诺要可兑现。

**三个放大器**：

| 放大器 | 说明 | 后果 |
|---|---|---|
| 资金放大 | 一次错退/超赔乘以用户量 | 直接资损、对账困难 |
| 库存放大 | 推荐无货、超卖承诺 | 下单失败、投诉、赔付 |
| 口碑放大 | 错误推荐、承诺不兑现 | 信任下降、留存流失 |

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 推荐转化 vs 可信 | 推高佣/高毛利商品 | 相关性 + 可得性优先 | 广告位可显式标注 |
| 自动化 vs 资金安全 | 自动退款快但风险高 | 阈值 + 审批 | 低金额可全自动 |
| 实时 vs 成本 | 实时查价库存贵 | 缓存 + 时间戳 + 关键节点复核 | 大促可加缓存 |
| 多轮灵活 vs 状态一致 | 自由对话易丢约束 | 结构化事实槽位 | 简单问答可轻量 |
| 并行效率 vs 依赖正确 | 写操作并行会乱序 | DAG/Wave 串行 | 无依赖可并行 |
| 个性化 vs 合规 | 千人千面易越界 | 模板 + 审核 | 品牌强管控统一 |
| 工具丰富 vs 攻击面 | 工具多风险大 | 白名单 + 最小权限 | 内部工具可放宽 |
| 快速响应 vs 完整校验 | 少查一步更快 | 关键状态必查 | 只读场景可缓存 |

**四类正确性**：

| 层次 | 要求 | 保障手段 |
|---|---|---|
| 商品事实 | 价格、库存、参数、促销准确 | 实时接口 + 时间戳 |
| 交易状态 | 订单、退款、履约状态正确 | 状态机 + 先查后写 |
| 资金金额 | 实付、运费、分摊、补贴一致 | 统一口径 + 规则引擎 |
| 权限归属 | 本人/商家/租户不越权 | 身份校验 + 资源级鉴权 |

**八类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| 推荐无货 | 下单失败 | 只查索引不查实时 | 实时双校验 |
| 券后价错 | 价格纠纷/资损 | 券规则复杂 | 营销引擎为准 |
| 重复退款 | 同一单退两次 | 重试/并发 | 幂等 + 状态机 |
| 超额赔付 | 金额算多 | 口径不统一 | 统一规则 + 审批 |
| 改地址越权 | 改他人订单 | 身份校验缺失 | 实名 + 归属校验 |
| 状态错乱 | 并发写覆盖 | 无锁/无版本 | 订单级锁 + 版本 |
| 提示注入 | 备注含指令 | 外部文本不可信 | 隔离 + 白名单 |
| 问数口径错 | 经营决策误导 | 无语义层 | 指标卡 |

**五层设计原则**：

- **快慢分离**：高频封闭判断走轻量模型/规则，复杂规划才进 Agent。
- **读实时、写幂等**：价格、库存、订单状态必须实时查；所有写工具带幂等键。
- **模型提议、规则裁决、工具执行**：模型不能直接改资金或库存，只能调用受控工具。
- **可补偿、可审计**：每个写操作都有状态机、幂等键、补偿路径与操作日志。
- **先查后写**：写超时属于「结果未知」，必须先查状态再决定是否重试。

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| 冒充/越权 | 改他人订单、查他人信息 | 实名、归属校验、资源级鉴权 |
| 恶意退款 | 伪造破损、频繁退款 | 证据校验、风控、人工 |
| 薅羊毛 | 批量领券/赔付 | 限购、设备指纹、预算锁 |
| Prompt 注入 | 备注/评价含指令 | 数据隔离、工具白名单 |
| 内部作弊 | 违规改价/退款 | 审批、审计、权限分离 |

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| LLM | 最大 | 模型分级、缓存、上下文裁剪 |
| 实时查询 | 次之 | 批量、缓存、时间戳 |
| 工具调用 | 中 | 并行、结果缓存 |
| 人工审批 | 视风险 | 阈值优化、自动规则 |

#### 26.3.7 智能导购与商品推荐 Agent

**核心挑战**：理解模糊、多维需求，例如「适合油痘肌、成分温和、预算 200 元以内的晚间洁面」，并结合实时库存、价格、券后价与促销规则给出可信推荐。

**架构要点**：

- **检索 + 实时状态双校验**：商品知识与参数走混合检索（向量 + 关键词/属性过滤）；价格、库存、促销资格、券可用性必须调用实时商品/营销引擎，禁止依赖静态索引或模型记忆。
- **结构化事实槽位**：维护预算、尺码/肤质/偏好、必选条件与已排除商品；多轮追问不丢约束，不反复推荐用户已否决的款式。
- **推荐解释**：每条推荐说明「为什么适合」，并标注价格与库存的查询时点。

**工具契约**：

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `search_products` | 混合检索候选商品 | 支持属性过滤、分页、去重 |
| `get_realtime_offer` | 查实时价格/库存/促销 | 按 SKU 批量，带缓存时间戳 |
| `check_coupon_eligibility` | 校验券资格与券后价 | 以营销引擎结果为准 |
| `get_similar_in_stock` | 无货时给替代品 | 保持品类与价格带接近 |

**补充**：

- 查询改写覆盖同义词与口语（「油痘肌」→ 控油、温和、氨基酸洁面）。
- 无货时先给同款替代，再给相似款，明确说明差异，不能静默换品。
- 不编造参数、评价或销量；所有事实来自工具结果并可回溯。
- 商业推广位要显式标注，避免与自然结果混淆。
- 排序综合相关性、可得性、价格匹配、评价与库存健康度，但不能牺牲可信度。

#### 26.3.8 订单、履约与售后 Agent

**核心挑战**：查单、改地址、催发货、退换货、价保/补差、退款涉及强状态机与资金/库存变更；并发请求或超时重试极易导致重复退款、超额赔付或状态错乱。

**多工具依赖分批执行（DAG / Wave）**：

1. **只读波次**：`get_order`、`get_logistics`、`get_price_history`、`get_refund_policy` 并行执行。
2. **校验波次**：`check_refund_eligibility`、`calculate_refund_amount`、`check_price_protection`，校验不通过则跳过写操作并回填原因。
3. **写入波次**：`submit_refund`、`submit_price_protection`、`change_address` 按依赖串行执行，每步确认结果。

**写操作护栏**：

| 写操作 | 必查状态 | 审批/限额 | 幂等键示例 |
|---|---|---|---|
| 改地址 | 未发货、次数限制 | 高风险或多次修改转人工 | `addr:{order_id}:{version}` |
| 退款 | 已支付、未退款、售后窗口内 | 超金额阈值转人工 | `refund:{order_id}:{request_id}` |
| 补发 | 已签收、少件/破损证据 | 次数与金额限制 | `reship:{order_id}:{sku_id}` |
| 发券/赔付 | 活动资格、预算充足 | 预算中心校验 | `coupon:{user_id}:{campaign_id}` |

**金额计算**：退款金额要考虑实付、运费、优惠分摊、补贴追回与部分退款；券后价与价保比较口径必须固定，避免「按原价退、按券后价赔」。

**高风险动作**：高金额、频繁退款、政策歧义、疑似欺诈时挂起 `WAITING_FOR_HUMAN`，由规则引擎或人工审批。

**幂等与防注入**：

- 所有写工具强制携带 `idempotency_key`，服务端以幂等表去重。
- 用户备注、买家秀、外部物流/工单文本视为不可信数据，严禁其中的对抗性指令越权触发退款或改价。
- 工具参数做类型、范围与归属校验；不可逆动作执行前向用户确认。

**补充**：写接口超时不能盲目重试，必须先查订单/退款单状态；已成功则复用结果，未成功再重试。跨服务写操作按 Saga 设计正向与补偿动作，补偿失败进入人工队列。

#### 26.3.9 电商问数与经营分析 Agent

**核心挑战**：运营/商家问「华东区昨日净 GMV 环比变化及原因」「某类目退货率飙升」，面临指标口径分歧、宽表复杂、慢查询与数据权限隔离。

**语义层固化口径**：

- 支付 GMV、退款金额、净 GMV、券补贴、动销率、退货率等公式与统计口径统一。
- 明确退款归属：按原订单日期还是退款发生日期统计，必须写进指标卡。
- 示例：`净 GMV = 支付 GMV − 退款金额 − 券补贴`（具体口径按业务定义）。

**执行安全**：

- Schema 裁剪只召回相关表结构与样例值。
- SQL 走 AST 校验，仅放行只读查询，强制 `LIMIT` 与超时。
- 在执行层/视图层强制注入商家、店铺、部门权限过滤。
- 结果结合维度特征渲染图表与归因拆解。

**本章差异**：多租户商家隔离、数据新鲜度与经营指标口径；通用能力（语义层、Schema Linking、SQL 自愈、权限）见第二十三章。

#### 26.3.10 增长与召回营销 Agent

**核心场景**：加购未支付召回、浏览未下单提醒、沉睡用户激活、会员到期触达。

**链路**：决策模型判断时机/渠道 → 查实时订单与退订状态 → Redis Lua 原子频控 → 带幂等键下发 → 快慢信号归因。

**电商特有约束**：

- 触达前校验 SKU 是否仍有货、券是否仍可用、价格是否已变化。
- 已支付、已退款、已退订用户必须排除。
- 券预算与补贴成本纳入净 ROI，不只看点击率。

**本章差异**：频控、Holdout、Thompson Sampling 与降级矩阵详见第二十五章。

#### 26.3.11 多轮工具调用与上下文治理

**1. 原子工具组与配对安全**

多轮工具调用裁剪上下文时，把 `assistant(tool_calls)` 与对应的 `role="tool"` 消息视为不可拆分的原子组：先瘦身超长 JSON/日志，再整组淘汰；发往模型前做 `tool_call_id` 配对校验，防止协议报错或状态断裂。

**2. 结构化事实槽位 + 增量滚动摘要**

- 槽位锁定 `order_id`、`sku_id`、实付金额、已核实约束、已执行写操作，防止重复退款/重复查单。
- 增量摘要承接早期排查脉络；近期 K 轮保留完整原始交互。

**3. 上下文预算分配**

```
系统提示与工具定义 → 事实槽位 → 最近 K 轮 → 滚动摘要 → 工具结果
```

工具结果优先保留结构化字段，长日志截断并保留错误码与关键行。

**4. 并行与串行**

- 只读工具可并行；写工具按依赖串行。
- 同一订单的写操作加订单级锁或版本号，避免并发改地址/退款互相覆盖。
- 工具契约声明 `side_effect`、超时、重试语义、幂等要求与权限范围。

**5. 写超时的正确处理**

写调用超时属于「结果未知」，不能直接重试：先查订单/退款单状态，确认未成功后再用同一幂等键重试；已成功则复用结果。

#### 26.3.12 幂等设计

| 层 | 方案 |
|---|---|
| 工具调用 | `ticket_id + step_id + tool_call_id` |
| 退款 | `refund:{order_id}:{request_id}` + 唯一索引 |
| 价保 | `pp:{order_id}:{sku_id}:{price_version}` |
| 改地址 | `addr:{order_id}:{version}` |
| 发券 | `coupon:{user_id}:{campaign_id}` |
| 状态 | 条件更新 `WHERE status = ?` |
| 消息 | 去重表 + `msg_id` 唯一 |

#### 26.3.13 降级矩阵（Fail-Open / Fail-Closed）

| 依赖/环节 | 典型故障 | 策略 | 降级动作 |
|---|---|---|---|
| 退订/黑名单 | 状态服务超时 | **Fail-Closed** | 跳过触达并记原因码 |
| 订单/退款状态 | 查询超时 | **Fail-Closed** | 不执行写操作，提示稍后重试 |
| 支付/退款接口 | 超时、结果未知 | 先查后重试 | 查单确认，避免重复退款 |
| 库存/价格服务 | 超时 | 导购降级、下单拦截 | 展示缓存价并标注可能变化；结算 Fail-Closed |
| 决策模型 | 超时 | 规则兜底 | 默认低打扰渠道或 SKIP |
| 物料生成 | 失败 | 模板兜底 | 预审安全模板，仍失败则跳过 |
| ChatBI 查询 | 超时/报错 | 明确失败 | 返回错误与建议，不编造数据 |
| LLM 服务 | 超时/限流 | 模型降级 | 切备用模型，仍失败转人工 |
| Redis 频控 | 抖动 | **Fail-Closed** | 本地粗粒度限流兜底并告警 |

**治理要点**：降级必须打标 `degraded=true` 与 `reason_code`；资金、合规、防打扰默认 Fail-Closed；对高频抖动依赖配置熔断器，避免线程堆积。

#### 26.3.14 事件、原因码与可观测

**统一事件 Envelope**：

```
trace_id, session_id, turn_id, user_id, intent,
tool_name, tool_call_id, idempotency_key,
order_id, sku_id, amount, decision_meta,
reason_code, degraded
```

**核心事件**：

| 阶段 | 事件示例 |
|---|---|
| 会话与规划 | `agent.turn.started`、`agent.plan.created`、`agent.intent.resolved` |
| 工具执行 | `tool.called`、`tool.succeeded`、`tool.failed`、`tool.timeout` |
| 写操作与审批 | `write.confirmed`、`approval.requested`、`handoff.created` |
| 结果与归因 | `outcome.resolved`、`outcome.refunded`、`outcome.attributed` |

**原因码**：

| 前缀 | 典型原因码 | 含义 |
|---|---|---|
| `BIZ_*` | `BIZ_ALREADY_REFUNDED`、`BIZ_OUT_OF_WINDOW`、`BIZ_STATE_INVALID` | 业务状态不满足 |
| `TOOL_*` | `TOOL_TIMEOUT`、`TOOL_SCHEMA_MISMATCH`、`TOOL_RESULT_UNKNOWN` | 工具调用异常 |
| `AUTH_*` | `AUTH_PERMISSION_DENIED`、`AUTH_IDENTITY_MISMATCH` | 权限或身份问题 |
| `DEC_*` | `DEC_LOW_CONFIDENCE`、`DEC_MODEL_SKIP` | 模型/门控决策 |
| `SYS_*` | `SYS_STATE_SERVICE_TIMEOUT`、`SYS_CIRCUIT_BREAKER_OPEN` | 系统依赖异常 |

**核心指标**：任务成功率、一次解决率、人工转接率、满意度；工具成功率、写操作成功率、重复退款率、错误写操作率；决策/工具延迟 P99、单会话成本、降级比例；导购转化率、售后处理时长、营销增量 ROI。

#### 26.3.15 评测闭环

- **黄金轨迹集**：问题 + 期望工具序列 + 期望结果。
- **工具沙箱**：模拟订单、退款、库存状态，覆盖成功、失败、超时、重复提交。
- **对抗测试**：Prompt 注入、越权、诱导退款、伪造物流信息。
- **在线 A/B / Holdout**：验证真实解决率与增量。
- **回流**：决策快照、工具轨迹、原因码与结果，用于阈值校准、工具参数优化与策略精调。

#### 26.3.16 容量估算

**假设**：日会话 100 万，峰值 5 倍，平均 3 轮、5 次工具调用，写操作 5%，单次 4000 输入 + 500 输出 token。

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均会话 QPS | 100 万 ÷ 86400 | ≈ 11.6 |
| 峰值会话 QPS | 11.6 × 5 | ≈ 58 |
| 工具调用峰值 | 58 × 5 | ≈ 290 QPS |
| 写操作峰值 | 290 × 5% | ≈ 15 QPS |
| LLM 调用峰值 | 58 × 3 | ≈ 174 QPS |
| Token/天 | 100 万 × 3 × 4500 | ≈ 135 亿 |
| 会话存储 | 100 万 × 20KB | ≈ 20GB/天 |
| 工具调用日志 | 500 万 × 2KB | ≈ 10GB/天 |

**结论**：LLM 成本与工具下游压力是主要瓶颈；写操作量不大但必须强幂等。

### 26.4 工程落地与规则护栏

#### 26.4.1 端到端链路

```
用户消息
  → Gateway（鉴权、租户、限流）
  → Intent Router（导购/售后/问数/增长）
  → Agent Orchestrator
      ├→ 加载槽位与摘要
      ├→ 规划 DAG（只读/校验/写入）
      ├→ Tool Gateway（白名单、Schema、幂等）
      ├→ 高风险 → HITL 审批
      └→ Checkpoint
  → 领域服务执行
  → 结果校验与回复
  → 事件、审计、归因
```

#### 26.4.2 门控与路由护栏

- 快慢分离：简单查询走规则/轻模型，复杂多步进 Agent。
- 意图置信度低 → 追问或转人工。
- 高风险意图（退款、改地址）强制进入工作流，不允许自由发挥。
- 租户/商家隔离，工具按租户授权。

#### 26.4.3 工具契约护栏

| 项 | 要求 |
|---|---|
| 描述 | 用途、参数、限制、示例 |
| Schema | 类型、范围、枚举、必填 |
| 副作用 | 声明 `side_effect`（读/写/资金） |
| 幂等 | 写工具必须接受 `idempotency_key` |
| 超时 | 独立超时与重试语义 |
| 权限 | 资源级鉴权、租户隔离 |
| 审计 | 参数、结果、耗时、调用者 |

#### 26.4.4 写操作护栏

- 先查后写：写前查状态，写超时先查结果。
- 订单级锁/版本号：防并发覆盖。
- 金额规则引擎：统一口径，不由模型计算。
- 阈值审批：超金额转人工。
- 二次确认：不可逆动作向用户确认。
- 补偿：Saga 逆序补偿，失败进人工队列。

#### 26.4.5 上下文治理护栏

| 步骤 | 动作 |
|---|---|
| 1 | 估算 token，预留输出 |
| 2 | 裁剪超长工具结果 |
| 3 | 整组淘汰早期 tool 交互 |
| 4 | 更新事实槽位与摘要 |
| 5 | 配对校验 `tool_call_id` |

#### 26.4.6 降级与熔断

- 资金/状态/频控：Fail-Closed。
- 导购/生成：缓存/模板兜底。
- 高频抖动依赖：熔断器。
- 降级打标，避免效果误算。

#### 26.4.7 观测与压测

**观测**：

| 类别 | 指标 |
|---|---|
| 会话 | 轮次、意图分布、解决率 |
| 工具 | 成功率、P99、超时率 |
| 写操作 | 成功率、重复率、审批率 |
| 业务 | 转化率、退款时长、ROI |
| 安全 | 越权、注入、资损 |

**压测**：

- 峰值 5 倍会话。
- 单订单并发写。
- 支付/退款超时。
- 库存/价格服务故障。
- LLM 限流。
- 重复消息与重复点击。

#### 26.4.8 上线检查

1. 写工具是否全部支持幂等键？
2. 写超时是否先查后重试？
3. 状态机是否覆盖所有跃迁？
4. 金额规则是否统一、可审计？
5. 高风险操作是否强制审批？
6. 工具是否白名单 + Schema 校验？
7. 上下文是否原子组裁剪？
8. 降级是否按 Fail-Open/Fail-Closed 分级？
9. 审计是否覆盖决策与动作？
10. 黄金轨迹与对抗测试是否通过？

### 26.5 典型案例与端到端解决

#### 26.5.1 案例：价保 + 退款组合请求

**用户**：「上周买的耳机现在降了 80，能价保吗？另外昨天那单面霜我想退。」

1. **意图拆分**：价保 + 退货退款，分别绑定订单与 SKU。
2. **槽位**：两个 `order_id`、`sku_id`、实付金额、收货时间、是否拆封。
3. **只读波次**：并行查订单、物流、价格历史、售后政策。
4. **校验波次**：
   - 耳机已签收 5 天，在 7 天价保窗口内，价差 80 元，无「特殊商品不参与价保」限制。
   - 面霜昨日签收、未拆封，在 7 天无理由退货窗口内。
5. **风险判断**：合计退款 379 元，低于自动处理阈值；但该用户近 30 天已有 3 次退款，触发风控标记 → `WAITING_FOR_HUMAN` 人工复核。
6. **写入波次**：审批通过后，分别以 `pp:{order_id}:{sku_id}:{price_version}` 与 `refund:{order_id}:{request_id}` 为幂等键提交价保和退款，串行确认。
7. **补偿**：退款成功但优惠券追回失败时，进入 Saga 补偿/人工队列，绝不对同一订单再次发起退款。
8. **回复**：告知价保金额、退款到账时间、退货方式与所需材料。

**常见失败**：重复点击 → 幂等键去重；写超时 → 先查单再重试；已退款 → `BIZ_ALREADY_REFUNDED`；超窗口 → `BIZ_OUT_OF_WINDOW` 并解释规则。

#### 26.5.2 变体 A：智能导购

**用户**：「适合油痘肌、成分温和、预算 200 元以内的晚间洁面。」

1. 查询改写：控油、温和、氨基酸洁面。
2. 混合检索：向量 + 属性过滤，Top-20。
3. 实时校验：批量查价格、库存、券后价。
4. 排序：相关性 + 可得性 + 价格匹配 + 评价。
5. 无货替代：同款不同规格 → 相似款，明确差异。
6. 解释：说明成分、适用肤质、券后价与查询时点。

**护栏**：不编造参数；推广位标注；价格库存带时间戳。

#### 26.5.3 变体 B：无货与替代

- 先查同款其他规格/颜色。
- 再查相似款，保持品类与价格带。
- 明确告知「原商品无货，以下为替代」。
- 不静默换品，不虚标库存。

#### 26.5.4 变体 C：经营问数

**问题**：「华东区昨日净 GMV 环比下降的原因？」

- 语义层确认净 GMV 口径与退款归属。
- Schema 裁剪：订单、退款、券、门店、地区。
- 权限重写：仅华东、仅本商家。
- 归因：按渠道、品类、门店拆贡献度。
- 输出：结论 + SQL + 口径 + 注意事项。

#### 26.5.5 故障与兜底

| 故障 | 影响 | 兜底 |
|---|---|---|
| 重复退款 | 资损 | 幂等键 + 唯一索引 + 状态机 |
| 写超时 | 结果未知 | 先查单，再决定重试 |
| 库存服务超时 | 推荐无货 | 展示缓存 + 标注；结算拦截 |
| 支付接口超时 | 状态未知 | 查单确认 |
| LLM 限流 | 无法回复 | 备用模型/转人工 |
| 审批系统故障 | 高风险阻塞 | 暂停写入，保留只读 |

#### 26.5.6 扩容 10 倍，哪里先坏？

| 顺序 | 先坏的点 | 现象 | 对策 |
|---|---|---|---|
| 1 | LLM 配额 | 429、排队 | 模型分级、缓存、限流 |
| 2 | 实时商品查询 | P99 上升 | 批量、缓存、读写分离 |
| 3 | 订单库 | 连接数/锁竞争 | 分片、读写分离 |
| 4 | 工具下游 | 超时 | 并发控制、熔断 |
| 5 | 审批人力 | 排队 | 阈值优化、自动规则 |
| 6 | 事件链路 | 积压 | 扩分区、采样 |

#### 26.5.7 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| 快慢分离 | 架构复杂 | 低延迟 + 可控 | 场景简单可合并 |
| 写操作审批 | 人工成本 | 防资损 | 风控成熟可放宽 |
| 实时双校验 | 延迟与成本 | 不推荐无货 | 库存稳定可缓存 |
| DAG/Wave | 编排复杂 | 依赖正确 | 单工具场景可简化 |
| 原子组裁剪 | 实现复杂 | 协议安全 | 上下文充足可简化 |
| Fail-Closed | 少成交 | 不资损 | 依赖稳定可放宽 |

| 商家问数 | 语义层 + 多租户 | 口径、权限 |
| 增长召回 | CDP + 频控 | 打扰、归因 |
| 本地生活 | 门店 + 履约 | 时效、库存 |
| 跨境电商 | 多币种 + 合规 | 汇率、税务 |

#### 26.6.6 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 只查索引不查实时 | 推荐无货 | 实时双校验 |
| 模型计算退款金额 | 金额错 | 规则引擎 |
| 写超时直接重试 | 重复退款 | 先查后重试 |
| 只靠幂等键不查状态 | 状态错乱 | 幂等 + 状态机 |
| 写操作并行 | 依赖乱序 | DAG/Wave |
| 上下文直接截断 | tool 配对断裂 | 原子组裁剪 |
| 用户备注当指令 | 注入 | 数据隔离 |
| 不标注推广位 | 误导 | 显式标注 |
| 无审批阈值 | 资损 | 分级审批 |
| 不做黄金轨迹 | 无法回归 | 评测闭环 |

#### 26.6.7 高频追问

- **如何防止重复退款？** → 幂等键 + 唯一约束 + 状态机条件更新，超时先查单。
- **如何避免推荐已下架/无货商品？** → 检索后调用实时价格库存接口二次校验。
- **多个 Tool Call 怎么排？** → 只读并行、校验居中、写入串行，按 DAG/Wave 执行。
- **如何防止用户备注里的 Prompt 注入？** → 不可信文本隔离，工具白名单与参数校验，写操作确认。
- **如何评测电商 Agent？** → 黄金轨迹 + 工具沙箱 + 对抗测试 + 在线 A/B 与人工转接率。
- **退款金额怎么算？** → 实付、运费、优惠分摊、补贴追回与部分退款统一口径。
- **写超时怎么办？** → 先查订单/退款单状态，确认未成功再用同一幂等键重试。
- **并发写同一订单怎么办？** → 订单级锁 + 版本号 + 条件更新。
- **上下文怎么裁？** → `assistant(tool_calls)` 与 `tool` 消息整组保留/淘汰。
- **如何做多租户隔离？** → 工具、数据、权限、审计全隔离。
- **金额口径不一致怎么办？** → 规则引擎统一，指标卡固化。
- **如何防止越权改地址？** → 实名 + 订单归属校验 + 二次确认。

#### 26.6.8 答题提纲与练习

**25 分钟答题提纲**：

| 时间 | 内容 |
|---|---|
| 0–3 min | 澄清：场景、会话量、交易风险、实时性 |
| 3–6 min | 容量：会话/工具/写操作 QPS、token |
| 6–11 min | 五层架构：门控 → 编排 → 工作流 → 工具 → 归因 |
| 11–16 min | 导购双校验、售后状态机、DAG/Wave |
| 16–21 min | 幂等、金额规则、上下文治理、降级 |
| 21–25 min | 评测、成本、取舍 |

**练习**：

1. 设计日 100 万会话的电商 Agent，给出五层架构。
2. 设计退款链路的幂等与状态机，要求不重复扣款。
3. 设计多工具 DAG，覆盖只读、校验、写入三波次。
4. 设计上下文原子组裁剪与槽位方案。
5. 设计导购的实时双校验与无货替代策略。

#### 26.6.9 一页纸速记

**主线与放大器**

- 电商 Agent = 导购 + 交易 + 售后 + 问数 + 增长。
- 三个放大器：资金、库存、口碑。

**工具与写路径**

- 读实时、写幂等、钱必审。
- 工具分批：只读并行、校验居中、写入串行。
- 上下文原子组：`assistant(tool_calls)` + `tool` 不可拆。
- 写超时先查后重试，绝不盲目重试。

**金额与验证**

- 模型提议、规则裁决、工具执行。
- 金额由规则引擎算，不由模型算。
- 降级：资金/状态/频控 Fail-Closed。
- 没有黄金轨迹与对抗测试，就无法证明 Agent 可靠。

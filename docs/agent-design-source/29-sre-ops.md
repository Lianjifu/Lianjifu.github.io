## 第二十九章 系统运维 AI Agent（AIOps / SRE Agent）

> **本章导读**：运维 Agent 面对的是真实生产基础设施——一次误操作可能把局部抖动放大成全站故障，核心不是「会聊天」，而是「先把告警风暴降噪成事件，再跨层溯源，最后在最小爆炸半径内受控止血」。本章围绕告警指纹与风暴抑制、拓扑富化与变更关联、根因溯源、风险分级与受控止血展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 29.1 核心定义与定位

**定义**：系统运维 AI Agent（AIOps / SRE Agent）是在告警接入、故障调查、受控止血、变更关联与复盘沉淀全链路中，理解生产遥测与变更上下文、调用运维工具、执行受控动作并对结果负责的智能体系统。

**核心目标**（原文保留）：在保障生产可用性（SLA）与业务安全底线的前提下，把「告警/异常事件」转化为可归并降噪、可跨层溯源、可受控止血、可复盘沉淀的生产级故障处置闭环。

**五类核心场景**：

| 场景 | 核心工具 | 主要风险 | 关键护栏 |
|---|---|---|---|
| 告警降噪与事件归并 | 告警平台、指纹、拓扑、时间窗 | 漏报、误抑制 | 父子抑制规则 + 起点识别 |
| 故障调查与根因定位 | 指标、日志、Trace、CMDB、变更历史 | 误判根因 | 证据绑定 + 假设排除 |
| 受控止血与恢复 | K8s、CI/CD、限流、切流、回滚 | 误改生产、级联故障 | 风险分级 + 审批 + 爆炸半径 |
| 容量与成本治理 | 容量水位、HPA、资源画像 | 缩容过度、扩容滞后 | 观察窗口 + 可回滚 |
| 值班辅助与复盘 | Runbook、工单、复盘库 | 值班负担、结论失真 | 证据留痕 + 人工确认 |

**典型用户**：

| 用户 | 诉求 | 关注点 |
|---|---|---|
| 一线值班 SRE | 快速判断、少打扰 | 告警准、证据全、动作稳 |
| 服务负责人 | 根因、影响面、恢复 | 定位准、止损快 |
| 运维经理 | MTTR、值班负担、自动化率 | 可度量、可审计 |
| 安全与合规 | 变更可追溯、权限合规 | 审计、审批、最小权限 |

**与通用问答/离线分析 Agent 的差异**：

| 维度 | 通用问答 Agent | 运维 Agent |
|---|---|---|
| 作用对象 | 文本/知识 | 真实生产基础设施 |
| 错误代价 | 答案不佳 | 级联故障、资损、SLA 违约 |
| 输入 | 用户问题 | 海量遥测 + 变更 + 工单 |
| 状态 | 会话内 | 事件生命周期 + 资源状态 |
| 动作 | 基本无副作用 | 重启、扩容、切流、回滚 |
| 实时性 | 可缓存 | 秒级遥测与状态 |
| 审计 | 一般 | 全链路不可篡改 |

原文四条差异（保留）：

1. **直面真实线上基础设施**：错误动作会直接影响生产，必须「防误改、防级联故障」。
2. **海量遥测噪声与告警风暴**：一次依赖雪崩可能瞬间触发上百条告警。
3. **多轮工具调用下的上下文与状态一致性**：调查链路长，容易遗忘已排除假设或重复查询。
4. **部分依赖不可用时的稳健降级**：监控、日志、CMDB 抖动时既不能卡死值班，也不能盲改。

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 告警归并、降噪、富化 | 监控采集与存储底座 |
| 故障调查与根因排序 | 应用代码修复 |
| 受控止血动作编排 | 云厂商控制面内部实现 |
| 变更关联与回滚建议 | 发布平台的产品设计 |
| 复盘与 Runbook 沉淀 | 组织级故障管理流程 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 降噪 | 归并率、噪音率、误报率 |
| 调查 | 根因 Top-1/Top-3 命中率、平均确认时间 |
| 处置 | MTTR、自动止血成功率、回滚率 |
| 安全 | 未授权写操作数、爆炸半径超限次数、审批合规率 |
| 效率 | 值班负担（告警量/人）、Runbook 覆盖率 |

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 告警归并延迟 P95 | 小于 30s |
| 事件初筛 P95 | 小于 60s |
| 根因报告生成 P95 | 小于 3min |
| 只读诊断查询 P95 | 小于 2s |
| 未授权写操作 | 0（硬约束） |
| 审批绕过 | 0（硬约束） |
| 止血动作可回滚率 | 100% |

### 29.2 核心解读与关键矛盾

**本质**：运维 Agent 的核心矛盾，是「线上问题的概率性推断」与「生产变更的确定性要求」之间的冲突。模型可以给出「最可能根因」，但不能凭概率直接重启核心服务。

**三个放大器**：

| 放大器 | 说明 | 后果 |
|---|---|---|
| 生产放大 | 动作直接作用于线上 | 局部故障变全站事故 |
| 噪声放大 | 一次雪崩触发上百告警 | 值班被淹没、错过起点 |
| 时间放大 | 故障每分钟都在损失 | 误判与犹豫都昂贵 |

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 自动化 vs 安全 | 自动回滚快但风险高 | 风险分级 + 审批 | 低风险可逆动作可自动 |
| 降噪 vs 漏报 | 抑制过多会漏真故障 | 保留起点告警与硬规则 | 维护窗口可放宽 |
| 快速止血 vs 根因消除 | 重启能缓解但会复发 | 先稳后治、记录待办 | 根因明确可直接修 |
| 全面取证 vs 查询成本 | 全量拉日志很贵 | 分层采样、按需下钻 | 疑难故障可加采样 |
| 模型推断 vs 证据约束 | 模型爱编根因 | 结论必须绑定证据 | 无证据时只给假设 |
| 多 Agent 并行 vs 状态一致 | 同时改同一资源 | 资源锁 + 版本校验 | 只读可并行 |
| 降级可用 vs 盲改风险 | 依赖挂了仍要处置 | 读降级、写 Fail-Closed | 有本地缓存证据可放宽读 |
| 复盘沉淀 vs 隐私合规 | 日志含敏感信息 | 脱敏后入库 | 合规环境更严格 |

**四类正确性**：

| 层次 | 要求 | 保障手段 |
|---|---|---|
| 事件正确 | 告警归并准确、不漏起点 | 指纹 + 拓扑 + 时间窗 |
| 诊断正确 | 根因有证据、假设可排除 | 证据槽位 + 分层收敛 |
| 动作正确 | 目标、参数、权限、时机正确 | 资源级鉴权 + 风险分级 |
| 结果正确 | 恢复已验证、失败可回滚 | 健康检查 + 变更前后状态 |

**八类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| 告警风暴淹没 | 值班漏看真故障 | 无归并抑制 | 指纹 + 拓扑 + 父子抑制 |
| 根因误判 | 修错对象 | 只看最后爆发告警 | 找最早异常 + 变更关联 |
| 误重启 | 重启后复发或更糟 | 根因未消除 | 先只读、后写 |
| 级联放大 | 切流/缩容引发雪崩 | 无爆炸半径控制 | 灰度 + 限流 + 审批 |
| 重复执行 | 多实例同时改资源 | 无锁无幂等 | 幂等键 + 租约锁 |
| 状态不明盲改 | 写超时后直接重试 | 结果未知 | 先查后重试 |
| 注入越权 | 日志文本诱导执行 | 不可信数据入指令区 | 数据隔离 + 策略引擎 |
| 复盘失真 | 结论无证据、行动项不闭环 | 无审计与回流 | 全链路留痕 + 复盘标签 |

**五条设计原则**（原文保留）：

- **先降噪、再调查**：先把告警归并成 `incident_id`，避免每条告警各拉起一个 Agent。
- **先只读、后写**：诊断证据不足时不允许执行变更。
- **状态不明不改**：目标资源状态、审批状态或身份校验不明确时 Fail-Closed。
- **最小爆炸半径**：优先可逆、局部、可灰度的动作，高危动作必须审批。
- **一切留痕**：输入证据、工具调用、审批、执行结果与恢复验证全部审计。

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| Prompt 注入 | 日志、请求参数、Webhook 含指令 | 数据隔离 + 策略引擎 |
| 越权操作 | 冒充高权限执行变更 | 身份校验 + 资源级鉴权 |
| 审批绕过 | 伪造审批或跳过闸门 | 审批服务独立 + 审计 |
| 内部误操作 | 参数填错、目标选错 | Schema 校验 + 二次确认 |
| 重放/重复 | 重试与多实例冲突 | 幂等键 + 资源锁 |
| 数据泄露 | 日志含敏感信息 | 脱敏 + 最小读取 |

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| LLM | 最大 | 模型分级、证据裁剪、缓存 |
| 遥测查询 | 次之 | 时间窗收敛、采样、批量 |
| 日志存储/扫描 | 中 | 分级存储、按需下钻 |
| 人工审批 | 视风险 | 阈值优化、低风险自动化 |

#### 29.3.7 告警接入、指纹去重与风暴抑制

**核心挑战**：数据库慢查询、网络抖动或上游依赖雪崩会瞬间触发大量连环告警；单条告警独立调查既浪费资源，也容易错过真正的异常起点。

**降噪与归并**（原文保留）：

- **指纹去重**：按 `alertname + service + cluster + region + error_signature` 生成指纹。
- **拓扑关联**：沿服务依赖图把上下游告警归入同一事件。
- **时间窗关联**：把同一时间窗内同源告警合并，识别「起点告警」与「派生告警」。
- **风暴抑制**：父告警抑制子告警、维护窗口静默、抖动/翻覆检测。
- **富化**：附带近期发布、配置变更、容量水位与值班信息。

**补充**：

- 指纹要包含错误签名摘要，避免同一服务的不同故障被错误合并。
- 抑制规则必须可解释：记录「被谁抑制、依据哪条规则」，防止真故障被静默。
- 合并窗口按故障类型配置（秒级抖动 vs 分钟级雪崩）。
- 保留原始告警明细，供复盘与规则调优。

#### 29.3.8 拓扑富化与依赖分析

- 服务依赖图来自 CMDB、服务注册、调用链与 K8s 资源关系。
- 告警挂到图节点上，计算影响面：受影响服务、上下游、入口流量、关键业务。
- 区分「自身故障」与「被上游拖垮」：看上游错误率、超时与容量，而不是只看本服务指标。
- 拓扑可能过期，降级时标注置信度。

#### 29.3.9 变更关联

发布、配置、扩缩容、证书、网络策略变更往往先于故障。

| 变更类型 | 关联方式 | 典型故障 |
|---|---|---|
| 应用发布 | 版本、实例、时间窗 | N+1 查询、内存泄漏 |
| 配置变更 | 配置项、下发时间 | 超时、限流错配 |
| 扩缩容 | 副本数、节点池 | 冷启动、连接风暴 |
| 证书/密钥 | 到期时间 | 握手失败 |
| 网络策略 | 规则变更 | 跨服务不通 |

**方法**：按故障开始时间回溯 30–120 分钟，列出同服务、同集群、同依赖链路的变更，按相关性与时间接近度排序，作为根因假设的强证据。

#### 29.3.10 结构化事实槽位

| 槽位 | 作用 |
|---|---|
| `incident_id` | 单一调查上下文 |
| `affected_services` | 受影响服务与依赖范围 |
| `time_window` | 异常时间窗与对比基线 |
| `suspected_root_cause` | 当前最可能根因与置信度 |
| `confirmed_evidence` | 已核实证据（指标/日志/Trace/变更） |
| `ruled_out_hypotheses` | 已排除假设，防止重复调查 |
| `executed_actions` | 已执行动作与结果，防重复/冲突 |

**使用要求**：

- 槽位是唯一事实来源，摘要只做压缩，不覆盖槽位。
- 每个结论绑定证据来源与时间戳。
- 排除假设必须写清依据，避免模型反复走回头路。
- 动作执行后立即更新 `executed_actions`。

#### 29.3.11 根因溯源方法

1. **看起点**：按时间排序找最早异常，而不是最后爆发的告警。
2. **看变更**：发布、配置、扩缩容、证书、网络策略变更往往先于故障。
3. **看依赖**：沿拓扑向上游/下游追，区分「自身故障」与「被上游拖垮」。
4. **看分层**：指标（症状）→ Trace（路径）→ 日志/堆栈（原因）逐层收敛。
5. **做对照**：同版本、同区域、同时间窗对比，排除流量自然波动。

**证据收敛顺序**：

| 层次 | 回答的问题 | 典型信号 |
|---|---|---|
| 指标 | 哪里不对、何时开始 | 错误率、P99、饱和度、QPS |
| Trace | 哪条路径慢/错 | 跨服务耗时、错误标签 |
| 日志 | 具体原因 | 异常栈、错误码、慢查询 |
| 变更 | 谁改了什么 | 发布、配置、扩缩容 |

**假设管理**：维护「待验证假设 → 证据 → 结论」，每轮调查只推进最高价值假设，避免漫无目的扫日志。

#### 29.3.12 多工具 DAG 排查与 Wave

**核心挑战**：定位故障需要交叉比对指标、日志、链路与变更；止血动作一旦误判或参数错误，可能把局部故障扩大为全站事故。

**先查后改、分批执行**（原文保留）：

1. **只读诊断波次**：并发查错误率、延迟分位、QPS、饱和度、错误日志、Trace、变更历史、下游依赖。
2. **证据汇总**：把确认证据写入槽位，更新根因假设与排除项。
3. **止血决策**：只有根因指向本服务且动作收益明确时才考虑写操作；若根因在上游，跳过本服务重启/扩容。
4. **护栏校验**：检查事件是否已自愈、是否处于变更冻结、是否超爆炸半径与频控。
5. **执行与观察**：低风险动作带幂等键执行并观察指标；高风险动作挂起审批。
6. **验证与回滚**：健康检查与核心指标恢复才确认成功，否则按预案回滚。

**只读诊断工具**：

| 工具 | 用途 |
|---|---|
| `query_metrics` | 错误率、延迟分位、QPS、饱和度 |
| `query_logs` | 错误日志、异常栈、错误码分布 |
| `query_traces` | 跨服务耗时与错误路径 |
| `get_topology` | 依赖关系与影响面 |
| `get_changes` | 发布、配置、扩缩容历史 |
| `get_capacity` | 容量水位与配额 |
| `get_runbook` | 标准处置步骤 |

#### 29.3.13 风险分级与受控止血

| 风险级别 | 示例 | 处理方式 |
|---|---|---|
| 低风险/可逆 | 拉取现场诊断、临时提高日志采样、单 Pod 重启 | 白名单 + 速率限制内受控执行 |
| 中风险 | 调整副本数、切只读、限流阈值小幅调整 | 规则校验 + 观察窗口 + 可回滚 |
| 高风险/大影响面 | 生产库写操作、跨 AZ 切流、大规模缩容、核心服务回滚、关键路由/限流配置 | 强制 `WAITING_FOR_HUMAN` 或灰度变更通道 |

**爆炸半径控制**：

- 先单实例、再单集群、再区域，逐级扩大。
- 动作前估算受影响实例数与流量占比。
- 设置观察窗口与自动回滚条件。
- 变更冻结期内禁止非紧急写操作。

#### 29.3.14 幂等、锁与回滚

- 所有写工具带 `idempotency_key` 与目标资源版本/租约锁。
- 多 Agent 实例或重试任务不能同时对同一资源执行冲突变更。
- 执行前记录「变更前状态」，执行后验证「变更后状态」，失败按 Runbook 回滚。
- 写超时属于「结果未知」：先查资源状态，再决定是否重试。
- 回滚本身也要幂等，并验证回滚后的健康状态。

**幂等键示例**：

| 层 | 方案 |
|---|---|
| 重启 | `restart:{cluster}:{workload}:{pod}:{request_id}` |
| 扩容 | `scale:{workload}:{from}:{to}:{request_id}` |
| 回滚 | `rollback:{service}:{from_version}:{to_version}` |
| 切流 | `traffic:{service}:{from_zone}:{to_zone}:{version}` |
| 审批 | `approval:{incident_id}:{action_hash}` |

#### 29.3.15 上下文治理

- **日志瘦身**：工具层按关键字、时间窗、错误级别截断日志/堆栈，只保留错误码、关键行与调用链。
- **原子工具组**：`assistant(tool_calls)` 与对应 `role="tool"` 不可拆分，先裁剪冗长 JSON 再整组淘汰；请求模型前做 `tool_call_id` 配对校验。
- **槽位 + 摘要**：槽位锁定关键 ID、时间窗、已核实结论与已执行动作；增量摘要承接早期脉络，近期 K 轮保留原始交互。
- **证据引用**：结论必须绑定证据来源与时间戳，避免模型凭印象编造根因。

#### 29.3.16 防 Prompt Injection

- 日志、异常请求参数、Webhook、工单文本一律视为**不可信数据**，作为数据字段隔离，不进入指令区。
- 写操作准入由**代码策略引擎**独立判定，不依赖 LLM 自我约束。
- 工具白名单 + 参数类型/范围/资源归属校验；高危动作要求人工确认。
- 对疑似注入内容做标记与告警，保留原始样本用于复盘。

#### 29.3.17 异常降级矩阵

| 依赖/环节 | 典型故障 | 策略 | 降级动作 |
|---|---|---|---|
| 指标/日志/Trace | 查询超时 | 降级读 | 输出已有证据、未查项与建议，不阻塞值班 |
| CMDB/拓扑 | 超时 | 降级读 | 用缓存拓扑并标注可能过期 |
| 变更历史 | 超时 | 降级读 | 提示「变更信息未确认」，禁止据此执行高风险动作 |
| 策略/审批/身份 | 不可用 | **Fail-Closed** | 拦截写操作，转人工 |
| 写执行接口 | 超时、结果未知 | **Fail-Closed** | 先查资源状态，禁止盲目重试 |
| 决策模型 | 超时 | 规则兜底 | 切确定性 Runbook 或转人工 |
| LLM 服务 | 超时/限流 | 模型降级 | 切备用模型，仍失败输出诊断摘要 |
| 通知渠道 | 失败 | 重试/排队 | 记录待发送，避免事件被静默丢弃 |
| K8s/云控制面 | 超时 | **Fail-Closed** | 不执行变更，转人工 |
| 告警平台 | 延迟 | 本地缓冲 | 去重后补投，避免重复拉起 |

**治理要点**：降级打标 `degraded=true` 与 `reason_code`；写操作、审批、身份默认 Fail-Closed；读路径可降级并明确标注证据缺失。

#### 29.3.18 事件、原因码与可观测

**统一事件 Envelope**：

```
trace_id, incident_id, alert_id, session_id, turn_id,
service, cluster, region, severity,
tool_name, tool_call_id, idempotency_key,
action, target, approval_id,
evidence_refs, decision_meta, reason_code, degraded
```

**核心事件**：

| 阶段 | 事件示例 |
|---|---|
| 接入降噪 | `alert.received`、`alert.suppressed`、`incident.merged` |
| 调查 | `incident.triaged`、`tool.called`、`evidence.added`、`rca.proposed` |
| 处置 | `action.requested`、`approval.requested`、`action.executed`、`action.rolled_back` |
| 闭环 | `incident.resolved`、`postmortem.created`、`runbook.updated` |

**统一原因码示例**（原文保留并扩展）：

- `CANCEL_ALERT_RESOLVED`：告警已自愈，取消处置。
- `POL_APPROVAL_REQUIRED`：策略要求人工审批。
- `FREQ_ACTION_RATE_LIMITED`：动作触发频控。
- `DEC_BENIGN_NOISE`：判定为良性噪音。
- `SYS_TELEMETRY_TIMEOUT`：遥测查询超时。
- `AUTH_PERMISSION_DENIED`：权限不足。
- `TOOL_RESULT_UNKNOWN`：写操作结果未知。
- `BIZ_STATE_INVALID`：资源状态不满足动作前提。

**核心指标**：告警归并率、噪音率、误报率、平均确认时间、MTTR、根因 Top-1/Top-3 命中率、自动止血成功率、回滚率、未授权写操作数、爆炸半径超限次数、审批合规率、值班负担、Runbook 覆盖率、复盘行动项完成率。

#### 29.3.19 评测闭环

**离线评测**：

- 历史故障回放：给定告警/遥测快照，评估根因定位准确率与建议动作合理性。
- 黄金事件集：标准根因、关键证据、允许动作与禁止动作。
- 对抗测试：日志注入、伪造 Webhook、误导性指标、审批绕过。

**在线指标**：

- 告警归并率、噪音率、误报率、平均确认时间、MTTR。
- 根因 Top-1/Top-3 命中率、自动止血成功率、回滚率。
- 未授权写操作数（应为 0）、爆炸半径超限次数、审批合规率。
- 值班负担（告警量/人）、Runbook 覆盖率、复盘行动项完成率。

**持续迭代**：

- 把处置轨迹、原因码、人工修正与最终结果回流，校准降噪阈值、根因排序与动作策略。
- 成功案例转 Runbook，重复出现的低风险场景再逐步自动化，始终保留审计与回滚。

#### 29.3.20 容量估算

**假设**：原始告警 50 万条/天，峰值 10 倍；归并后 2 万事件/天；30% 进入 Agent 调查；平均 6 轮、10 次工具调用；单轮 6000 输入 + 600 输出 token。

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均告警 QPS | 50 万 ÷ 86400 | ≈ 5.8 |
| 峰值告警 QPS | 5.8 × 10 | ≈ 58 |
| 平均事件 QPS | 2 万 ÷ 86400 | ≈ 0.23 |
| 峰值事件 QPS | 0.23 × 10 | ≈ 2.3 |
| Agent 调查峰值 | 0.7 事件/秒 | ≈ 0.7 |
| 工具调用峰值 | 0.7 × 10 | ≈ 7 QPS |
| LLM 调用峰值 | 0.7 × 6 | ≈ 4.2 QPS |
| Token/天 | 6000 × 6 × 6600 | ≈ 2.4 亿 |
| 轨迹存储 | 6000 × 50KB | ≈ 300MB/天 |
| 遥测查询/天 | 6000 × 10 | 6 万次 |

**结论**：瓶颈通常不在 LLM，而在遥测查询与写操作审批；告警风暴时接入层与归并层最先承压。

### 29.4 工程落地与规则护栏

#### 29.4.1 端到端链路

```
告警 / 指标异常 / 变更事件
  → Alert Gateway（指纹、去重、限流）
  → Incident Service（归并、拓扑富化、严重度）
  → 门控（噪音快筛 / 自动或人工）
  → Investigation Orchestrator
      ├→ 只读诊断波次（指标/日志/Trace/变更）
      ├→ 证据槽位与假设更新
      ├→ 止血决策
      └→ 策略引擎校验 → 审批（高风险）
  → Action Gateway（幂等、锁、灰度、回滚）
  → 恢复验证（健康检查 + 核心指标）
  → 审计、复盘、Runbook 回流
```

#### 29.4.2 门控与路由护栏

- 噪音快筛：已知抖动、维护窗口、重复指纹直接抑制并记录原因。
- 严重度分级：按影响面、SLO、业务关键性定 P0–P3。
- 自动/人工分流：低风险标准动作走自动化，其余进人工。
- 每事件只允许一个主调查 Agent，避免重复拉起与写冲突。
- 门控判定要可解释、可回放。

#### 29.4.3 只读诊断工具契约

| 项 | 要求 |
|---|---|
| 描述 | 用途、参数、时间窗、返回字段 |
| Schema | 类型、范围、枚举、必填 |
| 超时 | 独立超时与降级策略 |
| 限流 | 单事件查询配额，防打爆遥测 |
| 证据 | 返回 `source`、`timestamp`、`query` |
| 权限 | 按服务/集群/租户鉴权 |
| 审计 | 参数、结果摘要、耗时 |

#### 29.4.4 写操作与爆炸半径护栏

- 白名单：只有注册过的动作可执行，禁止任意 shell。
- 参数校验：目标、命名空间、副本数、版本必须在允许范围。
- 爆炸半径：单次影响实例数/流量比例设上限。
- 灰度：先单实例、再小比例、再全量。
- 观察窗口：动作后必须等待指标稳定再扩大。
- 回滚预案：执行前确定回滚条件与命令。
- 频控：同一资源单位时间动作次数上限。

#### 29.4.5 审批与变更冻结

- 高风险动作强制 `WAITING_FOR_HUMAN`，审批人需具备对应权限。
- 审批请求附带：证据、拟执行动作、影响面、回滚方案。
- 变更冻结期内仅允许紧急通道，并需额外审批。
- 审批超时升级，不允许自动放行。
- 审批与执行分离，执行者不能自批。

#### 29.4.6 上下文与证据护栏

- 证据必须带来源、查询语句、时间戳。
- 结论与证据分离存储，便于审计。
- 已排除假设进入槽位，防止重复调查。
- 工具结果超长时先摘要、保留错误码与关键行。
- 原子组裁剪 + 配对校验。

#### 29.4.7 降级与熔断

- 遥测读：降级并标注缺失，不阻塞值班。
- 写操作/审批/身份：Fail-Closed。
- 决策模型：切确定性 Runbook。
- 通知渠道：排队重试，不静默丢弃。
- 高频抖动依赖：熔断器 + 本地缓存。

#### 29.4.8 观测与压测

**观测**：

| 类别 | 指标 |
|---|---|
| 接入 | 告警量、指纹重复率、抑制率 |
| 归并 | 事件数、归并率、误并率 |
| 调查 | 轮次、工具成功率、P99 |
| 处置 | 动作成功率、回滚率、审批时长 |
| 安全 | 未授权写、注入拦截 |
| 成本 | 单事件 token、遥测查询量 |

**压测**：

- 告警风暴（10 倍、50 倍）。
- 依赖雪崩多事件并发。
- 遥测查询超时。
- 写接口超时与重复回调。
- 审批服务不可用。
- LLM 限流。

#### 29.4.9 上线检查

1. 告警是否先归并成事件再调查？
2. 指纹与抑制规则是否可解释、可回放？
3. 根因结论是否绑定证据与时间戳？
4. 写操作是否全部白名单 + Schema 校验？
5. 高风险动作是否强制审批且审批执行分离？
6. 是否有爆炸半径与频控上限？
7. 是否支持灰度、观察窗口与回滚？
8. 写超时是否先查状态再重试？
9. 降级是否按读降级、写 Fail-Closed 分级？
10. 审计是否覆盖证据、审批、动作与恢复验证？

### 29.5 典型案例与端到端解决

#### 29.5.1 案例：核心接口错误率突增

1. **告警归并**：同服务/同依赖链路的 87 条告警按 5 分钟窗口归并为单一 `incident_id`，附带近 30 分钟发布与配置变更摘要。
2. **门控初筛**：排除维护窗口与已知抖动，判定为 P1 有效事件，进入调查编排。
3. **只读诊断**：并发查错误率、P99、连接池、慢查询、错误日志、Trace 与变更历史。
4. **证据收敛**：发现 20 分钟前发布新版本后，某接口出现 N+1 查询，数据库连接池打满；上游依赖正常，排除「被上游拖垮」。
5. **止血决策**：
   - 低风险：暂停继续放量、临时提高日志采样，保留现场。
   - 中风险：若发布平台支持，暂停滚动发布并回滚上一版本；回滚核心服务属于高风险，挂起 `WAITING_FOR_HUMAN`。
   - 不建议：直接重启 Pod（根因未消除，重启只能短暂缓解）。
6. **执行与验证**：审批通过后按幂等键回滚，观察错误率与连接池恢复；失败则按 Runbook 降级限流并升级处理。
7. **审计归档**：记录证据、审批、动作与恢复曲线，更新 Runbook 与发布检查项。

**常见失败**：只重启不修根因导致复发；未看变更历史错过发布；回滚未验证健康状态；多实例重复执行同一回滚。

#### 29.5.2 变体 A：数据库连接池打满

- 症状：接口超时、连接等待、错误率上升。
- 诊断：连接池使用率、慢查询、活跃事务、应用线程栈。
- 根因：N+1 查询、长事务、连接泄漏、突发流量。
- 处置：限流/降级非核心查询、终止长事务、回滚问题版本；扩容连接池需谨慎，可能压垮数据库。
- 护栏：生产库写操作与参数调整属高风险，必须审批。

#### 29.5.3 变体 B：磁盘写满 / 日志暴涨

- 症状：节点 NotReady、写入失败、Pod 驱逐。
- 诊断：磁盘使用率、inode、日志增长速率、大文件。
- 处置：清理过期日志、调整日志级别与轮转、扩容磁盘、迁移 Pod。
- 护栏：清理命令必须限定路径与白名单，禁止通配删除。

#### 29.5.4 变体 C：依赖雪崩与告警风暴

- 症状：数百条告警、多个服务同时异常。
- 诊断：找最早异常与共同上游；对比同依赖的其他服务。
- 处置：先在上游限流/熔断，再处理本服务；避免对每个下游服务分别重启。
- 护栏：风暴期间限制并发调查与写操作，防止处置本身造成二次冲击。

#### 29.5.5 变体 D：变更导致的故障回滚

- 症状：发布后错误率/延迟上升，时间高度吻合。
- 诊断：版本对比、灰度实例对比、配置差异。
- 处置：暂停发布、回滚上一版本、观察核心指标。
- 护栏：回滚核心服务属高风险，需审批；回滚后验证并记录变更单。

#### 29.5.6 故障与兜底

| 故障 | 影响 | 兜底 |
|---|---|---|
| 遥测查询超时 | 证据不全 | 降级读，输出已有证据与未查项 |
| 拓扑服务不可用 | 影响面不清 | 用缓存拓扑并标注可能过期 |
| 变更历史不可用 | 无法关联变更 | 禁止据此执行高风险动作 |
| 审批服务不可用 | 高风险阻塞 | 拦截写操作，转人工 |
| 写接口超时 | 结果未知 | 先查资源状态，不盲目重试 |
| LLM 限流 | 无法生成结论 | 备用模型 / 规则 Runbook / 人工 |
| 通知失败 | 事件可能丢失 | 排队重试，记录待发送 |
| 告警平台延迟 | 事件滞后 | 本地缓冲去重后补投 |

#### 29.5.7 扩容 10 倍，哪里先坏？

| 顺序 | 先坏的点 | 现象 | 对策 |
|---|---|---|---|
| 1 | 告警接入/归并 | 积压、重复事件 | 分区、批量、指纹缓存 |
| 2 | 遥测查询 | P99 上升、限流 | 时间窗收敛、采样、缓存 |
| 3 | 事件存储 | 写入热点 | 分片、冷热分离 |
| 4 | LLM 配额 | 429 | 模型分级、摘要裁剪 |
| 5 | 审批人力 | 排队 | 阈值优化、低风险自动化 |
| 6 | 审计存储 | 膨胀 | 分层、采样、归档 |

#### 29.5.8 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| 先降噪再调查 | 可能延迟个别事件 | 值班不被淹没 | 单点故障可直通 |
| 先只读后写 | 止血稍慢 | 防止误改 | 证据充分可加速 |
| 高风险审批 | 人工成本 | 防级联事故 | 风控成熟可放宽 |
| 读降级 | 证据不全 | 值班不阻塞 | 遥测稳定可收紧 |
| 写 Fail-Closed | 少自动化 | 不误改 | 依赖稳定可放宽 |
| Runbook 自动化 | 维护成本 | MTTR 下降 | 场景稳定后扩大 |

### 29.6 闭环演进与常见误区

#### 29.6.1 演进路线

| 阶段 | 形态 | 触发条件 | 关键改造 |
|---|---|---|---|
| L0 | 告警 + 人工 Runbook | 起步 | 告警分级、值班 |
| L1 | 告警归并与富化 | 噪声大 | 指纹、拓扑、变更关联 |
| L2 | 只读诊断助手 | 调查耗时 | 指标/日志/Trace 工具 |
| L3 | 受控止血 | 标准动作多 | 风险分级、幂等、审批 |
| L4 | 自动调查 + 建议 | 事件量大 | DAG、证据槽位、根因排序 |
| L5 | 闭环自治 | 成熟 | 低风险自动处置、复盘回流 |

#### 29.6.2 指标体系

| 层级 | 指标 | 用途 |
|---|---|---|
| 降噪 | 归并率、噪音率、误报率 | 判断告警质量 |
| 调查 | 根因命中率、确认时间 | 判断诊断能力 |
| 处置 | MTTR、自动止血率、回滚率 | 判断恢复能力 |
| 安全 | 未授权写、审批合规 | 判断风险 |
| 效率 | 值班负担、Runbook 覆盖率 | 判断可持续 |

#### 29.6.3 评测与回归

- 历史故障回放覆盖典型根因与噪声场景。
- 黄金事件集校验「允许动作」与「禁止动作」。
- 对抗测试：注入、伪造告警、审批绕过。
- 在线 A/B 验证 MTTR 与误动作率。
- 每周复盘 Top 错误，沉淀为规则与 Runbook。

#### 29.6.4 Runbook 沉淀与自动化分级

| 级别 | 形态 | 人工参与 |
|---|---|---|
| R0 | 文档步骤 | 全人工 |
| R1 | 半自动脚本 | 人工确认关键步 |
| R2 | 受控工作流 | 低风险自动、高风险审批 |
| R3 | 自动处置 + 观察 | 人工监督、可随时接管 |

**要求**：Runbook 版本化、可回滚、带前置校验与回滚步骤；自动化只覆盖已验证的低风险场景。

#### 29.6.5 成本优化

- 模型分级：噪音快筛用小模型。
- 证据裁剪：只保留错误码、关键行与时间窗。
- 缓存：拓扑、变更摘要、常见 Runbook。
- 批量：多指标一次查询。
- 早停：假设已收敛即停止调查。

#### 29.6.6 产品对比

| 产品/场景 | 核心 | 关键挑战 |
|---|---|---|
| 告警平台 | 归并、路由、值班 | 降噪与漏报 |
| APM/可观测平台 | 指标、Trace、日志 | 跨源关联 |
| AIOps 平台 | 异常检测、根因排序 | 误报、解释性 |

#### 29.6.7 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 每条告警拉起一个 Agent | 资源浪费、结论冲突 | 先归并成事件 |
| 只看最后爆发的告警 | 根因误判 | 找最早异常 |
| 直接重启 Pod | 复发、掩盖问题 | 先查根因与变更 |
| 自动执行所有动作 | 误改生产 | 风险分级 + 审批 |
| 写超时直接重试 | 重复变更 | 先查后重试 |
| 无爆炸半径上限 | 级联故障 | 灰度 + 限流 |
| 模型自行决定写操作 | 注入/越权 | 策略引擎独立裁决 |
| 结论无证据 | 复盘失真 | 证据绑定时间戳 |
| 只做告警降噪不做复盘 | 同类故障反复 | Runbook 与回流 |
| 用离线指标评估在线效果 | 结论偏差 | 在线 A/B + 历史回放 |

#### 29.6.8 高频追问

- **告警风暴怎么处理？** → 指纹去重 + 拓扑/时间窗归并 + 父子抑制，形成单一 incident。
- **如何避免 Agent 误改生产？** → 风险分级 + 审批 + 白名单 + 爆炸半径/频控 + 幂等与版本锁。
- **根因怎么定位？** → 找最早异常、看变更、沿拓扑追依赖、指标→Trace→日志逐层收敛。
- **遥测查询超时怎么办？** → 降级读，输出已有证据与未查项；写操作仍 Fail-Closed。
- **日志里的 Prompt 注入怎么防？** → 不可信数据隔离，策略引擎独立裁决，工具白名单与参数校验。
- **如何评估运维 Agent？** → 历史回放 + 黄金事件 + 根因命中率 + MTTR + 未授权写操作数。
- **什么时候可以自动止血？** → 低风险、可逆、白名单动作，且有观察窗口与回滚。
- **多事件并发怎么办？** → 每事件单主 Agent，资源锁，全局动作频控。
- **如何防止重复回滚？** → 幂等键 + 资源版本 + 执行前状态检查。
- **变更冻结期怎么处理？** → 仅紧急通道，额外审批。
- **如何处理误报？** → 记录 `DEC_BENIGN_NOISE`，回流优化阈值与抑制规则。
- **如何沉淀 Runbook？** → 成功轨迹转步骤，版本化，先半自动再受控自动。

#### 29.6.9 答题提纲与练习

**25 分钟答题提纲**：

| 时间 | 内容 |
|---|---|
| 0–3 min | 澄清：告警量、SLA、自动化边界、合规 |
| 3–6 min | 容量：告警/事件/工具/LLM QPS、token |
| 6–11 min | 五层架构：接入降噪 → 门控 → 编排 → 执行 → 审计 |
| 11–16 min | 归并、槽位、根因溯源、只读 DAG |
| 16–21 min | 风险分级、幂等、爆炸半径、降级 |
| 21–25 min | 评测、Runbook、取舍 |

**练习**：

1. 设计日 50 万告警的运维 Agent，给出五层架构。
2. 设计告警指纹与风暴抑制规则，要求不漏起点。
3. 设计只读诊断 DAG 与证据槽位。
4. 设计受控止血的风险分级、审批与回滚。
5. 设计遥测超时与审批不可用时的降级方案。

#### 29.6.10 一页纸速记

**主线与放大器**

- 运维 Agent = 降噪 + 调查 + 止血 + 复盘。
- 三个放大器：生产、噪声、时间。

**调查与遏制**

- 先降噪再调查、先只读后写、状态不明不改。
- 告警归并成 `incident_id`，找最早异常而不是最后爆发。
- 根因收敛：指标 → Trace → 日志 → 变更。

**写操作与降级**

- 写操作：白名单 + 风险分级 + 审批 + 爆炸半径 + 幂等锁。
- 写超时先查后重试；回滚也要幂等。
- 读可降级且标注缺失，写与审批 Fail-Closed。
- 日志与 Webhook 是不可信数据，策略引擎独立裁决。
- 没有历史回放与黄金事件，就无法证明 Agent 可靠。

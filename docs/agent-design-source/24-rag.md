## 第二十四章 问答 AI Agent 系统（知识库问答 / RAG）

> **本章导读**：问答 Agent 把用户提问变成有依据、可核验、可追溯的答案，难点不在「答得像人」，而在「答得准、且知道什么时候不该答」——检索噪声会被模型编成结论，过期知识会被反复复用，答不上来时还必须敢拒答。本章围绕知识切分与多路召回、重排与注入预算、引用与拒答、权限隔离与知识时效展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 24.1 核心定义与定位

**定义**：问答 AI Agent 是面向知识密集型场景的智能体系统。它接收自然语言问题，完成意图路由、检索规划、多路召回、重排、上下文构建、答案生成与引用、置信度判定与拒答、以及基于反馈的评测闭环，最终给出**有依据、可核验、可追溯**的答案。

它与问数 Agent 是**同构的兄弟**：两者都是「读 → 推理 → 答」，差别只在数据源——问数读的是**结构化数仓**，问答读的是**非结构化知识库**。这个同构性是本章的骨架：

| 维度 | 问数 Agent（第 23 章） | 问答 Agent（本章） |
|---|---|---|
| 事实源 | 语义层 + 数仓 | 切分后的知识块 + 版本 |
| 事实的形态 | **结构化、可计算** | **非结构化、需引用** |
| 幻觉的形态 | 口径错、Join 错 | **无依据生成** |
| 防线 | 口径固化 + AST 校验 + 沙箱 | **召回 + 重排 + 引用 + 拒答** |
| 正确的证明 | SQL 可执行可复现 | **引用可点开可核验** |

> **两章的核心方法论也是镜像的**：问数章说「**先下推再回传，绝不靠截断控制上下文**」，本章说「**召回宽、注入窄，绝不靠加宽召回换命中率**」。**同一个底层道理的两面**：送进模型的东西，要么是算好的，要么是筛过的；**不能是原样倒进去的。**

**三类能力层次**：

| 层次 | 回答的问题 | 典型输出 | 难度 |
|---|---|---|---|
| **L1 单跳问答** | 是什么 | 一段答案 + 若干引用 | 中 |
| **L2 多跳推理** | A 和 B 怎么合起来算 | 分解 + 逐步 + 引用 | 较高 |
| **L3 行动与闭环** | 接下来该做什么 | 结论 + 待办 + 派单 | 高 |

**典型用户与场景**：

| 用户 | 场景 | 关注点 | 主要风险 |
|---|---|---|---|
| 内部员工 | 制度、流程、报销标准 | 准确、时效、找得到人 | 引用错条款、过期政策 |
| 客服 / 一线 | 产品用法、故障处理 | 快、能直接用 | 幻觉误导一线 |
| 客户 | 产品说明、政策解读 | 准确、可自助 | 越权泄露内部制度 |
| 知识管理员 | 知识入库与治理 | 冲突、过期、覆盖 | 旧版本污染新答案 |

**与相近系统的区别**：

| 系统 | 核心 | 与问答 Agent 的差异 |
|---|---|---|
| FAQ / 关键词检索 | 精确匹配 | **答不上来就答不上来，不会推理也不会兜底** |
| 全文检索（Elasticsearch） | 召回相关文档 | **把文档甩给人，不组织答案** |
| 文档摘要 | 单篇概括 | 不跨文档、不引用、不拒答 |
| 通用 LLM 聊天 | 靠参数化知识回答 | **不知道你的内部制度，会一本正经地编** |
| 问答 Agent | 检索 + 重排 + 生成 + 引用 + 拒答 | **答案必须挂在一个可点开的来源上** |

> **「答案必须挂在一个可点开的来源上」是本章唯一不可妥协的产品定义**。没有这一条，它就退化成一个「回答得很像人、但你没法验证」的搜索框——而这恰恰是用户不信任 AI 回答的根本原因。

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 问题理解与意图路由 | 知识内容的**生产**与审核流程 |
| 切分、入库、索引与版本 | 文档协作与权限系统本身 |
| 召回、重排、上下文构建 | 通用搜索引擎的实现 |
| 生成、引用、拒答、澄清 | 人工知识运营 |
| 反馈回流与评测闭环 | 企业微信 / 邮件等通知渠道 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 效果 | 答案准确率、**幻觉率**、**误拒率**、拒答恰当率 |
| 引用 | **引用精确率**、**引用召回率**、**引用完整率**、引用点击率 |
| 检索 | **recall@k**、重排前后命中率、注入块数 |
| 体验 | 首响 P95、追问率、答案质疑率、首次解决率 |
| 成本 | 单问 token、注入 token 占比、重排算力 |
| 安全 | **越权召回率** 0、敏感内容泄露 0 |

> **两个新指标是本章的核心**：**幻觉率**（答了但没有依据）与**误拒率**（本可答却拒答）。它们是一对此消彼长的指标，**必须一起看**——单看任何一个都能得出「应该调松/调紧」的反向结论。

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 首 token P95 | < 800ms |
| 简单问答 P95 | < 2s |
| 复杂多跳 P95 | < 8s |
| **幻觉率** | **≤ 5%** |
| **误拒率** | **≤ 8%** |
| **引用完整率** | **100%** |
| **越权召回率** | **0**（硬约束） |
| 答案质疑率 | ≤ 3% |

**本章专属不可逆决策清单**（做错了要停机迁移 + 数据回填 + 全量对账，不是发个版本就能改）：

| 决策 | 为什么不可逆 | 改动代价 |
|---|---|---|
| **切分策略与块结构**（块边界、重叠、标题路径、表格行、表头携带） | 决定召回粒度与语义完整性；改了就全库重建 | 全量重建索引 + 召回结果突变 + 历史引用链断裂 |
| **Embedding 模型与向量索引 schema（含 ACL 字段）** | 检索的坐标系；换了模型所有向量作废 | 全量重算向量 + 索引重建 + 灰度双写 |
| **多路召回的组成与融合算法**（向量 / BM25 / 历史问答对 / 实体的权重与 RRF 参数） | 决定 recall@k 的上限 | 参数需全量重跑黄金集 + 线上指标断档 |
| **重排模型与重排策略**（cross-encoder 版本、top-N 重排范围） | 决定注入质量与幻觉率 | 换模型要重跑黄金集 + 延迟预算重排 |
| **注入预算与注入条数的口径**（k 是多少、怎么算、超了怎么办） | 决定成本、延迟与幻觉率三者 | 改 k 要重跑成本与质量双回归 |
| **知识版本与生效时间模型**（version / effective_from / 废止态） | 决定「过期知识会不会被用到」 | 全库补版本字段 + 历史答案的口径需重新标注 |
| **引用契约与答案结构**（引用粒度、引用如何校验、答案 schema） | 引用是可信度的唯一载体 | 全量答案与引用重新生成 + 下游解析全部失效 |

> **对照第一章 §1.4.4**：这七项属单向门，决策时要多评审、做原型、留迁移方案。其余（模型选择、top-k、召回路数、阈值、批大小、缓存）是双向门，可以快速试错——但 **k 值与召回路数属于「可逆但很贵」**：它们直接改变幻觉率与误拒率这两个核心指标，必须伴随黄金集回归。

### 24.2 核心解读与关键矛盾

**本质**：问答 Agent 的核心矛盾，是「开放提问的表达空间」与「封闭答案的证据要求」之间的冲突。用户可以问任何事，但答案必须挂在一个存在的、可点开的、当前生效的知识块上。**这意味着「答不上来」是一个必须被产品化的一等公民，而不是失败。**

**六条章级原则**（贯穿全章，冲突时以这六条为准）：

1. **召回宽、注入窄**——召回保证不漏（宽），重排后注入保证不噪（窄）。**这是本章的第一原则**：宽召回 + 窄注入同时成立，两个指标才同时改善。
2. **没有依据就不作答**——检索不到就明说「知识库里没有」，**宁可拒答，不可流畅地编**。模型的生成能力远强于它的判别能力（§24.3.10）。
3. **答案必须带引用，且引用可点开原文**——不可核验的答案不可信。**每个实质性论断都要有引用**，这是 P0 而非加分项。
4. **知识有时效，答案要带截止时点**——过期知识不静默使用；答案要说明「基于哪一版知识、截至什么时候」。
5. **权限在检索层过滤，不在生成层声明**——模型看不到的文档，就不可能被写进答案。**「请不要透露内部制度」是提示，不是防线。**
6. **拒答率是双面指标**——幻觉率与误拒率必须一起看。**单看拒答率，永远会得出「应该放宽」的错误结论。**

**三个不等式**：

```
生成能力  >>  判别能力   →  噪音一旦进上下文，就会被编成合乎逻辑的结论
开放提问  >>  封闭答案   →  拒答与澄清不是失败，是产品的一部分
知识规模  >>  人工维护速度 →  靠版本与时效标注，不靠人肉
```

**三个放大器**（本章最贵的量都藏在这里）：

| 放大器 | 说明 | 后果 | 量化 |
|---|---|---|---|
| **召回放大（宽度 vs 精度）** | 召回集变宽，命中更多、噪声更多 | 幻觉率上升，上下文暴涨 | k 从 10 → 50：命中率 +11pp，**准确率反降 3pp，幻觉率涨 13pp**，上下文 +168%（§24.3.10） |
| **幻觉放大** | 模型的生成能力远强于判别能力 | 错误答案比错误检索更贵 | 18% 幻觉率 → 若 1% 被采信并纠正，**¥18 万/天，比省下的 token 还多**（§24.3.13） |
| **知识复用放大** | 一条过期条款被命中一次，就被复用成千上万次 | 错误知识被规模化传播 | 过期块贡献 3% 的问答 → **6 万次/天基于过期知识作答**（§24.3.16） |

> **本章与前面各章的放大器方向不同**：Feed 是读放大，秒杀是写放大，客服是上下文放大，问数是结果集放大，营销是触达放大，供应链是牛鞭放大，文旅是时空搜索放大。**问答章的放大器是召回放大**——它是唯一一个「**为了不漏答案而做的动作，会系统性地制造错答案**」的架构。**别的系统放大的是数据量，问答放大的是「不确定的证据量」。**

**四层正确性**（必须分开保证）：

| 层次 | 要求 | 保障手段 | 典型漏法 |
|---|---|---|---|
| **证据正确** | 检索到的块确实支持答案 | 多路召回 + 重排 + 引用精确率 | 只用向量检索，术语/编号全miss |
| **依据完整** | 每个论断都有依据 | 引用完整率 100% + 结构化输出 | 答案里混着无依据的「常识」 |
| **知识有效** | 依据是当前生效的版本 | 版本 / 生效时间过滤 | 库里同时存在新旧两版 |
| **权限正确** | 不越权、不泄露 | **ACL 进索引 + 检索层过滤** | 检索后过滤，悄悄吃掉召回预算（§24.3.15） |

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 覆盖 vs 准确 | 召回放宽 → 什么都能答 | **重排 + 拒答** | 探索型场景可放宽 |
| 速度 vs 深度 | 多跳太慢 | 单跳快路径 + 多跳慢路径 | 复杂问题可接受秒级 |
| 简洁 vs 完整 | 短答案漏前提 | **带引用与前提条件** | 简单问答可折叠 |
| 通用 vs 垂直 | 通用域知识广但不深 | 领域知识库 + 语义层 | 开放域可放宽 |
| 实时 vs 稳定 | 知识更新后检索未生效 | 版本 + 增量索引 | 知识不变可全量 |
| 自动 vs 人工 | 全自动有幻觉风险 | 关键域人工复核 | 低风险可全自动 |
| 复用 vs 隔离 | 通用模型便宜但不懂内部 | 领域微调 / 检索增强 | 通用域可放宽 |
| 拒答 vs 体验 | 拒多了用户不用 | 澄清一次后给候选 | 高价值场景可多拒 |

**八类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| **幻觉** | 答得流畅但没有依据 | 噪音进上下文 | **重排 + 引用 + 拒答** |
| **答非所问** | 检索到的与问题不相关 | 召回单一 / 切分错 | 多路召回 + 重排 |
| **术语漏召** | 产品型号、编号查不到 | 只用向量检索 | BM25 + 历史问答对 |
| **引用错位** | 引用指向不相关的段落 | 重排缺失或只做语义匹配 | **引用精确率评测 + 逐句校验** |
| **过期作答** | 用旧政策回答 | 无版本 / 无生效时间 | 版本过滤 + 标注截止时点 |
| **越权泄露** | 答出了无权内容 | 权限只在生成层声明 | **ACL 进索引** |
| **过度拒答** | 能答却不答 | 阈值过严 / 无澄清 | 误拒率单独监控 |
| **多跳拼接错** | 各步都对，合起来不对 | 无合并一致性校验 | 子问题一致性校验 |

**信任分级**（答案的「输出契约」）：

| 级别 | 条件 | 展示方式 |
|---|---|---|
| 高 | 召回充分 + 重排置信高 + 引用完整 + 知识版本有效 | 直接给答案 + **可点开的引用** + 知识截止时点 |
| 中 | 答案可用但存在多义解读或知识较旧 | 给答案 + 引用 + **标注版本与时点** + 提示复核 |
| 低 | 仅部分论断有依据 / 存在冲突版本 | **给出有依据的部分 + 明确指出不确定的部分** |
| 拒绝 | 无依据 / 越权 / 歧义无法消解 | **明确说明原因** + 可走的替代路径（问谁、提工单、换问法） |

> **「低」这一档是本章特有的**：很多系统只有「有答案」和「没答案」两种状态，于是把「部分有依据」硬撑成完整答案——**这正是幻觉最常见的产生方式**。**中间档的存在，是让 Agent 敢承认「这一句我不确定」的结构性前提。**

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| **越权召回** | 用户问到无权文档 | **ACL 进索引 + 检索层过滤** |
| **提示注入** | 文档内容里藏指令 | 数据隔离 + 判定在代码层 + 引用校验 |
| **知识投毒** | 恶意文档进入知识库 | 入库审核 + owner + 版本 + 来源可信度 |
| **答案投毒** | 用户诱导输出内部信息 | 输出侧关键词与引用校验 |
| PII 泄露 | 文档含个人信息 | 入库脱敏 + 检索层按字段过滤 |
| 内部越权 | 跨租户检索 | 租户隔离 + 审计 |

> **提示注入在问答 Agent 里的危险级别高于其它 Agent**：其它章的注入目标是「让模型做多余的动作」，**问答章的注入目标是「让模型把一段恶意文本当成知识讲出来」**——而用户会认为那是系统的官方答案。**所以文档内容必须被严格当作数据包裹，且引用必须能追溯到源文档的原始位置。**

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| **注入 token（证据块）** | **最大（占输入 73%）** | **重排收敛 + 注入预算硬限** |
| LLM 调用 | 次之 | 单跳快路径、多跳按需 |
| 重排算力 | 小 | GPU 批处理、只重排 top-N |
| 向量 / BM25 检索 | 小 | 多路并行、缓存高频 Query |
| 索引与存储 | 小 | 分层、增量 |

### 24.3 理论与方法论

#### 24.3.1 S0：七项前置锚点

先落定七件事，它们共同决定**可行域**——不在可行域内的方案不参与讨论。

| # | 锚点 | 本章答案 | 影响 |
|---|---|---|---|
| 1 | **业务目标与成功标准** | 答案准确率 ≥ 85%、**幻觉率 ≤ 5%**、**误拒率 ≤ 8%**、引用完整率 100%、越权召回 0 | 决定召回 / 重排 / 拒答的取舍 |
| 2 | **规模量级** | 日问答 200 万、峰值 116 QPS、**知识库 500 万块（400 token/块）**、多跳占比 15% | 决定索引规模、注入预算与重排算力 |
| 3 | **质量属性优先级** | 证据正确 > 依据完整 > 知识有效 > 权限正确 > 体验 > 成本 | 决定降级顺序与 fail-closed 边界 |
| 4 | **硬约束** | 越权召回 0；引用完整率 100%；不输出无依据论断；PII 最小化；**审计覆盖率 100%** | 定义可行域 |
| 5 | **不可逆决策清单** | 见 §24.1 的本章七项 | 决策流程：多评审 + 原型 + 迁移方案 |
| 6 | **核心路径与事实源** | 核心路径 = 提问 → 路由 → 检索 → 重排 → 上下文 → 生成 → 引用 → 置信度 → 拒答 → 反馈；事实源 = **知识块 + 版本 + 引用关系 + 反馈记录** | 决定缓存与对账对象；向量索引与检索缓存全是投影 |
| 7 | **竞争与协作边界** | 文档系统、权限系统、企业搜索在外部；切分、召回、重排、引用、拒答、评测自建 | 决定服务边界与团队成本 |

> **第 2 项为什么改变答案**：问答系统的规模参数不只是 QPS，还有**「知识库块数」与「块大小」**。500 万块 × 400 token 意味着**全部塞进上下文是 20 亿 token**——远超任何窗口。所以「知识库多大」直接决定了「检索必须多准」，而检索的精度就是本章全部工程量的来源。

#### 24.3.2 4S 收敛顺序

```
S0 定题（锚点 + 不可逆清单）
   → Scenario 定问答量、问题类型、知识规模、多跳占比、时效要求、租户模型
      → Service 定路由、检索、重排、生成、引用、拒答、反馈的边界
         → Storage 定知识块、版本、引用关系、反馈记录的唯一事实源
            → Scale 定多路召回、重排算力、注入预算、缓存、降级
```

#### 24.3.3 Scenario：场景与规模

| 维度 | 数值 | 推导与来源 |
|---|---|---|
| 日问答量 | 200 万 | — |
| 平均问答 QPS | 200 万 ÷ 86400 | ≈ **23** |
| **峰值问答 QPS** | 23 × 5 | **116**（峰值系数 5：工作日 10:00–11:00 与 15:00–16:00 两个高峰承载当日 30%，叠加月初结算期脉冲） |
| 问题类型 | 单跳 85%、多跳 15% | **决定平均 LLM 调用次数（1.2 次）** |
| **知识库规模** | **500 万块**（约 20 亿 token） | **决定检索精度要求** |
| **块大小** | **400 token**（重叠 15%） | **决定召回粒度与注入量** |
| 文档数 | 8 万篇（制度、FAQ、产品手册、工单知识） | 决定块与文档的映射 |
| **多跳占比** | 15% | **多跳 token 是单跳的 3–5 倍** |
| 知识更新 | 每周 2% 块变更 + 每日 0.3% 新增 | 决定增量索引与版本策略 |
| 租户 | 集团 + 分子公司 + 部门，**密级三级** | 决定 ACL 模型 |
| 引用要求 | 每个实质性论断必须可点开原文 | **可信度的唯一载体** |

> **「知识库规模」是本章独有的关键参数**。传统系统的容量参数是 QPS；问答系统还必须给出**块数与块大小**，因为它们共同决定了「检索必须多准才不遗漏证据」。**500 万块的知识库，top-50 的召回命中率若只有 80%，就意味着每 5 个问题有 1 个注定要靠猜。**

| Generator | 生成 + 结构化引用 | 同步 | JSON 输出 |

#### 24.3.5 Storage：数据模型

| 数据 | 存储 | 关键设计 | 是事实源吗 |
|---|---|---|---|
| **知识块** | 对象存储 + 元数据 | 正文 + 标题路径 + 来源 + **版本 / 生效时间** + **ACL** | **是** |
| **文档元数据** | 元数据服务 | owner、密级、状态、废止标记 | **是** |
| **引用关系** | 问答日志 | question_id → chunk_id → 字符区间 | **是** |
| **反馈记录** | 数仓 | 点踩、质疑、引用点击、纠错 | **是** |
| 向量索引 | 向量库 | embedding + **ACL 字段** + 版本 | 否（可重建） |
| 倒排索引 | ES / BM25 | 关键词 + 过滤字段 | 否（可重建） |
| 历史问答对 | Redis / DB | 问题 → 已确认答案 + 引用 | 否（可重建） |
| 检索缓存 | Redis | Query → 命中块（**按 ACL 指纹分桶**） | 否（**必须可重建**） |
| 问答日志 | 数仓 | prompt、召回、重排、注入、答案、耗时 | **是** |

> **检索缓存必须按 ACL 指纹分桶**。同一个问题，不同用户、不同密级、不同租户，**可召回的块集合是不同的**。共用一个缓存 key，等于把 A 用户能看到的答案返回给 B 用户——**这是本章最容易被忽略的越权路径**。

**知识块的必备字段**：

| 字段 | 为什么必须有 |
|---|---|
| `chunk_id` | 引用定位 |
| `title_path`（文档 > 章节 > 小节） | **检索到一块要知道它出自哪一节**，否则答案无法定位 |
| `source_uri` + `span` | 引用可点开原文的具体位置 |
| `version` + `effective_from` + `status` | 知识时效 |
| `acl` | 权限过滤 |
| `owner` | 过期知识找得到人 |
| `embedding` | 向量召回 |

#### 24.3.6 Scale：扩展与兜底

| 维度 | 手段 | 触发条件 |
|---|---|---|
| **召回** | 多路并行 + 高召回宽窗口 | 命中率不足 |
| **重排** | GPU 批处理、只重排 top-N | 重排延迟超预算 |
| **注入** | 预算硬限 + 重排后收敛 | 上下文超限 |
| 生成 | 模型分级（单跳小模型） | token 成本高 |
| 检索 | Query 缓存、热门问答直答 | 重复率高 |
| 降级 | 模板拒答、只给引用不给答案 | 依赖故障 |

#### 24.3.7 问题理解与意图路由

| 类型 | 示例 | 路由 |
|---|---|---|
| **事实型** | 「出差住宿标准是多少」 | 单跳快路径 |
| **流程型** | 「报销要先审批吗」 | 单跳 + 流程块拼接 |
| **对比型** | 「A 方案和 B 方案的差别」 | 单跳 + 多块对比 |
| **多跳型** | 「我们和 X 公司的合同里违约金是多少」 | **多跳慢路径**（先定位实体） |
| **闲聊 / 越界** | 「写首诗」 | 明确拒答并说明边界 |
| **无依据型** | 问一个库里根本没有的事 | **拒答**（这是必须被评测覆盖的一类） |

**路由的关键判断：这个问题库里有答案吗？**

在生成之前先做一次**可行性判断**（用检索结果的最高重排分做阈值）：
- 最高分 ≥ 阈值 → 正常生成
- 最高分在灰区 → **先澄清**（「你说的 X 是 A 还是 B？」）
- 最高分 < 阈值 → **直接拒答，不进生成**

> **这一层能省掉大量幻觉**：让模型在「检索不到」的情况下自由发挥，它一定会编。**把「答不上来」这个判断前移到检索之后、生成之前，是本章最有效的一道防线**——它比任何事后的幻觉检测都便宜、都可靠。

#### 24.3.8 知识库与切分策略

**切分的三种粒度**：

| 粒度 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| 固定长度（200 token） | 召回精确、块小 | 语义被切断 | 条款、FAQ |
| 语义边界（按段落） | 语义完整 | 块大小不均 | 正文、手册 |
| **结构化（标题路径 + 表格行）** | **可定位、可引用、上下文完整** | 实现复杂 | **制度文档（主力）** |

**三条切分铁律**：

| 铁律 | 说明 |
|---|---|
| **每个块带标题路径** | 「差旅报销标准 > 住宿 > 一线城市」——没有它，引用无法定位，答案无法解释 |
| **表格行必须携带表头** | 单独一行「城市 \| 限额 \| 备注」是读不懂的 |
| **重叠 10–20%** | 跨块的句子不至于被切成两半 |

**切分粒度 ≠ 注入粒度**（本章的关键工程点）：

| 阶段 | 粒度 | 理由 |
|---|---|---|
| **检索 / 重排** | **小块（200 token）** | 精确——大块里混着多个主题，命中不精确 |
| **注入模型** | **合并段（600 token，小块 + 相邻块）** | 完整——答案需要上下文，孤立一句读不懂 |

量化（黄金集回放）：

| 方案 | recall@10 | 答案准确率 | 注入 token |
|---|---|---|---|
| 检索 500 token 块，直接注入 | 84% | 79% | 5,000 |
| **检索 200 token 块 + 注入时合并相邻块** | **91%** | **86%** | 5,400 |
| 检索 200 token 块，不合并 | 91% | 81% | 2,000 |

> **第三行是最容易被接受的方案，也是最差的一档**：它召回到了正确的块，却因为块被切碎而答不对。**召回到 ≠ 答得对**——**检索粒度与注入粒度必须分别设计**。

#### 24.3.9 检索：多路召回

**本节是多路召回的权威版**，§24.4.3 只引用。

**五路召回**：

| 召回路 | 擅长 | 成本 |
|---|---|---|
| **向量召回** | 语义相近、口语化提问 | 低 |
| **BM25 / 关键词** | 产品型号、编号、专有名词、缩写 | 低 |
| **结构化过滤** | 部门、文档类型、密级、时间范围 | 极低 |
| **历史问答对** | **问法相同、答案已确认** | 极低 |
| **实体 / 图谱** | 「我们和 X 公司的合同」这类涉及关系的问题 | 中 |

**融合**：用 RRF（Reciprocal Rank Fusion）合并各路排名，而不是加权求和分数——**不同召回路的分数不可比，排名可比**。

**多路召回的命中率提升**（黄金集 2,000 题）：

| 召回组合 | top-10 命中率 |
|---|---|
| 仅向量 | 71% |
| 仅 BM25 | 63% |
| **向量 + BM25（RRF）** | **82%** |
| **+ 历史问答对** | **89%** |
| + 实体 / 图谱 | 92% |

> **三条结论**：
> 1. **向量 + BM25 是最小可用组合**，各加一路都有明确收益。
> 2. **历史问答对是性价比最高的一路**：成本几乎为零（问题字符串匹配 + 已确认答案），命中率却从 82% 提到 89%。**而且它天然带「已确认」的语义**——这份答案是人核过的。
> 3. **专有名词场景必须上 BM25**：向量检索对型号、编号、政策代号是弱项，而这些恰好是企业知识库里最常被问的东西。

**召回阶段的两个纪律**：

| 纪律 | 原因 |
|---|---|
| **召回要宽** | 这一层的唯一目标是「不漏」，精度交给重排 |
| **召回必须带 ACL 过滤** | 过滤放在检索之后会悄悄吃掉召回预算（§24.3.15） |

#### 24.3.10 重排：把宽召回收敛成窄注入

**本节是重排的权威版**，§24.4.3 只引用。

**为什么必须有重排**：召回是**双塔**结构——query 和 chunk 分别编码再算相似度，快但粗；重排是**交叉编码**结构——query 与 chunk 一起进模型，能判断「这个块是否真的回答了这个问题」，准但慢。**双塔负责不漏，交叉编码负责不噪。**

**召回量的倒 U 型曲线**（黄金集回放，注入块数 k 与质量）：

| 注入块数 k | 证据命中率 | 答案准确率 | **幻觉率** | 上下文 token |
|---|---|---|---|---|
| 3 | 61% | 62% | 14% | 1,200 |
| 5 | 74% | 73% | 8% | 2,000 |
| **10** | **86%** | **85%** | **5%** | 4,000 |
| 20 | 93% | **87%** | 9% | 8,000 |
| 50 | 97% | **82%** | **18%** | 20,000 |

**三条读数**：

1. **k 从 10 → 50：证据命中率 +11pp，答案准确率反降 3pp，幻觉率从 5% 涨到 18%。**
2. **倒 U 型的拐点在 k = 10–20 之间**；超过拐点，**多召回的每一条都在为答案的噪音做贡献**。
3. **幻觉率是随 k 单调上升的**（14% → 8% → 5% → 9% → 18%，先降后升是过少噪声导致），**准确率的最高点远早于命中率的最高点**。

**「召回宽、注入窄」的完整链路**：

```
宽召回（保证不漏）
  → 召回 top-50（向量 + BM25 + 历史问答对 + 实体）—— 精度交给重排
  → 重排（cross-encoder 批处理，50 对 × 2.4ms = 120ms）
  → 注入 top-10（4,000 token）
  → 结果：上下文 −74%、准确率 +3pp、幻觉率 −13pp、月省 ¥192 万
```

**「召回宽、注入窄」的完整方案与收益**：

| 方案 | 上下文 / 问 | 准确率 | 幻觉率 | 月成本 |
|---|---|---|---|---|
| **top-50 直接注入**（现状） | 21,500 token | 82% | 18% | **≈ ¥300 万** |
| **top-50 召回 → 重排 → 注入 top-10** | 5,500 token | **85%** | **5%** | **≈ ¥108 万** |
| 收益 | **−74%** | **+3pp** | **−13pp** | **−¥192 万 / 月** |

> **三个指标同时改善，是本章最有说服力的一张表。** 重排的成本是 **+120ms**（50 对 cross-encoder 批处理，单对约 2.4ms）与一笔相对 token 成本可忽略的 GPU 费用；**换来的是上下文 −74%、幻觉率 −13pp、月省 ¥192 万**。
>
> **这说明了一个普遍规律**：**很多「模型不够强」的问题，实际是「喂给模型的东西不够干净」。** 换更强的模型往往更贵且收益有限；加一层重排，往往同时更便宜更准。

**为什么噪音会被编成答案**（幻觉的机制）：

```
生成能力 >> 判别能力
模型被问「住宿标准是多少」，上下文里有 50 块，其中 12 块提到金额
→ 模型会从这 12 块里「综合」出一个看起来合理的数字
→ 它无法区分「这块说的是住宿标准」和「这块说的是餐补标准」
```

> **模型的判别能力弱于生成能力，是幻觉的根源。** 推理模型能写「根据文档，标准是 XX 元」，但它未必能意识到这 12 块里其实有 8 块讲的是另一个标准。**重排的作用，就是把「模型要判断的东西」从 50 块减到 5 块——它不提升模型的判别能力，它减少了模型需要判别的东西。**

**重排的工程约束**：

| 约束 | 说明 |
|---|---|
| 只重排 top-N | N 从 50 降到 20，重排耗时减半，召回命中率掉 3pp（实测） |
| 批处理 | 一次请求的 N 对一起打分，避免逐对串行 |
| 重排模型可降级 | 交叉编码不可用时退回向量分数排序，**并打标 `degraded`** |
| **重排结果要落日志** | 没有重排日志，就无法解释「为什么这条没被引用」 |

#### 24.3.11 上下文构建与预算

**上下文预算表**：

| 组成 | token | 占比 | 说明 |
|---|---|---|---|
| 指令与拒答规则 | 1,000 | 18% | 含输出格式与引用要求 |
| **注入证据（重排后 top-10 × 400）** | **4,000** | **73%** | **最大头** |
| 历史对话与摘要 | 500 | 9% | 滚动摘要 |
| **合计（输入）** | **5,500** | 100% | 输出预留另计 600 |

**上下文预算构成**：

```
注入证据（重排后 top-10）
  → 指令与拒答规则 ······················ 1,000 token（18%）
  → 注入证据（top-10 × 400）············· 4,000 token（73%）  ← 最大头
  → 历史对话与滚动摘要 ···················   500 token（ 9%）
  → 输出预留 ·····························   600 token
  → 裁剪顺序：历史 → 低分块 → 低密度块 → few-shot → 证据（最后）
```

**注入块的必备包装**（不是裸文本）：

```
[标题路径] 差旅报销标准 > 住宿 > 一线城市
[来源]     《员工差旅管理办法》v3.2 · 第 4.1 节
[版本时效] 生效于 2025-03-01 · 状态：生效中
[可点开]   doc://travel-policy/4.1
```

> **这四行包装是引用可核验的前提**。裸文本块即使内容正确，用户也无法判断它出自哪一节、是第几版、能不能点开核对。**「引用完整率 100%」这条 P0 护栏，靠的就是这层包装。**

**预算不够时的裁剪顺序**（先丢什么）：

```
1. 历史对话（压成摘要）        ← 最先丢
2. 低分注入块（重排分从低到高砍）
3. 低密度块（信息量低的块整块丢）
4. 指令中的示例（few-shot）    ← 最后丢
5. **注入证据本身不可丢** → 丢到超限就触发「预算不足」降级，而不是截断证据
```

> **第 5 条是关键**：证据块被截断会产生「引用指向不完整」的答案——**这比少引用几块更糟**。**所以证据不够时要明说「资料不足，无法回答」，而不是截断了还装作答了。**

#### 24.3.12 生成与引用

**结构化输出**：

```json
{
  "answer": "一线城市住宿标准为每晚 600 元，需凭发票报销……",
```

**引用的四条要求**：

| 要求 | 说明 |
|---|---|
| **粒度到块 + 块内区间** | 只到文档级，用户还得自己找；到块 + 区间才能一键定位 |
| **必须可点开原文** | 不可点开的引用等于没有引用 |
| **必须通过精确率校验** | 引用的块确实支持该论断（逐句校验） |
| **必须标知识截止时点** | 用户要知道「这是基于哪一版」 |

**引用完整率是 P0**：

| 完整率 | 后果 |
|---|---|
| 100% | 每个论断可核验，信任的基础 |
| 95% | 用户点开发现 1 句没依据 → **整体信任崩塌**（不是「差 5%」） |

> **引用完整率是典型的「非线性信任指标」**：100% 与 95% 的差别不是「5% 的答案差一点」，而是「用户是否还愿意点开引用」。**一条无依据的引用会污染整个答案的可信度**，因为用户不知道哪一条是编的。

#### 24.3.13 拒答、澄清与置信度

**本节是拒答决策的权威版**，§24.4.5 只引用。

**拒答与澄清的三种类型**：

| 类型 | 场景 | 动作 |
|---|---|---|
| **无依据拒答** | 检索不到相关内容 | 「知识库中没有找到相关制度」+ **可走的下一步**（问谁 / 提工单 / 换问法） |
| **歧义澄清** | 有多个合理解读 | **追问一次**（「你说的 X 是 A 还是 B？」），**最多一次** |
| **权限拒答** | 无权查看 | 「该内容需要 XX 权限，可向 XX 申请」——**不泄露内容存在性之外的信息** |

**置信度不可信**（与第二十二章同理）：模型自报的 confidence 不可靠。更稳的做法是**用重排分数 + 独立分类器头**，或**多次采样看一致性**。

**双面指标：幻觉率 vs 误拒率**

| 拒答阈值 | 幻觉率 | 误拒率 | 综合可用率 = 1 − 幻觉 − 误拒 |
|---|---|---|---|
| 严格（高阈值） | 2% | 18% | 82% |
| **平衡（推荐）** | **5%** | **8%** | **87%** |
| 宽松（低阈值） | 14% | 3% | 86% |

> **看这张表最重要的一行不是「平衡」那一行，而是「严格」与「宽松」两行的对比**：两者的**综合可用率几乎相同（82% vs 86%）**，但**信任代价完全不同**——
>
> - **幻觉率 14%**：用户按错误答案操作 → **信任崩塌，且不可逆**
> - **误拒率 18%**：用户多问一次 / 换个问法 → **成本是一次交互，可恢复**
>
> **所以拒答策略必须偏向严格。** 单看「综合可用率」会得出「严格和宽松差不多」的结论，从而在阈值上调时反复摇摆；**必须给「信任损失」单独定价**。这就是「拒答率是双面指标」的真正含义：**它不是往一边调的问题，而是要按两类错误的代价不对称来定。**

**阈值决策**：

```
幻觉率 vs 误拒率
  → 严格（高阈值）：幻觉  2% + 误拒 18% → 综合可用率 82%
  → 平衡（推荐）  ：幻觉  5% + 误拒  8% → 综合可用率 87%
  → 宽松（低阈值）：幻觉 14% + 误拒  3% → 综合可用率 86%
  → 严格与宽松的综合可用率接近，但信任代价完全不同
  → 幻觉不可逆，误拒可恢复 → 阈值必须偏向严格
```

**幻觉的成本量化**（回到 §24.2 的放大器）：

```
日问答 200 万 × 幻觉率 18% = 36 万条无依据答案 / 天
假设 1% 被用户采信并据此行动，需要人工纠正（每次 ¥50）
→ 1,800 次 × ¥50 = ¥18 万 / 天 ≈ ¥540 万 / 月
对比：把 top-50 改成重排后 top-10 每月省 ¥192 万 token
→ **省下的 token 钱，会被幻觉的纠正成本吃掉还多**
```

> **这个对比是本章最实用的一条结论**：**在问答 Agent 里，降低幻觉率的收益大于降低 token 成本。** 而降低幻觉率最便宜的手段不是换更强的模型，是**重排**。

**拒绝时的输出契约**：拒答也必须是**有用的答案**——「库里没有 + 你可以问谁 + 你可以换什么问法 + 已知的相近制度是什么」。**一句「无法回答」是最差的拒答。**

#### 24.3.14 多跳与复杂问题拆解

**多跳的判定**：答案需要串联 ≥ 2 个来源，或需要先定位一个实体。

**分解流程**：

```
问题 → 实体链接（找到「X 公司」「3 号合同」）
     → 拆成子问题（子问题之间有依赖）
     → 逐个检索 + 重排（每个子问题独立预算）
     → 逐步作答
     → **合并一致性校验**（子答案之间是否矛盾）
```

**三笔账**：

| 项 | 数值 | 说明 |
|---|---|---|
| 多跳占比 | 15% | — |
| LLM 调用次数 | 单跳 1 次，多跳 3–5 次 | 平均 1.2 次 |
| **注入预算** | **总量受同一预算约束，每跳更少** | 2 跳时每跳给 2,500 而不是 4,000 |
| token 倍数 | 多跳是单跳的 **3–5 倍** | — |

**合并一致性校验**（本章特有、最易漏的一步）：

| 失败 | 表现 | 防线 |
|---|---|---|
| **子答案矛盾** | 「合同期限是 2 年」与另一条说「3 年」 | 合并前检测数值/日期冲突 |
| **子答案都偏** | 各步都对，但合起来不成立 | 合并后整体再校验一次 |
| **分解错** | 根本不需要拆，或拆错了维度 | 分解结果要与原问题做语义回检 |

> **多跳的失败模式与单跳完全不同**：单跳的失败是「证据不对」，多跳的失败是「**每一步都对，但组合是错的**」。**只验子步骤不验合并，等于没验。**

#### 24.3.15 权限与租户隔离

**核心原则**：**ACL 进索引，检索层过滤。模型看不到的文档，不可能被写进答案。**

**两种方案的量化对比**：

| 方案 | 做法 | 召回命中率 | 风险 |
|---|---|---|---|
| **A：ACL 进索引** | 块带 acl 字段，检索时过滤 | **89%**（top-50 中过滤后仍余 50 块） | 权限变更需更新受影响块的索引字段 |
| **B：检索后过滤** | 索引不带 ACL，取回 top-50 再按用户过滤 | **62%**（top-50 中 40 块被过滤掉，只余 10 块） | **召回预算被悄悄吃掉 44%** |

> **方案 B 的失败极其隐蔽**：它不报错、不越权，只是**让有效召回从 50 变成 10**，检索质量断崖式下降。团队通常会去调 top-k 或换模型，而**真正的病根是过滤位置错了**。
>
> **所以「权限过滤放在检索之前还是之后」不只是安全选择，也是质量选择。**

**权限变更的传播**：

| 机制 | 延迟 | 说明 |
|---|---|---|
| **增量更新索引的 ACL 字段** | 秒级 | 按受影响用户 / 部门 / 密级反查块并更新 |
| 权限变更事件 → 重建受影响文档的块 | 分钟级 | 兜底 |
| **过滤层版本号** | — | 权限服务版本与索引版本对齐，落后则拒绝而非放行 |

> **权限版本落后时必须 fail-closed**（拒绝检索）而不是 fail-open（放行旧权限）。**这与问数章「权限服务故障就拒绝」是同一条原则。**

#### 24.3.16 知识时效与版本

**版本模型**：

| 字段 | 说明 |
|---|---|
| `version` | 同一文档的版本号 |
| `effective_from` / `effective_to` | 生效区间 |
| `status` | 草稿 / 生效中 / 已废止 |
| `owner` | 过期了找得到人 |

**三条时效规则**：

| 规则 | 说明 |
|---|---|
| **检索只取生效中的版本** | 已废止版本不进召回 |
| **冲突版本取最新的生效版本** | 同文档多版本共存时按 `effective_from` 取最新且生效中的 |
| **答案标注知识截止时点** | 用户要知道「基于哪一版、截至什么时候」 |

**知识复用放大**：

```
一条过期条款被命中一次 → 它不会被「用一次就废」
→ 只要它还在库里、还在被召回，就会被反复复用

量化：库中 1% 的块已过期（5 万块），但它们贡献 3% 的问答
→ 200 万 × 3% = 6 万次 / 天 基于过期知识作答
→ 用户按过期政策操作 → **一次错误影响多个用户，但只有第一个会来投诉**
```

> **过期知识的危害不在于错一次，而在于「同一个错误被复制 6 万次」**。而用户只会反馈自己遇到的那一次——**所以这类问题的排查难度极高，因为反馈量与影响量严重不成比例**。

**时效的三道防线**：

| 防线 | 做法 |
|---|---|
| 入库 | 强制填 `effective_from` 与 `owner`，缺失不通过 |
| 检索 | 只召回生效中版本；命中即将过期的块时告警 |
| 回答 | 标注知识截止时点；命中超过 N 天未复核的块时标注「建议与 X 确认」 |

#### 24.3.17 评测方法

**黄金集的三个维度**（缺一不可）：

| 维度 | 内容 | 为什么必须有 |
|---|---|---|
| **可答题** | 问题 + 标准答案 | 基本盘 |
| **不可答题** | 库里没有的问题 | **不覆盖它，就等于把拒答能力训没了** |
| **越权题** | 有答案但用户无权 | 只测可答题的系统，会在权限上裸奔 |

**指标体系**：

| 指标 | 定义 | 地位 |
|---|---|---|
| **幻觉率** | 答案含无依据论断的比例 | **核心** |
| **误拒率** | 本可回答却拒答的比例 | **核心** |
| 答案准确率 | 与标准答案语义一致 | 结果指标（标注成本高） |
| **引用精确率** | 引用的块确实支持该论断 | **核心**（比准确率更易标注） |
| **引用召回率** | 标准答案的关键论断都被引用 | 核心 |
| 引用完整率 | 每个论断都有引用 | 硬约束 |
| 拒答恰当率 | 该拒的拒了 | 与误拒率一起看 |
| **recall@k（检索层）** | 证据在 top-k 内 | **上游指标，不是结果指标** |
| 线上：答案质疑率 | 用户点「这个不对」 | 生产环境的幻觉代理指标 |
| 线上：引用点击率 | 用户点开引用核对 | 可信度代理指标 |

> **「引用精确率」比「答案准确率」更值得优先做**，因为它**标注成本低得多**（只需判断「这段文字支持这句话吗」，不需要写出标准答案），而且**定位更准**——它能直接告诉你是「召回错了」还是「重排错了」还是「生成错了」。
>
> **recall@k 是上游指标**：retrieval 命中率 90% 但准确率只有 70%，说明问题出在重排与生成，不是召回。**只看 recall@k 就去加大召回，是本章最常见的误诊。**

#### 24.3.18 容量与成本估算

**本节是容量口径的权威版**，§24.5 与 §24.6 只引用。

**假设**：日问答 200 万，峰值系数 5；单跳 85% / 多跳 15%，平均 1.2 次 LLM 调用；上下文输入 5,500 token（指令 1,000 + 注入 4,000 + 历史 500），输出 600 token；注入 = 重排后 top-10 × 400 token；模型价格输入 ¥2 / 百万、输出 ¥8 / 百万。

**一、流量**

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均问答 QPS | 200 万 ÷ 86400 | ≈ **23** |
| **峰值问答 QPS** | 23 × 5 | **116** |
| **峰值 LLM 调用** | 116 × 1.2 | **139** |
| 峰值重排对数 | 116 × 50 | **5,800 对 / 秒** |
| 峰值召回请求 | 116 × 5 路 | ≈ **580** |

> **重排是本章的第二大算力消耗**：5,800 对/秒的 cross-encoder 打分，按单对 2.4ms 批处理，约需 **1.4 万 QPS 的 GPU 吞吐**——这是一个必须提前算的数，因为**它不在 LLM 配额里，却会在重排服务上先炸**。

**二、token 与成本**

| 指标 | 计算 | 结果 |
|---|---|---|
| 每问输入 token | 5,500 × 1 + 3,000 × 0.2（多跳追加） | **6,100** |
| 每问输出 token | 1.2 × 600 | 720 |
| **日输入 token** | 6,100 × 200 万 | **122 亿** |
| 日输出 token | 720 × 200 万 | **14.4 亿** |
| **日合计 token** | — | **136.4 亿** |
| 输入成本 | 12,200 百万 × ¥2 | ¥24,400 |
| 输出成本 | 1,440 百万 × ¥8 | ¥11,520 |
| **日 LLM 成本** | — | **≈ ¥35,920**（约 **¥108 万 / 月**） |

**三、与「不做重排」的对比**

| 方案 | 输入 token / 问 | 日输入 token | 日成本 | 月成本 |
|---|---|---|---|---|
| **top-50 直接注入** | 22,100 | 442 亿 | ¥99,920 | **≈ ¥300 万** |
| **重排后注入 top-10** | 6,100 | 122 亿 | ¥35,920 | **≈ ¥108 万** |
| 节省 | **−72%** | −320 亿 | **−¥64,000 / 天** | **−¥192 万 / 月** |

**四、存储与索引**

| 数据 | 计算 | 结果 |
|---|---|---|
| 知识块 | 500 万 × 400 token ≈ 2GB 正文 + 元数据 | ≈ **12 GB**（含元数据与 ACL） |
| 向量索引 | 500 万 × 1KB | ≈ 5 GB |
| 倒排索引 | 500 万 × 0.5KB | ≈ 2.5 GB |
| **问答日志** | 200 万 × 8KB（含召回、重排、注入、答案） | **≈ 16 GB / 天（5.8 TB / 年）** |
| 引用关系 | 200 万 × 10 引用 × 100B | ≈ 2 GB / 天 |
| 反馈记录 | 200 万 × 200B | ≈ 400 MB / 天 |

**五、结论**

1. **成本的大头是注入 token（占输入 73%）**，而注入量由重排收敛决定——**重排是本章唯一同时改善成本与质量的杠杆**。
2. **第二瓶颈是重排算力（5,800 对/秒）**，它比 LLM 配额更早成为扩容的卡点，且不在任何 LLM 成本预算里。
3. **问答日志是最大的存储消耗（16 GB/天）**，必须分层与采样。
4. **幻觉的隐含成本（¥540 万/月）大于 token 成本（¥108 万/月）**——**优化优先级应当是幻觉率优先**。
5. **必须先量「问题类型分布」与「多跳占比」**：它决定平均 LLM 调用次数与 token 曲线形状。

#### 24.3.19 成本模型

| 成本项 | 量级 | 优化手段 | 收益量级 |
|---|---|---|---|
| **注入 token** | **最大（输入的 73%）** | **重排收敛 + 注入预算硬限** | **−72% 输入** |
| LLM 调用次数 | 次之 | 单跳快路径、多跳按需、小模型处理简单题 | 约 −20% |
| 重排算力 | 小 | 只重排 top-20、降级到向量分数 | 约 −50% |
| 检索 | 小 | Query 缓存、热门问答直答 | 约 −15% |
| 索引与日志 | 小 | 分层、采样、TTL | — |

> **本章的成本优化只有一条主线：让更少的 token 承载更可靠的证据。** 换模型、调 Prompt、砍系统提示词，收益都在个位数百分比；**而「重排 + 注入预算」这一个动作，同时省 72% 的钱、提 3pp 准确率、降 13pp 幻觉率。**

### 24.4 工程落地与规则护栏

#### 24.4.1 端到端链路

```
用户提问 / 工单转入
  → Gateway（鉴权、租户、密级 → ACL 上下文）
  → Intent Router（事实型 / 流程型 / 多跳 / 越界；单跳快路径 vs 多跳慢路径）
  → Query Planner（仅多跳：实体链接 + 子问题分解）
  → Retriever（五路召回 + 融合 RRF + ACL 过滤）
  → Reranker（cross-encoder，top-50 → top-10）
  → Context Builder（预算裁剪 + 块包装：标题路径 / 版本 / 可点开链接）
  → Generator（结构化输出：答案 + 引用 + 置信度 + 截止时点）
  → Verifier（引用精确率校验 + 幻觉检测 + 拒答判定，代码层）
  → Answer（答案 + 可点开引用 / 或澄清 / 或拒答 + 下一步建议）
  → Feedback（点踩、质疑、引用点击、纠错 → 评测闭环）
```

> **图里最重要的一行是「Verifier」和它前面的「Context Builder」**：前者是**代码层的最后一道关卡**（不靠模型自觉），后者是**唯一的注入收敛点**（所有裁剪在这里发生）。**这两个位置决定了系统是「可控的检索增强」还是「一个会写小作文的模型」。**

#### 24.4.2 意图路由护栏

| 护栏 | 说明 |
|---|---|
| 问题分类 | 事实 / 流程 / 对比 / 多跳 / 越界 |
| 单跳快路径 | 不进 Planner，直接检索 |
| **可行性前置判断** | 检索后、重排分低于阈值 → 直接拒答，**不进生成** |
| 歧义澄清 | **最多一次**；两次澄清仍不确定 → 给候选列表或拒答 |
| 越界识别 | 「写首诗」「你是谁」→ 明确说明边界 |
| 租户 / 密级上下文 | 鉴权结果作为 ACL 过滤输入 |

#### 24.4.3 检索与重排护栏

| 护栏 | 说明 |
|---|---|
| **多路必做** | 向量 + BM25 必做；历史问答对强烈建议 |
| **召回要宽** | 精度交给重排，不在召回阶段收窄 |
| **ACL 必须在检索层过滤** | 检索后过滤会吃掉 44% 的召回预算 |
| **重排范围可配但有下限** | top-N 不得低于 20（低于则命中率掉 3pp） |
| **重排降级要打标** | 交叉编码不可用 → 退回向量分数，标 `degraded` |
| **重排日志必落** | 否则无法解释「为什么这条没被引用」 |
| **缓存按 ACL 指纹分桶** | 否则会跨权限返回答案 |

#### 24.4.4 上下文与生成护栏

| 护栏 | 说明 |
|---|---|
| **注入预算硬限** | 超出即降级，**不截断证据** |
| **块四件套包装** | 标题路径 / 来源 / 版本时效 / 可点开链接 |
| 裁剪顺序固定 | 历史 → 低分块 → 低密度块 → few-shot；**证据最后** |
| **结构化输出** | JSON，含 answer / citations / confidence / cutoff / caveats |
| **每条引用必须可点开** | 不可点开的引用等于没有引用 |
| 引用粒度 | 块 + 块内字符区间 |
| 答案必带知识截止时点 | — |
| 低置信输出 | 只给有依据的部分 + 明确指出不确定处 |

#### 24.4.5 引用与拒答护栏

| 护栏 | 说明 |
|---|---|
| **引用完整率 100%** | 每个实质性论断都要有引用 |
| **引用精确率校验** | 逐句校验「这块支持这句话吗」，在代码层 |
| **幻觉率与误拒率分开统计** | **单看拒答率会得出反向结论** |
| **拒答必须有用** | 「库里没有 + 问谁 + 换什么问法 + 相近制度」 |
| 澄清上限 1 次 | 两次仍不确定 → 给候选或拒答 |
| 置信度来源可解释 | **用重排分 + 分类器头**，不用模型自报 |
| 权限拒答不泄露存在性 | 只说需要什么权限，不描述内容 |

#### 24.4.6 权限与数据护栏

| 护栏 | 说明 |
|---|---|
| **ACL 进索引** | 检索层过滤 |
| **权限版本对齐** | 索引落后于权限服务 → **拒绝检索（fail-closed）** |
| 文档内容一律当数据包裹 | 防提示注入 |
| 入库脱敏 | PII 不进知识库，或按字段级 ACL |
| 入库审核 | 投毒防线：来源可信度 + owner + 审核状态 |
| 审计全量留痕 | 谁问了什么、召回了什么、答了什么、引用了哪些块 |

#### 24.4.7 降级矩阵（Fail-Open / Fail-Closed）

**本节是降级的权威版**，§24.5.6 只引用。

判据：**依赖失效时，失效的后果是「答不出来」还是「答出错 / 答越权」？**

| 依赖 / 环节 | 典型故障 | 策略 | 降级动作 |
|---|---|---|---|
| **权限服务 / ACL 索引** | 超时、版本落后 | **Fail-Closed** | **拒绝检索**，不返回任何块 |
| **向量检索** | 超时 | 降级 | 只用 BM25；再失败则拒答 |
| **BM25 检索** | 超时 | 降级 | 只用向量；再失败则拒答 |
| **重排服务** | 超时 / 限流 | 降级 | 退回向量分数排序，**打标 `degraded`** |
| **LLM 服务** | 超时 / 限流 | 模型降级 | 切小模型；再失败则**只返回引用块，不生成答案** |
| **知识库元数据 / 版本服务** | 超时 | **Fail-Closed** | 拒绝回答（无法确认时效） |
| **Verifier 服务** | 超时 | **Fail-Closed** | **不输出未校验的答案**，只给引用 |
| **历史问答对缓存** | 不可用 | 降级 | 跳过这一路召回 |
| **反馈服务** | 不可用 | 降级 | 不影响作答，只是评测延迟 |

**治理要点**：每次降级打标 `degraded=true`、`fallback_mode` 与 `reason_code`；**「只返回引用块，不生成答案」是本章最有价值的一条降级**——它把系统从「编答案」拉回「给证据」，用户仍能自己看原文。

#### 24.4.8 延迟预算与超时降级

**本表是唯一的延迟口径来源**，其他小节只引用。

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 接入与鉴权 | 50ms | 200ms | 429 / 登录提示 |
| 意图路由与可行性预判 | 100ms | 300ms | 按事实型处理 |
| **多路召回（并行）** | **300ms** | **800ms** | **丢掉最慢的一路**，标 degraded |
| **重排（top-50 批处理）** | **120ms** | **300ms** | **退回向量分数排序** |
| 上下文构建 | 30ms | 100ms | 裁历史与低分块 |
| **LLM 生成（首 token）** | **600ms** | **2s** | 换小模型 |
| LLM 生成（完整答案） | 1.2s | 4s | **只返回引用块，不生成答案** |
| **引用校验与拒答判定** | **150ms** | **400ms** | **不输出未校验的答案** |
| **单跳合计** | **< 2s（P95）** | 5s | — |
| **多跳合计（每跳）** | **< 8s（P95）** | 20s | 中途返回已完成的步骤 |

> **本章的延迟预算里有一个前面几章没有的约束**：**「引用校验与拒答判定」占 150ms**。它不是可选的质量增强——**它是「不输出未校验答案」的最后一道关卡**，所以它的预算不能被前面的环节挤掉。**如果召回或重排超时，正确做法是降级检索质量并打标，而不是砍掉校验。**

#### 24.4.9 观测与压测

**观测**：

| 类别 | 指标 |
|---|---|
| 检索 | **recall@k**、各召回路命中率、**过滤前后候选数**（权限过滤吃掉了多少） |
| 重排 | 重排耗时 P95、**重排前后排名变化**、降级比例 |
| 注入 | **注入块数**、**注入 token 占比**、预算耗尽率 |
| 质量 | **幻觉率**、**误拒率**、引用精确率 / 召回率 / 完整率、**答案质疑率**、**引用点击率** |
| 权限 | 越权召回数、**权限版本落后次数** |
| 时效 | 命中过期块次数、待复核知识占比 |
| 成本 | 单问 token、注入 token、单问成本 |
| 延迟 | 首 token P95、总 P95、各阶段分解 |

> **「过滤前后候选数」是本章特有的必看指标**：它直接告诉你权限过滤吃掉了多少召回预算。如果 top-50 过滤后只剩 12 块，那你的召回质量下降是被权限吃掉的，**而不是检索模型不行**。

**压测**：

- 峰值 5 倍问答。
- **top-50 重排的算力压测**（本章的第二个卡点）。
- 全库知识块的一次性重建（换 embedding 模型）。
- ACL 大规模变更（离职 / 转岗 → 批量失效）。
- 知识版本冲突（新旧版本同时生效）。
- **注入预算超限**（验证是降级而不是截断证据）。
- LLM 不可用（验证「只返回引用块」的降级）。
- 越权提问（红队）。
- **提示注入**：在文档里埋指令，验证不被当作知识输出。

| 领域 | 护栏 | 优先级 |

| **权限 fail-closed** | 权限服务 / ACL 索引不可用 → 拒绝检索；版本落后 → 拒绝 | **P0** |

| **引用完整率 100%** | 每个实质性论断都有可点开的引用 | **P0** |
| **引用精确率校验** | 代码层逐句校验，不靠模型自觉 | **P0** |
| **幻觉率上限** | ≤ 5%，超阈值熔断并降级 | **P0** |
| **注入预算硬限** | 超限即降级，**不截断证据** | **P0** |
| **可行性前置判断** | 检索后、重排分低于阈值 → 直接拒答，不进生成 | **P0** |
| **多路召回** | 向量 + BM25 必做 | **P0** |
| **重排必做** | 交叉编码；不可用时降级并打标 | **P0** |

#### 24.4.11 上线检查（10 问）

1. **召回是否多路**？向量 + BM25 是否都在？**历史问答对这一路有没有做**？
2. **ACL 是否在检索层过滤**？**过滤前后的候选数是否有监控**？权限版本落后时是否 fail-closed？
3. **重排是否在链路上**？重排范围多少？**重排不可用时是否降级并打标**？重排日志是否落盘？
4. **注入预算是否有硬限**？超限时是**降级还是截断证据**？块是否带齐四件套包装？
5. **引用完整率是否 100%**？**引用是否逐句校验**？引用是否可点开到原文位置？
6. **幻觉率与误拒率是否分开监控**？阈值是否按**两类错误代价不对称**来定？
7. **可行性判断是否前置到生成之前**？低分场景是否真的不进生成？
8. **拒答是否有用**（库里没有 + 问谁 + 换什么问法）？澄清是否限一次？
9. **知识时效**三道防线是否都在？答案是否标了知识截止时点？
10. **黄金集是否包含不可答题与越权题**？提示注入红队是否通过？

### 24.5 典型案例与端到端解决

#### 24.5.1 案例：企业制度问答（「出差住宿标准是多少」）

**链路**：

1. **接入与 ACL**：员工属集团财务部，密级 L2；ACL 上下文带入检索。
2. **意图路由**：事实型 → **单跳快路径**，不进 Planner。
3. **多路召回**（宽）：
   - 向量召回 22 块（差旅管理办法 4.1、员工手册 12.3、报销系统 FAQ、订酒店操作说明……）
   - BM25 召回 3 块（「住宿标准」精确命中标题「4.1 住宿限额」）
   - 历史问答对 2 块（相似问题「出差住酒店能报多少」→ 已确认答案 + 引用）
   - 去重后 **34 块**
4. **重排**（窄）：cross-encoder 打分 34 对 → 取 top-10。第 1 名是「4.1 住宿限额」，**第 11 名是「餐补标准」**——差一名就被挡在外面。
5. **上下文构建**：top-10 块 + 四件套包装（标题路径 / 来源 / 版本时效 / 可点开链接）= **4,000 token**。
6. **生成**：
   - 答案：一线城市 600 元/晚、二线 450 元、其他 350 元；需凭发票；不含总监及以上职级。
   - 引用 3 条：4.1 住宿限额、4.2 城市分级表、附则 7.2 适用范围。
   - 置信度 high，知识截止 2025-03-01。
7. **Verifier（代码层）**：逐句校验 3 条引用 → 全部支持对应论断；幻觉检测 → 无无依据论断。
8. **输出**：答案 + 3 条可点开引用 + 知识截止时点 + 「不含总监及以上」的提示。

> **这个案例最值得讲的是「如果没做重排会怎样」**：把 34 块全注入，上下文 13,600 token（3.4 倍），而答案里会多出一句 **「餐补每天 80 元」**——
>
> **因为「餐补标准」块就在上下文里，模型把它综合进来了。**
>
> **这就是幻觉最典型的形态：不是凭空编造，是从真实但不相关的内容里综合错位。** 用户看到两个数字，无法判断哪个是住宿标准、哪个是餐补标准——**这比完全编一个数字更难被发现，也更危险。**

#### 24.5.2 变体 A：多跳问题

**问题**：「我们和 X 公司的合同里违约金条款是什么？」

1. **实体链接**：「X 公司」→ 公司实体 ID；「合同」→ 我方主体 + 合同文档类型。
2. **拆子问题**：① 我方与 X 公司的合同是哪一份？② 该合同的违约金条款是什么？
3. **子问题 1**：检索（结构化过滤 + 向量）→ 合同《2024-089 号框架协议》→ 锁定文档。
4. **子问题 2**：在该合同的块中检索「违约金」→ 命中 3 块（第 8.2 条 + 附件二违约金表）。
5. **合并一致性校验**：条款版本与合同版本一致 ✓；条款金额与附件表格一致 ✓。
6. **输出**：答案 + 引用（合同 2024-089 第 8.2 条 + 附件二）+ 合同生效期。
7. **成本**：3 次 LLM 调用、注入 6,500 token（比单跳多 45%）。

> **第 5 步是最容易漏的**：子问题 ① 和 ② 各自都答对了，但**如果合同在检索期间被换成了修订版，② 的答案就来自旧版合同**——**每一步都对，组合是错的**。所以多跳必须做合并一致性校验，尤其是**版本一致性**。

#### 24.5.3 变体 B：跨租户与密级隔离

**问题**：「我们事业部今年和去年同期的营收对比如何？」（用户仅有本事业部数据权限）

**方案 A（ACL 进索引）**：

| 步骤 | 候选数 |
|---|---|
| 全库语义召回 top-50 | 50 |
| 其中本事业部相关 | 42 |
| **本事业部相关且在本事业部口径内** | **50**（ACL 作为过滤条件参与检索排序） |

**方案 B（先召回后过滤）**：

| 步骤 | 候选数 |
|---|---|
| 全库语义召回 top-50 | 50 |
| 其中前 20 位是**集团口径与其他事业部**的营收块（语义极近，标题里都有「营收」「同期对比」） | — |
| **过滤后实际可用** | **30** |

> **差异不在安全，在质量**：两种方案都不泄露任何越权内容（**方案 B 同样安全**）。但方案 B 的**有效召回从 50 掉到 30，且排名头部被过滤掉**——黄金集上命中率从 89% 掉到 62%。
>
> **所以「ACL 过滤放在检索前还是检索后」是质量决策，不是安全决策。** 很多团队把它当安全问题处理，于是选了检索后过滤（因为实现简单），**悄悄损失了 27pp 的召回命中率，然后跑去调 top-k 和换模型——治错了地方**。

**输出**：仅本事业部数据，答案带权限范围说明；审计记录「召回了哪些块、过滤掉了哪些块」。

#### 24.5.4 变体 C：知识过期与版本冲突

**问题**：「年假政策现在是怎么规定的？」

**库里的三份材料**：

| 文档 | 版本 | 生效时间 | 状态 |
|---|---|---|---|
| 《员工手册》年假条款 | v5.0 | 2023-06-01 | **已废止** |
| 《员工手册》年假条款 | v6.0 | 2025-01-01 | **生效中** |
| 《2026 年假补充通知》 | — | 2026-06-01 | **生效中** |

**处理**：

1. **检索时按状态过滤**：只召回生效中版本 → v5.0 被挡在召回层。
2. **冲突检测**：v6.0 与 2026 补充通知在「病假天数」上有出入。
3. **裁决规则**：以 `effective_from` 更晚且状态为生效中的为准 → 补充通知优先。
4. **答案显式说明冲突**：「按 2026-06-01 生效的《2026 年假补充通知》，病假天数为 X；2025-01-01 版《员工手册》v6.0 中为 Y，以新通知为准。」

> **第 4 步比「选一个对的」更重要**：**把冲突摊开给用户，比悄悄选一个更可信**。用户能自己判断「公司到底按哪个执行」，而一个被悄悄裁决过的答案，用户只能选择信或不信。

**量化这个风险**：不做版本过滤时，这道题有 **43% 的概率召回 v5.0**（向量检索对「年假政策」的语义相似度，两个版本几乎一样）——**用户拿到的可能是已废止一年的规定**。

#### 24.5.5 变体 D：召回宽度与重排的取舍

**场景**：团队反馈「召回不准，命中只有 78%」，提议**把注入条数从 top-10 加到 top-50**。

**先查表**（§24.3.10）：

| 方案 | 证据命中率 | 准确率 | 幻觉率 | 上下文 |
|---|---|---|---|---|
| 现状 top-10 | 86% | 85% | 5% | 4,000 |
| **提议 top-50** | **97%** | **82%** | **18%** | **20,000** |

**诊断**：命中率确实涨了 11pp，但**准确率掉了 3pp、幻觉率涨了 13pp、上下文涨了 5 倍**。**加宽 k 没有解决任何问题，它只是把噪音也一起加了进来。**

**正确的三步诊断顺序**：

```
召回命中率低
  → ① 先查重排：召回 top-50 里本来有 97% 的证据，
              重排后 top-10 只剩 86% → **重排在丢证据**
  → ② 再查召回路数：只用向量？加 BM25 后 top-10 命中率 71% → 82%，
                  **成本几乎为零，收益比加宽 k 大得多**
  → ③ 最后才考虑加宽 k，且必须窄注入
```

**本案例的实际修复**：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 定位到重排在丢证据 | 重排后 top-10 命中率 86% vs 召回 97% |
| 2 | 换重排模型（bge-reranker-v2-m3），范围 top-50 → **top-30** | 重排后 top-10 命中率 **92%** |
| 3 | 加 BM25 召回路 | top-10 命中率再加 3pp |
| 4 | **召回范围从 50 收到 30** | **准确率 85% → 88%，幻觉率 5% → 3%，重排算力还省了 40%** |

> **第 4 步是本案例最反直觉的地方**：**召回范围收窄了，质量反而提升。**
>
> 原因就是「召回宽、注入窄」这六个字的意思：**宽是为了不漏，但漏掉的证据本该由重排捡回来**。当重排变强之后，召回范围可以往回收——**因为证据还有第二道机会**。
>
> **反过来说：如果重排没做对，加宽召回就是在给模型喂噪音。** 「召回不够」这个判断，几乎总是应该先怀疑重排，而不是先怀疑召回。

#### 24.5.6 故障与兜底

降级矩阵以 §24.4.7 为准，本例补充三条：

| 故障 | 影响 | 兜底 |
|---|---|---|
| **重排服务不可用** | 注入变成宽召回 | **退回向量分数排序并打标 `degraded`**；**此时应同步收紧注入条数**（噪音更多，注入更少） |
| **Verifier 超时** | 答案未校验 | **不输出未校验答案，只给引用块** |
| **知识库整体不可用** | 无任何依据 | **明确拒答 + 指向人工渠道**，不提供任何无依据内容 |

> **第一条的「同步收紧注入条数」值得单独强调**：降级到没有重排时，注入的每一块都可能是噪音，**这时候还按原来的 k 注入，等于降级成了一个「更宽更噪」的版本**。**降级不只是换模型，注入参数也要一起降级。**

#### 24.5.7 扩容 10 倍，哪里先坏？

以 §24.3.18 的基准扩容 10 倍（日问答 2,000 万、峰值 1,160 QPS、LLM 调用 1,390 QPS、重排 58,000 对 / 秒、日 token 1,364 亿、日成本 ¥359,200、问答日志 160 GB / 天）：

| 顺序 | 先坏的点 | 现象 | 触发指标 | 对策 |
|---|---|---|---|---|
| 1 | **重排算力** | 重排 P95 超 300ms、开始降级 | 重排对数 > 目标 QPS 的 80% | **GPU 扩容、缩小重排范围、批量优化、向量分桶** |
| 2 | **向量 / BM25 检索** | P99 上升 | 峰值 > 580 QPS | 分片、Query 缓存 |
| 3 | **LLM 配额** | 429 | 调用 QPS > 配额 80% | 模型分级、单跳小模型、热门直答 |
| 4 | **注入预算与成本** | 账单超支 | 单问 token > 预算 120% | 收紧注入、Query 缓存、结果复用 |
| 5 | **问答日志存储** | 增长过快 | 磁盘水位 > 70% | 分层、采样、只留引用不留全文 |
| 6 | **权限服务** | 变慢、版本落后 | 权限版本落后次数 > 0 | 增量更新 ACL、fail-closed 会自然减少查询 |
| 7 | **知识更新时效** | 新知识生效延迟 | 索引滞后 > 30min | 增量索引、热点优先刷新 |

> **第 1 位是本章最容易被漏掉的卡点**：**重排算力不像 LLM 那样容易横向扩**（GPU 供给有限、单模型显存吃紧），而且它**不在任何 LLM 配额里**，所以不会出现在成本评审的表上——**它会在第一个扩容窗口里炸掉**。
>
> **第 7 位是本章特有的非线性**：流量涨 10 倍时，如果知识库规模不变，更新频率也不变；但**如果知识库规模同步涨 10 倍，重算与重建的量也涨 10 倍**——**索引重建的耗时会成为新知识的生效延迟**，而新知识生效越慢，「过期知识被反复复用」的放大倍数越大。

#### 24.5.8 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| **宽召回 + 窄注入** | 需要重排算力 | **质量与成本双赢** | 重排算力充足时可放宽 |
| 多路召回 | 检索复杂度 | 命中率 +11pp | 术语问题变少后可减路数 |
| **ACL 进索引** | **权限变更要增量更新** | **召回不被吃掉 27pp** | —— |
| 可行性前置判断 | 多一次判断 | 幻觉源头被掐 | —— |
| 引用完整率 100% | 生成受限、token 增 | 信任基础 | **永不放松** |
| 重排范围可配 | 需评测支撑 | 成本与延迟可调 | 算力富余时放宽 |
| 历史问答对 | 需人工确认机制 | 零成本高命中 | —— |
| **偏向严格的拒答** | 误拒率 8% | **信任不崩** | 业务容忍度高时可放宽 |
| **冲突摊开而非悄悄裁决** | 答案更长 | 用户可自行判断 | 内部低风险场景可简化 |

### 24.6 闭环演进与常见误区

#### 24.6.1 演进路线

| 阶段 | 形态 | 触发条件 | 关键改造 |
|---|---|---|---|
| L0 | FAQ + 关键词检索 | 起步 | 倒排、精确匹配 |
| L1 | 语义检索 + 单轮生成 | 泛化需求 | embedding、切分、top-k |
| **L2** | **混合检索 + 重排** | **命中与幻觉问题** | **BM25、cross-encoder、窄注入** |
| **L3** | **引用与拒答** | **信任问题** | **结构化输出、引用校验、拒答策略** |
| **L4** | **权限与知识治理** | **规模与合规** | **ACL 进索引、版本、时效、审计** |
| L5 | 多跳与主动服务 | 成熟 | 实体链接、问题分解、一致性校验、订阅推送 |

> **L2 与 L3 是本章最关键的两级跳跃，而且顺序不能颠倒**。很多系统跳过 L2 直接上 L3——**加了引用机制，但没有重排**——结果就是**引用齐全、引用准确率却很低**：每一句都有引用，但引用的是一堆不相关的块。**引用机制会放大召回质量的问题，而不是掩盖它。**

#### 24.6.2 指标体系

| 层级 | 指标 | 用途 |
|---|---|---|
| **质量** | **幻觉率**、**误拒率**、答案准确率、拒答恰当率 | **判断可信度** |
| **引用** | 引用精确率 / 召回率 / 完整率、引用点击率 | **判断可核验性** |
| 检索 | recall@k、各召回路命中率、**过滤前后候选数** | 判断检索链路 |
| 时效 | 命中过期块次数、索引滞后 | 判断知识治理 |
| 权限 | 越权召回数、权限版本落后次数 | 判断安全 |
| 体验 | 首 token P95、追问率、**答案质疑率** | 判断可用性 |
| 成本 | 单问 token、**注入 token 占比**、单问成本 | 判断可持续 |

#### 24.6.3 评测与回归

- **黄金集三个分区**：可答题 / **不可答题** / **越权题**，缺一不可。
- 标注以**引用精确率**优先（标注成本低、定位准），答案准确率作为结果指标。
- **每周重跑**：换 embedding 模型、改切分、改召回权重、改重排、调整 k 值、改拒答阈值——**六类变更全都要重跑黄金集**，因为它们都直接改变幻觉率与误拒率。
- **变更回归要看两个数**：幻觉率与误拒率**同时**看；**只看准确率会把系统调成「什么都不敢答」**。
- 线上以**答案质疑率**与**引用点击率**做生产环境的幻觉代理；质疑率上升即回滚。
- **重排日志是回归的抓手**：出现一条坏答案，要能回溯到「召回给了什么、重排排成了什么、注入了什么」。

#### 24.6.4 成本优化

| 顺序 | 手段 | 收益 | 说明 |
|---|---|---|---|
| 1 | **重排收敛注入条数** | **输入 token −72%** | **同时提准确率、降幻觉率** |
| 2 | **收窄召回范围**（重排变强后） | 重排算力 −40% | 质量反而提升 |
| 3 | Query 缓存 / 热门问答直答 | 请求 −15% | 无损 |
| 4 | 模型分级（单跳走小模型） | 约 −20% | 简单题不需要大模型 |
| 5 | 引用块去重与裁剪 | 注入 −5% | 收益有限 |

> **第 1 行是本章全部成本优化的 90%**：**「让更少的 token 承载更可靠的证据」**。其余手段都在个位数到十几个百分点，而第 1 行是 **−72%**。

#### 24.6.5 产品对比

| 产品 / 形态 | 核心 | 关键挑战 |
|---|---|---|
| 企业 Wiki + 搜索 | 内容 + 倒排 | 找到文档但不组织答案 |
| 通用 AI 搜索 | 广域检索 + 生成 | 引用弱、内部知识缺失 |
| **垂直领域问答** | **领域切分 + 混合检索 + 重排** | **召回精度与引用质量** |
| 客服知识库 | 面向单一场景 | 覆盖面窄 |
| 对话式客服 | 多轮 + 转人工 | 与本章同构，但重在转人工 |
| 私有化 RAG 平台 | 部署与权限 | **ACL 与数据不出域** |

> **本章与第 22 章（客服 Agent）、第 23 章（问数 Agent）是同构的三兄弟**：客服是「答 + 有副作用 + 转人工」，问数是「答 + 可计算 + 有口径」，**本章是「答 + 有引用 + 会拒答」**。**它们共用检索与上下文治理，但各自的核心防线不同**：客服防重复执行，问数防口径错，本章防幻觉。

#### 24.6.6 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| **召回不够就加宽 k** | **噪音进上下文，幻觉率翻三倍** | **先查重排，再查召回路数，最后才加宽** |
| **只做向量检索** | 型号、编号、专名全漏 | **向量 + BM25** |
| **检索后过滤权限** | 悄悄吃掉 27pp 召回 | **ACL 进索引** |
| **不做重排** | 宽召回来直接注入 = 喂噪音 | **重排是核心环节，不是优化项** |
| **切分粒度 = 注入粒度** | 块被切碎，召回到也答不对 | **检索小块 + 注入合并段** |
| **无引用也输出** | 不可核验 = 不可信 | **引用完整率 100%，P0** |
| **只评答案准确率** | 定位不到是召回还是重排的锅 | **评引用精确率** |
| **黄金集只有可答题** | 拒答能力被训没了 | **必须含不可答题与越权题** |
| **单看拒答率调阈值** | 会得出相反结论 | **幻觉率与误拒率一起看** |
| **置信度用模型自报** | 不可靠 | **重排分 + 分类器头** |
| **引用与事实混在一起写** | 读者分不清哪句是编的 | **结构化输出，分开呈现** |
| **无版本、不过期** | 过期知识被规模化复用 | **版本 + 生效时间 + 状态** |
| **上下文超限就截断证据** | 引用指向不完整 | **降级，不截断** |
| **只返回生成答案** | 模型不可用就完全不可用 | **降级时只给引用块** |
| **多跳不校验合并** | 每步都对、合起来错 | **合并一致性校验** |

#### 24.6.7 高频追问

- **如何减少幻觉？** → 三层：① **重排收敛注入**（最有效，且同时省 72% token）；② **引用精确率校验**（代码层逐句校验）；③ **可行性前置判断**（检索不到就不进生成）。
- **召回和准确率是矛盾的吗？** → 不矛盾，但要**先重排后加宽**：召回宽保证不漏，重排窄保证不噪。**加宽 k 只在重排已经做对之后才安全。**
- **为什么不直接用更大的上下文？** → 更大的上下文只是把更多噪音塞进去，**准确率在 k=20 之后就下降了**；成本还是线性涨。**上下文不是答案质量的免费午餐。**
- **权限过滤放哪一层？** → **检索层**。放检索后会吃掉 27pp 召回命中率，**而且不报错，只是变差**。
- **如何让答案可信？** → 引用完整率 100% + 引用可点开 + 引用逐句校验 + 标注知识截止时点。**可信度不是靠措辞，是靠可核验。**
- **什么时候该拒答？** → 检索后最高重排分低于阈值、越权、或歧义无法消解。**拒答必须有用**：说明库里没有 + 问谁 + 换什么问法。
- **如何平衡幻觉与误拒？** → 按代价不对称定阈值：**幻觉不可逆、误拒可恢复，所以偏向严格**；且两率必须一起看。
- **怎么评估问答 Agent？** → 黄金集含「可答 / 不可答 / 越权」三类；主指标**引用精确率** + 幻觉率 + 误拒率；**recall@k 只是上游指标**。
- **如何控成本？** → **第一刀是注入 token**（占输入 73%），重排收敛是唯一量级级别的手段。
- **多跳怎么做？** → 实体链接 → 分解 → 逐跳检索重排 → **合并一致性校验**；每跳注入预算要比单跳少。
- **知识过期怎么办？** → 入库必填生效时间与 owner、检索只取生效中、答案标截止时点；**冲突要摊开而不是悄悄裁决**。
- **模型不可用怎么办？** → **只返回引用块，不生成答案**——把系统从「编答案」拉回「给证据」。

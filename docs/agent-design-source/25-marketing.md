## 第二十五章 营销 AI Agent 系统

> **本章导读**：营销 Agent 把「自然语言营销目标」转化为可圈选、可生成、可合规风控、可原子频控、可实时校验、可增量归因、可自动调优的生产级增长闭环，难点不在生成文案，而在「高并发下不发错、不超发、不违规、不算错」。本章围绕目标解析与动态分群、千人千面与合规、触达放大与频控阈值、增量归因与降级矩阵展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 25.1 核心定义与定位

**定义**：营销 AI Agent 是面向增长场景的智能体系统。它接收自然语言营销目标（如「对加购未支付用户做 30 分钟召回，预算 5 万，ROI ≥ 3」），完成目标解析、人群圈选、物料生成、合规审核、延迟调度、实时状态复核、原子频控、幂等下发、增量归因与策略调优。

它和客服 Agent 的根本差别在于**方向**：客服是**响应式**的——用户先来，系统再答；营销是**主动式**的——系统先决定打扰谁，再去打扰。**主动式的系统，天生带着放大能力**：客服的一次误判最多害了一个用户，营销的一次误判会复制到百万人的手机里。

**营销闭环七段**：

```
目标解析 → 人群圈选 → 策略与物料 → 合规审核 → 调度触达 → 行为归因 → 策略调优
```

**与其他系统的区别**：

| 系统 | 核心 | 与营销 Agent 的差异 |
|---|---|---|
| 广告投放 | 竞价买量 | 营销 Agent 主要用自有渠道触达 |
| CRM | 客户关系与销售流程 | 营销 Agent 是自动化触达闭环 |
| 营销自动化（MA） | 规则流程编排 | Agent 增加目标解析、生成、MAB |
| 推荐系统 | 站内内容分发 | 营销 Agent 跨渠道主动触达 |
| 客服 Agent | 响应式服务 | 营销 Agent 是主动式增长 |
| **风控 Agent** | **拦截与阻断** | **营销 Agent 是放行与打扰**——**两者的默认动作正好相反** |

> **最后一行值得单独记住**：营销与风控面对同一个决策时，默认动作是相反的。风控的默认值是「拦」，营销的默认值是「发」。**这意味着营销系统的护栏必须是显式的、有预算的、可熔断的，而不是「系统里恰好有这些检查」。**

**三方价值**：

| 角色 | 价值 | 失效后果 |
|---|---|---|
| 用户 | 及时、相关、不过度打扰的权益信息 | 骚扰、退订、投诉 |
| 商家 | 转化、复购、留存提升 | 预算浪费、ROI 为负 |
| 平台 | 增长与商业化 | 生态恶化、合规风险 |

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 目标解析与策略建模 | 商品与权益主数据 |
| 人群圈选（CDP） | 埋点与数据采集 |
| 文案 / 图片生成 | 品牌视觉规范制定 |
| 合规审核与风控 | 法务最终裁定 |
| 调度、频控、下发 | 渠道网关底层 |
| 归因与 MAB 调优 | 财务结算 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 触达 | 触达量、送达率、点击率、决策延迟 P99、**人均日触达次数** |
| 效果 | 转化率、增量转化（Uplift）、净 ROI、客单价 |
| 体验 | 退订率、投诉率、频控命中率、跳过率、**累计退订存量** |
| 合规 | 违规拦截率、文案一致率、审批通过率 |
| 成本 | 单次触达成本、补贴成本、token 成本 |

> **新增的两个指标是本章特有的**：「人均日触达次数」是打扰的即时度量，「累计退订存量」是打扰的**不可逆资产损失**——退订不像点击率那样会自己恢复，**退订过的用户永远不会再被触达**。只看「退订率」会低估一个正在不断累积的漏损。

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 决策 P99 | < 150ms |
| 下发 P99 | < 500ms |
| 状态复核覆盖率 | **100%** |
| 退订 / 黑名单拦截 | **100%** |
| 频控超发 | **0**（硬约束） |
| 预算超发 | **0**（硬约束） |
| 归因回填（T+24h） | 完成率 > 99% |

**本章专属不可逆决策清单**（做错了要停机迁移 + 数据回填 + 全量对账，不是发个版本就能改）：

| 决策 | 为什么不可逆 | 改动代价 |
|---|---|---|
| **幂等键的构造规则**（`campaign_id + user_id + step_id + trigger_bucket`） | 所有下发、频控、状态机、去重表共用它 | 存量幂等记录失效 → **历史重复触达无法自动识别**，需人工对账与用户补偿 |
| **频控的维度与窗口定义**（日 / 周上限口径、冷却期、跨渠道共享配额的范围） | 决定打扰强度与退订率的换算关系 | 阈值改一次 → **全部历史活动的实际打扰量无法重算**，退订归因全部作废 |
| **人群快照的版本与标签口径模型**（CDP 标签定义、快照粒度与有效期） | 决定「同一活动内口径可复现」这个承诺能否兑现 | 存量快照无法重放 → 历史活动的圈选结果不可审计 |
| **触达事件的主键与 Envelope**（`trace_id` / `decision_id`） | 归因、样本回流、实验分流、离线校准全建立在它上面 | 历史事件无法补齐 `decision_id` → **全部历史归因不可复现**，模型无法回溯校准 |
| **归因窗口与 Holdout 分流规则**（窗口长度、抽样比例、随机种子） | 决定增量 ROI 是否可复现 | 换种子或窗口 → **同一活动前后两套 Uplift**，历史实验结论不可比 |
| **权益 / 补贴的结构化契约**（权益 ID、面额、有效期、库存、适用人群） | 决定文案与实际发放是否强一致 | 存量权益失效 → 历史文案需重新审核，且已发券无法回溯核销 |
| **渠道适配契约**（各渠道的能力声明、限流、回执语义、重试规则） | 决定下发顺序、降级链与「失败是否回补」 | 换渠道语义 → 全部下发逻辑重写 + 历史投递状态需重新映射 |

> **对照第一章 §1.4.4**：这七项属单向门，决策时要多评审、做原型、留迁移方案。其余（模型选择、批大小、生成并发、频控阈值数值、Holdout 比例）是双向门，可以快速试错——但 **频控阈值与 Holdout 比例属于「可逆但很贵」**：调它们会改变全部历史活动的打扰强度与增量口径，必须伴随归因回归。

### 25.2 核心解读与关键矛盾

**本质**：营销 Agent 的核心矛盾，是「尽可能多触达以提升 GMV」与「不能打扰、不能违规、不能资损」之间的冲突。设计原则一句话：**模型负责「更优」，规则负责「不出事」**。

**六条章级原则**（贯穿全章，冲突时以这六条为准）：

1. **模型负责「更优」，规则负责「不出事」**——模型只能决定「哪个变体更好」「什么时候更值得发」，**不能决定「能不能发」**。所有合规、权限、频控、预算判定必须落在确定性代码层。
2. **顺序铁律：状态复核 → 决策 → 频控扣减 → 下发**——**绝不先扣后查**。先扣频控再查状态，会给已付款的用户扣掉额度并发出一条催单。
3. **宁可少发，不可发错**——一次错误触达的代价是单次价值的**上百倍**（§25.3.11）。少发只是少一次机会，发错是永久损失一个用户。
4. **触达量必须与错误率一起写进方案**——每次决策的放大倍数要显式算出来。**「一次决策触达 564 万人」和「一次决策触达 564 人」是两个完全不同风险等级的系统**，而它们在目标描述里长得一模一样。
5. **快信号止损，慢信号调优**——退订与投诉 5 分钟能发现，转化与 ROI 24 小时才能发现。**慢信号永远来不及止损，只能用来调权重。**
6. **每一次降级都要打标**——`degraded` + `fallback_mode` + `reason_code` 三件套缺一不可。**不打标的降级会让效果被算成策略效果，模型会因此学到错误的因果。**

**三个不等式**：

```
一次决策的触达量   >>  一次决策的纠错能力     → 错误必须在发出前拦住，不能靠事后修
快信号检测窗(5min) <<  慢信号检测窗(24h)     → 止损只能靠快信号与前置护栏
打扰强度            >>  退订率的线性预期      → 频控阈值必须按退订曲线的拐点定
```

**四大挑战**：

1. **高并发下的状态一致性与防过期触达**：用户可能已经下单、退订或标的失效，消息却仍在队列里。
2. **多维频控的原子性**：日 / 周上限、活动冷却、静默时段、退订黑名单往往同时生效，不能并发超发。
3. **千人千面多模态物料的合规性**：文案、图片、权益必须真实一致，且不能触碰违禁词与品牌底线。
4. **短期点击 / 探索 vs 长期净转化与 ROI 的平衡**：高点击可能带来高退订，自然转化又容易把功劳误记给营销。

**三个放大器**（本章最贵的量都藏在这里）：

| 放大器 | 说明 | 后果 | 量化 |
|---|---|---|---|
| **触达放大（人群 × 并发 × 时间）** | 一次决策复制成百万次触达 | 打扰、退订、投诉、品牌受损 | 1 次决策 → 564 万次触达；幂等失效时单用户再放大 50–100 倍；慢信号止损比快信号晚 288 倍（§25.3.10） |
| **资损放大** | 一张券错发到全量 | 直接资金损失 | 直接发券 10 万人 = **¥100 万**沉没成本；延迟发券 = ¥3 万，**差 33 倍**（§25.3.21） |
| **合规放大** | 一句违禁词进入全量文案 | 监管处罚、下架 | 564 万次触达 × 0.15% 投诉率 = **8,460 次投诉**（§25.3.11） |

> **本章与第 02、05、22、23 章的放大器方向不同**：Feed 是读放大，广告是三层放大，客服是上下文放大，问数是结果集放大。**营销章的放大器是触达放大**——它是唯一一个「错误会主动跑到用户手机里」的架构。**别的系统错了是一行脏数据，营销错了是几百万人今天被打扰。**

**四类正确性**（必须分开保证）：

| 层次 | 要求 | 保障手段 | 典型漏法 |
|---|---|---|---|
| **状态正确** | 不催已付款、不发失效标的 | 下发前实时复核 | 队列里的消息发出时状态已变 |
| **频控正确** | 不超发、不重复发 | Lua 原子 + 幂等键 | check-then-act 竞态 |
| **合规正确** | 文案与权益一致、无违禁词 | 双层审核 + 结构化权益 | 模型编造权益 |
| **归因正确** | 剔除自然转化水分 | Holdout + 净 ROI | 无对照组 |

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 触达量 vs 打扰 | 多发 GMV 高但退订高 | 频控 + 护栏指标 | 低打扰场景可放宽 |
| 短期点击 vs 长期 ROI | 大额券拉 CVR 却亏毛利 | 净 ROI + 慢信号 | 拉新期可容忍 |
| 千人千面 vs 合规 | 个性化易越界 | 模板 + 双层审核 | 品牌强管控统一 |
| 实时 vs 状态准确 | 实时快但状态旧 | 下发前复核 | 非时效场景可异步 |
| 自动化 vs 审批 | 全自动快但风险 | 分级审批 | 低预算可全自动 |
| 频控严 vs 机会 | 严则少触达 | 分渠道 / 分场景阈值 | 高价值用户可放宽 |
| 探索 vs 利用 | 一直探索亏 | MAB + 最小探索比例 | 明确假设时用固定 A/B |
| 归因窗口 vs 时效 | 等 7 天太久 | 快慢信号分离 | 短周期活动可缩短 |

**八类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| 催单 | 已支付仍收到提醒 | 状态过期 | 下发前复核 |
| 重复发 | 同用户多次收到 | 重试 / 并发 | 幂等键 + 版本 |
| 超发 | 超频控 / 超预算 | check-then-act | Lua 原子 + 预算锁 |
| 违规 | 违禁词 / 虚假宣传 | 生成不可控 | 双层审核 + 模板 |
| 资损 | 超发券 / 补贴 | 预算无强约束 | 预算中心 Fail-Closed |
| 误归因 | 自然转化算作营销 | 无对照组 | Holdout |
| 打扰 | 静默时段发送 | 时区 / 顺延错误 | 静默时段 + `schedule_seq` |
| 素材错配 | 文案与权益不符 | 模型编造 | 结构化权益服务 |

**快慢双层智能**：

| 层 | 职责 | 典型实现 | 延迟 |
|---|---|---|---|
| 决策模型层（System One） | 高频、封闭选项、低延迟门控：渠道选择、打扰敏感度、是否值得立即触达 | 轻量模型 / 规则 / 特征服务 | 50–150ms |
| 生成与规划层（System Two / Agent） | 人群标签组合、千人千面文案与多模态物料、异动归因、策略提案 | LLM、工具调用、规划与反思 | 秒级（**离线，不在实时链路**） |
| 确定性规则与状态层 | 退订 / 黑名单一票否决、Redis 原子频控、实时业务状态校验、任务幂等 | Lua、状态机、幂等表、版本号 | < 10ms |

> **生成层必须离线**。这是本章最容易被忽略的一条架构约束：千人千面文案的生成是秒级的，而决策链路的预算只有 150ms。**把生成放进实时链路，等于用 150ms 的预算去跑 3 秒的任务。** 生成必须提前批量做好、按「人群包 × 变体」缓存，下发时只做查表 + 渲染。

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| 薅羊毛 | 批量账号领券 | 风控、限购、设备指纹 |
| 刷量 | 伪造点击 / 曝光 | 归因去重、反作弊 |
| Prompt 注入 | 商品标题 / 评论含指令 | 清洗隔离、数据包裹 |
| PII 泄露 | 画像 / 标签外泄 | 脱敏、最小化、权限 |
| 内部越权 | 超预算 / 超范围投放 | 审批、预算锁、审计 |
| **误触达（内部无意）** | **条件写反，圈中全量敏感人群** | **规模上下界预检 + 样本预览 + 分级审批** |

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| **补贴 / 权益** | **最大** | 精准圈选、增量归因、预算控制、**延迟发券** |
| 渠道费用 | 次之 | 渠道选择、频控 |
| LLM 生成 | 中（可忽略） | 模板缓存、批量生成 |
| 计算 / 存储 | 小 | 分层、TTL |

> **补贴是最大的成本项，而它有一个被忽略的杠杆：发券时机**。直接发券的成本 = 触达量 × 面额，与转化率完全无关；延迟发券的成本 = 触达量 × 转化率 × 面额。**10 万人的活动，两者相差 33 倍**（§25.3.21）。**同样的钱，先优化「发给谁」的收益通常远大于优化「什么时候发」。**

### 25.3 理论与方法论

#### 25.3.1 S0：七项前置锚点

先落定七件事，它们共同决定**可行域**——不在可行域内的方案不参与讨论。

| # | 锚点 | 本章答案 | 影响 |
|---|---|---|---|
| 1 | **业务目标与成功标准** | 净 ROI ≥ 3、退订率 ≤ 0.1%、投诉率 ≤ 0.05%、频控超发 0 | 决定自动化分级与熔断阈值 |
| 2 | **规模量级** | 日触达 5000 万、峰值 2894 QPS、活动 1 万 / 天、单活动 10 万–1000 万人、**人群池 1 亿** | 决定频控集群、渠道容量、预算与成本模型 |
| 3 | **质量属性优先级** | 不打扰 > 不资损 > 不违规 > 增量 ROI > 触达量 | 决定降级顺序与熔断优先级 |
| 4 | **硬约束** | 广告法与平台合规红线；退订与黑名单 100% 拦截；频控超发 0；预算不超发；静默时段与冷却期不得违反；PII 最小化 | 定义可行域；合规与资金要求不可用增长折抵 |
| 5 | **不可逆决策清单** | 见 §25.1 的本章七项 | 决策流程：多评审 + 原型 + 迁移方案 |
| 6 | **核心路径与事实源** | 核心路径 = 目标 → 圈选 → 生成 → 审核 → 调度 → 决策 → 状态复核 → 频控 → 下发 → 归因；事实源 = **活动配置 + 人群快照 + 触达事件 + 预算账本** | 决定缓存与对账对象；频控计数与结果缓存全是投影 |
| 7 | **竞争与协作边界** | 渠道网关、短信 / 推送服务商、支付与权益库存在外部；触达、频控、归因、实验、审核自建 | 决定服务边界与团队成本 |

> **第 2 项为什么改变答案**：营销系统的规模参数不只是 QPS，还有**人群池大小**。同样日触达 5000 万，人群池 1 亿时人均日触达 0.5 次，人群池 500 万时人均 10 次——**后者必然退订率爆表**。**「人群池」是营销章独有的关键参数，它决定触达量与打扰强度之间的换算关系。**

#### 25.3.2 4S 收敛顺序

```
S0 定题（锚点 + 不可逆清单）
   → Scenario 定触达量、活动数、人群池、单活动规模、渠道、合规要求
      → Service 定解析、圈选、生成、审核、调度、决策、频控、下发、归因的边界
         → Storage 定人群快照、触达事件、频控计数、预算账本的唯一事实源
            → Scale 定分层决策、原子频控、异步调度、离线生成、降级熔断
```

#### 25.3.3 Scenario：场景与规模

| 维度 | 数值 | 推导与来源 |
|---|---|---|
| 日触达量 | 5000 万条 | — |
| 平均下发 QPS | 5000 万 ÷ 86400 | ≈ **579** |
| **峰值下发 QPS** | 579 × 5 | **2,894**（峰值系数 5：晚 8 点与 10 点两个高峰承载当日 35%，叠加 12 点大促脉冲） |
| 活动数 | 1 万个 / 天 | 决定目标解析与审批的并发形态 |
| **人群池** | **1 亿可触达用户** | **决定打扰强度：人均日触达 = 触达量 / 人群池** |
| 单活动人群 | 10 万 – 1000 万 | 决定审批级别与分批放量策略 |
| **人均日触达次数** | 5000 万 ÷ 1 亿 | **0.5 次 / 人 / 日**（基线；**这是打扰强度的直接读数**） |
| 决策延迟 | 50–150ms | 决定快慢分层与降级链 |
| 渠道 | Push 60%、短信 25%、站内信 10%、IM 5% | 渠道占比决定成本与频控共享口径 |
| 生成模式 | 离线批量，按「人群包 × 变体」缓存 | **生成不在实时链路** |
| 合规 | 广告法、退订、静默时段、PII | — |
| 归因 | 快信号 T+0（5 min 内）、慢信号 T+24h / T+7d | 决定止损窗口 |

> **「人均日触达次数」是本章独有的关键参数**。传统系统的容量参数是 QPS，营销系统还必须给出**人群池**，否则「日触达 5000 万」这个数字完全无法解读：它可以是「每天打扰全公司一次」，也可以是「每天打扰百分之一的用户十次」。**同样的 QPS，用户的感受天差地别。**

#### 25.3.5 Storage：数据模型

| 数据 | 存储 | 关键设计 | 是事实源吗 |
|---|---|---|---|
| 人群快照 | 对象存储 / 位图 | `campaign_id + snapshot_version` | **是** |
| 活动配置 | MySQL | 目标、预算、护栏、状态、版本 | **是** |
| 触达任务 | MySQL / Redis | `campaign_id + user_id + step_id` | 否（可重建） |
| 延迟调度 | 延迟队列 / 时间轮 | `schedule_seq` | 否（可重建） |
| 频控计数 | Redis | `freq:{user_id}:{scope}:{window}` | 否（可重建，但**必须能重放**） |
| 幂等表 | Redis / MySQL | `idempotency_key` 唯一 | **是**（去重的依据） |
| 触达事件 | Kafka / 数仓 | 统一 Envelope | **是** |
| 归因宽表 | 数仓 | `trace_id` 对齐 | **是** |
| 预算账本 | 预算中心 | 原子扣减、Fail-Closed、对账 | **是** |
| 生成结果缓存 | Redis / 对象存储 | 按「人群包 × 变体」 | 否（可重建） |

> **频控计数是不是事实源，是一个需要想清楚的问题**。它可以重放（从触达事件重算），但**重放的结果与线上的原子计数可能不一致**（并发顺序、失败回补）。因此它虽然可以重建，**却必须保留原始的扣减日志**，否则事后无法解释「为什么这个人收到了 5 条」。**投影可以丢，投影的日志不能丢。**

**任务模型**：

```
Campaign（活动）
  └→ Strategy（策略）
       └→ Step（触达步骤）
            └→ Delivery Task（单用户单次下发）
```

#### 25.3.7 目标解析与策略建模

**目标结构化字段**：

| 字段 | 示例 |
|---|---|
| 目标 | 召回、复购、拉新、唤醒 |
| 人群 | 加购未支付、近 30 天未活跃 |
| 预算 | 5 万元 |
| 周期 | 30 分钟延迟、持续 7 天 |
| 渠道 | Push 优先，短信兜底 |
| 约束 | ROI ≥ 3，退订率 ≤ 0.1% |
| 护栏 | 日上限 2，静默时段不发 |

**目标解析要求**：

- 输出结构化 JSON，缺字段时追问。
- 预算、周期、护栏必须显式确认。
- 解析结果进入审批，不能直接执行。
- **必须解析出「触达量」与「预算」的比值**——这是唯一能提前判断「这个活动会不会打扰过头」的量。

> **最后一条是本章新增的硬要求**。一个「预算 5 万、覆盖 1000 万人」的目标，人均补贴只有 0.5 元——**这个活动要么根本发不出有意义的权益，要么必然大面积打扰却换不来转化**。**目标解析阶段就要把「人均预算 / 人均补贴面额」算出来并显示给审批人**，因为它是「这个活动值不值得做」的第一道判断。

#### 25.3.8 用户洞察与动态分群（CDP）

**五类标签**：

| 类别 | 示例 |
|---|---|
| 生命周期 | 新客、首购、复购、流失预警、赢回 |
| 时间 | 最近活跃、最近购买、加购未支付时长 |
| 偏好 | 品类偏好、价格带、渠道偏好 |
| 价值 | 客单价区间、历史 GMV、毛利贡献 |
| 约束 | 免打扰、退订、黑名单、静默时段 |

**执行前预检**：

- 输出预估人群规模与样本特征（地域、活跃、品类分布）。
- 防止条件写反导致「误圈全量」或「圈出 0 人」；设置规模上下界告警。
- 高预算、全量触达、敏感人群进入 `WAITING_APPROVAL` 挂起审批。
- 固定人群快照版本，保证同一活动内口径可复现、可审计。

**规模预检的量化阈值**（参考）：

| 预检项 | 阈值参考 | 触发动作 |
|---|---|---|
| 预估规模 > 目标人群池 20% | 相当于人均日触达 ≥ 1 次 | 强制审批 + 分批放量 |
| 预估规模 > 人群池 60% | 相当于人均日触达 ≥ 3 次 | **强制收紧频控 + 分级审批** |
| 预估规模 = 0 | 条件写错 | 阻断，不允许发起 |
| 预估规模 > 历史同活动 P99 × 3 | 条件可能写宽了 | 阻断，要求二次确认 |

> **规模预检的本质是「在发出之前把触达量翻译成打扰强度」**。业务方看到的是「圈了 600 万人」，而用户感受到的是「我今天收到了 5 条推送」。**这两个数字之间必须有一个自动换算，否则规模预检形同虚设。**

**排除与去重**：

- 近期已购、已退订、已投诉、其他活动冷却期内用户应被抑制。
- 多活动并行时按优先级分配同一用户配额。

#### 25.3.9 千人千面物料生成与合规

**上下文收敛与脱敏**：只向生成模型输入标签化、脱敏后的偏好与画像，避免暴露敏感隐私，也避免把细碎行为生硬拼进文案。

**双层合规网关**：

| 层 | 检查内容 | 失败处理 |
|---|---|---|
| 硬规则与一致性校验 | 绝对化用语、违规承诺、违禁词；文案与实际权益 / 价格 / 有效期是否一致 | 直接拦截或改写 |
| 语义 / 多模态审核 | 图文合规、品牌调性、歧视与误导风险 | 重生成或降级模板 |

**兜底**：生成超时或审核未通过时，降级到预审通过的安全模板，保证任务不卡死；若连模板或权益校验都失败，则跳过。

**补充**：

- 商品标题、用户评论等外部文本可能含 Prompt 注入，进入上下文前要清洗与隔离。
- 权益、价格、有效期必须来自结构化权益服务，不能让模型编造。
- 按「模板 × 人群包 × 权益」缓存生成结果，控制 token 成本与延迟。
- 渠道有长度、图片尺寸、敏感词差异，渲染前按渠道能力裁剪。

**生成粒度的成本与收益**：

| 粒度 | 单活动生成次数 | 单活动生成成本 | 个性化收益 |
|---|---|---|---|
| 1 套文案（不分群） | 3 次 | ≈ ¥0.02 | 无 |
| 20 个人群包 | 60 次 | ≈ ¥0.38 | 品类级个性化 |
| 100 个人群包 | 300 次 | ≈ ¥1.92 | 品类 × 价格带级 |
| 每人一份 | 10 万次 | ≈ ¥640 | 近乎随机，**且违反「同一人群收到不同文案」的公平性** |

> **生成成本几乎可以忽略**——单活动最多 ¥2，相比补贴成本是四位数对两位数。所以**人群包粒度不该由成本决定，而该由「收益拐点」决定**：同一品类偏好的人群，再细分下去文案差异很小、转化提升很快趋近于零。**但更重要的是第 4 行：每人一份的写法不仅是浪费，它还破坏了实验的可解释性**——同一活动的用户看到完全不同的文案，你无法归因「是文案好还是人群选得好」。**粒度的上限是「人能理解的分组数」，不是「用户数」。**

#### 25.3.10 触达放大的三段放大

**本节是触达放大的权威版**，§25.3.11、§25.5.2、§25.5.7 只引用。

**营销系统与其它系统最根本的差别**：一次决策会复制成百万次触达。别的系统错了是一行脏数据，营销错了是几百万人今天被打扰。**因此本章的第一性问题不是「怎么做得更准」，而是「一次决策最多能放大到多少」。**

**第一段：人群放大（决策 → 触达）**

```
一次决策 → 触达 N 人
N = 圈选人数 × 决策通过率 × 渠道成功率 × 送达率
```

以大促全量 Push 为例（目标 1000 万人，人群池 1 亿）：

| 环节 | 系数 | 剩余 |
|---|---|---|
| 圈选人数 | — | 10,000,000 |
| 决策通过率（值得立即触达） | 60% | 6,000,000 |
| 渠道成功率 | 99% | 5,940,000 |
| 送达率 | 95% | **5,640,000** |

> **放大倍率 = 564 万倍**。一次自然语言目标、一个人群圈选、一条策略，复制成 564 万次打扰。**这个数字必须出现在方案里**，因为它是后续所有风险（合规、退订、资损）的公共乘数。

**第二段：并发放大（幂等 / 频控不原子）**

| 做法 | 并发窗口 | 单 key 并发 | 结果 |
|---|---|---|---|
| GET 读限额 → 判断 → INCR 写计数 | 读返回到写入生效 ≈ **1ms** | 热点 key 上 50–100 | **单用户收到 50–100 条，而不是 1 条** |
| Lua 原子脚本 | 0（单次脚本内完成） | 不限 | 单用户恒为 1 条 |

量化：1000 万次下发中，若 0.5% 落在已触达用户上 → 5 万条重复触达；**重复触达是退订的第一诱因**，退订率因此额外 +0.03%。

> **并发放大的本质是「读—判断—写」这三步之间存在一个时间缝隙**。这个缝隙在低并发时看不出来（单用户并发为 1），在大促首分钟才暴露。**幂等键 + Lua 原子是唯一的解**——加机器、加超时都无效。

**第三段：时间放大（检测延迟）**

| 信号 | 典型检测窗 | 峰值 2,894 QPS 下可抑制的触达量 |
|---|---|---|
| **快信号**（退订、投诉、点击异常） | **5 min** | 2,894 × 300 ≈ **87 万条** |
| **慢信号**（转化、净 ROI） | **24 h** | 2,894 × 86,400 ≈ **2.5 亿条** |
| **倍差** | — | **288 倍** |

> **这条是本章最重要的结论**：**慢信号永远来不及止损。** 转化和 ROI 要 24 小时后才算得出来，而在这一天里，一个坏策略可以触达 2.5 亿次。**止损只能靠三样东西**：前置护栏（规模预检、审批、合规审核）、幂等与原子频控、快信号熔断。**指望「事后归因发现不对再改」是营销系统最贵的错误。**

**三段放大合起来**：

| 段 | 放大 | 防线 | 防得住吗 |
|---|---|---|---|
| 人群放大 | 564 万倍 | 规模预检 + 分级审批 + 频控 | ✅ 可控（但必须在发出前） |
| 并发放大 | 单用户 50–100 倍 | 幂等键 + Lua 原子 | ✅ 完全可控 |
| 时间放大 | 止损差 288 倍 | 快信号熔断 + 前置护栏 | ⚠️ **只能部分控制** |

> **前两段是可以彻底解决的，第三段不能**。所以真正的架构问题不是「怎么发现错」，而是「**怎么让它错得少、错得早**」——这是本章所有护栏的出发点。

#### 25.3.11 打扰成本与频控阈值

**本节是打扰成本核算的权威版**，§25.3.21、§25.5.5 只引用。

**单次触达的总成本**：

| 项 | 量级 | 说明 |
|---|---|---|
| 渠道成本 | Push ¥0.005 / 短信 ¥0.03 | 可忽略 |
| 补贴成本 | 券面额 × 发放率 | 可占 90% |
| **打扰成本** | **退订 LTV 损失 + 投诉处理 + 信任消耗** | **当期看不见，事后最大** |

**退订的 LTV 损失量化**（这是最容易被漏算的一项）：

```
人均月毛利贡献 ¥30 × 期望活跃 24 个月 = 单用户生命周期毛利 ≈ ¥720
一次退订 = 永久失去该用户的全部未来触达价值 ≈ −¥720（不是 0，是负的）
```

以 564 万次触达、退订率从 0.02% 升到 0.15% 为例：

| 项 | 计算 | 结果 |
|---|---|---|
| 增量退订人数 | 564 万 × 0.13% | **7,332 人** |
| **LTV 损失** | 7,332 × ¥720 | **≈ ¥528 万** |
| 投诉次数 | 564 万 × 0.15% | **8,460 次** |
| 对比：活动补贴预算 | — | ¥50 万 |
| **LTV 损失 / 活动预算** | 528 / 50 | **10.6 倍** |

> **这是本章最重要的一组对比**：一次触达放大造成的用户资产损失，是整个活动补贴预算的十倍。**补贴花的是「这一单的钱」，打扰花的是「这个用户剩下的所有钱」。** 而后者在当期报表上完全看不见——它只表现为「下个月的转化率莫名其妙降了」。

**打扰强度与退订率是超线性关系**：

| 人均日触达次数 | 退订率（参考曲线） | 说明 |
|---|---|---|
| 0.5 | 0.02% | 基线，良性 |
| 1 | 0.03% | 平稳 |
| **2** | **0.07%** | **拐点附近** |
| **3** | **0.11%** | **超过拐点** |
| 5 | 0.15% | 明显打扰 |

> **「日上限 2」和「日上限 3」在退订率上是 0.07% 与 0.11% 的差别**，而这两个数字通常是被随手拍出来的。**频控阈值必须按曲线定，不能拍脑袋定。** 三步：① 量出自己的「退订率 — 人均日触达」曲线（按渠道、按人群分层）；② 找拐点；③ 阈值设在拐点之前，并对高价值人群单独放宽。

**人群池固定时，触达量就是打扰强度**：

```
人均日触达次数 = 日触达量 ÷ 人群池
```

| 规模 | 日触达 | 人群池 | 人均日触达 | 退订率（曲线） |
|---|---|---|---|---|
| 基线 | 5000 万 | 1 亿 | 0.5 次 | 0.02% |
| **扩容 10 倍** | **5 亿** | **1 亿** | **5 次** | **0.15%（涨 7.5 倍）** |

> **扩容 10 倍，在用户手机上表现为「每天 0.5 条」变成「每天 5 条」。** 人群池不会因为流量涨而变大——**它是存量用户的集合**。所以**营销系统的扩容不是纯技术问题**：QPS 翻 10 倍很容易，但「打扰强度翻 10 倍」会直接引爆退订。**频控阈值必须先收紧，再谈扩容。**

**净价值模型**（用来定「最优触达量」）：

```
净增量价值 = 触达人数 × (增量转化率 × 客单毛利 − 人均补贴) − 触达人数 × 单位打扰成本
最优点在：边际增量价值 = 边际打扰成本
```

> **单位打扰成本随打扰强度上升而上升**（超线性），所以最优触达量是一个**内点解**，而不是「能触达多少就触达多少」。**没有这个模型，触达量的决策只能靠拍脑袋。**

#### 25.3.12 事件驱动触达与频控

**触发方式**：实时行为事件（加购未支付、浏览未下单、会员到期）或定时任务；支持延迟触发与多步推进。

**下发前二次校验**：真正发送前重新检查实时业务状态——是否已支付、是否已退订、标的是否失效、是否处于免打扰时段。状态已变则取消或顺延。

**任务幂等**：`campaign_id + user_id + step_id + trigger_ts_bucket` 等幂等键，防止重试、乱序、跨节点重复下发。

**分布式频控**（Redis Lua 原子）：

- 日 / 周触达上限；
- 活动冷却期；
- 静默时段；
- 退订 / 黑名单强拦截；
- 同用户多策略的配额抢占。

Lua 一次完成「检查 + 计数 + 记录原因」，避免 check-then-act 竞态。

**关键顺序**：

```
状态复核 → 决策 → 频控扣减 → 下发
```

| 顺序颠倒的后果 | 具体表现 |
|---|---|
| 先扣频控再查状态 | 已付款用户被扣掉额度，并收到一条催单 |
| 先下发再扣频控 | 超发，且无法回补 |
| 先决策再复核状态 | 决策基于已过期的状态，方向就错了 |

> **顺序铁律的四步里，「状态复核」在最前、「频控扣减」在第三。** 理由是：**状态复核是只读的、免费的、无副作用的；频控扣减是有副作用的、不可撤销的。** **永远把无副作用的检查放在有副作用的动作之前**——这是本章最容易被违反、也最容易修的一条。

**决策模型超时兜底**：短超时（50–150ms），超时降级到确定性规则（默认低打扰渠道或 SKIP），但仍必须通过硬频控与退订校验。

#### 25.3.13 延迟 / 顺延任务的状态复核与并发防重入

延迟触发（加购 30 分钟后）与静默顺延（22:00–08:00 顺延到次日 08:30）最容易出现状态过期、重复消费与并发抢占。

**三重防重**：

1. **任务级幂等键**：`campaign_id:user_id:step_id:biz_id`，多轮触发加入 `trigger_bucket`。
2. **到达时刻二次状态复核**：入队状态只代表过去，执行前重新拉取订单、退订、库存 / 券状态。
3. **用户 + 活动级短锁 + 原子频控**：短 TTL 锁串行化关键门控检查，再由 Lua 原子扣减配额。

**顺延版本控制**：重新计算唤醒时间时更新 `schedule_seq`；只有当前调度单的 `schedule_seq` 与消息携带值一致才允许执行，防止旧延迟消息在顺延后误触发。

**状态机原子跃迁**：

```
SCHEDULED → EVALUATING → DISPATCHED / CANCELLED
```

使用条件更新或版本号，确保同一任务不会被两个 Worker 同时推进。

**常见竞态**：

- 先扣频控还是先查状态？→ 先查状态，再扣频控。
- 频控已扣但渠道报错？→ 记录 `delivery_failed`，按规则回补额度并告警。
- 锁超时？→ 合理 TTL + 幂等键兜底，避免死锁与重复发送。

#### 25.3.14 幂等设计

| 层 | 方案 | 幂等键 / 约束 |
|---|---|---|
| 任务 | 任务级幂等 | `campaign_id + user_id + step_id + trigger_ts_bucket` |
| 下发 | 渠道去重 | `idempotency_key` + 渠道侧去重 |
| 频控 | 原子计数 + 记录 | Lua 脚本 + 计数版本 |
| 状态 | 条件更新 | `WHERE status = ?` |
| 顺延 | 版本校验 | `schedule_seq` 一致才执行 |
| 归因 | 主键对齐 | `trace_id` 唯一 |
| 预算 | 原子扣减 + 账本 | `budget_ledger` 唯一键 |

> **七层幂等不是冗余，是职责分离**：任务层防「重发任务」，下发层防「渠道重投」，频控层防「超发」，状态层防「并发推进」，顺延层防「旧消息误触发」，归因层防「重复计功」，预算层防「超发资金」。**任何一层单独存在都不够**——最常见的漏洞是「任务幂等做了，但渠道重投没做」。

#### 25.3.15 自动化 A/B、MAB 与增量归因

**固定 A/B** 适合验证明确假设；**Multi-Armed Bandit** 适合在探索与利用之间动态分配流量：

- ε-greedy：以 ε 概率探索，其余选择当前最优。
- UCB：按均值 + 不确定性给冷门臂探索机会。
- Thompson Sampling：从各变体后验分布采样，选择采样收益最高者。

**快慢双信号**：

```
快信号检测窗 = 5 min  → 峰值 2,894 QPS 下可抑制 87 万条
慢信号检测窗 = 24 h   → 峰值 2,894 QPS 下可抑制 2.5 亿条
倍差 288 倍 → 慢信号永远来不及止损，止损只能靠快信号 + 前置护栏
```

| 信号 | 内容 | 延迟 | 用途 |
|---|---|---|---|
| **快信号** | 曝光、点击、退订、投诉 | T+0（5 min 内） | **熔断高退订 / 高投诉变体——止损** |
| **慢信号** | 归因窗口内的真实转化、客单价、补贴成本、净贡献、ROI | T+24h / T+7d | 修正权重与最终评估——**调优，不是止损** |

**Holdout 增量归因**：保留空白对照组，计算真实增量提升（Uplift），剔除自然转化水分：

```
Uplift = Conversion(TREATMENT) − Conversion(HOLDOUT)
Net Value_i = Attributed GMV_i × Margin Rate − Subsidy Cost_i − Channel Cost_i
```

**Thompson Sampling 细节**：

- 二元转化用 Beta-Bernoulli 后验，成功 / 失败计数可加先验与时间衰减。
- 连续收益（客单价、净 ROI 差异大）用正态 / 伽马等后验或分桶近似，避免「大额券拉高 CVR 却亏毛利」。
- 保留最小探索比例（Floor Exploration）与 Holdout，防止早期噪音锁死变体。
- 大促、季节、生命周期变化时使用滑动窗口 / 折扣因子，避免旧赢家长期霸占流量。

**护栏优先**：退订率、投诉率触达上限直接熔断（`mkt.strategy.circuit_broken`），不参与常规放量。

> **护栏指标与收益指标不在同一个量纲上，必须硬隔离**。一个变体可以「点击率最高」但「退订率也最高」。如果退订与 ROI 一起参与加权，模型会去探索「高点击高退订」的变体——**那是在优化打扰，不是在优化生意**。

#### 25.3.16 降级矩阵（Fail-Open / Fail-Closed）

**本节是降级的权威版**，§25.4.7、§25.5.6 只引用。

不能一刀切全拦截，也不能在资金 / 合规 / 防打扰场景盲目放行。**判据只有一条：依赖失效时，失效的后果是「少赚一点」还是「伤到用户」？**

| 依赖 / 门控环节 | 典型故障 | 推荐策略 | 降级动作 |
|---|---|---|---|
| 退订与全局黑名单 | 状态服务超时 | **Fail-Closed** | 状态不明直接跳过，记 `SYS_STATE_SERVICE_TIMEOUT` |
| 召回标的实时状态 | 订单 / 加购服务超时 | 视场景 | 强时效召回（防催单）Fail-Closed；仅辅助标签且有快照可设短容忍窗口 |
| Redis 分布式频控 | 节点抖动 / 超时 | **Fail-Closed** | 拦截并告警，或切本地粗粒度限流兜底 |
| 预算 / 权益额度 | 预算中心超时或余额不足 | **Fail-Closed** | 拦截发券 / 补贴，防超发资损 |
| 决策模型（时机 / 渠道） | 超时 / 降级 | 降级兜底 | 切确定性规则（默认低打扰渠道或 SKIP），仍过硬频控与退订 |
| 千人千面物料生成 | 生成失败 / 超时 | 降级兜底 | 切预审安全模板；模板也失败则 Fail-Closed |
| 渠道网关 | 限流 / 故障 | 降级兜底 | 换备用渠道；全不可用则记录失败并回补额度 |

**治理要点**：

- 每次降级打标 `degraded=true`、`fallback_mode` 与 `reason_code`，避免把降级效果误算成策略效果。
- 高频抖动依赖配置熔断器，触发后快速失败（`SYS_CIRCUIT_BREAKER_OPEN`），避免线程堆积。
- 降级比例、原因码分布进入监控与告警。

> **「语义层 / 权限不可用就停」在本章对应的是「退订状态不可用就停」「预算不可用就停」**。这两条与问数章的 fail-closed 是同一个原则：**宁可少触达，不可打扰一个不该被打扰的人；宁可少发券，不可超发资金。**

#### 25.3.17 事件规范、原因码与可观测

**统一事件 Envelope**：

```
event_id, event_name, event_time, ingest_time, trace_id,
idempotency_key, campaign_id, strategy_id, variant_id,
experiment_group, user_id, biz_context, decision_meta,
reason_code, ext
```

**核心事件分层**：

| 阶段 | 事件示例 |
|---|---|
| 圈群与调度 | `mkt.audience.matched`、`mkt.holdout.assigned`、`mkt.schedule.delayed` |
| 决策与物料 | `mkt.decision.evaluated`、`mkt.content.generated`、`mkt.gate.skipped` |
| 触达执行 | `mkt.delivery.dispatched`、`mkt.delivery.delivered`、`mkt.delivery.failed` |
| 反馈与归因 | `mkt.user.exposed`、`mkt.user.clicked`、`mkt.user.unsubscribed`、`mkt.user.complained`、`mkt.attribution.converted`、`mkt.strategy.circuit_broken` |

**原因码规范**：`[领域]_[类别]_[具体原因]`。

| 前缀 | 典型原因码 | 排查方向 |
|---|---|---|
| `CANCEL_*` | `CANCEL_ALREADY_CONVERTED`、`CANCEL_TARGET_INVALID`、`CANCEL_LIFECYCLE_CHANGED`、`CANCEL_WINDOW_EXPIRED` | 延迟窗口过长、标的有效期短、触发滞后 |
| `FREQ_*` | `FREQ_USER_DAILY_CAP`、`FREQ_USER_WEEKLY_CAP`、`FREQ_CAMPAIGN_COOLDOWN`、`FREQ_QUIET_HOURS_DROPPED`、`FREQ_CONFLICT_HIGHER_PRIO` | 打扰强度、冷却期、多策略抢占配额 |
| `COMP_*` | `COMP_GLOBAL_OPT_OUT`、`COMP_CHANNEL_UNSUBSCRIBED`、`COMP_USER_BLOCKLIST`、`COMP_CONTENT_COMPLIANCE_FAIL` | 退订 / 黑名单底线，或合规规则与模板 |
| `DEC_* / CNT_*` | `DEC_MODEL_SKIP`、`DEC_LOW_CONFIDENCE`、`CNT_GENERATION_FAILED`、`CNT_BUDGET_EXHAUSTED` | 模型阈值 / 特征、生成兜底、预算策略 |
| `SYS_*` | `SYS_STATE_SERVICE_TIMEOUT`、`SYS_DECISION_TIMEOUT`、`SYS_LOCK_CONTENTION`、`SYS_CIRCUIT_BREAKER_OPEN` | 下游状态接口、决策模型、锁与熔断器 |

**可观测指标**：触达量、送达率、决策延迟 P99、跳过率、频控命中率、取消原因分布、退订 / 投诉率、增量转化、净 ROI、降级比例、单次触达成本、**人均日触达次数**、**累计退订存量**。

> **原因码是营销系统最被低估的可观测资产**。它把「退订率上升」这个笼统的现象拆成可定位的原因：`CANCEL_ALREADY_CONVERTED` 上升说明延迟窗口太长，`FREQ_USER_DAILY_CAP` 上升说明触达量超了人群承受力，`COMP_CONTENT_COMPLIANCE_FAIL` 上升说明文案模板出了问题。**没有原因码，退订率上升永远只能靠猜。**

#### 25.3.18 样本回流与离线校准

在线决策、门控拦截、触达反馈与延迟归因必须按统一主键对齐沉淀。

**对齐主键**：`decision_id / trace_id`，关联 `campaign_id`、`strategy_id`、`variant_id`、`user_id`、`experiment_group`、`event_time`。

**回填机制**：曝光 / 点击 / 退订为快信号，可较快拼接；转化、净成交、补贴成本为慢信号，通常在归因窗口结束后（T+24h / T+7d）批流一体回填，避免把「尚未到期的转化」误标为负样本。

**核心宽表字段**：

| 分组 | 关键字段 | 用途 |
|---|---|---|
| 标识与实验 | `trace_id`、`user_id`、`campaign_id`、`strategy_id`、`variant_id`、`experiment_group` | 区分 TREATMENT / HOLDOUT，支撑增量归因 |
| 决策输入快照 | `trigger_type`、`lifecycle_stage`、`recent_active_hours`、`is_quiet_hours`、`user_feature_ver` | 还原决策上下文，防特征穿越与口径漂移 |
| 模型输出 | `model_name`、`model_version`、`choice_dist`、`selected_choice`、`score_val`、`confidence`、`is_fallback` | 评估校准度、阈值合理性与降级占比 |
| 门控与执行 | `final_action`（SENT / SKIPPED / DELAYED / FAILED）、`stage`、`reason_code`、`channel`、`delivery_status` | 区分模型主动跳过、频控拦截与真正触达 |
| 反馈与归因 | `is_exposed`、`is_clicked`、`is_unsubscribed`、`is_converted`、`order_gmv`、`subsidy_cost`、`net_margin` | 快信号熔断，慢信号做 ROI 调优与训练 |

**典型用法**：

- **模型校准**：对比预测分数与真实转化 / 退订，校准概率并调整 SKIP 与置信度阈值。
- **反事实与漏放分析**：结合 Holdout 与被 `DEC_MODEL_SKIP` / `FREQ_*` 拦截的样本，分析高价值机会流失与过度打扰边界。
- **策略库沉淀**：高转化、低退订、高净贡献的变体沉淀为模板 / 先验；高频合规失败与高退订表达进入负样本与规则库。

**补充**：只对「已触达用户」建模会产生选择偏差，需保留随机探索与 Holdout；标签成熟度要按归因窗口打标，训练时排除未到期样本。

> **这里有一个容易被忽略的选择偏差**：模型只在「已触达用户」身上学到「什么该发」，但真正的目标函数是「什么该发**且**不打扰」。被 `FREQ_*` 拦下的人没有标签，于是**频控抑制掉的高价值人群永远学不到**。**Holdout 不只是用来算增量，它还是模型能看见「被抑制者」的唯一样本来源。**

#### 25.3.19 渠道契约与容量预估

**渠道能力声明**（每个渠道必须显式声明，不能靠约定俗成）：

| 能力 | 声明项 |
|---|---|
| 限流 | 最大 QPS、单渠道并发上限、单租户配额 |
| 内容 | 标题长度、正文长度、图片尺寸、模板 ID、富文本能力 |
| 回执 | 送达 / 打开 / 点击 / 失败 的语义与到达延迟 |
| 重试 | 可重试错误码、重试次数、退避策略 |
| 幂等 | 渠道侧是否支持去重键、支持的去重窗口 |
| 费用 | 单条费用与计费口径（按发送还是按送达） |
| 合规 | 渠道侧签名规则、渠道自有敏感词、黑名单 |

**容量预估**（下发前必做）：

```
预计下发量 = 圈选人数 × 决策通过率 × 渠道占比
若 预计下发量 / 渠道限流 > 1 → 分批放量或降级到备用渠道
```

| 场景 | 处置 |
|---|---|
| 预计量 > 渠道限流 × 10s | **必须分批**，并把放量节奏与静默时段一起规划 |
| 预计量 > 渠道限流 | 降级到备用渠道或延长窗口 |
| 单渠道不可用 | 切换备用渠道，**但不重复计数、不重复计费** |

> **「渠道切换」是营销系统特有的失败模式**：切换意味着同一个用户可能被两个渠道各触达一次，而频控口径必须跨渠道共享。**如果不共享配额，渠道切换就成了绕过频控的后门。**

#### 25.3.20 容量与成本估算

**本节是容量口径的权威版**，§25.5 与 §25.6 只引用。

**假设**：日触达 5000 万条，峰值系数 5，活动 1 万个 / 天，人群池 1 亿；每条触达产生 5 个事件；在线链路上「决策 + 状态复核 + 频控 + 下发」各 1 次调用；生成离线进行。

**一、在线链路**

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均下发 QPS | 5000 万 ÷ 86400 | ≈ 579 |
| **峰值下发 QPS** | 579 × 5 | **2,894** |
| 峰值决策 QPS | 与下发同量级 | 2,894 |
| 峰值状态复核 QPS | 1 × 下发 | 2,894 |
| 峰值频控 Redis QPS | Lua 1 次 + 失败回补 0.5 次 | ≈ 4,341 |
| 峰值渠道网关 QPS | 1 × 下发 | 2,894 |
| **峰值下游总 QPS** | — | **≈ 1.3 万** |

**二、决策链路的延迟可行性**（这才是真正的硬约束）

```
决策模型 80ms + 状态复核 40ms + 频控 Lua 10ms + 序列化与网络 20ms = 150ms ✓
```

> **150ms 的预算意味着频控与状态复核只能分到 50ms。** 这不是「性能优化项」，而是**架构约束**：状态复核要批量化（一次拉多个字段）、频控要一次脚本覆盖全部维度、决策模型必须能降级。**任何一段超过预算，方案就只剩「扩容」或「降级」两条路。**

**三、离线生成**

| 指标 | 计算 | 结果 |
|---|---|---|
| 需生成的日活动数 | 1 万 × 10% | 1,000 |
| 单活动生成次数 | 人群包 50 × 变体 3 | 150 |
| 日生成次数 | 1,000 × 150 | 15 万 |
| 单次 token | 输入 2,000 + 输出 300 | 2,300 |
| **日生成 token** | 15 万 × 2,300 | **3.45 亿** |
| **日生成成本** | 300×¥2 + 45×¥8 | **≈ ¥960**（约 ¥2.9 万 / 月） |

> **生成成本几乎可以忽略**（¥960 / 天），因为人群包粒度把「千人千面」压到了 150 次 / 活动。**若改成「每人一份」**：5000 万次 × 2,300 token = **115 亿 token / 天 ≈ ¥3.2 万 / 天（约 96 万元 / 月）**——**不可接受**。**这正是人群包粒度必须受限的原因**（§25.3.9）。

**四、事件与存储**

| 指标 | 计算 | 结果 |
|---|---|---|
| 事件量 / 天 | 5000 万 × 5 | **2.5 亿** |
| 事件峰值 QPS | 2.5 亿 ÷ 86400 × 5 | ≈ **1.4 万** |
| 事件存储 / 天 | 2.5 亿 × 500B | ≈ **125 GB** |
| 归因宽表 / 天 | 5000 万 × 1KB | ≈ **50 GB** |
| 人群位图 / 快照 | 1 亿 bit | ≈ **12.5 MB** |
| **频控 key 空间** | 1 亿用户 × 3 scope | **≈ 3 亿 key（约 30 GB）** |

> **频控的 key 空间比它的 QPS 更值得担心**：3 亿个 key 常驻 Redis 是很重的资产。**必须给每个 scope 设计独立的 TTL**（用户日窗口 2 天、用户周窗口 8 天、活动冷却按活动周期），否则 key 空间只增不减。**而且要注意：触达量涨 10 倍时，key 空间不涨（人群池固定），但 TTL 内的写入量涨 10 倍**——这是本章少见的「扩容不涨成本」的地方。

**五、结论**

1. **在线链路 1.3 万 QPS，真正要精算的是决策链路的 150ms**——频控与状态复核只能分到 50ms。
2. **生成成本可忽略（¥960 / 天），触达成本才可怕**——生成不是成本问题，补贴与打扰才是（§25.3.11、§25.3.21）。
3. **频控 key 空间（3 亿）比 QPS 更需要治理**——靠 TTL 分层，不靠扩容。
4. **事件链路（1.4 万 QPS、125 GB / 天）是最大存储消耗**——必须分层与 TTL。
5. **必须先量人群池**——它决定打扰强度，进而决定退订率与全部合规风险。

#### 25.3.21 成本模型

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| **补贴 / 权益** | **最大** | 精准圈选、增量归因、预算控制、**延迟发券** |
| 渠道费用 | 次之 | 渠道选择、频控、跨渠道配额共享 |
| LLM 生成 | 可忽略 | 人群包粒度约束 + 模板缓存 |
| 计算 / 存储 | 小 | 分层、TTL |
| **打扰成本（LTV 损失）** | **当期不显现，长期最大** | 频控曲线、静默时段、退订前置拦截 |

**补贴成本的两种形态**（本章最实用的一条成本知识）：

| 形态 | 成本公式 | 10 万人群 × ¥10 券 | 转化率假设 | 风险 |
|---|---|---|---|---|
| **直接发券**（下单即得） | 触达量 × 面额 | **¥100 万** | 与转化率**无关** | **纯沉没成本，无论转化多少** |
| **延迟发券**（转化后发） | 触达量 × 转化率 × 面额 | **¥3 万** | 3% | 转化率略降（需回访） |

> **两者相差 33 倍，而转化率的损失通常只有 10–20%。** 这个对比说明一件事：**营销成本优化的第一杠杆是「发给谁」和「什么时候发」，而不是「生成得更好看」。** 千人千面、文案质量这些大家最爱讨论的事，成本加起来只有补贴的千分之一。

**成本优化手段与收益量级**：

| 手段 | 说明 | 本章收益量级 |
|---|---|---|
| **精准圈选** | 减少无效触达 | **直接减少补贴成本（最大）** |
| **延迟发券** | 转化后才发 | 补贴成本降 90%+ |
| **增量归因** | 砍掉负 ROI 策略 | **防止长期亏损**（当期看不见） |
| 频控 | 降低退订与渠道成本 | **保护长期 LTV** |
| 渠道选择 | 优先低成本高转化渠道 | 渠道费降约 60% |
| 模型分级 | 决策用小模型 | 决策成本降约 70% |
| 模板缓存 | 降低生成成本 | 生成成本本就可忽略 |

> **注意最后三行的量级远小于前两行**。这说明一个反直觉的事实：**在营销系统里，生成与模型的优化天花板很低，而「圈谁」「什么时候发」「发不发」这三件事的优化空间是数量级的。** 很多团队把精力花在第一条上。

### 25.4 工程落地与规则护栏

#### 25.4.1 端到端链路

```
自然语言目标
  → Goal Parser（结构化 + 追问 + 人均预算提示）
  → Audience Service（CDP + 规模预检 + 快照）
  → Content Service（离线批量生成，按人群包缓存）
  → Compliance Service（硬规则 + 语义审核）
  → Scheduler（延迟 / 事件触发 + schedule_seq）
  → Decision Service（渠道 / 时机 / 打扰，50–150ms）
  → State Service（实时业务状态复核，Fail-Closed）
  → Frequency Service（Redis Lua 原子频控）
  → Delivery Service（幂等下发 + 失败回补）
  → Attribution Service（快慢信号 + Holdout）
  → Experiment Service（MAB / 护栏熔断）
  → 样本回流与离线校准
```

> **图里最重要的一行是「规模预检」与「State Service」**：前者把「圈了 600 万人」翻译成「人均打扰 6 次 / 日」让审批人看见，后者保证发出的每一条都不是过期状态。**这两行决定了错误是在发出前被拦住，还是在 24 小时后被归因发现。**

#### 25.4.2 目标解析护栏

- 输出结构化 JSON，字段缺失必须追问。
- 预算、周期、护栏必须显式确认。
- **必须计算并展示「人均预算 / 人均补贴面额」与「预估人均日触达次数」。**
- 高风险目标（全量、高预算、敏感人群）强制审批。
- 解析结果可回放、可审计。

#### 25.4.3 圈选护栏

| 护栏 | 说明 |
|---|---|
| 规模上下界 | 防误圈全量 / 0 人（阈值见 §25.3.8） |
| **打扰强度换算** | **规模 ÷ 人群池 = 人均日触达，超阈值必须提示** |
| 样本预览 | 地域 / 活跃 / 品类分布 |
| 快照版本 | 口径可复现 |
| 排除规则 | 已购、退订、投诉、冷却 |
| 审批 | 高预算 / 全量 / 敏感人群 |

#### 25.4.4 生成与审核护栏

- 只输入脱敏标签，不输入原始 PII。
- 权益来自结构化服务，模型不得编造。
- 硬规则：违禁词、绝对化用语、价格 / 有效期一致性。
- 语义 / 多模态：品牌调性、歧视、误导。
- 失败降级安全模板；模板失败则跳过。
- 外部文本清洗，防 Prompt 注入。
- **生成必须离线批量，且粒度受「人群包数」约束（§25.3.9）。**

#### 25.4.5 调度与状态复核

- 延迟任务带 `schedule_seq`，顺延时递增。
- 到达时先复核状态，再决定发送 / 取消 / 顺延。
- 状态机条件更新，防并发推进。
- 用户 + 活动级短锁，防重复进入。
- **复核覆盖率必须为 100%，并单独监控（不是抽样）。**

#### 25.4.6 频控与幂等

**顺序**：状态复核 → 决策 → 频控扣减 → 下发。**绝不先扣后查**（理由见 §25.3.12）。

**Lua 频控要点**：

- 一次脚本完成多维度检查（日 / 周 / 冷却 / 静默 / 黑名单）。
- 返回明确原因码。
- 扣减成功后写入幂等键。
- 下发失败按规则回补，并记录 `delivery_failed`。

**频控阈值的三步法**：① 量退订-打扰曲线 → ② 找拐点 → ③ 阈值设在拐点前，并按人群价值分层（§25.3.11）。

#### 25.4.7 降级与熔断

降级矩阵以 §25.3.16 为准，本节只列执行动作：

- 退订 / 黑名单、频控、预算：**Fail-Closed**。
- 物料生成、决策模型：降级到安全模板 / 规则。
- 高频抖动依赖配置熔断器。
- 所有降级打标 `degraded` + `fallback_mode` + `reason_code`。
- **熔断要分两级**：单变体熔断（护栏指标触发）与全局降级（依赖故障触发）。

#### 25.4.8 延迟预算与超时降级

**本表是唯一的延迟口径来源**，其他小节只引用。

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 接入与鉴权 | 30ms | 100ms | 429 / 鉴权失败提示 |
| 目标解析 | 200ms | 800ms | 追问补全；仍失败则转人工 |
| 人群规模预检 | 100ms | 500ms | 拒绝执行，要求重跑 |
| **决策（渠道 / 时机）** | **80ms** | **150ms** | **切确定性规则（默认低打扰渠道或 SKIP）**，仍过硬频控与退订 |
| **实时状态复核** | **40ms** | **120ms** | **Fail-Closed**（强时效场景跳过） |
| **频控扣减（Lua）** | **10ms** | **40ms** | **Fail-Closed** + 本地粗粒度限流 |
| 序列化与网络 | 20ms | — | — |
| **在线链路合计** | **150ms（P99）** | 500ms | — |
| **物料生成（离线，不在实时链路）** | 秒级 | 30s | 切预审安全模板 |
| 下发（渠道网关） | 120ms | 500ms | 记录失败 + 回补额度 |
| 归因回填 | 异步 | T+24h | 分批补齐 |

> **预算与超时是两个数**：预算是正常情况下希望花多少，超时是超过就触发降级的硬限，两者必须满足「超时 ≥ 预算」。**「决策 P99 < 150ms」是用户可感知的承诺，「归因 T+24h」是后台完成时间，两者不是同一个数**——原版把它们混在一张 SLO 表里，没有给出每一步的分解，**导致超时降级无从设计**。

#### 25.4.9 观测与压测

**观测**：

| 类别 | 指标 |
|---|---|
| 决策 | QPS、P99、跳过率、降级比例、**各原因码分布** |
| 触达 | 下发量、送达率、失败率、**人均日触达次数** |
| 频控 | 命中率、各原因码分布、**扣减后回补率** |
| 体验 | 退订率、投诉率、**累计退订存量** |
| 效果 | 增量转化、净 ROI、**Uplift 与 CTR 的背离度** |
| 成本 | 单次触达成本、补贴成本 |
| 状态 | **复核覆盖率、复核失败率** |

> **「Uplift 与 CTR 的背离度」是本章特有的健康指标**：点击率高而 Uplift 低，说明这个变体吸引的是**本来就会买的人**（自然转化被误记为营销功劳），它的真实价值接近零。**这个指标比 CTR 更能反映策略质量**，也正是 Holdout 存在的意义。

**压测**：

- 峰值 5 倍触达。
- **单用户并发触达**（验证幂等与 Lua 原子）。
- 单活动千万级人群（验证规模预检与分批放量）。
- Redis 频控节点故障（验证 Fail-Closed）。
- 状态服务超时（验证不催单）。
- 延迟队列堆积。
- 生成服务超时。
- 预算中心余额不足。
- **人群池固定、触达量放大 10 倍**（验证频控阈值与熔断在超线性打扰下仍有效）。

#### 25.4.10 规则护栏清单

| 领域 | 护栏 | 优先级 |
|---|---|---|
| **退订与黑名单** | 全局 + 分渠道退订一票否决，100% 拦截，状态不明即跳过 | **P0** |
| **频控原子性** | 单次 Lua 完成全部维度；**顺序为「先复核后扣减」** | **P0** |
| **幂等** | 七层幂等键；状态机条件更新；`schedule_seq` 版本校验 | **P0** |
| **预算原子扣减** | 预算中心原子扣减 + 账本对账，Fail-Closed | **P0** |
| **下发前状态复核** | 覆盖率 **100%**（非抽样），强时效场景 Fail-Closed | **P0** |
| **合规双层审核** | 硬规则一票否决 + 语义 / 多模态审核；权益来自结构化服务 | **P0** |
| **静默时段与冷却期** | 强制生效，顺延必须更新 `schedule_seq` | **P0** |
| **规模预检** | 规模上下界 + 人均打扰强度换算 + 样本预览 | **P0** |
| **降级打标** | `degraded` + `fallback_mode` + `reason_code` 三件套 | **P0** |
| **审计** | 目标、圈选快照、审批、下发、归因全量留痕、不可篡改 | **P0** |
| **快信号熔断** | 退订 / 投诉超护栏阈值即熔断变体，不参与放量 | P1 |
| **Holdout 分流** | 固定比例 + 固定随机种子，可复现 | P1 |
| **样本回流对齐** | `trace_id` 主键、快慢信号分层回填、排除未到期样本 | P1 |
| **跨渠道配额共享** | 渠道切换不得绕过频控 | P1 |
| **模型校准** | 预测分数与真实退订 / 转化对比校准，定期重定阈值 | P1 |
| **渠道容量预估** | 下发前按渠道限流预估，超限分批或降级 | P1 |
| **MAB 最小探索比例** | 保底探索 + Holdout 防早期噪音锁死 | P2 |
| 成本 | 单次触达成本与补贴成本看板 | P2 |

> **营销 Agent 的十个 P0 里有六个是「发出去之前」的检查**（复核、频控、幂等、预检、合规、静默）。**这不是过度设计，而是因为发出去就收不回来**——用户可以关掉推送、可以退订、可以投诉，但**系统不能撤销一次打扰**。

#### 25.4.11 上线检查（10 问）

1. 目标解析是否结构化并可确认？**是否计算并展示了人均补贴与预估人均日触达次数？**
2. 圈选是否有规模上下界、样本预览与**打扰强度换算**？高风险规模是否强制审批？
3. 人群快照是否版本化？**快照标签口径变更后历史活动是否仍可复现？**
4. 文案与权益是否强一致校验？权益是否只来自结构化服务、模型无法编造？
5. **下发前状态复核覆盖率是否 100%**？复核失败时是否 Fail-Closed？
6. 频控是否 Lua 原子？**顺序是否为「复核 → 决策 → 扣减 → 下发」？** 阈值是否按退订-打扰曲线的拐点定的？
7. 幂等键是否覆盖重试、乱序、并发与顺延？扣减后下发失败是否回补并告警？
8. 降级是否按 Fail-Open / Fail-Closed 分级？**是否每次降级都打了 `degraded` + `reason_code`？**
9. 事件与原因码是否统一？Holdout 与归因是否可复现？**是否排除了未到期样本？**
10. **快信号熔断是否已演练？** 人群池固定、触达量放大 10 倍时，退订率是否会失控？

### 25.5 典型案例与端到端解决

#### 25.5.1 案例：加购未支付 30 分钟召回

**目标**：对加购未支付用户做 30 分钟召回，预算 5 万，要求增量 ROI ≥ 3，退订率 ≤ 0.1%。

**先算触达放大**（这是本章的习惯：先算放大倍数，再设计链路）：

| 环节 | 系数 | 剩余 |
|---|---|---|
| 圈选人数 | — | 120,000 |
| 决策通过率（30 分钟后仍值得召回） | 85% | 102,000 |
| 渠道成功率 | 99% | 100,980 |
| 送达率 | 95% | **95,931** |

**放大倍率 ≈ 9.6 万倍**；但对照人群池 1 亿，**这个活动贡献的人均日触达只有 0.001 次**——**这是一个低放大、低打扰的良性活动**，可以放心跑自动化。

**链路**：

1. **目标解析**：解析出「人群 = 近 24h 加购未支付；预算 ¥50,000；延迟 30 分钟；ROI ≥ 3；护栏 = 日上限 2、72h 冷却」。**计算并展示人均补贴 = ¥50,000 / 120,000 ≈ ¥0.42 / 人**——低于常规券面额，因此**只能发小额券或权益，不能发满减**。这个提示直接决定了后续的权益设计。
2. **圈选**：近 24h 加购、未支付、未退订、非黑名单、近 7 天未购买；预估 12 万人，抽样 10% 作为 Holdout。**规模预检通过**（12 万 ÷ 1 亿，远低于阈值）。
3. **生成**：按品类与价格带切 20 个人群包 × 3 套文案，权益为小额券；**离线批量生成 60 次**（成本约 ¥0.4）。硬规则校验「限时」「最高」等措辞与券有效期一致。
4. **触发**：消费 `add_to_cart_unpaid`，延迟 30 分钟；到达后决策模型输出渠道 Push、置信度 0.82。
5. **复核**：8% 用户已支付 → `CANCEL_ALREADY_CONVERTED`；部分处于静默时段 → 顺延并更新 `schedule_seq`。
6. **频控**：日上限 2、活动冷却 72h；超限记 `FREQ_USER_DAILY_CAP`，**不扣减、不发送**。
7. **下发**：渲染通过后带幂等键发送；渠道失败记 `delivery_failed` 并按规则回补额度。
8. **归因**：点击与退订实时回流；T+24h 回填支付转化与补贴成本，对比 Holdout 计算 Uplift 与净 ROI。
9. **调优**：变体 B 退订率超护栏被熔断；变体 A/C 由 Thompson Sampling 动态倾斜流量，保留 10% 探索。

**结果示例**：增量转化 +1.8pp，净 ROI 4.2，退订率 0.03%；确认「先状态复核、再频控、后下发」的顺序避免了催单投诉。

> **这个案例最有价值的地方是第 1 步**：人均补贴 ¥0.42 在目标解析阶段就把「发什么权益」定了。**如果等生成阶段才发券，很可能发了一张 ¥10 的券给 12 万人 —— 那是 ¥120 万的沉没成本，而预算是 ¥5 万。**

#### 25.5.2 变体 A：大促全量 Push

**特点**：人群大、预算高、时效强。

**先算触达放大**：

| 环节 | 系数 | 剩余 |
|---|---|---|
| 圈选人数 | — | 10,000,000 |
| 决策通过率 | 60% | 6,000,000 |
| 渠道成功率 | 99% | 5,940,000 |
| 送达率 | 95% | **5,640,000** |

**放大倍率 564 万倍**。这个活动单独贡献**人均日触达 0.1 次**，是大促日基线 0.5 次的 **20%**——**一个活动就贡献了五分之一的日常打扰**。

**额外护栏**：

- 全量人群必须审批，且**分批放量**（按小时拆 4–6 批）。
- **频控阈值临时收紧**（日上限从 2 降到 1），避免与常规活动叠加。
- 渠道容量预估，防止 Push 网关过载。
- 实时监控退订 / 投诉，超阈值自动熔断。
- **预算按批释放**，避免第一批就把额度用光。

> **「大促全量」最危险的地方不是技术，是它把「日上限 2」这个约束在事实上架空了**：全量推送让 564 万人各收到 1 条，而这一天还有其它活动在跑。**频控阈值不随活动规模收紧，就等于没有频控。**

#### 25.5.3 变体 B：会员到期续费

**特点**：标的时效强，错发代价高。

**额外护栏**：

- 下发前核验会员状态与到期时间。
- 已续费用户必须取消（`CANCEL_ALREADY_CONVERTED`）。
- 权益与价格以结构化服务为准。
- 归因窗口对齐续费周期。
- **到期前 30 / 7 / 1 天三步递进提醒，三步共享同一活动配额**（否则「递进提醒」变成三次打扰）。

#### 25.5.4 变体 C：多渠道协同

**特点**：Push、短信、站内信、IM 组合。

**额外护栏**：

- 统一频控口径，跨渠道共享配额。
- 渠道优先级与降级链。
- 同一用户同一活动只触达一次。
- 渠道失败自动切换，但**不重复计数、不重复计费、不重复占用配额**。

> **「渠道切换不重复占用配额」是本章特有的一个坑**：Push 失败降级到短信，如果短信侧再扣一次频控配额，用户实际收到 1 条却扣了 2 次额度，**系统会误判「打扰强度高」而提前收紧频控**，久而久之营销量自己就上不去了。

#### 25.5.5 变体 D：频控阈值与打扰曲线

**场景**：大促期人群池 1 亿，日触达从 3 亿（人均 3 次）被业务要求压回 2 亿（人均 2 次）。要不要做？

**数据（按 §25.3.11 的退订曲线）**：

| 指标 | 人均 3 次 / 日 | 人均 2 次 / 日 | 差异 |
|---|---|---|---|
| 日触达量 | 3 亿 | 2 亿 | −1 亿人次 |
| 退订率 | 0.11% | 0.07% | −0.04pct |
| **日新增退订** | 33 万人 | 14 万人 | **−19 万人** |
| **日 LTV 损失** | ¥2,376 万 | ¥1,008 万 | **−¥1,368 万** |
| 投诉 | 3 亿 × 0.05% = 15 万次 | 10 万次 | −5 万次 |

**代价（少触达 1 亿人次）**：

```
少触达 1 亿 × 增量转化率 0.3pp = 少 3 万单 × 毛利 ¥50 = ¥150 万（一次性、当期可补）
```

**结论**：

| | 收益 | 代价 | 性质 |
|---|---|---|---|
| 收紧频控 | **¥1,368 万 / 天** | ¥150 万（一次性） | **收益是代价的 9 倍，且收益是永久的** |

> **这就是频控阈值的正确算法**：**边际 LTV 损失 vs 边际转化收益，比值 > 1 就该收紧。** 而不是「日上限 2 还是 3 拍脑袋定」。**注意两者的性质差异**：收紧阈值省下的 LTV 是**永久的**（少退订 19 万人，这 19 万人今后两年还会继续买），而少掉的 3 万单转化是**一次性的**。**用永久收益去换一次性损失，永远划算。**

**定阈值的三步**：

| 步骤 | 动作 | 产出 |
|---|---|---|
| 1 | 量「退订率 — 人均日触达」曲线（按渠道、按人群价值分层） | 一张曲线，不是拍脑袋 |
| 2 | 找拐点（例中在 2–3 次 / 日之间） | 一个可解释的阈值区间 |
| 3 | 阈值设在拐点前，并对高价值人群单独放宽 | 分层的频控策略 |

#### 25.5.6 故障与兜底

降级矩阵以 §25.3.16 为准，本例补充三条：

| 故障 | 影响 | 兜底 |
|---|---|---|
| **渠道切换后重复计费** | 预算与频控双错 | 渠道去重键 + 配额只扣一次 |
| **频控扣减成功但下发失败** | 额度被吞 | 按规则回补 + 记录 `delivery_failed` + 告警；**回补失败需人工兜底** |
| **生成缓存未命中且生成超时** | 大促时大面积缺物料 | 预审安全模板兜底；模板也失败则**跳过该人群包**，不得临时降级为无差别文案 |

#### 25.5.7 扩容 10 倍，哪里先坏？

以 §25.3.20 的基准放大 10 倍（日 5 亿触达、峰值 28,940 QPS、Redis 43,410 QPS、事件峰值 14 万 QPS、事件存储 1.25 TB / 天），**人群池仍是 1 亿**：

| 顺序 | 先坏的点 | 现象 | 触发指标 | 对策 |
|---|---|---|---|---|
| 1 | **频控 Redis（热点 key）** | 延迟 P99 上升、单用户超发 | 单分片 QPS > 10 万、热点 key 集中度 > 5% | 分片 + 用户哈希打散 + 预扣 + 本地粗粒度限流 |
| 2 | **渠道网关** | 限流、失败率上升 | 下发失败率 > 1% | 分渠道分流、错峰、降级备用渠道 |
| 3 | **打扰（非线性，扩容本身造成）** | **退订率上升、投诉上升** | **人均日触达 > 2 次** | **收紧频控阈值、分批放量、熔断变体** |
| 4 | 决策模型 | P99 上升 | 决策 P99 > 150ms | 模型分级、特征缓存 |
| 5 | 延迟调度 | 堆积、延迟 | 队列积压 > 10 万 | 分片、时间轮、扩容 |
| 6 | 事件链路 | Kafka 积压 | lag > 100 万 | 扩分区、批量、采样 |
| 7 | 归因宽表 | 存储与计算压力 | 单分区 > 1TB | 分层、预聚合 |
| 8 | 预算中心 | 扣减 P99 上升、失败率上升 | 扣减 P99 > 50ms | 预扣 + 批量对账 |

> **第 3 位是本章特有的非线性，也是唯一由「扩容本身」造成的破坏**。触达量涨 10 倍、人群池不变 → 人均日触达从 0.5 次涨到 **5 次**：
>
> - 退订率 0.02% → **0.15%**（涨 7.5 倍）
> - 日新增退订 1 万人 → **75 万人**
> - **日 LTV 损失 ¥720 万 → ¥5.4 亿**
>
> **同时频控的 key 空间完全不变**（人群池固定）——**成本的增长 100% 来自打扰，不来自技术**。
>
> **所以「扩容 10 倍」的容量评审必须加一条：频控阈值同步收紧，否则技术上撑住了、用户却流失了。** 只做乘 10 的评审，会在第一次大促把用户的信任烧光。

#### 25.5.8 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| 快慢双层 | 架构复杂 | 低延迟 + 高质量 | 场景简单可合并 |
| Fail-Closed | 少触达 | 不打扰、不资损 | 依赖稳定性提升 |
| Holdout | 损失部分触达 | 真实增量 + 无偏样本 | 归因体系成熟 |
| MAB | 探索成本 | 动态最优 | 假设明确可用 A/B |
| 模板兜底 | 个性化下降 | 任务不卡死 | 生成稳定性提升 |
| 严格频控 | 触达机会减少 | 退订下降、**LTV 保住** | 用户偏好可学习 |
| **离线生成 + 人群包粒度** | **个性化上限受限** | **生成成本从 ¥3.2 万/天降到 ¥960/天** | 生成成本可忽略时可放宽 |
| **延迟发券** | **转化率略降** | **补贴成本降 90%+** | 券后核销链路成熟时可提前发 |
| **规模预检（打扰强度换算）** | **多一次查询** | **在发出前拦下误圈全量** | —— |
| **渠道配额共享** | **切换逻辑复杂** | **防止切换绕过频控** | 单渠道场景可简化 |

### 25.6 闭环演进与常见误区

#### 25.6.1 演进路线

| 阶段 | 形态 | 触发条件 | 关键改造 |
|---|---|---|---|
| L0 | 人工配置活动 | 起步 | 规则 + 模板 |
| L1 | 规则自动化 | 活动量大 | 调度、频控 |
| L2 | 数据驱动圈选 | 精准度需求 | CDP、快照、**规模预检** |
| L3 | 生成 + 合规 | 个性化需求 | 离线生成、双层审核 |
| L4 | MAB + 增量归因 | ROI 压力 | Holdout、Thompson、**快慢信号分层** |
| L5 | 自主策略 | 成熟 | 目标解析、自动调优、**打扰曲线驱动的频控** |

> **L2 是最容易被跳过、也最不能跳过的一层**。很多系统直接从「人工配置」跳到「LLM 生成文案」，结果是一套会写文案但不知道自己在打扰谁的系统。**规模预检、快照版本化、排除规则这三条属于 L2，它们不产生任何智能，却决定了这套系统会不会伤到用户。**

#### 25.6.2 指标体系

| 层级 | 指标 | 用途 |
|---|---|---|
| 触达 | 下发量、送达率、决策 P99、**人均日触达次数** | 判断链路与打扰 |
| 体验 | 退订率、投诉率、频控命中、**累计退订存量** | 判断打扰 |
| 效果 | 转化率、Uplift、净 ROI、**CTR 与 Uplift 的背离度** | 判断真实价值 |
| 合规 | 违规拦截、文案一致率 | 判断风险 |
| 成本 | 单次触达成本、补贴成本 | 判断可持续 |
| 护栏 | **频控超发数、预算超发数、复核覆盖率** | **判断底线是否守住** |

> **护栏指标必须与业务指标分层看板**。业务指标涨了但护栏指标也涨了（超发、复核覆盖率下降），**这不是好消息**——它意味着增长有一部分是拿底线换来的。

#### 25.6.3 实验与调优

- 固定 A/B 验证明确假设。
- MAB 做动态流量分配，保留最小探索比例。
- 护栏指标优先：退订 / 投诉超限直接熔断，**不参与收益加权**。
- 快信号熔断，慢信号定输赢。
- 每次策略变更记录版本与实验分组。
- **阈值类参数（频控、折扣、预算）变更必须带归因回归**——它们改变的不是一次活动，是所有未来活动的打扰强度。

#### 25.6.4 成本优化

**分两条轨道，不排成一条队**：

**轨道一：补贴与触达成本**（占大头）

| 顺序 | 手段 | 收益 | 备注 |
|---|---|---|---|
| 1 | **精准圈选** | **直接减少触达量 → 减少补贴** | 最大杠杆 |
| 2 | **延迟发券** | 补贴成本降 90%+ | 收益与转化率的权衡 |
| 3 | 增量归因 | 砍掉负 ROI 策略 | 防长期亏损 |
| 4 | 渠道选择 | 渠道费降约 60% | |

**轨道二：模型与计算成本**（占小头）

| 顺序 | 手段 | 收益 | 备注 |
|---|---|---|---|
| 1 | 离线生成 + 人群包粒度 | ¥3.2 万/天 → ¥960/天 | 粒度是主因 |
| 2 | 模型分级 | 决策成本降约 70% | 决策用小模型 |
| 3 | 模板缓存 | 生成延迟降 | 收益有限 |

> **两条轨道的量级差三个数量级**（补贴 ¥50 万 / 活动，生成 ¥960 / 天）。**把资源投在「生成得更好看」上，优化空间不到「少发一点」的二十分之一。**

#### 25.6.6 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 先扣频控再查状态 | 已支付用户被误扣 | **先状态后频控** |
| 频控用 GET + INCR | 并发超发 | Lua 原子 |
| 只靠模型拦违规 | 可被绕过 | 硬规则 + 审核 |
| 让模型编造权益 | 虚假宣传 | 结构化权益服务 |
| 不做下发前复核 | 催单、发失效标的 | 实时状态复核 |
| 忽略顺延版本 | 旧消息误触发 | `schedule_seq` |
| 只看看点击率 | 高退订被掩盖 | 护栏 + 净 ROI |
| 无 Holdout | 自然转化算营销 | 空白对照组 |
| 归因窗口未到期就训练 | 负样本错误 | 按窗口打标 |
| 降级不标记 | 效果误算 | `degraded` + 原因码 |
| 全量触达不审批 | 资损 / 舆情 | 分级审批 |
| 跨渠道不共享频控 | 重复打扰 | 统一配额 |
| **用「日上限 N」当频控设计** | **N 是拍的，退订率是超线性的** | **按退订-打扰曲线的拐点定** |
| **把生成成本当主要成本** | **优化错靶子** | **补贴与打扰才是大头** |
| **只算当期转化不算 LTV** | **退订的损失被低估 100 倍** | **退订必须按 LTV 计** |
| **扩容只做容量评审** | **用户被打扰到退订** | **频控阈值同步收紧** |
| **规模预检只看人数** | **看不见打扰强度** | **规模 ÷ 人群池 = 人均触达** |

#### 25.6.7 高频追问

- **如何避免「刚付款又收到催单」？** → 下发前实时状态复核，状态已变记 `CANCEL_ALREADY_CONVERTED`；**复核覆盖率必须 100%**。
- **Redis 频控挂了怎么办？** → 默认 Fail-Closed，本地粗粒度限流兜底并告警。
- **如何保证不重复发？** → 七层幂等键 + 状态机条件更新 + `schedule_seq` 版本校验。
- **如何评估营销真实增量？** → Holdout 对照组 + 归因窗口 + 净 ROI；**同一活动同一问法必须可复现**。
- **高点击高退订的变体怎么处理？** → 护栏指标熔断，**不参与收益加权**。
- **生成模型超时怎么办？** → 降级预审安全模板，仍失败则跳过。
- **先扣频控还是先查状态？** → 先查状态，再扣频控。**无副作用的检查永远在前。**
- **频控扣了但下发失败？** → 回补额度、记录失败、告警；回补失败需人工兜底。
- **频控阈值怎么定？** → 量退订-打扰曲线 → 找拐点 → 设在拐点前，按人群价值分层。
- **如何防薅羊毛？** → 限购、设备指纹、风控、预算锁。
- **如何做多渠道协同？** → 统一频控口径、渠道优先级、失败切换不重复计数也不重复占用配额。
- **如何做样本回流？** → `trace_id` 对齐，快慢信号分层回填。
- **如何避免选择偏差？** → 保留随机探索与 Holdout，排除未到期样本。
- **一次活动最多能打扰多少人？** → 圈选 × 决策通过率 × 渠道成功率 × 送达率，**这个数必须写进方案与审批**。

#### 25.6.8 答题提纲与练习

**10 分钟版（自述型）**：

| 时间 | 内容 |
|---|---|
| 0–1 min | 澄清：触达量、**人群池**、活动数、单活动规模、渠道、护栏 |
| 1–3 min | **触达放大**：人群 × 并发 × 时间三段；**容量**：QPS、事件量、频控 key 空间 |
| 3–5 min | 架构：解析 → 圈选 → 生成 → 审核 → 调度 → 决策 → 复核 → 频控 → 下发 |
| 5–7 min | 顺序铁律、幂等、合规、预算 |
| 7–9 min | 深挖一个点（推荐：触达放大 / 频控阈值） |
| 9–10 min | 护栏、降级、归因（Holdout / MAB） |

**35 分钟版（深聊型）**：

| 时间 | 内容 |
|---|---|
| 0–5 min | 澄清与七锚点：规模、**人群池**、合规、不可逆清单 |
| 5–14 min | **触达放大的三段推导 + 打扰成本与 LTV 量化 + 退订曲线** |
| 14–22 min | 架构与数据流：解析 / 圈选 / 离线生成 / 审核 / 调度 / 决策 / 复核 / 频控 / 下发 / 归因 |
| 22–26 min | 数据模型与 API：人群快照、七层幂等、事件 Envelope、预算账本 |
| 26–34 min | 深挖三个点（各约 3 min）：① 触达放大与止损窗口 ② 频控阈值与 LTV 权衡 ③ Holdout 与归因去偏 |
| 34–35 min | 演进阈值、护栏清单、评测闭环 |

**练习**：

1. 设计日 5000 万触达的营销 Agent，给出完整链路与容量（**必须包含人群池与人均日触达次数**）。
2. 计算：圈选 1000 万人、决策通过率 60%、渠道成功率 99%、送达率 95%——一次决策放大成多少次触达？若快信号 5 分钟、慢信号 24 小时才止损，两者各能抑制多少次？
3. 设计多维频控的 Lua 脚本与原因码，并说明**为什么不能先扣后查**。
4. 设计延迟任务的幂等与顺延方案，说明 `schedule_seq` 解决的是哪个竞态。
5. 设计 Holdout 与净 ROI 的归因方案，并说明**为什么只用「已触达用户」训练会有选择偏差**。
6. 计算：人群池 1 亿，日触达从 3 亿压到 2 亿，按退订率 0.11% → 0.07%、单用户 LTV ¥720 算，日 LTV 变化是多少？代价是少转化 3 万单、每单毛利 ¥50。请判断该不该压。
7. 计算：日触达从 5000 万涨到 5 亿（人群池不变 1 亿），人均日触达怎么变？退订率怎么变？日 LTV 损失怎么变？**为什么这条不在容量评审的常规项里？**
8. 设计「生成服务超时 + 渠道故障 + 预算中心超时」三重叠加时的降级矩阵，并说明每一层是 Fail-Open 还是 Fail-Closed。

#### 25.6.9 一页纸作战手册

**S0 定题**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 落七锚点 | 唯一事实源是什么？哪几个决策不可逆？ | 7 项写下来，事实源 = 活动配置 + 人群快照 + 触达事件 + 预算账本 |
| 定优先级 | 打扰、资损、增长冲突时保谁？ | 不打扰 > 不资损 > 不违规 > 增量 ROI > 触达量 |
| **量人群池** | **人均日触达是多少？** | **给出一个带来源的数值，并换算成退订率** |

**S1 建模**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 分层 | 每层只做什么、明确不做什么？ | 解析 / 圈选 / 生成 / 审核 / 调度 / 决策 / 复核 / 频控 / 下发 / 归因十层职责表 |
| 定顺序 | 哪一步必须在前面？ | **复核 → 决策 → 扣减 → 下发**，无副作用在前 |
| 定幂等 | 每层怎么防重？ | 七层幂等键表 + 状态机条件更新 + `schedule_seq` |
| 定事实源 | 哪些不可重建？ | 快照、事件、幂等表、预算账本是事实源；频控计数是投影但要留扣减日志 |

**S2 决策**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 选路径 | 快慢怎么分层？ | 决策 150ms 在线；**生成离线批量** |
| 选粒度 | 千人千面切几包？ | 50 包 / 活动；生成成本 ¥0.4 |
| 选阈值 | 频控日上限定几？ | **按退订-打扰曲线的拐点定**，并按人群价值分层 |
| 选降级 | 每个依赖挂了怎么办？ | 退订 / 频控 / 预算 Fail-Closed；生成 / 决策降级兜底 |

**S3 论证**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 算放大 | 一次决策最多打扰多少人？ | 圈选 × 通过率 × 成功率 × 送达率，写进方案与审批 |
| 算容量 | 扛得住吗？ | 峰值 2,894 QPS、下游 1.3 万 QPS、决策链 150ms |
| 算打扰 | 会不会伤用户？ | 人均日触达 → 退订率 → 日 LTV 损失 |
| 算成本 | 钱花在哪？ | 补贴是大头；生成 ¥960/天可忽略；渠道次之 |

**S4 兜底**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 写延迟预算 | 每一步各多少？ | 9 阶段预算 + 硬限（§25.4.8） |
| 写降级矩阵 | 每个依赖挂了用户看到什么？ | 7 类依赖各有行为；**退订 / 频控 / 预算 Fail-Closed** |
| 定护栏 | 安全排第几？ | 退订 / 频控 / 幂等 / 预算 / 复核 / 合规 / 静默 / 预检 / 打标 / 审计 **十项 P0** |

**S5 闭环**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 定演进阈值 | 涨 10 倍哪里先坏？ | 频控 Redis → 渠道 → **打扰（非线性）**（§25.5.7） |
| 定指标 | 技术好了业务就好了吗？ | 采纳与 ROI 必须与退订、投诉、Uplift 背离度合看 |
| 建复盘闭环 | 行动项有负责人吗？ | 行动项 → 负责人 → 验证结果 |

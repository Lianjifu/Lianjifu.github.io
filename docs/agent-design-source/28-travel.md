## 第二十八章 文旅 AI Agent 系统

> **本章导读**：文旅 Agent 覆盖行前灵感与行程规划、机酒景交资源检索与预订、旅中动态伴游与突发重排、景区运营与营销转化，核心是「时空约束下的组合优化 + 实时资源锁定 + 旅中动态重排 + 长周期归因」。本章围绕需求解析与槽位、时空搜索与剪枝、预占支付与对账、影响图与旅中重排展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 28.1 核心定义与定位

**定义**：文旅 AI Agent 是在旅行前、中、后全周期内，理解用户偏好与实时环境，完成行程规划、资源检索、预订交易、旅中伴游、突发重排与经营分析的智能体系统。它不仅「会推荐景点」，还要「排得顺、订得到、改得动、算得清」。

**它与前面几章的 Agent 有两个根本差别**：

| 差别 | 具体含义 | 对设计的影响 |
|---|---|---|
| **约束来自物理世界** | 营业时间、余票、天气、交通、人力——**不是模型能商量的** | 硬约束校验层不可省，且**必须在生成之前跑** |
| **资源是共享且强实时的** | 房间、座位、机票是**有限且会被别人买走的** | 必须预占 + TTL + 对账，**缓存不能承诺有位** |

> **第二个差别决定了文旅 Agent 与营销 Agent 的分水岭**：营销发错了可以撤回一部分，文旅发错了是**超售**——用户到了现场才知道。而营销的触达是「打扰用户」，文旅的超售是「**让用户白跑一趟**」，后者在社交平台上的传播成本高一个量级。**所以本章的 P0 护栏几乎全部集中在「承诺之前」。**

**三类能力层次**：

| 层次 | 回答的问题 | 典型输出 | 决策周期 | 难度 |
|---|---|---|---|---|
| **L1 规划** | 去哪、怎么排 | 行程时间轴、候选清单 | 分钟级 | 中 |
| **L2 预订** | 订得到吗、花多少 | 预占、订单、支付 | 秒级（资源侧） | 较高 |
| **L3 旅中** | 现在怎么办 | 伴游回答、突发重排方案 | 秒级 | 高 |

**典型用户与场景**：

| 用户 | 诉求 | 关注点 | 主要风险 |
|---|---|---|---|
| 自由行游客 | 规划、比价、预订 | 可行、省心、不被坑 | 闭园扑空、超售 |
| 家庭 / 亲子 | 节奏、无障碍、安全 | 老人小孩体力 | 强度不匹配、安全风险 |
| 景区运营 | 客流、核销、收益 | 口径、权限 | 口径错、越权 |
| 文旅集团 | 多景区经营分析 | 跨域对比、归因 | 口径不一、归因虚高 |

**与相近系统的区别**：

| 系统 | 核心 | 与文旅 Agent 的差异 |
|---|---|---|
| 传统 OTA | 固定商品位 + 交易 | 卖「机票酒店」这一个个单品，**不组合、不排程** |
| 旅游攻略 / 内容社区 | 内容推荐 | **说得好，但不管今天能不能去、还有没有房** |
| 地图导航 | 路径规划 | **只管两点之间，不管多点组合与时间窗** |
| 通用旅行 LLM | 生成建议 | **不接实时资源，会推荐已闭园的地方** |
| 文旅 Agent | 规划 + 锁定 + 重排 | **把「建议」变成「订得到、改得动」** |

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 需求理解与行程规划 | POI / 酒店 / 航班主数据 |
| 资源检索与实时校验 | 航司 / 酒店内部系统 |
| 预占、下单、支付编排 | 支付渠道 |
| 旅中伴游与重排 | 景区现场调度 |
| 经营问数 | 数仓建模 |
| 营销触达 | 渠道网关 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 行程 | 采纳率、**约束满足率**、绕路率、重排成功率与耗时 |
| 搜索 | **可行解产出率**、剪枝后候选数、**评估次数 / 预算** |
| 交易 | 预订转化率、**超售率**、预占过期率、退款率、**重复扣款数** |
| 体验 | 首响、P99、客诉率、通知打扰率 |
| 经营 | 净营收、核销率、连带消费、营销增量 ROI |
| 安全 | 越权拦截、注入拦截、资损事件、安全提醒触达率 |

> **新增的两个指标是本章特有的**：**可行解产出率**（有多少比例的规划请求真的产出了可行行程——它衡量搜索效率），**评估次数 / 预算**（剪枝效率的直接读数）。**没有这两个指标，团队只会盯着「采纳率」，而采纳率低的时候无法判断是模型不行还是搜索预算被吃光了。**

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 行程规划 P95 | < 15s |
| 伴游回答 P95 | < 1.5s |
| 库存查询 P95 | < 300ms |
| 预占 P99 | < 1s |
| **超售** | **0**（硬约束） |
| **重复扣款** | **0**（硬约束） |
| **约束违反的行程** | **0**（硬约束） |
| 重排方案生成 P95 | < 30s |
| 审计覆盖率 | **100%** |

**本章专属不可逆决策清单**（做错了要停机迁移 + 数据回填 + 全量对账，不是发个版本就能改）：

| 决策 | 为什么不可逆 | 改动代价 |
|---|---|---|
| **行程对象模型与版本语义**（Itinerary / Day / Item / buffer / `confirmed_items`） | 行程、订单、重排、通知全部引用这些结构 | 存量行程无法迁移 + 通知模板失效 + 已确认项判定错乱 |
| **硬约束的定义与数据来源**（营业时间、余票、时间矩阵、天气规则的来源与口径） | 决定「行程可行」的判定标准 | 所有历史行程的可行性判定失效 + 需全量重跑评测 + 用户的「已确认」承诺失效 |
| **预占语义与 TTL 策略**（hold 的粒度、时长、回收方式） | 决定库存占用与超售边界 | 存量预占无法对账 → **超售与少卖同时可能发生** |
| **写操作的幂等键构造规则**（`booking:{user_id}:{request_id}` 等六层） | 下单、支付、退改、预占共用 | 存量幂等记录失效 → **已发生的重复扣款无法自动识别** |
| **与资源服务的对接契约**（库存 / 价格 / 退改规则的接口语义与错误码） | 「查不到」与「查错了」的处理方式完全由它决定 | 全部调用方重写 + 历史错误码无法回放 + 降级路径全部失效 |
| **支付与退款的账务口径**（对账口径、退款归属、佣金与补贴归属） | 决定净营收与营销 ROI 是否可信 | 历史账务需重新对账 + 营销归因全部作废 |
| **归因窗口与 Holdout 分流规则**（窗口长度、抽样比例、随机种子） | 决定增量 ROI 是否可复现 | 换种子或窗口 → 同一活动前后两套结论，历史不可比 |

> **对照第一章 §1.4.4**：这七项属单向门，决策时要多评审、做原型、留迁移方案。其余（模型选择、K 值、评估预算、TTL 时长、剪枝策略、召回方式）是双向门，可以快速试错——但 **K 值与评估预算属于「可逆但很贵」**：调它们会改变全部历史行程的形态与可行率，必须伴随黄金行程集回归。

### 28.2 核心解读与关键矛盾

**本质**：文旅 Agent 的核心矛盾，是「用户想要的自由度」与「现实世界的硬约束」之间的冲突。模型可以生成任意行程，但景区会闭园、航班会延误、房间会售罄。**自由度的上限由约束决定，而约束由实时接口决定——所以这是本章所有工程量的来源。**

**六条章级原则**（贯穿全章，冲突时以这六条为准）：

1. **先可行、后好看**——硬约束（营业时间、余票、交通耗时、天气、人力）全部过闸之后，才谈推荐理由与文案。**顺序不能反：先给理由再校验，等于给用户希望再撤回。**
2. **资源服务是唯一事实源**——价格、库存、余票、退改规则必须实时查询。**索引、缓存、模型记忆都不构成「有位」的承诺。**
3. **先预占、后支付；写超时先查单**——没有成功预占就不承诺有位；支付超时**先查单确认，绝不盲目重试**。
4. **行程是版本化对象**——局部变更只重排受影响的天 / 项，已确认项不可被静默改写。
5. **变更必确认、触达必克制**——涉及资金或行程大改时让用户确认；旅中通知严格频控，紧急安全事件才可突破。
6. **搜索空间靠剪枝，不靠召回**——候选数的上限由**评估预算倒推**，不由召回率正推。**召回更多候选，大部分会死在第一道硬约束上，白白吃掉上下文与时间预算。**

**三个不等式**：

```
候选组合数 C(N,k)^D   >>  评估预算能覆盖的分支数  → 靠剪枝，不靠穷举
行程项数              >>  单次事件的受影响项数    → 靠影响图，不靠全量重排
行程客单价            >>  单次错误的容忍度        → 资金类错误必须 fail-closed
```

**三个放大器**（本章最贵的量都藏在这里）：

| 放大器 | 说明 | 后果 | 量化 |
|---|---|---|---|
| **时空搜索放大** | 候选组合数随天数与每日点数指数增长，而可行比例随约束收紧急降 | 规划跑不完、可行解找不到 | 3 天 × 每天 3 点 = **2.26 × 10¹⁸ 种组合**；可行解只剩 **万分之一**；**必须剪枝 15 个数量级**（§28.3.9） |
| **行程变更放大** | 一个事件沿行程依赖图传播，重排是受影响项的组合爆炸 | 全量重排毁掉已确认项 | 全行程 20 项重排 = **3.5 × 10⁹ 种**；只重排受影响 8 项 = **6,561 种**，**降 5 个数量级**（§28.3.12） |
| **资金与安全放大** | 机酒客单价高，旅中错误指引危及人身 | 真金白银 + 不可逆后果 | 5 天 4 晚行程客单价 **¥6,700**；重复扣款一次实际损失 **≈ ¥10,000**（§28.3.11） |

> **本章与前面各章的放大器方向不同**：Feed 是读放大，秒杀是写放大，客服是上下文放大，问数是结果集放大，营销是触达放大，供应链是牛鞭放大。**文旅章的放大器是时空搜索放大**——它是唯一一个「**搜索空间随用户要求变复杂而指数爆炸**」的架构。**别的系统放大的是数据量，文旅放大的是组合数。**

**四层正确性**（必须分开保证）：

| 层次 | 要求 | 保障手段 | 典型漏法 |
|---|---|---|---|
| **时空可行** | 营业、交通、天气、人力允许 | 硬约束校验 + 时间矩阵 | 先推荐后校验，用户到了才发现闭园 |
| **资源真实** | 库存、价格、余票准确 | 实时接口 + 预占 + TTL | 用缓存承诺有位 → 超售 |
| **资金正确** | 预占、支付、退改金额一致 | 状态机 + 幂等 + 对账 | 超时盲目重试 → 重复扣款 |
| **变更可控** | 不静默改已确认项 | 版本化 + 影响图 + 用户确认 | 全量重排 → 已付的酒店被改掉 |

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 可行 vs 好看 | 网红点但不顺路 | 硬约束优先 | 时间充裕可绕行 |
| 实时 vs 成本 | 频繁查库存 / 价格 | 缓存 + 关键节点复核 | 大促可加缓存 |
| 预占 vs 库存利用 | 占而不买 | TTL + 主动释放 | 高价值客户可延长 |
| 自动化 vs 确认 | 静默改行程 | 重大变更必须确认 | 低影响可自动 |
| 个性化 vs 安全 | 推荐野景点 | 安全优先 | 专业用户可放宽 |
| 长归因 vs 时效 | 等 30 天太久 | 快慢信号分离 | 短周期可缩短 |
| 丰富信息 vs 低延迟 | 伴游要塞很多 | 精简 + 分层 | 非实时场景可详 |
| 灵活重排 vs 已确认项 | 全量重算 | 局部重排 + 版本 | 结构大改才全量 |
| **召回量 vs 评估预算** | **召回越多越全，越跑不完** | **按预算倒推 K 值** | 单次评估极快时可放宽 |

**八类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| 闭园扑空 | 到景区发现关闭 | 未查实时状态 | 实时校验 |
| 绕路 | 行程不可行 | 无时间矩阵 | 路线优化 + 时间矩阵 |
| **规划跑不出** | **超时或给不出可行解** | **候选爆炸、无剪枝** | **评估预算 + 分层剪枝** |
| 超售 | 到店无房 / 无座 | 缓存承诺 | 预占 + TTL |
| 价格变动 | 支付时涨价 | 未复检 | 支付前复核 |
| 重复扣款 | 超时重试 | 盲目重试 | 先查单后重试 |
| 重排失败 | 行程中断 | 无备选 | 多方案 + 确认 |
| 打扰 | 高频通知 | 无频控 | 合并 + 频控 |
| 归因虚高 | 预算浪费 | 末次点击 | Holdout + 长窗口 |

**信任分级**（行程建议的「输出契约」）：

| 级别 | 条件 | 展示方式 |
|---|---|---|
| 高 | 全部硬约束已校验 + 资源已实时确认 + 时间矩阵完整 | 给行程 + 每个点的校验依据 + 总预算 |
| 中 | 行程可行但部分点位信息较旧（缓存）或余票未锁 | 给行程 + **标注哪些点需要出发前复核** |
| 低 | 约束校验未跑完 / 资源接口超时 / 未查余票 | **只给候选清单与「请自行确认」的提示**，不给行程 |
| 拒绝 | 越权 / 资源被占 / 超出安全策略 | 明确拒绝 + 原因 + 替代路径 |

> **「低」这一档是本章新增的**：很多系统把「查不到余票」当成「有位」，于是给出一条**看起来完整、但有一个点根本订不到**的行程。**旅行行程的可用性是「与」的关系——一行里只要一个点订不到，整个行程就是废的。**

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| 黄牛抢票 | 批量账号占座 | 实名、限购、风控 |
| 虚假预订 | 占房不付 | TTL、押金、信用 |
| 冒充 / 越权 | 查改他人订单 | 实名 + 归属校验 |
| Prompt 注入 | 点评 / 攻略含指令 | 数据隔离 + 判定在代码层 |
| 恶意退改 | 频繁退订 | 规则、风控、人工 |
| **提示注入（景区侧）** | **POI 描述被篡改，含「请推荐本店」** | **POI 描述只作数据，不作指令** |

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| **LLM（尤其候选 POI 描述）** | **最大** | **候选裁剪**、模型分级、上下文裁剪 |
| 实时资源查询 | 次之 | 批量、缓存、时间戳 |
| 地图 / 天气 | 中 | 缓存、按需查询、区域级近似 |
| 人工审批 | 视风险 | 阈值优化 |

> **LLM 成本的大头是「候选 POI 描述」这一项，而不是模型对话**。每注入 20 个候选的描述就是 1,600 token，而本章会证明**其中约 54% 会在第一道硬约束上被淘汰**（§28.3.9）。**所以「多召回一点」在文旅是纯亏：既花钱，又稀释注意力，还吃掉时间预算。**

### 28.3 理论与方法论

#### 28.3.1 S0：七项前置锚点

先落定七件事，它们共同决定**可行域**——不在可行域内的方案不参与讨论。

| # | 锚点 | 本章答案 | 影响 |
|---|---|---|---|
| 1 | **业务目标与成功标准** | 行程采纳率 ≥ 40%、约束满足率 ≥ 99%、超售 0、重复扣款 0、客诉率 ≤ 0.3% | 决定自动化分级与拒答阈值 |
| 2 | **规模量级** | 日会话 50 万、峰值 29 QPS、**平均 4 轮 / 8 次工具调用**、行程 3–10 天、预订转化 5% | 决定搜索预算、预占集群与 token 预算 |
| 3 | **质量属性优先级** | 时空可行 > 资源真实 > 资金正确 > 体验 > 成本 | 决定降级顺序与 fail-closed 边界 |
| 4 | **硬约束** | 营业时间、预约余票、天气、人力与无障碍；超售 0、重复扣款 0、行程不得违反硬约束 | 定义可行域；物理约束不可用模型折抵 |
| 5 | **不可逆决策清单** | 见 §28.1 的本章七项 | 决策流程：多评审 + 原型 + 迁移方案 |
| 6 | **核心路径与事实源** | 核心路径 = 提问 → 槽位 → 召回 → 硬约束 → 组合优化 → 预占 → 支付 → 履约 → 旅中重排；事实源 = **行程对象 + 订单 + 预占记录 + 资源服务实时返回** | 决定缓存与对账对象；缓存与索引全是投影 |
| 7 | **竞争与协作边界** | 航司 / 酒店 / 票务 / 支付渠道在外部；规划、预占编排、重排、伴游、问数自建 | 决定服务边界与团队成本 |

> **第 2 项为什么改变答案**：文旅系统的规模参数不只是 QPS，还有**「行程长度」与「每天的点数」**。同样是 50 万会话，1 天 2 个点和 10 天 4 个点，**组合空间的量级完全不同**（3 天 3 点已是 10¹⁸）。**没有这两个参数，就没法估搜索预算，也就没法知道系统能撑多大的行程。**

#### 28.3.2 4S 收敛顺序

```
S0 定题（锚点 + 不可逆清单）
   → Scenario 定会话量、行程长度、每天点数、预算、实时性、渠道
      → Service 定规划、检索、预占、支付、重排、伴游、问数的边界
         → Storage 定行程、订单、预占、事件、归因的唯一事实源
            → Scale 定剪枝、评估预算、预占 TTL、对账、降级
```

#### 28.3.3 Scenario：场景与规模

| 维度 | 数值 | 推导与来源 |
|---|---|---|
| 日会话 | 50 万 | — |
| 平均会话 QPS | 50 万 ÷ 86400 | ≈ **5.8** |
| **峰值会话 QPS** | 5.8 × 5 | **29**（峰值系数 5：节假日前 2 周晚 8–10 点与周末全天两个高峰） |
| 场景占比 | 规划 40%、预订 35%、伴游 15%、问数 / 营销 10% | 决定各链路的负载结构 |
| **平均轮数** | **4 轮** | **直接决定上下文成本曲线** |
| **每会话工具调用** | **8 次** | 规划 4、预订 3、伴游 1 |
| **行程长度** | 1–10 天，**均值 4 天** | **决定组合空间** |
| **每天点数** | 2–4 个，**均值 3 个** | **决定组合空间** |
| 预订转化率 | 5% | 决定预占与支付写流量 |
| 资源实时性 | 库存 / 价格秒级；营业与余票分钟级 | 决定缓存 TTL 与复核节点 |
| 决策周期 | 行前 7–30 天；旅中秒级 | 决定快慢双轨 |
| 多租户 | 景区、酒店、航司、文旅集团 | 决定权限隔离与口径 |

> **「行程长度 × 每天点数」是本章独有的关键参数**。传统系统的容量参数是 QPS，文旅系统还必须给出**这两个乘积参数**——它们决定了搜索空间的大小，也决定了「规划 P95 < 15s」这个 SLO 到底能不能成立。

#### 28.3.5 Storage：数据模型

| 数据 | 存储 | 关键设计 | 是事实源吗 |
|---|---|---|---|
| **行程对象** | MySQL / 文档库 | `itinerary_id`、版本、每日项 | **是** |
| **订单** | MySQL | `booking_id`、状态机 | **是** |
| **预占记录** | Redis + DB | `hold_id`、TTL、幂等键 | **是** |
| **槽位与会话** | Redis / DB | 偏好、已确认、已否决 | 否（可重建） |
| 资源快照 | 缓存 | 价格 / 库存 + 查询时点 | 否（**必须有查询时点**） |
| 事件 | Kafka / 数仓 | 统一 Envelope | **是** |
| 归因宽表 | 数仓 | 长窗口、Holdout | **是** |

> **资源快照必须带查询时点**。缓存里的「有房」在用户下单那一刻可能已经过期 40 秒——**没有时点，客服无法判断一个投诉是系统的错还是缓存的错**，对账也无从下手。**时点是这个表里最重要的一列。**

**行程对象**：

```
Itinerary
  ├→ version
  ├→ days[]
  │    ├→ date
  │    ├→ items[]（POI/餐饮/交通/住宿）
  │    └→ buffer（用餐/休息/机动）
  └→ confirmed_items[]（不可静默修改）
```

#### 28.3.6 Scale：扩展与兜底

| 维度 | 手段 | 触发条件 |
|---|---|---|
| **规划** | **分层剪枝 + 评估预算 + 早停** | **组合爆炸、跑不完** |
| 资源查询 | 批量、缓存、批量合并 | QPS 高 |
| 预占 | 分片、TTL、异步回收 | 并发抢购 |
| 重排 | 影响图、局部重排、批量 | 事件频繁 |
| 伴游 | 精简上下文、缓存热点状态 | 低延迟要求 |
| 降级 | 候选清单 + 保守方案、Fail-Closed | 依赖故障 |

#### 28.3.7 需求解析与结构化槽位

| 槽位 | 作用 |
|---|---|
| `destination`、`date_range` | 目的地与日期范围 |
| `travelers`（成人 / 儿童 / 老人） | 人群结构与体力约束 |
| `budget_cap` | 预算上限与分项预算 |
| `pace_preference` | 紧凑 / 宽松 / 不赶路 |
| `confirmed_items` | 已确认的机酒票，重排时不可静默修改 |
| `rejected_pois` | 用户已否决的景点，避免重复推荐 |

**解析要求**：

- 隐含约束要显式化（「带老人小孩」→ 步行强度、休息点、无障碍）。
- 缺失关键字段要追问（日期、人数、预算）。
- 预算给区间与分项，不给单点假精确。
- 多轮对话保留已确认槽位。

**槽位即约束的来源**：「带老人小孩」不是偏好，是**硬约束**——它会排除掉需要爬 800 级台阶的景点。**槽位必须区分「偏好」（可放宽）与「约束」（不可放宽）**，否则放宽策略会连老人孩子的体力约束一起放宽。

#### 28.3.8 候选召回与硬约束

**召回维度**：

| 维度 | 示例 |
|---|---|
| 目的地 | 城市、景区、商圈 |
| 主题 | 亲子、人文、自然、美食 |
| 人群 | 老人、儿童、无障碍 |
| 季节 | 花期、雨季、冰雪 |
| 预算 | 价格带 |

**硬约束校验（按淘汰顺序排列）**：

| 序 | 约束 | 通过率（参考） | 数据来源 |
|---|---|---|---|
| 1 | **已闭园 / 封路 / 不可达** | 92% | POI 实时状态 |
| 2 | **营业时间与行程时段吻合** | 85% | 营业时间表 + 实时状态 |
| 3 | **预约有余票 / 可容纳人数** | 70% | 票务实时接口 |
| 4 | **天气适配**（暴雨、极端高温） | 90% | 天气 + 预警 |
| 5 | **体力与同行人匹配**（老人、儿童、无障碍） | 90% | POI 属性 + 槽位 |
| 6 | **价格带与预算匹配** | 95% | 实时价格 |

**联合通过率**：

```
单点通过率 = 0.92 × 0.85 × 0.70 × 0.90 × 0.90 × 0.95 ≈ 0.421
```

> **约 58% 的候选会死在硬约束上。** 这个数字是 §28.3.9 全部结论的基础——**大部分召回是白召回的**。

**无可行解时的放宽顺序**（按影响从小到大，让用户选，而不是硬凑）：

```
减少点数 → 放宽时段（接受排队）→ 提高预算 → 调整日期 → 换区域 → 明确告知无解
```

> **「明确告知无解」必须排在最后而不是排除掉**。硬凑出来的行程——闭园的景点、过期的余票、超出预算的门票——**每一个都会在旅途中变成一次客诉**。

#### 28.3.9 时空搜索放大：候选、可行解与剪枝

**本节是搜索与剪枝的权威版**，§28.3.10、§28.4.3、§28.5.5 只引用。

**问题定义**：给定候选集 N 个 POI、行程 D 天、每天 k 个点，求一个满足全部硬约束的时间轴。

**组合空间**：

```
每天的无序组合数 = C(N, k)
D 天的组合数     = C(N, k)^D
```

**五层剪枝漏斗**（把 10¹⁸ 降到能算的量级）：

```
原始组合空间
  → 召回裁剪（域 / 主题聚类）           2.26e18 → 6.3e16
  → 单点硬约束预筛（通过率 0.421）      → 2.2e11
  → 时空分块剪枝（区域 × 时段）          → 6.1e11
  → 回溯剪枝（排除与已选点冲突的分支）   → 3e6
  → 局部搜索收敛（2-opt 邻域改进）       → 1e3–1e4
```

代入基准（召回 Top-200，每天 3 点，3 天）：

| 量 | 计算 | 结果 |
|---|---|---|
| 每天组合数 | C(200, 3) | 1,313,400 |
| **3 天组合空间** | 1,313,400³ | **≈ 2.26 × 10¹⁸** |
| **每天可行比例** | (0.421)³ × 跨点冲突折扣 0.6 | ≈ **4.5%** |
| **3 天可行比例** | 0.045³ | ≈ **0.009%（万分之一）** |
| **可行解数量** | 2.26e18 × 9e-5 | ≈ **2.0 × 10¹⁴** |

> **数字大到没有意义，这才是重点**：真正的问题不是「组合数多大」，而是**「你只有几万次评估机会，而可行解分散在 10¹⁸ 的空间里」**。**所以可行解多不多根本不是瓶颈——能不能找到才是。**

**评估预算是真正的稀缺资源**：

| 项 | 数值 | 说明 |
|---|---|---|
| 规划 P95 | 15s | 用户可感知的上限 |
| 留给评估的时间 | 10s | 留 5s 给 LLM 生成与序列化 |
| 单点约束评估 | 2ms | 时间矩阵查表 + 规则校验，本地内存 |
| 单组合评估 | 50ms | 两两衔接 + 路径搜索 + 时间窗冲突 |
| **单点评估预算** | 10,000 ÷ 2ms | **5,000 次** |
| **单组合评估预算** | 10,000 ÷ 50ms | **200 次** |

> **算一下差距**：组合空间 2.26 × 10¹⁸，评估预算 5,000 次 → **必须剪枝 15 个数量级**。**「剪枝」不是优化，它是这个系统能不能存在的前提。**

**五层剪枝漏斗**（把 10¹⁸ 降到能算的量级）：

| 层 | 手段 | 剩余（三天组合数） | 省掉的量级 |
|---|---|---|---|
| 0 | 原始 | 2.26 × 10¹⁸ | — |
| 1 | **召回裁剪**：按域 / 主题聚类，候选 200 → 80 | C(80, 3)³ ≈ 5.5 × 10¹⁴ | 3.6 个量级 |
| 2 | **单点硬约束预筛**（营业 / 余票 / 天气 / 体力 / 预算），80 → 34 | C(34, 3)³ ≈ 2.2 × 10¹¹ | 3.4 个量级 |
| 3 | **时空分块剪枝**：按「区域 × 时段」分块，只在块内组合 | ≈ 1 × 10⁹ | 2.3 个量级 |
| 4 | **回溯剪枝**：逐点插入时排除与已选点冲突的分支 | ≈ 1 × 10⁶ | 3 个量级 |
| 5 | **局部搜索收敛**（2-opt / 邻域改进） | ≈ 10³–10⁴ | 2–3 个量级 |

**单点预筛的那一刀最值钱**：它把 80 个候选砍到 **34 个**（通过率 0.421），**一步去掉 58% 的组合空间**，而且成本极低（80 × 2ms = 160ms）。

**「召回 Top-K 越大越好」在文旅是错的**（这是本章的核心结论）：

| 方案 | 进 Prompt 的 POI 描述 | 预筛耗时 / 天 | 通过硬约束 | 产出的可行解 |
|---|---|---|---|---|
| K = 200 | 200 × 80 = 16,000 token | 400ms | 84 个 | 基准 |
| **K = 84** | **84 × 80 = 6,720 token** | **168ms** | 84 个 | **完全相同** |
| 节省 | **−58% 上下文** | **−58% 预筛时间** | — | **0 损失** |

> **这个对照是本章最反直觉、也最省钱的一条结论**：**把 K 从 200 降到 84，规划和预筛都省 58%，可行解一个不少。** 因为那 116 个多召回的候选**全部死在第一道硬约束上**——它们消耗了 Prompt 上下文、消耗了评估时间、稀释了模型的注意力，却**一个可行解都没贡献**。
>
> **所以 K 的正确取法是倒推，不是正推**：
> ```
> K 上限 = 单点评估预算 ÷ (每天点数 × 剪枝保留率)
> ```
> 而不是「召回率能到多少就取多少」。**文旅的系统不是缺候选，是缺剪枝。**

**剪枝之外的两个工程约束**：

| 约束 | 说明 |
|---|---|
| **时间矩阵必须降维** | 全量两两时间矩阵 = C(10万, 2) = **5 × 10⁹ 项**，不可行。必须按区域聚类：2,000 个区域 × 每区 50 个 POI → 区域对 200 万项，缓存 ≈ 32MB。**代价是同区域内耗时用平均值 + 距离修正，精度下降** |
| **必须有早停** | 找到第一个满足全部约束且评分达标的解即可停止；继续搜索只在「用户要最优解」时才需要。**搜索预算的默认花法是「够好就停」，不是「搜到最优」** |

**规划的输出契约**：不是「一个行程」，而是**「一个行程 + 每个点的校验依据 + 未通过项的说明 + 总预算与耗时」**。用户需要知道哪一天比较紧、哪个点是雨天备选、哪里超了预算 80 元——**这比多推荐两个景点重要得多**。

#### 28.3.10 组合优化与路线排序

**目标**：在时间窗内最小化通勤、平衡每日强度、满足全部硬约束。

**方法**：

- 时间矩阵：POI 两两之间的通勤时间（**必须区域级降维，见 §28.3.9**）。
- 时间窗约束：营业时间、预约时段。
- 启发式：最近邻构造 + 2-opt 局部优化。
- 每日缓冲：用餐、休息、机动时间。

**输出**：每天时间轴、交通方式、预约提醒、室内备选方案。

**评分函数**（在可行解里挑「最好的」）：

```
总分 = w1·(行程紧凑度) + w2·(用户偏好命中) + w3·(体力均衡)
     − w4·(预算超支) − w5·(绕路惩罚) − w6·(天气风险)
```

> **权重不是玄学，必须能被解释与回放**。用户问「为什么排成这样」，系统要能说出「因为你说不赶路，所以每天只排 2 个点并留了 1.5 小时缓冲」——**权重表 + 槽位 + 约束余量，三样加起来就是行程的解释**。解释不了的评分函数，用户不会信任，也不会采纳。

**「不赶路」的工程含义**：不是「少排一个点」，而是**把缓冲时间显式建模**。带老人小孩的行程若不留缓冲，路上 20 分钟的延误就会顶掉下一个预约——**缓冲不是浪费，它是可行性的一部分**。

#### 28.3.11 资源锁定：预占、支付与对账

**本节是预占 / 支付 / 对账的权威版**，§28.4.4、§28.5.6 只引用。

**多工具 DAG / Wave**：

1. **只读波次**：并发 `search_hotels`、`check_flight_status`、`get_ticket_quota`、`get_transfer_routes`。
2. **校验波次**：价格、余票、退改规则、实名信息、日期与入住规则。
3. **预占波次**：锁房 / 占座 / 锁票，带 TTL 与幂等键。
4. **支付与确认**：支付成功后确认订单；失败则释放预占。
5. **补偿波次**：多段订单部分失败时，取消 / 退款已成功段或改订备选。

**预订状态机**：

```
QUOTED → HELD → PAYING → CONFIRMED
   │       │       │          │
   │       │       └→ FAILED  └→ CANCELLED / REFUNDED
   │       └→ EXPIRED（TTL 到期回收）
   └→ NEED_RECONFIRM（价格/库存变化）
```

**资金放大：一次错误值多少钱**：

| 项 | 数值 | 说明 |
|---|---|---|
| 5 天 4 晚行程客单价 | 机票 ¥2,000 + 酒店 4 晚 ¥3,200 + 门票餐饮 ¥1,500 | **¥6,700** |
| **重复扣款一次的实际损失** | ¥6,700 + 客诉处理与补偿 ≈ ¥3,300 | **≈ ¥10,000** |
| **超售一次（到店无房）** | 同级安置差价 ¥600 + 交通 ¥200 + 赔付 | **≈ ¥1,200 / 间** |
| 日预订量 | 50 万会话 × 5% | **2.5 万单 / 天** |
| 重复扣款率 1e-5 | 2.5 万 × 1e-5 | 0.25 单 / 天 → **≈ ¥2,500 / 天** |
| 超售率 1e-4 | 2.5 万 × 1e-4 | 2.5 单 / 天 → **≈ ¥3,000 / 天** |

> **这些数字说明一件事：在 2.5 万单/天的量级上，「重复扣款 0」和「超售 0」不能靠事后对账兜底**。1e-5 的概率乘上单量就是每天几千元的直接损失，再加上不可控的口碑损失。**它们必须是 P0 护栏，必须在架构上不可能发生，而不是「概率很低所以还行」。**

**预占与支付之间的竞态**（本章最隐蔽的一个 bug 来源）：

```
预占 TTL 900s，支付 P99 800ms
若不做续期：
  回收线程在 TTL 边界扫到「支付中」的持有 → 释放 → 支付成功 → 超售
峰值预占创建 3,000 QPS
  每秒扫过 3,000 个持有，其中处于支付窗口的 ≈ 3,000 × 0.8s / 900s ≈ 2.7 个
  竞态率 ≈ 2.7 / 3,000 ≈ 0.09%
日订单 2.5 万单 → 每天约 22 单可能超售 → 每天 ≈ ¥26,400 直接损失
```

**三道防护**：

| 防护 | 做法 |
|---|---|
| **支付前续期** | 进入支付流程即延长 TTL（一次延长到覆盖支付 P99 + 余量） |
| **「支付中」状态** | 回收线程遇到 `PAYING` 状态的持有**跳过**，不释放 |
| **超时先查单** | 支付 / 退改超时**先查订单状态**，确认未成功再决定是否重试 |

**关键护栏**：

- **防超售**：库存扣减以资源服务为准，预占用原子操作与 TTL；**绝不在本地缓存上直接承诺有位**。
- **价格变化**：报价到支付之间重新校验；涨幅超过阈值必须让用户确认，**不能静默扣款**。
- **幂等**：下单、支付、退改都带 `idempotency_key`；同一订单的写操作加版本号或订单级锁。
- **高金额 / 非标退改**：挂起 `WAITING_FOR_HUMAN`，由用户确认或规则审批。
- **对账**：预占、支付、确认、退款定时对账，处理超时未决与单边账。

#### 28.3.12 旅中事件驱动重排

**本节是重排的权威版**，§28.4.5、§28.5.1 只引用。

**行程变更放大（本章第二个签名量）**：

```
全行程 20 项、每项 3 个备选 → 3^20 = 3.49 × 10^9 种重排组合
只重排受影响 8 项            → 3^8  = 6,561 种
                                    ↓
                              降 5 个数量级
```

> **这就是「局部重排」的全部价值**：不是「少改几项比较温和」，而是**组合数从 10⁹ 降到 10³，让重排能在 30 秒内算完**。全量重排在数学上就不可行——**它不是慢，是根本算不出来**。

**影响图**：

```
事件（航班延误 4h）
  → 传播：硬时间依赖 / 资源依赖 / 预算耦合
  → 不传播：软时间依赖 / 偏好耦合
  → 受影响 8 项 / 全行程 20 项
  → 组合数 3^8 = 6,561（全量 3^20 = 3.5e9，降 5 个数量级）
  → 生成 2–3 个方案 → 成本与可行性比较
  → 用户确认 → 幂等执行 + 回滚预案
```

**传播规则（决定影响图的边界）**：

| 关系 | 是否传播 | 例子 |
|---|---|---|
| 硬时间依赖（必须在其后开始） | **传播** | 机场接送 → 酒店入住 |
| 资源依赖（同一预占 / 同一名额） | **传播** | 景区预约名额 → 次日入园 |
| 预算耦合 | **传播**（成本重算） | 改签费用 → 总预算 |
| 软时间依赖（推荐顺序） | **不传播** | 晚餐排在午餐之后 |
| **偏好耦合**（主题连贯） | **不传播** | 体力变化不重排美食推荐 |

> **最后两条「不传播」规则是影响图设计的核心**。没有它们，任何一个事件都会沿依赖链扩散到整个行程——**航班晚 4 小时会把用户的美食偏好也算进去重排**，既慢又没意义。**影响图的价值不在于「找全受影响项」，而在于「精确切出不相关的项」。**

**重排的四条纪律**：

| 纪律 | 理由 |
|---|---|
| **只改受影响项** | 已确认项不动 |
| **至少两个方案** | 一个备选都没有 = 把选择压力全推给用户 |
| **涉及费用变化必须确认** | 静默扣款是本章最恶劣的失败模式 |
| **失败要回滚并给备选** | 改签成功但接送失败 → 行程更糟 |

#### 28.3.13 旅中伴游导览

**核心挑战**：依赖实时定位（LBS）、当前时段与步行 / 打车距离，要求低延迟、短回答、强可核验性（营业状态、排队 / 预约提示、安全提醒）。

**工具**：

| 工具 | 用途 |
|---|---|
| `get_nearby_pois` | 按位置、距离、类型召回附近景点 / 餐饮 |
| `get_opening_status` | 实时营业、闭园、限流状态 |
| `get_queue_or_quota` | 排队时长、预约余量 |
| `get_route` | 步行 / 驾车 / 公交耗时与路线 |
| `get_weather_alert` | 天气预警与安全提示 |

**上下文策略**：

- 保留当前所在区域、已选 / 已去景点、同行人约束；压缩历史闲聊。
- 近期 K 轮保留原始交互，更早内容进滚动摘要。
- 回答突出「时间、距离、费用、注意事项」，并标注数据查询时点。

**安全与体验**：

- 不推荐已闭园、封路、极端天气下的户外路线。
- 老人 / 儿童同行时降低步行强度，提示休息点、洗手间与无障碍设施。
- 紧急事件优先给安全指引与官方联系方式，**不做不确定承诺**。

**伴游与规划的上下文差异**：伴游只有 **1.5 秒**，因此**不注入完整行程，只注入「当前位置 + 同行人约束 + 附近候选 Top-8」**。规划要 15 秒，可以注入完整行程与全部候选。**同一个系统在两条轨道上的上下文预算差 10 倍——把它们混成一条链路是伴游做不快的根本原因。**

#### 28.3.14 文旅经营问数

**核心挑战**：景区 / 航司 / 酒店运营分析「分时入园人数、核销率、连带消费、客诉率、淡旺季净收益」，面临口径分歧、宽表复杂与跨部门 / 跨景区权限隔离。

**指标口径**：

- 分时入园人数、预约核销率、客单价、连带消费、客诉率、退款率、净营收。
- 明确统计粒度（小时 / 日 / 节假日）、分母（预约量 / 入园量 / 可售库存）与退款归属。
- 示例：`核销率 = 实际核销数 / 有效预约数`；`净营收 = 门票 + 园内消费 − 退款 − 渠道佣金`。

**执行安全**：

- 语义层固化指标；Schema 裁剪只召回相关表。
- SQL 经 AST 校验，只读、强制 `LIMIT` 与超时。
- 执行层 / 视图层强制注入景区、门店、部门权限过滤。
- 图表自动匹配，并做同比 / 环比、分时与贡献度拆解。

**补充**：文旅数据受天气、节假日、促销影响大，归因时要控制混杂因素；跨景区对比要统一口径与统计周期。

> **问数的方法论与第二十三章完全一致**（语义层、AST 校验、行级权限、结果集下推）。本章只强调文旅特有的两点：**一是跨景区的口径必须先统一再对比**（不同景区的「入园」定义可能包含不同票种），**二是天气 / 节假日 / 促销三个混杂因素必须显式控制**——不控制它们，「客流下降 5%」的归因结论会全是错的。

#### 28.3.15 营销与长周期归因

**核心场景**：浏览行程未下单、收藏酒店未预订、节假日 / 暑期行前唤醒、会员积分即将到期。

**链路**：决策模型判断时机 / 渠道 → 查实时订单 / 退订 / 免打扰 → Redis Lua 原子频控 → 带幂等键下发 → 快慢信号归因。

**文旅特点**：

- 决策周期长，归因窗口要覆盖 7–30 天，并区分直接成单与辅助转化。
- 价格敏感度高，券补贴要计入净贡献，不能只看 GMV。
- 促销轰炸反感强，旅中与行前都要控制频次与静默时段。
- 保留 Holdout 计算真实增量，结合曝光 / 点击 / 退订快信号熔断高打扰变体。

> **本章与第二十五章的关系**：频控、MAB、Holdout 与降级细节**见第二十五章，本节只引用**。本章强调文旅特有的两点：**一是长决策周期下的辅助转化**（用户 20 天前看的行程今天下单，硬分给谁都不对），**二是旅中触达克制**——用户正在路上，此时推送营销是最招人烦的时刻。

#### 28.3.16 上下文治理

- `assistant(tool_calls)` 与 `role="tool"` 是**原子组**，先裁剪冗长 JSON / POI 列表，再整组淘汰。
- 发往模型前做 `tool_call_id` 配对校验，防止协议报错或丢失调用结果。
- 槽位锁定行程参数、已确认预订、已排除偏好、已执行写操作，防重复占座 / 重复查单。
- 工具契约声明 `side_effect`、超时、重试语义、幂等要求与权限范围。

**本章的上下文大头是候选 POI 描述**（见 §28.3.9）：

| 组成 | token | 占比 |
|---|---|---|
| system + 规则 | 800 | 16% |
| 槽位 + 行程摘要 | 700 | 14% |
| **候选 POI 描述（20 个 × 80）** | **1,600** | **32%** |
| 工具结果（库存 / 路线 / 天气） | 900 | 18% |
| 历史对话 | 1,000 | 20% |
| 合计 | 5,000 | 100% |

> **POI 列表占输入 token 的三分之一，而其中约 58% 的候选会死在硬约束上**（§28.3.9）。所以上下文治理的第一刀不是「裁历史对话」，**而是「裁掉注定被淘汰的候选」**——**这一刀同时省了 token、时间和模型的注意力**。

#### 28.3.17 幂等设计

| 层 | 方案 | 幂等键 / 约束 |
|---|---|---|
| 预占 | `hold:{type}:{resource_id}:{user_id}:{request_id}` | TTL 内唯一 |
| 下单 | `booking:{user_id}:{request_id}` | 唯一索引 |
| 支付 | `pay:{booking_id}:{pay_request_id}` | 状态机条件更新 |
| 退改 | `change:{booking_id}:{change_request_id}` | 状态机条件更新 |
| 状态 | 条件更新 | `WHERE status = ?` |
| 消息 | 去重表 + `msg_id` 唯一 | 通知不重复 |
| **资源查询** | **查询带查询时点** | **写操作必须复核，不复用查询结果** |

> **最后一层容易被忽略**：查询结果**不能直接当作写操作的依据**。「30 秒前查到有房」不能作为 30 秒后扣款的理由——**写之前必须重新确认**，否则超售就发生了。

#### 28.3.18 降级矩阵（Fail-Open / Fail-Closed）

**本节是降级的权威版**，§28.4.7、§28.5.6 只引用。

判据：**依赖失效时，失效的后果是「少卖一单」还是「让用户白跑一趟 / 白扣一次钱」？**

| 依赖 / 环节 | 典型故障 | 策略 | 降级动作 |
|---|---|---|---|
| **支付 / 退款 / 退改** | 超时、结果未知 | **Fail-Closed** | **查单确认，不重复扣款 / 退款** |
| **库存 / 票务余量** | 服务超时 | **Fail-Closed** | **不承诺有位**，提示稍后确认 |
| **退订 / 黑名单（旅中触达）** | 状态服务超时 | **Fail-Closed** | 跳过触达并记原因码 |
| **Redis 频控** | 抖动 | **Fail-Closed** | 本地粗粒度限流兜底并告警 |
| **营业状态 / 闭园** | 超时 | **Fail-Closed** | 该点不排入行程；无法确认的点不推荐 |
| **天气 / 预警** | 超时 | 保守降级 | 采用保守方案并提示用户自行确认 |
| **地图 / 路线** | 超时 | 降级 | 用缓存 / 直线距离估算并**标注不确定性** |
| **决策模型** | 超时 | 规则兜底 | 默认低打扰渠道或跳过 |
| **推荐 / 文案生成** | 失败 | 模板兜底 | 预审安全模板，仍失败则给基础列表 |
| **LLM 服务** | 超时 / 限流 | 模型降级 | 切备用模型，仍失败转人工 |
| **硬约束评估** | 超时 | **降级为候选清单** | **不给行程**，只给候选与提示 |

**治理要点**：降级打标 `degraded=true` 与 `reason_code`；资金、库存、合规默认 Fail-Closed；高频抖动依赖配置熔断器；预占到期与支付超时要定时对账。

> **最后一行的降级方向与其它章都不同**：文旅在硬约束评估失败时，**正确的降级不是「给一个宽松的行程」，而是「不给行程」**。因为行程的价值是「可行」，一个不可行的行程比没有行程更糟——**用户会照着它出门**。

#### 28.3.19 事件、原因码与可观测

**统一事件 Envelope**：

```
trace_id, session_id, turn_id, user_id, intent,
tool_name, tool_call_id, idempotency_key,
itinerary_id, booking_id, poi_id, amount,
decision_meta, reason_code, degraded
```

**核心事件**：

| 阶段 | 事件示例 |
|---|---|
| 行程规划 | `itinerary.plan.created`、`itinerary.item.rejected`、`itinerary.replanned` |
| 资源与预订 | `inventory.held`、`inventory.hold.expired`、`booking.confirmed`、`booking.failed` |
| 旅中变更 | `flight.status.changed`、`weather.alert`、`poi.closure.detected` |
| 反馈与归因 | `traveler.feedback`、`booking.attributed`、`refund.completed` |

**原因码**：

| 前缀 | 典型原因码 | 含义 |
|---|---|---|
| `BIZ_*` | `BIZ_SOLD_OUT`、`BIZ_OUT_OF_WINDOW`、`BIZ_STATE_INVALID` | 业务条件不满足 |
| `INV_*` | `INV_HOLD_EXPIRED`、`INV_QUOTA_EXCEEDED`、`INV_PRICE_CHANGED` | 库存 / 票务 / 价格异常 |
| `TOOL_*` | `TOOL_TIMEOUT`、`TOOL_SCHEMA_MISMATCH`、`TOOL_RESULT_UNKNOWN` | 工具调用异常 |
| `AUTH_*` | `AUTH_PERMISSION_DENIED`、`AUTH_IDENTITY_MISMATCH` | 权限或实名问题 |
| `DEC_*` | `DEC_LOW_CONFIDENCE`、`DEC_MODEL_SKIP` | 模型 / 门控决策 |
| `SYS_*` | `SYS_DEPENDENCY_TIMEOUT`、`SYS_CIRCUIT_BREAKER_OPEN` | 系统依赖异常 |
| **搜索相关（本章新增）** | **`SEARCH_BUDGET_EXHAUSTED`、`SEARCH_NO_FEASIBLE_SOLUTION`、`SEARCH_PRUNED_TO_CAP`** | **搜索预算耗尽 / 无可行解 / 被剪枝到上限** |

> **搜索相关的原因码是本章新增的**。没有它们，「用户没订」这件事无法区分是「行程不可行」还是「行程太烂」还是「搜索没跑完」——**而这三者的改进方向完全不同**。

**核心指标**：行程采纳率、约束满足率、**可行解产出率**、**评估次数 / 预算**、预订转化率、超售率、预占过期率、重排成功率与耗时、工具成功率、P99 延迟、单会话成本、客诉率、退款率、净营收、营销增量 ROI。

#### 28.3.20 评测闭环

- **黄金行程集**：需求 + 期望约束 + 可行路线。
- **资源沙箱**：模拟航班、酒店、票务、天气、闭园，覆盖售罄、超时、价格变动、重复提交。
- **故障注入**：航班延误、台风闭园、预约余票归零、支付超时。
- **搜索专项评测**（本章新增）：给定候选集与约束，统计**剪枝后候选数、评估次数、可行解产出率、是否触发预算耗尽**。
- 在线 A/B / Holdout：验证采纳率、转化率与客诉率；决策快照、工具轨迹、原因码与结果回流，用于约束权重、阈值与策略优化。

> **「搜索专项评测」是本章特有的**：规划质量不只由「最终行程好不好」衡量，还由「花了多少评估找到它」衡量。**同样一个好行程，用 5,000 次评估找到的和用 500 次找到的，是两个系统**——后者才能扛住峰值流量。

#### 28.3.21 容量与成本估算

**本节是容量口径的权威版**，§28.5 与 §28.6 只引用。

**假设**：日会话 50 万，峰值系数 5，平均 4 轮 / 8 次工具调用，预订转化 5%；system + 规则 800 token、槽位 + 行程摘要 700、候选 POI 描述 20 个 × 80 = 1,600、工具结果 900、历史对话 1,000，**单次输入 5,000 token**；单次输出 800 token；模型价格输入 ¥2 / 百万、输出 ¥8 / 百万。

**一、流量**

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均会话 QPS | 50 万 ÷ 86400 | ≈ **5.8** |
| **峰值会话 QPS** | 5.8 × 5 | **29** |
| **峰值 LLM 调用** | 29 × 4 | **116** |
| **峰值工具调用** | 29 × 8 | **232** |
| 其中资源查询（库存 / 价格 / 余票） | 232 × 60% | ≈ **139** |
| 其中规划查询（POI / 路线 / 矩阵） | 232 × 40% | ≈ **93** |
| **峰值预订写** | 232 × 5% | ≈ **12** |

**二、上下文与 token**

| 指标 | 计算 | 结果 |
|---|---|---|
| 每会话输入 token | 4 次 × 5,000 | 20,000 |
| 每会话输出 token | 4 × 800 | 3,200 |
| **日输入 token** | 20,000 × 50 万 | **100 亿** |
| 日输出 token | 3,200 × 50 万 | **16 亿** |
| **日合计 token** | — | **116 亿** |
| 输入成本 | 10,000 百万 × ¥2 | ¥20,000 |
| 输出成本 | 1,600 百万 × ¥8 | ¥12,800 |
| **日 LLM 成本** | — | **≈ ¥32,800**（约 **98 万元 / 月**） |

> **注意这里的 token 结构与其它章不同**：文旅是**唯一一章「候选描述」占输入三分之一**的（1,600 / 5,000 = 32%）。这直接决定了本章的成本优化第一刀是**裁候选**而不是裁历史对话。

**三、候选裁剪的收益**

| 方案 | 每会话输入 token | 日输入 token | 日成本 | 可行解 |
|---|---|---|---|---|
| K = 20（基线） | 20,000 | 100 亿 | ¥32,800 | 基准 |
| **K = 8（按通过率裁到 84 个中的 Top-8）** | 4 × 4,040 | 80.8 亿 | ¥28,960 | 需实测，通常持平 |
| 节省 | **−19.2%** | −19.2 亿 | **−¥3,840 / 天** | — |

> **要诚实**：裁到 8 个是否还找得到同样的可行解，取决于「每天 3 个点」这个约束——**8 个候选可能凑不出满足「不重样 + 时间窗 + 交通」的三点组合**。所以正确的做法是**按每天点数动态定 K**：K ≥ 3 × 期望点数 × 安全系数。**这个公式必须按真实数据校准，而不是照抄。**

**四、存储**

| 数据 | 计算 | 结果 |
|---|---|---|
| 会话存储 | 50 万 × 30KB | ≈ 15 GB / 天 |
| 行程对象 | 10 万行程 / 天（20% 会话）× 50KB | ≈ 5 GB / 天 |
| 订单 | 2.5 万单 / 天 × 20KB | ≈ 500 MB / 天 |
| 事件 | 1,000 万 / 天 × 300B | ≈ 3 GB / 天 |
| **合计** | — | **≈ 23.5 GB / 天（≈ 8.6 TB / 年）** |
| **时间矩阵缓存** | 2,000 区域对 × 16B | ≈ 32 MB |

**五、结论**

1. **瓶颈在 LLM 成本（约 ¥98 万 / 月）与资源查询（139 QPS）**，而预订写只有 12 QPS——**但写操作虽少，一次错误的代价是查询的一万倍**（§28.3.11）。
2. **上下文的大头是候选 POI 描述（32%）**，成本优化的第一刀是裁候选。
3. **时间矩阵必须区域级降维**：全量 5 × 10⁹ 项不可行，降到 200 万项、32MB，代价是同区域精度下降。
4. **搜索预算（评估次数）必须被当作容量指标**：它不体现在 QPS 上，但决定规划 P95 能不能守住。
5. **必须先量「行程长度 × 每天点数」的分布**——它决定搜索空间，进而决定「规划 P95 < 15s」的可行区间。

### 28.4 工程落地与规则护栏

#### 28.4.1 端到端链路

```
用户请求 / 旅中事件
  → Gateway（鉴权、租户、限流）
  → Intent Router（规划/预订/伴游/问数/营销）
  → Planner / Agent Orchestrator
      ├→ 加载槽位与行程版本
      ├→ 候选召回（按预算定 K）
      ├→ 硬约束预筛（单点，2ms × K）
      ├→ 组合优化 / 影响图重排（带评估预算）
      ├→ Tool Gateway（白名单、Schema、幂等）
      └→ 高风险变更 → 用户确认/审批
  → 资源服务执行（预占/支付/退改）
  → 结果校验与回复
  → 事件、审计、归因
```

> **图里最重要的三行是「按预算定 K」「硬约束预筛」「带评估预算」**。前两行决定搜不搜得到，第三行决定来不来得及。**这三行都在 Planner 内部——所以 Planner 不是「一个 LLM 调用」，而是一套有明确时间预算的搜索系统。**

#### 28.4.2 门控与路由护栏

- 快慢分离：简单查询走规则 / 轻模型，复杂规划进 Planner。
- 意图置信度低 → 追问。
- 高风险意图（支付、退改）强制进入工作流。
- 租户 / 景区 / 商家隔离。
- **规划类请求必须带「行程长度 × 每天点数」的槽位**，否则无法估搜索预算。

#### 28.4.3 行程规划护栏

| 护栏 | 说明 |
|---|---|
| **硬约束优先** | 营业、余票、交通、天气、体力、预算 |
| **K 按预算倒推** | 不按召回率正推（§28.3.9） |
| **评估预算硬限** | 超出即早停，返回当前最优可行解 |
| **时间矩阵区域级降维** | 精度下降要在答案里标注 |
| **每日缓冲** | 用餐、休息、机动 |
| **已确认项** | 重排不可静默修改 |
| **无解放宽** | 让用户选择，不硬凑；「明确告知无解」是合法输出 |
| **预算区间** | 不给单点假精确 |
| **校验依据随行程输出** | 每个点附校验结果与查询时点 |

#### 28.4.4 预订与写操作护栏

- 先预占后支付，预占带 TTL。
- **支付前续期 + 「支付中」状态 + 回收跳过**（消除 TTL 竞态）。
- 支付前复检价格 / 库存。
- 所有写操作用幂等键 + 状态机条件更新。
- **写超时先查单，不盲目重试**。
- 高金额 / 非标退改转人工。
- 多段订单失败按 Saga 逆序补偿。
- 定时对账：预占、支付、确认、退款。

#### 28.4.5 重排护栏

- 事件驱动，不做全量轮询。
- 影响图定位受影响项，**且必须有「不传播」规则**（§28.3.12）。
- 局部重排，不重算未受影响项。
- 生成至少两个方案，比较成本与可行性。
- 涉及费用变化必须用户确认。
- 合并通知，避免轰炸。
- 执行失败回滚并给备选。

#### 28.4.6 上下文与工具护栏

- 原子组裁剪，配对校验。
- **候选 POI 列表按通过率裁剪**（不是按 top-k 截断）。
- 槽位锁定行程、预订、偏好、已执行动作。
- 工具声明副作用、超时、重试、幂等、权限。
- **查询结果不得直接作为写操作依据**。
- 敏感信息脱敏。

#### 28.4.7 降级与熔断

降级矩阵以 §28.3.18 为准，本节只列执行动作：

- 资金 / 库存 / 营业状态：**Fail-Closed**。
- 地图 / 天气：保守降级并提示不确定性。
- 生成 / 推荐：模板或基础列表兜底。
- **硬约束评估超时 → 降级为候选清单，不给行程。**
- 高频抖动依赖：熔断器。
- 降级打标 `degraded` + `fallback_mode` + `reason_code`。

#### 28.4.8 延迟预算与超时降级

**本表是唯一的延迟口径来源**，其他小节只引用。

**规划轨道（P95 < 15s）**：

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 槽位解析与追问 | 300ms | 1s | 追问 / 转人工 |
| 候选召回（多路并行） | 500ms | 1.5s | 减少召回路数，缩小 K |
| **单点硬约束预筛** | **400ms** | **1s** | **收紧 K，宁可少候选** |
| **组合评估** | **8s** | **12s** | **早停，返回当前最优可行解** |
| 行程渲染与校验依据 | 500ms | 1.5s | 输出基础时间轴 |
| LLM 生成说明 | 2s | 4s | 模板文案 |
| **规划合计** | **< 15s（P95）** | 25s | — |

**伴游轨道（P95 < 1.5s）**：

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 定位与附近召回（Top-8） | 200ms | 500ms | 缩小半径 / 减少类型 |
| 营业 / 排队 / 预约状态 | 300ms | 800ms | **无法确认的点不推荐** |
| 路线耗时 | 200ms | 500ms | 直线距离估算 + 标注 |
| LLM 生成短答 | 500ms | 1.2s | 结构化列表，不生成散文 |
| **伴游合计** | **< 1.5s（P95）** | 3s | — |

**预订写轨道**：

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 预占创建 | 200ms | 800ms | **不重试，先查预占状态** |
| 支付 | 500ms | 2s | **先查单，确认未成功再决定是否重试** |
| 退改 | 500ms | 2s | 同上 |

**重排轨道（P95 < 30s）**：

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 事件接入与影响图构建 | 1s | 3s | 人工介入 |
| 受影响项重新评估 | 5s | 15s | 只给「取消受影响项」的保守方案 |
| 多方案生成（2–3 个） | 10s | 20s | 只给一个方案 + 说明 |
| 用户确认（异步） | — | 24h | 过期 → 保守执行（取消受影响项） |
| **方案生成合计** | **< 30s（P95）** | 60s | — |

> **四条轨道的时间预算是同一个方法论**：**每一步都要有「超时后用户看到什么」的答案**，而不是「超时了报错」。本章最反直觉的一条是伴游轨道：**结构化列表（距离、耗时、是否开放）比一段生成的散文更快也更有用**——在 1.5 秒的预算里，生成散文是最不该花的钱。

#### 28.4.9 观测与压测

**观测**：

| 类别 | 指标 |
|---|---|
| 行程 | 采纳率、约束满足率、重排耗时 |
| **搜索** | **可行解产出率、剪枝后候选数、评估次数 / 预算、预算耗尽率** |
| 资源 | 查询 P99、预占成功率、过期率、**支付竞态次数** |
| 交易 | 转化率、超售率、退款率、**重复扣款数** |
| 体验 | 首响、客诉率、通知打扰率 |
| 成本 | 单会话成本、token、降级比例 |

**压测**：

- 峰值 5 倍会话。
- **10 天行程 × 每天 4 点的最坏搜索**（验证评估预算与早停）。
- 热门景区 / 航班抢购。
- 预占 TTL 到期回收（**含与支付并发**）。
- 航班大面积延误（重排风暴）。
- 天气 / 闭园事件风暴。
- 支付超时与重复回调。
- **硬约束评估超时**（验证降级为候选清单而不是给出不可行行程）。

#### 28.4.10 规则护栏清单

| 领域 | 护栏 | 优先级 |
|---|---|---|
| **硬约束前置** | 行程不得违反营业 / 余票 / 交通 / 天气 / 体力 / 预算；违反数 0 | **P0** |
| **超售 0** | 预占原子 + TTL + **回收跳过「支付中」** + 定时对账 | **P0** |
| **重复扣款 0** | 六层幂等键 + 状态机条件更新 + **超时先查单** | **P0** |
| **支付前复检** | 价格与库存重新校验；涨幅超阈值必须确认 | **P0** |
| **资源唯一事实源** | 缓存不得承诺有位；写操作不复用查询结果 | **P0** |
| **已确认项不可静默改** | 版本化 + 影响图 + 用户确认 | **P0** |
| **影响图有「不传播」规则** | 软依赖与偏好耦合不传播 | **P0** |
| **变更必确认 + 通知克制** | 涉资金或行程大改必确认；旅中频控 | **P0** |
| **降级打标** | `degraded` + `fallback_mode` + `reason_code` | **P0** |
| **审计不可篡改** | 行程版本、预占、支付、退改全量留痕 | **P0** |
| **安全优先** | 老人儿童体力、极端天气、封闭路线优先于推荐 | P1 |
| **搜索预算** | K 按预算倒推；评估次数硬限；早停 | P1 |
| **时间矩阵降维** | 区域级近似；精度下降要标注 | P1 |
| **上下文原子组** | `tool_calls` 与 `tool` 消息整组裁剪与配对校验 | P1 |
| 长归因 | 30 天窗口 + Holdout + 净贡献（券与佣金计入） | P1 |
| **成本** | 单会话 token 超预算 120% 触发容量评审 | P2 |

> **文旅 Agent 的十个 P0 里有五个是「承诺之前」**（硬约束、超售、重复扣款、复检、唯一事实源），**两个是「变更可控」**（已确认项、影响图）。**这与营销章的「发出去之前」是同一个道理，但文旅多了一条：钱一旦扣错，用户在千里之外。**

#### 28.4.11 上线检查（10 问）

1. **K 值是按评估预算倒推的，还是按召回率正推的？** 评估次数是否有硬限与早停？
2. 硬约束是否**全部实时校验**？营业、余票、交通、天气、体力、预算六项是否都有对应接口？
3. 时间矩阵是否已降维？**同区域近似带来的精度误差是否在答案里标注**？
4. 库存承诺是否基于**预占**而非缓存？**预占 TTL 与回收是否可靠？回收是否跳过「支付中」？**
5. 写操作是否全部幂等、**超时先查单**？**支付前是否复检价格与库存**？
6. 重排是否只改受影响项？**影响图是否有「不传播」规则？** 是否用户确认？
7. 上下文是否原子组裁剪？**候选 POI 列表是否按通过率裁剪，而非按 top-k 截断？**
8. 降级是否按 Fail-Open / Fail-Closed 分级？**硬约束评估超时是否降级为「候选清单」而不是给出行程？**
9. 对账是否覆盖预占 / 支付 / 退款 / **支付竞态**？
10. **黄金行程集、资源沙箱、故障注入、搜索专项评测**是否都通过并可回归？

### 28.5 典型案例与端到端解决

#### 28.5.1 案例：航班延误 4 小时后的行程重排

**背景**：用户原定 14:00 航班，18:00 入住酒店，次日 09:00 景区预约入园。航班状态变更为延误至 18:00 起飞。

1. **事件接入**：`flight.status.changed` 触发重排，关联 `itinerary_id` 与后续预订。
2. **影响分析**：机场接送需后移；酒店入住变为 22:00 后；次日 09:00 预约可能受疲劳影响；晚餐时间被压缩。**按传播规则判定**：接送 → 酒店入住 → 晚餐 → 次日预约 **传播**；次日早餐、次日的美食推荐 **不传播**（软依赖与偏好耦合）→ **受影响 4 项，不是全行程 20 项**。
3. **只读查询**：航班新时刻、酒店最晚入住政策、接送运力、景区次日各时段余票。
4. **生成方案**（组合数 3⁴ = 81 种，秒级算完）：
   - 方案 A：改约 22:30 接送，酒店确认保留房间，景区改约次日 11:00。
   - 方案 B：取消当晚酒店，改住机场附近，次日直接前往景区。
5. **成本与确认**：方案 A 接送 +60 元、景区改约免费；方案 B 产生酒店取消损失。涉及费用变化，推送**一次**并等待用户确认。
6. **执行**：确认后以幂等键锁定接送与景区新时段，更新酒店入住备注；失败则回滚并给备选。
7. **触达**：合并为一条通知，避免重复轰炸；后续仅在有新变更时提醒。

**常见失败**：未先查余票就承诺改约 → `BIZ_SOLD_OUT`；支付超时直接重试 → 可能重复扣款；酒店房间未预占 → 到店无房。

> **第 2 步的「受影响 4 项 vs 20 项」是本章最重要的一个数**：它把重排的组合数从 3²⁰ 降到 3⁴，**从 35 亿种变成 81 种**。如果影响图没有「不传播」规则，这一步就会退化成 20 项全排——**算法再强也算不出来，而且用户已确认的酒店入住时间会被改掉。**

#### 28.5.2 变体 A：多日行程规划

**需求**：「带老人小孩，5 天 4 晚，预算 6000，不赶路，避开雨天户外。」

1. 槽位：人数结构、日期、预算、节奏、偏好；**「带老人小孩」被标记为硬约束而非偏好**。
2. 候选召回：亲子 / 人文 / 自然，按体力分级；**K 按 5 天 × 3 点倒推**。
3. 硬约束：营业、预约、交通、天气、体力、预算，六项全过。
4. 组合优化：每天 2–3 个点，预留午休与机动。
5. 天气备选：每天至少一个室内方案。
6. 输出：时间轴 + 交通 + 预约提醒 + 预算分项 + **每个点的校验依据**。

**这个需求最狠的地方**：5 天 × 3 点的组合空间是 C(200,3)⁵ = 3.9 × 10²⁴——**比 §28.3.9 的 3 天例子还大 6 个数量级**。**所以「5 天行程」必须靠分天求解（每天独立求最优 + 天间衔接约束），而不是全局穷举。**

#### 28.5.3 变体 B：旅中伴游

**需求**：「现在在西湖边，带孩子，附近有什么能去的？」

1. LBS 召回附近 POI（**Top-8，不是 Top-20**——伴游只有 1.5 秒预算）。
2. 实时营业 / 排队 / 预约校验；**无法确认的点不推荐**。
3. 路线耗时与天气提醒。
4. 输出：**3 个结构化选项 + 距离 + 耗时 + 注意事项 + 查询时点**（不生成散文）。
5. 安全：不推荐闭园 / 封路 / 极端天气路线；带小孩时优先有洗手间与休息点的选项。

> **伴游与规划用同一套候选召回逻辑，但预算差 10 倍**：规划 15 秒、Top-20、可生成解释；伴游 1.5 秒、Top-8、只能给结构化列表。**用同一个「召回 Top-K」的参数去驱动两条轨道，是伴游做不快的最常见原因。**

#### 28.5.4 变体 C：长周期营销归因

**场景**：用户 20 天前看过三亚行程，今天下单。

- 归因窗口 30 天，区分直接与辅助转化。
- Holdout 计算真实增量。
- 扣除券补贴与渠道佣金，算净贡献。
- 快信号熔断高退订变体。

> **文旅营销的归因有一个别的章没有的陷阱**：用户今天下单的可能是**上个月的行程**（提前很久订好），也可能是**今天的最后一刻**。**30 天窗口对前者仍然不够。** 所以文旅的归因窗口必须按**决策周期分布**来定，而不是拍一个 30 天。

#### 28.5.5 变体 D：时空搜索预算与 K 值取舍

**场景**：规划请求量涨了 3 倍（20 万 → 60 万 / 天），规划 P95 从 12s 涨到 19s。怎么办？

**先算清楚三条路的账**（规划部分日成本基线 ¥13,120）：

| 方案 | 增量成本 / 天 | 可行解产出率 | 性质 |
|---|---|---|---|
| **A 加机器** | **+¥26,240** | 95% → 95%（不变） | 贵但无损 |
| **B 下调 K（20 → 8）** | **−¥4,608**（规划输入 −19.2%） | **95% → 60%** | **省得少，损得多** |
| **C 热门行程结果缓存** | **−¥9,600** | 95% → 95%（不变） | **省且无损** |

**C 的算法**：命中 40% 的规划请求（60 万 × 40% = 24 万 / 天）直接返回预计算结果，**省 24 万 × 4 次 × 5,000 token = 48 亿 token = ¥9,600 / 天**，且**一个可行解都没损失**。

**决策顺序**：

```
1. 先做结果缓存（C）——无损且更便宜
2. 再加机器（A）——贵但无损
3. 最后才考虑降 K（B）——有损，且损的是可行性
```

> **降 K 是最后手段，不是第一手段**，因为它的代价不是「行程差一点」而是「**35% 的请求给不出行程**」——而给不出行程的用户不会投诉，只会走掉。**这是本章的一条反直觉但极其重要的结论：搜索系统的降级顺序应该是「先降质量、最后降可行性」，因为可行性是这个产品唯一不可妥协的东西。**

#### 28.5.6 故障与兜底

降级矩阵以 §28.3.18 为准，本例补充三条：

| 故障 | 影响 | 兜底 |
|---|---|---|
| **预占 TTL 与支付竞态** | 支付成功但库存已释放 | **支付前续期 + 回收跳过「支付中」** |
| **硬约束评估超时** | 规划跑不完 | **降级为候选清单，不给行程**（不给不可行的行程） |
| **重排时备选资源也售罄** | 方案不可执行 | 给出「取消该点 + 退款」方案，**而不是重试到成功为止** |

#### 28.5.7 扩容 10 倍，哪里先坏？

以 §28.3.21 的基准扩容 10 倍（日会话 500 万、峰值 290 QPS、LLM 调用 1,160 QPS、工具调用 2,320 QPS、资源查询 1,390 QPS、预订写 120 QPS、日 token 1,160 亿、日成本 ¥328,000）：

| 顺序 | 先坏的点 | 现象 | 触发指标 | 对策 |
|---|---|---|---|---|
| 1 | **搜索预算（非线性）** | 规划 P95 超 15s、**无行程产出率上升** | 评估次数 / 预算 > 80%、预算耗尽率 > 5% | **K 下调（最后手段）、早停、热门行程模板化、结果缓存** |
| 2 | **资源查询** | P99 上升、超时 | 峰值 > 1,400 QPS | 批量、缓存、读写分离 |
| 3 | **LLM 配额** | 429 | 调用 QPS > 配额 80% | 模型分级、候选裁剪、缓存 |
| 4 | **预占** | 冲突、TTL 堆积、**竞态增多** | 预占成功率下降、过期率上升 | 分片、异步回收、**预占准入限流** |
| 5 | **重排事件** | 风暴、积压 | 事件队列 lag | 影响图、批量、优先级；**全网重排需人工批准** |
| 6 | **地图 / 天气** | 限流 | P99 > 500ms | 缓存、按需、区域级近似 |
| 7 | **归因存储** | 长窗口数据膨胀 | 单分区 > 1TB | 分层、预聚合 |
| 8 | **成本（非线性）** | 账单涨幅 > 流量涨幅 | 单会话 token > 预算 120% | 裁候选、模型分级、结果缓存 |

> **第 1 位的非线性不是 QPS，而是「可行解产出率」**：并发涨 10 倍后，每个请求的**实际**评估时间被排队挤压 → 早停触发率上升 → **给出的行程质量断崖式下降**。而第 8 位的账单（¥98 万/月 → ¥984 万/月）说明：**这一章的扩容成本主要在 LLM，而 LLM 的成本主要在候选描述。**

#### 28.5.8 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| 硬约束优先 | 推荐不够「惊艳」 | 行程可行 | 用户明确要求冒险 |
| 先预占后支付 | 占用库存 | 不超售 | 库存充足可简化 |
| 局部重排 | 实现复杂 | 保留已确认项 | 结构大改才全量 |
| 重大变更确认 | 多一步交互 | 不静默改行程 | 低影响可自动 |
| 长归因窗口 | 数据延迟 | 真实增量 | 短周期可缩短 |
| Fail-Closed | 少成交 | 不超售 / 不资损 | 依赖稳定可放宽 |
| **按预算定 K（而非按召回率）** | **可能漏掉冷门但可行的组合** | **时间与 token 双省** | 单次评估成本大幅下降时可放宽 |
| **影响图带「不传播」规则** | **规则要人工维护** | **组合数降 5 个数量级** | —— |
| **硬约束超时降级为候选清单** | **少给行程** | **不给不可行的行程** | —— |
| **预占准入限流** | **峰值时少接单** | **不超售** | 资源服务容量提升后可放宽 |

### 28.6 闭环演进与常见误区

#### 28.6.1 演进路线

| 阶段 | 形态 | 触发条件 | 关键改造 |
|---|---|---|---|
| L0 | 攻略 + 人工客服 | 起步 | 内容、FAQ |
| L1 | 模板行程 | 标准化需求 | 模板 + 参数 |
| L2 | 规划 Agent | 个性化需求 | 检索、硬约束、**剪枝** |
| L3 | 预订闭环 | 交易需求 | 预占、支付、退改、**支付竞态防护** |
| L4 | 旅中重排 | 实时事件 | **影响图 + 不传播规则**、多方案 |
| L5 | 全周期智能体 | 成熟 | 伴游、问数、营销一体 |

> **L2 是最容易被跳过、也最不该跳过的一层**：很多系统从「攻略内容」直接跳到「能订票」，中间跳过了**硬约束校验与剪枝**。结果是一套会订票但会给出行程的晚、景点会闭园、老人走不动路的系统。**L2 的关键改造是剪枝，不是检索——检索是通用能力，剪枝是本章独有的工程量。**

| 层级 | 指标 | 用途 |
|---|---|---|
| 行程 | 采纳率、约束满足率、绕路率 | 判断规划质量 |
| **搜索** | **可行解产出率、评估次数 / 预算、预算耗尽率** | **判断搜索效率** |
| 交易 | 转化率、超售率、退款率、**重复扣款数** | 判断交易可靠 |
| 体验 | 首响、客诉率、打扰率 | 判断体验 |
| 经营 | 净营收、核销率、ROI | 判断价值 |
| 成本 | 单会话 token、候选描述占比、降级比例 | 判断可持续 |

#### 28.6.3 评测与回归

- 黄金行程集覆盖亲子、老人、雨季、预算紧等场景。
- 资源沙箱模拟售罄、超时、价格变动、重复提交。
- 故障注入：延误、闭园、余票归零、支付超时、**预占与支付并发**。
- **搜索专项评测**：剪枝后候选数、评估次数、可行解产出率、预算耗尽率。
- 在线 A/B 与 Holdout 验证采纳率、转化率、客诉率。
- 每周复盘 Top 错误，沉淀到约束权重与工具描述。
- **变更回归**：改 K 值、改剪枝策略、改硬约束口径，都必须重跑黄金行程集——**它们改变的是「搜不搜得到」，而不是「搜得好不好」。**

#### 28.6.4 成本优化

| 顺序 | 手段 | 收益 | 说明 |
|---|---|---|---|
| 1 | **裁候选（按通过率，不按 top-k）** | 输入 token **−19.2%** | **成本与延迟双赢** |
| 2 | **热门行程结果缓存** | 规划请求 −40% | **无损** |
| 3 | 模型分级 | 意图 / 抽取用小模型 | 约 −30% |
| 4 | 上下文原子组裁剪 | 历史对话 | 收益有限（只占 20%） |
| 5 | 资源查询批量 + 缓存 | 外部调用 | 降低外部依赖压力 |
| 6 | 早停 | 评估次数 | 质量略降，**最后手段** |

> **第 1 行的收益（−19.2%）远大于第 4 行**（历史对话只占输入的 20%），但第 4 行是大家通常先想到的。**这又是一个「优化靶子」问题**：本章最贵的不是对话历史，是候选描述。

#### 28.6.6 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 先推荐后校验 | 闭园扑空 | **硬约束前置** |
| **召回 Top-K 越大越好** | **烧 token、吃时间预算、可行解不变** | **按评估预算倒推 K** |
| **用两两时间矩阵** | **5×10⁹ 项，不可行** | **区域级降维** |
| **全量重排** | 改掉已确认项、算不出来 | **影响图 + 局部重排** |
| **影响图无「不传播」规则** | 任何事件都重排全行程 | **软依赖与偏好耦合不传播** |
| 用缓存承诺库存 | 超售 | 预占 + TTL |
| 支付前不复检 | 价格纠纷 | 支付前复核 |
| 写超时直接重试 | 重复扣款 | **先查单后重试** |
| **无支付竞态防护** | **支付成功但库存已释放** | **续期 + 回收跳过「支付中」** |
| 静默改行程 | 用户不满 | 重大变更确认 |
| 通知轰炸 | 投诉 | 合并 + 频控 |
| 末次点击归因 | 贡献虚高 | Holdout + 长窗口 |
| **硬约束超时后给宽松行程** | **用户照着不可行的行程出门** | **降级为候选清单** |
| **用缓存结果直接写操作** | **超售** | **写前必须重新确认** |

#### 28.6.7 高频追问

- **如何防止机酒票超售？** → 资源服务原子扣减 + 预占 TTL + **回收跳过「支付中」** + 幂等键 + 定时对账。
- **如何在航班延误后快速重排？** → 事件驱动影响图（**带不传播规则**）+ 实时余票 / 政策查询 + 备选方案 + 用户确认。
- **行程规划如何避免绕路？** → 时间矩阵（**区域级降维**）+ 时间窗约束 + 路线排序 + 每日缓冲。
- ****规划为什么会超时？** → **候选组合爆炸**。要查三件事：**K 值是不是按预算定的、剪枝漏斗有没有生效、评估预算有没有硬限与早停**。
- **召回多少候选合适？** → **按评估预算倒推**：`K ≤ 单点评估预算 ÷ (每天点数 × 剪枝保留率)`，而不是按召回率正推。
- **长决策周期如何归因？** → 长窗口（按决策周期分布定）+ Holdout + 辅助转化 + 扣除补贴与渠道成本。
- **伴游如何做到低延迟？** → 实时工具 + **Top-8 而非 Top-20** + 精简上下文 + 结构化列表 + 缓存热点状态。
- **依赖超时怎么降级？** → 资金 / 库存 / 营业状态 Fail-Closed；地图 / 天气保守降级并提示不确定性；**硬约束评估超时 → 给候选清单，不给行程**。
- **价格变了怎么办？** → 支付前复检，超阈值让用户确认。
- **预占过期怎么办？** → TTL 回收，重新预占或给备选；**回收必须跳过「支付中」的持有**。
- **重排会不会改掉已确认项？** → 局部重排 + 版本 + 确认。
- **如何评估文旅 Agent？** → 黄金行程 + 资源沙箱 + 故障注入 + **搜索专项评测** + 在线 A/B。
- **紧急安全事件如何触达？** → 可突破普通频控，但必须去重与分级。

## 第二十三章 问数 AI Agent 系统

> **本章导读**：问数 Agent（ChatBI / Text-to-SQL）把自然语言问题转成可信 SQL，再转成可解释的数据结论，难点不在「生成 SQL」，而在语义歧义、Schema 过大、结果集过大、权限越界与结论解读。本章围绕语义层与指标治理、Schema 裁剪、SQL 校验与权限重写、结果集下推、沙箱与资源护栏、归因与可信表达展开，整体按「定义 → 矛盾 → 方法论 → 工程护栏 → 端到端案例 → 演进与误区」组织。

### 23.1 核心定义与定位

**定义**：问数 AI Agent 是面向数据分析场景的智能体系统。它接收自然语言问题，完成意图澄清、指标映射、Schema 裁剪、SQL 生成与校验、沙箱执行、结果校验、图表路由与结论表达，最终给出**可追溯、可核验、可解释**的数据答案。

它不是「一个更聪明的 SQL 生成器」，而是一条**从提问到可信答案的受控流水线**：每一步都可能出错，系统的价值在于**把每种错误拦在答案之前**，而不是指望模型一次就对。

**三个能力层次**：

| 层次 | 回答的问题 | 典型输出 | 难度 | 本章覆盖 |
|---|---|---|---|---|
| L1 取数 | 是多少 | 明细 / 聚合结果、图表 | 中 | 全链路 |
| L2 分析 | 怎么变 | 同比环比、趋势、分组对比 | 较高 | §23.3.20 |
| L3 归因 / 建议 | 为什么、怎么办 | 贡献度拆解、原因假设、下一步 | 高 | §23.3.20、§23.5.1 |

**典型用户与场景**：

| 用户 | 场景 | 关注点 | 主要风险 |
|---|---|---|---|
| 业务分析师 | 自助取数、探索 | 灵活、口径可控 | 口径漂移、结果被截断 |
| 运营 | 活动效果、渠道对比 | 时效、可视化 | 指标口径不一致 |
| 管理层 | 日报周报、异常归因 | 结论、可信度 | 把相关当因果 |
| 数据团队 | 取数需求分流 | 减少重复取数 | 明细导出打爆数仓 |

**与传统 BI 的区别**：

| 维度 | 传统 BI | 问数 Agent |
|---|---|---|
| 交互 | 拖拽、固定报表 | 自然语言 |
| 口径 | 人工配置在报表里 | 语义层 + 自动映射 |
| 覆盖 | 预设问题 | 长尾问题 |
| 风险 | 较低 | 幻觉、越权、资源耗尽 |
| 评估 | 报表准确性 | 执行准确率 + 采纳率 + 分歧率 + 安全 |

> **两者不是替代关系，而是分工关系**：固定报表负责「高频、已知、口径已定」，问数 Agent 负责「长尾、探索、口径待定」。**凡是能固化成报表的需求，就不该留在问数链路里**——报表是零成本、零幻觉、零越权的。

**系统边界**：

| 范围内 | 范围外 |
|---|---|
| 问题理解与澄清 | 数据采集与埋点 |
| 指标语义与口径 | 数仓建模本身 |
| Schema 检索与裁剪 | 数据质量治理 |
| SQL 生成、校验、执行 | 数据库内核 |
| 权限重写与审计 | 统一身份认证 |
| 图表路由与结论表达 | 人工深度分析 |

**核心指标**：

| 类别 | 指标 |
|---|---|
| 正确 | 执行准确率（EX）、有效 SQL 率、完全匹配率（EM）、**口径一致率** |
| 体验 | 首次采纳率、追问率、平均延迟、P95 延迟、**分歧率** |
| 安全 | 越权拦截率、危险 SQL 拦截率、PII 泄露数 |
| 成本 | 单次查询 token、单次查询计算成本、缓存命中率、**结果集回传 token 占比** |
| 质量 | 结果复核率、空结果率、用户满意度 |

**SLO 示例**：

| 指标 | 目标 |
|---|---|
| 简单查询 P95 | < 5s |
| 复杂查询 P95 | < 30s |
| 有效 SQL 率 | > 98% |
| 首次采纳率 | ≥ 55% |
| 越权访问 | **0**（硬约束） |
| 危险 SQL 拦截 | **100%** |
| 审计覆盖率 | **100%** |

**本章专属不可逆决策清单**（做错了要停机迁移 + 数据回填 + 全量对账，不是发个版本就能改）：

| 决策 | 为什么不可逆 | 改动代价 |
|---|---|---|
| **指标的「标准表达式」与口径版本策略** | 口径是所有答案的坐标系；表达式一改，全部历史答案失效 | 历史答案需重新标注口径 + 报表与看板对齐 + 指标版本全量回填 |
| **语义层的命名与作用域模型** | 决定指标能否复用、口径冲突如何裁决 | 全量指标重命名 + 上下游血缘断裂 + 同义词映射重训 |
| **元数据 schema 与 Schema 检索的分层索引结构** | 召回质量与裁剪效果全建立在它上面 | 全量重建索引 + 召回结果突变 + Top-K 命中率重训 |
| **权限的强制技术形态**（数据库策略层 / 视图 / AST 重写） | 决定权限能否绕不过模型 | 全部查询重写逻辑重写 + 历史审计无法回放 + 存量视图迁移 |
| **审计记录的粒度与不可篡改存储选型** | 问数是读操作却会泄露数据，事后补不回「当时查了什么」 | 历史审计无法补齐 + 合规举证出现空洞 |
| **缓存指纹的定义**（问题 + 权限 + 数据版本 + 语义层版本） | 少一个维度就可能给出过期答案或越权答案 | 全量缓存击穿 + 历史答案需重新评估 + 指纹算法变更即全域失效 |
| **SQL 方言与执行引擎的绑定**（Hive / Spark / Presto / ClickHouse） | 生成、校验、自愈、成本模型全部按方言展开 | 全部 Few-shot 与校验规则重写 + 归因 SQL 全量回归 |

> **对照第一章 §1.4.4**：这七项属单向门，决策时要多评审、做原型、留迁移方案。其余（模型选择、Top-K、批大小、超时阈值、缓存 TTL、样本量）是双向门，可以快速试错——但 **Top-K 与样本量属于「可逆但很贵」**：调它们会改变全部历史答案的完整度，必须伴随回归。

### 23.2 核心解读与关键矛盾

**本质**：问数 Agent 的核心矛盾，是「自然语言的模糊性」与「数据库语义的精确性」之间的鸿沟，再叠加「LLM 的概率生成」与「SQL 的确定性执行」。**模型可以猜，账不能猜**——而问数 Agent 恰好是在「猜出来的 SQL」上直接驱动生产数仓。

**六条章级原则**（贯穿全章，冲突时以这六条为准）：

1. **口径在语义层，不在 Prompt 里**——模型只能引用标准指标，不能自创公式。**「模型算出来的」不是口径，「指标卡里写着的」才是口径。**
2. **权限在执行层强制，不靠模型自觉**——查询重写、视图、策略层是硬约束，Prompt 里的「请只查本部门」是软建议。**Prompt 会被注入内容覆盖，策略层不会。**
3. **先下推再回传，绝不靠截断控制上下文**——统计在 SQL 里算完，明细只回传样本。**截断省的是 token，丢的是分布。**
4. **结论必须可回溯到 SQL 与口径**——没有可回溯 SQL 的答案不可信；没有口径的答案不可用。
5. **不确定就降级为「给 SQL 不给结论」**——检索不足、结果异常、口径冲突时，宁可只交 SQL 和原始结果，也不要编一个结论。**「不知道」必须能被识别，不能被润色掉。**
6. **读操作没有回滚，所以防线必须前置**——问数不写业务库，但会泄露数据、打爆数仓、给出错误结论。**这三件事都没有「撤销」按钮，因此校验必须发生在执行之前，而不是之后。**

**三个不等式**：

```
结果集行数    >>  上下文能装的行数     → 靠下推聚合，不靠截断
Schema 规模   >>  Prompt 能承载的规模  → 靠裁剪 + 分层索引
自然语言歧义  >>  SQL 的确定性         → 靠语义层 + 澄清 + 校验
```

**三个放大器**（本章最贵的量都藏在这里）：

| 放大器 | 说明 | 后果 | 量化 |
|---|---|---|---|
| **结果集放大** | 一次查询可能回传几十万行；行放大 × 列放大 | 上下文撑爆 / 结论失真 | 明细直返 **21.6 亿** token/题；下推后 2.16 万，**10 万倍**（§23.3.17） |
| **Schema 放大** | 5000 张表的元数据全进 Prompt | 选错表 + 根本放不下 | 全量 **200 万** token；裁剪后 1500，**1333 倍**（§23.3.9） |
| **口径放大** | 同一个「营收」在多个部门有多种口径 | 答案无法互认、结论对不上会 | 口径版本 × 作用域组合，冲突必须显式裁决（§23.3.8） |

> **本章与第 02、04、05、22 章的放大器方向不同**：Feed 是读放大，秒杀是写放大，广告是三层放大，客服是上下文放大。**问数章的放大器是结果集放大**——它是唯一一个「答案本身太大，把模型挤爆」的架构：进上下文的是 Schema，中间是 SQL，出上下文的是结果集，**三头都在挤压同一个窗口**。

**四层正确性**（必须分开保证，缺一层就有一类错答案）：

| 层次 | 要求 | 保障手段 | 典型漏法 |
|---|---|---|---|
| **口径正确** | 指标、时间、过滤与业务定义一致 | 语义层固化 + 版本 + 作用域 | SQL 语法全对，指标算错了 |
| **SQL 正确** | 语法、Join、聚合、方言 | AST 校验 + 白名单 + 自愈 | 笛卡尔积、少 Join、枚举写错 |
| **权限正确** | 行 / 列 / 租户 / 密级 | 查询重写 + 视图 + 策略层 | 只靠 Prompt 提醒模型 |
| **解读正确** | 不过度推断、不混淆相关与因果 | 归因规范 + 引用 + 人工复核 | 把相关性写成因果 |

**为什么「生成对了 SQL」还不够**：

- **口径可能错**：SQL 语法正确，但指标定义不是业务要的。
- **权限可能错**：查到了不该看的数据。
- **性能可能错**：结果对，但打爆数仓。
- **结果可能残**：SQL 对，但只回传了前 100 行，用户以为这就是全量（§23.3.17）。
- **解读可能错**：数据对，结论错。

> **结论**：**问数 Agent 的正确性是「口径 + SQL + 权限 + 结果完整 + 解读」五层叠加**。原版只列了四层，**漏掉了「结果完整」这一层**——它恰恰是本章放大器最直接的后果，也是最容易被忽略的一类错误。

**八组关键矛盾**：

| 矛盾 | 典型表现 | 默认策略 | 何时反转 |
|---|---|---|---|
| 准确 vs 覆盖 | 只答确定问题准确率高 | 语义层 + 置信度分级 | 探索场景可放宽 |
| 延迟 vs 推理深度 | 多轮自愈慢 | 快路径 + 慢路径 | 复杂归因可接受分钟级 |
| 灵活 vs 受控 | 自由 SQL 灵活但危险 | 语义层 + 模板 + 沙箱 | 专家模式可放开 |
| 口径统一 vs 业务多样 | 各部门口径不同 | 指标版本 + 作用域 | 强治理组织统一 |
| 权限 vs 可用 | 过滤后数据不全 | 明确告知 + 申请流程 | 公开数据可放宽 |
| 成本 vs 质量 | 大模型准但贵 | 模型分级 + 缓存 | 高价值问题可用大模型 |
| 自动化 vs 可解释 | 直接给结论快 | 必须附 SQL / 口径 | 管理层摘要可折叠 |
| 实时 vs 稳定 | 实时数仓贵 | 分层：T+1 / 小时 / 实时 | 强实时业务单独链路 |
| **覆盖 vs 资源** | 什么都能问，但数仓扛不住 | 结果集下推 + 查询预算 | 内部可信场景可放宽 |

**七类失败模式**：

| 失败 | 表现 | 根因 | 防线 |
|---|---|---|---|
| 指标错 | 口径不一致 | 无语义层 | 指标卡 + 版本 + 作用域 |
| 表错 | 选错表 / 视图 | Schema 太大 | Schema Linking + 分层索引 |
| Join 错 | 笛卡尔积、漏 Join | 关系不清 | 元数据 + AST 校验 |
| 过滤错 | 枚举 / 时间写错 | 缺样本 | 枚举抽样 + 澄清 |
| 权限错 | 越权读取 | 只靠 Prompt | 查询重写 / 策略层 |
| 性能错 | 全表扫描、超时 | 无代价评估 | EXPLAIN + 沙箱 + 扫描量上限 |
| **结果残** | **只返回部分行却当成全量** | **用截断代替下推** | **统计 + 样本分离 + 截断标注** |
| 解读错 | 相关当因果 | 过度推断 | 归因规范 + 人工 |

**信任分级**（这是问数 Agent 的「输出契约」，决定了用户敢不敢用）：

| 级别 | 条件 | 展示方式 |
|---|---|---|
| 高 | 命中标准指标 + SQL 校验通过 + 结果校验通过 + 结果未被截断 | 直接给结论 + SQL + 口径 |
| 中 | 指标需推断或存在多口径 | 给结果 + 口径说明 + 待确认标记 |
| 低 | 检索不足 / 结果异常 / 结果已截断 | **只给 SQL 与原始结果，不下结论** |
| 拒绝 | 越权 / 危险 / 资源超限 | 明确拒绝 + 原因 + 可走的替代路径 |

> **「已截断」必须体现在信任级别里**。截断后的结果如果仍按「高」级给出结论，用户会把前 100 行当成全量——**这是本章最隐蔽、也最昂贵的一类错误**，因为它不会报错。

**威胁模型**：

| 威胁 | 路径 | 防线 |
|---|---|---|
| SQL 注入 | 多语句、注释、UNION | AST 白名单 + 参数化 |
| 越权 | 租户 / 行 / 列 | 查询重写 + 视图 + 策略层 |
| 资源耗尽 | 笛卡尔积、全表扫描、递归 CTE | EXPLAIN + 超时 + 扫描量上限 |
| PII 泄露 | 敏感列 / 明细导出 | 列级权限 + 脱敏 + 导出审批 |
| 提示注入 | 问题文本里塞指令（「忽略前面的规则」） | 指令隔离 + 结构化输出 + 判定在代码层 |
| 元数据投毒 | 指标定义 / 表注释被篡改 | 变更审核 + 版本 + 指纹 |
| **口径漂移** | **同名指标被改定义，答案静默变化** | **指标版本 + 口径一致率监控 + 变更公告** |

**成本结构**：

| 成本项 | 占比量级 | 优化手段 |
|---|---|---|
| **结果集回传 token** | **最大（实测约 63% 的输入 token）** | **统计下推、列裁剪、样本替代全量** |
| LLM token（Schema + 指令 + 推理） | 次之 | Schema 裁剪、模型分级、缓存 |
| 数仓计算 | 次之 | 物化视图、结果缓存、查询预算 |
| 向量检索 | 小 | 索引优化、Top-K 控制 |
| 存储 / 审计 | 小 | 分层、TTL |

> **成本表的第一行是本章新增的**。原版把「LLM token」笼统列为最大项，没有拆分**「Schema 侧 token」与「结果集侧 token」**。而实测（§23.3.24）表明**结果集侧占输入 token 的 63%，是 Schema 侧的近 7 倍**。**不区分这两侧，优化就会打错靶子**——很多人拼命压缩 Schema 提示词，却任由几万行的结果集直接进上下文。

### 23.3 理论与方法论

#### 23.3.1 S0：七项前置锚点

先落定七件事，它们共同决定**可行域**——不在可行域内的方案不参与讨论。

| # | 锚点 | 本章答案 | 影响 |
|---|---|---|---|
| 1 | **业务目标与成功标准** | 首次采纳率 ≥ 55%、口径一致率 ≥ 95%、分歧率 ≤ 3%、越权访问 0 | 决定自动化分级与拒答阈值 |
| 2 | **规模量级** | 日问题 50 万、峰值 29 QPS、每题 1.5 次 LLM 调用、**明细类问题占 28%**、单次结果集可达 120 万行 | 决定数仓并发、模型配额与结果集护栏阈值 |
| 3 | **质量属性优先级** | 权限正确 > 口径正确 > SQL 正确 > 结果完整 > 体验 > 成本 | 决定降级顺序与 fail-closed 边界 |
| 4 | **硬约束** | 越权 0；危险 SQL 拦截 100%；只读；PII 最小化与留存期；审计覆盖率 100% | 定义可行域；合规要求不可用技术折抵 |
| 5 | **不可逆决策清单** | 见 §23.1 的本章七项 | 决策流程：多评审 + 原型 + 迁移方案 |
| 6 | **核心路径与事实源** | 核心路径 = 提问 → 澄清 → 语义 → Schema → 生成 → 校验 → 执行 → 结果校验 → 解读；事实源 = **指标卡 + SQL + 查询日志 + 审计** | 决定缓存与对账对象；结果缓存与元数据索引全是投影 |
| 7 | **竞争与协作边界** | 数仓、元数据平台、BI 平台在外部；问数 Agent 自建语义层、生成、校验、解读与审计 | 决定服务边界与团队成本 |

> **第 2 项为什么改变答案**：问数系统的规模参数不只是 QPS，还有**「明细类问题占比」与「单次结果集行数」**。前者决定上下文预算的形状，后者决定结果集护栏的阈值。只给「日 50 万问题」这一个数，算不出任何东西——**50 万个「昨天各渠道订单量」和 50 万个「导出上周全部订单明细」，是两个完全不同的系统**。

#### 23.3.2 4S 收敛顺序

```
S0 定题（锚点 + 不可逆清单）
   → Scenario 定问题量、问题类型分布、明细占比、时效、权限模型
      → Service 定澄清、语义、生成、校验、执行、解读的边界
         → Storage 定指标卡、元数据、查询日志、结果缓存的唯一事实源
            → Scale 定 Schema 裁剪、结果集下推、沙箱、缓存、限流
```

#### 23.3.3 Scenario：场景与规模

| 维度 | 数值 | 推导与来源 |
|---|---|---|
| 日问题量 | 50 万 | — |
| 平均问题 QPS | 50 万 ÷ 86400 | ≈ **5.8** |
| **峰值问题 QPS** | 5.8 × 5 | **29**（峰值系数 5：9:30–11:30 与 20:00–21:30 两个业务高峰承载当日 40%，叠加周一早会脉冲） |
| **问题类型分布** | 取数 70%、分析 25%、归因 5% | **决定是否需要多步归因链路**；取数类可走快路径 |
| **取数类内部拆分** | 聚合 60% / 明细 40% | 明细类合计占 **28%**，是结果集放大的主要来源 |
| 数据规模 | 数仓 5000 张表，核心表 200 张 | 决定 Schema 裁剪与域路由的必要性 |
| 单次结果集行数 | 聚合 5–50 行；明细可达 **120 万行** | **决定结果集护栏阈值与是否必须下推** |
| 每题 LLM 调用 | 平均 1.5 次 | 澄清 25% 触发一次追问；生成 1 次 |
| 时效 | T+1 为主，部分小时级 / 实时 | 决定缓存 TTL 与数据版本策略 |
| 权限模型 | 多租户 + 区域 + 部门 + 列级密级 | 决定查询重写与视图层设计 |
| 合规 | PII 保护、查询审计全量留痕、留存期 | — |

> **「取数类内部拆分」是本章独有的关键参数**。传统系统的容量参数是 QPS，问数系统还必须给出**明细类问题占比**——因为它是唯一能把「一次查询 120 万行」放进系统的入口，占比每上升 1 个百分点，日上下文 token 就会涨约 0.36 亿。

#### 23.3.4 Service：服务与接口

| 服务 | 职责 | 同步 / 异步 | 关键点 |
|---|---|---|---|
| Question Service | 会话、澄清、意图分类 | 同步 | 多轮状态、`confirmed_slots` |
| Semantic Service | 指标、维度、口径、作用域 | 同步 | **版本化、冲突裁决** |
| Metadata Service | 表 / 列 / 血缘 / 枚举 / PII | 同步 | 新鲜度、血缘可信度 |
| Schema Retriever | 表列召回与裁剪 | 同步 | 向量 + 关键词 + Join 历史 + 域路由 |
| SQL Generator | SQL 生成 | 同步 | 结构化输出、方言适配 |
| SQL Validator | AST、白名单、权限重写、代价预估 | 同步 | **规则在代码层** |
| Query Executor | 沙箱执行 | 同步 / 异步 | 资源组、超时、扫描量上限 |
| Result Guard | 结果集裁剪与形状判定 | 同步 | **统计 + 样本分离** |
| Result Validator | 结果校验 | 同步 | 一致性、空值、异常、截断标注 |
| Chart / Attribution Service | 图表路由、贡献度拆解 | 同步 / 异步 | 下推优先 |
| Answer Composer | 结论 + SQL + 口径 + 注意 | 同步 | 置信度分级 |
| Audit Service | 全量审计 | 异步 | 不可篡改 |
| Budget Service | token / 扫描量 / 结果行数 / 时长预算 | 同步 | 超预算即降级 |

**核心 API**：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/ask` | 提问，返回答案或澄清 |
| POST | `/api/v1/ask/{id}/clarify` | 补充澄清信息 |
| GET | `/api/v1/ask/{id}` | 查询结果与状态 |
| GET | `/api/v1/metrics` | 指标列表与口径 |
| GET | `/api/v1/metrics/{name}/versions` | 指标历史版本与生效时间 |
| POST | `/api/v1/queries/{id}/export` | 导出（**独立审批链路，不在问数链路内**） |

> **`export` 为什么单独拆出来**：明细导出是问数链路上唯一一个「结果集大小不受控」的出口，也是唯一一个「绕过 Schema 裁剪与结果集下推」的出口。它必须走独立的审批、水印与限量流程，**绝不能作为问数的一个普通 API 参数**存在。

#### 23.3.5 Storage：数据模型

| 数据 | 存储 | 关键设计 | 是事实源吗 |
|---|---|---|---|
| 指标定义 | 元数据服务 / DB | 名称、表达式、版本、owner、作用域 | **是** |
| 表 / 列元数据 | 元数据服务 | 注释、类型、枚举、血缘、PII 标签 | **是** |
| 查询会话 | Redis / DB | 多轮上下文、已确认槽位 | 否（可重建） |
| 查询日志 | 数仓 / 日志 | SQL、耗时、扫描量、行数、用户 | **是** |
| 结果缓存 | Redis / 对象存储 | **四元指纹**（见 §23.3.22） | 否（可重建） |
| 向量索引 | 向量库 | 元数据 embedding + 版本 | 否（可重建） |
| 审计 | 不可篡改存储 | 谁、何时、问了什么、查了什么、改写前后 SQL | **是** |

> **区分事实源与投影是本章的基本功**。指标卡、元数据、查询日志、审计是事实源；会话、缓存、向量索引全是投影，可以丢、可以重建、可以随时重建。**投影丢了不致命，事实源丢了就没有回溯能力**——而问数系统的价值恰恰在于「三年前有人问过什么、查到了什么、当时的口径是哪一版」。

**指标卡结构**：

| 字段 | 说明 |
|---|---|
| `metric_id` | 稳定 ID，**跨版本不变**（改名不改 ID） |
| `name` / `synonyms` | 指标名与同义词、口语映射 |
| `definition` | 业务定义（人读） |
| `sql_expression` | 标准 SQL 表达式（机器读） |
| `dimensions` | 可用维度 |
| `time_grain` | 支持的时间粒度与时区 |
| `scope` | 适用业务 / 部门 / 租户（**口径冲突的裁决依据**） |
| `owner` | 负责人 |
| `version` / `effective_from` | 版本与生效时间 |
| `lineage` | 上游表与依赖 |
| `caveats` | 使用注意（如「不含内部单」） |
| `policies` | 密级、行级过滤策略引用 |

> **`metric_id` 与 `name` 分离是本章新增的一条硬要求**。一旦允许「改名字不改语义」或「改语义不改名字」，历史答案的口径就无法回指——**口径版本化会立刻失效**。

#### 23.3.6 Scale：扩展与兜底

| 维度 | 手段 | 触发条件 |
|---|---|---|
| Schema | 分层裁剪、域路由、Top-K | 表太多、上下文超限 |
| 结果集 | **统计下推、列裁剪、样本替代** | 回传行数超阈值 |
| 生成 | 模型分级、问题缓存 | token 成本高 |
| 执行 | 只读副本、资源组、队列 | 数仓并发压力 |
| 结果 | 结果缓存、物化视图 | 重复问题多 |
| 权限 | 预计算视图、策略层 | 行级过滤复杂 |
| 降级 | 模板查询、保存问题、策展表集合 | 模型 / 数仓 / 元数据故障 |

#### 23.3.7 语义层与指标治理

**本节是语义层与指标治理的权威版**，§23.4.3、§23.5 只引用。

**三类对象**：

| 对象 | 示例 | 作用 |
|---|---|---|
| Measure | 净营收、GMV、客单价、退款率 | 可聚合的数值 |
| Dimension | 时间、地区、渠道、品类、租户 | 分组维度 |
| Time Grain | 自然日 / 周 / 财周、时区、截止时点 | 时间口径 |

**计算逻辑示例**：

```
净营收 = 含税销售额 - 退货冲减 - 折扣补贴
排除：测试单、未结算单、内部单
```

**治理规则**：

- Agent 只能引用标准指标，不能自创公式；探索性公式必须显式标记「非标准」。
- 指标变更走评审，保留版本与生效时间，旧版本不删除。
- 指标卡带 owner 与血缘，出问题可追溯到人。
- 同义词与口语映射到标准指标（「销售额」→「净营收」**需用户确认**，因为这是口径选择而不是措辞问题）。
- **指标定义变更后，所有依赖它的固定报表与看板必须同步评审**——否则语义层与报表层会分叉。

> **语义层不是「指标字典」，是「口径的执行版本」**。区别在于：指标字典描述「净营收是什么」，语义层**规定**「在这个系统里，净营收只能这样算、这样取、这样授权」。前者是文档，后者是约束。

#### 23.3.8 口径冲突与作用域

**本节是口径冲突裁决的权威版**，§23.4.3 只引用。

**冲突的三个来源**：

| 来源 | 表现 | 例 |
|---|---|---|
| 定义不同 | 同一指标名，两套算法 | 财务的「营收」含税，运营的「营收」不含税 |
| 范围不同 | 同一算法，不同过滤 | 「GMV」是否含未支付订单 |
| 粒度不同 | 同一指标，聚合口径不同 | 「日活」是去重设备还是去重用户 |

**裁决顺序（固定，不随上下文变化）**：

```
1. 用户所属租户 / 部门的强制口径   ← 最高优先级
2. 指标的 scope 作用域匹配
3. 平台默认口径
4. 若仍无法判定 → 列出候选口径让用户选，绝不默认
```

**答案里必须携带的口径元信息**：

| 字段 | 例 |
|---|---|
| 指标 ID 与版本 | `net_revenue@v2.3` |
| 生效时间 | 2026-01-01 起生效 |
| 作用域 | 华东区 / 财务口径 |
| 排除项 | 测试单、未结算单 |
| 时间口径 | 自然日，Asia/Shanghai，含当日未结算 |
| 数据截止时点 | T+1，2026-11-24 06:00 数据就绪 |

**口径冲突的三个处理动作**：

| 场景 | 动作 |
|---|---|
| 能按作用域唯一确定 | 直接用，**在答案中注明版本与作用域** |
| 有多个候选 | **列出候选让用户选**，不静默选一个 |
| 同名但完全不同义 | **判定为口径冲突并拒绝自动作答**，提示联系指标 owner |

> **「口径冲突时默认选一个」是本章最不可接受的错误**。它不会报错、不会超时、SQL 也能正常执行——但它会安静地给出一个「看起来完全合理但业务上是错的」数字。**这类错误比失败可怕一百倍**：失败会被人发现，错误的数字会被拿去做决策。

#### 23.3.9 Schema 裁剪（Schema Linking）

**本节是 Schema 裁剪的权威版**，§23.4.3 只引用。

**元数据维度**：

| 维度 | 用途 |
|---|---|
| 表 / 列注释 | 语义匹配 |
| 主外键 | Join 路径 |
| 枚举值抽样 | 过滤条件 |
| 基数 | 判断聚合粒度 |
| 新鲜度 | 避免用过期表 |
| PII 标签 | 权限与脱敏 |
| 血缘 | 选上游 / 下游表 |
| 业务域标签 | 域路由 |

**检索策略（五路并行，合并去重）**：

1. **语义检索**：问题 → 表 / 列描述向量召回。
2. **关键词检索**：专有名词、编号、字段名精确匹配。
3. **历史 Join 路径**：相似问题用过的关系（命中率最高的一路）。
4. **相似问题缓存**：命中直接复用表集合。
5. **业务域路由**：先定位域，再在域内检索。

**裁剪原则**：

- 只暴露 Top-K 表与关键列，降低噪音。
- 大表只给常用列与分区键。
- 枚举值给抽样，不给全量。
- 敏感列默认不暴露给模型（**不是「暴露了再要求模型别用」**）。

**Schema 放大有多严重**（量化）：

```
全量 Schema = 5000 张表 × (表级描述 100 token + 15 列 × 20 token)
            = 5000 × 400 = 200 万 token
上下文窗口 ≈ 200K token → 放不下，且噪声会让召回精度崩塌

裁剪后 = Top-5 表 × (100 + 10 列 × 20) = 5 × 300 = 1500 token
放大倍数 = 200 万 / 1500 = 1333 倍
```

> **1333 倍这个数字要说明两件事**：第一，**不裁剪不是「贵一点」，而是「根本不可行」**——200 万 token 远超任何模型的上下文窗口；第二，裁剪不只是省 token，**它同时是召回精度的手段**：5000 张表进 Prompt，Top-1 命中率会低到无法使用。**Schema 裁剪是可行性需求，不是成本优化项。**

**裁剪的三层漏斗**：

| 层 | 手段 | 典型收敛比 |
|---|---|---|
| 域路由 | 先定业务域 | 5000 → 200 |
| 表召回 | 向量 + 关键词 + 历史路径 | 200 → 20 |
| 列裁剪 | 关键列 + 分区键 + 抽样枚举 | 20 表 × 40 列 → 5 表 × 10 列 |

#### 23.3.10 问题分类与澄清

| 类型 | 示例 | 路由 |
|---|---|---|
| 简单取数 | 「昨天华东订单量」 | 快路径，直接生成 |
| 多维分析 | 「各渠道转化率对比」 | 标准 SQL + 图表 |
| 归因 | 「为什么下降」 | 慢路径，多步分析 |
| 口径咨询 | 「净营收怎么算」 | **查指标卡，不查库** |
| 明细导出 | 「导出上周全部订单」 | **走独立导出审批链路** |
| 闲聊 / 越界 | 「帮我写周报」 | 拒绝或转人工 |

> **两类问题必须被识别出来并从主链路分流**：**口径咨询**根本不该生成 SQL（查指标卡即可，省掉整个数仓链路）；**明细导出**根本不该留在问数链路里（结果集不可控、权限与合规要求不同）。**把它们混在同一条流水线里，是很多问数系统后期失控的根因。**

**何时追问**：

- 指标不明确（营收 vs 净营收）。
- 时间范围缺失或模糊（「最近」）。
- 实体不明确（「华东」是否含某省）。
- **口径冲突（多版本 / 多作用域）**。
- 权限范围影响结果。

**何时用默认值**：

- 低风险、可撤销、有明确惯例。
- 默认值必须在答案中**显著注明**。

**多轮澄清**：保留 `confirmed_slots`（指标、时间、实体、过滤、粒度），后续轮次复用，避免重复问。

#### 23.3.11 澄清成本 vs 错误成本

追问一次的成本是可量化的，而错误答案的成本往往不可量化——**这正是必须写进方案的判据**。

**澄清成本**：

| 项 | 数值 | 说明 |
|---|---|---|
| 额外 LLM 调用 | 1 次 | 输入 ~1000 token（已确认槽位 + 问题） |
| token 成本 | ≈ 2,000 token | 按输入 ¥2 / 百万计，约 ¥0.004 |
| 额外延迟 | +1.5s | 一次生成调用 |
| 用户耐心消耗 | 1 次 | 追问 2 次以上，转人工率显著上升 |
| 口径风险 | **0** | 槽位确认后写入，后续复用 |

**错误答案的成本**：

| 项 | 量级 | 说明 |
|---|---|---|
| 直接成本 | 视决策金额而定 | 错误的投放 / 库存 / 人力决策 |
| 信任成本 | 高且不可逆 | 一次错答被识破，采纳率长期下降 |
| 复核成本 | 每次 +1 人天 | 分析师复核 + 沟通 + 纠正 |
| 权限成本 | 不可估 | 越权口径泄露属于合规事故 |

**判据**：

```
追问成本（¥0.004 + 1.5s）  <<  错误成本（≥ 1 人天复核 + 决策损失 + 信任损失）
                                    → 追问

口径可由作用域唯一确定                →  不追问，直接答 + 注明版本
```

**澄清决策链路**：

```
追问一次的成本（实测）
  → 2,000 token + 1.5s + 一次用户耐心（≈ ¥0.004）
  → 对照：错误答案 ≥ 1 人天复核 + 决策损失 + 信任损失（不可逆）
  → 结论：口径不确定时，追问永远划算
  → 但上限 1 次（同一问题）—— 追问 2 次以上，用户会直接转人工
  → 一次问全所有必要槽位，不挤牙膏
```

> **三个必须记住的推论**：
> 1. **追问几乎是零成本的**：一次追问不到半分钱，而一次错误答案至少一个人天。**口径不确定时，追问永远是划算的**。
> 2. **但追问有次数上限**：连续追问 2 次以上，用户会放弃并转人工。所以应当**一次问全所有必要槽位**，而不是挤牙膏。
> 3. **可以用默认值替代追问的只有一种情况**：默认值既符合惯例、又被显式注明、且用户能一眼看出并纠正。其余情况都要追问。

#### 23.3.12 SQL 生成

**Prompt 结构**：

```
System：角色、约束、输出格式、安全规则
Context：指标定义（含版本）、裁剪后 Schema、枚举样本、方言、业务规则
Examples：按问题类型检索的 Few-shot
Question：用户问题 + 已确认槽位
Output：JSON { sql, explanation, assumptions, confidence, metrics_used }
```

**生成约束**：

- 只输出 `SELECT` / `WITH`。
- 禁止 `SELECT *`，必须显式列。
- 必须带时间过滤（除非用户明确全量）。
- **默认带聚合**：除非问题明确要明细，否则强制 `GROUP BY` 或聚合函数（§23.3.17）。
- 自动加 `LIMIT`。
- 使用标准 Join，禁止隐式笛卡尔积。
- 方言适配（MySQL / PostgreSQL / Hive / Spark / ClickHouse）。
- **必须声明所用指标**（`metrics_used`），供下游做口径核对。

**Few-shot 选择**：按问题类型（单表、多表、聚合、窗口、同比、贡献度）检索相似样例；**样例必须是本方言、本指标版本下验证过的**。

> **`metrics_used` 是一个成本极低、价值极高的字段**：它让下游可以在生成阶段就核对「这个 SQL 用的是不是标准指标口径」，而不是等到结果出来再靠人肉看 SQL。**它在错误还没变成一个数字之前就把错误拦下了。**

#### 23.3.13 SQL 校验与权限重写

**本节是 SQL 校验与权限重写的权威版**，§23.4.4 只引用。

| 校验 | 内容 | 拦截还是改写 |
|---|---|---|
| 语法 | AST 解析成功 | 拦截 |
| 语句类型 | 仅 `SELECT` / `WITH` | 拦截 |
| 危险操作 | DDL / DML / 多语句 / 注释注入 | 拦截 |
| 函数 | 黑名单（文件、系统、网络、反射类） | 拦截 |
| 对象 | 表 / 列存在且在白名单内 | 拦截 |
| Join | 必须有连接条件，防笛卡尔积 | 拦截 |
| 权限 | 注入行级条件、列级过滤 | **改写** |
| 资源 | 自动 LIMIT、扫描量预估 | 改写 |
| 代价 | EXPLAIN 预估，超阈值拒绝或改写 | 拦截 / 改写 |

**权限重写示例**：

```sql
-- 原始
SELECT region, SUM(amount) FROM orders GROUP BY region;

-- 重写后（用户仅华东）
SELECT region, SUM(amount) FROM orders
WHERE tenant_id = 42 AND region = 'east'
GROUP BY region;
```

**权限强制链路**：

```
原始 SQL（模型生成）
  → AST 解析（失败即拦截，不给模型解释机会）
  → 语义校验（表列白名单、Join 条件、聚合合法性）
  → 权限重写（行级 WHERE 注入 + 列级白名单裁剪 + 密级掩码）
  → 资源改写（LIMIT 注入、扫描量预估、超阈值改写或拒绝）
  → 方言编译（转为目标引擎可执行计划）
  → 送入只读沙箱执行
```

**为什么必须在执行层**：Prompt 里的「请只查本部门」可以被注入或忽略；**只有重写 / 视图 / 策略层才是强制约束**。而且模型是概率性的——即使 Prompt 写对了，同一输入也可能生成一条漏掉租户条件的 SQL。**依赖模型守规矩的系统，迟早会漏一次。**

#### 23.3.14 沙箱执行与资源护栏

| 措施 | 说明 | 参考阈值 |
|---|---|---|
| 只读副本 | 与生产隔离 | 独立资源组 |
| 独立资源组 | 限制 CPU / 内存 / 并发 | 问数专用队列 |
| Statement Timeout | 防长查询 | 简单 15s / 复杂 60s |
| 最大返回行数 | 防大结果集 | **10 万行（硬限）** |
| 最大扫描量 | 防全表扫描 | **100 GB（硬限）** |
| 并发上限 | 防打爆数仓 | 峰值 360 并发 → 配额 300 |
| 查询队列 | 削峰 | 按复杂度分优先级 |
| Kill 机制 | 超资源强制终止 | 到限即杀，不等自然结束 |
| 成本预估拦截 | EXPLAIN 超阈值直接拒绝 | 提前于执行阻断 |

> **最大返回行数与最大扫描量是两个不同的闸**：扫描量拦的是「代价高但结果小」的查询（一次全表聚合），返回行数拦的是「代价中等但结果巨大」的查询（明细导出）。**只设其中一个，另一个方向就会被打爆。**

#### 23.3.15 报错自愈

```
执行失败
  → 分类错误：语法 / 语义 / 权限 / 资源 / 超时
  → 语法 / 语义：把报错 + 相关 Schema 回填，重新生成
  → 权限：不重试，直接拒绝并提示
  → 资源 / 超时：缩小范围或改写，最多 1 次
  → 超过最大重试（2–3 次）：返回可解释错误或转人工
```

**自愈的安全边界**：自愈**只能改写「怎么查」，不能改写「查什么」**——重试时可以调整时间范围、分区裁剪、Join 顺序、聚合粒度，**但不得放宽行级权限、不得去掉用户确认过的过滤条件、不得把聚合改回明细全量**。放宽语义的自愈会变成权限绕过。

**失败样本沉淀**：记录错误 SQL、报错、修正结果，用于优化 Schema 描述与 Few-shot；**同时按错误类型统计 Top-N**——「枚举写错」占比高说明枚举样本要给全；「表选错」占比高说明域路由有问题。

#### 23.3.16 结果校验

| 校验 | 说明 | 不通过时 |
|---|---|---|
| 行数 | 空结果是否合理 | 区分「无数据」与「过滤错」 |
| 列类型 | 数值 / 时间 / 字符串是否符合预期 | 拒绝或降级 |
| 空值 / NaN | 比例是否异常 | 标注 |
| 口径一致性 | 分项之和是否等于总计 | 拒绝 |
| 异常值 | 同比 / 环比是否超阈值 | 标注 + 提示复核 |
| 二次核对 | 关键结论用另一条 SQL 验证 | 降级为只给 SQL |
| **截断检测** | **本次结果是否被截断 / 是否为部分结果** | **标注 + 降低信任级别** |

**空结果处理**：区分「确实没有数据」与「过滤条件写错」；后者应触发澄清或自愈。**空结果绝不能当成「答案是 0」**。

#### 23.3.17 结果集治理与下推

**本节是结果集治理的权威版**，§23.4.6、§23.5.5 只引用。

**三段漏斗**：问数系统的上下文被三头夹住——进来的 Schema、生成的 SQL、回去的结果集。

```
扫描量（数仓成本）  →  结果集行数（上下文成本）  →  进上下文的 token（模型成本）
   120 万行              120 万行                    120 万行 × 180 token = 2.16 亿
```

**结果集放大**（本章的签名量）：

场景：订单明细查询，`orders` 宽表 120 列，筛选后 **120 万行**；单行序列化后显式 12 列 = 180 token，全列 `SELECT *` = 1800 token。

| 策略 | 回传行数 | 单行 token | 上下文 token | 分布是否完整 |
|---|---|---|---|---|
| 明细直返 + `SELECT *` | 120 万 | 1800 | **21.6 亿** | 完整但**物理不可行** |
| 明细直返 + 显式列 | 120 万 | 180 | **2.16 亿** | 完整但**物理不可行** |
| `LIMIT 100` 截断 | 100 | 180 | 1.8 万 | **不完整**（尾部分布丢失） |
| **统计下推 + 显式列 + 样本 100** | 120 | 180 | **2.16 万** | **完整** |

**两个放大维度**：

| 维度 | 放大 | 治理手段 |
|---|---|---|
| **行放大** | 120 万行 / 120 行 = **10,000×** | 聚合下推、样本替代、分位数在 SQL 内计算 |
| **列放大** | 1800 token / 180 token = **10×** | 禁 `SELECT *`、显式列白名单、敏感列不暴露 |
| **合计** | **100,000×** | — |

> **两条必须写进方案的结论**：
> 1. **「截断」和「下推」的 token 几乎一样（1.8 万 vs 2.16 万，只差 20%），但结论完整性完全不同。** 截断把「订单金额的 P99」从全量分布变成前 100 行的分布——**结论完整性不是一个能用 token 衡量的量**。所以控制上下文的正确做法是**下推**，绝不是截断。
> 2. **行放大（10,000×）比列放大（10×）严重三个数量级。** 这意味着治理重心是「别把那么多行带回来」，而不是「少查几列」。**很多团队把力气花在列裁剪上，因为列裁剪容易看见；真正会爆的是行。**

**结果集放大的四段漏斗**：

```
明细直返 + SELECT *        21.6 亿 token   ← 不可行
明细直返 + 显式列           2.16 亿 token   ← 仍不可行
截断 LIMIT 100              1.8 万 token    ← 可行但结论残
统计下推 + 显式列 + 样本     2.16 万 token    ← 可行且结论完整
```

**下推算子清单**（都要在 SQL 里算完，不要拉回本地再算）：

| 算子 | SQL 写法 | 替代了什么 |
|---|---|---|
| 计数 | `COUNT(*)` | 全量行 |
| 汇总 | `SUM` / `AVG` / `MIN` / `MAX` | 全量行 |
| 分位数 | `PERCENTILE_APPROX` / `NTILE` | 排序全部行 |
| 直方图 | 按分桶 `GROUP BY bucket` | 全部原始行 |
| Top-N 分组 | `ORDER BY v DESC LIMIT N` | 全部分组 |
| 占比 | `SUM(v) / SUM(SUM(v)) OVER ()` | 交叉计算 |
| 环比 / 同比 | 窗口函数 `LAG` / 自连接 | 两期全量 |

**明细问题的标准返回结构**（把「统计」与「样本」在协议层就分开）：

```json
{
  "stats":       { "row_count": 1200000, "sum": 0, "p50": 0, "p90": 0, "p99": 0 },
  "histogram":   [ { "bucket": "0-100", "count": 0 } ],
  "top_groups":  [ { "key": "channel_a", "value": 0 } ],
  "sample_rows": [ { "...": "..." } ],
  "sample_size": 100,
  "truncated":   true
}
```

> `truncated: true` 必须在协议层存在，并且直接驱动信任级别（§23.2）。**「模型看到的样本」和「用户看到的结论」必须是同一个数据契约的两端**——只要中间少了一个字段，截断就会静默发生。

**结果集护栏三层**：

| 层 | 手段 | 阈值参考 |
|---|---|---|
| **生成层** | 默认聚合、禁 `SELECT *`、显式列、强制 LIMIT | 明细类须显式声明 |
| **执行层** | 最大返回行数 10 万、最大扫描量 100GB、并发上限 | 硬限，到限即拒 |
| **回传层** | 统计 + 样本分离、列裁剪、分位数下推 | 单次回传 ≤ 32K token |

**什么时候允许明细全量返回**：只有三种情况——用户明确申请导出（走独立审批链路）、问题本身就是「导出行级明细」且行数在 1000 以内、以及分析 / 归因链路中的中间结果（且必须先聚合再回传）。**其余一律走「统计 + 样本」。**

#### 23.3.18 权限模型

| 层级 | 方案 | 强制位置 |
|---|---|---|
| 租户 | 强制 `tenant_id` 过滤 | 策略层 / 重写 |
| 行级 | 查询重写 / 视图 / 策略层 | 策略层 / 重写 |
| 列级 | 掩码 / 拦截 / 不暴露 Schema | 重写 + 检索 |
| 数据密级 | 按标签授权 | 策略层 |
| 导出 | 单独审批、水印、限量 | 独立链路 |
| 审计 | 全量记录（含改写前后 SQL） | 审计服务 |

**实现优先级**：数据库视图 / 策略层 > 查询重写 > 应用层过滤。Prompt 提示只能作为辅助。

**列级权限与 Schema 裁剪的联动**：敏感列**默认不进入给模型的 Schema**。这不是「优化」，而是安全边界——**模型看不到的列，就不可能被写进 SQL**。等执行层再拦截，等于依赖模型不犯错。

#### 23.3.19 可视化路由与结论表达

| 结果形状 | 图表 |
|---|---|
| 单值 | KPI 卡片 |
| 时间序列 | 折线 |
| 分类对比 | 柱状 |
| 构成占比 | 堆叠柱（慎用饼图） |
| 明细 | 表格（**默认只展示样本 + 统计**） |
| 分布 | 直方图（**来自 SQL 聚合，不是前端现算**） |
| 相关性 | 散点 |

**结论表达的四件套**（缺一件都不算合格答案）：

```
1. 结论（可核验的数字）
2. 口径（指标 ID + 版本 + 作用域 + 时间口径 + 数据截止时点）
3. SQL（可复制、可审计）
4. 注意事项（截断、排除项、假设、待验证）
```

**禁止的表达**：

- 把相关系数直接表述为因果。
- 把部分结果表述为全部（「前 100 行显示…」必须写出来）。
- 把非标准口径的探索公式表述为公司口径。
- 在结果被截断时给出确定性结论。

#### 23.3.20 归因分析

| 方法 | 说明 | 注意 |
|---|---|---|
| 同比 / 环比 | 与上期对比 | 注意基期效应（春节 / 大促） |
| 维度下钻 | 按地区 / 渠道 / 品类拆 | **避免维度爆炸**（见下） |
| 贡献度 | 各维度对总变化的贡献 | 加法 / 乘法分解不同 |
| 结构分析 | mix 变化 vs 单价变化 | 辛普森悖论 |
| 相关性 | 找候选因素 | 不等于因果 |

**三种分解方式**：

| 方式 | 公式 | 适用 |
|---|---|---|
| 加法分解 | Δ总 = Σ Δ维度 | 可加指标（销售额、订单量） |
| 乘法分解 | Δ总 = Δ量 × 价 + Δ价 × 量 + 交叉项 | 乘积指标（GMV = 价 × 量） |
| 结构分解 | Δ总 = Σ (mix 变化) + Σ (单价变化) | 指标可拆成「量 × 价」 |

**维度爆炸与解法**：

```
地区(8) × 渠道(6) × 品类(20) = 960 行
直接回传 960 行 × 180 token = 17.3 万 token   ← 又一次结果集放大
解法：贡献度在 SQL 里算完，只回传 Top-20 贡献行 = 3,600 token（省 48 倍）
```

**辛普森悖论的具体形态**：

> 整体退款率从 3.0% 升到 3.6%，看似恶化。但按渠道拆开，A/B/C 三个渠道的退款率**全部下降**（3.2%→3.1%、2.8%→2.7%、3.1%→3.0%）。真正原因是**高退款率渠道 D 的订单占比从 20% 升到 32%**——**整体上升不是任何渠道变差，是结构变了**。
>
> **这正是「不标注假设」最贵的时刻**：一句「渠道 D 变差了」会让运营去「优化 D」，而 D 什么都没做错。**归因结论必须先做结构校验，再下结论。**

**归因结论模板**：

```
总变化 X%
  → 按维度 A 拆解：A1 贡献 a%，A2 贡献 b%
  → 按维度 B 拆解：B1 贡献 c%
  → 交叉定位：A1 × B1 贡献最大
  → 结构校验：各子项是否同向？（辛普森检查）
  → 可能原因（待验证）：……
```

#### 23.3.21 评测方法

**离线评测**：

- 黄金集：问题 + 标准 SQL + 标准结果 + 指标版本。
- 指标：

| 指标 | 定义 | 局限 |
|---|---|---|
| 执行准确率（EX） | 分别执行生成 SQL 与标准 SQL，比较结果集 | **不区分「等价 SQL」与「偶然相同」** |
| 有效 SQL 率 | 能成功执行的比例 | 成功不等于正确 |
| 完全匹配率（EM） | SQL 结构完全一致 | **过严**，等价写法会被判错 |
| 组件指标 | Schema Linking / Join / 过滤条件准确率 | 便于定位 |
| **口径正确率** | 所用指标版本与黄金集一致 | **原版缺失，必须补** |

> **只评 EM 是最常见的评测错误**：同一份结果可以由十几条等价 SQL 得到（别名、CTE 写法、子查询改写），EM 会把这些全判错；而 EM 相同的结果集也可能口径不同。**评测的主指标必须是 EX，口径正确率单独看，EM 只能作为回归报警的辅助信号。**

**在线评测**：

| 指标 | 说明 | 用途 |
|---|---|---|
| 首次采纳率 | 用户不追问、不改写就用结果 | 最贴近真实价值 |
| 追问率 | 澄清轮数分布 | 口径歧义的直接信号 |
| **分歧率** | 同一问题在不同时间 / 不同人得到不同数值或不同口径版本 | **口径一致性的在线代理指标** |
| 空结果率 | 结果为空的占比 | 过滤条件写错的信号 |
| P95 延迟 | 端到端 | 体验 |
| 单次成本 | token + 计算 | 成本 |
| 用户满意度 | 点赞 / 点踩 / 举报 | 最终裁决 |

> **分歧率是本章新增的在线指标**：同一个「上周华东净营收」今天和下个月由两个分析师问出不同数字，**说明口径漂了或数据版本不一致**。它是「口径一致率」在生产环境唯一可行的代理——因为生产环境不可能人工标注每一个答案的口径。

**安全评测**：注入、越权、危险函数、PII、资源耗尽、资源组隔离（**不能打穿到数仓其他租户**）。

#### 23.3.22 缓存与数据版本

**缓存指纹必须是四元组**，缺一维就会给出错误答案：

```
cache_key = hash(问题指纹 + 权限指纹 + 数据版本 + 语义层版本)
```

| 维度 | 含义 | 缺失的后果 |
|---|---|---|
| 问题指纹 | 归一化后的问题 + 已确认槽位 | 命中不相干的问题 |
| 权限指纹 | 用户 / 租户 / 角色 / 生效的过滤条件 | **越权泄露** |
| 数据版本 | 分区版本 / 快照 ID / 指标物化批次 | **给出过期答案**（最常见） |
| 语义层版本 | 指标卡版本集合 | 口径漂移，答案静默变化 |

**TTL 分层**：

| 数据层 | TTL | 理由 |
|---|---|---|
| 实时表 | 1–5 分钟 | 数据在变 |
| 小时级物化 | 1 小时 | 批次对齐 |
| T+1 事实表 | 到次日分区就绪 | 口径与数据同时固定 |
| 指标聚合层 | 1 小时 | 随上游批次失效 |
| **指标定义（语义层）** | **变更即刻失效** | **口径变了，旧答案不再成立** |

> **最危险的一种错误是「数据版本缺失」**：缓存命中后返回了昨天的分区数据，但用户不知道它来自昨天——**答案看起来完全正常，只是过时了**。问数系统的使用者往往不会去核对时间戳，**所以过期必须被显式标注，而不是被隐藏**。

#### 23.3.23 成本模型

| 手段 | 说明 | 本章收益量级 |
|---|---|---|
| **结果集下推** | 统计在 SQL 里算完 | **最大杠杆**（结果集占输入 token 的 63%） |
| 问题 / SQL 缓存 | 命中直接返回 | 约 20%（取决于重复率） |
| 模型分级 | 小模型做意图 / 路由与简单 SQL | 约 14% |
| 早停 | 置信度高不重试 | 约 8% |
| Schema 裁剪 | 只给相关表列 | 可行性刚需 + 整题输入约 2% |
| 结果缓存 | 四元指纹 | 与上面重叠，避免重复计入 |
| 物化视图 | 高频聚合预计算 | **token 不省，但同时降扫描量与结果集行数** |
| 查询预算 | 每用户 / 租户配额 | 防止单租户吃满 |

> **成本优化要分两条轨道，不能排成一条队**。**上下文 token 侧**（结果集下推 → 缓存 → 模型分级 → 早停 → Schema 裁剪）省的是模型账单；**数仓计算侧**（物化视图 → 结果缓存 → 查询预算）省的是扫描量账单——**后者在问数系统里通常更大**，却一分钱 token 都省不了。原版把「Schema 裁剪」列为第一手段，但实测显示结果集侧的 token 是 Schema 侧的近 7 倍。**先削大头，两条轨道分开算。**

#### 23.3.24 容量与成本估算

**本节是容量口径的权威版**，§23.5 与 §23.6 只引用。

**假设**：日问题 50 万，峰值系数 5，每题平均 1.5 次 LLM 调用；基线输入 4000 token/次（system 600 + 指标卡 1200 + 裁剪后 Schema 1500 + 会话历史 400 + 输出预留 300）；输出 500 token/次；单行结果序列化 180 token（显式 12 列）；结果集回传行数：聚合类 20 行、明细类 120 行（统计 20 + 样本 100）、分析归因类 50 行；模型价格输入 ¥2 / 百万 token、输出 ¥8 / 百万 token。

**一、流量与并发**

| 指标 | 计算 | 结果 |
|---|---|---|
| 平均问题 QPS | 50 万 ÷ 86400 | ≈ **5.8** |
| **峰值问题 QPS** | 5.8 × 5 | **29** |
| **峰值 LLM 调用 QPS** | 29 × 1.5 | **44** |
| 并发查询（简单查询 70%，P95 5s） | 29 × 0.7 × 5 | ≈ 102 |
| 并发查询（分析归因 30%，P95 30s） | 29 × 0.3 × 30 | ≈ 261 |
| **峰值并发查询合计** | — | **≈ 360**（配额按 300 留余量） |

**二、上下文与 token**

| 指标 | 计算 | 结果 |
|---|---|---|
| 每题基线输入 token | 1.5 × 4000 | 6,000 |
| 每题结果集回传 token | 0.42×3,600 + 0.28×21,600 + 0.30×9,000 | **10,260** |
| **每题输入 token 合计** | 6,000 + 10,260 | **16,260** |
| **其中结果集占比** | 10,260 ÷ 16,260 | **63%** |
| 每题输出 token | 1.5 × 500 | 750 |
| **日输入 token** | 16,260 × 50 万 | **81.3 亿** |
| 日输出 token | 750 × 50 万 | **3.75 亿** |
| **日合计 token** | — | **85 亿** |
| 输入成本 | 8,130 百万 × ¥2 | ¥16,260 |
| 输出成本 | 375 百万 × ¥8 | ¥3,000 |
| **日 LLM 成本** | — | **≈ ¥19,300**（约 **58 万元 / 月**） |

> **这一节最重要的一个数字是 63%**：**结果集占了输入 token 的近三分之二，而 Schema 只占 1500 / 16260 ≈ 9%。** 原版的成本模型只估了「LLM token 总量」，没有拆分这两侧，因此优化方向指错了——**真正该削的是结果集，不是 Schema**。

**三、优化的收益对比**

| 优化项 | 效果 | 代价 |
|---|---|---|
| Schema 裁剪 Top-5 → Top-3 | 基线 4000 → 3700，整题输入 −1.8% | 召回可能变差 |
| 模型分级（60% 的调用走小模型，仅作用于基线输入） | 基线输入 6000 → 4200 token/题，日省 ≈ ¥2,700 | 路由复杂度 |
| **明细类占比 28% → 10%** | **结果集 51.3 亿 → 35.1 亿 token，每题输入 16,260 → 13,020（−20%），日省 ≈ ¥3,240** | **需产品侧引导 + 物化视图** |
| 用 LIMIT 截断替代下推 | 结果集 −17%（21,600 → 18,000 token/题） | **丢失分布，结论失真——不可接受** |
| 问题缓存（重复率 20%） | 日省 ≈ ¥3,850 | 需四元指纹正确 |

> **最后一行是最值得警惕的对照**：把下推换成截断，能省 17% 的 token——**代价是所有明细类问题的结论全部失真**。**任何以「牺牲结论完整性」换来的成本优化，在问数系统里都是负收益**，因为一次错误决策的损失远大于几个月的模型账单。

**四、存储**

| 指标 | 计算 | 结果 |
|---|---|---|
| 查询日志 | 50 万 × 5KB | ≈ 2.5 GB/天 |
| 审计记录 | 50 万 × 2KB | ≈ 1 GB/天（不可删） |
| 结果缓存 | 热 20% × 100KB | ≈ 10 GB |
| 向量索引 | 5000 表 × 40 列 × 1.5KB | ≈ 300 MB |
| 指标卡 | 200 指标 × 5KB | ≈ 1 MB |

**五、结论**

1. **上下文预算的大头是结果集（63%），不是 Schema（9%）**。Schema 裁剪是可行性需求，结果集下推才是成本主杠杆。
2. **瓶颈在数仓并发（360），不在 LLM QPS（44）**——数仓一侧必须先做资源组、队列与物化视图。
3. **明细类问题占比是最大的成本旋钮**：28% → 10%，每题输入 16,260 → 13,020 token，日省约 ¥3,240。但它需要产品侧引导（把明细需求转成聚合查询 + 物化视图），**不是纯技术能单方面解决的**。
4. **LLM 成本约 58 万元 / 月，在合理区间；而数仓计算成本通常更高**——明细查询一次扫 100GB，物化视图的收益要先于模型优化。
5. **必须先量「明细类问题占比」与「单次结果集行数分布」**——这两个参数决定上下文曲线的形状，只给 QPS 算不出结论。

### 23.4 工程落地与规则护栏

#### 23.4.1 端到端链路

```
客户端 / IM / 报表嵌入
  → API 网关（鉴权、租户、限流、配额）
  → Question Service（会话、澄清、意图分类、confirmed_slots）
  → Semantic Service（指标、维度、口径版本、作用域裁决）
  → Schema Retriever（域路由 → 表召回 → 列裁剪）
  → SQL Generator（指标卡 + 裁剪 Schema + Few-shot + 方言）
  → SQL Validator（AST → 语义 → 权限重写 → 资源改写 → 代价预估）
  → Query Executor（只读副本、资源组、超时、扫描量上限）
  → Result Guard（统计 + 样本分离、列裁剪、截断标注）
  → Result Validator（空值、一致性、异常、截断检测）
  → Chart Router / Attribution（贡献度在 SQL 里算完）
  → Answer Composer（结论 + 口径 + SQL + 注意事项，按信任分级）
  → Audit Service（改写前后 SQL、扫描量、返回行数，全量留痕）
```

> **图里最重要的两行是「权限重写」与「Result Guard」**：前者保证「查不到不该查的」，后者保证「带回来的不会撑爆模型，也不会被当成全量」。**这两行都必须在执行层，不能靠 Prompt。**

#### 23.4.2 接入层护栏

| 护栏 | 说明 |
|---|---|
| 鉴权 | 用户、租户、角色 |
| 限流 | 按用户 / 租户 / 接口三维 |
| 配额 | 每日查询数、扫描量、**单次回传 token** |
| 输入校验 | 长度、注入特征 |
| 敏感问题 | 拒绝或转人工 |
| 导出分流 | 明细导出在网关层即路由到独立审批链路 |

#### 23.4.3 语义层护栏

- 指标必须有 owner、版本、口径、适用范围、血缘。
- 变更走评审与灰度，保留历史版本与生效时间。
- Agent 不得自创指标；探索性公式标记为非标准。
- 口径冲突时按 §23.3.8 的固定顺序裁决，并注明版本与作用域。
- **指标定义变更须同步评审所有依赖的报表与看板。**
- `metric_id` 与名称分离，改名不改 ID。

#### 23.4.4 生成与校验护栏

| 阶段 | 护栏 |
|---|---|
| 生成 | 结构化输出、禁 `SELECT *`、强制时间过滤、**默认带聚合**、声明 `metrics_used` |
| 语法 | AST 解析 |
| 语句 | 仅只读 |
| 对象 | 表 / 列白名单 |
| Join | 连接条件校验 |
| 权限 | 行 / 列重写（**执行层强制**） |
| 资源 | 自动 LIMIT、扫描量上限 |
| 代价 | EXPLAIN 预估 |
| 指标 | 所用指标必须在语义层存在且版本匹配 |

#### 23.4.5 执行护栏

- 只读副本 / 独立资源组。
- Statement Timeout（简单 15s、复杂 60s）。
- **最大返回行数 10 万**。
- **最大扫描量 100 GB**。
- 并发上限 300 与队列（按复杂度分优先级）。
- 超资源 Kill。
- **权限服务故障时 fail-closed**：拒绝执行，不放行。

#### 23.4.6 结果集与回传护栏

方案见 §23.3.17，本节只列执行动作：

| 动作 | 规则 |
|---|---|
| 1 | 生成阶段已判定是明细类 → 强制走「统计 + 样本」模板 |
| 2 | 执行层统计行数、扫描量，超限即拒绝并给出建议改写 |
| 3 | 回传层按协议分离 `stats` / `histogram` / `top_groups` / `sample_rows` |
| 4 | 列裁剪：只保留最终答案会用到的列 |
| 5 | **截断即标注 `truncated: true`，并下调信任级别** |
| 6 | 明细导出 → 独立审批链路，不在本链路内完成 |

> 第 5 步是本章最容易被省略、也最不能省的一步。**截断标记缺失一次，就可能产生一个基于「前 100 行」的业务决策。**

#### 23.4.7 结果与解读护栏

- 结果校验不通过时，不下结论。
- 低置信度只给 SQL 与原始结果。
- 归因结论必须标注「相关 / 假设 / 待验证」。
- 禁止把相关系数直接表述为因果。
- **归因前先做结构校验（辛普森检查）**。
- 关键结论附口径与 SQL。
- **每条答案带数据截止时点与是否截断**。

#### 23.4.8 审计

| 记录 | 内容 |
|---|---|
| 谁 | 用户、租户、角色 |
| 何时 | 时间戳 |
| 问什么 | 原始问题、澄清轮次、已确认槽位 |
| 生成什么 | SQL、参数、**所用指标与版本** |
| 改写什么 | **改写前 SQL、改写后 SQL** |
| 查什么 | 表、列、行数、扫描量、耗时 |
| 返回什么 | 是否成功、返回行数、**是否截断** |
| 给了什么 | 结论、信任级别、注意事项 |

> **「改写前 SQL」必须留档**：它是证明「这条 SQL 本来会越权、是我们拦下来的」的唯一证据。**只留改写后的 SQL，等于没留审计。**

#### 23.4.9 降级矩阵

**本节是降级的权威版**，§23.5.6 只引用。

| 故障 | 影响 | 降级 | 用户看到什么 |
|---|---|---|---|
| LLM 不可用 | 无法生成 | 模板查询 / 保存问题 | 明确告知暂不可用 |
| 语义层不可用 | 口径无法保证 | **停止问数**（可查指标卡） | 明确告知口径服务不可用 |
| Schema 检索故障 | 选表不准 | 使用策展表集合 | 答案范围收窄 + 注明 |
| 数仓繁忙 | 查询排队 | 降低并发、缩小时间范围、提示稍后 | 排队提示 + 范围收窄 |
| 权限服务故障 | 无法判定权限 | **fail-closed，拒绝查询** | 明确告知无法校验权限 |
| 结果校验失败 | 结论不可信 | 只返回 SQL 与原始结果 | 无结论，只有数据 |
| **结果被截断** | **结论可能失真** | **标注截断 + 下调信任级别** | **明确的「部分结果」提示** |
| 指标版本冲突 | 口径不一致 | 列出候选让用户选 | 候选清单 |

> **「语义层不可用就停止问数」是最反直觉、也最正确的一条降级**。此时系统可以照常生成 SQL，但**它不知道「净营收」在你的组织里是怎么定义的**——此时给出的任何数字都是随机的。**宁可拒绝服务，不可给随机答案。**

#### 23.4.10 延迟预算与超时降级

**本表是唯一的延迟口径来源**，其他小节只引用。

| 阶段 | 预算（目标） | 超时上限（硬限） | 超时后的降级 |
|---|---|---|---|
| 接入与鉴权 | 50ms | 200ms | 429 / 登录提示 |
| 意图分类与路由 | 200ms | 800ms | 走模板问数 |
| 语义层与指标解析 | 100ms | 400ms | 用已缓存的指标卡；仍失败则拒答 |
| Schema 召回与裁剪 | 300ms | 1s | 退化为策展表集合 |
| SQL 生成 | 1.2s | 4s | 换小模型；仍超时走模板 |
| SQL 校验与重写 | 50ms | 200ms | 校验失败即拒绝执行 |
| **数仓执行** | **1.5s** | **15s**（复杂 60s） | 排队；超限改写范围 |
| 结果集治理与校验 | 200ms | 800ms | 只给原始结果，标注未校验 |
| 结论生成与解读 | 800ms | 3s | 只给 SQL 与原始结果 |
| **简单查询合计** | **< 5s（P95）** | 15s | — |
| **归因多步合计** | **< 30s（P95）** | 60s | 中途返回已完成的分解 |

> **预算是目标，超时是硬限，两者必须满足「超时 ≥ 预算」**。「简单查询 P95 < 5s」是用户可感知的承诺，「归因 P95 < 30s」是分析类问题的承诺，**两者不是同一个数**——原版把它们混在一张 SLO 表里，没有给出每一步的分解，**导致超时降级无从设计**。

#### 23.4.11 观测与压测

**指标**：

| 类别 | 指标 |
|---|---|
| 请求 | QPS、成功率、P95、澄清率、追问轮数分布 |
| 生成 | 有效 SQL 率、重试率、Schema 命中率、**指标版本匹配率** |
| 执行 | 查询耗时、扫描量、**返回行数分布**、超时率、排队时长 |
| **结果集** | **回传 token 占比、截断率、明细类问题占比** |
| 结果 | 空结果率、异常值率、复核率 |
| 解读 | **分歧率**、采纳率、改写率 |
| 安全 | 越权拦截、危险 SQL 拦截、PII、资源组越界 |
| 成本 | token、扫描量、缓存命中、单题成本 |

> **「结果集」这一类指标是本章特有的必看项**：`回传 token 占比` 告诉你成本花在哪，`截断率` 告诉你有多少答案在丢分布，`明细类问题占比` 告诉你成本曲线的形状。**它们比「token 总量」更能提前发现问题——token 总量是结果，这三个是原因。**

**压测**：

- 峰值 5 倍问题。
- **明细大结果集（120 万行）压测**，验证护栏是否真的拦住。
- 大表全扫描（验证扫描量上限）。
- 笛卡尔积（验证 AST 校验）。
- 数仓并发打满（验证排队与降级）。
- LLM 限流（验证模型分级与快路径）。
- 权限服务故障（**验证 fail-closed，不是 fail-open**）。
- **口径变更冲击**：改一个指标定义，验证缓存失效与版本标注。
- 注入与越权红队。

#### 23.4.12 规则护栏清单

| 领域 | 护栏 | 优先级 |
|---|---|---|
| **权限强制** | 行 / 列 / 租户 / 密级在执行层强制；敏感列不进入模型 Schema | **P0** |
| **危险 SQL 拦截** | AST 白名单，只读；DDL / DML / 多语句 / 危险函数 100% 拦截 | **P0** |
| **资源上限** | 超时 / 最大行数 / 最大扫描量 / 并发上限；到限即拒 | **P0** |
| **结果集完整性** | 截断必须标注；统计与样本分离；单次回传 ≤ 32K token | **P0** |
| **PII 与隐私** | 列级权限、入上下文与日志前脱敏、导出独立审批水印、留存期 | **P0** |
| **口径可追溯** | 每条答案带指标 ID + 版本 + 作用域 + 数据截止时点 | **P0** |
| **审计不可篡改** | 全量留痕，含**改写前后 SQL**、扫描量、返回行数、是否截断 | **P0** |
| **fail-closed** | 权限 / 语义层不可用时拒绝，而非放行 | **P0** |
| **归因规范** | 相关不表述为因果；归因前做结构校验；结论标注假设 | P1 |
| **评测** | EX 为主指标 + 口径正确率 + 分层黄金集 + 每次变更回归 | P1 |
| **缓存正确性** | 四元指纹（问题 + 权限 + 数据版本 + 语义层版本） | P1 |
| **自愈边界** | 自愈只改「怎么查」，不改「查什么」，不放宽权限 | P1 |
| 成本 | 单题 token 超预算 120% 触发容量评审 | P2 |

> **问数 Agent 的八个 P0 里有三个是「结果集」相关**（资源上限、结果集完整性、审计含返回行数）。这不是因为它最复杂，而是因为**它是唯一一个「错误会安静地变成一个数字」的架构**——越权会报错、超时会报错，**只有截断和口径漂移会笑眯眯地给出答案**。

#### 23.4.13 上线检查（10 问）

1. 所有指标是否都有标准表达式、owner、版本、作用域与血缘？`metric_id` 是否跨版本稳定？
2. Schema 裁剪是否能稳定命中正确表？域路由与 Top-K 是否经过实测？
3. AST 白名单是否覆盖所有危险语句？**权限是否在执行层强制，而不是写在 Prompt 里**？
4. 行 / 列权限是否覆盖全部可查表？敏感列是否已从给模型的 Schema 中移除？
5. 是否强制超时、返回行数、扫描量与并发上限？**这四个是否都配了 Kill 与排队**？
6. **结果集是否强制「统计 + 样本」？截断是否一定会被标注并下调信任级别？**
7. 报错自愈是否有上限？**自愈是否被限制在「只改怎么查、不改查什么」？**
8. 权限服务故障时是否 fail-closed？语义层不可用时是否停止问数？
9. 归因结论是否标注假设？**归因前是否做结构校验（辛普森检查）**？
10. 审计是否覆盖改写前后 SQL 与返回行数？口径变更时缓存是否失效？

### 23.5 典型案例与端到端解决

#### 23.5.1 案例：净营收环比下降归因

**问题**：「为什么本周净营收环比下降 12%？」

**链路**：

1. **澄清**：净营收口径（`net_revenue@v2.3`，财务口径，含税减退货冲减减折扣补贴）、本周 / 上周口径（自然周 W46 / W45，Asia/Shanghai）、范围（全公司还是某区域）。三个槽位一次问全，**不挤牙膏**。
2. **语义层**：`net_revenue@v2.3` 表达式解析；排除测试单、未结算单、内部单；时间口径到「数据截止 2026-11-24 06:00」。
3. **Schema 裁剪**：域路由到「交易域」→ 表召回命中 `orders` / `refunds` / `discounts` / `channel_dim` / `region_dim` → 列裁剪到 18 列。
4. **权限**：用户只看华东区 → 查询重写注入 `tenant_id = 42 AND region = 'east'`。
5. **SQL**：CTE 计算本期与上期净营收，**贡献度在 SQL 里算完**，只回传 Top-20 贡献行。
6. **执行**：发现华东区下降 18%，其中渠道 A 下降 30%，品类 X 退款率上升。
7. **自愈**：首次 SQL 用了错误的退款状态枚举，结果为空；用枚举样本修正为 `refund_status IN ('APPROVED','COMPLETED')` 后成功。
8. **输出**：折线趋势 + 贡献度柱状图 + 结论「主要来自华东区渠道 A 的品类 X 退货上升」。

**贡献度下推的 SQL**（这是本章方法论最关键的一段代码）：

```sql
WITH base AS (
  SELECT o.region, o.channel, o.category,
         SUM(o.paid_amount) - SUM(r.refund_amount) - SUM(d.discount_amount) AS net_revenue
  FROM orders o
  LEFT JOIN refunds r
         ON r.order_id = o.order_id
        AND r.refund_status IN ('APPROVED','COMPLETED')
  LEFT JOIN discounts d ON d.order_id = o.order_id
  WHERE o.tenant_id = 42
    AND o.region = 'east'
    AND o.stat_date BETWEEN '2026-11-10' AND '2026-11-23'
  GROUP BY o.region, o.channel, o.category
),
cur  AS (SELECT * FROM base WHERE stat_week = 'W46'),
prev AS (SELECT * FROM base WHERE stat_week = 'W45'),
contrib AS (
  SELECT c.region, c.channel, c.category,
         c.net_revenue - p.net_revenue AS delta,
         SUM(c.net_revenue - p.net_revenue) OVER () AS total_delta
  FROM cur c JOIN prev p
    ON c.region = p.region AND c.channel = p.channel AND c.category = p.category
)
SELECT region, channel, category, delta,
       delta / NULLIF(total_delta, 0) AS contrib_pct
FROM contrib
ORDER BY ABS(delta) DESC
LIMIT 20;
```

> **这段 SQL 的价值不在语法，在它把「哪几行贡献最大」变成了数据库的一次排序**。如果让模型把 960 行（8 地区 × 6 渠道 × 20 品类）全拿回来自己算贡献度，回传 17.3 万 token；用这个写法，**数据库算完只回传 20 行 = 3,600 token，省 48 倍**，而且**排序是精确的**——模型在小样本上排序会出错，在全量上排序则根本做不到。
>
> **这就是「下推」的通用范式**：**凡是「对结果集的全体做一次计算」的步骤，都应该下推到 SQL，而不是把结果集交给模型。**

**结论表达**：

```
本周净营收环比 -12%（口径：net_revenue@v2.3 财务口径，排除测试单/未结算）
数据截止 2026-11-24 06:00 · 已按租户与区域权限过滤 · 结果未截断

华东区贡献 -8.1pct，其中渠道 A 贡献 -5.4pct
渠道 A 下品类 X 退款率由 3.1% 升至 6.8%

可能原因（待验证）：X 品类批次质量问题
注意：本次归因为相关关系，非因果结论
```

#### 23.5.2 变体 A：自助取数

**问题**：「昨天各渠道订单量」

- 无需澄清，命中标准指标 `order_count`，**无多口径**。
- Schema 只需 `orders` + `channel_dim`。
- 生成单表聚合 SQL（带 `GROUP BY channel`）。
- 结果形状：分类对比 → 柱状图。
- **结果集 8 行**，无放大问题，直接给结果 + SQL + 口径。

> **快路径是这个系统的主路径**：像这样的问题应当走「意图分类 → 直接生成 → 校验 → 执行」，**全程不超过 5s，不做任何 Schema 深度检索与多步分析**。问数系统能不能上线，取决于这条路径的延迟与准确率，而不是归因能力。

#### 23.5.3 变体 B：多轮澄清

**问题**：「最近销售额怎么样？」

- 「最近」不明确 → 追问时间范围。
- 「销售额」有歧义 → 提供 `gmv` / `net_revenue` 两个候选（**两个都是标准指标，不自创**）。
- 用户确认后写入 `confirmed_slots`。
- 后续追问复用已确认口径，**不再重复问**。

**澄清决策**：

```
澄清一次的成本（实测）
  2,000 token（≈ ¥0.004） + 1.5s + 一次用户耐心
  vs
错误答案的成本
  ≥ 1 人天复核 + 决策损失 + 信任损失（不可逆）
→ 追问

但：追问上限 1 次（同一问题），追问 2 次以上 → 直接给候选列表或转人工
```

**原则**：澄清成本低于错误成本时追问；否则用默认值并显著注明。**口径类问题几乎总是「追问」——因为默认值错误的代价太高。**

#### 23.5.4 变体 C：权限受限

**问题**：「全公司各区域营收」

- 用户仅有华东权限。
- 查询重写注入 `tenant_id = 42 AND region = 'east'`。
- **答案明确说明「仅展示您有权限的华东区域」**——不能默默只给一个区域，让用户误以为是全公司。
- 审计记录**改写前 SQL 与改写后 SQL**。

> **权限过滤后必须在答案里说出来**，否则用户会把「华东」当成「全公司」，得出「其他地区营收为 0」的错误结论。**被过滤掉的维度，必须以「不可见」的形式出现在答案里。**

#### 23.5.5 变体 D：明细查询与结果集放大

**问题**：「上周华东区所有订单明细，看一下金额分布」

**症状**：系统按字面理解，生成一条明细 SQL，回传 120 万行。

**处置**：

| 步骤 | 动作 |
|---|---|
| 1 | 识别为**明细类**问题，但诉求里含「分布」——分布是聚合概念 |
| 2 | **改写问题**：金额分布 = 直方图 + 分位数，不是明细列举 |
| 3 | 一次 SQL 同时返回统计与样本 |
| 4 | 回传 `stats` / `histogram` / `sample_rows`（100 行） |
| 5 | 图表用 `histogram`（**来自 SQL 聚合，不是前端拿样本现算**） |

**一次 SQL 同时出统计与样本**：

```sql
SELECT
  COUNT(*)                                   AS row_count,
  SUM(paid_amount)                          AS total_amount,
  AVG(paid_amount)                          AS avg_amount,
  PERCENTILE_APPROX(paid_amount, 0.5)       AS p50,
  PERCENTILE_APPROX(paid_amount, 0.9)       AS p90,
  PERCENTILE_APPROX(paid_amount, 0.99)      AS p99
FROM orders
WHERE tenant_id = 42 AND region = 'east'
  AND stat_date BETWEEN '2026-11-10' AND '2026-11-16';

SELECT FLOOR(paid_amount / 100) * 100 AS bucket, COUNT(*) AS cnt
FROM orders
WHERE tenant_id = 42 AND region = 'east'
  AND stat_date BETWEEN '2026-11-10' AND '2026-11-16'
GROUP BY 1 ORDER BY 1;

SELECT order_id, paid_amount, stat_date, channel
FROM orders
WHERE tenant_id = 42 AND region = 'east'
  AND stat_date BETWEEN '2026-11-10' AND '2026-11-16'
LIMIT 100;
```

**效果对比**：

| 方案 | 回传 token | 分布完整 |
|---|---|---|
| 明细直返 + `SELECT *` | **21.6 亿** | 完整但不可行 |
| `LIMIT 100` 截断 | 1.8 万 | **不完整**（P99 变成前 100 行的 P99） |
| **统计 + 直方图 + 样本 100** | **2.16 万** | **完整** |

> **这就是本章核心方法论的一次实地验证**：省 token 靠下推，保结论靠下推，**两者是同一件事**。任何用「截断」换 token 的方案，都是在用一个 16% 的成本节省，去换一个「P99 算错」的隐性损失。

#### 23.5.6 故障与兜底

降级矩阵以 §23.4.9 为准，本例补充三条：

| 故障 | 影响 | 兜底 |
|---|---|---|
| SQL 报错 | 无结果 | 回填报错自愈，最多 3 次，且不越过自愈安全边界 |
| 结果为空 | 可能是过滤错 | 区分无数据 / 条件错，触发澄清 |
| **结果被截断** | **结论可能失真** | **标注 `truncated: true` + 下调信任级别 + 给出「下载完整结果」的路径** |

#### 23.5.7 扩容 10 倍，哪里先坏？

以 §23.3.24 的基准放大 10 倍（日 500 万问题、峰值 290 QPS、LLM 调用 440 QPS、并发查询 3600）：

| 顺序 | 先坏的点 | 现象 | 触发指标 | 对策 |
|---|---|---|---|---|
| 1 | **数仓并发** | 排队、超时 | 并发 > 300 配额 | 队列、资源组、物化视图 |
| 2 | **扫描量与成本** | 日扫描量与账单飙升，查询被拒 | 日扫描量 > 预算 | 物化视图、结果缓存、查询预算 |
| 3 | LLM 配额 | 429 | 调用 QPS > 配额 80% | 模型分级、缓存、限流 |
| 4 | Schema 检索 | 选表不准 | Top-5 命中率下降 | 分层索引、域路由 |
| 5 | 语义层维护 | 口径冲突 | 指标变更积压 | 治理流程、版本 |
| 6 | 审计存储 | 增长快 | 磁盘水位 > 70% | 分层、归档 |
| 7 | **成本（非线性）** | 账单涨幅 > 流量涨幅 | 单题 token > 预算 120% | 治理明细占比、下推、模型分级 |

> **第 2 与第 7 位是本章特有的非线性**。大促期间明细诉求激增，明细类问题占比从 28% 升到 45%：
>
> - **扫描量**：聚合查询约扫 1GB、明细约扫 8GB → 日扫描量从 1.33 PB 涨到 1.93 PB，**涨 45%，而流量只涨 10%——放大 4.5 倍**。
> - **token**：结果集回传从 10,260 涨到 13,320 token/题（+30%），总输入 token 从 16,260 涨到 19,320（**+18.8%**）。
>
> **容量评审必须按「明细类问题占比右移」后的口径算，而不是简单乘 10。** 只乘 10 的评审，会在第一个大促就把数仓和账单一起打爆。

#### 23.5.8 取舍复盘

| 决策 | 代价 | 收益 | 重新评估条件 |
|---|---|---|---|
| 语义层优先 | 建设成本高 | 口径可信 | 指标少时可轻量 |
| 只读沙箱 | 资源成本 | 安全隔离 | 专用集群可合并 |
| 查询重写 | 实现复杂 | 权限强约束 | 视图层完善后可简化 |
| 强制引用 SQL | 体验略重 | 可追溯 | 管理层摘要可折叠 |
| 结果缓存 | 一致性风险 | 成本下降 | 实时性要求提高 |
| 归因标注假设 | 结论不够「干脆」 | 避免误导 | 高置信场景可简化 |
| **默认聚合而非默认明细** | 用户要多点一次 | 结果集可控、结论完整 | 明细诉求常态化后评估 |
| **下推优先于截断** | SQL 更复杂、开发更慢 | 结论不失真、成本可控 | 引擎算力能力足够时才考虑更多下推 |
| **四元缓存指纹** | 缓存命中率略降 | 不给过期 / 越权答案 | 数据版本机制成熟后可简化 |
| **导出独立成链** | 用户多一步审批 | 结果集与合规可控 | 内部可信场景可合并 |

### 23.6 闭环演进与常见误区

#### 23.6.1 演进路线

| 阶段 | 形态 | 触发条件 | 关键改造 |
|---|---|---|---|
| L0 | 固定报表 | 起步 | BI 工具 |
| L1 | 模板问数 | 参数化需求多 | 模板 + 参数 |
| L2 | NL2SQL | 长尾取数 | Schema 检索、生成 |
| L3 | 语义层 + 权限 | 口径 / 安全问题 | 指标卡、重写、沙箱 |
| L4 | 归因与建议 | 分析需求 | 多步分析、贡献度 |
| L5 | 主动洞察 | 成熟 | 订阅、异常推送 |

> **L2 → L3 是最关键的一次跨越，也是最容易被跳过的**。很多系统停在 L2（NL2SQL 直连数仓），然后被两类问题逼回 L3：**口径问题**（同一个「营收」两个部门算出两个数）和**安全问题**（模型把租户条件漏掉了）。**这两类问题都不会自己消失，只会在规模变大后变得更频繁。**

#### 23.6.2 指标体系

| 层级 | 指标 | 用途 |
|---|---|---|
| 正确 | EX、有效 SQL 率、EM、**口径正确率** | 判断生成质量 |
| 体验 | 采纳率、追问率、P95、**分歧率** | 判断可用性 |
| 安全 | 越权 / 危险 / PII 拦截 | 判断风险 |
| **结果集** | **回传 token 占比、截断率、明细类占比** | **判断成本与结论完整性** |
| 成本 | token、扫描量、缓存命中 | 判断可持续 |
| 治理 | 口径一致率、指标覆盖率、变更积压 | 判断语义层质量 |

#### 23.6.3 评测与回归

- 黄金集覆盖：单表、多表 Join、嵌套聚合、时间窗口、权限、归因、**明细类**、**口径冲突**。
- 每次模型 / Prompt / 语义层 / 引擎变更跑回归。
- 在线 A/B，**护栏指标优先**（越权、错误结论、截断未标注）。
- 每周复盘 Top 错误，沉淀到 Few-shot 与 Schema 描述。
- **口径变更专项回归**：改一个指标定义，验证历史黄金集用新版本重跑后的差异可解释。

#### 23.6.4 成本优化

**分两条轨道，不排成一条队**：

**轨道一：上下文 token 侧**（省模型账单）

| 顺序 | 手段 | 收益 | 备注 |
|---|---|---|---|
| 1 | **结果集下推** | 63% 的输入 token 都在这里 | 最大杠杆 |
| 2 | 问题 / SQL 缓存 | 约 20%（取决于重复率） | 需四元指纹正确 |
| 3 | 模型分级 | 约 14% | 意图 / 简单 SQL 走小模型 |
| 4 | 早停 | 约 8% | 置信度高不重试 |
| 5 | Schema 裁剪 | 约 2% | 同时是可行性刚需 |

**轨道二：数仓计算侧**（省扫描量账单）

| 顺序 | 手段 | 收益 | 备注 |
|---|---|---|---|
| 1 | **物化视图** | 同时降扫描量与结果集行数 | **数仓侧收益通常超过模型侧** |
| 2 | 结果缓存 | 重复问题不再扫库 | 四元指纹必须正确 |
| 3 | 查询预算 | 防止单租户吃满 | 按用户 / 租户配额 |

> **「省 token」不等于「降成本」**。物化视图虽然一分钱 token 都不省，但它同时降低扫描量与数仓成本，而**扫描量通常才是问数系统真正的大头**（本章基准：日扫描 1.33 PB vs 日模型账单 ¥1.93 万）。**两条轨道分开算，不要合并成一个排行榜。**

#### 23.6.5 产品对比

| 产品 / 形态 | 核心 | 优势 | 局限 |
|---|---|---|---|
| 传统 BI | 拖拽报表 | 稳定、可控、零幻觉 | 长尾覆盖差 |
| 指标平台 | 指标治理 | 口径统一 | 不解决自由提问 |
| NL2SQL Agent | 自然语言取数 | 覆盖长尾 | 口径 / 权限 / 结果集风险 |
| 数据搜索 | 关键词找表 | 发现数据 | 不做分析 |
| 通用 LLM + DB | 直接生成 SQL | 灵活 | 安全 / 口径 / 资源全弱 |
| **问数 Agent（本章形态）** | **语义层 + 生成 + 校验 + 解读** | **口径可信、可审计、结果可控** | **建设成本高、依赖语义层成熟度** |

#### 23.6.6 常见误区

| 误区 | 问题 | 正确做法 |
|---|---|---|
| 只做 Text-to-SQL | 口径不可控 | 语义层优先 |
| 让模型自由写 SQL | 危险 / 越权 | AST 白名单 + 沙箱 |
| 权限靠 Prompt | 可被绕过 | 查询重写 / 视图 |
| 不做 AST 校验 | 注入风险 | 解析 + 白名单 |
| 不限制资源 | 打爆数仓 | 超时 / 行数 / 扫描量 |
| 不做口径说明 | 结论不可信 | 附口径与版本 |
| 相关当因果 | 误导决策 | 标注假设 + 结构校验 |
| 只评 EM | 忽略结果正确 | EX + 口径正确率 |
| 不做失败沉淀 | 重复犯错 | 错误样本库 |
| 忽略 Schema 大小 | 选错表 | 裁剪 + 域路由 |
| 不做缓存 | 成本高 | 四元指纹缓存 |
| 不做审计 | 无法追责 | 全量记录 + 改写前后 SQL |
| **用截断控制上下文** | **结论失真且静默** | **统计下推 + 样本分离** |
| **把 Schema 裁剪当成本优化** | **打错靶子** | **结果集才是大头（63%）** |
| **明细导出混在问数链路** | **结果集与合规失控** | **独立审批链路** |
| **口径冲突时默认选一个** | **安静地产出错误数字** | **列候选让用户选** |
| **只留改写后的 SQL 审计** | **无法证明拦截生效** | **前后都留** |

#### 23.6.7 高频追问

- **如何防止模型编造指标？** → 语义层固化指标，Agent 只能引用标准定义；生成阶段声明 `metrics_used`，执行前核对版本；SQL 与结果可追溯。
- **如何防止危险 SQL？** → AST 白名单 + 只读资源组 + 超时 / 行数 / 扫描量限制 + EXPLAIN 代价预估。
- **如何保证行 / 列权限？** → 查询重写 / 视图 / 策略层强制，不靠 Prompt；敏感列不进入模型 Schema。
- **SQL 生成错了怎么办？** → 报错回填 + 最大重试 2–3 次 + 失败样本沉淀；**自愈只改「怎么查」，不改「查什么」**。
- **Schema 太大怎么办？** → 域路由 + 语义检索 + 关键词 + Join 历史 + 列裁剪，只暴露 Top-K。
- **结果集太大怎么办？** → 统计下推到 SQL + 样本替代全量 + 列裁剪；**不要靠截断**。
- **如何评估问数 Agent？** → 执行准确率为主 + 口径正确率 + 在线采纳率与分歧率 + 安全测试。
- **如何做归因？** → 同比环比 + 维度下钻 + 贡献度拆解（**贡献度在 SQL 里算**）；结论标注假设并做结构校验。
- **如何控制成本？** → 先下推结果集，再物化视图，再模型分级，再缓存；先削大头。
- **口径冲突怎么办？** → 指标版本 + 作用域 + 固定裁决顺序 + 答案注明；判不了就列候选。
- **多轮如何不重复问？** → `confirmed_slots` 保存已确认口径。
- **如何防止提示注入？** → 问题文本作为数据、结构化输出、规则与判定在代码层。
- **如何保证结果可信？** → 结果校验 + 二次核对 + 截断标注 + 低置信不下结论。

#### 23.6.8 答题提纲与练习

**10 分钟版（自述型）**：

| 时间 | 内容 |
|---|---|
| 0–1 min | 澄清：问题量、**问题类型分布与明细占比**、数据规模、权限模型、时效 |
| 1–3 min | 容量：QPS、LLM 调用峰值、数仓并发、**上下文 token 结构（结果集占 63%）** |
| 3–5 min | 架构：语义层 → Schema 裁剪 → 生成 → 校验重写 → 沙箱 → 结果集治理 → 解读 |
| 5–7 min | 权限、结果集下推、审计 |
| 7–9 min | 深挖一个点（推荐：结果集放大 / 权限强制） |
| 9–10 min | 安全护栏、降级、评测 |

**35 分钟版（深聊型）**：

| 时间 | 内容 |
|---|---|
| 0–5 min | 澄清与七锚点：规模、**明细占比**、权限模型、口径现状、不可逆清单 |
| 5–14 min | 容量与成本（含结果集 63% 占比的推导、扫描量的非线性） |
| 14–22 min | 架构与数据流：语义层 / Schema 裁剪 / 生成 / 校验重写 / 沙箱 / 结果集治理 / 解读 |
| 22–26 min | 数据模型与 API：指标卡（含版本与作用域）、审计、缓存四元指纹 |
| 26–34 min | 深挖三个点（各约 3 min）：① 结果集放大与下推 ② 权限强制与 fail-closed ③ 口径治理与分歧率 |
| 34–35 min | 演进阈值、安全护栏、评测闭环 |

**练习**：

1. 设计日 50 万问题的问数 Agent，给出完整链路与容量（**必须包含结果集 token 的估算**）。
2. 设计 Schema Linking 方案，要求 Top-5 命中率 > 90%，并给出裁剪前后的 token 对比。
3. 设计行 / 列权限的强制执行方案，并说明权限服务故障时为什么必须 fail-closed。
4. 设计 SQL 自愈与失败样本沉淀机制，**并给出自愈的安全边界**。
5. 设计归因分析流程，避免相关当因果，**并说明如何避免维度爆炸**。
6. 计算：日 50 万问题、每题 1.5 次调用、基线输入 4000、输出 500；聚合类 42% 回传 20 行、明细类 28% 回传 120 行、分析类 30% 回传 50 行；单行 180 token；输入 ¥2/百万、输出 ¥8/百万——每天多少 token、多少钱？**结果集占输入的百分之几？**
7. 计算：若明细类占比从 28% 升到 45%（大促），日扫描量与日 token 分别涨多少倍？为什么容量评审不能简单乘 10？
8. 设计「答案数字看起来正常但实际是过期数据」的排查路径。

#### 23.6.9 一页纸作战手册

**S0 定题**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 落七锚点 | 唯一事实源是什么？哪几个决策不可逆？ | 7 项写下来，事实源 = 指标卡 + SQL + 查询日志 + 审计 |
| 定优先级 | 口径、权限、成本冲突时保谁？ | 权限 > 口径 > SQL > 结果完整 > 体验 > 成本 |
| **量两个参数** | **明细类问题占比？单次结果集行数？** | **各给一个带来源的数值** |

**S1 建模**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 分层 | 每层只做什么、明确不做什么？ | 澄清 / 语义 / Schema / 生成 / 校验 / 执行 / 结果集 / 解读八层职责表 |
| 定口径 | 冲突怎么裁决？ | 固定裁决顺序 + `metric_id` 稳定 + 版本与作用域入答案 |
| 定事实源 | 哪些不可重建？ | 指标卡、元数据、查询日志、审计是事实源；缓存与索引是投影 |

**S2 决策**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 选路径 | 快慢路径怎么分？ | 命中标准指标走快路径（P95 < 5s）；归因走慢路径（< 30s） |
| 选下推策略 | 明细怎么返回？ | 统计 + 样本分离；**禁止用截断替代下推** |
| 选权限形态 | 强制在哪一层？ | 策略层 / 视图 > 查询重写 > 应用层；Prompt 不算 |

**S3 论证**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 算并发 | 数仓扛得住吗？ | 峰值 29 QPS → 约 360 并发查询，配额 300 |
| 算 token | 钱花在哪？ | 日 85 亿 token、约 ¥1.93 万；**结果集占输入 63%** |
| 算扫描 | 数仓账单呢？ | 日 1.33 PB；明细占比 28% → 45% → 扫描涨 45% |
| 算质量 | 怎么知道变好了？ | EX 为主 + 口径正确率 + 分歧率 |

**S4 兜底**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 写延迟预算 | 每一步各多少？ | 9 阶段预算 + 硬限（§23.4.10） |
| 写降级矩阵 | 每个依赖挂了用户看到什么？ | 8 类故障各有行为；**语义层挂了就停问数；权限挂了 fail-closed** |
| 定护栏 | 安全排第几？ | 权限 / 危险 SQL / 资源 / 结果集 / PII / 口径 / 审计 / fail-closed **八项 P0** |

**S5 闭环**

| 动作 | 自检问题 | 合格线 |
|---|---|---|
| 定演进阈值 | 涨 10 倍哪里先坏？ | 数仓并发 → 扫描量 → LLM 配额（§23.5.7） |
| 定指标 | 技术好了业务就好了吗？ | 采纳率必须与分歧率、复核率合看 |
| 建复盘闭环 | 行动项有负责人吗？ | 行动项 → 负责人 → 验证结果 |
